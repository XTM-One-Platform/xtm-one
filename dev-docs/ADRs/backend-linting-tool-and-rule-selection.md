# ADR Linting Tool and Rule Selection in XTM One Python Backend

Status: Approved
Scope: `backend/`
Reviewed in refinement: 2026-04-30, 2026-05-05

## Context

The XTM One backend needs a documented linting baseline before broader hardening work, CI enforcement decisions, and expected open-source exposure.

The backend is a large Python codebase centered on FastAPI, asynchronous execution, network-facing integrations, background workers, typed models, and increasing use of AI-generated code. In that context, linting policy is not only a formatting choice. It affects security posture, maintainability, refactoring cost, and trust in automated code review.

The team reviewed the backend Ruff rule matrix and its per-rule rationales in working sessions on April 30, 2026 and May 5, 2026. The review focused on:

- which rule families are relevant to the backend's actual stack
- which rules are high-signal enough to keep
- which rules should stay disabled because they are unstable, low-signal, or out of scope
- how linting priorities relate to security hardening and future CI enforcement

NOTA BENE : This ADR covers linting tool choice and rule selection for the Python backend. It does not decide the Python type checker, the broader testing strategy, package-audit policy such as `pip-audit`, penetration testing, prompt-security validation, or the exact CI rollout mechanism for staged enforcement.

## Decision

The team adopted Ruff as the standard linting tool for the Python backend.

The team also adopted a stable, high-signal Ruff baseline aligned with the backend's architecture and risk profile. The approved baseline favors:

- correctness rules
- security rules
- FastAPI-specific rules
- async-safety rules
- typing and import-hygiene rules
- naming and maintainability rules
- modernization rules
- documentation and pytest hygiene rules when they provide clear signal

The approved baseline is intentionally selective. It does not try to maximize the total number of enabled rules. Rules are enabled only when they fit the backend's current stack and provide durable value.

Preview rules are rejected from the approved baseline.

Removed Ruff rules are not part of the approved baseline.

Rules tied to technologies not used by the backend stay disabled, including families or subsets related to:

- Airflow
- Django
- NumPy
- pandas
- stub-only `PYI` rules
- Trio-only async checks
- other framework- or ecosystem-specific checks that do not match the backend stack

The team explicitly reintroduced the previously excluded stable rules:

- `S307`
- `RUF001`
- `RUF002`
- `RUF003`
- `RUF006`
- `RUF012`

Appendix A, is the detailed source of truth for the approved per-rule selection and rationale.

## Rationale

Ruff was chosen because it provides one fast, consolidated entry point over a large part of the Python linting ecosystem, including correctness, import hygiene, security, modernization, documentation, and framework-specific checks. Using one main linting tool reduces tool sprawl, configuration drift, and duplicated maintenance effort.

The team rejected an "enable everything" strategy because the backend is not served by blanket rule maximization. Some Ruff rules are excellent fits for a typed, async, FastAPI-based backend. Others are tied to unused frameworks, stub files, or debatable micro-style preferences that would add churn without improving reliability.

Preview rules were rejected because the team wants the approved baseline to be stable. During review, the team explicitly considered the risk that preview rules can change semantics, generate false positives, disappear, or silently stop providing expected coverage across Ruff upgrades. Stable rules can support CI policy; preview rules were considered too unstable for that role.

Security rules were prioritized because the backend is network-facing and belongs to a cybersecurity product. The team agreed that stable security lint rules are a necessary baseline for preventing avoidable regressions in ordinary application code, even though linting does not replace broader security testing.

Rules for unused stacks remain disabled to preserve signal quality. A baseline that flags Airflow-, Django-, pandas-, or stub-specific patterns in a backend that does not use those technologies would create noise and weaken trust in the lint output.

## Consequences

Implementing this decision gives the backend one documented linting tool and one explicit rule-selection policy. It aligns the baseline with FastAPI, async execution, security concerns, typing, modernization, and maintainability, and it gives future code review and CI work a review-backed policy instead of ad hoc exceptions.

Selecting rules does not, by itself, make the current backend architecture clean or solve deeper design issues.

## Alternatives Considered

Multiple specialized linters instead of Ruff were considered, especially well-established tools such as Pylint and Flake8, and rejected because they increase configuration sprawl, slow feedback, and split rule ownership across too many tools. In addition, since there is no current need for custom plugins or project-specific lint rules, their customization advantages do not outweigh the cost of using several tools and their slower execution.

Enabling preview rules in the approved baseline was considered and rejected because preview rules are unstable by definition and were explicitly considered too risky for a stable backend policy.

Enabling all Ruff rules by default was considered and rejected because the backend does not use every framework Ruff knows about, and many rules would create noise rather than value.

Restricting linting to formatting and a minimal correctness subset was considered and rejected because the backend needs stronger coverage for security, async behavior, typing discipline, import hygiene, and framework correctness.
