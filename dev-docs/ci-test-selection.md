# CI test selection

A pull request runs the static checks of `ci.yml`, the ROI ledger's invariants, the built-in tool schema budget (`tests/test_builtin_tool_groups.py`, job `tool-schema-budget`, #1625: a description past its ceiling is red on the pull request, not ejected from the queue), the frontend's catalog tests (`src/i18n/`) and its build (about a minute). The merge queue runs the suites, but only what the merge group's change reaches: each of `ci.yml` and `e2e.yml` starts with a `select` job that calls `backend/tests/selection.py` on the group's own change (`merge_group.base_sha..sha`, every pull request batched in it) and sizes the other jobs from its answer. Measuring each group from the one ahead of it is safe because the queue merges only non-failing pull requests (the `Merge queue` ruleset's `grouping_strategy: ALLGREEN`): a pull request merges only once its own group passes, and the groups behind a failed one are rebuilt without it. Under `HEADGREEN` a group's pass would merge the pull requests ahead of it on its own change's tests alone: switch the diff to `main`'s tip first. Every other event - the nightly run on `main`, a manual run, a push to `main` - runs everything, and the nightly run opens an issue when it fails (`notify-on-failure`): it is the full pass that catches what the rules below cannot see.

The `Test selection` and `E2E selection` jobs write a table to their summary: what runs, and why.

Before a push, the sandbox check `backend-queue-tests` (`backend/scripts/queue_tests.py`) runs the same backend selection on a checkout's change: it prints each selected test file with its reason and runs the ones the queue's unit job runs, so a pull request green on its static checks does not turn red in the queue first. Only the changed files under `backend/` reach it; args `["--list"]` prints the selection without running it. It runs pytest with `--continue-on-collection-errors`: on a narrow checkout a selected module that cannot be imported (a frontend fixture outside `sub_paths`) is reported as a collection error and the exit stays non-zero, but the other selected files still run. The selection runs as the queue's unit job runs it: up to 4 pytest-xdist workers with `--dist loadgroup` and the 300 s stall guard (`PYTEST_STALL_SECONDS`). The script prints the seconds the selection weighs (`tests/shard_durations.json`); a selection over 900 s of one worker is not run in one call: the script names the parts and exits 3, and args `["--part", "i/n"]` run one share each (dealt out by `tests.sharding.shard_files`), `["--budget", "0"]` the whole selection at once.

## Backend (unit, integration, Browser tool)

A test file runs when the change reaches it through the source:

- **Imports.** A module reaches what it imports as it loads, at any depth (a package `__init__` included). An `app` function's own import counts one step, from a changed module only: followed further, the one function that imports `app.main` would put every module in every closure. A test file, or a helper of `tests/`, reaches everything it imports, at module level or in a test, and every dotted name it writes as a string (`mock.patch("app.x.y")`). `scripts/` is in the graph: a test that imports a script (`tests/test_hitl_whitelist_snapshots.py`) reaches what the script imports. Code that runs at import - a Pydantic schema, a constant, a registry - is reached the same way; a coverage map would miss it, its lines running during collection under no test.
- **The test itself** when the change adds or edits it, and the **test walkers** (`glob("test_*.py")`: `tests/test_evaluation_guards.py`) when the change adds, edits or deletes a test file.
- **Tree readers** whenever a `.py` file of `app/` changes, deletions included: a file that reads `app/` through `tests/app_sources.py`, a package walk or `import_module`, or that lists a directory it names `app` (`APP.rglob("*.py")`, `Path(app.__file__).rglob`, the egress and other source tripwires).
- **Path readers.** Any changed file, a module included, selects the tests that write its name as a path piece: a tripwire reads a module's source by its path (`tests/test_agent_copy_manifest.py` reads `agent_import.py`). A file outside `backend/app` also selects the tests that write its area (`frontend`, `.github`, `docs`, `alembic`, a data directory of `tests/`; not `tests` itself, which every test writes in its imports). A data file of `app/` (seed data, templates) reaches the modules that name it or a directory above it, and the tests that name its own directories up to the package holding them (`agent_persona`, `seed_data`: the tests that glob the seeded personas).
- **Repository readers** (`git ls-files`: `tests/test_repo_text_hygiene.py`) on every change.
- **A package's Markdown** (`AGENTS.md`, `copyright.md` beside its modules) reaches only a module of that package that writes its name in a string, and the tests that name it: it documents the package, no module reads it.
- **A deleted module** selects what still names it in an import.

The whole suite runs when the change touches what every test runs under: a `conftest.py` and the helpers of `tests/` it loads at any depth (`frozen_clock.py`, `redis_unreachable.py`, `stall_guard.py`: an autouse fixture applies them to tests that never import them), `pyproject.toml` / `uv.lock`, `selection.py` / `sharding.py` / `marked_files.py`, `ci.yml` or the backend-venv action. So does a data file of `app/` no module names, and a backend file the graph cannot parse. A change to `alembic/`, `app/models/` or the database setup runs the integration suite whole. The autouse fixtures of `conftest.py` also import `app` modules whose state they reset; a test that reads that state imports the module too, so a change that breaks the reset reaches it.

`tests/test_selection.py` pins each rule on a small tree and, on the real one, each tripwire a review found unselected for the file it guards (`test_a_tripwire_runs_when_what_it_guards_changes`): a rule that loses one fails there, not after a merge.

The jobs read the selection through `PYTEST_SELECTED_FILES` (a list of test files; `tests/conftest.py`). A file it lists that does not exist stops the run; a job that collects nothing from it passes (a unit shard dealt only integration files). A selected suite takes its share of the shards: the unit suite one shard per ~17 minutes of one worker's tests (about five minutes a shard), a file marked `integration` or `chromium` as a whole (`pytestmark`) left out of the count (by the run's shard weights, below; four workers a job, at most eight), the integration suite (at most four) in proportion to its files, and the Browser tool (at most five: its tests run one at a time) in proportion to its seconds. A suite the change does not reach skips, and `CI verdict` reads a skipped job as passed.

Replayed over `main`'s last 60 merges (18 Nov 2026, timed on the queue's own runs of that day), a merge group runs a median 32% of the unit suite (75th percentile 54%), 54 of the 60 end under ten minutes (median 8, against 12 to 13.5 when every job ran) - the other six change the migration chain, whose job takes about 11 - and the runner time halves. The path, script, test-walker and conftest rules above cost nothing measurable: replayed on 19 Nov over the 60 merges before it, with and without them, the median group (8 minutes) and the groups under ten (55) stay the same. Of the queue runs that failed in the same days, every failure a group's own change caused is in its selection; the others - `main` already red, a flaky a2a spec, a group stacked on a failing one - would no longer eject a pull request that did not cause them.

## Migrations, frontend

- **Migrations (Alembic)** runs when the change touches what the chain runs: `alembic/`, the models, the dependencies and the actions that install them, `selection.py` (`MIGRATION_INPUTS`), or an `app` module the chain loads - what `alembic/` imports anywhere in a file (`app.core.migration_ddl` in a migration's `upgrade()`), `app.core.migrations` (the job calls `run_migrations()` itself), what those load at import, then one step of what their functions import, with what that loads: a function may run during the import (`Settings()`'s validators import `app.core.url_identity`), and `run_migrations()` imports `app.core.index_maintenance` (`migration_chain_modules`, about a quarter of `app`). Otherwise the chain is `main`'s, which passed.
- **Frontend (TypeScript)** (the build and the design-system guards, about 40 seconds) runs on every pull request, and in the queue when `frontend/` or `selection.py` changes.
- **Frontend unit tests** run `vitest related` on one shard: the tests that import a changed file of `src/` or `tests_unit/`, plus the vitest files and their helpers (`src/testing/`) that read a changed file from disk (an `fs` import, and the file's name or directory in a string literal - a comment or a test title names no path; a file that lists a directory, its area too: `src`, `tests_unit`, or outside `frontend/` `app`, `docs`): `vitest related` follows a helper to the tests that import it. A change to the dependencies, the vite or vitest config, `selection.py`, a setup file or what a setup file imports at any depth (`src/testing/design-system-warnings.ts`: `vitest related` follows the spec files' imports, not the setup files') runs every file on three shards; a change that reaches no vitest file skips the job. The whole-tree gates, the catalog tests of `src/i18n/` and every source-scan guard (a vitest file that imports `fs` and lists a directory, listed by `frontend/scripts/source-scan-tests.mjs`) run on every pull request and merge group anyway (`frontend-gates`).

## E2E

- **None** when every changed file is one the stack does not carry: `dev-docs/`, unit tests, `.xtm-one/`, `scripts/`, the runner and relay sources (`E2E_INERT`). A path the list does not know runs the suite. `docs/` is in the list although the image carries it: the boot only reads it as the text of a knowledge base, as UTF-8, which the repository reader above checks. Markdown is inert too, but under `backend/app` only a package's own (`AGENTS.md`, `copyright.md`): the boot seeds personas, skills and templates from the rest.
- **core** (ten shards) for any other change.
- **a2a** and **evaluation** for their own modules and the modules those import directly, their specs, their UI (a `frontend/src` path naming the area), and what every project runs on: the images and their start script, the compose files, the dependencies, the database and its init script, the suite's harness (a file of `tests_e2e/` outside the areas' directories that is not a core spec) (`E2E_EVERY_PROJECT`). Their code reaches most of `app` through the agentic loop, so a deeper rule would run them on every change; the nightly run covers the rest. A new Playwright project needs its `E2E_AREAS` entry: `tests/test_selection.py` fails while `e2e.yml`'s matrix shards a project the selection does not decide.

## Running everything on a branch

`gh workflow run ci.yml --ref <branch>` and `gh workflow run e2e.yml --ref <branch>` run every job. The Video Studio ultra render (50 to 85 minutes) runs nightly, opening an issue when it fails, and by hand: `gh workflow run video-studio-ultra.yml --ref <branch>` before merging a change to the render pipeline.

## Shard weights

The unit, Browser tool and E2E jobs deal whole files to their shards, longest first, by the seconds each file took on CI, so the shards end together. The weights refresh themselves (`backend/scripts/shard_weights.py`):

- **Published by the nightly runs.** Each nightly run of `ci.yml` and `e2e.yml` on `main` measures its own reports (the unit and Browser tool JUnit, the Playwright `timings.json`), keeps that measure (`shard-weights-measured`, `e2e-shard-weights-measured`) and publishes the median of it and the four nightly measures before it (`shard-weights`, `e2e-shard-weights`): one run is a noisy sample. The published table names the files of the newest measure only: a file deleted, or sped up below the threshold, leaves it at once. The test files under 2 s are left out (their job weighs them 1 s); every spec keeps its line, to the tenth (an unnamed spec weighs the median of the others). It publishes only from green suites, and a measure that names too few files (a run that lost shards) not at all; a manual run publishes too, to check the job, but only a scheduled run on `main` is ever read.
- **Read by every run.** The select job of each run fetches the latest table published in the last 14 days (`.github/actions/fetch-shard-weights`, `actions: read`), checks it (only file names of its kind, numbers from 0 to four hours, enough files) and hands that one table to every job of the run: `PYTEST_SHARD_DURATIONS` for the unit and Browser tool jobs (in the `test-selection` artifact), `E2E_SHARD_TIMINGS` for the E2E shards (the run's `shard-weights` artifact). Every job deals by the same table, so each file runs in exactly one; a job handed a table it cannot read stops rather than deal by another.
- **The committed tables are the fallback**: `backend/tests/shard_durations.json` (unit), `backend/tests/shard_durations_chromium.json` (Browser tool), `frontend/tests_e2e/shard-timings.json` (E2E). A table that fails a check, or that cannot be fetched, gives way to them, and the select job's summary says which table dealt the run. Weights only decide which shard runs a file, never whether it runs.

The Browser tool job deals only the files that spell `mark.chromium` (`PYTEST_MARKED_FILES`): the files it leaves out would otherwise weigh in the deal. To refresh a committed table by hand, download each full run into a directory of its own (`gh workflow run ci.yml --ref <branch>` keeps the JUnit reports; `chromium-junit-*` for the Browser tool, `test-results-*` of `e2e.yml` for the E2E specs); several runs give each file its median, the newest first:

```bash
gh run download <full run id> --pattern 'unit-junit-*' --dir /tmp/runs/<full run id>
cd backend && uv run python scripts/shard_weights.py refresh --kind unit /tmp/runs/<newest id> /tmp/runs/<older id>
```
