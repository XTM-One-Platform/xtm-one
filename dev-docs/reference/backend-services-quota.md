# Services: quotas, AI gate and telemetry

Service map rows and patterns for agentic quotas, the failure pool, support codes, the AI switch, the background AI gate and holds, the license and licence sharing, tracing and telemetry in `backend/app/services/`; the binding rules live in `backend/app/services/AGENTS.md`.

## Service map

| File | Purpose |
|------|---------|
| `agentic_executions.py` | Agentic execution accounting — the volume of agentic *work* an install performs. `record_agentic_execution(source)` is the hot path (one Redis `INCR` per top-level agentic loop run, never raises, never touches the caller's DB session); `refund_agentic_execution(source)` reverses it on the same refund-safe condition as `quota.refund_agentic_usage` (a `skip_llm` PREPARE refusal did no work), so the metric and the quota cannot drift; `flush_agentic_executions()` folds the day counters into `agentic_execution_daily` with an idempotent + monotonic `ON CONFLICT ... GREATEST` upsert (no advisory lock needed, unlike the quota flush) every ~5 min from `autonomous.py`. Sources: `agent_chat` (chat turns, public widget turns - counted since they go through the one quota gate - sub-agent tasks, self-fan-out), `general_chat`, `assignment`, `extension` — `SOURCE_MAX_LENGTH` (from the model) clamps every source before it becomes part of a Redis or DB key, so two sources cannot collide into a double-touched upsert row. Metered exactly once per logical request — nested consult/transfer handovers belong to their parent. Read by `telemetry.py`; counts only, no identities. |
| `ai_hold.py` | Holding background AI work while agentic AI is unavailable. Work that comes due while the gate refuses - a delayed / queued assignment run, the resume of a paused (HITL) run answered meanwhile (the respond route stays ungated), a delegated task not yet started, the pending runs of an evaluation - is HELD, not failed: `execute_assignment_run(run_id, hold=True)` returns `RunHeld(refusal)` and `_execute_sub_agent_task(..., hold=True)` a `held` outcome, both leaving the row as it is with the `HOLD_MARKER_KEY` (`ai_hold`) marker on `AssignmentRun.trigger_context` / `SubAgentTask.metadata_json` (and on a delegation's linked run); the evaluation adapter holds without touching its runs (its held state is read off the execution: `held_evaluations()`, `EvaluationRunResponse.held_reason`). The adapters return `hold_result(execution, refusal)` = `AdapterResult.defer(...)`, which the reconciler applies through `orchestration_engine.defer`: `running -> pending`, `run_at` pushed by `hold_delay_seconds()` (30 s doubling, capped at `HOLD_MAX_DELAY_SECONDS` = 300 s - held work resumes within five minutes of AI coming back), `adapter_state = held:<code>` and `last_error = held_message(code)`, and `payload['hold'] = {since, count, reason, attempts, budget_seconds}` (closed when the held work starts - the adapters call `close_hold_if_ai_is_back()` -> `orchestration_engine.end_hold` before the body runs, so a later hold gets its own start, attempts and budget; also cleared by `complete` / `await_event` / final `fail`; a transient retry keeps it). Nothing spent waiting is taken from the work: the first deferral records the pre-hold attempt count and the runnable time left, and every deferral restores them - the claim is given back, and so is an attempt used meanwhile by a transient read or a worker lost mid-check (consecutive ones still dead-letter), and the deadline is set that runnable time past the new `run_at`, so a week of re-checks never drains the timeout and the claim lag is never charged. `defer` locks with `refresh` (the reconciler defers on the session that loaded the row before the adapter ran). `hold_budget_left(execution)` bounds it with `AI_UNAVAILABLE_HOLD_MAX_SECONDS` (default one week, `0` = never hold): past it the adapters call the body without `hold` and the work is failed with `expired_message()` and its structural cause, a delegation waking its parent. A held delegation's parent is woken by the ordinary completion path when the task finally runs. Enterprise Edition with AI on never meets a hold (pure payload reads, no extra query, the payload of a never-held execution is not rewritten). Held work is never charged. What reads a hold by age reads it off a row in flight (`held_execution_conditions()`: `pending` or `running` with `payload['hold']`): the per-user fan-out counts a user's held run (the marker) or running run as that user's catch-up whatever its age, while any other old run - a paused one nobody answered - keeps the dedup window; the stale-assignment sweep leaves a held run whose execution is live out of its oldest-first batch of 500 (it would skip it anyway), so a long hold never crowds a real orphan out, while a held run whose execution is gone is still swept. **A quota store that cannot be reached while quotas fail closed is held the same way** (`QUOTA_STORE_UNAVAILABLE_CODE` = `quota_unavailable`): a due assignment run whose quota CHECK meets an outage (`quota.is_quota_store_outage`: a refused, reset or timed-out connection, a store loading or failing over - `LOADING`, `MASTERDOWN`, `CLUSTERDOWN`, `TRYAGAIN` - a read-only replica, a store out of memory - never a rejected credential or permission - a wrong password, `NOAUTH`, an ACL denial: a configuration error, refused at once as before -, never a fault of the quota code or its data, and never a failure while charging, which may have partly landed) returns `RunHeld(quota_unavailable)` uncharged, and a delegated task whose start finds the store out (`quota.quota_store_out`, a write probe asked only while quotas fail closed) is held before it is marked running, so its agent turn never charges or counts it; a task whose turn's quota check meets the outage the probe missed (a flapping store: the gate says so with `agent_chat.QUOTA_STORE_OUTAGE_KEY`, set only for an outage met before any charge) goes back to pending, held, and the execution the refused turn counted is given back (`sub_agent._refuse_task_before_turn`). `close_hold_if_ai_is_back` keeps such a hold open while the probe finds the store out (bound, backoff and runnable budget keep counting) and ends it before the work starts once the store answers, so a running execution never carries a hold the deadline sweep would rebase. A run's quota marker stays until the run passes the quota; the failure past the bound is `expired_message` / `failure_cause_of` (`quota_backend_unavailable`). Chat turns are not held. |
| `agentic_gate.py` | The background gate: "may agentic AI run here right now?" for the work nobody waits on. `agentic_refusal(db)` returns `None`, `ai_disabled` (the administrator's switch, asked first) or `license_required` (Community Edition: no valid license in `copilot` mode) - the meaning of `platform.is_agentic_ai_enabled`, with the licence half resolved through `platform.is_agentic_ai_licensed` itself, never a second rule. The licence answer is cached process-locally for `ai_state.CACHE_TTL_SECONDS` (a miss is one shared read however many callers arrive meanwhile), read on a session of its own (never the caller's), and never raises: a failed read keeps the last answer read since the last `invalidate_cache()`, or refuses (transiently) when there is none. `invalidate_cache()` is called AFTER the commit of every edition change (license install / removal, platform register - which is also each platform's heartbeat - / unregister / purge) and bumps a generation, so a read begun before it caches nothing. Asked at every background entry point, before any work: the scheduler tick (once) and the per-user fan-out (a refusal midway stops it with the cron window left open), the integration-event poller (per assignment, before anything is polled or claimed; a refused trigger gives back its event and the provider cursor the poll advanced), `trigger_assignment` / `trigger_or_queue_assignment` (`_refuse_if_ai_disabled`, raising `{code, message}` 403s its callers branch on through `refusal_code()` - the change-notification receivers (Microsoft Graph, Slack, LinkedIn) keep answering 200, every webhook receiver answers its sender the 403, and a scheduled assignment refused mid-tick gets its cron window back), a run's start in `execute_assignment_run` (before the quota; failed with the `FailureCause` of the same value), the chain dispatch, the delivery-queue drain (asked only when a delivery is queued; deliveries stay queued), `channels/router.handle_message` (a state that could not be read first, either half: nothing is processed, a direct message is told the AI service is temporarily unavailable and a group channel gets silence; then the AI switch's reply, unchanged; the licence refusal answered with `chat_unavailable_detail()` only where a model would have answered - after every routing rule, the anonymous, private and only-mention checks and the routed agent's own channel rules included (`_route_turn`) - and before anything is stored), flow triggers (`hold_back_if_ai_required`: a held trigger is not consumed - a schedule keeps its window, a polled event goes back unseen with the provider cursor - and an unreadable state records no skip), a delegated task's start, parent / partner wakes (after the wake's text is persisted, so the result waits in the history; a task's refused wake falls back to the completion notice a non-waking parent gets, which carries its files), fresh evaluations (pending runs only) and the worker's AI jobs (a one-shot workset job schedules itself again, since nothing else comes back for its subject, on a slot-aligned key so the jobs of one subject share one retry). The three sites that FAIL work on a refusal - a run's start, a delegated task's start, a fresh evaluation - ask `agentic_verdict(db)` instead: its `transient` flag marks a refusal that comes from the failure policy (the switch could not be read - `ai_state.cached_state()` holds no `False` - or the licence was never read in this process, or its read failed and the answer kept is a refusal), and such a refusal leaves the work untouched and uncharged: `execute_assignment_run` returns `RUN_DEFERRED`, the task returns a `deferred` outcome, and the adapters return a retryable failure with `backoff_seconds=UNKNOWN_STATE_RETRY_SECONDS`, bounded by the execution's attempts and deadline (dead-lettered, the work fails with the engine's cause, never `license_required`). A definitive refusal HOLDS that not-yet-started work (`ai_hold.py`): it is failed at its start only once its hold is over. Never read mid-execution (FR-013). `refusal_message()` gives the REST refusals' own sentence. Refusals are otherwise non-destructive: nothing is disabled, paused or deleted. `tests/test_background_edition_gate.py` fails the build on an entry point deciding with `ai_state.is_ai_enabled()` alone, or on a site that fails work without deferring a transient refusal first. |
| `quota.py` | Four-tier agentic / LLM-proxy quota enforcement (license > platform > group > user), Redis-buffered and flushed to `quota_usage`. **When the quota store cannot be read**, `quota_fail_closed()` (the one reader, shared by the chat gate, the assignment engine and the sandbox dispatch) is ALWAYS true in XTM One mode (xtm_one / ai_disabled): quotas are what the licence sells, so `core/security_options.py` pins `quota_fail_mode` to `closed` there and `QUOTA_FAIL_MODE` / Settings > Security decide only in `copilot` / `dev` mode. A due background run that meets an unreachable store is held rather than failed (`is_quota_store_outage` / `quota_store_out`, see `ai_hold.py`); a store refusing the platform's credentials or permissions is a configuration error, refused at once like a credential an LLM provider rejects. **A run with no account behind it is metered too** - an external-channel sender without an account (`"anonymous"`), a public widget visitor (`public_chat._run_public_agent_chat`), a `/mcp/global` call made with the platform key (`"mcp-global"`), an assignment run no user can be attributed to: the one gate (`agent_chat.enforce_agentic_quota_ex`, the assignment engine's own check) hands `user_id=None` to `check_agentic_quota` / `increment_agentic_usage` / `refund_agentic_usage*`, which read it as the platform-wide tiers alone (licence ceilings, `platform_limit` - the tiers each mode already enforces for everyone) and the `_global` counters alone, never a per-user or per-agent one, under the same fail mode. Its refusals are `ACCOUNTLESS_QUOTA_EXCEEDED_MESSAGE` / `ACCOUNTLESS_QUOTA_UNAVAILABLE_MESSAGE` (the service is at capacity / unavailable - never the quota, the licence or the store); the failure pool does not apply (`REFUND_OUTCOME_NO_ACCOUNT`, the charge stands), a run that reached no model gets its `_global` charge back through `decr_if_positive` (logged, not tallied: the card counts credits per user), and a receipt or a dead-lettered run records its user as `None`. The platform-wide rows of `get_platform_quota_monitoring` read the `_global` counter their ceiling is enforced against (never below the per-user total), so they include these runs; per-user figures and top consumers never do. Also owns the **agent failure pool**: usage is metered BEFORE the agent runs, so a failed run has already spent an agentic action, and `refund_agentic_usage_for_failure` / `refund_agentic_usage_for_provider_outage` / `refund_agentic_usage_by_receipt` credit it back — the first out of a bounded per-agent allowance (`AGENT_FAILURE_QUOTA_POOL`, env-sized, on by default), the other two free and unbounded when no model was ever reached. Counters ride the ordinary `quota:usage:` key space under `agentic_failure_pool` / `agentic_free_refund` so `flush_quota_usage` persists a year-long window that Redis alone cannot hold; `_load_pool_baseline` reads that high-water mark back when a key is missing, so a cache wipe cannot refill a pool. **A user whose agentic quota is unlimited is never pooled**: `has_enforceable_agentic_limit` mirrors `check_agentic_quota` tier for tier (platform cap via `agentic_platform_cap_enforced`, then the same `resolve_quota_config` the gate reads — never a second resolution), and the pool path returns `REFUND_OUTCOME_QUOTA_UNLIMITED` through its `outcome_out` dict without claiming a slot: the counters are incremented whether or not anything caps them, so a failed run always LOOKS charged, but the charge cost nothing. With `db=None` the question cannot be answered and the pool applies as before. **An admin clear** (`reset_user_quota_usage`, the support-code recharge `agent_failure_pool._clear_pool_counters`) never deletes a counter without the flush lock nor before its commit: it waits for the lock through `_wait_for_flush_lock`, which asks a running flush to stand aside (`_FLUSH_YIELD_KEY`, checked by the flush every `_FLUSH_YIELD_CHECK_ROWS` rows) and is refused with `QuotaClearBusyError` (503 `quota_flush_busy`) before anything is cleared when the lock stays taken; its counters leave Redis through a stash (`_CLEAR_STASH_PREFIX`, registered with the clearing transaction's id in `_CLEAR_STASH_INDEX`), dropped once it committed and put back when it did not (`_abandon_clear`), and every holder of the flush lock settles the stashes of ended clears from `pg_xact_status` before it touches a counter (`_settle_clear_stashes`). A new clear path goes through these, never a bare `DEL` of `quota:usage:` keys. **Why each failure is funded the way it is — and why anything the provider REPLIES stays bounded — is in `agent_failure_pool.py`'s module docstring.** |
| `agent_failure_pool.py` | Everything around the failure pool that is not the counter itself. **The renewal window**: one year anchored on the Filigran license start date (`resolve_pool_window`), falling back to the platform's `created_at` and then the calendar year, and only ever anchored on a license whose signature actually verified — an unvalidated PEM's dates are attacker-controlled and moving the anniversary would be worth forging one for. Leap-day anchors land on 28 February; windows are contiguous across the anniversary; a future anchor (clock skew) clamps rather than producing a window that has not begun. **Support codes**: `XTMP-<b64url(payload)>.<b64url(RSA-PKCS1v15-SHA256 signature)>`, verified offline with `licensing._load_trust_anchor_public_key` against the CA already embedded in `xtm_ca.py` — the same trust as a license, minus X.509, because a ~700-char token can be pasted out of a support email and a certificate cannot. The signature covers the payload's RAW BYTES, so issuer and verifier never have to agree on a canonical JSON form, and it is checked BEFORE any field of the payload is read. Offline verification has two consequences the code handles explicitly: a signature is replayable forever, so every code carries an `id` burned into `support_code_redemptions` under a UNIQUE constraint (two concurrent redemptions are resolved by the database, not by a racing check); and a code cannot be revoked, only expired. A code is bound to one `PLATFORM_ID` unless minted `global`. **The recharge** clears every pool counter in Redis *and* in `quota_usage` while holding `flush_quota_usage`'s advisory lock — without that ordering the flush's monotonic `max()` would resurrect the rows it had already read and the recharge would do nothing — and commits the redemption with the clear, through the same clear protocol as a quota reset (see `quota.py`). Issuing side: `backend/scripts/mint_support_code.py` (needs the Filigran private key; never shipped). |
| `support_codes.py` | The one entry point for every kind of Filigran support code: `verify_redeemable_code` (signature, kind - `agent_failure_pool_recharge` or `platform_quota_reset` - and a reset's scope), `describe_grant` (the audit line), `apply_support_code` (burns the code with `agent_failure_pool.burn_support_code` and applies the grant in ONE commit, so whatever the caller added to the session - the route's audit row - lands with it or not at all). A `platform_quota_reset` code resets the platform-wide counters the license ceilings are enforced against, which no admin action resets (`quota.reset_platform_quota_usage`: the current windows of the named types, Redis and `quota_global_usage` alike, under the flush lock and the platform-wide counters' write lock held exclusively, through the clear stash). Its `quota_types` / `periods` claims are optional (default `agentic` + `sandbox`, every period) and refused unless a non-empty list of known names - never guessed at. Route: `POST /settings/quotas/support-codes/redeem`; the pool-only `/quotas/agent-failure-pool/redeem` is kept. |
| `attempt_charges.py` | Each orchestration attempt's agentic charge, fenced to that attempt. A lost lease re-runs an execution from the start while the lost attempt may still be running (a heartbeat outage only stops the heartbeat), so every charge is credited back by at most one of the re-run that replaces its attempt, that attempt's own failure handler and the dead-letter. An assignment run records its charge on the run row with the id of the attempt that made it (`recorded_charge` / `with_recorded_charge` / `without_recorded_charge`, `QUOTA_METERED_CHARGE_KEY`): `take_lost_charge` (the re-run, before anything else, then a free credit), `release_charge_record` (the failure handler, before its credit) and the dead-letter take the record off the row under its lock before they credit, and `claim_charge_record` records a new charge only if nothing was recorded since the attempt loaded the run and no later attempt started - otherwise the attempt was replaced before it charged and gives its charge back. An attempt is placed by `(epoch, attempt)`: a re-run records its place on the row as it starts (`fence_attempt`, `QUOTA_ATTEMPT_FENCE_KEY`), before the attempt it replaces could charge, and the HITL pause opens the next epoch (`open_pause_epoch`), because a resume counts attempts from 1 again; a lost charge is only one of this epoch. A hold the engine defers restores the attempt count too, so a hold made after a re-run fenced the run opens the next epoch as well (`fence_for_deferral`); every attempt, a first one included, checks the run under its lock as it starts (`assignment_engine._ended_elsewhere(starting=True)`), so a replaced attempt's hold writes nothing. The dead-letter of a run already `failed` credits a record it still carries (a stale attempt failed it while its re-run was charged); a retry copies the context without record or fence (`without_charge_state`). A delegated task's turn writes one metering receipt per attempt (`task_receipt_token(task_id, attempt=)`): `credit_lost_attempts` (a re-run), `credit_abandoned_task` (the dead-letter of a task that had not ended, the older task-wide receipt included, or that failed, the task-wide receipt excluded) and `quota.claim_own_receipt` (the charging turn's failure refunds in `run_agent_chat`) redeem receipts once (`quota._REDEEM_RECEIPT_LUA`), and a charge landing under a receipt already redeemed is given straight back (`quota._WRITE_RECEIPT_LUA`). A charge is credited through these, never by a path of its own. Flow runs are not covered. |
| `concierge/budget.py` | The Platform Concierge's own budget line (#8254, decision B20): the licence gate first (`agentic_gate.agentic_verdict`), then caps per cycle and per month, in tokens and in dollars, from Settings > Concierge. `open_cycle` / `reserve` / `charge` / `release` / `close_cycle` / `remaining` / `budget_refusal` / `close_stale_cycles` over `concierge_cycles` and `concierge_budget_months`, the month row locked before the cycle row so concurrent reservations never pass a cap together. `concierge_budget_work` keys work by id: a reservation `reserve(hold=...)` keeps past its cycle's close (an evaluation still running), and a charge with a `ref` booked once (a run's traces). An extra cap, never a bypass: the fleet's runs still count in the platform-wide action tiers. The identity and the one consent rule live beside it (`concierge/identity.py`, `concierge/consent.py`; `dev-docs/platform-health.md`). |
| `licence_verdict.py` | The licensed verdict the web process shares with the worker. `ENTERPRISE_LICENSE` is read per process: a worker deployed without it (the variable set on the platform container only) resolves Community Edition on its own, and `agentic_gate` would hold every run start, delegated task, evaluation and worker AI job of a licensed deployment. The web process (`share_licensed_verdicts()`, from its lifespan) publishes a short-lived "licensed until" verdict in Redis after a licence read that answered yes while `ENTERPRISE_LICENSE` is set, signed with a key derived from `SECRET_KEY` (no license material leaves it, at most once a minute); the worker (`accept_licensed_verdicts()`, from its startup) accepts it in `agentic_gate._read_licence` when its own read answers no, and logs it once. Every Redis call is bounded by `REDIS_TIMEOUT_SECONDS` and never raises; no other process touches Redis for it. |
| `langfuse_tracing.py` | Langfuse observability: traces LLM calls, tool usage, and assignment execution |
| `trace_switches.py` | The trace storage and payload switches of Settings > Observability: what the native trace store keeps (`apply_trace_switches()`), from a per-process snapshot refreshed with the security options; applied by the tracing dispatcher and both sinks, never by Langfuse nor by a copy of what is already stored (`ClickHouseSink.write_score` for the score rewrite) |
| `telemetry.py` | Anonymous usage/adoption telemetry over OpenTelemetry. Exports aggregate counts (agents, assignments, users, integrations, ...), provider breakdowns (integrations + channel bots by catalog `provider`), the platform version, the anonymous `instance_id`, the deployment edition (EE vs CE), optional deployment tags (`TELEMETRY_TAGS` env var, normalized comma-separated tags like `saas,eu-west`, exported as the `filigran.telemetry.tags` resource attribute), per-day activity series (assignment runs / conversations / messages created per UTC day over the rolling 30-day window, `date`-attributed — the source for runs/conversations/messages per day in adoption analytics; the matching `*_count` totals stay cumulative snapshots), agentic executions (`agentic_executions_count` all-time total + `agentic_executions_by_day` over the same window, read from the durable `agentic_execution_daily` table — see `agentic_executions.py`), and LLM analytics aggregates from the local trace store (total cost, total tokens, avg latency, avg feedback — overall + per-day over the last 30 days, aggregate numbers only) via OTLP/HTTP to the Filigran collector. `init_telemetry()` (startup; connectivity-probed, self-disabling, seeds the snapshot), `export_telemetry_if_due()` (every scheduler tick in `autonomous.py`; a Redis window lease lets one process per install export once per interval, 6 h or 3 h in dev), `refresh_telemetry_data()` (snapshot recompute, called by `init_telemetry()` and just before each export), `shutdown_telemetry()` (closes the exporter; the reader has no timer, so nothing is exported at shutdown), `is_telemetry_active()`. On by default; `TELEMETRY_ENABLED=false` turns it off before the startup probe (no exporter, no export lease). Otherwise self-disables when the collector is unreachable, in CI or under the test runner. Every gauge is listed in the user docs page `docs/docs/deployment/telemetry.md`, which `tests/test_telemetry.py` keeps in sync. Never collects personal data, secrets, or content. |

Process-local cache (`CACHE_TTL_SECONDS`, `invalidate_cache`, `cached_state`); `is_ai_enabled()` is the switch alone - background work asks `agentic_gate`. |

## Platform-wide quota counters (`quota.py`)

The platform-wide limits (the license ceilings in XTM One mode, `platform_limit` in `copilot` mode) are enforced against the `_global` Redis counters alone (`quota:usage:_global:<agentic|sandbox|llm_proxy>:_total:<period>`), and Redis can lose one mid-period (eviction, restart without persistence, cold replica, a yearly key lapsing after `_USAGE_KEY_TTL` without a run). So:

1. `flush_quota_usage` persists them to `quota_global_usage` (`_upsert_global_usage`: one `INSERT ... ON CONFLICT` per cycle that only ever raises a count), a table with no user column: they count runs with no account behind them too, and Settings > Quotas never lists them under anybody. They are written FIRST, in a transaction of their own under `_QUOTA_GLOBAL_FLUSH_LOCK_KEY` (`_flush_global_usage`, the counters re-read under that lock), never inside the per-user flush transaction, which holds the flush lock for as long as its rows take (a read-back waiting on it would time out at a period rollover).
2. Every reader of a platform-wide counter goes through `_get_global_count`: a key Redis does not hold is seeded (`SET NX`) from that row, read on its own session once no write of the platform-wide counters holds `_QUOTA_GLOBAL_FLUSH_LOCK_KEY` (`_load_global_baseline`: a write in flight may be saving a higher mark than the row holds; the callers of a process that miss the same counter share one read, so a herd after a Redis loss does not drain the connection pool), before it is compared with a ceiling. Every charge counts its platform-wide periods through `_count_global`, BEFORE the user's own counters: one script (`_COUNT_GLOBAL_LUA`) that increments the counters Redis holds and seeds a lost one from its row in the same step, so a counter lost between a read and an increment never restarts at 1 (an `INCR` on a missing key would create it there, and the row would never be read again for the period). A refund never seeds. A read-back that fails raises before anything is counted: the gate treats it as a quota store it cannot read (refused in XTM One), and no counter is created without its baseline.
3. No clear touches them: a quota reset and a support-code recharge clear one user's counters or the failure pools, never a `_global` key or a `quota_global_usage` row, so they need none of the stash-and-settle protocol. A new clear that does must go through it.

The unit suite answers "nothing saved yet" for the read-back (`tests/conftest.py`); `tests/test_quota_global_postgres.py` runs it against a real PostgreSQL and Redis.
