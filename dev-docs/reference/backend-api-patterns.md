# API route patterns

The full text of the conventions every `backend/app/api/` route follows - auth, sessions and commits, visibility and admin reach, company-managed toggles, ids, files and continuing runs; the one-line rules live in `backend/app/api/AGENTS.md`.

## Patterns

- **Authentication**: Every route (except public endpoints) uses `Depends(get_current_user)` or `Depends(require_admin)`
- **Database**: Inject `AsyncSession` via `Depends(get_db)` – the session commits on dependency teardown, which FastAPI runs AFTER the response is sent, so a route that writes commits before it answers: the page refetching right after the 2xx, or the next request presenting the id or key it was handed, must find the write. `await db.commit()` comes after the write and its audit row (`expire_on_commit=False` keeps the response readable); a step that can still fail and must take the write back with it (an outbound request) stays before that commit, and a cache drop or any other side effect that cannot be undone comes after it (the After-commit rule below). `tests/test_write_routes_commit_before_response.py` checks every route statically - a path it cannot see through is an entry in its `EXEMPTIONS` or `REVIEWED_ESCAPES`, with the reason - and the tripwires in `tests/test_account_writes_commit_before_response.py` also hold the account routers (`auth`, `users`, `groups`, `api_keys`, `invitations`) and every route that mints or replaces a credential
- **Validation**: Pydantic `BaseModel` for all schemas
- **After-commit side effects**: a side effect that must follow the route's commit (the Database rule above) - a cache drop above all: run before it, a concurrent read re-caches the old state for the cache's whole TTL - runs right after that commit or, registered where the route decides on it, through the route's `AfterCommit`: declare `after_commit: AfterCommit = Depends(run_after_commit, scope="function")` (`app/api/deps.py`) and call `after_commit.add(invalidate_quota_cache, user_id)`. It runs once the route has committed and returned, before the response is sent, and not at all if the route raises. Always function-scoped: request-scoped it would run after the send (`tests/test_account_writes_commit_before_response.py` checks every use)
- **Status codes**: Use `status.HTTP_*` named constants from `fastapi` in route decorators — `status.HTTP_201_CREATED` (create), `status.HTTP_204_NO_CONTENT` (delete). Default 200 for list/get. Error responses use numeric codes in `HTTPException` (400/401/403/404).
- **List queries**: Use `user_visible_query(ModelClass, user_id, user_group_ids)` from `helpers.py` for entity list endpoints (own + group-shared + company-managed, ordered by created_at desc). Use `user_visible_filter(ModelClass, user_id, user_group_ids)` for composable filter clauses in counts/aggregates. Get `user_group_ids` via `get_user_group_ids(db, user_id)`.
- **Invisible = unknown**: An entity the caller cannot see gets exactly the answer an unknown id gets (same 404, same body), never a 403 that would confirm it exists: load by id through the visibility predicate (`user_visible_filter()`, the owner for an owner-only resource), then check the manage tier. A 403 is kept ONLY for an entity the caller can see but may not manage (company-managed for a non-admin, a read-only share, a built-in) - the UI's read-only banners rely on it. `get_manageable_entity()` does this for non-admins; admins are unchanged.
- **Assignment queries**: An assignment has no audience of its own, it is visible exactly when its parent agent is - filter with `assignment_visible_filter(user_id, user_group_ids)` from `helpers.py`, never over the mirrored `Assignment.user_id` / `is_company_managed` (they miss per-user shares and `access_restricted`). Every assignment route passes `is_admin=user.is_admin` - one assignment, one agent's assignments, the list across agents and `GET /assignments/schedule`, which read the whole platform for an admin; the Manual Triggers panel offers only the assignments whose agent its viewer's agent list holds (`lib/manual-triggers.ts`). An agent tool that reads or starts an assignment goes through the same helpers, never a copy: `find_user_assignment(..., is_admin=agent_tool_admin_bypass(caller))` (the lookup `get_user_assignment()` wraps, `None` for unknown and invisible alike - an admin's agent reaches every assignment, as the REST routes do, unless `AGENT_TOOLS_STRICT_ADMIN_ACCESS`; that helper is the one admin bypass of EVERY agent tool - the agent builder's agents, runs, entities and binding checks, the flow builder, the trace and evaluation tools, the XTM One MCP server - and a REST helper a tool calls is handed its answer, while the role is read directly only in the permission gates listed by the tripwire in `tests/test_manual_trigger_gate.py`) and, for a run started as the caller, `manual_trigger_refusal()` / `manual_trigger_overlap()` - the REST trigger route, the agent-builder `trigger_assignment` tool and the work-items `delegate_to_assignment` tool share them.
- **Admin reach**: The library lists (and the pickers the UI builds from them) are three-tier for everyone, admins included. Everything else takes the admin bypass: detail routes read and write with `is_admin=user.is_admin`, and the entity list endpoints and run feeds accept `scope: EntityListScope = Query("visible", description=ENTITY_LIST_SCOPE_DESCRIPTION)` - `all` is every row for an admin (`list_scope_admin_bypass(scope, user)`), the library set for anyone else, and is what the detail pages read to show an entity's bindings, runs and users. A new entity list endpoint takes the same `scope`; a new detail route passes `is_admin`. A view whose rows carry other users' private content and reach an admin by the role alone is an audited oversight read, never a silent bypass: a machine's command history (`is_admin_oversight_read` in `runners.py`) and an agent's delegations (`GET /chat/delegations` with `agent_id` / `parent_agent_id` / `target_agent_id`, and `GET /chat/delegations/{id}`, `_audit_delegation_oversight` in `chat.py` - an unfiltered admin list stays the admin's own). One `break_glass` entry per admin, entity and 15-minute window, committed BEFORE the rows are served, the Redis marker written only after the commit (a Redis failure audits anyway), none for the caller's own rows.
- **Company-managed helpers**: Use `require_admin_for_company_managed()`, `toggle_company_managed_list_field()`, `handle_company_managed_toggle()`, `get_manageable_entity()`, and `build_mcp_runtime()` from `helpers.py`
- **Assignment run access**: Use `require_run_access(run, user, *, action)` from `helpers.py` for assignment run permission checks: an admin acts on every run; otherwise the run's own user may, a company-managed run (visible to everyone, `run_visible_filter()`) gets the 403, and another user's personal run, which the caller cannot see, gets the unknown run's 404 `Run not found`
- **Continuing runs**: a run that continues another is never more visible than it and never runs as a user who could not open it - see "Continuing runs" below
- **File access**: A route that serves or acts on ONE stored file loads it through `load_readable_file()` from `services/file_access.py` (`load_readable_chat_image()` for `/chat/images/{id}`): a malformed, an unknown and an unreadable id all get the same 404 `File not found`, so the answer never confirms which file ids exist. Never answer a file refusal with a 403; a distinct answer is only for a caller who may READ the file but not perform the action (the template-asset 409 on `DELETE /files/{id}`). Who may read what stays `can_read_file()` / `authorize_file_access()`; a file or a legacy `ChatImage` (`can_read_chat_image()`) of a conversation is readable by whoever may read that conversation, whoever uploaded or made it, as an attachment is part of the transcript (never an internal file such as a checkpoint spill, `INTERNAL_FILE_SOURCES`, which stays its owner's) (the chat panel downloads through the id-scoped route); a `ChatImage` of no one and of no conversation is admins-only.
- **Client-supplied ids**: Never parse a path, query or body id with a bare `uuid.UUID(...)` (a malformed value is a 500). An id naming the ONE row a route acts on goes through `parse_conversation_id()` / `parse_path_id()` from `helpers.py`, so a malformed id gets the route's unknown-id 404. The shared entity lookups (every `get_user_*()` helper and `get_manageable_entity()`, and for a stored file `load_readable_file()` / `load_readable_chat_image()`, see **File access**) parse their id this way before any query, so a route that resolves its entity through them needs nothing more; every other route that looks a path id up itself uses `parse_path_id()` with its own unknown-id wording, where the lookup happens, so the checks before it run for a malformed id exactly as for an unknown one; a list or body filter keeps `parse_uuid()`'s 422; `safe_uuid()` where the route has its own answer for an id that names nothing (a fresh session, an empty list, an in-band error frame, an idempotent delete, a token bound to another deck, a stored id skipped); a FastAPI `uuid.UUID`-typed path param keeps its validation 422. Pinned by the tripwires in `tests/test_malformed_conversation_id.py` and `tests/test_malformed_path_id_routes.py` (no path param reaches `parse_uuid()` or a bare `uuid.UUID()`, nor a primary-key comparison before anything checked it, in a route or the module helper it passes the id to; a route answering a malformed path id itself through `safe_uuid()` is listed in `_OWN_ANSWERS` with the test proving that answer is the unknown id's - webhook receivers, whose `ignored` reason names what was wrong for the sender, are the one listed exception).
- **Constants**: Use `LANGFUSE_DEFAULT_HOST` from `settings.py` for Langfuse host defaults (single source of truth)

## Company-Managed Toggle Pattern

A shareable entity's update endpoint takes `is_company_managed`:

```
PUT /api/v1/{entity}/{id}  { "is_company_managed": true }
```

- **Only admins** change the flag (403 for non-admins); creating an entity company-managed is admin-only too (`require_admin_for_company_managed()` on the create body).
- **Private → Company**: `user_id` is kept (the owner stays for provenance; visibility comes from the flag) and the group grants are cleared, unless the same request sets `access_restricted`, where they become the audience (`keep_grants`).
- **Company → Private**: the owner gets it back (the acting admin only for a legacy row with no owner) and the entity is removed from other users' agents (`agent_field`: `knowledge_base_ids`, `mcp_server_ids`, `custom_tool_ids`, `skill_ids`, `prompt_ids`, `runner_ids`; `None` for an entity agents never bind by id).
- **Where**: `handle_company_managed_toggle()` (over `toggle_company_managed_list_field()`) for knowledge bases, MCP servers, custom tools, agent skills, prompts, runners, flows, workspaces, Nova rules, investigation packs, template containers, relay groups, presentations (`services/presentation_sharing.py`), evaluations and datasets (`agent_field=None`: no agent binds one by id, and what else points at them, evaluation links and Platform Health's experiments and entry sources, is reachable only by admins and Platform Health). Agents (`agents.py`: strips personal bindings and mirrors the flag onto assignments and runs; back to private through `revert_company_managed_to_private()`; both ways, and from the agent builder too, the worksets the agent owns and their internal knowledge bases move to its tier through `services/workset.retier_agent_worksets()`) and integrations (`integrations.py`: drops the integration from other users' `integration_bindings`) have their own branch; variables gate the flag with `require_admin_for_company_managed()`. Channel bots are always company-managed (create, update and delete are admin-only), with no toggle. `rg -n "handle_company_managed_toggle\(|require_admin_for_company_managed\(" backend/app` gives the current list.

## Continuing runs

A run that continues another carries that run's id and its input or result, so it is never more visible than the run it continues and never runs as a user who could not open it. Two helpers in `helpers.py` hold the rule, and a run of an assignment gets both through `trigger_assignment(continues_run=...)`:

- **Visibility**: `continuing_run_is_company_managed(source, *, fallback, ceiling)` - the source run's `is_company_managed`, capped by `ceiling`, the widest the new run's own settings allow (the assignment's visibility and `hide_runs` as they are now; `True` for a delegation child or a retry, which have none of their own). `ceiling` has no default: every caller states its cap. `resolve_child_run_is_company_managed()` loads a delegation parent's flag and applies it.
- **Execution identity**: `can_open_continued_run(session, source, user_id)` - the identity the new run would act as (its stored user, else its agent's owner - `_acting_identity`, the engine's own resolution; no identity at all is refused) must be an active account able to open the source (its own user, or `openable_parent_runs`, the rule a run names its parent by: everyone for a company-managed run, admins); a missing or deactivated user opens nothing, as authentication refuses them. `trigger_assignment` asks it before anything is written (before the overlap lock) and raises `ContinuedRunNotOpenableError` (403 `continued_run_not_openable`, `{code, message}`) otherwise. `user_id` stays the execution identity: it is never rewritten to make a run visible or invisible.

Per continuation:

| Continuation | Runs as | Visibility | When the identity cannot open the source |
|---|---|---|---|
| Follow-up (`POST /runs/{id}/followup`) | the clicker (`triggered_by_user_id`) | source's flag, capped by the assignment | cannot happen: the clicker passed `require_run_access` (the run's owner or an admin); were it to, the route answers the 403 with the code |
| Follow-up chat (`POST /runs/{id}/followup-chat`) | no run: a conversation owned by the clicker | private (`link_access = private`), read by the agent's chat readers (`can_view_agent_chats`) like every chat of that user with that agent | n/a |
| Chained run (`next_assignment_id`, dispatched in `execute_assignment_run` once `_persist_assignment_memories` is written) | the NEXT assignment's own identity (run-as user, else owner), never the source run's user: its integrations and credentials belong to that identity, and running another agent as the source's user could hand that user an agent they cannot reach | source's flag, capped by the next assignment | not dispatched and reported (`_report_refused_continuation`, see below) |
| Retry (`retry_on_failure`, transient model failure, built directly in `execute_assignment_run`) | the failed run's `user_id` | the failed run's flag (`ceiling=True`) | that user deactivated or gone (a company-managed assignment's run-as user, say, while its owner stays active): no retry, reported the same way. The check runs in `execute_assignment_run`, before the retry row is created |
| Delegation child (sub-agent task, consult, transfer) | the parent's user | the parent's flag (`resolve_child_run_is_company_managed`, `ceiling=True`) | n/a: the same principal |
| HITL respond / dismiss / resume | the same run | unchanged | n/a: no new run |

A refused chain or retry is never dropped silently. `_report_refused_continuation` logs a WARNING, writes a `log_system_audit` `continuation_refused` entry on the assignment, and sends an `assignment_continuation_refused` Activity (the header bell) to the assignment's owner ALONE: `_emit_assignment_notice(only_to=...)` stores it for that user and publishes it on their channel only, never `activity:company`, company-managed assignment or not. None of them names the run or carries its result, since the owner may not be able to open it: they name the assignment(s), the kind and the code. A live delegation child is the one continuation not checked: it runs inside its running parent, as the parent's user.

Tripwires in `tests/test_continuing_run_visibility.py` fail on a continuation that bypasses either helper: an `AssignmentRun(...)` naming a parent run, counting a retry, or carrying a source key (`parent_run_id`, `parent_result`, `previous_result`, `chained_from_run_id`) in its payload or context whose flag does not come from the rule, whose `user_id` is read off an assignment, or which (a retry) is built without asking `can_open_continued_run` first, a notice not sent recipient-only, and a `trigger_assignment` whose `payload` / `trigger_context` carries one of those keys without `continues_run`. A new continuation that carries its source some other way adds its marker there.
