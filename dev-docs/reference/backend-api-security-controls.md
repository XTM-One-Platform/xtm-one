# Security controls and Security Audit checks

How to add a security switch or a Security Audit check (`app/core/security_controls.py`, `v1/security_audit.py`); the one-line rules live in `backend/app/api/AGENTS.md`.

## Adding a security switch or check

The Security Audit (`v1/security_audit.py`) reports findings and every security control registered in `app/core/security_controls.py`; the contract is stated in that module's docstring:

- **One control per switch.** A new `Settings` field (or stored `platform_settings` / `sso_config` column) that makes the platform safer when set gets a `SecurityControl` in `SECURITY_CONTROLS`: id `<category>.<name>`, the setting, the enforcing value as an administrator types it (`hardened`), the `enforced` predicate (plus `monitoring` / `applies` when relevant), what enforcing it changes for users (`impact`) and where what it would block is recorded (`evidence`). A switch-shaped field that protects nothing goes to `NOT_CONTROLS` with its reason.
- **A finding about a control names it** with a literal `control="<control id>"`; its `id` stays a literal `<category>.<name>`, and its category is one of `SECURITY_CATEGORIES` (the dashboard labels exactly these, `CATEGORY_LABELS` in `frontend/src/pages/settings/security-audit.ts`).
- **Severity rubric**: `critical` = exploitable now; `warning` = a protection off or misconfigured while what it protects is in use, or a setting that silently weakens one; `info` = off with nothing it protects in use, a monitoring mode, or context; `pass` = enforced or nothing to fix. "In use" is something the audit sees the protection would refuse or change right now (an embedded widget, a secretless webhook, a stored token URL on loopback, credentials issued over plain HTTP), never the switch alone: an opt-in protection off with nothing in use stays `info`.
- **An id is a durable key**: the notified-once memory and an administrator's dismissal are stored by finding id in `security_audit_finding_states`, so renaming an id notifies its finding again and drops its dismissal. Keep ids literal and stable.
- **No silent pass**: a check that can warn also reports its pass when what it protects is in use. Keep checks cheap (counts in SQL, no per-row loads) and name long lists with `_listed()`.
- **Tripwires** in `tests/test_security_controls.py` fail the build on a switch-shaped `Settings` field that is neither a control nor exempted (the message gives the entry to add), a category outside the taxonomy, a `control=` naming nothing, a finding that names a security option (`option_reference()` / `where_to_set()`) without `control=`, a dashboard labelling other categories, or a Settings > Security option with no control or grouped under another category than its control's; such an option is reported as `security_option()` resolves it, never off `settings` alone. `EXPECTED_CATEGORY_BY_CHECK` there maps every function that builds a finding to its category: a finding built inside it under another category or id prefix fails with the function, the category and the id to write, and a new function that builds findings fails until it joins the map.
