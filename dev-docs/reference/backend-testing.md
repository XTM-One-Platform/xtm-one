# Backend tests

How the backend suites run in CI and the rules that follow from it. `backend/AGENTS.md` keeps the one-line summary.

Locally, `make test` (repo root) runs the unit suite with CI's markers but unsharded (`-m "not integration" -n auto --dist loadgroup`; CI's `-n logical` and shards below) from `backend/.venv`, which it syncs with `uv sync --locked` when `pyproject.toml` or `uv.lock` changes; `ARGS="tests/test_x.py -k name"` narrows it.

## Tests under pytest-xdist

CI runs both suites with `-n logical`, each split between several jobs by `PYTEST_SHARD` (`tests/sharding.py`, `docs/docs/development.md` > "Running tests in parallel"). The unit job splits by file (`PYTEST_SHARD_SPLIT=files`): each job imports only its share of the test files, dealt out longest-first by the per-file seconds of `tests/shard_durations.json`, because collecting the whole suite held about 1.6 GB per xdist worker and left the 8 GB runner swapping until it lost its agent (#10437). The nightly runs measure and publish the table every run deals by, and the committed one is only the fallback (`scripts/shard_weights.py`, `dev-docs/ci-test-selection.md`). In the merge queue each suite collects only the files the change reaches (`PYTEST_SELECTED_FILES`, `tests/selection.py`, `dev-docs/ci-test-selection.md`): a test that reads a file through a path the graph cannot see - built from pieces it never writes - should name the file or its directory, or it runs only nightly. Four rules follow from the split:

- **Deterministic test ids.** A `parametrize` value built at import from `uuid.uuid4()`, `time.time()` or a generated key needs `ids=` / `pytest.param(..., id=...)`: every worker must collect the same ids, or the run stops before a test executes.
- **A PostgreSQL test uses `tests/scratch_database.py`**, never a `CREATE DATABASE` + `create_all` of its own. The schema is built once per process into a template database (keyed by the tables and extensions asked for) and every scratch database is a copy of it; `conftest.py` drops the templates at the end of the session.
- **A tripwire over the backend's own source reads `tests/app_sources.py`** (`python_files()`, `source()`, `tree()`, `walk()`, `parents()`, `modules()`): the tree is parsed once per process and the parsed modules are shared, so a scan never mutates a node. The parsed tree holds about 1.5 GB per process, so the conftest deals the files that name `app_sources` (themselves or through a helper module of `tests/`) into `app_sources.XDIST_GROUPS` xdist groups (`app_sources-1`, `app_sources-2`), longest first by the shard weights: under `--dist loadgroup` one worker per group builds it, not one per worker (#10437; two groups fit the 16 GB runner and stop one worker from ending each job alone). A tripwire never parses `app/` on its own: it reads the shared trees, or it pays the parse again (about 20 s on CI).
- **A module that owns a fixed resource keeps its tests on one worker.** `test_bootstrap.py` starts one backend on port 8099 in a module-scoped fixture (a backend that never becomes ready is stopped with SIGABRT under `PYTHONFAULTHANDLER=1`, so the failure names the phase, never bound or bound and not ready, and carries the thread stacks; `test_bootstrap_fixture.py` pins it); spread over workers, each would start its own and all but one fail to bind. A host-wide name counts too: `install.ps1` stops every process named `xtm-one-runner`, so `test_runner_install_scripts.py` (install.sh, whose tests run stand-in runners by that name) and `test_runner_install_ps1.py` share the xdist group `runner_install_scripts`: one worker per job, while two jobs can each take one file, on two hosts. Such a module marks itself `pytest.mark.xdist_group("<name>")`, which only takes effect under `--dist loadgroup` - CI and `scripts/ci-local.sh` pass it, and a local `-n` run must too.

A separate rule comes from `PYTEST_MARKED_FILES`: **an `integration` or `chromium` test spells its marker in its own file** (`@pytest.mark.integration`, `pytestmark = pytest.mark.chromium`). The Bootstrap and Browser tool jobs set it and collect only the files whose source names `mark.<marker>` (`tests/marked_files.py`): collecting the whole suite cost them two to four minutes. `tests/test_marked_files.py` fails on a test that carries the marker some other way (a conftest's `add_marker` included), which those jobs would never see.

`scripts/ci-local.sh` runs one at a time per clone (`scripts/ci-local-lock.sh`, tested by `tests/test_ci_local_lock.py`): a second run waits for the first. Run it in the background and let it wait; never bypass the queue with `CI_LOCAL_NO_LOCK=1` or by running its steps by hand.

## No flaky test on main

A test red on main, or red on a pull request that did not touch what it tests, is fixed at the root, never re-run and forgotten: a re-run may unblock the pull request, the fix lands the same day. The root fix makes the test deterministic: a fake clock or frame source, an isolated fixture, an explicit ordering, or a skip whose reason carries the measured value that proves the runner cannot run it, with every assertion that does not depend on the runner kept. Lowering a threshold to the last red value is not a fix. `tests/test_video_studio_canvas_alone_6761_chromium.py` is the pattern: its screencast floor is asked only where the page drew the move fast enough to owe it.

The fix is measured before and after: `python -m pytest --repeat 20 tests/test_x.py::test_y` runs the test 20 times in one session (`tests/repeat.py`, declared and registered by `tests/conftest.py`; pytest-repeat is not a dependency, and the same node id given 20 times runs once). Each run is a parametrized case `test_y[repeat3of20]` (beside the test's own ids: `test_y[a-repeat3of20]`), so the JUnit report holds 20 cases, and the terminal summary ends with one line per test: `tests/test_x.py::test_y: 17 passed, 3 failed (failed: 4, 9, 15)`. It works under xdist (`-n`), takes 1 to 500 (1, the default, changes nothing), and runs through the sandbox's declared `backend-unit` check with `args: ["<node id>", "--repeat", "20"]`. `tests/test_repeat_option.py` pins it.

## A hung test fails fast and names itself

CI sets `PYTEST_STALL_SECONDS` (300) on the backend and bootstrap test steps. `tests/stall_guard.py`, armed by the suite's `pytest_runtest_protocol` hook, runs each test under `faulthandler`'s watchdog: a test still running past the bound writes the stack of every thread to `$PYTEST_STALL_DIR/stall-<worker>.log` and ends its worker, which xdist reports as crashed while running that test. The step's "Stall report" prints every report that is not empty. Without it, a hang ate the rest of the step's 25 minutes and failed the run with a step timeout that named no test. Unset, the guard does nothing (local runs, the sandbox checks). The longest integration test on main runs about 72 s; a test that needs more than the bound is split or made faster, not exempted.

The unit step also sets `PYTEST_MEMORY_REPORT`. `tests/memory_report.py`, through a second `pytest_runtest_protocol` wrapper, reads each worker's resident set size (`/proc/self/statm`) before and after every test and adds the difference to the test's file; at the end of the session each worker writes `memory-<worker>.txt`, the 25 files that added the most memory and kept it, with their test count and the worker's size at its first and last test. The step's `Memory report` prints them on every run, red or green, so a shard close to the runner's memory names the modules to bound (#10437). Unset, the hook only reads the variable.

## A degraded runner is named, not mistaken for a code red

A GitHub-hosted runner is sometimes three to six times slower than usual: a shard then collects for 7 to 18 minutes instead of about 1.5, hits the step's 25-minute timeout at a quarter of its tests and fails with no FAILED line (runs 42457304415, 42562920294, 42766031078). The backend and bootstrap test steps start `python -m tests.runner_speed` in the background before pytest, with `PYTEST_COLLECTION_MEDIAN_SECONDS` (90 on the backend shards, 70 on the bootstrap shards: 84 to 102 s and 62 to 74 s on green main run 42767506994) and `PYTEST_COLLECTED_MARKER`. The suite's `pytest_collection_finish` writes the marker; once collection has run past three times the median without it, the watcher prints one `::error::runner degraded: collection Ns vs median Ms` annotation, which the job summary and the failure blocks of the log show before the timeout. At the marker it prints `[runner] collection Ns` on a plain line, red or green. A green run shows no annotation. It never loosens a timeout and never retries; a shard whose collection grows for a code reason moves its median in `ci.yml` in the same pull request. Unset, the watcher returns at once and the marker is not written.

## Unit tests meet no Redis

CI's unit job starts no Redis. `tests/conftest.py::_no_redis_in_the_unit_suite` gives every test not marked `integration` the same (`tests/redis_unreachable.refusing`): the shared client and pool of `app.core.redis` are swapped for a fresh pair, and redis-py's socket connection classes, asyncio and sync (switched once per session), refuse every connection, so every client - shared, pub/sub, the SAQ queue's, a Sentinel's, a sync `redis.Redis` - raises `redis.exceptions.ConnectionError` without touching the network. None of it goes through the test's `monkeypatch`: its `undo()`, or a patch of the same names, can neither lift the refusal nor carry it into the next test. A run on a machine with Redis neither reads nor writes it. A test OF Redis-backed code fakes `redis_client` itself; a test that needs the real one is an `integration` test.

## Live LLM smoke suite (opt-in)

`tests/live/` (marker `live_llm`) sends the platform's own provider requests - built by `llm/router.build_provider()`, tool-loop transcripts shaped like `tools/agent_loop.py`'s - to the real Anthropic, Gemini and OpenRouter APIs, to catch a request the API refuses (a 400 a mocked SDK never raises). It is skipped unless `LIVE_LLM_SMOKE=1` AND the provider's `LLM_PROVIDER_<PROVIDER>_API_KEY` are set, so CI and every normal run collect it and skip it without a network call; `tests/test_live_llm_gate.py` pins that gate and fails if a workflow mentions the flag. It spends real money (cents per run) and never runs in CI. Run it after changing what a provider sends (a `thinking` / `output_config` form, a replay, a new parameter): `tests/live/README.md`.
