# Progressive tool disclosure (tool gating)

How `tool_gating.py` reveals large tool sets on demand through the `load_tools` meta-tool, fits them to the provider's `max_tools` cap and resolves model-supplied tool names; the rules of this area live in `backend/app/tools/AGENTS.md`.

## 3b. Progressive Tool Disclosure (the "tool multiplexer")

Implemented in `tool_gating.py` and wired into `run_agent_loop`. Sending every tool schema on every turn is expensive — a trivial `"hello"` pays the full tool-definition token cost for tools it never uses, and large flat tool lists degrade tool-selection accuracy.

Instead, when an agent has many tools the loop:

1. Partitions tools into an **always-on core** (built-ins: KB search, memory, handover, agent builder) and **gateable groups** keyed by `source` — one per integration provider (`integration:notion`), one per channel-bot provider (`channel_bot:slack`, every bot of that provider in one group), one per MCP server (`mcp:GitHub`), and one for all custom tools (`custom`). Any other source is always-on (`tool_group`), except the large **built-in groups loadable on demand**: a group of the built-in registry (`app/services/builtin_tool_groups.py`) that declares a `core` keeps those functions (its create and read functions) always-on, and its other functions are gated as `builtin:<id>` (labelled with the card name), loaded like an integration. The loop passes `builtin_on_demand_groups()` to `build_tool_gate(on_demand=...)`, so the gate holds no product list; a group without a `core`, and any tool flagged `core=True`, stays always-on whole. Today: `agent_builder`, `flow_builder`, `fleets`, `generate_presentation`, `video_studio`, `template_authoring`, `platform_insights`; `tests/test_builtin_on_demand_groups.py` pins every core name to a function of its group and checks that the default General Assistant answers a presentation, report, file and web request without a `load_tools` call.
2. Injects a compact **catalogue** (group id + label + count + sample names) into the system context — a few dozen tokens instead of full schemas.
3. Exposes a single `load_tools(groups=[...], tools=[...])` meta-tool. When the model calls it, the loop reveals that group's full schemas for subsequent iterations (the call is handled inside the loop — it never routes through the executor). Revealed groups stay visible for the rest of the loop unless the provider cap below forces an eviction.

A simple turn answers from the always-on core and never pays for the gated schemas; a real task issues one `load_tools` call, then proceeds.

**Loaded groups persist across the turns of a conversation**. The gate is built per `run_agent_loop` call, but the transcript the caller hands in is the durable record of what earlier turns loaded: right after the gate is built the loop calls `ToolGate.preload_from_transcript(messages)`, which reads every `load_tools` call an earlier assistant turn made (its `groups` / `tools` arguments) and every tool call and tool result name of those turns, resolves them through the same resolver dispatch uses, over THIS gate's tools only (a tool the agent no longer carries, or a tool of the agent a conversation was transferred from, is skipped - a preload never widens the surface, and execution stays scoped by the executor whatever is visible), and reveals at most `_PRELOAD_MAX_GROUPS` (6) of them - the most recently used, oldest-first / most-recently-used-last - so an LRU eviction under the provider cap keeps the groups the conversation used last, and a long conversation that touched many integrations does not put every schema on every request (an older group is one `load_tools` away, as before). A follow-up turn on Notion / HiBob / Metabase starts with their schemas on the wire instead of paying a `load_tools` round-trip, and the catalogue gains no line for them (invariant 16: its intro already says a visible tool needs no loading; `ToolGate.preloaded_group_ids` is for the log). The preload is best effort: historical `load_tools` arguments are read as the loop reads a live call (`_string_items`: a number or a boolean names nothing), and the loop catches anything it raises - a history the preload cannot read costs the preload, never the turn. Conversation compaction can drop the old tool calls from the loaded history; the groups then simply need one load again.

**Activation** (both must hold): `settings.progressive_tools_enabled` (default `True`, overridable per-call via the `progressive_tools` argument) **and** the number of gateable tools ≥ `settings.progressive_tools_min_tools` (default `16`). Below the threshold, or when no executor is provided (e.g. dry-run previews), the legacy "send everything" path is used unchanged.

The gate only controls **which schemas the LLM sees** — every tool stays registered in the executor, so tool *execution* is unaffected.

**The provider's `max_tools` cap is enforced on the VISIBLE list, never on the inventory**. `max_tools` is a property of the wire — how many schemas one request may carry (128 on OpenAI-compatible providers, 1024 on Anthropic; per model on the AI Gateway, by the upstream its `/v1/models` names — read through `max_tools_for(model)`) — and with gating active only the visible list is ever on the wire. The loop therefore hands the cap to the gate as `max_visible` and leaves the agent's tool inventory whole: the catalogue lists **every** group on every provider, and `ToolGate.visible_tools()` can never exceed the cap. When a reveal does not fit, the gate first **evicts the least recently used** revealed group(s) — recency is refreshed on reveal *and* on every tool call (`touch()`), so a group in active use is never the one evicted — and reports the eviction in the tool result; the model can simply load the group again. **A tool the run has called is pinned** (`touch()` records it, `ToolGate.called_tool_names`): eviction first takes only as many UNCALLED tools of the least recently used group as the load needs (`RevealResult.trimmed`, reported as "Unloaded the tools not called yet to make room"), so a sandbox or GitHub tool used earlier in the run stays on the wire; a group goes whole, called tools included, only when no uncalled tool is left. A named load never displaces a called tool, `set_max_visible()` drops uncalled tools before called ones, and a `no_room` answer names what fills the budget (each loaded group with its loaded and called counts) and points to the per-tool load (`tools=[...]`, names found with `search`). A single group larger than the remaining room is **revealed partially**, highest `tool_retention_key` first (builtins, then per-tool `priority`), the unrevealed remainder is listed by name in the result — **every** name, never an "and N more" summary, because that list is the model's only handle on the rest of the group — and any of them is reachable **by name** through the `tools=[...]` argument (a named load that finds no other room displaces the least important visible tool of its own group — never one this same call loaded). Re-loading a group that is already as loaded as the budget allows, with nothing else evictable, is a one-line no-op (`RevealResult.at_capacity`) rather than another partial reveal, so a repeated call never re-emits the not-loaded list. That listing is **not durable**, though: it is an ordinary tool result, and `_clear_stale_tool_results()` / `_prune_session_context()` stub older results out of the context once they are stale — so the remainder must be **re-fetchable** without relying on the first result still being in the transcript. That is the `search` argument of `load_tools` (`ToolGate.search()` / `describe_search()`): keyword(s) matched against the name and description of every gated tool (all words must match, case-insensitive), scoped to `groups` when both are given, returning the exact not-loaded names (most important first, with their group) **bounded** to `_SEARCH_RESULT_LIMIT` — the model narrows a wide match, the context is never re-inflated — plus the matches that are already loaded so the model calls them instead. The scope is literal: no `groups` = every gated group plus the always-on core, whose matches are listed as already loaded (a search that skipped the core answered a core tool's name with "No not-loaded tool matches" alone, and the model concluded the tool did not exist although its schema was on the wire), `groups` given = **only** the groups that resolve, and when none of them does the search covers *nothing* and the result reports the unknown token(s) with a hint to check the catalogue or omit `groups` — a misspelled group must never silently widen into a catalogue-wide search that answers with unrelated tools. The not-loaded cut is *"least important first, across every searched group"*: all matches are collected first, ranked by the one `tool_retention_key` a partial reveal and LRU eviction already use, and sliced only then, so a `priority=0` tool in the last group searched is never hidden behind forty default-priority matches from the first (the query is split into `\w+` tokens, so punctuation separates words instead of turning a hit into a miss). The already-loaded list is capped as well — at the much smaller `_SEARCH_LOADED_LIMIT`, with a `+N more loaded match(es)` marker when cut — because those schemas are on the wire already: it is a reminder, not a handle, and an uncapped one would re-list hundreds of visible names after a broad search. A search is read-only (no recency, no visibility change) and a search-only call gets only the search text, never a "nothing was loaded" line for a load it did not request. The at-capacity retry and the unknown-tool refusal both point to `search`, so the recovery path is discoverable from the very message that omits the names; this is tool-result text, not system-prompt text. When the cap binds, the catalogue carries one extra "Tool budget" paragraph; the "N tools were unavailable this run" notice is emitted only on the legacy ungated path — a gated run **never drops a tool**. The always-on core is fitted to the budget by `_fit_core()`, and the invariant it keeps is that after the core is placed **one slot is left for `load_tools` and one for a gated tool**: the core is trimmed to `max_visible - MIN_GATED_BUDGET` (the same two slots the floor below reserves), because a core that fills the cap leaves a gate that catalogues groups every `load_tools` call answers with `no_room` — the core is never evicted, so nothing could ever make room. This is realistic, not theoretical: a 64-tool provider with a large built-in suite enabled reaches it. The core tools that do not fit are **demoted, not discarded**: they move into a synthetic gated group, `CORE_OVERFLOW_GROUP_ID` (`builtin:overflow`), listed in the catalogue and in the meta-tool's `groups` enum like any other group and loadable by group or by exact name (`ToolGate.demoted_always_on` records them; `set_max_visible` returns them as its second element). The catalogue therefore lists every tool that is reachable and nothing that is not. Cutting the inventory to `max_tools` before building the gate would instead remove tools from the catalogue itself, beyond the reach of `load_tools` (an agent bound to ~770 integration tools would keep 128 on an OpenAI-compatible provider). A per-call provider **failover** (`llm/router.FailoverLLMProvider`) is deliberately *not* a re-cap: the wrapper retries the primary on every call, and the loop reads which model served a call (`last_model`) only to attribute its usage, so the gate stays budgeted to the primary's cap and only the one failed-over request is trimmed to the fallback model's cap (`_fit_tools`, ordered by the same `tool_retention_key`, so the always-on core and `load_tools` always survive and that single reply merely misses the tail of the visible list). A **decline route** is the exception: the wrapper sends the rest of the run's calls to the decline fallback, so `max_tools_for` follows the route and the loop, which re-reads the cap at the top of every iteration, re-caps the gate when it changes (`_follow_model_cap`, the same `set_max_visible` and catalogue rewrite as a downgrade, with the unloaded groups named to the model; on the legacy ungated path it re-cuts the wire list from the untrimmed one, so a cap that rises — e.g. once a failed `/v1/models` listing succeeds — restores the tools a lower one dropped and tells the model). The *sticky* switch — a budget-driven model downgrade — is the one that re-caps the gate (`set_max_visible`); its guard compares the **required** surface (the gate's `required_budget` — always-on core + `load_tools` + one slot for a gated tool, so that re-capping never has to demote a core tool the model has been using as always-on — or the whole list on the legacy path) against the fallback's `max_tools`, *without* counting the `wait` timer: `_with_wait_tool` only appends the timer while the offered list is below the cap, so a surface that exactly fills the fallback still yields a valid request with the timer omitted, and counting it would refuse that exact-fit fallback for a slot the timer yields anyway. Gating also has a **floor**, `MIN_GATED_BUDGET` (= 2: the `load_tools` meta-tool plus room for one real tool): a gate always sends the meta-tool, so on a `max_tools == 0` provider it would break the cap with a single schema, and on `max_tools == 1` it could never reveal anything. `build_tool_gate` returns `None` under that floor and the legacy path truncates the wire list to the cap instead (to zero on a zero-tool provider — the providers themselves declare 64–1024, so this is the zero-tool stub the failover/selection tests already use, not a production model), and the downgrade guard refuses a fallback below the floor for the tool-calling phase (`set_max_visible` raises on such a cap): a gate is never re-capped below what it could have been built on, and switching a gated run to the legacy path mid-flight would drop the catalogue the model has been told about — the same "worse than stopping" the count guard enforces. The tool-free closing synthesis may still degrade onto such a provider; the gate is then simply left as it is. It rewrites the catalogue system message **in place** (the loop keeps the message by identity; compaction preserves `system` messages) because the budget paragraph is part of that text and the fallback's cap may bind where the primary's did not — an appended notice would leave the stale catalogue in front of the model. Anything that describes "the tools this request offers" is read from the **live** visible set through `_offer_at(iteration)`, never from a snapshot taken at the top of the iteration: the downgrade happens *inside* the iteration, after the Langfuse iteration span was opened, so the span's `available_tools` is refreshed (`update_iteration_span_tools`) once the re-cap succeeded, and the one-shot capability-not-found nudge lists what the *next* request will carry — otherwise both would still name the group the re-cap just evicted. Recency is also refreshed for the sibling calls of a mixed response **before** its `load_tools` call is processed: a response that calls into group A and loads group C in one batch must not evict A as the least recently used group, and an unloaded group can no longer be touched back. Recency alone is not enough when one response carries **several** `load_tools` calls (the first reveal makes its own group the newest, so the second could evict A), so the loop seeds one `protect` set with the groups in use (`ToolGate.groups_in_use`) and passes that same set to every `reveal()` of the response — each reveal adds what it loaded, so a group being called into, or loaded by an earlier meta-call of the same response, is never evicted; the request that does not fit becomes `partial` / `no_room` instead. Every gate lookup keyed by a model-supplied tool name (`touch()`, `groups_in_use()`, `load_tools(tools=[...])`) resolves through `base.ToolNameResolver` — the **same** exact / unambiguous-reordered-tokens / known-alias rules `CompositeToolExecutor` and `ScopedToolExecutor` dispatch with — so a call the executor runs (`jira_search_issues` for `search_jira_issues`, `list_github_issues` for `search_github_issues`) always refreshes its group, and a name the executor would refuse (ambiguous token key) touches nothing. That resolver is built over the **whole offered surface** (always-on core + every gated tool), never over the gated tools alone, and the loop hands the gate the very instance `_ExecutorNameMap` dispatches with (`build_tool_gate(..., resolver=_tool_name_map.resolver)`): the invariant is that **the gate resolves a name to the same tool the executor dispatches it to**. A resolver over the gated names alone would break it: with core `jira_search_issues` and gated `search_jira_issues` in one surface, dispatch runs the exact core tool while such a gate would token-match the same call to the gated one and protect its group, so a sibling reveal would evict the wrong group or report `no_room`. Over the full surface the exact core name wins as it does in dispatch, and a name ambiguous *between* a core and a gated tool is refused by both. `_resolve_tool()` then returns a hit only when the canonical name is a **gated** tool (`_tool_index`); a call that resolves to an always-on tool touches and protects nothing (the core is never evicted, so there is nothing to protect) and naming one in `tools=[...]` is a no-op, not an unknown name. Never re-implement any of those rules at a call site — and never *pre-process* the name before handing it to the resolver either (no `strip()`, no case folding): the gate and the executors must accept **exactly** the same strings, or a padded `" jira_search_issues "` protects a group whose call the executor then refuses. Within one `load_tools` call, group tokens and tool names are **deduplicated after resolution** (`notion` and `integration:notion` are one group), so an oversized group named twice is revealed once — never a partial reveal followed by an `at_capacity` note for the same group in the same result. Name spaces matter here: the gate is built from `effective_tools`, i.e. the **sanitised, collision-suffixed** definitions, so it lives in the LLM-visible name space and the loop hands it the model's call names **verbatim** (`touch`, `groups_in_use`, `load_tools(tools=[...])`) — never reverse-mapped through `_tool_name_map` (with originals `a.b` / `a/b` exposed as `a_b` / `a_b_2`, a call to `a_b_2` mapped back to `a/b` would token-match `a_b` and touch or pin the wrong tool). The executors live in the **original** name space, and the only place the loop reverse-maps is executor dispatch (`_exec_call`) — through `_ExecutorNameMap`, which **canonicalises in the LLM-visible space first** (the same `ToolNameResolver` rules, over the sanitised `effective_tools` names) and only then reverse-maps: `b_a_2` -> `a_b_2` -> `a/b`. Reverse-mapping exact visible names alone would let the gate and dispatch disagree (the gate would accept and protect `b_a_2`, and the executor, handed `b_a_2`, would refuse it: no original carries the synthetic `2`); the invariant is that **every name the gate accepts is a name the executor executes**, and a name neither stage resolves (unknown, ambiguous) is forwarded untouched for the executor's own refusal. The known-alias table is keyed by **original** names, so it too has to cross into the visible space before either resolver may use it: with originals `search.github.issues` and `search_github_issues` in one surface the sanitiser assigns `search_github_issues` to the *first* and `search_github_issues_2` to the second, and the original-name table, applied verbatim, would route the alias `list_github_issues` to the dotted tool. `base.visible_aliases(original_to_visible)` translates each alias through its canonical original's assigned visible name (`-> search_github_issues_2`), drops an alias whose canonical original is not in the surface (never let it dangle onto an unrelated visible name) or whose key a real visible tool already owns, and the loop builds that table **once** and hands the same one to `_ExecutorNameMap` and `build_tool_gate` — so gate and dispatch cannot disagree on what an alias denotes; the executors' "Did you mean" hint (`_format_tool_not_found`) is fed the same translated table over the same visible listing. Every dispatch-side "which tool did the model mean" (`_exec_call`, wait-round detection, dedup keys, the terminal-tool decision, schema lookup for pre-execution validation) goes through that one map. `describe_reveal` never follows an `at_capacity` or `no_room` paragraph with the generic "did not match anything" line: those requests *did* match, and the specific paragraph already says why nothing moved.
