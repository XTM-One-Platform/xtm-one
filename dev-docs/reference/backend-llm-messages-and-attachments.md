# LLM messages, attachments and provider extras

Message conversion shared by the providers (images, SVG, tool-result order, Converse role alternation), the per-request attachment budget, and how provider replay data is weighed by the context gates; the rules of this area live in `backend/app/llm/AGENTS.md`.

## Shared Message Conversion Helpers

`base.py` exports the OpenAI-format message conversion shared by `openai_provider.py` and `openai_compat.py` (and all subclasses: OpenRouter, Ollama, Mistral, SpaceXAI, Azure OpenAI, LiteLLM, Custom OpenAI, Filigran AI Gateway):

| Function | Purpose |
|----------|---------|
| `build_openai_messages_async(messages, provider_key, *, context_window)` | What every OpenAI-format path runs (`chat()`, `chat_stream()`, `chat_stream_with_tools()`): system, user (with multimodal images), assistant (with tool calls) and tool-result messages, with attachments resolved under one request budget (`resolve_payload_files`) |
| `build_openai_messages(messages)` | The synchronous conversion without file resolution, which the async one falls back to for messages without files |

**Tool-result `ChatMessage.files` (runner / browser screenshots) must become native vision blocks**, not a `[File: name (N bytes)]` stub and not Markdown-only. Anthropic and Bedrock put images *inside* `tool_result` / `toolResult` content (the computer-use shape). Gemini puts `Part.from_bytes` on the same user turn as the `function_response`. OpenAI Chat Completions `role=tool` cannot hold `image_url`, so the pixels ride on a follow-up user message with `detail: high` after the tool result (`TOOL_RESULT_VISION_NOTICE`). Optimize those images with `detail='high'` (PNG preserved, 2048px long-edge) — JPEG 85 + 1568px is the photo path and destroys UI text.

When adding a new OpenAI-compatible provider, use these helpers instead of re-implementing message conversion. Anthropic, Gemini and Bedrock (Converse) have their own format and do not use these helpers.

### SVG images become PNG through the one bounded rasterizer

No vision provider accepts `image/svg+xml`, so an SVG (a chat upload, a user-message image, a tool-result image - detected by its bytes, whatever it is declared as) is rasterized to PNG before it reaches the model, in `base.py` via the shared `app/services/svg_raster.py`. The markup is untrusted, so the render is bounded there (defused parse with bounded internal entities; nothing outside the document is ever fetched or read - a non-local reference is dropped and the rest renders, or the whole SVG is refused under `SVG_STRICT_RENDERING`; a shape budget, a filter budget, a nesting limit, a pixel box; absolute units at 96 dpi, the CSS definition every browser draws them at - the SVG's own size (`width="432pt"`, an em under a `font-size` in pt) and every `12pt` font size, `1mm` stroke or `8mm` nested viewport inside it, which resvg-py's default 0 dpi read as 0; the async renders cached per exact bytes) - see that module and its row in `dev-docs/reference/backend-services-tools.md`. An SVG with no absolute length renders byte for byte as it did; the logo geometry keeps `dpi=0`, so a stored trim box never moves. `_detect_image_mime_from_bytes` finds the `<svg>` root past a DOCTYPE's internal subset, so an Illustrator export reaches the rasterizer. resvg holds the GIL, so **every `async def` awaits the async variant** (`prepare_base64_image_for_llm_async` / `prepare_image_bytes_for_llm_async` / `_rasterize_svg_to_png_async`), which renders in a worker process off the event loop - the only place the render is also bounded in time and memory; the sync `prepare_*` / `_rasterize_svg_to_png` are for sync callers only. `test_svg_raster_bounds.py::test_no_async_function_prepares_images_on_the_event_loop` is the AST tripwire that fails the build if an `async def` calls a sync rasterizing function (`svg_raster.rasterize_svg` and `image_geometry.analyze_image_geometry` included). A refused or failed render returns `None`, and the caller substitutes `IMAGE_UNAVAILABLE_TEXT`.

**Tool results go out in the model's call order.** The agent loop answers some calls of a batch in place before the rest runs (a validation failure, a loop-breaker refusal, a call cut by the tool-call budget), so the transcript can hold a turn's results out of call order. Gemini pairs a `function_response` with its call by position (the part carries the name, never the call id), and so does whatever an OpenAI-format or Bedrock request reaches when the id is dropped on the way (a proxy to Gemini, a local model's chat template). Every builder - `_build_anthropic_messages`, `_build_converse_messages`, `_build_gemini_contents`, `build_openai_messages` / `build_openai_messages_async` - therefore iterates `tool_results_in_call_order(messages)` from `base.py`: each run of consecutive tool messages is stably sorted by its assistant turn's call order (ids the turn does not know stay last) and every other message keeps its index, which is what the payload file plan is keyed on. A new builder runs it too.

**A Converse request alternates roles.** Bedrock refuses two consecutive messages of one role, and a transcript holds such runs (a message right after the tool results it follows - steering, the resumed work of an interrupted turn - or a mid-turn segment stored before its answer). `_build_converse_messages` merges each run into one message (`_alternating`), blocks in order, so tool results stay first in their user turn. The Anthropic API merges consecutive turns itself; OpenAI-format requests take them as they are.

## Attachments: one budget per request (`file_resolver.py`)

Every text the resolver puts in front of the model for a file - the extracted text's header, the size stub, the duplicate and omitted stubs, a tool-result document - starts with `file_label(file_ref, detail)`: `[File <file_id><detail>]`, then the stored name in a `stable` `wrap_untrusted` block. The name is often a third party's text (a downloaded document's title, an email attachment's name) and is re-read on every request, so it never sits in the label itself; the kind the label shows is the extension only when it is in the fixed `_LABEL_KINDS` list (not `mimetypes`, whose table depends on the image's `/etc/mime.types`, which would change the label and miss the prompt cache from one process to another), else `FILE`.

The other places a stored name could reach a request follow the same rule: the OpenAI-shaped builder's stub for a native non-image file is a `file_label`; Bedrock's document block `name` - a plain string Converse reads as part of the prompt, which cannot hold a block - is `File <file_id> (<kind>)` (`bedrock_provider._document_name`, no other provider names a native document block); the user message the chat upload route writes (`create_message=True`) and the public widget's document text (`widget_uploads.document_text`) open with `upload_header(file_id, filename, detail)` - `[File: <file_id><detail>]`, a blank line, then the name's block (`file_name_block`) - which keeps the `[File: ` shape `agent_chat.strip_file_content_from_history` strips from older turns and the web chat reads as an upload message. The widget chooses the row's id before the guard screens the text, so the guard reads exactly what the model will. The image-preparation log labels name the file by its id too. In the attachment texts these paths and the resolver write, the one part still derived from the name is the code-interpreter mount path of `inline_truncation_footer`, which must be exact and is bounded by `code_interpreter.safe_mount_name` instead.

Chat attachments live in the conversation history and are **re-sent on every turn** (`get_conversation_history` rehydrates them so a file stays readable after the turn it was uploaded on). Resolved one file at a time, nothing would bound their sum: a conversation carrying the same PDF three times reaches Anthropic's 1M-token and 600-page request caps, and from then on EVERY turn fails, because the payload being refused is the history itself.

`resolve_payload_files(messages, provider_key, context_window=...)` is therefore what every provider's message builder runs, through its `_prepare_request(messages, tools, model)` helper (Anthropic / Gemini / Bedrock) or `build_openai_messages_async(..., context_window=)` (OpenAI-shaped). It resolves the user-message attachments of the whole request **together, newest first**, and returns a `PayloadFilePlan` the builder reads per `(message_index, file_index)`:

- the same bytes (sha256, hashed off the event loop) already kept from a LATER message → a one-line stub naming that copy; a re-attached file is sent once;
- an image → native, always (bounded by the image optimizer, counted per image by the overflow check);
- a PDF over the provider's per-file page cap → text;
- a PDF that fits the request's remaining **page cap** (`PROVIDER_PDF_PAGE_LIMITS`, spent over the whole request) AND **token budget** (`attachment_token_budget` = `ATTACHMENT_WINDOW_SHARE` of the model's context window) → native, costed at `PDF_TOKENS_PER_PAGE` per page;
- otherwise — including every file the provider does not take natively (OpenAI-shaped providers take no PDF at all) and a file whose download failed → extracted text if its characters fit the remaining budget, else a stub saying the file was omitted and can be re-attached. Every stub is charged to the budget too: it is sent, so it is spent.

The files of the request's **current user turn** — the last user-role message, whatever tool results or assistant turns follow it in the agentic loop — are never stubbed: a turn that cannot see its own attachment is not worth saving (they still degrade from native to text; whether that text fits at all is the overflow check's call). An attachment on an EARLIER user message is history and may be stubbed even when no later message carries a file — protecting it forever would let one oversized fallback fail every later turn of the conversation.

`NativeFile.pages` carries the page count so `_check_resolved_overflow(..., native_document_tokens=plan.native_pdf_tokens)` costs the kept PDFs by their pages, not by the byte proxy (`_BYTES_PER_NATIVE_TOKEN`, used only for the document types nobody can page-count), which would read a 592 KB PDF as ~2,400 tokens that the API bills at hundreds of thousands. `resolve_file()` stays the single-attachment entry point (tool-result screenshots, a file a builder meets outside the plan) and knows nothing about the rest of the request on purpose. When the provider still refuses for size, the PDF page cap message is a `REQUEST_TOO_LARGE_KEYWORDS` entry, so it gets the same graceful handling as a 413.

**The work is done once, not per request.** Every request of a run resolves the whole history again, so everything that is a pure function of a file's bytes is memoized process-wide in `attachment_cache.py` (bounded LRU maps, stdlib only): a download by object key and size (`STORED_BYTES`, forgotten by `file_storage.delete`), its sha256 (`CONTENT_DIGESTS`), a PDF's page count by digest (`PDF_PAGES`) and an image's provider-ready form by input digest, declared type and detail (`PREPARED_IMAGES`, `None` for an unusable image included). An async builder prepares images through `prepare_image_bytes_for_llm_async()` / `prepare_base64_image_for_llm_async()`, which run a miss on the image preparation pool (`parse_offload.run_image_prep`, never the document parse pool, where a request would queue behind a knowledge-base ingestion) - never the sync functions inline, which stall the event loop ~230 ms per Retina screenshot on every request - and `resolve_payload_files` downloads a request's missing attachments a few at a time. A plain text extraction is memoized per content hash like a rendering (`attachment_extract._plain_key`); for an HTML / JSON / CSV attachment the inline rule keeps its plain text only when it is inlined and remembers the LENGTH of one too long to inline (`attachment_extract._plain_lengths`), so such a file is neither extracted again on every request - the render memo keeps no entry over 4,000,000 characters and an upload reaches 40 MB - nor held next to the rendering inlined in its place, where it would push that rendering out. A text the render memo cannot hold (a large CSV rendering, which carries the whole file after its digest, or a large text file) is remembered by what the inline surfaces read of it - its first `limit` characters and its lengths, `attachment_extract.inline_attachment_text()` / `_inline_heads` - never by the whole text. Never add per-request work on attachment bytes without a memo; the tests reset every map around each test (`conftest._reset_attachment_cache`).

## Provider extras: what a message weighs when it is sent

`ChatMessage._provider_extra` is replay data only the provider that wrote it understands, and that provider sends it back on every later request of the run - so it is part of what each of those requests weighs. Gemini keeps a tool-calling model turn's raw parts under `GEMINI_PARTS_KEY` (`gemini_parts`: the thought parts `include_thoughts` returns, the answer text, the function calls, and the thought signature that can ride on any part) and replays them verbatim IN PLACE of the message content. Function calling needs the signatures back where they were received (a Gemini 3 call without its signature is a 400; the SDK's own chat helper replays the same way), so the parts are never stripped or rewritten to save space. Weighed as `len(content)` alone, a Gemini tool loop whose weight is its thoughts would reach no compaction threshold, leaving the provider's own overflow check as the only safeguard: the hook below lets the context gates weigh what is actually sent.

The hook, in `base.py`:

| Name | Contract |
|---|---|
| `register_provider_extra_counter(key, counter)` | Declares what `_provider_extra[key]` adds to a request. `counter(message, value) -> int` returns the characters the provider sends for the message BEYOND `message.content`; a negative answer counts as zero, and a counter that raises counts zero (logged once per key) - a measure never fails the turn it measures. Register it at import, next to the code that replays the data, under a key exported as a constant there (`GEMINI_PARTS_KEY`); a key belongs to the one provider that writes it. It runs on every pass of the loop's context gates, several per iteration: a counter that serializes keeps its measure of the value on the message and reuses it while the value is the very same object (Gemini's `_gemini_parts_measure`), reading the live `content` every time. |
| `provider_extra_chars(message)` | The registered counters summed over the message's extras keys; zero without extras and for a key nobody registered. Counted whoever answers next: after a cross-provider failover the figure over-states the request, the safe direction for a gate. |
| `message_payload_chars(message)` | `len(content)` plus `provider_extra_chars(message)`: the ONE measure every agent-loop context gate reads (`dev-docs/reference/backend-tools-context-compaction.md` > "3c. Context management & compaction"). A message without extras weighs exactly its text. |

Rules for a provider that keeps replay data it must re-send (Gemini's `gemini_parts`; the Anthropic guarded thinking-block replay's `anthropic_thinking`, is deliberately not registered - see "Which gates read it" below):

- **One counter, shared with the provider's own overflow check** - never a second copy of the counting. Gemini's is `measure_gemini_parts(parts)`: `_measure_gemini_payload` runs it over the whole payload, the `gemini_parts` counter over the replayed turn, so the loop and the provider cannot disagree. It counts every text part, a thought part included; a function call's name and JSON arguments and a function response's name and JSON payload, as `_measure_oai_payload` counts tool calls (so a call with a large structured argument is not reduced to its signature, and the provider's check counts the tool results it sends); and a thought signature at its wire size (the base64 of its bytes): Google bills a signature as input when it is sent back.
- **Say what the data adds relative to how the provider sends it.** Gemini sends the parts in place of the content, so its counter returns the parts' size minus `len(content)` (the message weighs whichever is larger, and an empty part list adds nothing). A provider that sends the content AND the extras returns the extras' size alone.
- **Read the live message on every call**, never a count cached at response time: a gate that truncates the content in place is then re-measured, and one that drops the message drops its extras.
- **Which gates read it.** Every registered counter is read by every gate: the compaction trigger and target, the 95% overflow guard and the emergency prune's eviction, the forced-answer guard, the per-run budget reservation and the context readout all weigh a message through `message_payload_chars`. So only data the provider MUST re-send is registered. Data the provider may drop on its own when a request would overflow (a best-effort replay) is never registered: the provider owns it and sheds what does not fit, and counted in the gates it would make the loop compact, evict whole turns, stop the run or raise `ContextOverflowError` to make room for data the provider strips anyway. The Anthropic thinking-block replay (`anthropic_thinking`) is that case: droppable, counted and shed by `AnthropicProvider._prepare_request` alone, and pinned unregistered by `test_the_replayed_blocks_are_never_registered_on_the_loop_gates`. The contract is per gate: a counter tier some gates leave out is declared here, with the gates that read it, before any droppable data is registered.
- **Cheap and synchronous**: the counter runs over the whole transcript in several gates of every iteration, on the event loop - linear in the size of the value, no hashing, no request building, no I/O.
