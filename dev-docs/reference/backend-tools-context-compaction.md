# Agent loop context management and compaction

How the agentic loop keeps its context focused inside one turn: tool-result budgets and clearing, vision retention, the file-recovery guard, the dedup cache, semantic compaction, the emergency prune and their triggers; the rules of this area live in `backend/app/tools/AGENTS.md`.

## 3c. Context management & compaction (layered, signal-driven)

LLM performance degrades as the context window fills (models "lose focus" and can return empty turns well below the hard token limit). XTM One follows the industry best practice (Anthropic's server-side Compaction API; the Claude Code multi-layer compaction pipeline): keep the working context **focused** with a layered set of strategies, cheapest first, and reserve the expensive layer for when it's actually needed.

The layers, in `agent_loop.py`:

1. **Budget reduction** — `_truncate_tool_result()` caps any single tool result at `max_tool_result_chars` (derived from the provider's context window) when it is appended.
2. **Tool-result clearing** — `_prune_session_context()` replaces the *bodies* of the oldest tool results with a compact stub, keeping the most recent `_RECENT_TOOL_RESULTS_KEEP` intact; the always-on `_clear_stale_tool_results()` does the same by BYTES (a live budget from `_compute_live_tool_result_budget`) and `_collapse_redundant_tool_results()` stubs exact duplicates. Independently, `_clear_stale_tool_result_files()` bounds the native vision attachments (screenshot / downloaded-image Markdown is too short for body-based pruning, but the pixels are expensive). The rules below keep a tool result, and its images, in front of the model until it has used them:
   - **A tool result is not curated until a successful provider request has carried it.** The three always-on passes and the proactive compaction gate's `_prune_session_context()` run at the top of an iteration, BEFORE the request that carries what the previous iteration appended, and every one of them takes the loop's `is_unseen` predicate (`_unseen_tool_result_predicate()` over `consumed_tool_results`, an identity map the loop fills with the caller's history at entry and with the whole transcript after every completed in-loop LLM call — `_mark_tool_results_consumed()`, so a timed-out or failed request leaves the results protected for the retry; strong references, so a compaction-dropped message can never lend its `id()` to a new one). The forced-answer backstop's prune takes it too: the iteration cap or the wall-clock guard can end the loop right after a batch was appended, and the synthesis request is what shows that batch — the count-based prune (`_RECENT_TOOL_RESULTS_KEEP` = 4) would otherwise stub the first results of a wider batch before the model had read them. An unseen result is neither cleared, collapsed, pruned nor stripped of its files, whatever the budgets say; its bytes are counted FIRST, so it is the older, already-seen material that gives way. A file-bearing result therefore reaches the model at least once — the budgets bound how long it STAYS visible afterwards. Semantic compaction needs no predicate: its verbatim tail always includes the latest tool-call group. The one path deliberately outside this guarantee is the emergency overflow prune (`_emergency_prune_session_context()`, context still over 95% of the window after all of the above): there the alternative is a provider rejection, which shows the model nothing at all — it honours only the file-recovery guard's pins (next rule) through its `keep` argument.
   - **The vision retention window is counted in tool-call GROUPS, not messages.** A group is every `tool` result answering one assistant `tool_calls` turn (`_tool_result_groups()` — maximal runs of consecutive `tool` messages, never a global `tool_call_id` map). Files stay on the last `_RECENT_TOOL_FILES_KEEP` (= 2) file-bearing groups, and the most recent file-bearing group is never stripped by the window. Counted per message, the first N-2 images of an N-image batch would be stripped before the model saw them.
   - **The exception is bounded by size, not count.** The kept, already-seen results share what the unseen ones left of a byte budget of image data (`_compute_tool_result_files_budget()`, window-scaled with a floor and a cap like the text budget), spent newest group first and in call order within a group — the first M results that fit keep their pixels, the rest are stubbed (recency cliff). Without an `is_unseen` predicate (unit tests, a caller outside the loop) the first result of the latest group is kept regardless — the structural floor. Never raise the budget to "fix" a vision problem: the fix is consumed-tracking, batch awareness and honest stubs, not more pixels in context.
   - **A stub that drops pixels must name the file and the recovery tool, and state ONE thing.** Every site that sets `msg.files = None` (`_clear_stale_tool_result_files`, `_clear_stale_tool_results`, `_collapse_redundant_tool_results`, `_prune_session_context`, the emergency prune's phase 2) goes through `_drop_tool_result_files()`, which appends ONE `_files_removed_note()` built from the `FileRef` metadata the tool emitted — its own line names each file by the persisted **file id** (never an invented one) and size, after a `stable` `wrap_untrusted` block holding the name, MIME type and saved notes (`_files_note_facts()`: a stored name is often a third party's text), so the line comes last and a tail cut keeps it — saying the file is no longer attached, is stored but not in context, and is viewed with `read_file_content(file_id=…)`. The tool's own text (the `[[FILE:id]]` marker, the Markdown image tag the reply must carry, evidence ids) is kept, minus every SENTENCE in which the platform's own tools claim the attachment (`_strip_attachment_claims()` over `_ATTACHMENT_CLAIM_RE`: "the image is attached to this result", "The PNG is attached as a native vision block - you can see the pixels", "The PNGs are attached to this result as native vision blocks - LOOK at them", the download tools' "The file has been attached for analysis" and "It is attached to this conversation for analysis"); a body that was nothing but the claim becomes the note alone. A new file-bearing tool that words its claim differently must either reuse one of those phrasings or extend the regex in the same change — a phrasing the regex misses is a contradiction waiting for the first strip. Never a tense change: "was attached" next to "no longer attached" is two statements about the same pixels, which a model reads as a contradiction and answers by re-reading the file. A later pass that replaces the body (`_clear_stale_tool_results`) preserves that note (`_split_files_removed_note()`), and a file-bearing result gets the file-aware stub — never "stale and re-fetchable, re-call the tool": re-calling a download or screenshot tool creates a NEW file and lands the model back in the same retention pass.
   - **The recovery path is watched, and force-kept once it has failed twice for a file.** `read_file_content(file_id=…)` is the ONE way back to a stored image every note names; when its result reaches the model without the pixels it was appended with, the model's only move is to call again. `_FileRecoveryGuard` (one per run) is the belt for the case where the seen rule fails anyway: `track()` at the append of every `read_file_content` result, `observe()` right after every completed provider request — the in-loop calls, streamed or not, and the forced-answer synthesis and its stronger-prompt retry alike; never after a timed-out, failed or cancelled call, which showed the model nothing (through `_consume_transcript()`, the ONE place the transcript is marked consumed) — a tracked result appended with files and carried without them is a pixel-less answer, counted per file id and logged at WARNING with its message index and the budget state (`_context_budget_state()`: vision bytes attached vs `_compute_tool_result_files_budget`, tool-result chars vs the live budget, file-bearing groups vs `_RECENT_TOOL_FILES_KEEP`, transcript chars vs the window) and recorded on the iteration span — on the root trace's metadata (`enrich_trace_metadata`, tagged with the request's `phase`) for the backstop's requests, which run after the last iteration span closed. Once a file id has been answered that way `_FILE_RECOVERY_FORCE_KEEP_AFTER` (= 2) times, the NEXT `read_file_content` result for it is pinned: the loop's predicate answers `True` for it whatever the consumed map says, so every pass above leaves it alone, and the emergency prune skips it in phases 1-4 (`keep=`, also threaded through `_compact_for_empty_recovery()`); the pin is logged the same way. A pin is released by the first completed request that carries the result — with its files (the success) or without them (a counted failure; nothing is left to keep) — observed, never inferred from the consumed map; at most one pin per file id; the count is not reset by a success. A live pin therefore always sits in the latest tool-call group, the one semantic compaction keeps verbatim, which is why that layer takes no `keep`. A healthy loop never logs a guard line — one in a trace is the root cause, read where it happened, instead of a count of repeated calls.
   - **An image is shown once per turn, and the turn shows at most `AGENT_LOOP_VISION_VIEWS_PER_TURN` distinct images per 25 steps of its step budget (`vision_cap_for(max_iterations)`, read as the budget stands - an extension raises it) — both enforced by the loop, at ONE boundary, for every tool.** The turn's vision ledger is `FileContext.vision_views` (file id -> the 1-based step the tool ran in, `appended_at_iteration`), written by `_record_vision_views()` from `_consume_transcript()` BEFORE the consumed map is updated — i.e. only for a result a completed provider request carried WITH its image files. Never at append time: a result the emergency prune stripped before any request was never seen, must NOT read as `already viewed`, and its re-read must carry the pixels again so the recovery guard above can count and pin it. `read_file_content` only READS the ledger (a shown file is answered with the notes, or the explicit error naming `annotate_file`). Every tool result crosses `_admit_tool_result_images()` when it is appended — the sequential site, the parallel-batch site and the sequential cache-replay site, BEFORE `_track_file_recovery()` — which stamps `appended_at_iteration` and then, with a ledger to keep (the loop's `file_context`, else the executor's — one object either way): a result whose EVERY image was already shown loses its pixels through `_drop_tool_result_files(note=_files_removed_note(seen_at=...))` (the once-per-turn rule for a tool that does not consult the ledger: a cache replay of a render, a second tool attaching the same file); a result whose NEW images would take the ledger plus the images still in flight (appended, not yet carried — a batch of three screenshots spends three before any request) past the cap loses its pixels through `_vision_budget_note()` — `[Image(s) not attached - vision budget exhausted for this turn: N distinct images already shown (the cap is C) ...]`, the files by name, id and saved notes, matched by `_FILES_REMOVED_NOTE_RE` so a later re-stub keeps it — and keeps its text minus the attachment claim. All or nothing per result, never a partial send; a refusal is a result appended WITHOUT files, so the guard never counts it and never pins. `0` = no cap (the once-per-file rule stays).
   - **Seen is not used: a current-turn result no substantive text has followed yet is not the byte budget's to clear.** The rules above protect a result until ONE completed request has carried it; on that alone, the byte-budget pass would stub it the moment the next batch landed, so a turn that gathers its material in two or three tool-call-only batches (page bodies, memory searches, query results) would lose the first batch as the second arrived, before the model had written a word about any of it, and a re-call served from the cache would be cleared again by the same pass. `_unwritten_turn_results()` names the current turn's tool results (everything appended since entry - the caller's history is `_entry_tool_results`, strong references like the consumed map) that no assistant message with at least `_SUBSTANTIVE_TEXT_MIN_CHARS` (900 - the loop's own preamble line, `_PREAMBLE_HOLDBACK_CHARS`, pinned equal by a tripwire) of text follows, newest first up to `max(_TURN_PROTECTION_MIN_CHARS, _TURN_PROTECTION_LIVE_BUDGET_FACTOR (4) x the live budget)` - half a 128k window, a fifth of a 1M one; the older ones fall back under the ordinary budget, so a tool-call-only turn does not re-send everything it gathered up to the compaction trigger. That is a HEURISTIC, named as one: it does not check that the text is ABOUT the result (nothing cheap could), only that the model has moved from gathering to writing; a tool-call-only turn or its stage plan ("Let me check HiBob now", up to 900 characters) does not count. `_refresh_turn_protection()` recomputes that set right before the body passes run and `_is_protected_tool_body()` - unseen, pinned, OR unwritten-this-turn - is the predicate `_clear_stale_tool_results()`, the compaction gate's `_prune_session_context()` and the forced-answer prune take. The vision pass and the duplicate collapse keep the plain unseen predicate (pixels are the ledger's, and a collapsed duplicate loses nothing). History results stay under the ordinary budget. **The window stays the hard bound of every request**: the protection only narrows what the COUNT- and byte-based passes may clear, so a turn whose protected results alone would not fit still reaches the window gate - semantic compaction, then, past 95% of the window, the protection GIVES WAY first (`_prune_session_context` with the plain unseen predicate stubs the older seen results, the unseen batch and the pins stay whole), then the emergency prune (pins honoured; it truncates every long message, so it is reached only when stubbing was not enough), then `ContextOverflowError` - and the forced-answer synthesis applies the same order after its prune (the cap can land right after a batch the gate never measured: two tool-call-only batches of four capped reads on a 20k-token window would otherwise send the synthesis at ~25k tokens; `test_no_request_exceeds_the_window_the_forced_answer_included`). Each protected result is itself bounded by the per-result cap (`_truncate_tool_result`) when it is appended.

   The identical-call dedup cache (CORE-6, `tool_result_cache`) follows the same contract: a cache hit **mirrors the cached files** onto the replayed tool message (`_CachedToolResult` / `_DedupedCall.files`), so a replayed download is the image, not a sentence about one, and the retention pass treats it like any other just-returned result — unseen until sent, then bounded. **A hit replays the FULL cached payload** under ONE header, `_DEDUP_CACHE_MARKER` ("the result is unchanged and repeated in full below"), true whether or not an earlier copy still stands - never a "use the previous result" nudge, since the previous result may be the very re-fetchable stub that sent the model here. The replay is recorded as its ask's answer like any executed result (`_record_breaker_answer`), so the loop breaker's held-answer rule (3f in `backend-tools-loop-guards.md`) is the ONE place that decides whether a re-call the curation invited is a repeat; there is no second ledger of appended results. A tool whose answer moves on its own between two calls - a background job's progress, a session waiting for an approval - declares `ToolDefinition.live_state` and is exempt like the polling names: the loop collects `_live_state_tools` from the definitions it is handed and passes them to `_is_dedup_exempt` and to the loop breaker. `get_video_jobs` carries no polling word in its name, so before the flag the cache replayed its first "Queued" answer for a whole render and the breaker then refused the poll; a new poller declares the flag, never joins a name list. `read_file_content` itself is in `DEDUP_EXEMPT_TOOLS`: it is the recovery path every dropped-files note and nudge names, called again precisely because its previous result is no longer in context, and served from the cache it would replay the stripped text with a nudge pointing at itself ("open it with read_file_content instead of calling this tool again"): the recovery path the notes advertise must never be a dead end. Re-executing it is cheap (the image path returns the stored `FileRef`, an identical text body is collapsed like any duplicate). Being exempt, it is also outside the near-duplicate read guard below, which counts dedup-eligible calls only — the guard's nudge points at `read_file_content` anyway, and the vision pass bounds what a repeated read can keep in context. `_DEDUP_CACHE_NUDGE` never invites "different arguments" — for a download tool that means renaming the output, which defeats the cache and re-fetches the same bytes — it points at `read_file_content`. The key excludes a tool's **cosmetic (output-naming) arguments**, declared by the tool's owner in `ToolDefinition.cosmetic_arguments` and read from the run's definitions (`declared_cosmetic_arguments`, #5303; the platform holds no name list) (`download_notion_file(block_id=X, filename="a.png")` and `(block_id=X, filename="b.png")` are one call; a different `block_id` is not); every other tool keeps every argument in its key, because for a tool that selects the file by name the filename is data. On top of the cache, the **near-duplicate read guard** (`_MAX_NEAR_DUPLICATE_CALLS` = 3) counts dedup-eligible calls per `(tool, effective arguments)` — executed or served from the cache alike — resets the counts when a write tool runs, and when a count crosses the threshold injects `_NEAR_DUPLICATE_NUDGE` once per tool (with a user-visible `thinking_text`) naming the tool, the count and the `read_file_content` path. The injection has ONE site, `_inject_near_duplicate_nudges()`, called after the batch's results next to the repeated-failure nudge AND on the sequential cache-hit path, which `continue`s to the next iteration before that block — the counter marks the tool as nudged the moment it fires, so a crossing served from the cache would otherwise consume the one-shot unread. Steering, never enforcement: the call is never blocked, so a legitimate re-read after context clearing still works. Persistence closes the loop from the other side: `builtin_tools._shared._persist_generated_file()` — the persistence path of every download tool, `generate_file`, the code interpreter and the presentation exports — records the SHA-256 of the bytes it stores (`file_attachments.sha256`, hashed off the event loop) and reuses the existing row for byte-identical bytes in the SAME conversation, of the SAME `source` (agent-provenance sources only — user uploads and runner evidence captures never take part; `source` decides the chip a file is shown as, so an `agent_working` write is never answered with an `agent_download` row) and bound to no assignment run (the engine re-points a run's files to itself, so another run's output is never handed over) nor shown by any message yet (a row is shown by at most one message, so a file regenerated in a later turn gets a row the later answer can carry - the embedded chat and the widget show a reply's files from that reply alone); the reused `FileRef` carries the stored row's filename, not the name the retry asked for, except for `generate_file` and an edit revision, which pass `match_filename=True` (a file the agent writes under a name is that name). A write handed a row a tool only FETCHED (same bytes, `agent_working` / `agent_download`) registers it through `register_produced_file()` (`FileContext.add_produced`), which clears the fetched mark: the write is what makes it a deliverable. A run therefore cannot persist the same download twice. One tool path writes its own row and stays outside it on purpose: `generate_image` (non-deterministic bytes, its legacy `ChatImage` twin). MCP binary content goes through `_persist_generated_file` with the run's scope and records its digest, but `source="mcp"` is outside the agent-provenance family, so it is never matched.
3. **Semantic compaction (auto-compact)** — `_semantic_compact_session_context()` distils the **oldest turns** into a single high-fidelity, LLM-generated summary while keeping the **original task** and the most recent turns **verbatim**. It is provider-agnostic (a single `llm.chat` call), operates on whole tool-call **groups** so no `tool_result` is ever orphaned, and preserves every `system` message. This is the information-preserving equivalent of brute truncation. **The summariser call is recorded like the loop's own calls**: a `context_compaction` generation of the observation it runs in (the iteration span, or the run's own span in the forced-answer backstop, whose iteration spans are closed), its provider retries as attempt events on it, and its usage through `_merge_usage` (the run budget, the token wind-down and the usage the run reports), once, when it returns. A returned call whose summary is unusable (empty) was billed and is recorded too. The compaction helpers take that hook as `merge_usage` (`_summarize_messages_for_context`, `_semantic_compact_session_context`, `_compact_for_empty_recovery`), and every compaction site of the loop passes `_merge_usage`. A call that raises, times out or is cancelled returned no usage (a non-streamed `chat()` reports it in its response only): its generation is closed with the error, nothing is debited and the fallback is unchanged. A failing usage hook is logged, never raised: it cannot take a delivered summary back. The summariser itself takes no reservation (whether and when compaction runs is unchanged), but **a compaction that spent is followed by the budget check again** before the LLM call it precedes, because that call was priced before the summariser was debited. In the loop (the proactive gate and both empty-response recoveries) `_call_refused_after_compaction()` re-prices the call on the compacted prompt (`try_reserve`, replacing the iteration's reservation) and checks the token wind-down; when the run is now exhausted the iteration makes no call, is not counted, and the next iteration's gate takes the run down the path every run reaching its budget at a boundary takes (the stop warning, the downgrade when one is allowed, the backstop). In the backstop, both compactions are followed by the backstop's own guard (`_budget_digest_if_unaffordable()`: the full-limit check, the downgrade, else the budget digest instead of the synthesis or its retry). A run still under budget after the compaction makes the same calls and emits the same events as it would without the check; a compaction that spent nothing checks nothing. **Identifiers survive the transcript excerpt** (#2382): `_build_inloop_transcript()` cuts each message to a head+tail window of `_SEMANTIC_COMPACTION_TRANSCRIPT_MSG_CHARS`; a tool result whose middle is elided also carries `_elided_identifier_table()` (the UUIDs, ULIDs, URLs and JSON `id` / `*_id` values of the elided part, each with the start of its line, verbatim, at most `_SEMANTIC_COMPACTION_ID_TABLE_RESULT_CHARS` per result and `_SEMANTIC_COMPACTION_ID_TABLE_TOTAL_CHARS` per compaction, the rest counted) and a `[Body elided: re-run <tool>(<args>) to read the rest]` line built from its tool call. The summary of a slice that carries identifier tables is asked with `_SEMANTIC_COMPACTION_ID_TABLE_MAX_TOKENS` instead of `_SEMANTIC_COMPACTION_MAX_TOKENS`, and `_with_rerun_hints()` appends the re-run hints (at most `_SEMANTIC_COMPACTION_RERUN_HINTS`) to the summary after the summariser answers, so the way back to an elided body never depends on the summariser. A summary cut at its budget is asked once more with twice the room inside the same `llm_timeout` (a generation of its own flagged `cut_answer_retry`, its usage merged once), and only while the run budget still pays for it and for the call the compaction precedes (`can_retry`: the in-loop gate on top of the iteration's reservation, the full limit with the synthesis in the backstop); refused, or cut again, the summary takes the deterministic pruner.
4. **Emergency prune (deterministic fallback)** — `_emergency_prune_session_context()` runs only when semantic compaction is unavailable/failed, or as the final overflow guard. It is **size-monotonic and guaranteed to make maximal progress** via five cheapest-first phases: (1) tool-result compression, (2) user/assistant/**tool** message tail-truncation, (3) oldest-group eviction down to the `_EMERGENCY_KEEP_MESSAGES` floor, (4) **dynamic-floor in-place truncation** — when the protected tail itself exceeds budget it truncates those remaining non-system messages in place (never dropped, so the floor count and tool-call/tool-result coupling survive), and (5) **system-prompt overflow** — an absolute last resort that head+tail-truncates an oversized system message (persona head + trailing security policy survive, bulky injected-memory middle elided) when the system prompt alone still exceeds the budget. Phases 4-5 stop the "nothing safe to drop -> empty-response loop -> forced-final-answer also fails" cascade and have no effect on healthy runs. All truncation goes through the shared, expansion-guarded `_emergency_truncate_text()` helper (tail or head+tail mode), which never returns a longer string and never splits a quarantine block: the head+tail cut moves outside it, and a tail cut that would start inside an untrusted block keeps the end of its data fenced again (`content_safety.refenced_block_tail`, same source label, `stable` boundary), past a memory block. `_split_files_removed_note()` takes only a note line outside every block, and pairs it with the block right before it only when that block is the note's own: its source line, read where the block writes it (`content_safety.untrusted_block_source`), is `[source: stored files]` - a payload that writes that line itself does not count.

**Every gate weighs what the request carries, provider extras included**. The compaction trigger and target, `_prune_session_context`, the "too little to gain" check of `_semantic_compact_session_context`, the 95% overflow guard, every running total of `_emergency_prune_session_context`, the large-context trigger of `_compact_for_empty_recovery` and the forced-answer context guard (`_over_final_window`) measure the transcript with `_transcript_chars(messages)` - `message_payload_chars` from `app/llm/base.py` summed: each message's text plus the replay data its provider resends from `ChatMessage._provider_extra` (a Gemini tool turn's thought parts, function calls and thought signatures, kept verbatim and replayed on every request of the run). So do the per-run budget reservation (`_estimate_prompt_tokens`), the context readout (`_context_breakdown_chars`) and the file-recovery budget state (`_context_budget_state`). The extras are only counted, never stripped or rewritten to save space: eviction and semantic compaction drop them with their message, and a message truncated in place (emergency phases 2 and 4) is re-measured - a Gemini turn is replayed as its parts whatever its content says, so that truncation frees nothing and the prune moves on to what does. The tool-result body passes (the duplicate collapse, the live budget of the stale clearing, the prune's stub wording) keep reading the result body: a tool result carries no provider extras. A provider that keeps replay data registers how much it weighs with `register_provider_extra_counter` (`dev-docs/reference/backend-llm-messages-and-attachments.md` > "Provider extras"). Never add a `len(m.content)` sum to a gate: a transcript whose weight is its thoughts would reach no threshold, and the provider's own overflow check would be the only safeguard.

**Triggers are real signals — never a fixed char threshold that would gut a legitimately long prompt:**

- **Proactive (near the real window limit):** the per-iteration gate compacts only when context approaches the model's window (`_COMPACTION_TRIGGER_UTILIZATION`, ~80%). Cheap tool-result clearing runs first; if still over target, semantic compaction runs. Within-window long prompts are untouched.
- **Reactive (empty-response recovery):** when the model returns an empty turn on a large context — the model itself signalling it lost focus — `_compact_for_empty_recovery()` runs semantic compaction (then deterministic fallback) before the retry, so the retry re-sends a *focused* prompt instead of the same oversized one. This breaks the "empty response → forced-final-answer backstop → synthesised digest" cascade, and it has **no impact on healthy conversations** because it only fires on an actual empty turn.

Because semantic compaction only ever summarises *older* turns (a single huge prompt has no old turns and is left untouched) and always keeps the task + recent window verbatim, long-prompt workflows are never degraded.

Conversation-level compaction (`services/conversation_memory.py`, with Pinned Directives + rolling summary) is a complementary layer that runs **between** chat turns; the layers above operate **inside** a single agent turn that balloons through many tool calls.
