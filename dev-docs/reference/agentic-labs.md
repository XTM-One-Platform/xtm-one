# Agentic coding labs (`AGENTIC_CODING`)

One Kubernetes pod per lab, created and reaped by the platform, behind the four sandbox service tools. Filigran's own development tooling in Copilot or dev mode (Sam's decision D1, 31 Oct 2026); never an XTM One feature. Code: `backend/app/services/sandbox_workspace/labs.py` (the labs) and `kube.py` (the API server client). Settings: `docs/docs/deployment/configuration.md` > "Agentic coding labs". The service tools and the rest of the workspace: `sandbox-workspace.md`.

## When the labs are on

- `labs.labs_enabled()`: the flag `AGENTIC_CODING` (`FLAG_CONDITIONS` gates it on `_copilot_like`, like `EVALUATION`: copilot or dev mode only, never `xtm_one` or `ai_disabled`, `*` included) AND `AGENTIC_LABS_NAMESPACE` set. Either missing: the service tools behave exactly as before (OpenSandbox, `services.start_service`).
- On, `sandbox_start_service` resolves the service the usual way (`services.resolve`) and hands it to `labs.start_lab`; `sandbox_service_status`, `sandbox_service_logs` and `sandbox_stop_service` reach the lab when `labs.find` knows the id, the OpenSandbox path otherwise. The service tools are offered when the labs are on even without OpenSandbox commands.
- `sandbox_service_status(service_id, env=[NAME, ...])` answers, for a lab, one line per container with each named variable `set`, `set (empty)` or `missing` (`labs.env_presence`, read from the pod spec, never a value): the check that a licence or a declared variable reached a container without an exec. A variable a service exports from its own script is not seen. An OpenSandbox service answers that env is read for a lab only.
- Its `services:` line names each service `ready`, `starting` or why it ended (`labs.service_states`); a service still starting carries its container's waiting reason and restart count when the pod reports them (`starting (ContainerCreating)`, `starting (restarted 2x)`), so a silent step (a long image pull, a crash loop) reads apart from a slow boot without an exec.
- `sandbox_service_status` on a service_id the workspace holds no record of (a lab or service the run stopped, which drops its record, or an id never started in this workspace) answers `<id>: not running (stopped or never started in this workspace).` as a normal result (`services.not_running`), so the read-back after `sandbox_stop_service` is never a tool error; an empty id or one with whitespace stays a refusal. A lab whose pod ended on its own still answers `<key>: gone (its pod ended).` (#10589).

## The pod (option B)

| Part | What |
|---|---|
| Name and labels | `lab-<12 hex>`, `app.kubernetes.io/managed-by=xtm-one-agentic-labs`, `xtm.filigran.io/workspace=<workspace id>`; annotations `xtm.filigran.io/last-used` (renewed by every call on the lab) and `xtm.filigran.io/service` |
| `workspace` container | the service's image, idles; the checkout is unpacked into its `emptyDir` at `/tmp/workspace` through the exec API (one tar, what a command builds left out: `commands.IGNORED_PATTERNS`; `checkout_archive` reads the blobs once per distinct content, `_ARCHIVE_READ_CONCURRENCY` at a time), then `/tmp/workspace/.xtm/lab-ready` is touched; `copy_checkout` gives each attempt `AGENTIC_LABS_COPY_SECONDS`, apart from the start budget, and tries a copy that timed out or lost its stream once more on the same pod (`KubeClient.exec` turns a refused upgrade into a `KubeError` carrying its HTTP status in `handshake`, never in `status`, so `run_check_in_lab` reads only a REST 404 as a pod gone, and a stream lost before the status frame into a `KubeError`; a stream the server closes while stdin is still sent, because the command ended before reading it all, keeps reading the frames already sent and answers the command's status when one came; a refused first stream, such as a 404 on a pod the API server has not caught up with, waits `_COPY_REFUSED_PAUSE_SECONDS` before the retry); a tar that exits non-zero is answered at once |
| One container per service of the chain | `svc-<name>`: waits for the ready marker, then for the ports of its `depends_on` on the shared `localhost`, then `cd <cwd> && exec <argv>`; readiness = the pod's probe on its port (`httpGet ready_path` when declared, `tcpSocket` otherwise), never a liveness probe; a service that declares `ready_log` is ready only once its container log holds that text too (`labs._wait_logged`, same deadline) |
| Resources | REQUESTS only (`AGENTIC_LABS_CPU_REQUEST`, `AGENTIC_LABS_MEMORY_REQUEST` per container) so the scheduler can place the pod; no limits |
| Hardening | `automountServiceAccountToken: false`, `enableServiceLinks: false`, `allowPrivilegeEscalation: false`, all capabilities dropped, `RuntimeDefault` seccomp, `restartPolicy: Never` |
| Hygiene | `activeDeadlineSeconds` = `AGENTIC_LABS_DEADLINE_HOURS` (absent at `0`) |

What a workspace holds (pod name, IP, port, containers, preview URL) lives in `kernel_state["labs"]` of its row, keyed by the service key: a lab survives a turn and is found again by its pod name or its key.

## No ceiling of any kind (D1b)

The lab path never calls `enforce_combined_sandbox_quota` nor `increment_sandbox_usage` (pinned by `tests/test_agentic_labs.py`, whose quota functions raise if called). No lab-hour budget, no count limit, no alert. The only ends of a lab other than `sandbox_stop_service`:

- `labs.reap`, from the hourly workspace sweep (`orchestration_adapters/sandbox_workspace.py`): deletes the lab pods that ended (`Succeeded` / `Failed`) and those unused for `AGENTIC_LABS_IDLE_HOURS` (`0` = never), and unregisters their previews. Errors are logged, never raised (`reap_logged`).
- Kubernetes' own `activeDeadlineSeconds` (`AGENTIC_LABS_DEADLINE_HOURS`, `0` = never).

Both are documented, generous by default (12 h idle, 72 h deadline) and overridable.

## The API server (`kube.py`)

- `httpx` and the service-account token, no Kubernetes client dependency; the exec call uses the `v4.channel.k8s.io` WebSocket protocol through the `websockets` package uvicorn already ships.
- Where: `AGENTIC_LABS_API_URL`, else `KUBERNETES_SERVICE_HOST` / `KUBERNETES_SERVICE_PORT`. Token and CA read on every call (`AGENTIC_LABS_TOKEN_PATH`, `AGENTIC_LABS_CA_PATH`), so a rotated token is picked up. The token never reaches an agent, a log line or a result (`KubeError` carries the status and the API server's message only). A call the API server never answers (an `httpx` timeout or connection error) is a `KubeError` too, status 0, its text naming the call and the error type (`_transport_failure`), never an exception the tools do not catch.
- Calls, all in the one namespace: create, get, list (label selector), merge-patch annotations, delete pods; `pods/log`; `pods/exec`. The RBAC this needs: `pods` create/get/list/patch/delete, `pods/log` get, `pods/exec` create (and get, for the WebSocket upgrade).
- Platform-internal for the egress funnel (`tests/test_egress_funnel.py`): a relay would see the service-account token.

## A check run inside a lab (`service_id`)

`sandbox_run_command(checkout, check, service_id)` runs a DECLARED check of the checkout inside the running lab `service_id` instead of a check container: `labs.run_check_in_lab` execs `sh -c "cd /tmp/workspace/<cwd> && exec env <check env> <argv>"` in the pod's `workspace` container (the pod exec API, `kube.KubeClient.exec`), so the command sees the lab's services on `127.0.0.1` and the lab's copy of the checkout (the files as of the lab's start, never the workspace's later edits). A check container has no route to a lab pod; this is the path for a runner that drives a lab (`lab-routing-eval`, `dev-docs/ootb-routing-eval.md`). The check resolves as any other (its argv, `default_args`, `args`, `cwd`, `env`; an arbitrary `argv` is refused where `CODE_INTERPRETER_COMMAND_ALLOW_ARGV` refuses it); its image key is not used, the lab's image runs it. Only a lab started from the same checkout runs it; `run_id`, `stop`, `background` and `affected` are refused with it. The call answers when the check ends, within `LAB_COMMAND_SECONDS` (270 s, below the agentic loop's per-tool timeout), with the exit code, the end of stdout (20,000 characters) and of stderr (4,000); a lab gone answers "gone" and drops its record. Nothing is copied back to the workspace. No network policy changes: the command runs where the lab already runs.

## Listing, sync and the start refusals

- `sandbox_start_service` without `service` lists the services the checkout declares (`services.list_declared`) as a normal answer: no refusal to probe for.
- `sync=true` on a running lab (`labs.sync_lab`) copies into the pod's workspace the checkout files written since its last copy (the record's `copied_at`, stamped at the start's copy and at each sync, two seconds of slack), under the adoption lock, without touching the services: a dev server that watches its files reloads them, another needs a restart. A file removed from the workspace stays in the lab. A lab with no copy yet, or whose pod is gone, refuses the sync with the start to call.
- `sync=true, restart=NAME` (#12104) then runs that service's process again in its own container, the pod kept: every service container runs its argv under a small shell supervisor (`labs._supervised`: the process in a group of its own through `setsid` when the image has it, its pid in `/tmp/.xtm-service.pid`), and `labs.restart_script`, run through the pod exec API, sets `/tmp/.xtm-service.restart`, sends SIGTERM to the group, waits up to 30 s for the whole group (not its leader alone) to end, then sends SIGKILL once and waits up to 10 s more, never in a loop (exit 5 when the group outlives it, #12198); the supervisor itself reruns the argv only once the old group is gone, so a database, JVM or dev server the service started has freed its port and data directory. The store start is idempotent for that rerun (`.xtm-one/stores.py` `init_cluster`: an existing `pgdata` with `PG_VERSION` is kept without `initdb`, its stale `postmaster.pid` dropped; `ensure_database`: a database is created only when missing), so lab-openaev and lab-opencrq keep their database and caches and run their migrations only. The supervisor reruns the argv only when that flag is set; otherwise the container still ends with the process's own status (`restartPolicy: Never`). What the container wrote (the lab cache under `/tmp/lab`, a Maven local repository, build output, `node_modules`) and the other services are kept, so a fix to a lab script costs its own run, not a new pod and a cold build. The call waits for the old process to stop answering, then for the new one, within `ANSWER_SECONDS`; past it the answer is `starting` with how to follow it. A name outside the lab's services is refused; a pod created before #12104 (no pid file, exit 3) is refused with the stop and start to make once. A service whose container has already exited (`restartPolicy: Never`: it is gone for good, and an exec into it is refused by the API server with an HTTP 500 on the WebSocket upgrade) is answered before any exec with its exit code and reason, its last lines and the way out, `sandbox_service_logs` then a stop and a fresh start (#115). `restart` without `sync` is refused. Build caches across a stop and a new pod (a volume per checkout) are not kept: that is an infrastructure change of the labs namespace.
- Restart readiness (#12236). The supervisor writes `[xtm-service] restarted in place` to the container's output before each rerun, and a restart counts the service ready only once its port answers and its `ready_log` is logged after that line (the old run's `lab up` never counts). A service may state `restart_target` (seconds) in its `[service.NAME]`; the sync answer names the time to ready and whether it was within or over the target. What a restart keeps: the xtm-one lab (`lab.py`) keeps the node and yarn toolchain and the frontend install while `frontend/yarn.lock` is unchanged (`/tmp/lab/cache/frontend-installed.lock.sha256`), and keeps its database with its seed when nothing that wrote the seed changed (#12253): `/tmp/lab/seed.sha256`, written once the seed ended, holds the sha256 of every `.xtm-one/lab/*.py` and of the `LAB_*`, `ADMIN_*`, `PLATFORM_MODE` and `ENABLED_FEATURES` variables; a restart that finds it equal keeps `pgdata`, skips the seed and only writes again what Dragonfly does not keep (the generating marker, the profile memory) and fresh signed-in session URLs, then logs every `seeded` line of `seeded.json`. Any other start (first start, seed cut half-way, a lab script or switch changed) drops `pgdata` before the stores start and seeds a fresh database, so a seed is never written twice; target 120 s (backend boot and migrations, no seed). The OpenAEV lab (`openaev_pr_head.py`) keeps its database and seed, skips the Maven build when no source of the API reactor is newer than `openaev-api.jar`, skips `yarn install` while `openaev-front/yarn.lock` is unchanged, and boots the JVM with a class data sharing archive (`-XX:+AutoCreateSharedArchive`, written at the first exit under the lab cache, read by every restart) and `-XX:TieredStopAtLevel=1`; target 180 s, from the measured 165 s JVM boot without the archive (retest 16 Nov 2026: 243 s before this change, first start 533 s).
- A start waits `ANSWER_SECONDS` (240 s since #12104, was 180 s) for readiness before it answers `starting`: a lab ready within 4 minutes is answered `ready`, sessions included, by its first call; the copy, the session read and the answer fit in the 300 s per-tool timeout.
- A chain whose dependency names an image key outside `AGENTIC_LABS_IMAGES` (and not the started service's image) is refused before any pod with each such service and its key named, and the configured keys listed.
- A `[service.NAME]` argv item holds up to `SERVICE_MAX_ARG_CHARS` (8,192) characters, apart from a check's 512: a lab's `sh -c` line outgrows the check bound. The refusal states the bound and the longest item found. An argument a call passes (`sandbox_run_command` `args`, a command of its own) holds up to `CALL_MAX_ARG_CHARS` (8,192) characters, so an inline `lab-sql --sql` text needs no file and no sync (#788); a declared check argv and its `default_args` keep the 512 bound.

## Previews

A start that times out keeps the lab's record without a pod IP or preview URL, so its logs stay readable. The next `start_lab` reads the pod live: a target container ready with a `status.podIP`, on a pod built from the same declaration (`fingerprint`: a digest of the image key and every field of every service of the chain), is adopted (the record completed, the preview registered, answered "already running"; a record written before the fingerprint existed is matched on its image key, port and service chain and gets the fingerprint at its adoption); a pod without an IP, from another declaration or terminating (`metadata.deletionTimestamp` set, or not `Running`) is deleted, its preview withdrawn (`_drop_pod`), and started again; an API error while reading it refuses the start and keeps the record. The adoption and `stop_lab` hold one lock per workspace and lab key (`WorkspaceSession.lock`: a PostgreSQL transaction-scoped advisory lock, so across API replicas), and both read the record as stored now: a stop waits for the adoption to answer, then finds the complete record and withdraws the pod, the preview and the record. A stop asked by pod name stops that pod only: when the key now records another pod (a replacement), it is refused and the replacement keeps running. A stop whose delete fails is retried once (`_STOP_ATTEMPTS`), then the pod is read: gone or terminating, the stop holds (answered "already gone" or "stopping"); still there, or unreadable, the stop answers an error naming the API server's answer and the pod's phase and KEEPS the record, so status, logs and a second stop still reach the pod (never an empty success, xtm-one #10541). A ready container on a pod that has no IP yet answers a failure naming the pod phase, never an exception.

A start that never answered ready (its call cut by a run resume, or timed out) leaves no `ready_seconds` in the record. When such a lab is adopted and a service of its chain declares `ready_log`, `start_lab` waits for that text in the container log as a fresh start does, for what is left of the first start's window (`AGENTIC_LABS_START_SECONDS` plus the chain's timeouts, from `started_at`, at least one read), outside the adoption lock; it then records `ready_seconds` and answers "already running, its start completed after Ns more", or not ready (the pod kept for its logs). A record with `ready_seconds` is answered at once. The OpenSandbox path (`services.start_service`) does the same with `_wait_ready` (port and `ready_log`) before answering a held service or replacing it (#9516).

A run resumed after a rollout restart comes back to its lab, not always to its browser session. Two guards keep a lab usable across a resume (gap family lab-session-after-resume):

- Signed-in sessions in every answer. A service may declare `session_log`, the text that opens each signed-in session line it logs (`seeded signed-in session` on every xtm-one lab of `checks.toml`). Once the lab is ready, `labs._with_sessions` reads those `<label>: <url>` lines from the container log once (`parse_sessions`, the last URL per label, at most 12), moves a loopback origin to the lab's preview origin (`_session_url`) and keeps them in the lab record (`sessions`). The start answer (fresh or adopted) and the `sandbox_service_status` answer of a ready lab end with a `Signed-in sessions` block, one line per account (administrator, the non-admin peer, any other the seed logs), so a resumed run whose tab is signed out signs it in again with one browser `navigate` and runs its retests as the non-admin peer, without reading the logs.
- Licences never lapse under a review. The start records `licences_expire_at` (now plus the validity `licences.issue` asked for, `AGENTIC_LABS_LICENCE_HOURS`) and the answers print it (`valid until ...`). A start that finds its lab running adopts it only while more than `LICENCE_MARGIN_HOURS` (1 h) of that validity is left; otherwise the pod is deleted and a new one is created with fresh licences, and the answer says `a new lab: the previous one (<pod>) was replaced because its Enterprise Edition licences expire at <time>`. A reused lab therefore never shows the Community Edition splash because its CI licence ran out.

A lab's preview is `http://<pod IP>:<port>/`. `preview.register_origin` admits that IP literal and port in Redis for the lab's life (the idle horizon, a day when the reaper is off), the value naming the owner pod; `preview.unregister_origin` deletes it only while it still names the pod withdrawing it (a compare-and-delete script), so a pod whose IP the cluster gave to another lab never revokes that lab's preview; an admission written before admissions named their pod (value `LEGACY_ORIGIN_OWNER`, "1") is withdrawn by the same script; `preview.match_origin` accepts only an `http` URL on a private unicast IP literal with a port (loopback, link-local, metadata, multicast and public addresses never), and `preview.request_headers(url)` adds the OpenSandbox key to the server's own proxy URLs only: a lab pod gets nothing. Fails closed without Redis.

Every HTTP service of the lab's chain is admitted the same way (#12094): the started service's port, then each service of its `depends_on` chain that declares a `ready_path` (`_browsable_ports`, recorded as `ports` in the lab record; a record written before keeps its single `port`). The lab OpenCTI of `lab-ootb-live` or `lab-ctem-opencti` (`http://<pod IP>:4000/`) therefore opens in the browser tool and web_fetch of the run, and the start answer names it ("Also admitted for the browser and web_fetch"). A store without a `ready_path` (search, broker, Redis, S3, a database) is never admitted. Status renews every port; a stop or a replaced pod withdraws every port. For data, `sandbox_run_command(check="lab-opencti-graphql", service_id=<the lab>)` runs one GraphQL query in the lab against the lab OpenCTI with the lab admin token (`.xtm-one/lab/opencti_graphql.py`: `--count TYPE`, or `--query TEXT [--variables JSON]`; `--base http://127.0.0.1:4100` for the `lab-opencti-pr-head` backend). For rows, `sandbox_run_command(check="lab-sql", service_id=<the lab>, args=["--database", "openaev", "--sql", "..."])` runs SQL on the lab's PostgreSQL (`.xtm-one/lab/lab_sql.py`, the simple query protocol in the standard library: the stores' `psql` lives in the container of the service that started them, never in the workspace container; `--var NAME=VALUE` binds `:'NAME'` as a quoted literal, `--list` the databases; JSON rows, exit 1 on a SQL error, 2 when the database does not answer) (#327). For one raw HTTP answer, `sandbox_run_command(check="lab-http", service_id=<the lab>, args=["--url", "http://127.0.0.1:<port>/path"])` prints the status, every header and the body's head with redirects never followed (`.xtm-one/lab/lab_http.py`; `--method`, `--header 'K: V'`, `--data`): a redirect loop's `Location` the browser tool hides behind an `opaqueredirect` is read there; exit 0 on any HTTP answer, 2 when nothing answers.

The browser tool on a preview keeps its sign-in across processes: after each navigation, click, `viewport`, `emulate_media` or `network` action, a session without a browser profile keeps its cookies, local storage, viewport, emulated media features, offline state and last URL in this process and, Fernet-encrypted, in Redis (`browser:kept_state:<session key>`, `KEPT_STATE_SECONDS`). A run resumed in another backend process (a rollout restarting the worker) re-creates its session from them instead of an empty page at about:blank, and its first browser action says so, naming the page it was on; `browser close` forgets them. When that first action is a `screenshot` and the page was opened again for it, the capture waits for the page to paint (network idle, then a capture every second until it is not one colour, at most `_REOPENED_PAINT_SECONDS`, 10 s; #9712); still blank then, the notice adds "had not painted after 10 s: capture again after a wait". Any other screenshot is taken at once. When that first action is an `evaluate`, the script runs once the reopened page has rendered (its `load` event, network idle, then a body showing text, read every second within the same 10 s bound; #9793); a script that still fails there answers its error followed by "The page was opened again by the resume just before this script: run it again." Any other evaluate runs at once. A navigate that answered "Still loading" (a sign-in link `<base>/login#token=...` on a dev server still serving its modules) leaves that document loading: the next navigate waits for it first, within `NAVIGATION_TIMEOUT_MS`, and keeps the signed-in state before it leaves the page (`_finish_loading`). Before this, a second navigate called in the same turn aborted the sign-in page before it stored its token, and the next rollout resumed the run signed out with 0 cookies restored. A dev server that compiles a route on its first visit (Next.js dev, over 30 s) answers nothing before the navigation timeout, so no document commits and the navigate fails; the browser tool's `timeout` argument also applies to `navigate` (seconds to wait for the page, default `NAVIGATION_TIMEOUT_MS`, at most `MAX_NAVIGATION_TIMEOUT_SECONDS`, 120 s; `browser_tool.navigation_timeout`, #123), and the "Still loading" answer names the wait used.

The product labs' preview Fronts (`opencti_ask_ariane.py`, `opencti_pr_head.py`, `filigran_licenses_pr_head.py`, `xtm_hub_pr_head.py`, and the openaev and opencrq labs through them) relay the dev server's answers with `relay_response` in `lab.py`: the body is re-chunked as it arrives, and an answer without a body (`has_body`: a HEAD, a 1xx, a 204, a 304) ends at its headers. A chunked terminator written after Vite's 304 on a cached module was read by the browser as the start of the next answer on the keep-alive connection, so the next lazy chunk failed with `ERR_INVALID_HTTP_RESPONSE` and the page fell in its error boundary (#309).

## The xtm-one lab

`[service.lab]` in `.xtm-one/checks.toml` runs `.xtm-one/lab/lab.py` (standard library only) on the `python-dev` image, whose virtualenv already holds the backend's locked dependencies. The script fetches every artefact from a host of `copilot_agentic_labs.egress_fqdns` (PyPI, GitHub releases, npm and yarn), each pinned by URL and digest (a digest that differs stops the lab), then starts, in one process tree:

| Service | Address | From |
|---|---|---|
| PostgreSQL 16 + pgvector 0.8 | 127.0.0.1:5432 | the `pixeltable-pgserver` 0.7.1 wheel (pgvector 0.8 has `halfvec`, which the HNSW index migration needs; the older `pgserver` 0.1.4 wheel does not) |
| Dragonfly (Redis API) | 127.0.0.1:6379 | GitHub release |
| Silo (S3 API) | 127.0.0.1:9000 | GitHub release |
| stub model (OpenAI API) | 127.0.0.1:9099 | the script: one fixed answer, no network |
| backend (uvicorn, migrations, seeded administrator) | 127.0.0.1:8100 | the checkout's `backend/` |
| Vite dev server, `/api` proxied to the backend | 0.0.0.0:3100 (the preview port) | the checkout's `frontend/` |

Every lab also answers `/api/v1/lab/locale/<en|fr|es|ja|default>?next=<path>` (`lab_asgi`, from `.xtm-one/lab/lab_locale.py`, #1653): it stores that language on every user of the lab (`default` stores `auto`) and redirects to `next` (a same-origin path, `/` by default), so one browser `navigate` reloads the app in French, Spanish or Japanese for a non-English self-check; `LAB_LOCALE` (`en`, `fr`, `es`, `ja`) in a declaration's `env` stores it for the administrator and the peer at seed time, beside `LAB_THEME` (logged `language: fr-fr (the administrator's preference)`).
Every lab also answers `/api/v1/lab/theme/<light|dark>?next=<path>` (`lab_asgi`, from `.xtm-one/lab/lab_locale.py`, #1848): it stores that theme as the preference of every user of the lab and redirects to `next` (same-origin, `/` by default), so one browser `navigate` repaints the app light or dark for the second pass of a self-check without a second lab. The browser's `emulate_media` color scheme cannot do it: the app reads the account preference, then its `copilot-theme` cache, never `prefers-color-scheme`. `[service.lab-light]` and `LAB_THEME` remain the seed-time choice.
Every lab also answers `/api/v1/lab/whatsapp-decision` (`lab_asgi`, from `.xtm-one/lab/whatsapp_decision_preview.py`): the WhatsApp decision message of the human gates drawn in every state from its real payload builder, by `lang`, `theme`, `width` and `state` (`/index` lists the links), since WhatsApp has no surface a review can open (`dev-docs/human-gates.md`, S12).

- Readiness is the Vite port; the frontend starts only once `/api/health/ready` answers, and while it waits the script prints the readiness answer (the `startup_error` included) every 15 s. The backend's own access lines for those polls are dropped from the output. A readiness answer that names a `startup_error` stops the lab at once (`startup_failure`): the backend keeps its process alive after a failed startup and would answer 503 until the 600 s wait ran out, so the start answer reports the failure in seconds, with `lab: backend startup failed: <error>` in `sandbox_service_logs`.
- `PLATFORM_MODE=xtm_one`: the lab carries no licence, and the Copilot mode puts every page behind the licence wall. `ENABLED_FEATURES=*`.

## Enterprise Edition licences (D2)

Every lab may carry Enterprise Edition licences for the products it runs. `licences.issue()` (`backend/app/services/sandbox_workspace/licences.py`), called by `start_lab` before the pod is created:

- asks Filigran's licensing server, `POST <AGENTIC_LABS_LICENSING_URL>/api/ci` with the Bearer API-user token `AGENTIC_LABS_LICENSING_TOKEN` (permission `can_create_ci`), for one short-lived `ci` licence per entry of `AGENTIC_LABS_LICENCES` (`ENV_VAR:product name,...`), valid `AGENTIC_LABS_LICENCE_HOURS` (default 24, capped at the server's 168), bound to no instance (`global`: a lab's products are created with ids nobody knows in advance);
- hands each PEM to every container of the pod under its `ENV_VAR`, below a service's own `env` (a declaration can still override one). Which products exist and which variable each reads are configuration only (invariant 18): each entry names the variable the product itself reads, for example `APP__ENTERPRISE_EDITION_LICENSE:OpenCTI,OPENAEV_APPLICATION_LICENSE:OpenAEV,ENTERPRISE_LICENSE:XTM` (the variables those products' own CI sets);
- never blocks a lab: a licence the server refuses, cannot answer or answers without a certificate is left out, and the start answer (and the logs) say `missing licences: VAR (why)`. The variables set are named in the answer, never their value;
- keeps the token on the platform: it goes in the `Authorization` header only, never in the pod manifest, an outcome, the workspace's `kernel_state` or a log line (`tests/test_agentic_labs_licences.py`). The client is platform-internal for the egress funnel: a relay would see the token.

XTM One (`app/enterprise/licensing.py`), OpenAEV and OpenCRQ end a `ci` licence at the earliest of 45 minutes after the product instance was created, a year after its start and its own expiry. A lab's product therefore runs in Enterprise Edition for 45 minutes after its first start in that lab (its database is the lab's own); a longer session stops and starts the lab again (`sandbox_stop_service`, `sandbox_start_service`) for a fresh instance and fresh licences. Off while the URL, the token or the mapping is empty: the pod is then exactly as before.

## A live model (option A)

Sam's decision (7 Nov 2026, #9646): a lab that needs a real model reaches the Copilot's own OpenAI-compatible LLM proxy with a short-lived key minted for that lab; no provider credential ever reaches a pod. `model_keys.mint()` (`backend/app/services/sandbox_workspace/model_keys.py`), called by `start_lab` after the licences:

- runs only for a declaration that opts in: `LAB_MODEL = "live"` in the `env` of a service of the chain (`[service.lab-live]` in `.xtm-one/checks.toml`); every other lab is exactly as before;
- creates one personal API key (`fcp-...`) of the account `AGENTIC_LABS_MODEL_KEY_ACCOUNT` (the email of a user of this platform, someone who signs in to it; a mailbox or an integration account with no platform user is refused as "no user of this platform signs in as ..."), named `agentic lab <pod>`, scoped to the `llm_proxy` surface only, expiring after `AGENTIC_LABS_MODEL_KEY_HOURS` (default 12, at most 72), so the proxy meters and rate-limits it like any key of that account;
- hands every container `LAB_MODEL_API_KEY`, `LAB_MODEL_BASE_URL` (`AGENTIC_LABS_MODEL_BASE_URL`) and `LAB_MODEL_NAMES` (`AGENTIC_LABS_MODEL_NAMES`); `lab.py` (`model_env`) then points the lab backend's custom OpenAI provider at the proxy instead of the stub;
- records the key's id and display prefix (the lab's `kernel_state`, the pod annotation `xtm.filigran.io/model-key`, the start answer), never the key;
- revokes the key when the lab stops, when its pod is replaced or fails to start, and when the hourly sweep reaps the pod; the expiry is the backstop;
- never blocks a lab: unset account or URL, an account with no platform user, a disabled platform user, or a database error leaves the stub model, and the start answer says which.

The quota a lab draws on is the `llm_proxy` quota of `AGENTIC_LABS_MODEL_KEY_ACCOUNT` (`check_llm_proxy_quota` in `backend/app/services/quota.py`: the account's per-user config, 200 calls a day as the proxy's 429 read on 10 Nov 2026, plus the platform-wide cap). It is counted per user, not per key: every lab of the day draws on the same counter, so one morning of live evals and captures can exhaust it for every later lab. Past the limit the proxy answers 429 `llm_proxy quota exceeded: N/M (daily)` with `Retry-After` set to the seconds left; a daily period resets at 00:00 UTC. Raising the limit or giving each lab key its own counter is a cost decision (#10848). `routing_eval.py` asks the proxy for one token with the lab's key before the first task (`preflight_model`) and stops at the first task whose error names the quota: either way it writes `quota_exceeded` (`llm_proxy quota exceeded N/M (daily), resets at <UTC>`) in the report and on stderr and exits 3, in seconds instead of the check's 270 s timeout.

While the quota is exhausted the lab's own background runs retry each 429 (`retry_llm_call` in `backend/app/llm/base.py`) and can hold the backend's database pool, so the API answers 503 "The database is temporarily unavailable" for a while. `routing_eval.py` retries a 503 on the sign-in and on every GET every 5 s for up to 60 s (`UNAVAILABLE_BUDGET`); a sign-in still refused past it writes `not_ready` and exits 2 (not ready), never 1, which stays reserved for a failed task. A task's POST is never retried.

The host of `AGENTIC_LABS_MODEL_BASE_URL` must be in the labs' egress allow-list (FiligranHQ/platform `copilot_agentic_labs.egress_fqdns`). The golden-task runner of `dev-docs/ootb-routing-eval.md` is `.xtm-one/lab/routing_eval.py` (#10169).
