# Agents, assignments, memory and templates

The root `AGENTS.md` keeps one line per entry, because every agent session loads it; this file holds the full contract. Add detail here, never to `AGENTS.md`.

## How Agents & Assignments Work

```
Agent (persona + tools + knowledge)
  └── Assignment 1: "Auto-triage email"
  │     trigger: integration_event (new email)
  │     prompt: "Analyze this email, flag if important, draft reply..."
  │     → AI runs with prompt + trigger payload + MCP tools + knowledge bases
  │
  └── Assignment 2: "Enforce labels on closed issues"
  │     trigger: webhook (GitHub issues.closed)
  │     delay: 10m
  │     prompt: "Check if issue has closing label, if not, comment..."
  │     → After 10min delay, AI runs with GitHub MCP tools
  │
  └── Assignment 3: "Answer Teams questions"
        trigger: integration_event (new Teams message)
        prompt: "Search knowledge bases, answer the question..."
        ai_label: true
        → AI searches docs and replies automatically
```

### Assignment Execution Flow

1. **Trigger fires** (schedule tick, webhook POST, integration event, or manual)
2. **AssignmentRun** record created with trigger payload
3. **Delay applied** (if configured — the orchestration execution's `run_at` is set in the future; the worker reconciler picks it up when due)
4. **Gate stages**, each optional and in this order: the tool check (`activation_check`, no model call, before the quota charge), then the activation prompt (one model call). A failed stage ends the run skipped (see "Activation gates" below).
5. **Prompt rendered** with template variables (`{{trigger.*}}`, `{{agent.persona}}`)
6. **Custom prompts applied** (activation gate, AI label, or human-in-the-loop prompt overrides if set; otherwise platform defaults)
7. **Agentic loop** runs: LLM + tools (MCP, knowledge base search) with the prompt. Read KBs are determined by `read_knowledge_base_ids` (NULL or [] = all agent KBs; subset = refine). Write access (`store_knowledge`) is determined by `write_knowledge_base_ids` refining the agent's writable KBs from `knowledge_base_permissions` (NULL = all agent-writable KBs, [] = none, subset = refine).
8. **Results recorded** (actions taken, summary, status)
9. **Notification** sent to user (if configured)

### Activation gates

An assignment has up to two gates, evaluated in order before the action prompt; a failed one ends the run `completed` with a `Skipped: ...` summary.

1. **Tool check** (`activation_check`, `services/assignment_activation_check.py`): `{"tool", "arguments", "condition"}` - one READ-ONLY tool the agent holds (`tool_classification`; a write tool is refused at save) and a condition on its structured result: `non_empty` (default), `empty`, or `{"path": "$.status", "in": [...]}` (also `not_in`, `none_in`, or `contains` with a string; a `.key` read on a list reads each element, `[n]` / `[*]` index; `not_in` needs the path to reach a value, `none_in` also passes when it reaches nothing). `{{agent.id}}` / `{{assignment.id}}` in the arguments name the running agent and assignment, so a duplicated or cloned assignment checks its own; `{{payload.<a.b.c>}}` names a plain value of the run's trigger payload, and a field the payload does not carry leaves the check not evaluated (#8655). Skipping an event run whose branch is leased by a live run: `{"tool": "get_shared_state", "arguments": {"key": "<lease prefix>:{{payload.pull_request.head.ref}}"}, "condition": {"path": "$.held_by_run.alive", "none_in": [true]}}` (an ended holder or no lease lets the run go ahead). Evaluated by `assignment_engine._skip_by_activation_check` before the quota charge, before a model is resolved and before the LLM gate: a failed check records `Skipped: gate check <tool> returned empty` (or the path condition it missed), zero tokens, the call and its result in the run's messages. The tool is called through the executors the run would build (the built-in coordination tools, then the integration tools of the run's bindings, read-only bindings and the enforced Scope(s) applied; MCP servers and custom tools are not connected for a check) and read from `ToolResult.structured` (`list_work_items`, `get_shared_state`, `list_microsoft_calendar_events` set it), else from JSON text. A check that cannot be evaluated (no such tool, a tool error, no structured result) lets the run proceed, logged. `also` chains up to 3 more checks of the same shape, evaluated in order (no nesting): the run is skipped at the first that fails, so a lease and a per-head claim, or an open review item, each stand an event run down at zero tokens; an extra check that cannot be evaluated is passed over (#10597). `or` lists up to 3 alternatives instead (any-of, never combined with `also`, no nesting): evaluated in order, the first that passes lets the run go ahead, the run is skipped only when every check fails, its summary `Skipped: gate checks: none of N passed (check 1: <tool> <arguments>: <reason>; ...)` naming each one; a check that cannot be evaluated lets the run go ahead and is named in `gate_checks_not_evaluated` (`assignment_engine._skip_by_any_of_checks`; `describe_check` reads `any of: ...; or ...` in `get_assignment`). A HITL resume is past both gates. Written by the REST create / update (`null` clears it), the agent builder's `create_assignment` / `update_assignment` (`'none'` clears it), and carried by duplicate, catalog clone and export / import.
   A `get_shared_state` read with `where_json` carries `matches` (the selected list items, flat) and `match_count` in its structured result next to the entry, so a check such as `{"tool": "get_shared_state", "arguments": {"key": "dev:open-prs", "path": "prs", "where_json": "{\"branch\": \"{{payload.workflow_run.head_branch}}\"}"}, "condition": {"path": "$.match_count", "not_in": [0]}}` skips an event whose item the list does not register, at zero tokens (#489).
2. **Activation prompt** (`activation_prompt`): one model call over the rendered prompt plus the trigger block, answering `YES` / `NO` / `SKIP`.

### Integration-event delivery and filters

Every `integration_event` event - polled (`services/event_poller.py`), pushed by Graph (`api/v1/integration_notifications.py`) or delivered to a webhook receiver (`api/v1/webhooks.py`: the provider URL, whose cached routing carries the filter in `_AssignmentMatcher.payload_filter`, the integration URL and the per-assignment URL) - goes through the trigger's filter (`trigger_config.filter`, `services/integration_event_filters.py`) before a run is created or any gate runs; a dropped event stays in the seen set and increments `Assignment.events_filtered_count` (`events_filtered_count` on the REST response, "Events filtered" in `get_assignment` and the trigger card). A `webhook` or `integration_event` delivery for an assignment whose acting user (or the platform) has exhausted the agentic quota creates no run either (`assignment_engine._drop_delivery_over_quota`, run by `trigger_assignment` and `trigger_or_queue_assignment`): it is counted the same way with the reason `quota_exceeded`, logged once per assignment per hour, and publishes no event; the per-assignment webhook answers `dropped`. A quota store that cannot answer drops nothing (the run's own check decides under `QUOTA_FAIL_MODE`). The first quota refusal of the UTC day for an agent (a delivery dropped here, or a queued run skipped at dequeue) sends one notification-bell entry to the agent's owner and every active administrator naming the assignment (`services/quota_exhausted_notice.py`, Redis `SET NX` on `assignment:quota_exhausted_notified:<agent>:<day>` with a 25 h TTL; Redis down sends nothing). The keys each event takes are declared on its catalog entry (`available_events[].filter_keys`, shown by the agent builder's `list_integration_catalog`). An event outside the mail, Teams, DocuSign and calendar families is matched on its payload (`payload_filter_reason`: subset equality, a list is any of, dotted paths, a literal dotted key wins, `labels[].name` maps a list). On top of those values a key takes an operator object (`eq`, `ne`, `in`, `not_in`, `starts_with`, `ends_with`, `contains`, `matches` whole-value regex bounded by `MAX_PATTERN_CHARS` / `MAX_MATCHED_CHARS`, `exists`; `ne`, `not_in` and `exists: false` hold on an absent field) and the filter takes `all` / `any` / `not` combinators; an object whose keys are all operators is an operator object and a combinator holds objects, so every filter saved before keeps its result (invariant in `tests/test_integration_event_filter_expressions.py`). `filter_expression_error` refuses at save (REST schemas, `create_assignment` / `update_assignment` through `platform_event_trigger_error`) an unknown or misspelled operator, a bad operand, a regex that does not compile or nests quantifiers, naming the key. A filter naming `enriched.` (`needs_enrichment`) is skipped by the cached routing and evaluated on the match path, its plain part first: the top-level entries reading no `enriched.` key (`plain_filter_reason`; they are ANDed, so their drop is the filter's drop) are matched on the delivery alone, in `webhooks._assignment_filter_reason` and in the retry's `_evaluate`, and a delivery they drop (a requested run, a conclusion the filter does not want) is counted with its own reason without any read of the facts; only a delivery they admit reads them: `services/event_enrichment.enrichment_for` runs the provider's registered enricher (`integrations/event_enrichment.py`; GitHub: `providers/github/event_enrichment.py`, the open pull request of the head commit of `workflow_run`, `check_suite`, `check_run`, `status` and `push` from `GET /repos/{repo}/commits/{sha}/pulls`) with the token of the assignment's integration (`trigger_integration_id`, `resolve_token_holder`), cached in Redis per integration and head for 10 minutes; an enricher declaring `EventEnricher.facets` reads only the optional parts the filter's keys (`filter_keys`) need, passed to its `fetch` as `facets=` and added to the cache key and the per-delivery memo key (GitHub: the head's check runs, `GET /repos/{repo}/commits/{sha}/check-runs`, are read on the CI events only when a key is `enriched`, `enriched.head`, `enriched.head.checks` or under it, so a filter on `enriched.pull_request.*` alone is never dropped by a check-run timeout, a GitHub error on it or the 1000 check runs cap, and a pull-requests-only answer never answers a checks filter); the facts are filter input only, the run receives the delivery as it came, and a failed read sets `enriched.unavailable` so every `enriched.` predicate drops the event. A failed read of an event the provider marks retryable (`EventEnricher.retryable`; GitHub: a completion, `is_completion`, the only delivery that can turn `enriched.head.checks.all_green` true), for any reason but a `PermanentEnrichmentError` (the 1000 check runs cap, an event naming no head), also sets `enriched.retryable`: the webhook receivers then defer the delivery for that assignment (`services/event_enrichment_retry.defer`, Redis sorted set `integration_event:enrichment_retry:pending` and one entry key per assignment and delivery, 30 minutes at most) instead of counting it filtered, and the scheduler tick (`process_due_retries` in `services/autonomous.py`) reads the assignment afresh (enabled, owner active, same provider, current filter), reads the facts again and triggers it like the receiver would (`skip_if_active`, `queue_busy_pushed_event`; `trigger_context.enrichment_retry` names the attempt and the first reason), at most twice (`RETRY_DELAYS_SECONDS` 60 s then 180 s); still unreadable after the last read, the delivery is counted filtered with its reason. Redis down, nothing is deferred and the drop stands. The reason of each drop is counted per assignment in Redis (`record_filter_reasons`, 7 days, 50 reasons) and listed by `get_assignment` under "Dropped by reason". `get_assignment` labels an event no poller reads (not in `event_poller.POLL_INTERVALS`) `Delivery: webhook (provider URL)`.

**A CI head whose last completion was lost still wakes its assignment once** (`services/event_enrichment_retry.py`: `watch`, `mark_admitted`, `process_watched_heads`; `EventEnricher.watch_subject` / `settled` / `best_case`, GitHub's in `integrations/providers/github/event_enrichment.py`). The completion of the last check of a head is the only delivery that turns `enriched.head.checks.all_green` true, and it can be lost before it is read at all (the workers replaced during a rollout): no read failed, so the enrichment retry has nothing to defer. A webhook receiver that drops a retryable completion for an assignment while the head still has checks running, when the same filter would admit it with every running check finished successfully, watches the head for that assignment (Redis `integration_event:head_watch:*`, one entry per assignment and head, the latest delivery kept). The scheduler tick (`autonomous.py`, after the enrichment retry) reads each watched head again every `WATCH_INTERVAL_SECONDS` (180 s) with `enrichment_for(fresh=True)`: the filter admits it, the assignment is triggered once (`skip_if_active`, trigger context `head_watch`); still running, watched again; finished red or a miss, the watch ends; `WATCH_TTL_SECONDS` (2 h) at most. A delivery the receiver (or the enrichment retry) admits marks the head admitted for the assignment (`ADMITTED_TTL_SECONDS`, 6 h), which ends its watch, so the head woken by its real last delivery is never woken twice. A head whose check runs all read green while one of its GitHub Actions workflow runs is not completed (a re-run of the failed jobs requested, the new check runs not listed yet) is pending, not green: on a candidate green head the GitHub enricher also reads `actions/runs?head_sha=` and counts each workflow run not completed as a pending check `workflow:<name>` (`_running_workflow_runs`, `with_running_workflows`), so a watched or late completion read in that window wakes nothing (#9740). `all_green` stays true on every completion delivered after the head turned green (a late or redelivered check run): `enriched.head.checks.last_to_complete` is true only when no check run of the head finished after the delivery's own completion time (`check_run.completed_at`, else the payload's `updated_at`; ties allowed), so a filter adding it wakes on the completion that turned the head green; a watched head, settled, reads it true through `event_enrichment.as_watched_delivery` (the provider's `best_case`), since the watch stands in for the lost last delivery (#10391). A completion whose facts could not be read for a retryable reason (a timeout, a provider error) also watches its head, next to its two deferred reads: nothing says it was not the head's last completion, and both deferred reads (60 s, then 180 s later) can time out in the same provider slowdown, which dropped the green of four PRs in a row on 13 Nov 2026 (the head watch keeps reading for 2 h; a settled red head ends it). Redis down: nothing is watched, as before.

**A CI event a run stood down on because another live run held its lease is delivered again** (`services/event_enrichment_retry.py`: `hold_for_lease`, `process_held_events`; `assignment_engine._hold_event_for_lease`; `assignment_activation_check.live_holder_id`). A run whose `activation_check` fails on a shared-state read naming a LIVE `held_by_run` (never the run itself) used to end skipped with the event gone, and a head's green is delivered once. The engine now keeps the event of an `integration_event` run on a watched CI head, one entry per assignment and head sha (a second event on the same sha replaces the first, so one delivery follows), and the scheduler tick reads the holder every `HELD_INTERVAL_SECONDS` (60): once that run ended, the assignment's current filter is evaluated on the head's fresh facts and an admitting head triggers it once, the run's `trigger_context.held_by_lease` naming the holder. An event waits `HELD_TTL_SECONDS` (2 h) at most. The skip summary says the event is delivered again. A scratch branch of the batched commit (`tmp/commit-batch/*`, never a pull request head) registers no head watch and no hold (`head_subject` answers `None`). **An admitted CI head is delivered once more at the end of a window** when the assignment sets `trigger_config.redeliver_after_seconds` (bounded to 60 s .. 2 h; `redeliver_after`, `schedule_redelivery`, `process_redeliveries`): the run the admission starts may stand down on a time-bound condition (a review or bot-thread window), so the head is evaluated again on fresh facts after the delay and triggers the assignment once if the filter still admits it (`trigger_context.redelivery`). One re-delivery per assignment and head, ever: a head is woken at most twice. It is also the stall safety net: an at-green merge assignment with `redeliver_after_seconds: 900` re-reads every green head it was woken on 15 minutes later.

**A platform event delivery that errors is delivered again, never lost** (`services/platform_event_retry.py`: `schedule`, `process_due`; `platform_events._dispatch_assignments`, `platform_events.redeliver`; #2101). When one subscriber's delivery raises (the database pool exhausted, a dropped connection) or the subscriptions cannot be read, the delivery is kept per (event, assignment) - per event when the subscriptions were unreadable, which is never read as "no subscriber" - in the Redis sorted set `platform_event:delivery_retry:pending` and delivered again by the scheduler tick through the same bounded dispatch gate (#2084), after 30 s, 2, 5, 15 and 30 minutes. A redelivery is safe: the run's `dedup_key` makes an event that did get its run a duplicate. A delivery still failing after its fifth attempt, or that cannot be stored, is abandoned: counted on the assignment's `events_filtered_count` with the reason `delivery failed: <error>` (`get_assignment` "Dropped by reason") and logged as an error.

**A head whose required checks passed wakes even when a non-required check never finishes** (`enriched.head.required`, facet `required` of `integrations/providers/github/event_enrichment.py`: `required_facts`, `_required`; #11419). `all_green` needs every check of the head, so a third-party check left in progress (a coverage upload) kept an approved pull request whose branch rules were met from waking any filter. A filter key under `enriched.head.required` reads the open pull request's base branch required contexts (`checks.read_required_contexts`, rulesets and classic protection, the read behind the "Required by" line of `get_github_ci_status`) and the head's latest check runs and commit statuses against them (`checks.summarize_required`): `total`, `passed` (skipped and neutral pass), `failed`, `pending`, `missing`, their `*_names`, `base`, `all_passed` (at least one required context, every one passed) and `last_to_complete` (no required check finished after the delivery). No open pull request or no required context reads `all_passed` false; a filter that does not name the facet makes none of these reads.

**Only a required check makes a head red** (`check_facts` of `integrations/providers/github/event_enrichment.py`, `record_unconfirmed_failure` of `services/work_item_pull_requests.py`; #11807). When a head heads an open pull request and one of its checks is red, the enrichment reads the base branch's required contexts once and weighs only them in `enriched.head.checks` (`failed`, `failed_names`, `first_failed`, `first_failure`, `all_green`); the other reds are `failed_not_required` / `failed_not_required_names`, and each of `names[]` carries `required` and `provisional` (a Codecov grade). The latest run of each check stands, so a red re-run green on the same head never counts; on a candidate green head it stands per workflow event too, so a later green of the `push` run never hides a red of the `pull_request` run with the same check name (`reds_of_another_event`, opencti #20153). A red `check_run` completion that reads `first_failure` true has the head's workflow runs read once: when the delivered check's workflow run (its URL or check suite) is running a later attempt (a re-run of failed jobs) that started after the check, `first_failure` reads false and `superseded_attempt` names the run (`superseded_attempt`, #2210); an unreadable answer keeps the wake. A base with no readable required context keeps every check deciding. On a work item, a delivered failure the live read does not confirm on a required check is recorded so (the live green, or the failed runs marked `not_required`): `red_pull_requests` no longer reads the pull request red, so neither the red self-block release nor the inbox red guard acts on it.

**A red the head did not cause can be told from a new one** (`parent_facts` and `_parent` of `integrations/providers/github/event_enrichment.py`; #752). A filter key under `enriched.head.parent` reads, on a head with a counted red only, the head's first parent and its latest check runs (two more reads): `failed_names` (the head's counted reds already red on the parent), `new_failed_names` (the others), `sha` and `unchanged_red` (at least one counted red, none new). A red-check filter adds `{"enriched.head.parent.unchanged_red": {"ne": true}}` to stand down on a red a bot or docs commit inherited; a green head, no parent or an unreadable parent reads `unchanged_red` false, so the wake is kept.

**A pending or red commit status holds a head its check runs read green** (`with_commit_statuses` of `integrations/providers/github/event_enrichment.py`). Check runs never carry a commit status (CircleCI, Snyk, any app on the Status API), so when the check runs read `all_green` the head's commit statuses are read too (`GET /commits/{sha}/status`, one more read on a candidate green head only): a pending status counts as a pending check and an `error` / `failure` one as a failed check, named `status:<context>` in `names[]` / `failed_names`; with the base's required contexts read, a red status outside them is `failed_not_required`. A status already left out as a stale optional check does not hold the head. A `check_run` completion no longer wakes `enriched.head.checks.all_green` while a CircleCI job still runs. A status app creates the statuses of a later stage only after the earlier one ended (CircleCI created the `build-*` statuses 16 s after the last `test-*` one passed), so a head whose newest status changed under `STATUS_SETTLE_SECONDS` (60 s) ago reads pending (`status:settling`, #773): the head watch reads it again and wakes green once no new status appeared. A red status is never held as settling.

**A Codecov red read before the uploads is provisional** (`coverage_pending` and `is_coverage_grade` of `integrations/providers/github/checks.py`; #12050). Codecov grades a head as soon as a first coverage upload lands and grades it again as the others arrive, so a red grade (app `codecov`, or a check run or commit status named `codecov/*`) read while another check of the same head still runs can turn green with no push. While that holds, `enriched.head.checks.coverage_pending` is true and the red grade is never `first_failed` nor `first_failure` (it still counts in `failed_names`, so `all_green` stays false); the live verdict `head_ci_decision` of `providers/github/reference_state.py` leaves the head undecided; and a delivered Codecov failure the live read finds provisional is not dispatched to the work items bound to the pull request: its run is marked `provisional`, its dispatch key given back, so neither the red-head release nor the inbox red guard acts on it. Once every other check of the head completed and Codecov is still red, the red decides as any other, and the head's last completion wakes once.

**A workflow run that concluded without any job is `no_jobs`, never a red to diagnose** (`enriched.run`, facet `run` of `integrations/providers/github/event_enrichment.py`: `run_facts`, `_run_jobs_total`; `no_jobs_run` and `_no_jobs_answer` in `integrations/providers/github/actions.py`; #11490). GitHub can conclude a run `failure` without ever assigning it a runner (9 Nov 2026 18:09-18:28Z: five workflows of xtm-one and two of OpenCTI at once, `checkSuite.checkRuns.totalCount` 0): no job, no log, nothing in the code to fix. On a `workflow_run` completion that is not green, a filter key under `enriched.run` reads the run's job count: `id`, `attempt`, `jobs`, `no_jobs`. A red-check filter adds `"enriched.run.no_jobs": false`; a listener on `no_jobs` true and `attempt` 1 re-runs it once. `list_github_workflow_jobs` answers such a run as classified `no_jobs` with its one rerun; `manage_github_workflow_run` turns `rerun_failed` into a whole `rerun` on it and refuses a rerun of attempt 2 or later.

**One run per inbound event on an agent** (`services/event_run_dedup.py`). The per-assignment seen set stops one Graph message from running twice on one assignment, but a mail that reached two mailboxes an agent listens to (a service account's and a person's) has a different Graph id in each, a notification and the poll behind it can race, and a delegated run (`delegate_to_assignment`, a work item) has no seen set: the same reply was sent twice from one agent. Every run about to start gets a *dedup key* (`run_dedup_key`, recorded in `trigger_context.dedup_key`, visible in `get_run` / `list_runs`): a Microsoft `new_email` takes the mail's `internetMessageId` (`payload.internet_message_id`; without one, `conversation_id` + `received_at` + `from`), a `calendar_event_changed` the event's `iCalUId` (else its id) + `lastModifiedDateTime` (one key per modification), a `delegation` / `work_item` run the single Message-ID its task text names or its work item payload's `message_id`; a webhook, scheduled, manual or follow-up run has none, and so do Teams, Slack and the other provider events (their per-assignment seen set stands). `trigger_assignment` and `trigger_or_queue_assignment` take an agent-wide advisory lock (`_acquire_agent_dedup_lock`, after the assignment lock, always in that order) and ask `duplicate_event_run` for a run of the same **agent** carrying the key within the window (`ASSIGNMENT_EVENT_DEDUP_WINDOW_SECONDS`, default 600; `trigger_config.dedup_window_seconds` per assignment, `0` off), across its assignments and delivery paths; found, the delivery becomes a `skipped` run whose `result_summary` starts with `skipped: duplicate of run <id>` and whose `trigger_context.dedup_duplicate_of` names the original (never itself an original), nothing executes, `events_filtered_count` is incremented, and `trigger_or_queue_assignment` answers `status="duplicate"`. Scheduled triggers are untouched. Tests: `test_event_run_dedup.py` (pure), `test_assignment_event_dedup.py` (engine, fake session), `test_event_run_dedup_postgres.py` (the query, the concurrent insert).

**Configured dispatch dedup key** (#10622, `trigger_config.dedup`). An `integration_event` (or provider-webhook) assignment may key its deliveries itself, for events no built-in key covers (two check runs of one head 0.4 s apart, a `workflow_run` and a `check_run` listener on one head): `{"key": "{{payload.repository.full_name}}@{{payload.check_run.head_sha}}", "window_seconds": 120, "group": "green"}`. `configured_dedup_key` renders the template (`{{payload.a.b}}` plain values only, lower-cased) over the delivered payload when the trigger context is an event delivery (`integration_event` or `webhook`), scoped `cfg:group:<group>:` when a group is named (assignments of one agent naming it share the key space) else `cfg:assignment:<id>:`; a field the delivery does not carry keys nothing and the run starts. The key then rides the same path as the built-in keys (agent lock, `duplicate_event_run`, `skipped` duplicate run), with `window_seconds` (1 to 3600, default 60) as its window; a run its own gate skipped does not count as the original for a configured key, so a later delivery still gets its run. Every duplicate is also counted under `Dropped by reason` (`dedup: same configured key within the window`, `dedup: same inbound event within the window`). `trigger_filter_error` refuses an unusable `dedup` at save time (`dedup_config_error`). No `dedup`: today's behaviour.

**One answer per conversation on the send** (`services/mail_send_guard.py`). Whatever let a second run start, the Microsoft mail tools send one answer per thread: before `send_microsoft_email`, `send_microsoft_draft` (and so every reply or reply-all draft sent) the provider takes a Redis lock keyed by the agent (`context.agent_id`, handed to `build_tools` by `integration_tools`; a send outside an agent's tools is not guarded) and the thread (the draft's `conversationId`; for a new email the normalised subject and To / Cc addresses, `thread_key`), reads the agent's record of its last send in that thread (`mail_send_guard:sent:<scope>:<thread>`, expiring with the window), then the mailbox's Sent Items bounded to the window (`sentDateTime ge`, matched by conversation id or thread fingerprint), and, when it finds one, reads the conversation once for a message from someone else received after that earlier send (`GET /me/messages`, `conversationId eq ... and receivedDateTime gt ...`, `inbound_after`; drafts and this mailbox's own messages, told by `/me`, do not count): such a message means the send answers something new and it goes out (recorded, no `force_duplicate` needed). Only when nothing new arrived, or when that cannot be checked (no conversation id, a failed read), is the send refused with an answer naming the earlier message (`refusal`, which says which) unless `force_duplicate=true` is passed; a lock already held by another attempt is refused too (`contention_refusal`). A successful send is recorded and the lock released; a failed one releases the lock and records nothing. `create_microsoft_draft_reply` warns in its answer when the conversation was already answered. Window `MAIL_SEND_GUARD_WINDOW_SECONDS` (default 300, `0` off). Redis is fail-open (no lock, no record, the Sent Items check still runs). Tests: `test_mail_send_guard.py` (pure parts and the tools on a fake Graph and Redis).

### Trigger Types

| Type | How it works |
|------|-------------|
| `schedule` | Cron expression. Background scheduler checks every 60s. The cron is read on the wall clock of `trigger_config.timezone` (an IANA name such as `Europe/Paris`, daylight saving included; `core.utils.schedule_timezone` / `next_cron_run(tz=)`), UTC when the key is absent; an unknown zone is read as UTC and reported ("timezone '<value>' not recognised, UTC used") by `GET /assignments/schedule` (`timezone_warning`) and `get_assignment`, which also show the next run in the zone (`next_run_local`) and in UTC (`next_run_at`). A local time a daylight saving change skips fires once at the first valid instant after the gap; a repeated one fires once, at its first occurrence. Older builds ignored the zone (every schedule ran at the cron hour in UTC): an existing assignment with a timezone needs no edit, it fires at the local hour from the deploy, one hour earlier in local winter time (two in summer) than on the broken builds, and its next fire is computed from `last_triggered_at`, so a deploy never fires it twice. A schedule created enabled runs once at the first tick after its creation (the creation auto-run) unless `trigger_config.run_on_create` is `false`: `core.utils.schedule_base` then anchors it on `created_at`, so its first fire is the first cron occurrence after creation (a non-boolean value is refused by `validate_schedule_trigger_config`). A due fire dropped because a run of the assignment is still active is recorded as a `skipped` run naming that run and since when (`Scheduled fire skipped: previous run <id> still running since ...`), and a resumed run is bounded by its timeout across its resumes (`dev-docs/background-task-resume.md` section 8sexies). |
| `webhook` | Custom HTTP endpoint: `POST /api/hooks/{agent_id}/{path}`. GitHub events, OpenCTI, any external system. An optional `events` allow-list filters on the delivery's event key. |
| `integration_event` | Events from integrations (new email, new message). Provider + `event` (the agent builder's old `event_type` key is read only on a trigger marked exact). |
| `manual` | Triggered from UI or API: `POST /api/v1/assignments/{id}/trigger`. |
| `work_item` | The agent's inbox: each scheduler tick claims the open work items its agent owns, in priority order (urgent, high, medium, low) then due then oldest, and runs them, one at a time by default (`autonomous._process_work_item_assignments`). `trigger_config.max_concurrent_runs` (1 to 10, default 1) runs up to that many items in parallel, each on its own claimed item: a pass fills every free slot, the end of each run wakes the next pass, and `trigger_assignment(max_active_runs=N)` counts the active runs against the cap under the per-assignment advisory lock, so two passes never exceed it (`assignment_dispatch.work_item_inbox_cap`, `work_item_concurrency_error`). `trigger_config.express_lane` `{"correlation_prefixes": [...], "slots": N}` (1 to 10 prefixes, 1 to 5 slots, #11082) adds N slots above the cap for the items whose correlation key starts with a prefix: the pass fills the regular slots first in the usual order, then lists the express items apart (`autonomous._with_express_candidates`, inside the inbox's own `correlation_prefix`) and claims only them, each trigger guarded by `max_active_runs=cap+N`, so short critical-path items never wait behind long runs (`assignment_dispatch.work_item_express_lane`, validated by `work_item_express_lane_error` through `work_item_concurrency_error`). `xtmone_assignment_runs_active` and `xtmone_assignment_concurrency_cap` report the inbox's slots. The same pass also runs as soon as an item becomes dispatchable (`services/work_item_dispatch_wake.py`): `create_work_item` of an owned open item, any status change or claim release back to `open` (`work_item._publish`), an open item routed to a new owner, the legacy orphan release, and the end of a run an inbox started (the assignment adapter) publish `work_items:dispatch`; every process listens and one runs the pass under `copilot:work_item_dispatch_lock` (renewed by token), a nudge during a pass sets `copilot:work_item_dispatch_pending` so the holder runs again (at most 5 passes). Same gates as the tick (AI on, owner active, atomic claim, `skip_if_active`); the 60 s tick stays the backstop. An open item whose open pull request (`payload.pull_requests`) is named by a shared-state entry a LIVE run holds as a lease (`set_shared_state(hold="take")`, value `{"pr": N, "repository": ...}` or a key ending with the head branch, the matcher of `shared_state_pull_requests.entry_names_pull_request`) is left open and unclaimed: that run is pushing the fix, and a dispatched run would only stand down (`shared_state_pull_requests.live_pull_request_lease`, #10737); a per-head claim keyed `<prefix>:<owner/name>@<head sha>` (the merging run's green claim) names its repository the same way (`repository_in_key`, #12040); the pass after the release or the holder's end takes it, and a failed lease read dispatches as before. At an inbox run's end, a ready green head whose `[merge] full_ci_workflows` run is still queued or running (`full_ci` of the live read, `reference_state.read_pull_request_ci`) is parked on its merge, never put back in the queue (#12040); so is a ready green head waiting in the base's merge queue (`merge_queue` of the live read, GraphQL `isInMergeQueue`, `work_item._merge_queued`): the queue's merge or its removal (`dequeued`) is the wake (#404). A ready green pull request with no CI completion left to come is put back with a `not_before` of `work_item.GREEN_HANDOFF_DEFER` (3 min): the head's own green event run (the listener that takes the per-head claim and merges) goes first, the inbox never starts a second run on that head. A failed read starts the run as before. `xtmone_work_item_dispatch_lag_seconds{path=tick|wake}` measures last activity to dispatch. `trigger_config` is `{}` or the optional `correlation_prefix`, `priority_min`, `owner_agent_id`, `max_concurrent_runs`, `express_lane`. | `platform_event` | An event raised inside the platform (`services/platform_events.py`). `trigger_config` is `{"event": <name or list>, "filter"?: {...}, "scope"?: "own" \| "fleet" \| "all", "once"?: bool, "expires_at"?: <ISO 8601 date-time with offset>, "role"?: "observer" \| "worker"}` (`role`: `observer` watches the objects of its events without working them, delivery unchanged, left out of who works a CTEM case by `frontend/src/pages/xtm-one/ctem/case-workers.ts`, #2054; `scope`: `own` the events of objects the agent takes part in, `fleet` the events whose `agent_id` or a participant is a home member of the agent's fleet, membership read once per dispatch by `_fleet_members` and refused at save by `fleet_scope_error` for an agent in no fleet, `all` an administrator's every event; `once`: a one-off watch; `expires_at`: the subscription's deadline, checked when the subscriptions are read and again under the row lock at delivery, so an event raised after it starts nothing and an expired watch is never consumed; refused on save when it does not parse, a hand-edited unparseable value counts as passed); the events and their filter keys are `PLATFORM_EVENTS` (agent builder: `list_platform_events`). |

**A blocked item is released by the workflow run delivery, and a backstop releases what every path missed** (#234; `work_item_blocked_refs`: `release_from_workflow_run_delivery`, `named_by_workflow_run`, `release_satisfied_blocks`, `note_unread_references`). A `workflow_run` completed delivery that succeeded (the `ci` form of the GitHub parser, `run_key` `workflow:<id>`, `extra.workflow_file`), signed or not, names the open `workflow_run` references of the same repository whose `workflow` is that file or id and whose `branch`, when set, is the run's; each is read back in the background through the polling fallback's `WorkflowRunReader` with its owner's credential (at most `HINT_MAX_READS` reads per delivery), and only the run that read returns is applied, so the release lands seconds after the run instead of the next pass; the poller stays the fallback. A run that already succeeded when the item is blocked sends no delivery any more: `create_work_item` / `update_work_item` call `schedule_workflow_run_check` once at a write that leaves the item blocked on a `workflow_run` reference, and `check_item_workflow_runs` reads its open `workflow_run` references through the same reader and apply, at most `HINT_MAX_READS` reads. A workflow GitHub does not know (404: a typo, a renamed or removed file, a repository the credential cannot read) is a read failure, never "no run yet": `read_successful_workflow_run` raises on it, and the check at the write writes the read-failure note on the item at once (`note_unread_references(quiet=False)`, still one note per 6 hours) (#386). Once per polling pass, `release_satisfied_blocks` releases any item blocked on references only whose references are all met, with no `blocked_on` and no `needs_human`, a note `released by the backstop: every reference was already met (...)` on top of its description. A reference the provider could not read is counted (`read_failed`) and, on an item blocked and quiet for 15 min, written as a claim note `not released yet: a reference could not be read at <time> (<reference>: <error>)` at most once per 6 hours, its activity time untouched.

**A blocked item waits for the end of an outbound A2A task** (`work_item_a2a_refs`: `refuse_unknown_a2a_tasks`, `release_ended_a2a_tasks`, `schedule_a2a_task_check`). A `blocked_on_refs` entry `{kind: a2a_task, task, release_on: completed | terminal}` (no repo; terminal by default) names the `collect_task_id` a delegation answered. The write refuses a task id the item's user has no `A2ADelegation` for (`partner_task_id`), so a wait nothing could release is never stored. The autonomous tick, and the write once, read the delegation's `outcome` and `terminal_at`: the reference records `state` completed (outcome completed) or ended with its `outcome`; terminal is met by both, completed is met by completed and a task that ended another way hands the item back too, its release note naming the outcome. An item whose references are all met, with no work item and no person to wait for, returns to open, unclaimed.

**A blocked item can wait for the first tag carrying a commit** (#2209; `work_item_blocked_refs`: `_normalize_tag_ref`, `_poll_tag`, `check_item_tags`, `release_from_tag_delivery`; `integrations/reference_state.TagReader`, GitHub `read_tag_carrying`). A reference `{"repo": "owner/name", "kind": "tag", "pattern": "*.*.*", "carries": "<sha>", "release_on": "created"}` (`pattern` a tag name glob, `*` when omitted; `carries` required, a commit of the same repository) is satisfied by the newest tag matching the pattern whose commit is `carries` or a descendant of it (GitHub: the first 100 tags, sorted by version, the compare of the commit and at most 3 of them). It is read at the write that blocks the item, by the polling fallback, and on a GitHub `create` delivery of a tag (parsed as a `tag_created` event, signed or not, read back before anything applies). **An item about one pull request waits on that pull request** (#11507, `work_item_blocked_refs.refuse_foreign_pull_request_ref`, `own_pull_request`). A UX verdict item (key `dev:ux-verdict-<N>-comment`, its title naming `owner/name#N`) or a UX review item (`ux:<repo>-<N>`, `ux:gate:<repo>-<N>`) belongs to pull request N. `create_work_item` and `update_work_item` refuse to block it on a `pull_request` or `deployment` reference naming another open pull request of the same repository (a sibling of the program, a superseded or stale number): the refusal names the expected `{repo, kind: pull_request, number: N}` and points to `blocked_on` for a wait on another change. **A waiter on a UX review reopens once its verdict is on the pull request** (`work_item.release_satisfied_dependencies`, `_pending_verdict_comments`). A UX review item (`ux:<repo>-<N>`, `ux:gate:<repo>-<N>`) completes when its verdict is decided, and the item that posts the verdict on the pull request (`dev:ux-verdict-<N>-comment`, same owner, the same repository when its title names `owner/name#N`) is often still running. **A reference follows a pull request regenerated on its branch** (#11187, `work_item_blocked_refs.followed_number`). A changesets release workflow closes its release pull request and opens a new number on every merge to main, always from the same head branch (`changeset-release/main`). A closing unmerged that the reference wanted merged no longer surfaces the item: the number is recorded in the reference's `superseded` list, the item stays blocked with a claim note, and the next pull request of the branch is followed; the successor's merge releases it (`merged_number` names it, the release note says `successor #N`). Without `head_branch` nothing changes: a superseded pull request surfaces the item as before.

**A dependant of a dev item waits for its pull request's deployment** (#9943, `work_item_pull_requests.carry_dependants_to_deployment`). Another repository: unchanged, released at the completion.

**A merge queue removal surfaces an item blocked on that merge** (#397, `work_item_blocked_refs.surface_on_dequeue`, called by `work_item_pull_requests.handle_pull_request_event` on a `dequeued` event). **One carrier per red on main** (#11562, `services/work_item_main_red.py`). a `run.*` event never wakes the assignment whose run it is about (no `run.completed` self-loop); the run's `trigger_context` is `{type: "platform_event", event, event_id, object_type, object_id, occurred_at, triggered_at, ordering_key, dedup_key}` (`occurred_at` when the event was raised, `triggered_at` when it was delivered: with the run's start, the event-to-run latency is measured) (ids only: every text field stays in the quarantined payload). **Dedupe**: `dedup_key = platform_event:<event id>:<assignment id>` through `duplicate_event_run` (24 h window). **Live holder**: an event about a work item whose holder is a live run of the same assignment (any of its concurrent runs) appends a dated `claim_notes` entry tagged `[event <id>]`, once per event, instead of a second run (the pattern of `work_item_pull_requests`). **One-off watch**: `once: true` in the trigger config makes the subscription a watch: `_deliver` locks the assignment row (`_consume_watch`), writes `fired_event_id` and `fired_at` into its `trigger_config` and starts the run in the same transaction, so two events raised together start one run and a failed trigger leaves the watch armed; `_subscriptions` skips a fired watch (`watch_fired`) and the run's `trigger_context` carries `once: true`. Saving the trigger config again without `fired_event_id` re-arms it. The UI reads the catalog from `GET /api/v1/assignments/platform-events` (the same `catalog()` the builder's `list_platform_events` tool reads): the trigger picker offers "Platform event" with an event select, a field/value filter editor, the scope (administrators) and the one-off switch (`pages/assignment-detail/PlatformEventFields.tsx`), and the run detail shows the triggering event (`event`, `event_id`, `object_type`, `object_id`, `occurred_at`) as tiles. `ignore_self_triggered_events` drops an event its own agent raised. Payloads are quarantined like `webhook` and `integration_event` ones (`_UNTRUSTED_TRIGGER_TYPES`): notes and outcomes are text other agents wrote. Everything is best-effort: a failure is logged and never fails the write. The unit suite keeps dispatch off (`tests/conftest.py::_no_platform_event_dispatch`).

**A platform event watch that wakes a background task** (`services/platform_event_task_watches.py`, table `platform_event_task_watches`). The orchestrator's one-off watch without an assignment: `create_watch(user_id, agent_id, task, events, filter, expires_at)` arms it, the first matching event starts ONE background task of `agent_id` (`sub_agent.create_sub_agent_task`, `extra_metadata.origin = "platform_event_watch"`, with the event's `occurred_at` and `triggered_at`; the task's first start writes `event_latency` in its metadata and feeds `xtmone_event_to_run_seconds{kind="platform_event_watch"}`), then the watch ends. The deadline is mandatory and at most 7 days ahead; a user holds at most 50 armed watches. Scope is the `scope: own` one of an assignment of the same agent and owner (`platform_events.mismatch_reason` + `can_read_workspace`); there is no `scope: all` task watch. At most once: the delivery locks the row, re-checks it is armed, its filter matches, the owner is active and the agent enabled, and commits the fired mark before it starts the task; a task that fails to start re-arms it. The task text is the brief, the event's ids, then the payload inside a quarantine block. The pre-flight of background tasks on a finished or held work item (`work_item_preflight.named_work_item_id`) skips a `work_item_id` inside a quarantine block, so a watch on `work_item.completed` wakes a task that reaches its first model call. `platform_events.dispatch_event` delivers to the task watches after the assignments, then to the flows (`flow_triggers.dispatch_flow_platform_event`, a flow's `trigger.platform_event` node; `dev-docs/reference/backend-services-execution.md` > Flows). Agent-builder tools: `watch_platform_event`, `list_platform_event_watches`, `cancel_platform_event_watch`; REST: `GET/POST /api/v1/assignments/platform-event-watches`, `DELETE /api/v1/assignments/platform-event-watches/{id}`. Setting one requires the agent-builder `run` right on the agent.

**A work item wakes up when the CI of its pull request ends** (`services/work_item_pull_requests.py`). A work item may name its pull requests in `payload.pull_requests` (`[{repo, number, head_branch?, head_sha?, url?, state, ci?}]`, at most `MAX_PULL_REQUESTS`; at the cap, binding a new one drops a merged or closed binding first, the earliest `closed_at` leaving first and an unstamped one before any stamped one, and only `MAX_PULL_REQUESTS` open ones refuse, so a long program item keeps naming the pull request it waits on); the GitHub `create_github_pr(work_item_id=)` writes it through `record_pull_request` under the item's own write rules. A provider registers a parser (`integrations/pull_request_events.py`, GitHub's in `providers/github/pr_events.py`: `workflow_run`, `check_suite` of non-Actions apps, `pull_request` closed / synchronize) that turns a signed webhook delivery into a generic `PullRequestEvent`; both webhook receivers (`api/v1/webhooks.py`, `_route_pull_request_event`) hand it to `handle_pull_request_event`, unsigned deliveries ignored, never failing the delivery. Per unfinished item naming the pull request (row lock): every CI run of the head commit is tracked under `ci.runs` (one key per workflow or check suite app, an older run id ignored, a late completion for a moved head ignored); once all known runs completed or one failed, the item is dispatched at once to its owner's `work_item` inbox (the scheduler pickup's claim then `trigger_assignment(skip_if_active=True)`, the claim released on failure), `trigger_context.reason = "pr_ci_completed"` with `conclusion`, `run_url`, `pull_request`. A live holding run gets a dated claim note instead. Dedupe (`ci_dispatch_key`, #11486): a failure dispatches once per (head sha, re-run attempts), whatever workflows the head runs, so another workflow failing or cancelled on a red head is dropped; a success once per (head sha, set of CI runs, re-run attempts); a re-run (`run_attempt` on the event, `attempt` on the run, a new attempt of the same run id) that concludes is a new key and an older attempt's late delivery is ignored; a dropped duplicate increments `ci.dropped`; keys in `ci.dispatched`. A run is concluded only with status completed and a conclusion; a non-Actions `check_suite` is advisory (it fails a head, never makes it green alone). A new head resets `ci`. Closed: a dated note; `complete_on_merge: true` completes the item with the merge SHA once every named pull request is merged; an item `parked_without_release` (blocked with a reason only, no `blocked_on`, no open `blocked_on_refs`, no `needs_human`) is set `open` with its claim and `blocked_reason` cleared, a `released: ...` note on top of its description and the blocked to open transition published, once the closing leaves none of its pull requests open (`released_on_closing`, `closing_release_note`; #10792: its CI was its only waker, so a merge after the CI completion was consumed left it blocked for good). A closing whose delivery never came or came late is read by the polling pass `poll_pull_request_ci`: a bound pull request its `PullRequestCiReader` answers nothing for (closed, or unreadable) has its closing read with the `ReferenceStateReader` and applied through `_apply_to_item`, the delivery's own path, so the item is released within one pass; a second closing of a binding already closed changes nothing, which keeps the delivery and the poll idempotent (#11045). A `blocked` write whose newly written `blocked_reason` names a pull request (`owner/name#12`, `filigran-ui #516`, `PR #12`; `reason_names_reference`) is refused by `refuse_unbound_reference_reason` when the item has no `blocked_on`, no open `blocked_on_refs`, no `needs_human` and no open bound pull request: nothing would read the text, so the error names `blocked_on_refs` (#11045). The views read `waiting_for_ci` (pickup state `waiting_for_ci`, `context.pickup.pull_request`) instead of "not picked up". Tests: `tests/test_work_item_pull_requests.py`.

**A red check the base branch does not require never wakes a work item as a CI failure** (#11766; `integrations/providers/github/reference_state.py`: `head_ci_decision`, `read_pull_request_ci`, `status_runs`; `services/work_item_pull_requests.py`: `reconcile_failure`, `confirm_failure_on_required`, `void_stale_reds`). When the base branch requires status checks (rulesets or classic protection), the live verdict of a head is decided by them alone: `failure` once one of them completed without passing, `success` once every one reported and passed, undecided while one runs or has not reported; a required context reported as a commit status (Codecov) is placed like a check run. A base that requires nothing, or rules that cannot be read, keep every check deciding. A delivered `failure` is read live before its dispatch: a live `success` on the same head dispatches `success`, an undecided read dispatches nothing (a dated note says why; the required checks' completion wakes the item), a live head the pull request moved to past the delivered one dispatches nothing either and moves the binding to the live head with a fresh CI record (#2014: a red delivered after the owner's push is spent), a live `failure` on the same head or no read keep the delivery. The inbox settle voids a recorded red the live read calls green on the same head, so a Codecov project status red before the uploads, or a labeler app, never releases an item on an unchanged red.

**The live CI read never calls a head green before the pull request's own workflows ran** (`integrations/providers/github/reference_state.py`: `read_pull_request_ci`, `own_ci_suites`, `own_ci_passed`). A `pull_request_target` workflow (the base's workflow, a feature branch deploy) completes on a new head before GitHub creates the pull request's own runs, so its checks alone read `success`. When the checks read `success`, the read also lists the head's workflow runs (`GET /repos/{repo}/actions/runs?head_sha=`) and keeps the head undecided until one GitHub Actions check of a non-`pull_request_target` suite completed `success`, the rule the webhook path applies to advisory runs (`_ci_conclusion`). A head with no workflow run at all (CI outside GitHub Actions) and an unreadable runs list keep the checks' verdict.

**The inbox trigger payload bounds a long description** (`work_item.bounded_trigger_item`, #10572). The `work_item` trigger payload of an inbox run (`autonomous._dispatch_inbox_item`) and of the CI-completion wake (`work_item_pull_requests`) carries the serialized item, but a description over `TRIGGER_DESCRIPTION_HEAD_CHARS + TRIGGER_DESCRIPTION_TAIL_CHARS` (5,000 + 3,000) comes as its head (the newest notes, which `update_work_item(note=)` prepends) and its tail (the brief), joined by a marker naming the total and the `get_work_item` offset that reads the rest; `description_total_chars` carries the total. Its `claim_notes` (one platform note per live-holder event, hundreds on a long-lived item) come as the newest `TRIGGER_CLAIM_NOTES_KEPT` (10), `claim_notes_total` carrying the full count when some were left out (#11181); `get_work_item` still reads them all. The payload sits in the run's first message and is re-read at every iteration, so a program item's notes (hundreds of KB) no longer ride along whole. Every other field is unchanged.

**An inbox run's end completes its item only when nothing is pending** (`work_item.settle_inbox_work_item`, called by the run finalizer in `assignment_engine.py` for the item the dispatcher named). A successful inbox run: an item the run completed or cancelled itself is kept as it is (`kept`); an item the run left `blocked` stays blocked with its claim released (`blocked`), so its blockers reopen it; an item that still names an open pull request in `payload.pull_requests` is set `blocked` with its claim released and a dated claim note (`parked`), so the CI completion dispatches it again and `complete_on_merge` completes it on the merge; only a ready pull request gets a `merged_or_closed` ref: a draft one (the binding's `draft`, recorded by the create-PR tool and kept current by the `ready_for_review` / `converted_to_draft` / `synchronize` deliveries) still has a review gate ahead of its merge, so the item is blocked with a `blocked_reason` naming the draft instead and any `merged_or_closed` ref on it is dropped, the claim note saying which path was taken (#10321); the views and the work item tools say what releases such an item, `Waits for: the CI completion or closing of owner/name#N (draft), released by itself` (`work_item_blocked_refs.bound_pull_request_wait`, read by `blocked_why` and `_blocked_why_lines`), so it is never taken for a reason-only block (#1617); before deciding, every open pull request of an item not left `blocked` is read live (`work_item._read_open_pull_request_ci`, the provider's `PullRequestCiReader`) and its binding brought to GitHub's head, draft flag and CI verdict (`work_item_pull_requests.refresh_open_from_live`, claim note `Read live at the inbox run's end: ...`), so a pull request marked ready mid-run, a push whose delivery has not come or a CI that finished unseen is decided on as it is now; an open UX round item (`ux:<repo>-<number>`, `_open_ux_gates`) on any open pull request, draft or ready, blocks the item on that round before any CI deferral, the gate id added to `blocked_on` once (a round the green-check run already blocked it on is not added twice); a ready pull request whose green verdict no dispatch will announce (decided by this live read, recorded in `ci.dispatched` so the poll never wakes it twice, or told to the run holding the item instead of dispatched, `ci.told_holder` set by `_apply_to_item` and consumed once at the run's end) puts the item back to `open` at once (`deferred`, no `not_before`) instead of parking it on a completion already spent (#11730); an item with open pull requests whose payload sets `pr_merge_not_required: true` (its deliverable is the pull requests open, not merged) goes back to `open` with its claim released and `not_before` `PR_OPEN_DEFER` (4 h) ahead, never blocked on the merge, the CI completion dispatching it sooner (`deferred`); an item the run ended on without completing it is put back in the queue (`released`: `open`, claim cleared, claim note `released: run <id> ended without completing the item (<why>)`, progress trail kept) when the run was offered `complete_work_item` and did not call it, or was wound down by the tool failure brake, the rejected work brake, the iteration backstop, the run budget, a timeout or a wait cut (`agent_loop.turn_wound_down`, read from the stop reason and the structured `ChatMessage.wind_down` code the loop sets on the system message of each stop, never from any text; `assignment_engine._inbox_release_reason`); each release counts in `payload._dispatch_attempts`; from the second release in a row of an item that names no open pull request the inbox waits before taking it again (`not_before`, `RELEASE_BACKOFF_BASE` 2 minutes doubled per release up to `RELEASE_BACKOFF_MAX` 30 minutes) and the release note tells the next run to name its pull request with `create_github_pr(work_item_id=...)`; at `work_item_max_dispatch_attempts` the item is `blocked` with a `blocked_reason` naming the runs (`payload._released_by_runs`), so a run that always fails never loops; that block keeps the item's own `blocked_on` / `blocked_on_refs` and names the open ones in the reason (`work_item.release_conditions`), and raises `work_item.release_exhausted` (payload: the work item keys plus `blocked_reason`, `dispatch_attempts`, `released_by_runs`, `release_conditions`, empty when nothing would release it) so the owner's fleet decides, never a silent block with no condition (#9540); an item released because one of its pull requests is red on its head records the red it was released on (`payload._red_released_on`: each red pull request, its head and its check runs, `work_item._red_signature`), and a second release on the same signature (no new head, run or conclusion since: a held draft at its rerun cap) also sets `not_before` `RED_UNCHANGED_DEFER` (1 h) ahead, recorded in `payload._red_deferred_until`, so the inbox does not dispatch it again at once; the next CI conclusion of its pull requests clears that deferral alone (`work_item.clear_red_deferral` in `work_item_pull_requests._dispatch`) and wakes it, a `not_before` a run or a person set is kept; no delivery reaches such an open item, so the CI poll (`poll_pull_request_ci`) reads it too (`work_item_pull_requests.red_deferred`) and a conclusion decided by a check run that completed after the release, or that the previous read did not see (the reader answers the deciding `check_id` and `completed_at`, `head_ci_decision`), wakes it within a pass: a re-run ending with the same conclusion on the same head counts (#11185); a new head or a new conclusion is a new signature and is released at once as before; only a run of an agent without `complete_work_item` that ended cleanly has its item `done` with the run summary (`completed`). A failed run releases the claim as before. Tests: `tests/test_work_item_inbox_settle_pending.py`, `tests/test_work_item_inbox_settle.py`.

**A run a chat triggered reports back**: the agent builder's `trigger_assignment` passes the conversation of its turn as `trigger_assignment(owed_conversation_id=)`, which writes an `AssignmentRunConversationNotice` in the run's own transaction. The run id it returns is a valid `wait(until=...)` id, as is a Video Studio job id (`dev-docs/video-studio.md` > "The wake"). When the run ends, the conversation is told once (`services/assignment_run_wake.py`): by the wait or the `get_run` that read it ended there, else by the worker, which resumes the conversation after `WAKE_GRACE_SECONDS` with the run id, assignment, status, duration and result through `parent_wake.wake_conversation` (one hidden platform message and one turn, folded into a running turn, never after a Stop). A cancelled run is not told. A manual trigger refused because a run is in flight names that run (`ManualTriggerRefusal.active_run`: id, status, start), in both agent tools that share the gate.

**Event matching**: `integration_event` and `webhook` triggers match event keys EXACTLY when `trigger_config.event_matching == "exact"` or `WEBHOOK_EXACT_EVENT_MATCHING` (security option, `security_option()`) is on - a selection matches itself and every key below it across a `.`, never a bare prefix (`pull_request` never runs on `pull_request_review`) - and use a prefix match otherwise. The marker is written by `new_trigger_config()` on a trigger created from scratch (REST create, agent-builder `create_assignment`, agent templates) and by `settle_event_matching()` (the model's `before_update` listener) on a save that asks for it or changes `EVENT_SELECTION_KEYS` (`provider`, `event`, `events`, `path`) or the trigger type; every other save carries the stored mode forward both ways, and nothing marks an insert, so a copy (duplicate, import, catalog clone) keeps its source's mode. Matching lives in `api/v1/webhooks.py` (`_event_selected`, `_event_key_allowed`, one rule for the live receivers and the cached provider route); never re-spell a `startswith` event check.

### Delay Support

Assignments can specify a delay (e.g. `10m`, `1h`) before execution. This enables "wait then check" patterns like:
- Wait 10 min after issue closed → check if label was added
- Wait 10 min after PR opened → check if review was requested

Delays are implemented via the durable orchestration engine: the trigger creates an `orchestration_executions` row with `run_at` in the future, and the worker reconciler claims it when the delay expires (see `dev-docs/FSM/`).

### Typed Agent Handovers

Each entry in `handover_agent_ids` has a corresponding type in `handover_types` (maps agent UUID → type). Three handover types are supported:

| Type | Tool | Behavior |
|------|------|----------|
| `delegate` (default) | `spawn_background_task` | Asynchronous — spawns a background task on the target agent. Parent continues. |
| `consult` | `consult_agent` | Synchronous — asks the target agent a question and receives the answer. Parent stays in control. |
| `transfer` | `transfer_to_agent` | Permanent — hands the conversation to the target agent (chat only). |

**The configured handover is the grant.** A person's chat or run with agent A reaches every peer A's handover names with the tool of its type, whether or not that person may open the peer (`configured_handover_reach` and `handover_peer_clause`, `services/fleets.py`, read by the peer loads of agent chat, assignment runs and the background-task start in `sub_agent.py`). Kept: `enabled`, `active_handover_target_clause`, the exposure rule (a non-exposed home member of another fleet stays refused, `refused_cross_fleet_handovers`), internal and sandbox agents never peers, and anonymous or public-web users reach company-managed peers only. The person gains nothing on the peer itself: no chat with it, no listing, no read of its configuration; the peer answers the calling agent. The peer's turn runs with the calling person's identity, so its integrations are limited to what that person may use: a binding the person may not use is withheld and named to the model and on the reply (`resolve_agent_integration_bindings`), never a silent empty answer. **The control point is who may configure the handover**, unchanged: the agent's owner or an administrator who can see the target.

**Work items handed to another person's agent** (`work_item._handed_to_clause`, `_refuse_unreachable_owner`): the owner agent's own tools, dispatch and settlement read a person's item filed for it on one of three grants: (1) the creator may open the owner agent; (2) the creating agent's and the owner agent's home fleets are connected; (3) the creating agent holds a configured handover (any type) to the owner agent, the exposure rule kept (`_creator_hands_over_to`). Any other hand-off is refused at creation with the owner agent's name. A person's own read gains nothing from any grant.

Tools are conditionally injected based on the configured types — if no agents use `consult`, the `consult_agent` tool is omitted (and similarly for `transfer` and `delegate`). When `handover_types` is empty or null, all tools are injected for backward compatibility: every screen and the agent flow graph show each target as `All types`, the system prompt tags it `[ANY]` with the tools it really gets (`handover_peer_tag()` in `builtin_tools/handover.py`), and the first type picked for one target types every target after a confirmation naming the ones that become `delegate`. A map that holds a type never falls back into that mode: removing its only typed target - on the flow map, through the API, by deleting that agent or by making the agent company-managed - writes the targets left out as `delegate`. One rule on each side, `services/handover_types.py` (read by every site that registers handover tools) and `lib/handover-types.ts`, both checked against `frontend/tests_e2e/fixtures/handover-type-cases.json`. The peers listed under `## Agent Delegation` and the targets the handover tools accept are ONE list, `reachable_handover_peers()` (`builtin_tools/handover.py`): the peers a tool of the turn's `offered_handover_types()` reaches, and the tools registered are `handover_tool_types()` of that list. Each tool accepts only its own type's share of it (`handover_peers_by_type()`, in chat, the General Assistant and assignment runs): `consult_agent` refuses a `delegate` peer exactly as it refuses an unknown one, while a peer of a legacy map is accepted by every tool the turn offers. A turn offers the types its caller allows (a mentioned agent consults and delegates, never transfers; a flow edge's label names its types), `spawn_background_task` only with an acting user (never for an anonymous chat user or an ownerless assignment run, and then no self-fan-out either), and no tool the agent's `tool_deny_list` names. A `mandatory_transfer` peer is never on the list (routed after the answer, never by the model), a peer of a legacy map runs every offered type, and a type no tool implements runs as `delegate`, in a constrained turn too (`filter_handover_agents_by_type()` in `agent_chat.py` reads the same rule).

Sub-agent tasks (delegate type) run in isolated sessions (no history, `allow_handover=False`) and persist results in the `sub_agent_tasks` table.

A **consulted configured peer consults its own consult peers**, so a desk that needs another desk's figure answers whole. `consulted_peer_handover(delegation_depth)` (`builtin_tools/handover.py`) is the one rule, read by the `consult_agent` of agent chat and of assignment runs (a run is the chain root, its peer runs at depth 1): the consulted turn runs with `allow_handover` while its own depth is below `_MAX_DELEGATION_DEPTH` and `allowed_handover_types={"consult"}`, so its `## Agent Delegation` block lists its consult peers only (every peer of a legacy map, as consult), and it never gets `transfer_to_agent`, `spawn_background_task`, self-fan-out nor a mandatory transfer - it answers the agent that asked. Past the depth it holds no handover tool. The visited chain every consult carries refuses an agent already in it (`handover_cycle_error()`), so A -> B -> A, or A -> B -> C -> A, returns the circular-handover message and never runs. A nested consult is recorded as today: a child run under the consulted agent's own child run, `meter_quota=False`, carrying the conversation the root turn works for (`investigations_conversation_id`: the stale-run sweep reads the live turn from it, an investigation files into it, the delegation log lists it there), and a turn withheld from OpenAEV writes by its caller (an advisory consult) withholds the peers it consults too. Its live frames arrive under one `consult_progress` wrapper per consult level (`agent_id`, `agent_name`, the frame under `inner`, and `consult_id`, one per consult call, so two consults of one agent at once read as two); the fan-out (`chat_turn_stream.slim_frame`, the journal filter) and the client (`unwrapConsultFrame`) read through all of them (`runner_activity.unwrap_consult_frame`, `MAX_CONSULT_DEPTH`). The General Assistant's consult keeps its peers without handover tools. A consulted peer runs on its row **as it is at call time**: the consulting turn loaded its peers when it started, so `consult_agent` (agent chat and assignment runs) re-reads the target by primary key on the consult's own session (`live_consult_target()`, one read, the loaded row kept when the read fails) before building the nested turn, and a persona, guardrails, skills or bindings saved during a long turn reach the next consult at once, as a run of that agent would get them. Every agent-chat trace records the configuration revision it ran with (`metadata.agent_config_revision`, the agent's `updated_at`, `agent_config_revision()`), so a consulted turn's trace names the row it carried.

A **delegated background task may ask its direct parent a question**. The chain guard (`handover_cycle_error`) refuses every handover to an agent already in the visited chain, so a task B that A spawned could not `consult_agent` A for a one-line decision. The sub-agent worker now names the spawning agent in the task turn's `handover_context` (`DELEGATING_AGENT_KEY`), and `delegated_parent_id(handover_context, visited_agents, self_id=...)` (`builtin_tools/handover.py`) returns it only when it is the chain's last ancestor (never a grandparent, never the agent itself on a self-fan-out). The `consult_agent` of agent chat then accepts a consult of that agent, when it is one of B's consult peers, `DELEGATED_PARENT_CONSULT_LIMIT` times per run (setting `delegated_parent_consult_limit`, default 3, 0 restores the refusal), counted by `ParentConsultBudget`: the parent answers with `allow_handover=False` (no consult, transfer or background task inside it) and `max_iterations_override=PARENT_CONSULT_MAX_ITERATIONS`, and the question past the limit gets a refusal naming the setting. `spawn_background_task` back to the parent keeps the chain refusal. The consult is recorded like any other (child run, `AgentDelegation` row), both marked `parent_consult: true`, plus a `parent consult:` log line with the run id, the parent agent id, the question length and the outcome (`log_parent_consult`). B never gains a tool of A: A answers with its own configuration, as the caller's identity.

An agent may also delegate to **itself** (`spawn_background_task(agent_id="self")`) to split a large workload across parallel background copies, even with no handover target. It is on by default and switched by two flags read together by `self_fanout_enabled(agent)` (`builtin_tools/handover.py`): the platform's `AGENT_SELF_FANOUT_ENABLED`, which wins, and the agent's own `allow_self_fanout` (Configuration > Agent Handover, NULL reads as on). An agent with it off is never offered itself as a target and its system prompt carries no "Parallel self-execution" block; its peer handovers are unchanged. The full contract is in `dev-docs/reference/backend-services-execution.md` > "Sub-Agent Background Tasks" > "Self-fan-out".

An agent holding the **agent-builder tools** may also delegate to any agent its acting user OWNS - every agent `create_agent` / `clone_agent` makes - with no handover binding: it can already create, configure and trigger those agents, so a background task to one widens nothing. `owned_target_resolver(builtin_tool_ids, user_id)` (`builtin_tools/handover.py`) is the one gate, read by agent chat and assignment runs; it also offers `spawn_background_task` to such an agent with no peer and no self-fan-out. Not the General Assistant: it has no agent row, and a background task's `parent_agent_id` is a non-null agent FK, so it tests a new agent with `run_agent_once` instead (its task creates an `AssignmentRun` of its own through `create_sub_agent_task(own_run_trigger="run_once")`: assignment_id None, payload `trigger_type` `run_once`, the caller's run as `parent_run_id` when the builder tools were built with `run_id`, company-managed flag by `resolve_child_run_is_company_managed`; the run keys the task's sandbox workspace in `WorkspaceScope.build`, so `$workspace:` references resolve, and the workspace is collected with the run, #12028). A configured peer of another type stays refused, and so does a disabled agent. Every refusal of `spawn_background_task` names what is missing (`background_task_refusal()`): not a delegate peer (and how to add one), a consult / transfer peer (and the tool that reaches it), a mandatory-transfer peer, self-fan-out turned off, a disabled target. Any other agent reaches its configured delegate peers and nothing else. The builder's `run_agent_once(agent_id, prompt)` runs an agent once the same way - a background task of the agent itself, no parent run - and awaits its answer, so a new agent can be smoke-tested without an assignment left behind. Its `file_ids` (at most `MAX_TURN_FILES`, 30, the web chat's `MAX_CHAT_ATTACHMENTS_PER_MESSAGE`) are resolved with `resolve_attachable_files` (the caller's turn or rows its user owns; any refusal runs nothing), handed as the task's `file_context` and named under `TURN_FILE_IDS_KEY` in its metadata; `_execute_sub_agent_task` passes those refs (`task_turn_file_refs`) as `files=` to `run_agent_chat`, so they ride on the run's user message exactly as a chat message's attachments do (images as vision blocks). Its `dry_run` (#1911) stores `RUN_DRY_RUN_KEY` (`dry_run: true`) in the task metadata; `_execute_sub_agent_task` then binds the turn to `SandboxSession(mode="dry_run")` (`health/sandbox/session.py`, the Platform Health dry-run interceptor): reads run live, every write (the shared `side_effects.tool_call_effect` classifier) is logged and answered `DRY_RUN_NOTICE` without running, nested consults included; the flag is on the task row, so a resumed attempt keeps it. The same gate offers `consult_agent` in chat for an agent its user owns (`owned_consult_target()`), even with no consult peer: the consulted agent answers with ALL its own handover tools, one delegation level deeper, so an orchestrator tests a desk's handover without a scheduled run; a configured peer consults its own consult peers only (above). **Built-in groups from the agent builder.** `update_agent` / `create_agent` / `duplicate_agent` validate `builtin_tool_ids` against `_VALID_BUILTIN_TOOL_IDS`, DERIVED from the registry (`BUILTIN_TOOL_GROUPS` ids, then every `BUILTIN_GROUP_ALIASES` former id); the "Supported" list in the error and the schema is `_advertised_builtin_tool_ids()` (groups only, feature-gated ones only while their flag is on). A read tool: in the HITL shipped whitelist and `XTM_MCP_READ_TOOLS`.

### Output Format

Agents have a configurable `output_format` that controls response formatting:

| Format | Description |
|--------|-------------|
| `markdown` (default) | Standard Markdown (headings, bold, italic, lists, code blocks) |
| `html` | Semantic HTML fragments (no wrappers) |
| `json` | Valid JSON with a top-level `response` key |
| `plain_text` | Unformatted text without any markup |

A `json` agent's answer is cleaned to JSON after the loop (`services/structured_output.py`): `emit_repaired_json` with an `output_schema` (chat and assignments), `emit_bare_json` without one (chat). The chat turn and the assignment run call them in a worker thread (`deliver_json_answer_in_thread`, `emit_repaired_json_in_thread`): repairing a large answer is CPU-bound and on the event loop it blocked the worker's health probe until the worker was restarted; schema validation collects at most `MAX_SAP_VALIDATION_ERRORS` errors. Both strip fences and surrounding prose and repair damaged JSON (trailing commas, quotes, unquoted keys, Python literals, comments). An answer whose JSON span would only parse after repair and reads as prose (`reads_as_prose`: `The actor is APT29 [high confidence], see the report.`, `{sorry}`, `[a] or [b]`) is delivered as written, never as the repaired fragment.

When the agent responds through an external channel (Slack, Teams, WhatsApp, Telegram, Discord, Google Chat), the format is **automatically overridden** to match the channel's native formatting rules. For assignments (server-side execution), the agent's configured format is always used.

### Publishing rendered images (visual verification)

An agent that RENDERS an image (a diagram screenshotted in the headless browser, a chart, an export) and PUBLISHES it (`upload_notion_file`, a channel post, a page cover) is at the one point where the platform cannot check the deliverable for it: whether a logo is the right colour or a card is laid out as the user asked is a question about pixels. On 2026-09-24 an agent twice put a diagram on a Notion page with the OpenCRQ mark cyan (`#0FBCFF`) instead of Filigran blue and a wrong card layout, after a DOM probe reported "clean" - its screenshot had been pruned from context and it published on the probe and its memory of an earlier version. The contract, for the agent and for whoever wires a tool it uses:

1. **A geometry probe is not a visual check.** A `browser(action=evaluate)` script measuring overflow, overlap and fonts says nothing about what the image looks like. Only looking at the PNG does.
2. **Look at the PNG once before uploading**, in the same run: `read_file_content(file_id=...)` attaches a raster image as a vision block. Compare it with the USER'S LAST SCREENSHOT (the file on their message), never with memory of an earlier version - the version in memory is the one that was wrong.
3. **Never upload from a run in which the image could not be viewed** - a pruned vision block, a `read_file_content` error, a budget-exhausted batch. Say so and stop; the user would rather wait than get the wrong diagram on the page.
4. **The tools ground what can be grounded deterministically** (invariant 16 - no prompt text): `browser(action=screenshot)` and `upload_notion_file(file_id=...)` results carry `format_visual_summary()` (`services/image_summary.py`: dimensions, dominant colour, the distinct SATURATED colours covering at least `SATURATED_COLOR_MIN_SHARE` of the opaque pixels, each with its uppercase hex and share, largest first) - one text line that outlives the pixels in context, so an unexpected hex is readable without vision, by the agent and by whoever reads the trace. `upload_notion_file(expect_colors=[...], forbid_colors=[...])` turns that summary into a gate run BEFORE the upload: a forbidden colour present, or an expected one absent (matched by ΔE within `COLOR_MATCH_DELTA_E`, so JPEG drift is caught and two brand colours never read as one), is a refusal naming the colour and its share - nothing reaches the page. Pass the brand hex values whenever the image carries a logo. The gate is refused, never skipped, when it cannot run (`external_url`, a non-raster or undecodable file, a grey / white / black entry the saturated list can never hold, an expected and a forbidden colour within `GATE_SEPARATION_DELTA_E` (twice the match radius: their match regions overlap and one pixel would count for both) of each other - `conflicting_gate_colors()` - and, for `forbid_colors`, a summary that is not `complete`: an animated image read at its first frame, an image too large or too colourful to count every pixel, which was `sampled`, or a whole-image count that held more distinct saturated colours than the gate palette keeps, `palette_cut`): silently uploading past a check the agent asked for is the failure it exists to prevent.

The runtime-facing half of these rules lives in the two tool descriptions and in the tool results (the refusal names `read_file_content` and the user's screenshot), never in a system prompt. A new tool that hands back or publishes a raster image the agent must judge appends the same `format_visual_summary(await summarize_image(bytes))` line - never a second colour counter.

### Persistent Agent Memory

Agents have a three-tier memory system:

1. **Redis short-term** (24h TTL): Rolling list of 10 recent interactions
2. **Redis medium-term** (30d TTL): LLM-consolidated summary, auto-updated after 5 new entries
3. **PostgreSQL persistent** (durable): Consolidated memories and extracted facts stored with vector embeddings in `agent_memory_entries`

When Redis consolidation occurs, the result is automatically persisted to PostgreSQL. Agents can semantically search their own persistent memory via the `search_memory` tool.

**State entries and supersession**. An entry describing an object that changes (a document, a deck, a ticket) used to stay in every prompt after the object changed. The rules live in `services/persistent_memory.py`, the one write funnel being `persist_memory()`:

| Column | Meaning |
|---|---|
| `subject_key` | The object an entry describes (`presentation:<id>`, `doc:X`), `normalize_subject_key()`: one printable line, case kept, at most 255 characters. NULL for an entry about no object in particular |
| `superseded_at` | Set once the entry no longer holds. Kept, searchable, never injected into a prompt |
| `superseded_by_id` | The entry that replaced it, by id without a key; NULL for a retirement |

- **Write.** `store_memory(content, memory_type, subject_key?, supersedes?)`. A `state` entry with a subject supersedes the writer's active state entries on that subject; `supersedes=<entry_id>` names one more entry it replaces, whatever its type (and skips the fact dedup). Only the writer's own pool is flagged (`_written_by`: the user's entries in a user's session, the agent-level pool when there is no user), never the agent-level pool from a user's session nor another user's entries; an id outside it is left as it is and the tool says so. The state write takes a transaction-scoped advisory lock on (agent, scope, subject); a subject keeps at most `_MAX_SUPERSEDED_PER_SUBJECT` (10) superseded state entries. Tradecraft takes no subject and supersedes nothing; a consolidated entry ignores both.
- **Retire.** `invalidate_memory(entry_id? | subject_key?)` (same executor and `builtin:memory_store` suite as `store_memory`) calls `retire_memories()`: the writer's active entries by id or on a subject, flagged with no successor. When the session user manages the agent's memory (`may_manage_shared_memory`: the owner of a private agent, an administrator, the rule of the memory screen's `_can_manage_memory`), `include_shared=True` retires the matching agent-level entries too; another user's entries are never touched. Otherwise it reports the matching entries of the shared pool it left active.
- **Read.** What still holds for a reader is `superseded_for_reader()`'s negation: not superseded, and not a state entry a newer active state entry on its subject outdates among the entries the reader sees (agent-level + their own; newest by `created_at`, then `id`). So a user's newer state entry wins over an older agent-level one for that user only, without flagging it. `load_persistent_entries()` selects only those; `format_persistent_context()` applies the same rule to whatever it is handed, prefixes a state entry with `as of <date>, verify live` and, when the block holds one, adds `STATE_GUIDANCE` under its header (zero characters otherwise, invariant 16). `search_agent_memories()` returns superseded entries too, ranked after the active ones, each with `stored_at`, `subject_key`, `superseded` and `superseded_by`; `search_memory` renders them and its notes outside the memory fence. The REST list serves the stored flag (`superseded`, `superseded_at`, `superseded_by_id`); the REST search the per-reader one.
- **Hygiene.** Dedup and reconciliation compare against entries that still hold (a retired fact can be stored again), fact consolidation never merges a superseded fact, the cap evicts superseded facts first, and `state` is age-pruned like `fact` / `learned`. Entries without a subject behave as before.

**Leaked reasoning** (#12356): a model's reasoning written as text, a leading closed `<reasoning>` / `<thinking>` / `<think>` block, is stripped on write (`persist_memory`, the Redis summary, short-term entries) and on every read into a prompt (recall, `search_memory`, the persistent context, and the consolidation, compression, fact merge and reconcile inputs), so an entry stored before is harmless. An entry that is only reasoning is not stored, and `store_memory` says so. An unclosed block cut by the token limit is not caught yet (#12362).

**Memory hygiene** keeps the persistent tier healthy for long-running agents:
- **Semantic deduplication**: Before persisting a new fact, cosine similarity is checked against existing facts (threshold: 0.92). Duplicates are silently skipped.
- **Age-based pruning**: Facts and state entries older than 90 days are automatically removed (hourly via the autonomous scheduler).
- **Per-agent cap**: Maximum 200 facts per agent. When exceeded, the superseded facts are evicted first, then the oldest.
- **Fact consolidation**: When an agent accumulates 50+ facts, the oldest batch of 15 is merged into a single condensed entry by the LLM.
- **On-demand maintenance**: `POST /agents/{id}/memory/maintain` triggers all hygiene tasks immediately. The Memory tab shows health indicators and an "Optimize" button.
- **Health monitoring**: `GET /agents/{id}/memory/health` returns entry counts, staleness indicators, cap status, and configuration values.
- **Reactive self-heal**: when an agent's combined memory block breaches the assignment prompt cap, `auto_heal_agent_memory()` is fired automatically (throttled per agent, 6h) — persistent-tier hygiene plus compression of an oversized Redis medium-term summary. `consolidate_memory` additionally clamps the medium-term summary at write time (LLM compression pass, hard-truncate fallback), so the Redis tier can never accrete past its prompt cap, and its consolidation and compression calls pass `disable_thinking` like every other memory utility call. The persistent block of an assignment run never breaches the cap: it holds the whole entries that fit in what the Redis tiers leave, most relevant first, and says how many it left out. Memory bloat never requires manual maintenance or memory clearing.

### Cross-Agent User Memory (scoped)

Every agent with `memory_user_enabled` reads what the platform remembers about the user it works for. That memory is a list of entries (`services/user_memory_entries.py`, stored as JSON in `user_mem:entries:<identity>`), never one free-text block every agent reads whole. The memory is generic: it knows nothing about what a statement is about, and nothing in it names an integration, a vendor or a kind of work.

| Field | Meaning |
|---|---|
| `scope` | `global` (the user's PROFILE - read by every agent) or `agent:<id>` (a NOTE the agent's work left about the user - read by that agent only) |
| `owner_agent_id` | The agent a note belongs to: the agent of the interaction it came from, never read from its text; `None` for the profile |
| `created_at` / `last_verified_at` | When the statement was first and last stated. A rewrite that copies a statement forward unchanged keeps its date (`keep_history`) |
| `ttl_seconds` / `perishable` | A note the model marks as something that can change without anyone saying so lives `PERISHABLE_TTL_SECONDS` (72 h) after it was last stated and is rendered `[UNVERIFIED as of <date>, verify against the live system]`; the agent checks it with its own tools |

- **Who decides what** - the consolidation model's structured answer `{"profile": [...], "notes": [{"agent": n, "text": ..., "perishable": ..., "restated": ...}]}` decides which statement is about the user and which is an agent's work, which can change, and which the new interactions state again (its date moves, so its expiry restarts); the code decides the owner (the window's agent `n`), the scope, the freshness and who reads it. No keyword list, no text classifier, no attribution by searching the text.
- **One read rule** - `visible_to()`: an agent's context carries the profile and its own live notes, plus its own recent interactions (matched on the interaction's `agent_id`); never another agent's notes or interactions, never an expired note. `format_user_memory_for_prompt(memory, agent_id=...)` renders it; every caller (agent chat, assignment runs, the public widget) passes the receiving agent.
- **Consolidation** (`consolidate_user_memory`): every interaction records its agent (`store_user_memory(agent_id=...)`, in `user_mem:recent:<identity>`); after 6 the model answers the JSON above. The profile and the notes the model was shown (the window's agents') are replaced; every other note is kept as stored at write time. A note naming no agent of the window is dropped (no agent would read it). The answer is applied only when it is that JSON with both lists: a missing field, a field that is not a list, a cut or broken answer, or text that is not that JSON keeps the memory as it is. Empty lists are an answer: the shown notes are dropped, while the profile is only replaced by a non-empty rewrite (it never empties on its own - the user's Clear does that). The cut-answer and size rules below still hold for the profile.
- **One write** - `update_entries(redis, identity, change, generation=...)`: `change` gets the entries as stored now and returns what to write; a Lua compare-and-set writes the entries and their profile copy together, only over the value read, else retries on a fresh read. The sweep and a consolidation (whose read precedes a model call) never overwrite each other, and a consolidation never brings back an entry removed while it waited. Entries written where none are stored (a split) land only while the free-text profile is still the one the writer read (`free_text_read`): an older replica rewrites it in place, and the next split reads the new text. Both pass the purge generation they read with their snapshot (`memory_generation()`): the user's Clear (`purge_user_memory()`, both `/settings/me/memory*` purges) and an account deletion (`clear_user_memory()`) move it and delete the profile keys in one transaction, so a write in flight writes nothing - an account re-created under its id included. Clearing one agent (`/settings/me/memory/agent/{id}`) drops its notes and its recent interactions (`forget_agent_notes()`). A consolidation takes off the interaction counter only what it integrated, in the generation it read it in (`_SETTLE_COUNTER_SCRIPT`). One consolidation of a memory runs at a time (`lease:user_memory_consolidation:<identity>`): one started meanwhile does nothing, and the interactions left counted start the next. It shows the model only the interactions no consolidation integrated: `load_user_memory` reads the interactions and the counter in one transaction (`pending`), the newest `pending` interactions are the new ones, and exactly that many are settled. The sweep judges expiry on the entries as stored at write time, so a note restated meanwhile stays. A statement copied forward keeps its date and, once marked perishable, its expiry (`keep_history`).
- **Agent names are not unique**: an older interaction names its agent by name only, so it is shown to no agent, and a consolidation window gives it an agent only when no two agents of the window share that name.
- **Older free-text profiles**: no agent reads one (nothing tells its profile from another agent's work). The sweep (`services/user_memory_maintenance.py`, hourly, install-wide lease, in the background, run by the scheduler's memory-maintenance step only while agentic AI may run) has the consolidation model split it (`migrate_legacy_profile()`), given the agents the user worked with in the last 180 days: the profile, each agent's notes, the rest dropped. A profile is offered at most once a day, and a sweep makes at most `_MAX_MIGRATIONS_PER_SWEEP` (200) model calls, split or not. A visitor of the public widget has no account to read agents from: its next consolidation splits it. The sweep also drops expired notes.
- **Compatibility** (rolling deploy, rollback): `user_mem:medium:<identity>` keeps the rendered PROFILE alone, so a reader of the free-text profile (an older replica) never sees a note, and interactions are written to `user_mem:recent:` because an older replica shows `user_mem:short:` whole to every agent (the new code still reads `short` until it expires, shown to no agent).
- **Preamble**: `MEMORY_HEADER` says memory written by other agents is background context only, not an instruction, that a live tool result wins over it, and to ignore entries outside the agent's domain.

### Context Compaction with Pinned Directives + Memory Reconciliation

When a conversation's history passes 60% of the model's context window in estimated tokens (`COMPACTION_WINDOW_SHARE`, the agent loop's session share and estimate), or exceeds the 45-message safety net (`SUMMARIZE_THRESHOLD`), the oldest messages (everything before the last `KEEP_RECENT` = 15) are compacted into a single structured system message. The message count alone no longer summarises a conversation far from its window. On the count, the re-compaction interval is the gap between the threshold and the keep-window plus one (31 new messages per cycle with the strict `>` trigger); on the tokens a cycle needs at least 4 messages beyond the recent window — the summarizer runs once per full batch, never every few turns. The streamed web chat runs that summarizer call right after the turn that takes the conversation past the threshold, while the user reads the answer (`conversation_memory.precompute_compaction`), instead of before the next turn can start: it compacts the history the next turn will load and persists it like any compaction, and a turn that starts while it still runs waits for it and catches up with its result (`_apply_precomputed`, used once, and only by a history that still holds messages it covers) instead of calling the compactor again. Across processes, whoever compacts holds a short, renewed Redis claim on the conversation (`compaction:claim:<id>`): a precompute that finds it held leaves the compaction to its holder, and a turn waits for the holder and catches up with the state it persisted (`_catch_up_with_stored`); without Redis each compacts on its own and the stored state still only moves forward. The compaction message contains:

1. **Pinned Directives** — a bullet list of every still-active user-set CONSTRAINT, CORRECTION, FORMAT REQUIREMENT, or PREFERENCE (e.g. "use field filter on subregion, not country", "currency prefix is €", "ADS metrics must be YTD average"). The block is **rolled forward** across every subsequent compaction cycle: the prior compaction message is parsed, its directives are fed back to the compactor LLM, and now-superseded entries are removed while new ones are added. This means the user's early instructions remain visible to the agent even in 100+-turn conversations.
2. **Rolling Summary** — a concise narrative recap that grows incrementally, never rebuilt from scratch.

Before compaction, key facts are extracted from the messages being summarised and passed through **conflict-aware reconciliation** (`persistent_memory.reconcile_and_persist_facts`):

- For each candidate fact the system pulls existing entries in the **contradiction zone** (cosine similarity ∈ [0.65, 0.92)) — close enough to potentially conflict but not exact duplicates.
- An LLM curator decides `ADD` / `SKIP` / `SUPERSEDE` / `MERGE` for each candidate.
- Superseded ids are deleted; merged content replaces both originals.
- Plain `ADD` still benefits from the standard 0.92-cosine dedup short-circuit inside `persist_memory`.

The worst case (LLM curator fails) silently degrades to plain ADDs — never worse than the legacy behaviour. This ensures contradictions (e.g. a corrected filter, a swapped data source) supersede old facts instead of silently coexisting with them and confusing the agent.

### Workspace knowledge in a turn

A turn in a conversation filed in a workspace receives, for the PERSON it acts
for (`services/workspace_knowledge.py`, the one place it is decided):

- the workspace's **instructions**, a system-prompt section after the attached
  prompts and skills;
- its **Sources**: every ready source inline, in quarantine blocks, while they
  all fit `PlatformSettings.workspace_sources_context_percent` (default 15,
  bounds 5-40) of the model's context window; otherwise the Sources knowledge
  base joins the turn's read-only set and is searched - never a partial set;
- the **bound knowledge bases** the person can see, read-only;
- the **linked skills** the person can see, in the agent's catalog
  (`resolve_agent_skills(extra_groups=...)`), re-checked on every `load_skill`.

The workspace comes from the conversation, or from `session_workspace_id` where
there is none: a consulted agent (the parent's), a delegated task (the
delegating conversation's), a flow agent node wired to a `capability.workspace`
node (resolved with `resolve_workspace_scope`, failing the run closed). The
General Assistant runs the same resolver. It fails closed: an anonymous
participant, an evaluation, an account's interlocutor, or a person who cannot
see the workspace (checked on every turn, so a revoked share applies at once)
gets nothing; an archived workspace still serves conversations already filed.
Workspace entries join AFTER any session replacement of the agent's lists. The
XTM One MCP server does not serve them.

**Conversation search** (`services/workspace_conversation_index.py`). Every
filed conversation whose thread is its owner's own, in a workspace that owner
still sees (`helpers.visible_to_user_column_clause`), is indexed into the
workspace's Conversations knowledge base once idle
(`PlatformSettings.workspace_conversation_idle_minutes`, default 30): one
document - a summary, what people wrote and the agent answered, attached files'
text - replaced on re-index, never a tool result (`tool_calls_json`,
`metadata_json.tool_call_trace`, `tool` rows) and never a hidden wake prompt;
secrets read `[secret]`. A step of the autonomous tick queues idle
conversations (`index_workspace_conversation_job`, keyed per conversation) and
reclaims the documents of conversations that left; nothing is written to
`conversations` (`updated_at` orders the sidebar). `search_workspace_conversations`
filters at query time on current eligibility, so an unfiled, moved, archived or
deleted conversation, or one whose owner lost the workspace, is gone from the
next search whatever path removed it, and
the current conversation is never returned. Passages are quarantined; the
conversation link's label goes through `core.markdown_links`.

**Filing by asking the agent** (`builtin_tools/workspace_filing.py`):
`list_workspaces`, `create_workspace` and `file_this_conversation` are offered
on every turn acting for an identified person in a conversation (or on a
channel thread's first message, where the tool says to ask again), never to a
consulted or delegated run; beside `agent_builder`, only
`file_this_conversation`. Into a workspace other people can see
(`workspaces.workspace_reaches_others`), the person approves the call:
`install_filing_consent` puts a consent screen
(`CompositeToolExecutor.require_consent`) on the turn's executor when it can
collect an approval (streamed, or REST with a resume), so a filing call naming
anything but one of the person's own private workspaces pauses on the approval
card whatever the agent's approval settings. The proposal carries
`requires_consent`: "always" saves no standing approval, and a surface that
cannot ask says how to do it instead (`no_approval_channel_message`). An
approval is spent by the call it was given for (providers reuse call ids). The
screen only predicts: `move_conversations_to_workspace` files into a shared
workspace only when `tools.base.consent_approved()` - the person approved that
call - judged on the workspace it resolved to. A call the screen cleared that
resolves to a shared workspace is sent back for its id; where nothing screens
(a channel thread, an MCP client, an assignment run, a sub-agent) it is
refused, and the person moves the conversation from its menu.

### Scheduled Work Items (one-off actions)

"Post this in the EMT channel tomorrow at 9:00": every agent schedules a one-off action and the platform runs it at that time, with no assignment and no flow. Recurring work stays an assignment. No new object and no new queue: the item is a `WorkItem`, its execution an assignment-less `AssignmentRun`, dispatched through the orchestration engine. User doc: `docs/docs/usage/scheduled-work-items.md`.

| Piece | Owner |
|---|---|
| The rules (action, time, ownership, state, audit, outcome delivery) | `services/scheduled_work_items.py` |
| Dispatch tick + execution + exact-mode tool resolution | `services/scheduled_work_item_runner.py` |
| The adapter (`scheduled_work_item`) | `services/orchestration_adapters/scheduled_work_item.py` |
| The four core tools | `services/builtin_tools/scheduling.py` |
| REST (`GET /work-items/scheduled`, `POST /{id}/cancel`, `POST /{id}/reschedule`, `PUT /{id}/action`) | `api/v1/work_items.py` |

- **The action.** `payload.action` is `{"mode": "exact", "tool", "arguments", "target"?}` (that tool call, as stored, no model) or `{"mode": "instruction", "prompt", "target"?}` (the owner agent runs the prompt in a background `run_agent_chat`, metered, one receipt per attempt). `WorkItem.action_mode` mirrors the mode and is written by `scheduled_work_items.py` alone: the generic writes refuse a payload carrying `action` (`refuse_generic_action_write`) and refuse to re-route, re-date, change the status of, claim, complete or delete an unsettled scheduled item (`work_item._refuse_scheduled`, a 409). An agent account turn's pinned integrations are recorded on the action by the platform (`pinned_integrations`), never taken from the model or an edit.
- **The tools** (`schedule_work_item`, `list_scheduled_work_items`, `cancel_scheduled_work_item`, `reschedule_scheduled_work_item`) are built for every turn run by a signed-in person whatever `builtin_tool_ids` says: `run_agent_chat` (chat, channels, background tasks, flows) unless the turn is anonymous, an agent account answering another person (`identity_from_platform`) or an evaluation, and assignment runs acting for a user. They are `ToolDefinition.core`: `apply_tool_deny_list` never removes them and the agent APIs and the agent builder refuse a `tool_deny_list` naming them (`refuse_core_tool_denials`). `schedule_work_item` and `list_scheduled_work_items` reach only the items the calling agent owns for the person it runs for; `cancel_scheduled_work_item` and `reschedule_scheduled_work_item` also reach, for that person (`change_authority`), the items of an agent the caller hands work to (`delegate` or `transfer` in its `handover_types`, or a legacy map without types: an orchestrator tidying its desk's actions) and any blocked or missed item of the person's agents (a restart leftover nobody will run). Across persons (#2220, `cross_person_agents`): when the person a turn runs for owns the calling agent, `list_scheduled_work_items` and `cancel_scheduled_work_item` (never `reschedule_scheduled_work_item`) also reach the one-offs that agent, or a same-owner agent it hands work to by `delegate` or `transfer`, scheduled in a run for another person; a run acting for anyone else gains nothing. Anyone else gets the same answer as for an item that does not exist. Both take the item's full id or an 8+ hexadecimal prefix (`builtin_tools/id_prefix.py`), looked up among the person's scheduled items only (`_full_item_id`): one match stands for the full id, several are refused with their ids and nothing changes, none is handed on as given. A change by another agent names it and its reason on the item (`result`) and in the audit row (`acting_agent_id`, `acting_agent_name`, `authority`: `handover` or `leftover`). Routing, claiming and completing stay in the optional `work_items` group. A turn that scheduled or rescheduled an item gets its card marker `[[WORK_ITEM:<id>]]` appended to the answer from what the tool did (`append_markers`); channels strip it (`strip_channel_work_item_markers`).
- **Ownership.** Private to `user_id` (the person who asked) whatever the agent's tier: `is_company_managed = False`, never filed into a workspace. `owner_agent_id = created_by_agent_id =` the calling agent.
- **Time.** `parse_due_at` refuses a `due_at` without a UTC offset (never read as UTC), in the past, or past `SCHEDULED_WORK_ITEM_MAX_HORIZON_DAYS`; the refusal names the fix in the person's `User.timezone` and in UTC, a wall time a daylight saving change repeats (it asks which) or skips. `offset_note` says when the offset written is not the person's zone on that date. Every message reads `describe_time`: local time, zone, offset and UTC.
- **Dispatch** (`dispatch_due_scheduled_work_items`, step 3c of the 60 s tick, not gated on the AI state). Per tick: settle the running items whose run ended without settling them (`_settle_from_runs`); mark missed every open item past `due_at` + `SCHEDULED_WORK_ITEM_GRACE_MINUTES` (15) - blocked, `outcome_code = missed`, creator notified, **never run late past the window** (reschedule it to run it); cancel every blocked item whose served work items are all `done` or `cancelled` (`_cancel_served_leftovers`: `served_work_item_ids` reads `payload.action.serves_work_item_id` when the scheduler named it, `build_action(serves_work_item_id=...)`, else the full work item ids the title, description, target or prompt write out plus the reference arguments of an exact action (`work_item_id`, `*_work_item_id`, `work_item_ids`, `*_work_item_ids`, at any nesting level of objects and lists down to `REFERENCE_SCAN_MAX_DEPTH` (8); a free-form argument is never read); only items of the same person count; it runs after the due dispatch, bounded to ONE keyset batch of `_LEFTOVER_BATCH_SIZE` blocked items per tick read without a lock and resumed from the process-local `_leftover_cursor` at the next tick (wraps at the end, so every row is reached every ceil(N / batch) ticks), then the rows to cancel are locked `skip_locked` and their targets re-read `FOR SHARE`, so a target requeued meanwhile keeps its action blocked; an item settled or missed in the same tick is delivered once), result "target already done", a `system:scheduler` cancel audit row with `served_work_items`, creator notified; then, while the kill switch is on, claim each due item with `work_item.claim_open_work_item` (THE atomic claim, on the tick's session) and in the same commit create ONE `AssignmentRun` (`assignment_id = NULL`, `agent_id = owner`, `user_id = item.user_id`, `trigger_payload = {"trigger_type": "scheduled_work_item", "work_item_id"}`, `trigger_context.type` the same plus title and mode), set `item.run_id`, create the execution keyed `assignment_run:<run id>` (so the stale-run sweep, a run deletion and the emergency stop find it) and a `log_system_audit` row. Two ticks racing create one run. `list_dispatchable_work_items` (assignments, flows) takes `action_mode IS NULL` only, the tick `IS NOT NULL` only.
- **Execution** (`execute_scheduled_run`). Re-checked when the run starts, for `item.user_id`: the kill switch, the action, the agent (exists, enabled), the account (exists, active), the person's right to use the agent (`user_visible_filter`), the edition and AI gate (`agentic_verdict`: transient = retried, refused = blocked with `refusal_message`); for an exact action the tool itself (`resolve_exact_toolset`: the assignment-run binding resolution for that person - fixed bindings with the shadowing of a colleague's, template bindings, pinned integrations, tool scoping, read-only bindings, enforced element scope, channel and custom tools, then the deny list; MCP tools are not offered), its arguments against its input schema, and the approval gate (`approval_refusal`: a tool the gate would hold is not run). A failed check runs nothing and blocks the item with the reason (`outcome_code`). The item follows its run: `claimed` -> `in_progress` -> `done` (proof: what the tool or the agent returned) or `blocked`; the run ends `completed` or `failed`.
- **Cut by a rollout.** `trigger_context.action_started_at` is written before the action is sent; an attempt that finds it set goes on by itself, never handed to the person (`resume_decision`). An instruction turn is checkpointed (`assignment_run_resume.checkpoint_for`, key `assignment-run:<run id>`); `TurnWoundDown`, or a cut while `worker_stopping()`, hands it back (`assignment_run_resume.hand_back`) and the adapter defers it to the head without spending an attempt; the next attempt resumes it (`prepare_resume`: cause, graceful flag and counts on `trigger_context.resumes`, `metadata.resumed_from` on its first trace) under the background-task caps (`MAX_GRACEFUL_RESUMES` 20, `MAX_RESUMES` 3; the execution's `max_attempts` is at least `MAX_ATTEMPTS`). An exact call in the approval whitelist's reads (`_is_read_only_tool`) is run again; any other call, and any run past a cap, is re-queued at once (`_requeue_for_owner`): the run fails, a fresh run of the owner agent is created with `trigger_context.owner_prompt` (the action, the previous outcome, the resume counts, "read the target's state first") and `requeued.count`, at most `MAX_OWNER_REQUEUES` (3), then the item is blocked `resume_exhausted` with what happened, asking nothing. `_settle_from_runs` and the dead letter re-queue a run the stale-run sweep failed or the engine gave up on after a restart. `payload.restarts` counts `resumed` and `requeued` (the views' `scheduled.restarts`, "resumed N times"; the outcome posted once, at the end). The cut turn's receipt is credited back as the action goes on. A replaced attempt never settles (`superseded_settle`): `_settle` writes nothing when the run already ended `completed` / `failed` / `skipped`, a later attempt fenced it (`attempt_charges.attempt_fence` past the attempt's place), or the item's `run_id` names another run, so a late attempt never moves an ended run back to a live status (which would keep its work item claims held). The frontend never offers Reschedule or Cancel on an item a restart cut (`canReschedule`). Retried (`SCHEDULED_WORK_ITEM_MAX_ATTEMPTS`, `SCHEDULED_WORK_ITEM_RETRY_SECONDS`): the AI state unreadable, a quota store outage, a target answering 429 (`ToolResult.target_throttled`), a model provider outage before any tool ran. Never retried: a refused check, an invalid payload, an error the tool returned. A dead-lettered run blocks its item `retries_exhausted` and credits every attempt's receipt back.
- **Feedback** (`deliver_outcome`, after the commit, best effort): a `notify_web_user` notification to the creator only when `notifies_person` says so, the outcome posted as an assistant message with the card marker in the conversation the item was scheduled from (`WorkItem.conversation_id`, owner-checked; Slack / Teams get it proactively), and a `work_item_update` SSE frame that refreshes the work-item views and the conversation.
- **Who is notified** (`payload.action.notify`, `payload.action.escalate_to_user`, both booleans written by `build_action`, kept by an edit that omits them): `schedule_work_item` takes `notify` and `escalate_to_user`. `notify` defaults to `build_scheduling_tools(caller_is_person=...)`: true in a chat turn a person asked (`run_agent_chat` with no `parent_run_id`), false in an assignment run (`assignment_engine`) and in a turn under a run (a background task, a delegated turn). In the run of a scheduled one-off (`scheduled_work_item_runner` wraps the instruction turn in `running_one_off(action)`, a context variable its sub-turns inherit), the default is that one-off's own `notify` (`default_notify`): a silent one-off that re-schedules itself or schedules a successor keeps the chain silent; an explicit `notify` still wins. With notify false the outcome is still posted to the conversation and readable in `list_scheduled_work_items`; no bell notification, no phone push. `escalate_to_user: true`, or an item with `needs_human`, notifies whatever `notify` says, with a title that names the agent ("escalated by <agent>") and `extra_data.scheduled_by_agent` / `escalated`. An item stored before the flag existed: silent when an agent created it (`created_by_agent_id` set) or it has no conversation, notified otherwise (no migration). `scheduled_view` serves the resolved value as `scheduled.notify`.
- **State** (`schedule_state`, served as `scheduled.state`): `scheduled`, `due` (within the grace window), `running`, `done`, `blocked`, `missed` (blocked as missed, or open past the window before the tick swept it), `cancelled`. A scheduled item is never stale (`is_work_item_stale`, `_stale_sql_clause`) and the abandonment reaper skips it.
- **Audit**: create (with the frozen action and the offset as written), cancel, reschedule, `update` (an edit of the action, before and after) - `entity_type = work_item`, `details.scheduled = true` - and the dispatch (`system:scheduler`, `trigger`, the run id).
- **Kill switch**: `scheduled_work_items_enabled` (security option, `SCHEDULED_WORK_ITEMS_ENABLED`, control `agents.scheduled_work_items`). Off: `schedule_work_item` / `reschedule_scheduled_work_item` answer `SCHEDULING_DISABLED_MESSAGE`, list and cancel keep working, the tick dispatches nothing and a run that starts blocks; items that come due meanwhile are missed.
- **UI**: the chat card (`ScheduledWorkItemCard`), the one fleet upcoming view (Agentic Flow > Schedule: one-off lanes beside recurring triggers, `buildTimelineLanes`, `?agent=`), Operations > Work Items (`Scheduled` view filter, marker, `?item=`), the agent Overview "Coming up" card, `RunCard` / `RunDetail` labelled "Scheduled" and linked to the item. No tab was added (`pages/operations/tabs.ts`, `pages/agent-detail/tabs.ts`, pinned by their tests).

No memory call ever uses an answer cut at `max_tokens`: json-repair would close the cut body into a parse that looks complete - a directive list cut short replacing the rolled-forward directives, a MERGE cut inside `merged_content` deleting the facts it supersedes. Each retries a cut answer once at twice its budget, capped at the model's output ceiling (`model_limits.retry_output_budget`). Still cut, the compactor raises `CompactionTruncatedError`, so the previous compaction stays in force and nothing is persisted - from the second consecutive cut that conversation's compactor calls pause for 15 minutes, doubling per cut up to 6 hours, so an always-cut conversation does not pay them on every turn; the curator falls back to plain ADD; fact extraction drops the cut last line; the hourly fact consolidation keeps its batch instead of deleting it for a cut merge; the cross-agent user profile keeps its existing text - condensed on its own when it is over `_MAX_PROFILE_CHARS` (3,000), the size no rewrite may store or inject past (`user_memory._condense_profile`): a profile left to grow past what one rewrite can reproduce had every later rewrite cut and stayed frozen.

### Programs

`services/work_item_programs.py` (#10833). A program is a work item, its root: the item keyed `program:<slug>` (no `/` after the slug), optionally described by `payload.program = {owner, target_date, exit_criterion, next_owed_to_user}` (owner and target date fall back on `owner_agent_id` and `due_at`). Its children are the items keyed `program:<slug>/...` and the items of any key whose `payload.program_key` is `program:<slug>` (`work_item._program_children_clause`, the `program_key` filter of `list_work_items`). Creating the root is the whole registration; no migration, no new column. An item created before its root (keyed `dev:...` for its owner's inbox) is linked with `update_work_item(program_key=...)` (#10852): `work_item_programs.with_program_key` sets or drops `payload.program_key` on a copy of the payload, the correlation key and every other payload key unchanged, under the update's write gate; a value that is not a root key (`program_key()` answers `None`) is refused before any read, and the link or unlink is recorded as a claim note.

- **Tools** (coordination group, read-only, on the HITL read whitelist): `list_programs(open_only, scope)` lists the visible roots with their children counted by status, the number of next steps and of items owed to the user, and the flags; `get_program_status(program, scope)` takes `program:<slug>`, the slug or the root id and returns every child (status, owner, `blocked_on`, references, due date), every pull request the root and children name (`payload.pull_requests` and the `pull_request` / `deployment` references of `blocked_on_refs`) with its state read from the code host at call time (`read_pull_request_closings` for merged / closed, `read_live_ci` for an open one's head, draft flag and CI verdict, `unread` when no reader answers), the next steps (open children with no blocker), the items owed to the user (`needs_human` or an `ask`, with their age) and the flags. Every line carries `read_at` and its object id.
- **Never cached**: nothing is stored; each call reads the items and the pull requests again, so a child completed or a pull request merged shows at the next call with no write. No shared-state register or memory is read: the tool description says a program status comes from these tools only.
- **Flags**: a root whose `next_owed_to_user` has no open child waiting for a person with a `due_at` (a step owed to a person is a dated work item, never prose); an open root whose children are all finished.
- **Bounds**: 500 children, 100 programs, 10 pull requests read per status (the cap of the readers it calls).
- **Every fleet orchestrator carries them** (#10979): `fleets.grant_program_status(agent)` gives an agent both reads through the `coordination` group (an unscoped group already offers them; a scoped one gets them added to its allow list; none gets `coordination` scoped to these two functions alone; a former id such as `shared_state` is made canonical first; idempotent). `fleets.set_orchestrator` calls it, so the fleet page, `apply_fleet_spec` and the templates grant them when they name an orchestrator, and the built-in fleet seed (`agents/fleet_seed._sync_members`) calls it on every boot, after the agent seed rewrote `builtin_tool_ids`. Scope `fleet` already covers a seeded fleet's items (`CoordinationScope.work_item_clause`: owned, created or claimed by a home member), so an admin-seeded fleet's programs are visible to its orchestrator. `tests/test_fleet_orchestrator_programs.py` pins it for every `BUILTIN_FLEETS` orchestrator.

### Work item end notifications

`services/work_item_notify.py`. A work item may carry `payload.notify = {"channel": "teams_dm", "user": <email>, "integration": <Microsoft integration id or name>, "message"?: <text>, "include_result"?: false}`. The recipient is `user` (a person: a 1:1 chat is opened), `chat_id` (an existing Teams 1:1 or group chat; `48:notes` is the sending account's own chat), or `channel: "teams_channel"` with `team_id` and `channel_id` (a Teams channel), or `channel: "email"` with `user`, one address (an Outlook email through `send_microsoft_email`, its subject the item's title; #842 S9b). While the item waits for a person's decision (`needs_human` with an `ask` for one user), the scheduler tick also sends that person the decision's answer links (`decision_graph_cards.deliver_work_item_cards`): the `Action.OpenUrl` link card in a Teams chat or channel, the same links as plain text in an email (human-gates.md I.4). The platform, not an agent, sends that message when the item ends, so a run cut by a rollout, a pick-up that never started or a sweep that cancelled the item cannot swallow it.

- **Validation** (`normalize_notify_payload`, called by `create_work_item` and `update_work_item`): an unknown channel, no recipient (a `user` without an address, a `chat_id` or `team_id`/`channel_id` that is not one Graph path segment, both `user` and `chat_id`) or no integration is refused (`NotifyError`, a `ValueError`) before anything is stored. `teams` is an alias of `teams_dm`; unknown keys are dropped.
- **Test items** (`refuse_test_recipient`): an item whose correlation key starts with `retest:` or `test:`, or whose title starts with `Notify retest`, may only name a target listed in `WORK_ITEM_NOTIFY_TEST_RECIPIENTS` (comma-separated addresses, chat ids or `team_id/channel_id`, case-insensitive; empty by default) or the sending account's own chat `chat_id: "48:notes"` (nobody else is in it, so a retest needs no platform values change); any other is refused at create and update, naming the rule.
- **When.** `done`, `cancelled` (an agent, the REST API, the retention reaper `reap_work_items`, any cleanup), or `blocked` once `release_work_item_claim` parked the item after `work_item_max_dispatch_attempts` failed pick-ups (`ending`). An item an agent blocked, or one waiting on `blocked_on`, has not ended. Items that ended more than two days ago are never notified.
- **Delivery** (`deliver_pending_notifications`, step 3b of the scheduler tick after the claim releases, not gated on AI): rows taken `FOR UPDATE SKIP LOCKED`; the send runs on a session of its own, so a token refresh never commits the session that holds the lock. The integration is resolved among the Microsoft integrations the item's user may see (`integration_visible_filter`). The send is a tool call of the agent that created the item (its owner when no agent did), checked live first like a scheduled action (`_usable_agent`: the agent exists and is enabled, the item's user is active and may still use it), then resolved like a scheduled exact action of that agent (`resolve_exact_toolset` with the integration pinned, then `approval_refusal`): its bindings, read-only integrations, allowed tools, enforced element scope and deny list apply, so an agent that may not send a Teams chat through that integration cannot make the platform send one. The tool is that integration's `create_microsoft_chat` for a `user`, `send_microsoft_chat_message` for a `chat_id`, `send_microsoft_channel_message` for a channel (by `base_name` and `entity_id` when several accounts are bound); a send only counts when the tool answers its own success sentence. A `user` that is the sending account itself (Graph: "Duplicate chat members") is sent to the account's own chat `48:notes` instead; when that cannot be used either, the delivery ends at once naming `chat_id` as the alternative. The text (`notification_text`) is plain words for a person: `message` verbatim when set; otherwise one sentence, `<title> is done.`, `<title> was cancelled.` or `<title> could not be started.`. The item's `result` (3000 characters; the cause of a cancellation, `<title> was cancelled: <cause>.`) is added only when `include_result` is true. Never the correlation key, the item id or a timestamp.
- **State**, written by this module only and kept on generic updates: `payload.notify.delivery = {attempts, last_attempt_at, sent_at | next_attempt_at, last_error | gave_up_at}`. A failure backs off 1, 2, 4, 8 minutes; the fifth failure gives up and sends the item's user a web notification instead. A refusal no retry fixes (`PermanentNotifyError`: the integration's bad request, resource not found or validation error, or a target id the tool refuses) gives up at the first attempt. A send interrupted between the Graph call and the commit is sent again by the next tick (at least once on a crash, never silent).

### Run outcome and agent health

`services/run_outcome.py` is the one rule every surface uses to judge an agent from its runs: the fleet Members badge (`GET /fleets/{id}/health`), the fleet activity feed (`GET /fleets/{id}/activity`, `outcome` per run) and the run responses (`AssignmentRunResponse.outcome`, `AssignmentRunDetailResponse.outcome`, read by `runStatusConfig` in the frontend).

- **`run_outcome(status, error)`**: `ok` (completed), `failed`, `interrupted`, `active`, `other`. A failed run whose error is one the platform writes when it ends a run (`INTERRUPTION_MARKERS`: a rollout cut of a consult, a consult cancelled with its caller, the stale-run cleanup after a restart, a worker lost) is `interrupted`. It keeps its `failed` status and stays listed; the run card labels it "Interrupted" in a neutral colour. `tests/test_run_outcome.py` pins every marker against the constant that writes it.
- **`member_verdict(runs)`**: the latest `HEALTH_RECENT_RUNS` (10) runs of the last `HEALTH_WINDOW` (24 h). The member is failing when the newest ended run of that window that was not interrupted failed: a later success clears a failure, and interruptions alone never make a member fail. "Last run" is the newest run of the same set. The counts (`failures_24h`, `recent_runs`, `recent_interruptions`, `last_run_outcome`) feed the badge tooltip (`healthReasons`, `lib/fleet-graph.ts`).

## Agent Templates

Templates are **stored in the database** (`agent_templates` table) and managed by admins via the UI or API. Built-in templates are synced on every startup from `backend/app/agents/templates.py` — new content, updated prompts, and removed templates are all applied automatically. Admins can also create entirely new templates.

Each built-in template ships in the platform modes its `platform_targets` names (`seed_matches_platform`, the rule the skill seed uses): the general-purpose templates below in Copilot mode, the nine CTI templates of `app/agents/cti_templates.py` (Feedly's CTI prompt library, `dev-docs/cti-pack.md`) in XTM One mode, all of them in dev; a built-in the current mode does not ship is removed.

- **Default skills** (`default_skills`): built-in skill slugs (the `slug:<x>` tag of a company-managed skill), resolved per caller by `app/services/agent_template_skills.py` through `user_visible_filter` - enabled and visible only, template order, unknown slugs skipped. `GET /agents/templates` serves them with the caller's `default_skill_ids` (the wizard preselects them and then always sends its list); a REST create from a template that omits `skill_ids` and the builder `create_agent` attach them; an explicit `skill_ids` (even `[]`) wins.
- **Suggested skills** (#12343): a builder `create_agent` that ends with no skill (no template defaults, no `skill_ids`) names in its result the craft skill of each built-in group the agent carries (`SKILL_SLUGS_BY_BUILTIN_GROUP` in `agent_template_skills.py`: `platform` -> fleet-design-practices and fleet-health-advisory, `generate_presentation` -> presentation-design, `generate_report` -> report-design, `video_studio` -> video-production), resolved for the caller through the same reader; nothing is attached, the caller adds them with `update_agent skill_ids`.
- **Manual inputs**: a default assignment may declare `manual_trigger_parameters` (`{key, label, type, description?, required?, default?, options?}`); both create paths copy them through `default_assignment_manual_parameters`, which drops an entry without a non-blank string `key`. The values reach the run in the trigger payload, which the prompt reads by key.

### Style Learning Pattern

Communication agents include **style learning assignments** that run on a nightly schedule:
1. Analyze recently sent messages (email, Teams, WhatsApp)
2. Extract tone, formality, common phrases, greeting/sign-off preferences
3. Store the style guide in the agent's knowledge base as embeddings
4. Drafting assignments use the knowledge base to match the user's voice

### Flagged Email = Draft Queue

The Mail Desk treats flagged emails as a work queue (Outlook follow-up flag):
- Triage assignment analyzes incoming emails and flags only those needing a reply
- Drafting assignment (every 10 min) scans for flagged emails, skips those that already have a draft
- Drafts include the full conversation thread and the user's email signature (from the signature integration the mailbox's Email signature setting resolves to, else copied from their sent mail; none when its signatures are off)
- All drafts are for review — never auto-sent
