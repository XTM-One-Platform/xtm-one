# Channel patterns

The implementation patterns every channel adapter follows - dispatch, credentials, Teams webhook and Graph notification authentication, inbound files, outbound formatting, typing and errors; the rules live in `backend/app/channels/AGENTS.md`.

## Patterns

- All channel webhooks acknowledge quickly (return 200) and process the inbound message asynchronously via `spawn_channel_task()` from `base.py` — a bounded, tracked replacement for a bare `asyncio.create_task()`. A process-wide semaphore (`CHANNEL_MAX_CONCURRENT_PROCESSING`, default 10) caps how many inbound messages are processed at once so an inbound burst cannot spawn unbounded concurrent DB-session-holding agentic loops and exhaust the web connection pool; excess messages queue (the webhook already returned 200) instead of being dropped. The task is also held by a strong reference until completion (no mid-flight GC) and its exceptions are logged, not swallowed. Never dispatch `_process_*_message` via a bare `asyncio.create_task` (a regression test in `tests/test_channel_task_bounding.py` enforces this)
- The `handle_message()` function in `router.py` is the single entry point for all channels
- **@mentions**: off unless `CHANNEL_AGENT_MENTIONS_ENABLED` is on (read first by `_read_channel_mentions`). On, after the routed agent answers an identified user, `_answer_channel_mentions()` has every other agent the message names as a typed `@key` (the web composer's grammar, `services/mention_dispatch.py`) answer in turn - only an agent whose own channel settings let it answer that message (`_answers_channel_mention`); any other token is plain text. Each agent with others after it reads who they are on the message it answers (`turn_lineup`). A routed agent answering `[NO_RESPONSE]` leaves the message to them: only their replies are stored and sent, and the channel activity entry names the last one's agent. The replies are stored as separate attributed messages and delivered in ONE outbound message, a section per agent labelled in the channel's bold syntax, so no adapter changes. One agentic action per agent that runs, charged by the chat quota gate of its own `run_agent_chat`; a handover inside a run rides that run's action
- Messages are stored with their originating channel for audit trail
- Conversations span channels (`services/channel_continuation.py`): an identified user's Slack DM thread or Teams personal chat is listed on the web and continued there, and a conversation the web continues can be bound to a direct-message thread of the bot (`ConversationChannelBinding`, opened by `slack.open_slack_dm_thread()` / `teams.post_to_teams_personal_chat()`, which needs the personal-chat reference recorded on every personal message). In a direct message the router looks for a binding first (`_find_bound_conversation`, owner-scoped: an unresolved sender or another user never reaches the conversation), keeps the conversation's agent (no DM re-routing), runs with its saved session tools, and takes its turn lock (`ChannelTurn`): see `ROUTING.md` section 4c. Group threads are never bound nor continued on the web
- **Credentials are always read from the DB via channel bot lookups, never from env vars**
- **Teams webhook and Graph notification authentication**: see the section of that name below
- **Teams 202 semantics**: `TeamsChannel.send_message()` returns `""` for HTTP 202 (queued async delivery — the norm for private/shared channels routed via Graph) and `None` only on failure. Callers MUST gate success on `is not None` — gating on truthiness would turn off private-channel thread monitoring.
- **Outbound chunking**: every adapter splits long replies with `chunk_message()` against `CHANNEL_MAX_CHARS` (Teams 20k - the Bot Framework cap is ~28 KB of payload bytes, not characters -, Slack 39k, Telegram/WhatsApp/Google Chat 4096, Discord 2000) instead of failing the send.
- **Teams embedded images**: delivered as separate hero-card activities — an activity carrying BOTH renderable `text` and `attachments` is rejected by the Teams connector with HTTP 400 ("multiple skype activities").
- **Teams inbound files**: `_extract_teams_file_attachments()` handles both delivery shapes — personal 1:1 chats send `application/vnd.microsoft.teams.file.download.info` with a pre-authenticated `content.downloadUrl` (requires `supportsFiles: true` in the app manifest), while group chats/channels send `reference` attachments whose SharePoint `contentUrl` is rewritten to the Graph `/shares/{u!…}/driveItem/content` endpoint and downloaded with the bot's app-only Graph token (`Files.Read.All`/`Files.ReadWrite.All`). The router's file downloader follows redirects (Graph content endpoints 302 to the real bytes; httpx drops the bearer header on the cross-origin hop).
- **Inbound file download is bounded**: `_download_channel_file()` in `router.py` never holds more than `MAX_UPLOAD_SIZE_BYTES` + 1 bytes of an attachment - a size the platform declared (`InboundFileAttachment.size`) or an unencoded `Content-Length` over the limit stops it before the body, and the body is read raw (`aiter_raw`, `Accept-Encoding: identity` asked) and dropped as soon as the count passes the limit (a Teams attachment declares no size, and httpx's `timeout` is per read, not a total). A gzip / deflate body is inflated with a `zlib` output cap of the room left, never through `aiter_bytes` (httpx inflates a whole wire chunk at once: 50 KB of gzip is 50 MB), a bare deflate stream retried with the raw window (`_CODING_WBITS`, as the MCP configuration fetch does); any other coding is refused (`ChannelFileEncodingError`). The raw read is capped too (limit + 1% + 1 KB), or a stream that inflates to nothing would be read forever, and the file is gathered in one `bytearray`, never a list of chunks. Never read a channel file with `resp.content` before checking its size.
- **Teams group-chat/channel Graph fallback**: in practice the Bot Framework activity for group chats and channels often carries only the `text/html` file-card stub and NO `reference` attachment. `_process_teams_message` therefore fetches the Graph copy of the message (`_fetch_graph_inbound_message` — `/chats/{id}/messages/{id}` for group chats, `/teams/{team}/channels/{channel}/messages[/{root}/replies]/{id}` for channels; activity ID == Graph message ID) and extracts `reference` attachments from it via `_extract_graph_message_attachments()` (requires `Chat.Read.All` / `ChannelMessage.Read.All`). The private-channel Graph-notification path extracts attachments from the already-fetched message directly. File-only messages (no text) are not dropped — the text falls back to `FILE_ONLY_PLACEHOLDER` (`base.py`, shared with Telegram) so the agent still reacts to the file.
- **Telegram inbound files**: Telegram never sets `text` on a message carrying a file - its text is the `caption` (entities in `caption_entities`), and a bare file has neither. `_message_files()` reads `document`, `photo` (the largest size), `audio`, `video`, `voice` and `video_note` (a sticker is not a file the agent reads; an animation also sets `document`); a message with one of them and a caption reaches the router with the caption as its text, a bare one with `FILE_ONLY_PLACEHOLDER`. Anything else without `text` (a sticker, a service message, a caption on another kind of media) and an edited caption (`edited_message` is processed only when it is a text message) is ignored. The `getFile` round trips run in `_process_telegram_message`, never before the webhook answers; a file declared larger than `getFile` serves (`TELEGRAM_GETFILE_MAX_BYTES`, 20 MB) or the router stores (`MAX_UPLOAD_SIZE_BYTES`) is not requested, and a file Telegram cannot serve is left out while the message goes on, as a file the router fails to download. Mentions are read from the entities of the text they belong to, offsets in UTF-16 code units (`_entity_bounds()`), a bot name compared whole (`/help@botname_backup` is another bot's) and stripped where its entity is, never by text replacement. Both Bot API URLs carry the bot token: the file lookups (`_resolve_telegram_file`, the router's download, which logs the host only) log neither a URL nor an httpx error's message, and no log line carries a file name or the caption.
- **WhatsApp inbound media**: an `image`, `document`, `audio` or `video` message reaches the router with its `caption` as its text, a bare one with `FILE_ONLY_PLACEHOLDER` (a `sticker` is ignored). `_message_media()` reads the media id (all digits, it is a URL path segment the token is sent to), a document's `filename` and the `mime_type`; `_process_whatsapp_message` resolves it with `GET /{media-id}?phone_number_id=<the bot's>` (never before the webhook answers) and hands the router the returned media URL with the access token, only when it is a Meta host (`whatsapp_bot._is_meta_media_host`); a media whose `file_size` is over `MAX_UPLOAD_SIZE_BYTES` is not downloaded, and one WhatsApp cannot serve is left out while the message goes on. The media URL expires after five minutes, so it is resolved in the processing task, right before the router downloads it.
- **Google Chat inbound attachments**: `_message_files()` reads `message.attachment`: content uploaded to Chat (`attachmentDataRef.resourceName`) is handed to the router as the `media.download` URL (`google.chat_media_url()`, the Google integration's own rule) with the app's `chat.bot` token, acquired in `_process_googlechat_message`; the router follows a redirect from that endpoint as it does from Graph. A Drive file (`driveDataRef`) is not served by `media.download` and the Drive API needs a user's authorization, so the message text names it (name, type, Drive file_id, link) for a Google integration to read. A message carrying only files gets `FILE_ONLY_PLACEHOLDER`. The bot cannot SEND a file: `media.upload` requires user authentication, which a Chat app's service account does not have (the `send_googlechat_bot_message` description says so).
- **Artifact markers**: `[[PRESENTATION:id]]`, `[[REPORT:id]]` and `[[VIDEO:id]]` become viewer links through `resolve_channel_presentation_markers()` / `resolve_channel_report_markers()` / `resolve_channel_video_markers()` in `base.py`, scoped to the conversation and user. `[[INVESTIGATION:id]]` and `[[WORK_ITEM:id]]` have no standalone viewer and are stripped instead (`strip_channel_investigation_markers()` / `strip_channel_work_item_markers()`), so the raw marker never reaches channel users.
- **`[[FILE:id]]` markers**: `resolve_channel_file_markers()` in `base.py` rewrites file download-card markers into signed public links before external-channel delivery (web chat renders them as cards in the frontend; a marker left unrewritten would reach the channel as raw text). The link (`GET /api/v1/chat/files/{id}/public?token=...&expires=...`, 24 h) opens raster images, PDF, plain text, Markdown, CSV, WebVTT, JSON (JSON Lines and `+json` types included), audio and video in the browser, and downloads HTML, SVG, XML and every other type (`inline_documents=True` in `services/file_responses.py`). The lookup is **scope-restricted** — links are only signed for `FileAttachment` rows matching the caller's `conversation_id`/`user_id` (marker text is LLM-controlled; an arbitrary UUID must never mint a public link), with no scope = strip everything (fail closed). Filenames embedded as Markdown link text go through `sanitize_md_link_text()` (also used by the teams_bot upload announcement).
- **Markers in a send tool's text** (#9990): an agent that posts through an integration send tool (Teams chat or channel, Outlook, Gmail, Slack, a channel bot) bypasses the reply path above, so `send_markers_as_links()` (`services/outbound_markers.py`) wraps every send tool's handler at build time (`integration_tools`): the arguments named by `ToolDefinition.outbound_text` (default: the body arguments of its `send_guard`, the subject excepted) go through the same resolvers, in the run's conversation / user scope, before the provider runs. A marker out of scope is dropped, never left raw. A new send tool with no `send_guard` declares `outbound_text`. A send tool that delivers `[[FILE:id]]` markers as attachments itself (`send_microsoft_chat_message`, #1829: Teams file cards) sets `ToolDefinition.outbound_keeps_file_markers`: its file markers pass the rewrite untouched, every other marker is still linked.
- **Bare platform links** (#10115): an agent that names a platform page without its scheme (`copilot.example.ai/presentations/<id>`) wrote plain text no channel links. `bare_platform_links_as_urls()` (`services/outbound_links.py`) gives every bare reference to the hosts of `FRONTEND_URL` and `BASE_URL` their configured scheme and writes it as a Markdown link (an `<a>` in a body already written as HTML), on the reply path (`router.py`, before the marker resolvers) and in the send-tool wrapper above (pure, no session). Inline and fenced code, a URL with a scheme, a well-formed link, an e-mail address and a longer host (`<host>.other.net`) are left as written. WhatsApp draws no Markdown: the WhatsApp channel adapter and the WhatsApp send tools (Cloud API, channel bot, gateway) write `[label](https://...)` as `label: https://...` (`markdown_links_as_plain_urls()`), which WhatsApp links by itself; Teams and mail render the Markdown link as an anchor.
- **Image addresses** (`![alt](/api/v1/chat/files/<id>)`, `![alt](/api/v1/chat/images/<id>)`): `resolve_channel_images()` signs a public link (and the adapters that upload bytes read them through `fetch_embedded_image`) only for an id of `allowed_ids`, which the router looks up with `channel_image_scope()` under the same conversation / user scope as the markers (`FileAttachment` and `ChatImage` rows); any other image keeps its alt text and gets no link, and no scope or a failed lookup signs nothing.
- **External images on a media host** (`![alt](https://media2.giphy.com/...)`): the router passes `trusted_media_hosts()` (`base.py`, the union of `integration_tools.PROVIDER_MEDIA_HOSTS`, each provider's `MEDIA_HOSTS`: a host and its subdomains) to `resolve_channel_images()`, which extracts an https image on one of them as an `EmbeddedImage` of source `EXTERNAL_IMAGE_SOURCE` whose `public_url` is its own address, the line left as written, each address once, at most `MAX_EXTERNAL_CHANNEL_IMAGES` (4), in reading order with the platform's images. `is_trusted_media_url()` refuses http, userinfo and a port other than 443. The address is LLM-controlled: an image on any other host is never fetched nor forwarded (a tracking pixel carrying conversation data in its query string stays a Markdown line). Teams (hero card), Google Chat (card) and WhatsApp (`link`, which takes JPEG and PNG only) hand the address to the platform; Slack, Telegram and Discord upload bytes read by `fetch_embedded_image()`, the one reader: a platform image by its id (`fetch_image_bytes`), an external one through `fetch_external_image_bytes()` (host checked again, `social_media.fetch_public_media` with the outbound URL policy on every hop, `MAX_EXTERNAL_IMAGE_BYTES`, typed by `sniff_raster_type`, never by the header). An upload is named by `image_upload_filename()` (the extension of its type: a GIF named `.png` is drawn still), and Telegram sends a GIF with `sendAnimation` (`sendPhoto` draws it still). A provider declares hosts only where they serve media; a new one adds its `MEDIA_HOSTS` to `PROVIDER_MEDIA_HOSTS`.
- **Slack thread fallback**: If Slack returns `cannot_reply_to_message` when posting with `thread_ts`, the adapter retries without the thread reference (posts to the channel directly instead of failing silently)
- **Markdown → Slack mrkdwn**: All Slack message sends (channel adapter, integration tools, bot tools, notifications) pass text through `markdown_to_slack()` from `core/utils.py` to convert standard Markdown (`**bold**`, `[text](url)`, `~~strike~~`) to Slack's native mrkdwn format (`*bold*`, `<url|text>`, `~strike~`)
- **Typing keepalive**: External channel adapters wrap `handle_message()` with `typing_keepalive()` from `base.py` — an async context manager that sends typing indicators at regular intervals (default 3s) while the agent is processing. This keeps the "typing…" state alive for the full duration of the LLM call. WhatsApp skips it (the Cloud API has no typing signal).
- **Error notices**: on processing exceptions, every adapter tells the user something went wrong in DMs (and explicit @mentions) instead of leaving a typing indicator followed by permanent silence.
- **Streaming**: a channel sends only the final reply; a channel turn on a conversation the web also reaches fans its events out to the web (`ChannelTurn`, `TurnPublisher`). The event contract (`thinking_text`, `streaming`, ...) is `dev-docs/reference/backend-tools-streaming-events.md`.

## Teams webhook and Graph notification authentication

### Bot Framework webhook

`/api/channels/teams/messages` validates the Bot Framework JWT (`_verify_botframework_jwt()` in `teams.py`): issuer `api.botframework.com`, audience = the bot's app ID, signing keys from the Bot Framework JWKS, 5-minute clock-skew leeway; a failed check is a 401. When no `teams_bot` with a `client_id` is configured, the endpoint processes the payload unauthenticated and logs a one-time warning (`warn_unauthenticated_once`); an unreadable credential fails closed via the `DECRYPT_FAILED_CREDENTIAL` sentinel.

### Invokes: pasted links and their cards

An `invoke` activity is answered in the response body, not dispatched: `_handle_invoke()` in `teams.py`, refused with a 401 when no bot can vouch for it (no `client_id`), whatever the unauthenticated mode does for messages. `composeExtension/queryLink` answers a link to one of the platform's pages (`teams_link_cards.parse_link`: `FRONTEND_URL` or `BASE_URL`, base path included) with the neutral card and reads nothing; `adaptiveCard/action` (each viewer's refresh, and the buttons) is refused unless the activity's tenant is the bot's configured `tenant_id` (none configured: refused), resolves the Teams user by email (Bot Framework member API, cached 10 minutes per Entra object id) then by linked identity, is rate limited per Teams user, and renders `teams_link_cards.viewer_card()` or acts through `teams_link_cards.act()`, which answers a run with `assignments.answer_paused_run()` - the respond endpoint's own function. Contract: `dev-docs/teams-link-unfurl.md`.

### The verdict on a Graph notification

`/api/channels/teams/graph-notifications` checks each notification against the subscription recorded for its channel (`teams:priv_ch_sub:{team}:{channel}`) through ONE verdict, `_notification_verdict` (`teams_graph_verdict.py`):

- **proven**: it echoes a recorded subscription id and the `clientState` that record says was issued, compared in constant time, from the recorded tenant when both are GUIDs. The issued value is one of: a random value stored Fernet-encrypted in `client_state_enc` (what a new subscription gets); a random plaintext `client_state` (an older record, re-stored encrypted in place by the renewal pass); the legacy `copilot_{team_id}`, only for a record written before random clientStates.
- **unverified**: not proven, but what earlier releases acted on: the same clientState comparison with no subscription id or tenant (`_compatible_client_state`: the plaintext or decrypted value, the legacy value for no record, an unreadable one or one holding none) or, for a clientState that no longer decrypts (a changed `SECRET_KEY`), the recorded subscription id and tenant, which a genuine notification always carries.
- **refused**: anything else. A refused notification is never trusted: only the fact that one arrived is recorded.

`_graph_notification_accepted` acts on a proven notification, and on an unverified one unless verification is required: `verification_required()` from `services/integration_notification_auth.py`, the ONE switch of every notification endpoint - Settings > Security "Require verified integration notifications", `INTEGRATION_NOTIFICATIONS_REQUIRE_VERIFICATION` winning, the control `integrations.notifications_require_verification`, off by default. An unverified notification it acts on is reported by a WARNING through that module's `log_rate_limited` (at most once every 15 minutes per reason, never the payload) and counted in `teams:graph_unverified`, which the Security Audit reads through `graph_notification_health()` (`channels.teams_graph_notifications_unverified` / `channels.teams_graph_notifications_verified`). Refusals are logged through `log_rate_limited` too, a count per POST, never the payload.

### Answering a POST

- **Bounded body**: a POST within `GRAPH_NOTIFICATION_MAX_BODY_BYTES` (4 MiB, read under that bound by `app.core.http_body.read_bounded_body`: the declared length, then the bytes read) is answered; a larger one is a 413.
- **Always 2xx**: every POST is answered 2xx, refused entries included (a 5xx only makes Graph retry for four hours) - except a 503 when Redis cannot be read to decide the batch or to record the gap of a refused entry (the route calls `_mark_notification_gap(..., best_effort=False)`; every other caller keeps it best effort), since nothing is queued yet and Graph's redelivery is then what saves it.
- **Decided before queueing**: the route decides every entry before queueing anything (`_decide_notifications`: chunked `MGET`s of the channels it names, each record decrypted once through `_IssuedStates`, the same `_notification_verdict` and `verification_required()`; a lifecycle notification through `_lifecycle_notification_proven`, the predicate its task uses). A refused entry never becomes a task, and an accepted message named twice in a batch is queued once. A refused entry on a monitored channel whose record is missing or unprovable still marks a gap (below), and the queued task decides again against the record as it is by then.
- **Pure decision**: the verdict and the decision on a POST are pure functions of `teams_graph_verdict.py`, which imports only the standard library, `app.core.security` and the Graph path-segment rule it shares with the Teams bot tools (`integrations/providers/graph_path.py`). `summarize_post` returns the entry count and the channel keys to read; `decide_post` reads the batch again from the raw body and decides it against the records read.
- **Off the event loop**: under the GIL, the C-level `json.loads` and the garbage collection it triggers hold the interpreter wherever they run in this process. So a POST from `GRAPH_NOTIFICATION_OFF_LOOP_BYTES` (64 KiB) runs both functions in a spawned worker process (`teams_graph_worker.py`, `core/worker_process.py`, the SVG rasterizer / Nova matching pattern: one worker, one job at a time per loop, killed past `DECISION_TIMEOUT_SECONDS` or with its caller, only the keys, the existing records and the decision crossing the process boundary); its `MGET`s and gap markers stay on the event loop. A smaller POST, which costs less than the hop, is decided inline. When no worker can be started (or a job did not finish), the webhook thread pool (`parse_offload.run_webhook_parse`) decides with the same functions, for `WORKER_RETRY_SECONDS` after a failed start.
- **Once per message**: a notification acted on is processed once per message (`_first_delivery`, `teams:graph_msg_seen:{team}:{channel}:{message}`), since Graph delivers at least once.

### Subscriptions

- **Creation**: a new subscription gets a random `clientState` stored Fernet-encrypted and a `lifecycleNotificationUrl` - Graph refuses a Teams subscription longer than an hour without one - which is the same endpoint with `?team=&channel=`, since a lifecycle notification names no channel.
- **Lifecycle notifications**: `_process_graph_lifecycle_notification` answers the proven ones: `reauthorizationRequired` renews the subscription (if ignored, Graph pauses its notifications), `subscriptionRemoved` creates a new one.
- **Replacement**: Graph allows one subscription per app and channel and never changes a `clientState`, so replacing a subscription means deleting it first, and a creation Graph then refuses leaves the channel silent.
- **Default (verification not required)**: nothing an earlier release relied on is deleted. A record with the legacy value or one whose `clientState` cannot be read is kept and renewed. A creation refused because the channel holds a subscription no record describes deletes that orphan only when this release created it (it has a `lifecycleNotificationUrl`, and its clientState was in the lost record, so nothing it sends is acted on); one an earlier release created is kept until it expires.
- **Verification required**: the renewal pass replaces legacy and unprovable subscriptions and deletes every orphan. The old subscription's notifications are accepted for `_REPLACED_SUBSCRIPTION_GRACE` (`replaced_subscriptions` on the record; Graph's four-hour retry horizon, since the pass runs right after a restart while Graph retries what failed during it); one that cannot be deleted is kept and renewed until the next pass tries again.
- **Renewal pass**: it runs on the first scheduler tick each process wins after a start, then hourly (`_teams_subscription_tick_counter`, seeded at its interval in `services/autonomous.py`). A renewal answered 404 recreates the subscription; any other failed renewal keeps it.
- **Channel lock**: every channel operation (the pass, lifecycle handling, first-time setup, which adopts what another worker records while it waits) holds the channel lock (`teams:priv_ch_sub_lock:*`, `_SUBSCRIPTION_LOCK_TTL` = 600 s, above the Graph work done under it), released by an atomic compare-and-delete. A subscription whose deletion failed keeps its record so the next pass retries.

### Gaps and catch-up

Nothing notified is lost. Whenever a channel may have missed notifications - a delete-then-create swap, an orphan's deletion, a `subscriptionRemoved`, a renewal answered 404, or a refused notification on a monitored channel whose record is missing or unprovable - a gap marker (`teams:priv_ch_gap:*`, earliest wins, at most `_CATCH_UP_MAX_LOOKBACK` = 4 h back) is written before anything is deleted. Once the channel has a subscription that notifies again (created, renewed, or not due for renewal; never after a failed renewal), `_catch_up_channel` reads the replies of the channel's monitored threads from Graph (`GET .../messages/{root}/replies`, the same `ChannelMessage.Read.Group` permission as reading one message; a page stops the read at an older reply only when it is newest first) and hands each through `_route_graph_channel_message`, the path a notification takes, behind the one once-per-message mark - so a reply both notified and read back is processed exactly once.
