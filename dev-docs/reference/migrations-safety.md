# Database migrations (safety)

READ before touching `backend/alembic/` or `backend/app/models/`. The six rules are numbered and code cites them by number ("rule 5"); `backend/AGENTS.md` keeps a one-line summary of each.

The platform **auto-migrates on startup** (`app/core/migrations.run_migrations()`, called from the `main.py` lifespan) and runs **multiple backend replicas**, so a migration can execute while older replicas still serve traffic, and several replicas can boot at once. A bad migration therefore breaks or stalls every booting backend - this has recurred, so these rules are mandatory. They are enforced by `tests/test_migration_integrity.py` (offline, in the `Backend lint` CI job) and the `Migrations (Alembic)` + `Bootstrap (fresh DB)` CI jobs (fresh install, idempotent re-run, downgrade round-trip).

1. **SINGLE HEAD.** Chain off the current head; never open a second head. After rebasing onto a `main` that added migration(s), re-point your earliest migration's `down_revision` to main's new head, then re-verify: `make test ARGS="tests/test_migration_integrity.py"` (repo root). Resolve a genuine fork with an Alembic merge migration. Your branch passing that test is **not** enough: two PRs cut from the same parent are each green on their own and fork the history when both land. The `Backend lint` CI job therefore runs the suite on GitHub's merge of the PR into `main` (as `main` stood at the push), the `Migrations (Alembic)` job checks the single head again on a PR that changes a migration, a model, the database setup or the backend's dependencies and in the merge queue on the exact commit that becomes `main`, CI runs nightly on `main` so a fork that reached it anyway is flagged, and any migration landing on `main` posts a rebase notice on every open PR touching `alembic/versions/`. If Backend lint goes red while the local test is green, `main` moved under you - rebase (`./scripts/ci-local.sh` checks against the live tip of `main`).

2. **IDEMPOTENT / re-runnable.** The body must be a no-op on re-run. Fresh installs run `create_all` + `stamp head` (the migration body **never** executes); existing installs run the body; a crashed/duplicate replica may retry - all paths must converge. Use guards:
   - `ALTER TABLE t ADD COLUMN IF NOT EXISTS ...` / `ALTER TABLE t DROP COLUMN IF EXISTS ...`
   - `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` / `DROP INDEX IF EXISTS`
   - enum value: `ALTER TYPE x ADD VALUE IF NOT EXISTS '...'`
   - constraint / FK: wrap in `DO $$ BEGIN IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname='...') THEN ... END IF; END $$;`
   Keep the SQLAlchemy model in sync so `create_all` + the `_ensure_model_columns` safety net reproduce the column on fresh installs.

3. **CONCURRENT MULTI-REPLICA STARTUP - already guarded; rely on it.** `run_migrations()` holds a Postgres advisory lock (`pg_advisory_lock(294837)`) so only ONE replica migrates at a time; seeding holds a second lock (`bootstrap_lock`, `294838`). A worker is not a new launch: `start-uvicorn.sh` exports a fresh `XTM_ONE_LAUNCH_ID` per run, the first worker whose bootstrap completes records it (`app/core/launch_marker.py`), and a worker that starts after that - the replacement of a worker recycled after `MAX_REQUESTS` included - skips both and only redoes the bootstrap's per-process state (`_adopt_launch_bootstrap` in `main.py`: a new process-level side effect of the bootstrap goes there too). Workers that start together still each pass the migration lock (the later one finds nothing to apply) and the later one adopts under the bootstrap lock. A failure-isolated bootstrap step that "retries on the next startup" is retried by the next LAUNCH, never by a recycled worker: during a rolling deploy that worker is the older code, and re-running the migrations or the built-in content sync from it fails against the newer head or puts the older content back. Do NOT add another migration lock and do NOT run schema DDL outside the Alembic path. (The advisory lock is the single-runner guard - its absence would be the classic multi-replica corruption cause; it is present, so the failure mode to worry about is non-idempotent or lock-heavy DDL, below.)

4. **LOCK-LIGHT DDL (rolling-deploy safe).** The advisory lock serializes *runners*, but old replicas keep serving during a rolling deploy, so a heavy/long lock on a hot table = downtime.
   - OK (metadata-only on PG 11+, brief `ACCESS EXCLUSIVE`, no rewrite): `ADD COLUMN ... DEFAULT <constant>`, including `NOT NULL` with a constant default.
   - BANNED unless reworked lock-light: full-table rewrites (`ADD COLUMN ... DEFAULT <volatile/expression>`, column type changes); `SET NOT NULL` on a large table (instead add `CHECK (col IS NOT NULL) NOT VALID`, then `VALIDATE CONSTRAINT` in a separate step); any unbounded `UPDATE`/backfill inside the migration transaction (batch it in bounded loops).
   - **BANNED: `CREATE/DROP INDEX CONCURRENTLY` in a migration body** (`test_no_new_migration_builds_an_index_concurrently`). The body runs under the migration advisory lock while the old pods serve; a concurrent build waits for every older transaction in the database - the siblings queued on that lock, the old pods' long sessions - and may never finish: `u5715sig01` hung a production rollout this way on 2026-10-12 (the startup bootstrap learned it first). Index idiom: `create_index_in_place(conn, "<index>", "<table>", "(<columns>)")` from `app.core.migration_ddl` inside `op.get_context().autocommit_block()` - a plain `CREATE INDEX IF NOT EXISTS` behind the canonical recipe below, under bounded timeouts, which first drops an INVALID index an interrupted concurrent build left (`IF NOT EXISTS` would match it forever); `required=True` when a later step needs the index. A drop is a plain `DROP INDEX IF EXISTS` behind the recipe. On a large, hot table a plain build blocks its writes for the build, so ask before adding one there - and an index the code does not need is not added. A foreign key to an existing table is lock-taking on that table too (rule 5): leave it out when the code can live without it.

5. **LOCK-SAFE DDL (mandatory, machine-enforced).** Even a metadata-only `ALTER TABLE` needs a brief `ACCESS EXCLUSIVE` lock, and during a rolling deploy the previous-version pods hold long-lived open transactions (agentic loops keep DB sessions open for minutes) whose `ACCESS SHARE` locks block it. PostgreSQL queues fairly, so every subsequent reader queues behind the blocked ALTER — the queue never empties and startup dies. **There is NO cold table**: `platform_settings`, a singleton row nobody writes to, took production down exactly this way on 2026-07-05 (migration `p1m2c3s4v5r6`, SQLSTATE 55P03). Every migration that emits lock-taking DDL MUST use the canonical recipe, in this order:
   1. Idempotency probe + early return (steady-state re-runs take NO lock).
   2. `terminate_lock_holders(conn, "<table>")` from `app.core.migration_ddl` — pre-flight that kills same-role lock holders so the ALTER acquires its lock instantly.
   3. `set_lock_timeout(conn)` from `app.core.migration_ddl` — short `SET LOCAL lock_timeout` belt so a racing reconnect fails fast (55P03) instead of wedging the lock queue.
   4. The guarded DDL (`IF NOT EXISTS` / `IF EXISTS`).

   The startup runner (`_apply_pending_migrations` in `app/core/migrations.py`) retries transient 55P03/57014 failures with exponential backoff (safe because bodies are idempotent), so a fired belt self-heals — but do NOT rely on the retry alone; the pre-flight is what makes the DDL actually complete. (`CREATE/DROP INDEX CONCURRENTLY` is banned in migration bodies, rule 4; the grandfathered migrations that use it run it outside the belt.) A brand-new table is NOT exempt when it carries a FOREIGN KEY to an existing table: the key takes a `SHARE ROW EXCLUSIVE` lock on the REFERENCED table (inline in `CREATE TABLE` too), which waits behind any open transaction that wrote to it and makes every later writer wait behind the DDL - so the `CREATE TABLE` runs under `set_lock_timeout` (see `a3rc4de0001_add_arcade_tables.py`). On an existing install the startup `create_all` creates a new model's table BEFORE its migration body runs, so it gets the same belt and the runner's retry (`_create_missing_tables` in `app/core/migrations.py`). `terminate_lock_holders` on the referenced table is not needed for it: that lock does not conflict with readers, and the pre-flight would kill them; dropping such a table (downgrade) takes an `ACCESS EXCLUSIVE` lock there and runs under the belt too. ENFORCED: `test_lock_taking_ddl_sets_lock_timeout` in `tests/test_migration_integrity.py` fails the build on any new migration with lock-taking DDL (FK-bearing `CREATE TABLE` included) and no `lock_timeout` in its CODE - a comment or docstring explaining why the belt is not needed does not count (three migrations passed that way); the grandfather list is frozen — never add to it.

   **A wait is bounded, never silent.** The Alembic connection starts with `lock_timeout` / `statement_timeout` (`MIGRATION_LOCK_TIMEOUT_SECONDS`, `MIGRATION_STATEMENT_TIMEOUT_SECONDS`; `alembic_server_settings()` in `app/core/migrations.py`), so a statement stuck on a lock or a snapshot fails into the runner's retry (a statement timeout is retried once, not six times), then fails startup with an error. A migration that legitimately needs longer sets its own `SET LOCAL statement_timeout`. Meanwhile `app/core/startup_watchdog.py` logs at ERROR, every `STARTUP_WATCHDOG_SECONDS`, the startup step in progress (`set_startup_step`) and the database sessions of the startup locks with their blockers (who and how long, never their SQL), and past the same delay the SAQ worker's schema wait turns to ERROR when no platform process holds the migration lock. A replica waiting for the migration lock polls `pg_try_advisory_lock` (`wait_for_advisory_lock()` in `app/core/migrations.py`) and ends its transaction after every miss, never a blocking `pg_advisory_lock`: a session blocked in that SELECT holds a snapshot, which a grandfathered `CONCURRENTLY` build run by the lock holder would wait for, a deadlock PostgreSQL cannot detect. The lock ids and the Alembic `application_name` live in `app/core/startup_locks.py`.

6. **REVERSIBLE — NO EXCEPTIONS.** Provide a real, working `downgrade()` for every migration (CI walks the last 5 with `downgrade -1` and fails on any downgrade error). There is NO "irreversible migration" concept, no allowlist, no escape hatch: if a migration cannot be cleanly downgraded, redesign the migration (e.g. keep the source data, rebuild the prior shape best-effort with `NOT VALID` FKs for a full data-migration downgrade). A data normalization whose old state carried no information may legitimately have a no-op `downgrade()` body — that is still a working downgrade, not an exemption. The only mechanical stop in CI's walk is a merge revision (`downgrade -1` is undefined at a merge point; merge bodies are empty, nothing is skipped).

**Reference migrations that model the idioms:** the earlier migration history (which contained the concrete idiom examples) was squashed into a single baseline (`d046bcdf345f_baseline_schema.py`), so there are no longer on-disk example migrations to point at. Follow the canonical recipe directly from `app.core.migration_ddl` (`terminate_lock_holders` + `set_lock_timeout`) and the guarded-DDL idioms above when writing any NEW migration on top of the baseline.
