# Tool argument validation and the loop breaker

How the agentic loop checks a tool call before it runs (argument coercion, schema validation, bounded schema regexes) and stops a stuck run (the loop breaker, the step-budget nudge, per-target throttling); the rules of this area live in `backend/app/tools/AGENTS.md`.

## 3e. Pre-execution argument validation, and the coercion in front of it

Every tool call is validated against its `input_schema` BEFORE dispatch (`validate_tool_arguments`, CORE-2; schema regexes excepted, see below): an invalid call is never executed, the model gets a structured tool-result error with the expected schema echoed, and the failure counts toward the per-tool failure nudge. Two things sit in front of that validator, both deterministic and both zero prompt characters:

* **`coerce_tool_arguments()`** turns a stringified scalar into the declared primitive when - and only when - the reading is unambiguous: `"true"` / `"false"` -> bool, `"12"` -> int, `"1.5"` -> float (finite only), `"null"` -> `None` where `null` is declared, a JSON-looking string -> list / dict where `array` / `object` is declared and it parses to that type; nested through `items` / `properties`, bounded in depth. It fires only when the declared type does NOT admit `string` (a `["string", "integer"]` union keeps the string - the model may mean it), returns the SAME object when nothing changed, and never raises. On an `anyOf` / `oneOf` node two more guards apply: a value that already validates against the whole union is left untouched (`{"id": "001"}` under an integer-or-string `id` IS the string branch - coercing it toward the first alternative made it `{"id": 1}` and lost the zeros silently), and the walk descends into an alternative only when exactly ONE alternative declares the value's JSON type - with several, nothing is coerced and the validator reports. It exists because several models emit every argument as a string (`{"include_spans": "true", "limit": "1"}`) and, told `'true' is not of type 'boolean'`, retry the identical shape until the failure budget is spent - a string that reads as the declared type is an input to accept, not an error to teach the model out of. A `$collected`-injected key is passed as `skip_keys` and never coerced (the injected value is a platform-written JSON string the tool must receive verbatim - the validator excludes it for the same reason). The coerced arguments replace `tc.arguments` on the `ToolCall`, so the replayed assistant turn shows a call that validates.
* **`_compact_schema()` strips prose before the cap.** The echoed schema is cut at `_VALIDATION_SCHEMA_MAX_CHARS`; `_strip_schema_prose` removes `description` / `title` / `$comment` / `examples` (string or list values only - a PROPERTY named `description`, as Jira and Notion tools have, holds a dict and stays) first, so a verbose schema is cut in its prose, never in the property names / types / enums / `required` the model needs to correct the call.

Never add a lenient branch to the validator itself to "accept" a wrong type: the coercion is the one place that decides what a string may become, and the validator stays strict on what comes out of it.

**A tool schema's regexes never run unbounded, and its references are never retrieved.** Any user can add an MCP server or a custom tool, so the schema is attacker-controlled. Every check is built on `app/services/schema_guard.py`, the one mechanism the agent output-schema checks use too: `LOCAL_SCHEMA_REFS_ONLY` retrieves nothing, `regex_keywords()` are the only `pattern` / `patternProperties` / `additionalProperties` / `unevaluatedProperties` implementations (each check passes its own judge), and `extend_pinned()` keeps a whole document on them - `jsonschema` picks the stock class again for a subschema's own `$schema`, whose `pattern` runs on `re`. Validation goes through `_argument_validator()`: those keywords with a judge that never runs a pattern (whatever shape `patternProperties` has), `check_schema(..., format_checker=None)` (the `regex` format compiles every pattern); a schema referencing another document, or mixing a regex with `not` / `oneOf` / `if` / `disallow` / `maxContains` (where ignoring a keyword tightens), is not pre-validated and the tool validates its own input. The union check of the coercion keeps the verdict it always gave through `_coercion_validator()`: its patterns run through `schema_guard.bounded_search()` within a per-call budget of CPU time (`schema_guard.regex_stopwatch()`, the searching thread's own clock - a loaded host's pauses never spend it), read as `re` reads them (one with no verdict in time or none `re` is sure to give, or a verdict that needs a remote document, leaves the value as sent), and a `patternProperties` that is not a mapping admits every key. Never check a tool schema with `validator_for(schema)(schema)` or `jsonschema.validate`, and never build a validator class with `jsonschema.validators.extend` alone: the stock class runs the regexes on the event loop and the default registry fetches `http(s)` / `file` / `data` URLs; a cache in front of validation wraps `_argument_validator`, it never replaces it. For the same reason MCP sessions (`mcp_client.ClientSession`) skip the SDK's check of `structuredContent` against the server's `outputSchema`. `tests/test_tool_arg_schema_regex.py` and `tests/test_schema_guard.py` fail if a schema pattern reaches `re` unbounded, a check retrieves a document, or a second copy of the mechanism appears.

## 3g. Write coalescing in one tool round (`app/tools/write_coalescing.py`)

Right after the loop breaker's screen, `coalesce_write_calls()` merges the updates of ONE object asked in the same round into the first of them, which runs once: two `update_microsoft_calendar_event` calls on one event (body, then location) are one Graph PATCH and one attendee notification. A tool opts in on its own definition, never in the generic module (invariant 18): `ToolDefinition.coalesce = WriteCoalescing(identity=..., mode=..., union_lists=...)`, the identity's first argument being the object id (`event_id`, `message_id`, `activity_id`) a call must carry to be merged; the loop reads it by LLM-visible name, so an instance-suffixed tool keeps it. Declared today on `update_microsoft_calendar_event`, `update_google_event`, `update_microsoft_channel_message`, `update_microsoft_chat_message`, `edit_teams_bot_channel_message` and `edit_teams_bot_group_chat_message`. `patch` (calendar updates, where an empty field means unchanged) lays the later non-empty values over the earlier ones and unions `attachment_file_ids`; `replace` (Teams message edits, which send the whole message) keeps the last call's arguments. A call of the round that names the same object in between (a read, a delete) closes the group, so it still sees the writes before it. The leader is a copy: the assistant message keeps the arguments the model wrote. Every absorbed call is answered by the loop, tagged `not_run="coalesced"`, its `tool_done` event carrying `coalesced_into`, and counted by `_record_breaker_answer`. Fleet-wide behind `SELF_VERIFICATION_LOOP` (default on); no read tool is ever touched. The post-write read-back (3i) runs on the same flag.

## 3h. Duplicate-send guard (`app/tools/send_guard.py`)

Right after write coalescing, every call of a tool declaring `ToolDefinition.send_guard = SendGuard(recipients=..., body=...)` is fingerprinted: the tool's executor name, the recipient set (the declared arguments' values split on commas, lower-cased, sorted) and a SHA-256 of the declared body arguments. A call matching a send that SUCCEEDED earlier in this run (`SendLedger`, per run), another call of the same round, or a send of the same agent in the last 10 minutes (Redis `send_guard:<agent_id>:<fingerprint>`, TTL 600 s, the agent bound by `send_guard.bind_sender` in `run_agent_chat`) is answered by the loop with the earlier call's id, tagged `not_run="duplicate_send"`, its `tool_done` carrying `duplicate_of`, counted as a refusal (no failure streak) and audited (`duplicate_send_refused`, actor `system:send_guard`). `allow_duplicate: true` lets the call through, audited `duplicate_send_allowed`, the flag stripped before the tool runs. A failed send is never recorded; another recipient or one byte of body difference is another send; an unreachable store fails open. Declared on `send_gmail`, `send_microsoft_email`, `send_microsoft_channel_message`, `send_microsoft_chat_message`, `send_teams_bot_channel_message` and `send_teams_bot_group_chat_message`; the mail tools' per-thread `force_duplicate` guard (`mail_send_guard`) stays as it is. Fleet-wide behind `SELF_VERIFICATION_LOOP`, no per-agent setting. `tests/test_send_guard.py`.

## 3i. Post-write read-back with a consistency block (`app/tools/read_back.py`)

After a write tool declaring `ToolDefinition.read_back = WriteReadBack(kind=..., ...)` succeeds (not an error, not a `no_op`), the loop appends to its result a `read_back:` block, the object as the system now shows it, and a `consistency:` block, the anomalies of the run. The object id is the first `identity` argument, else the first group of `id_pattern` in the result (a create). With a `read_tool` (same integration, its instance suffix kept), the harness reads the object and keeps the `fields` lines (`Start`, `End`, `Location`, `Attendees`...) and a SHA-256 prefix of the `body_label` section, never the body itself; without one (a sent message cannot be read again) the block is the call's `recipients`, its `shown_arguments` and the body hash. Anomalies, in `ReadBackLedger` (per run): `same_object` (the object written N times in the run), `burst_send` (N sends to the same recipient set within 120 s), `near_duplicate` (a text of the same kind more than 90% identical, `difflib` ratio, to an earlier one), `overlap` (with an `overlap_tool` answering `structured` events over the window, an invitation overlapping another busy event of the organizer). The reads share a 1.5 s budget (`READ_BACK_TIMEOUT_S`) and fail open: a slow or failed read adds one line and the write's own result stands. The block is capped at 1,200 characters. Declared on `create_microsoft_calendar_event`, `update_microsoft_calendar_event` (with overlap), `create_google_event`, `update_google_event`, `send_gmail`, `send_microsoft_email`, `send_microsoft_channel_message`, `send_microsoft_chat_message`, `update_work_item` and `edit_presentation`; the generic module names no tool (invariant 18). Fleet-wide behind `SELF_VERIFICATION_LOOP`, no per-agent setting. `tests/test_write_read_back.py`.

## 3f. The stuck-loop breaker and the step-budget nudge (`_LoopBreaker`)

A stuck run repeats a call (a re-read of the same file, a no-op edit) until the iteration budget or the failure brake ends it. Three deterministic guards stop it earlier, with zero prompt characters, all sized by `AGENT_LOOP_*` settings (`0` disables each):

1. **Identical calls** - `_LoopBreaker.screen()` counts `(tool, canonical arguments)` per turn, right after `_valid_calls`: at `agent_loop_identical_call_warn_after` (3) a system nudge is injected before the next model call (`_LOOP_BREAKER_IDENTICAL_NUDGE`: "You have called <tool> with identical arguments N times and received the same result. Stop and either change approach or report to the user."); from `agent_loop_identical_call_refuse_after` (5) the call is REFUSED - the refusal is a tool message (`_format_loop_breaker_refusal`), tracked as an error, a `tool_done` event flagged `loop_breaker`, and a `loop` observation in the trace (`langfuse_tracing.start_loop_span`, `observation_kind: "loop"`). A refused call still counts, so the numbering keeps rising instead of a warn / refuse ping-pong. The deterministic digest leaves refusals out (the loop tags them `ChatMessage.not_run = "loop_breaker"`): a call that never ran is not completed work.
2. **Near-identical calls** - the same target (`_LOOP_BREAKER_TARGET_ARGUMENTS`: `file_id`, `url`, a `file:<uuid>` / `[[FILE:id]]` spelling folded to the id) with different `max_chars` / `offset` / options is the second ledger (`agent_loop_similar_call_warn_after` 6 / `..._refuse_after` 10). A WRITE tool call that TOOK EFFECT resets the keys of every tool that is not a write BY ITS NAME (`after_write()`, keyed on `_is_named_write()`, never on the fallback classification - a check whose verb the classifier does not know, `capture_presentation_slides`, `workset_next_pending`, `computer_screenshot`, a camelCase or kebab-case MCP name, is still a check, so each edit resets the count of the capture that verifies it (edit, capture, edit, capture is never one repeated capture); the tools that wrote in the step keep their own keys, so an unknown-verb write repeated identically is still caught - the file may have changed; a tool whose name reads as a write but which CHECKS what the other writes change declares `ToolDefinition.recheck_after_write` (`sandbox_run_command`: a lint or test run on the workspace the edit tools change) and starts over like a check after every other tool's write (`_LoopBreaker(rechecks=...)`), so run, edit, run is never one repeated run, while its own repeats with nothing edited between them still escalate (#175); a failed or timed-out write and a `ToolResult.no_op` result - `edit_presentation`'s `No change` - mutated nothing and keep the counts, or a run of no-op probes between identical reads would launder them) - except a write by a stateful tool (`_loop_breaker_write_resets()`: the classifier reads `browser` as a write because it can submit a form, but a step of the agent's own browsing session mutates none of the files a read re-reads), a stateful tool (`_LOOP_BREAKER_STATEFUL_TOOLS`: `browser` and its runner twin `browser_control`) resets its OTHER argument sets in both ledgers, with their warnings, after every call, and the exempt tools (`_LOOP_BREAKER_EXEMPT_TOOLS`, `WAIT_TOOL_NAMES`, the `_DEDUP_EXEMPT_NAME_HINTS` polling names and the tools declaring `ToolDefinition.live_state` - an unchanged argument is their contract) are never counted. A name hint exempts a tool only when the classifier does not read it as a write BY NAME (`_is_named_write`: a write override or a write token, never the unknown-name fallback that would call `poll_job` a write) - `set_slack_user_status` / `update_openaev_run_status` repeated with identical arguments are counted like any other write.
3. **Step budget** - at `ceil(max_iterations * agent_loop_step_budget_nudge_fraction)` (0.6) ONE system message names the top three tools by call count (`_format_step_budget_nudge`) and asks the model to finish or report; it yields to the wind-down when that fires at or before the same iteration.

**A count is the number of asks whose answer the model STILL HAS.** Every screened call is an `_Ask` that keeps the tool message answering it (`record_answer()`, called by `_record_breaker_answer(tc)` right after EVERY `messages.append` of a counted result: executed, replayed from the dedup cache, timed out, raised or refused - the refusal is its own ask's answer). `screen()` first forgets the asks whose answer the HARNESS has since taken away - the body replaced by the tool-result curation's re-fetchable stub (`_is_refetchable_stub`: a full match of `_REFETCHABLE_STUB_TEMPLATE`, the `[Earlier {tool} result{target} ({chars} chars) cleared ... it is stale and re-fetchable. Re-call the tool only if you still need this exact data.]` stub of a TEXT result and ONLY that one (`{target}` is ` for path=..., offset_line=...` built by `_tool_call_target` from the addressing arguments of the call, or empty, so the model re-reads the cleared window alone), written and matched from the one template so the two cannot drift - and only when the body CHANGED since the tool answered: `_Ask.answer_len` remembers what the tool returned, so a stub-shaped body the tool itself produced is its answer, not a clearing, and never forgives) or the message object dropped from the transcript (semantic compaction, the emergency prune's eviction phase) - in both ledgers, re-arming the one-shot warning when a key empties. Everything else is HELD: an ask no site recorded (fail-closed: a missed hook makes the breaker stricter, never looser), an answer pruned or truncated IN PLACE (`[Pruned ...]`, `[Truncated ...]` - the same message object, still in front of the model), and an ask the breaker REFUSED whatever later happens to the refusal (`_Ask.refused`: the curation can stub a `similar`-shape refusal quoting a long URL, compaction can drop it; neither hands back data a re-call would restore, and forgiving it would restart the key at one with a fresh run to the bound). Without it, a run whose earliest results the curation cleared would be warned, then refused, for re-reading them as the stub told it to, for a result that is gone. A file-bearing result's stub (its recovery path is `read_file_content`, never a re-call), a `[Duplicate ...]` and a `[Pruned ...]` stub invite nothing and keep counting. What bounds a model that re-reads cleared files for as long as it may, with no dedup cache to replay them, is therefore the step budget, never the breaker: with ONE file re-read the collapse pass (`_collapse_redundant_tool_results`, which runs before the clearing) folds the older identical bodies into `[Duplicate ...]` stubs that stay counted and the fifth ask is refused as before; with several files alternating, every re-read is the one the harness invited and executes, and the 60% nudge, the wind-down and the tool strip end the run at `max_iterations` (`tests/test_loop_breaker.py`, the two `test_with_the_cache_off_*` runs). The user-visible line (`_format_loop_breaker_user_warning`, a `thinking_text` frame) names the tool, the count and the shape - `'get_github_file' has been called 3 times with identical arguments this turn.` - like the failure brake's and the near-duplicate guard's do; never a bare "the same tool call is being repeated".

**A page is not a repeat, and still has a bound.** Every ask records the POSITION it read in its target (`_loop_breaker_page()`: for a tool of `_LOOP_BREAKER_TOOL_POSITION_ARGUMENTS` its own arguments - `query_file_json`'s `path` / `block`, so ten JSONPaths of one plan are ten questions, worded as queries in the messages (`_LOOP_BREAKER_PART_NOUNS`); otherwise the first of `_LOOP_BREAKER_PAGING_ARGUMENTS` - `offset`, `start_index`, `skip`, `page`, `cursor`, `page_token`, `after`, ..., matched with case, `_` and `-` ignored so an MCP server's `startAt` / `pageToken` counts, an empty value skipped - as a number (a negative one reads the start) or an opaque token; `start` only as a number (`_LOOP_BREAKER_NUMERIC_ONLY_PAGING_ARGUMENTS`), a date / date-time value never, whatever the argument is called (`_LOOP_BREAKER_DATE_RE`), since a time-range scan asks a new question each call instead of paging one document; a call naming none reads `_LOOP_BREAKER_IMPLICIT_START`). A call naming a position that NO held ask on the same target read is a PAGE: `read_file_content(offset=0)`, `(offset=50000)`, `(offset=100000)` is one file read front to back, not one target read three times, so it skips the `similar` ledger. Re-reading a held position, or varying only `max_chars` at one offset (the cache-defeat shape), is a `similar` repeat as before, and the `identical` shape is untouched. The exemption composes with the held-answer rule instead of adding a second forgiveness: a page whose answer the harness took away is dropped from the page ledger like any ask, so its position is free and the re-read the stub invited is a page again. A REFUSED ask holds no position (`_position_held` skips it - a refusal read nothing), so the retry of a refused page is the next page and is refused in turn, never routed to the low `similar` count and run. What bounds a page series is the page ledger's COUNT - the pages the target served this turn, monotonic and never forgiven (an endless cursor whose older pages the curation clears would otherwise never reach any bound), reset only by a write or a stateful tool's switch like the other ledgers - warned at `_LOOP_BREAKER_PAGE_BUDGET_FACTOR` (3) x `agent_loop_similar_call_warn_after` (`_LOOP_BREAKER_PAGE_NUDGE`, `kind="page"`) and refused at 3 x `agent_loop_similar_call_refuse_after` (`_LOOP_BREAKER_PAGE_REFUSAL`); neither text claims the result would not differ, because a new page does differ. `read_file_content` has its own, much tighter per-file window cap on top (`AGENT_LOOP_READ_WINDOWS_PER_FILE`, the file tools in `dev-docs/reference/backend-services-tools.md`).

**A tool declares which arguments address a part of its target.** `ToolDefinition.position_arguments` names them (`save_video_frame`: `at_seconds`, `at_step`, `region`), read by `_declared_positions(tools)` when the loop builds its breaker: each distinct combination is a position of the call's target (its `file_id` / `url`), so it lands on the page ledger instead of the similar one - thirty frames of one MP4 at thirty moments are thirty questions, while the same frame asked again is still a repeat (the identical ledger, unchanged). A structured value (a region box) is compared canonically, so two key orders are one position. `ToolDefinition.position_budget` replaces the default page budget for that tool (warned at the same share of it as the default: 36 of 60), and the messages call one part a "position". No tool name is read by the loop: a tool that needs it declares it, as `query_file_json` would (its entry in `_LOOP_BREAKER_TOOL_POSITION_ARGUMENTS` predates the declaration).

The dedup cache (CORE-6) answers an identical call from cache; the breaker is what stops the model asking. The cache never answers a poll: an entry older than `_DEDUP_CACHE_TTL_S` (120 s) is dropped and the call runs again, and a pause that really waited (the explicit `wait`, a deferred wait after sibling tools, the implicit park, a wait-only round) clears the whole cache, the near-duplicate counts and the breaker's read counts (`_forget_reads_after_pause`), so a CI watch or a merge read-back across a `wait` reads live state. A replay names its age in the header (`Read N s ago.`). A tool that reads state other actors move with time (a pull request, its checks, a CI run, a work item) declares `ToolDefinition.live_read`: its cache entry lives `_LIVE_READ_WINDOW_S` (30 s) instead of 120 s, and the breaker forgets an ask of it older than that window (`_LoopBreaker._forget_aged_asks`), so the same PR read minutes later in a babysitting run is never replayed or refused, while the same read seconds apart is still warned and refused (#11488). A result flagged `ToolResult.transient` (a state the source is still computing: GitHub's `unknown` mergeability in `get_github_pr` and `list_github_pr_states`) is never cached, so the next read executes. Never turn a no-op tool result into an error to "stop the loop" - a no-op says so in one line, flags itself `ToolResult.no_op=True` (so the breaker counts it AND does not take it for a mutation that resets the read counts) (`edit_presentation`'s `No change: ...` results, `presentation_patch.PresentationPatchNoChangeError`), and never withdraw a tool for repeated no-ops: the failure brake (`_TOOL_FAILURE_BRAKE_THRESHOLD`) is for FAILURES. A tool whose calls act on one session each call changes (the built-in browser) declares `ToolDefinition.ordered_calls`: in a round of parallel calls, its calls run one after another in the order the model sent them (`_call_order_chain`, `_in_call_order`), the round's other calls still in parallel, and a failed call releases the next one. A tool whose one call does long work by design declares `ToolDefinition.execution_timeout` (seconds): it replaces the per-tool timeout (`TOOL_EXECUTION_TIMEOUT_SECONDS`, 300 s) as the agent tools' 900 s does, still capped by the run's wall-clock deadline (`_tool_timeout_for`); the grounded STIX extraction declares 1,800 s (tens of model calls per report). A tool that calls a model itself reserves each call's worst case through `ToolModelSpend.reserve` before it is made and releases it once `record` debited the usage, as the loop's own calls do, so calls it makes at once cannot together outspend the run.

A failure that belongs to ONE TARGET of a tool is not the tool's either. When a host throttles the platform (HTTP 429 to `fetch_image_asset`), the tool remembers the host, refuses it without a request until its `Retry-After`, and flags each such result `ToolResult.target_throttled=True`: `_track_tool_result` then applies neither the rate-limit cooldown (`is_rate_limit_error`, which would withdraw the tool for EVERY host for `_RATE_LIMIT_COOLDOWN_ITERS`) nor the failure streak (one parallel batch of refusals reached the brake and withdrew every tool of the turn), while the result stays an error. A multi-target tool that meets a per-target throttle uses the same flag; it never words its error to dodge the classifier. Those two are ALL it exempts: the result is still an error in the trace, the `tool_done` event and the activity signal, is never cached (the dedup cache stores successes only, so an identical call after the host reopens runs again), leaves a streak of genuine failures where it was, and the loop breaker still counts it (the same throttled URL asked again is warned at 3 and refused from 5, and those refusals do count toward the brake). There is deliberately no per-turn bound on throttled refusals of DIFFERENT targets: each is instant, sends no request and names the host, the time and the alternative, a bound that withdrew the tool would bring back the tool-wide reaction for the other hosts, and `max_iterations`, the per-run budget and the step-budget nudge already bound the turn.

A failure that is the OUTCOME of a right call is the call's, not the tool's. A tool whose call ran and whose work came out rejected - a paid generation the provider refused, or a check of the platform failed (`generate_video_clip`'s text / content drift or "screen lost", `generate_music`'s failed track, `generate_image`'s provider failure) - flags its result `ToolResult.outcome_failure=True`: `_track_tool_result` then counts it per CALL (`outcome_error_counts`, keyed by `_dedup_key`: the tool and its canonical arguments) toward the repeated-failure nudge and the brake, never in the tool's own streak, and applies no tool-wide cooldown. A retry the model fixed (another prompt, another model, a corrected `quad`) starts its own count; the same call rejected four times still brakes. A cumulative backstop counts the same results per TOOL whatever their arguments (`outcome_tool_streaks`): `_OUTCOME_FAILURE_BRAKE_THRESHOLD` (8) of them with no success of that tool in between wind the turn down like the brake, saying how many paid attempts came out rejected; a success of the tool resets both counts. The Metabase grind the brake was built for keeps its per-tool streak: an SQL error is a wrong call, not a rejected outcome.

A call the tool itself TURNS DOWN for a validation reason is not a runtime failure either. A tool that checks its arguments or the user's permission, changes nothing and says what to do instead (the deck tools: `generate_presentation`'s spec errors, `edit_presentation`'s patch refusals, a read-only deck, `delete_presentation` on a deck the user does not own - all through `builtin_tools/presentation._refusal`) flags its result `ToolResult.refused=True`: `_track_tool_result` then leaves it out of the tool's streak, the repeated-failure nudge, the cooldown and the brake, which only runtime errors feed (an exception, a crashed save, an upstream error). It stays an error everywhere else - trace, `tool_done`, never cached - and the loop breaker still counts it: the same refused call asked again is warned at the third ask and refused from the fifth, and THOSE refusals count, so the nudge withholds the tool. A probe that is not an edit at all is a no-op, not a refusal (`replace_text` with `find == replace` answers `No change` and names `search_presentation_text`). Opt-in per result: a tool flags only what it refused on purpose, never an error it could not classify.
