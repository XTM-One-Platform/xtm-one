# Core concepts and visibility

The root `AGENTS.md` keeps one line per entry, because every agent session loads it; this file holds the full contract. Add detail here, never to `AGENTS.md`.

## Core Concepts

| Concept            | What it is |
| ------------------ | ---------- |
| **Agent**          | A named, configured AI entity with a persona, integrations, tools, knowledge bases, and assignments. The primary user-facing entity. Can override the platform LLM model. Supports `disable_chat` to hide from chat/proxy while keeping assignments active. Has a configurable `output_format` (`markdown`, `html`, `json`, `plain_text`) that is auto-overridden per channel. Handover targets have typed relationships via `handover_types` (`delegate`, `consult`, `transfer`). `allow_self_fanout` (default on) lets it delegate to parallel background copies of itself. `integration_read_only` (`{provider: [integration_id]}`) marks bound integrations whose write tools are withheld and refused at run time (`services/integration_read_only.py`). `integration_signatures` (`{integration_id: {signature_mode, signature_integration_id?}}`) overrides the Email signature setting of a bound email-sending integration for this agent (`services/email_signature_settings.py`). Bound knowledge bases (`knowledge_base_ids`) are all readable; per-KB write access is granted via `knowledge_base_permissions` (`{kb_id: "read"\|"write"}`) — a `write` grant gives the agent the `store_knowledge` and `update_knowledge_document` tools for that KB in both chat and assignments — unless the KB itself is `is_read_only`, which overrides any grant. Supports `is_public_catalog` for Filigran AI Catalog publishing. |
| **Assignment**       | An automation rule attached to an agent. Defines: trigger (schedule, webhook, integration event, manual), prompt, delay, tool access, and output behavior. Supports custom prompt overrides for activation gate, AI label, and human-in-the-loop modes. Knowledge base access refines the agent's config (like tool/integration scoping): `read_knowledge_base_ids` (null OR `[]` = inherit all agent KBs — read has no "none" state, an empty/all-stale selection falls back to all; subset = refine) and `write_knowledge_base_ids` (null = inherit all agent-writable KBs, `[]` = none, subset = refine). |
| **Flow**           | A **visually composed** automation graph, authored on a canvas at `/flows/library/:id` and stored as a single JSON document (`{nodes, edges, viewport}`) on the `flows` table. Node kinds — triggers, agents, conditions, actions, integrations, utilities — are declared server-side in `app/services/flow_catalog.py`, which is the single source of truth the validator AND the builder UI both read (the builder renders its library panel and every config form from `GET /flows/node-catalog`, so the two cannot drift). A step's destination may be an **agent or another flow** (`flow.call`) — the explicit form of the composition an agent handover already expresses — so a chain can be composed instead of inlined. A call that loops back is reported as a warning, not refused: the fleet's assistants genuinely hand work to each other in both directions, and the runner will need a depth limit for the same reason the agent layer already does (`app/services/flow_references.py`). Edges are typed (`data`, `handover`, `condition_branch`, `error`) and a connection is only legal when the two ports' channel types intersect. Config fields may reference an **upstream** node's published outputs with `{{node_id.output_field}}`, validated at save time rather than at run time; the first segment after the node id must be a declared output and the rest is a path into its value. Each declared output carries a `type` (`OutputVariable.type`: `text`, `number`, `boolean`, `object`, `list`, or `any`), and a path into a `text` output warns (`ref.text_path`): it always renders empty. An agent node that answers in JSON (its `output_format`, or a wired `capability.structured_output`) with an object also publishes it parsed as `fields`, the Script node's contract. The builder's autocomplete and the drawer's Input data tree offer the paths below each output, from the declared structure (agent output schema, manual-trigger parameters, event-type fields, resolved server-side by `POST /flows/output-schemas` with the run's own rules and the caller's visibility, `app/services/flow_output_schemas.py`) merged with the flow's last run (`frontend/src/pages/flow-builder/output-shapes.ts`); the existing `{{var_id.UUID}}` and `{{trigger.*}}` prefixes belong to the assignment renderer and are left alone. Every save snapshots a `FlowVersion` (last 20 kept; restore is non-destructive). Import/export covers the native JSON format and, best-effort, **LangFlow** and **n8n** exports — components with no local equivalent land as `unresolved` nodes keeping their original payload, and the import report always states how many. An n8n node that maps but could not be carried over faithfully (a JavaScript expression, credentials, an operator with no local twin) keeps its kind and branches and lists why under `source_payload.review`: the validator warns (`node.import_review`, the draft still saves), activation is refused, and the walker refuses to execute the node — a trigger at the start of the run, an agent whose wired capability node carries notes, past its error edge too — until the notes are cleared (`flow_graph.pending_import_review`, `FlowWalker._import_review_refusal`, `app/services/flow_import_n8n.py`). The importer writes no `{{...}}` it did not resolve itself: every converted config is made inert (`_inert_value`) before its references are written, so a document cannot plant a `{{var_id.*}}`. Three-tier visibility. Deriving flows automatically from the agents' `handover_agent_ids` was built and then removed: the mapping could not be made precise enough to be trusted, and migrating an existing fleet is done by hand. **Phase 2 executes flows** through a dedicated `flow` orchestration adapter (durable FSM, one execution per run): a sequential, deterministic walker journals every node into `flow_run_steps`, conditions evaluate the catalog's nine operators (no LLM — unlike `mandatory_transfer` routing), and waits (`util.delay`, sub-flows, triggered assignments) park the execution with a scheduled self-resume. Loops (`util.loop`, `util.while`) advance when the queue drains, and they nest: the drain advances the innermost unfinished loop first (the one armed last), and a finished loop reached again starts afresh only when a loop it runs inside (one unfinished when it was armed, recorded in its `enclosing` cursor entry) has moved to another pass since, so an inner loop runs its body on every pass of the outer one while an edge back into a finished top-level loop (a merge-joined back-edge, a wire from `done`) stays ignored (`FlowWalker._innermost_unfinished_loop`, `_enclosing_pass_moved`). All four triggers are live: manual (`POST /flows/{id}/run`, drafts included), cron (the 60s scheduler tick, timezone-aware), inbound webhooks (`/api/hooks/flows/{id}/{path}`, HMAC secret minted on activation and shown once), and polled integration events. Selecting an agent in the builder can materialize its declared handovers as agent nodes + typed `handover` edges (the visual form of what it already delegates at runtime, idempotent, one level). An agent node keeps its declared handovers **inside** the node by default (`allow_handover` per node) — the flow decides what runs next, the agent still delegates freely within its step, so the two systems run side by side. **Capability nodes** (tool / integration / skill / knowledge base) wire into an agent node's `capabilities` port and EXTEND what that agent carries for this flow's runs only — one capability node may feed several agents, which is how capabilities are shared; under the hood they ride the same `session_*_ids` mechanism chat sessions use, as a union with the agent's own. Automatic triggers run as the flow's owner; company-managed flows without an owner only run manually. Activation is an explicit gated act (`POST /flows/{id}/activate`: zero validation errors + at least one trigger). |
| **Flow Shadow**    | A sandbox flow copy measured on an assignment's live triggers (`flow_shadows` / `flow_shadow_pairs`): each live run is paired with an intercepted run of the copy and the outputs compared. After an approved `agent_to_flow` proposal the shadow runs `flow_shadow_days` (3), then the production flow is created from the copy, activated and the assignment paused (`concierge_switch_over`); the `flow_watch_days` (7) watch rolls it back on a live regression (`services/health/flow_shadow.py`, `flow_switch_over.py`). Not shareable: who reads a shadow is who may experiment on its assignment. |
| **Agent Template** | Pre-built agent configuration for common use cases (Mail Desk, Support Relay, Channel Monitor, News Monitor, GitHub Sentinel, Social Media Manager, Deal Desk, HR Operations, Compliance Watchdog, SEO Research Analyst). Users create agents from templates or from scratch. |
| **Integration**    | A labeled connection to an external service with all credentials stored encrypted in the DB (not env vars). Supports an optional `description` field that is surfaced to agents as context for integration tools. An integration whose tools send email has an Email signature setting, `signature_enabled` (default true) and `signature_integration_id` (NULL = picked automatically; `services/email_signature_settings.py`). `uses_admin_oauth_credentials` records whether its OAuth app credentials were copied from the admin's OAuth defaults at creation (`True` only there, `False` on every other insert and once the client id is replaced or the integration leaves OAuth, `NULL` = created before it was recorded). Both edit paths (the REST and agent-builder `update_integration`) replace a client id through `replace_oauth_client_id()` (`services/integration_state.py`): a different id is a different app, so it also clears the tokens issued to the previous one and leaves an OAuth integration `configured` until it is authorized again, while the same id or a secret-only rotation changes nothing. An API key is bound to its address the same way when the provider's catalog entry declares `api_key_bound_to` (`{"field": <extra field>, "default": <address an empty field means>}`; the XTM Hub does): a new address, or a switch to `none`, without a new key forgets it (`api_key_binding_of()` read before the edit, `forget_key_bound_elsewhere()` after, same module), so a `config` grantee cannot send it to a host of their choosing. The frontend reads the column through `usesAdminOAuthApp()` (`pages/integration-detail/admin-oauth-app.ts`, which also reads the pending edit; `createsOnAdminOAuthApp()` answers for the creation form), and the API answers a `NULL` row from its stored client id compared with the provider's current OAuth default (`uses_admin_oauth_app()` in `services/integration_state.py`, the one rule behind `_effective_uses_admin_oauth_credentials` in `api/v1/integrations.py`, the provider-level webhook, the LinkedIn notifications and the Slack signing secrets), so the frontend falls back to the provider-wide `has_oauth_defaults` only when that cannot be read - never key a per-integration decision on the provider-wide flag. |
| **Channel Bot**    | A standalone messaging platform bot configuration (Slack, Teams, WhatsApp, Telegram, Discord, Google Chat) with encrypted credentials. Separate from integrations — channel bots use bot tokens (not OAuth) and have independent receive/publish channel whitelists. Supports `is_company_managed`. Has `allow_anonymous` flag for processing messages from users without a Copilot account. Has `allow_private` flag (default true) to let private/DM conversations bypass channel restrictions. Has `only_mention` flag (default false) to restrict the bot to only respond when explicitly @mentioned in group channels. |
| **Agent Account**  | An agent operating a real user account of a messaging platform through that account's delegated OAuth integration - not a bot. `on_behalf` (a delegate answering for a person) or `ai_user` (a service account that IS the agent). Ordered rules (conversation types, specific conversations, focused people or XTM One groups, excluded people, mention or every message, always reply or AI decides, and an access block narrowing the agent's integrations, knowledge bases, MCP servers, tools, skills and memory for that audience), response mode `auto` / `approval` / `shadow`, an AI label applied in code, grace period, owner takeover, hourly limit, active hours. One enabled account per integration and per platform account. A turn acts as the account (its integration pinned, the sender as interlocutor). Owner-only (admins reach all). Contract: `dev-docs/reference/agent-accounts.md`. |
| **Knowledge Base** | A vectorized document collection used by agents for RAG (semantic search). Tracks `query_count` for usage analytics. Beyond chunk retrieval, the original source of each document is readable verbatim (`get_knowledge_document`) and updatable with an automatic re-embed (`update_knowledge_document`). `is_read_only` locks the collection's content as ground truth — still fully searchable, but no agent (and no ad-hoc edit) can change it, whatever per-agent write grants say. See "Knowledge Bases (RAG)" below. |
| **MCP Server**     | An external tool server (Model Context Protocol). Agents use MCP tools during assignment execution. Supports `hide_from_chat` to exclude from chat tool pickers while remaining available for agent configuration and assignments. Supports `is_public_catalog` for Filigran AI Catalog publishing. Remote transports authenticate with static headers or OAuth 2.1 — and OAuth needs **no pre-provisioned `client_id` / `client_secret`**: with the credential fields empty, `app/services/mcp_oauth_discovery.py` resolves the authorization server from the server URL (RFC 9728 protected-resource metadata -> RFC 8414 / OIDC authorization-server metadata), registers this platform dynamically (RFC 7591) to mint a client, and runs Authorization Code + PKCE in the browser through the shared `/api/oauth/callback`. An Authorize + Token URL pair typed by hand always wins over what is discovered, and is enough on its own (the registration endpoint is then looked up at that authorization server). Discovered endpoints must be HTTPS (loopback may be plain HTTP); a dynamically registered client is disposable and re-registers itself when the server answers `invalid_client`. Kill switch: `MCP_OUTBOUND_DCR_ENABLED`. A short-lived token stays usable: `Authorize` adds `offline_access` to the scopes when the authorization server advertises it, before a client is registered (`ensure_mcp_oauth_client`; Okta, Entra ID and Auth0 issue a refresh token only on request, and an MCP server does not advertise that scope itself; a client registered without it keeps its scopes; it reads the client name, then releases the DB connection before its discovery and registration requests), a token response without `expires_in` takes a JWT's `exp` (`apply_oauth_token_expiry`, bounded to a year, a past `exp` stamped as expiring now), and a connection sends the freshest stored token on every request through the transports' `httpx.Auth` hook (`services/mcp_oauth_tokens.py`), refreshed when about to expire and once after a `401` that is not `insufficient_scope`, on top of the 60-second sweep. That refresh goes through the server's relay group like the sweep's, and runs to completion even when the connection is cancelled (`core/cancellation.run_to_completion`): the rotated refresh token exists nowhere else. A `401` challenge is followed rather than guessed at: its `WWW-Authenticate: Bearer resource_metadata="…"` URL is parsed, persisted on `oauth_metadata_url` and preferred over every well-known probe (RFC 9728 lets it live where no probe would look). Recovering that 401 needs a **direct probe** — the MCP SDK's transport task group consumes the HTTP error and cancels the request, so `initialize()` raises a bare `CancelledError` with no status code in the chain; `diagnose_auth_after_connect_failure` lifts that (spurious) cancellation, probes, and deliberately does *not* re-apply it once a 401 is confirmed, or the caller's next DB write dies. Connectivity tests therefore have **three** outcomes, not two: `auth_required` is returned both for a 401 and for a server that lists tools happily but publishes protected-resource metadata while no credential is held — the "green test, then `Authorization required` on every call" trap. Not to be confused with the *inbound* DCR registry (`app/api/v1/mcp_oauth.py`, `MCP_DCR_ENABLED`), where this platform is the authorization server. `transport` is one of `stdio` / `sse` / `streamable_http` and `auth_mode` one of `headers` / `oauth` (422 otherwise). A remote server's URL is held to the **MCP server URL policy** (`app/tools/mcp_destinations.py`, security options `mcp_server_url_policy` = `permissive` (default: cloud metadata refused) / `private_networks` / `public_only`, and `mcp_server_trusted_origins`): on save in the request models (syntax, a literal or shorthand metadata address) and in the routes through `helpers.require_allowed_mcp_server_url` (every address the name resolves to; a name that does not resolve is accepted) - form create/update, bundle and configuration import, agent import, agent builder; and on every connection - the MCP SDK client factory, `probe_auth_challenge`, OAuth discovery and registration - through `core/pinned_transport.py`, which resolves once, checks every address and connects to a checked one (Happy Eyeballs over the checked list), each redirect hop included; under `permissive` only, an environment proxy for the URL is still used after a metadata check on what the URL spells and resolves to here. An update re-judges the URL only when the URL, transport or relay group changes. A relay-routed server is judged only on what its URL spells. Refusals answer `REFUSED_DETAIL`; the reason is logged only. |
| **Custom Tool**    | A user-defined tool with input variables and a JavaScript or Python function. Executed in a hardened Docker sandbox when available (`CUSTOM_TOOL_SANDBOX`, default `auto`) with a sandboxed subprocess fallback. Agents can bind custom tools alongside MCP servers. Supports `hide_from_chat` to exclude from chat tool pickers while remaining available for agent configuration and assignments. Supports `is_public_catalog` for Filigran AI Catalog publishing. Declares tests (`test_cases`, `test_code`; `services/custom_tool_tests.py`): data cases and stdlib test code run in the same sandbox (`POST /custom-tools/{id}/run-tests`, last full run kept in `last_test_*`). Every run receives `dry_run` (`execute_tool_auto`), false for an agent's call: a contract the tool honours, not a sandbox guarantee. A tool with a `source_id` is synced from a Custom Tool Source: its content fields are read-only on every write surface (`helpers.source_managed_custom_tool_error`) until detached. |
| **Custom Tool Source** | A GitHub or GitLab repository (+ ref, sub-directory, optional bound integration) whose `tool.yaml` directories become custom tools (`models/custom_tool_source.py`, `services/custom_tool_sources.py`, `dev-docs/custom-tool-sources.md`). A tool's identity is its directory (`CustomTool.source_path`); a new or changed version is activated only when its declared tests pass, a removed one is disabled, a detached one (`detached_paths`) left alone. Owner-only, or company-managed (admins; set at creation, never changed) producing company-managed tools. Synced manually or on `sync_interval` by the autonomous loop. |
| **Assignment Run**   | A single execution of an assignment, tracked with status, actions, and results. A failed run also carries a **structured failure cause** — `failure_cause` plus `failure_determination` (`structural` / `heuristic` / `unattributed`), written by the single classifier in `app/services/failure_causes.py`. `error` stays the free text a human reads; the cause is what a query groups by, so "what is failing on this install, and whose fault is it?" is answerable without reading error strings one at a time. `unknown` is an explicit, displayed value rather than a silent default. A `completed` run whose agent loop stopped before the task was done carries `stop_reason` (`max_iterations`, `deadline`, `budget_exhausted`, `degenerate_repetition`, `timeout`, `waiting_on_tasks` - `agent_loop.UNFINISHED_STOP_REASONS`), NULL when it ended on its own terms; it keeps its answer and is shown as a partial result, never as a failure. A run whose integration calls failed authentication carries `integration_auth_failures` (`[{integration, status, first_tool, tools, readable}]`, `app/services/integration_auth_guard.py`); when none of the integrations it called was readable (401 rejected, or 403 on every call, whose calls stop after `FORBIDDEN_FAIL_FAST` forbidden tools) its `stop_reason` is `integrations_unreadable`: `get_run` and `list_runs` print a degraded marker and the failures, a JSON-output agent's result gets a `_coverage` key, and the CTEM stage assessment and exposure briefing reads never take such a run as their artifact and answer `not_assessable` (#1589). A run that continues another (delegation child, follow-up, chained run, retry) is never more visible than it and never runs as a user who could not open it: `continuing_run_is_company_managed()` and `can_open_continued_run()` in `api/v1/helpers.py`, applied by `trigger_assignment(continues_run=...)`; a chain or retry refused on that ground is reported to the assignment's owner alone, never dropped silently (`dev-docs/reference/backend-api-patterns.md` > "Continuing runs"). |
| **Channel**        | A messaging platform adapter (web, web_embed, Slack, Teams, WhatsApp, Telegram, Discord, Google Chat) for chatting with agents. New agents default to web chat only — external channels (Slack, Teams, WhatsApp, Telegram, Discord, Google Chat) must be explicitly enabled per agent. Embedded chat (`web_embed`) is used by the public chat widget. A conversation keeps the channel it started on and stays ONE record across channels (`services/channel_continuation.py`): an identified user's Slack DM thread or Teams personal chat is listed and continued on the web, and a conversation the web continues can be bound to a direct-message thread of the Slack or Teams bot (`ConversationChannelBinding`, owner-only, read by the router for that owner's own messages only); group threads, anonymous conversations and the other channels are never continued across surfaces. One turn runs at a time: a Slack / Teams direct message that finds a turn running is queued and answered as the next turn. |
| **Sub-Agent Task** | A background task delegated from one agent to another. Parent agent continues while the target agent works asynchronously. |
| **Annotation** | One user's thumbs up / down (+ optional comment) on a piece of agent work: a chat message, an assignment run, a background task, a delegation, an agent account's answer (`agent_account_reply`, owner + admins). A reaction on an agent account's answer in its platform is a rating too (`services/reaction_feedback.py`): its rater is a keyed digest (`rater_ref`, no `user_id`, exactly one of the two - `ck_annotations_one_rater`), with `source` and `emoji`; the list returns neither the digest nor a name for it. `/api/v1/annotations/{target_type}/{target_id}` reads, sets and retracts the caller's own rating under that target's own read rule (`services/annotations.resolve_target`); a chat message stays in `message_feedback` and is written through the chat's own path (`chat.apply_message_feedback`), every other target is an `annotations` row with no key on `target_id` (live-target reads + an hourly orphan sweep instead). `GET /api/v1/annotations?agent_id=` and `/summary` give an agent's managers every rating of its work (the agent `Feedback` tab). A run rating is forwarded to Langfuse like a message rating. A rating may also carry one score per **feedback criterion** (`annotation_scores`, sent as the whole `scores` set - omitted keeps the stored ones). |
| **Improvement Proposal** | A typed, evidenced change to a target - persona, skill, assignment prompt, flow (`improvement_proposals`, `services/improvement_proposals/`) - filed by a person or Platform Health's Experimenter, approved by the target's managers (`approval_error`: the gate of a manual edit, no admin bypass on a private target), applied as a new version by the type's handler, watched (re-evaluation, live watchers, Settings > Platform Health's window for an agent's change, 7 days by default; a window nothing read ends with no verdict) and rolled back on regression. One open change per target; a dedup key (type, target, evidence fingerprint) so a re-run files nothing twice. A person's request is reachable behind `EVALUATION`, an agent's behind `CONCIERGE`. |
| **Persona Improvement** | The `persona` type of the improvement proposals: one cycle of the human-approved persona self-improvement loop (`services/persona_improvement.py`, the agent `Versioning` tab). An admin proposes a rewrite against an evaluation (the baseline is the agent's latest completed run of it and must have measured the CURRENT persona version - `baseline_problem`); one model call writes it from the baseline's weakest cases and the feedback; only the PERSONA is rewritten, never a skill, and by targeted changes only (`rewrite_length_limit`: at most +50% or +2,000 characters, 20,000 in all - a rewrite must not inflate the system prompt). The cycles are listed for the agent's managers (`can_manage`). It is approved by someone who may manage the agent (`approval_error`: `writable_agent_error`, and for a private agent no admin bypass - owner or config grantee); approving writes a persona version (audited on the agent) and queues ONE candidate run of the same evaluation on the baseline's model. The scheduler step 9b settles it once that run ends: `evaluation_comparison.compare_metric` on the evaluation's QUALITY score (`QUALITY_METRIC`: the judge `score`, for an evaluation still set to the retired F1 too; never `overall_score`), margin 2 points; a regression rolls back through a new persona version (`log_system_audit`) only while the loop's version is still active - a human edit made meanwhile is kept (`regression_kept`). Manual trigger only; one open cycle per agent (partial unique index). |
| **Feedback Criterion** | A dimension admins define for rating agent work, in Settings > Quality (`/api/v1/feedback-criteria`: reads for everyone since the rating dialog draws them, writes admin-only): `scale` (whole steps between bounds), `categorical` (options, each worth a 0-1 score) or `numeric` (bounds), with a weight. A rating's **weighted score** is the weighted mean of its scores normalized to [0, 1] and falls back to its thumb (1 / 0) when nothing is scored; an agent's is the weighted mean of its criteria's means, falling back to the share of thumbs up. Enabled weights may never all be 0 (refused at the API). The rules live in ONE place, `services/feedback_criteria.py`, mirrored for inputs by `frontend/src/lib/feedback-criteria.ts`. Disabling keeps the history; deleting removes the scores. |
| **Agent Memory Entry** | A durable memory record stored in PostgreSQL with vector embedding. Enables semantic search over an agent's accumulated knowledge across sessions. |
| **General Assistant** | The platform-wide chat assistant with admin-configured default LLM model, system prompt, and channel routing (`channel_config`). Users can override the model in their profile. It runs the built-in suites `general_chat` wires (`GENERAL_ASSISTANT_BUILTIN_TOOL_IDS` — the agent-scoped ones need an agent), loads the company-managed skills of `skill_ids` like an agent's (NULL = the built-in skills declared `bind_to_general_assistant`, `general_assistant_skills`) and hands over only to enabled company-managed agents every user reaches (not narrowed by `access_restricted`), as a `delegate` / `consult` / `transfer` (`GENERAL_ASSISTANT_HANDOVER_TYPES`; a target added without a type is recorded as `delegate`, except next to stored targets saved without types - the legacy mode, an empty map that gives every handover tool to every target - which it joins: that map stays empty until a type is picked, the settings screen shows its targets as `All types`, and the first type picked types every target after a confirmation naming the ones that become `delegate`; `services/handover_types.py` / `lib/handover-types.ts`); the settings API refuses to add anything else, and keeps what an older configuration already stored. A new row ships `DEFAULT_GA_BUILTIN_TOOL_IDS` (the platform builder, web fetch, the Video Studio and report generation included); a default added later reaches existing rows only through a one-time data migration (`g5209gadefault`, `v5774gadflt02`, `r5931gareport`). In XTM One mode the linked CTEM Assistant carries the same default tools and skills (`DEFAULT_ASSISTANT_SLUGS`). `linked_agent_id` ("Link to Agent") names an agent that answers in its place when every user can chat with it - enabled, chat on, company-managed, not `access_restricted` (`services/general_assistant_link.py`, mirrored by `lib/general-assistant-stand-in.ts`): a web conversation created without an agent is bound to it (and stays its own, like any conversation started with an agent), the channel router answers the General Assistant's messages with it (conversation left unbound, the agent still the turn's answerer for compaction, @mentions, attribution and Activity), a channel conversation's wake runs it, and so does the web chat when that conversation is continued there (`turn_stand_in()`: who answers is the conversation's, not the surface's - a web conversation created without the link keeps the General Assistant in Slack or Teams too; a user who may not chat with the agent gets the General Assistant; the conversation responses say who answers as `answering_agent_id`); the settings API refuses a new link that does not qualify, and the settings screen says why a stored one is not followed. In XTM One mode boot and the AI toggle link the CTEM Assistant (`provisioning.wire_default_agents`) only while `linked_agent_configured` is false: any save of the link sets it, "no agent" included, and deleting the linked agent clears both. |
| **Audit Log** | Immutable record of user actions (CRUD, config changes, bindings, auth events). Admin-only visibility. |
| **Group** | Admin-managed user group for entity sharing. Entities can be shared with specific groups via `shared_group_ids` (JSON column) instead of making them company-managed (visible to all). Members managed via `group_members` join table. Managers (`group_managers`, elected by an admin, not necessarily members) read the LLM Analytics of the group's CURRENT members, administrators excepted - on the page and through the platform insights analytics tool - and no other right: no Traces, no Sessions (`services/group_managers.py`). `kind` (`org_unit`, `access`, `distribution`, `auto` = not classified, every group's default, SAML-created ones included) is an admin's classification the analytics filter a group listing by (`group_kinds`); a group is a membership set, never a department. |
| **Department** | An org unit of the LLM analytics (`departments`, admin-managed in Settings > Observability > Departments, `/api/v1/insights/departments`): a person counts for ONE, resolved by `services/departments.py` from an ordered chain (`PlatformSettings.department_settings.sources`): the directory department the identity provider sends (`User.directory_department`, refreshed at every SAML / OIDC sign-in from the configured attribute, or imported) matched to a department's name or `directory_values`, then the first `DepartmentGroupRule` by priority whose group the person is in, else Unassigned. Stored with the usage when it is written (`LLMTrace.department_id`, `LLMDailyStats.department_id`, by `services/tracing/attribution.py`), never resolved at read time: a move never rewrites history. ### Entity Visibility & Permissions (Three-Tier Model)

Entity visibility follows three tiers: **own + shared + company-managed**.
- **Own**: `user_id = current_user.id` — private to the creator. Full read/write.
- **Shared**: entity's `shared_group_ids` overlaps with the user's group memberships, or its `shared_user_ids` names the user. Every grant carries a tier (`shared_group_permissions` / `shared_user_permissions`, `read_only` by default) and the strongest one reaching the user wins: **`read_only` grantees can see the entity but not edit it**; `config` / `config_with_chats` grantees can edit it (`config_with_chats` also opens an agent's chats and its traces). A violet "Shared" badge/banner is shown; for a `read_only` share the banner says so and the "Read-only" badge takes the Edit button's place.
- **Company-managed**: `is_company_managed = True` — visible to all users. **Read-only for non-admins**, full read/write for admins. An amber "Read-only" badge and "Company-managed" banner are shown for non-admin users.

**Admins see and edit everything, and only the library lists are three-tier for them.** A library page (Agents, Integrations, Knowledge Bases, ... with its `Mine` / `Shared` / `Company` pills) and a picker list own + shared + company-managed for every caller, admins included. Everything else takes the admin bypass: every detail route, read and write, and every view reached from an entity - an agent's integrations, knowledge bases, tools, skills, prompts, handovers, assignments and runs, the agents using a knowledge base - which the detail pages read with `?scope=all` (`EntityListScope` / `list_scope_admin_bypass()` in `api/v1/helpers.py`, `useEntityListScope()` in the frontend list hooks: the whole platform for an admin, the library set for anyone else). A picker keeps its three-tier options plus the rows the entity is already bound to (`withBoundEntities()`), so an admin editing a colleague's agent sees and keeps every binding. An admin finds a colleague's private object in `Administration > Objects` and opens it from there; nothing an admin can open 404s.

Who may edit is one rule, `can_manage()` / `can_manage_as()` in `api/v1/helpers.py`, enforced by every write route; who may read an agent's chats is `can_view_agent_chats()` (admin, owner, or a `config_with_chats` grant - direct or through one of the user's groups; nobody else on a company-managed agent), enforced by the chats routes. A trace holds the conversation it records, so the same rule reads an agent's traces: the traces routes (`traces._assert_can_read_agent_traces`) and every trace tool an agent turn wires beyond the ones the agent carries itself (`builtin_tools.traces.may_read_agent_traces`, through `agent_chat._turn_trace_tool_ids`) - a `config` grantee configures the agent without reading its traces, and an A2A partner's task reads none whatever its run-as identity. Entity responses carry them for the requesting user as `can_manage` and, on agents, `can_view_chats`; the UI reads them as served (`canManageEntity()` for the manage right, `canViewAgentChats()` for the chats) - never re-derive share tiers in the browser.

An agent response carries `web_token`, the public widget link that runs the agent as its owner, only to a caller for whom `can_manage` is true (`_to_response` in `api/v1/agents.py`); a `read_only` grantee gets `null` and the Channels card shows the widget live without `Get Embed Code`. The binding and `integration_lending` ids stay on every response: the viewer pages list the agent's integrations and the lending state from them.

All seven main entities (Agents, Integrations, Knowledge Bases, MCP Servers, Custom Tools, Channel Bots, Prompts) have a `shared_group_ids` JSON column for group sharing.

**Deleting a user or a group drops its grants**: the grant columns are JSON arrays with no foreign key, so `prune_user_grants()` / `prune_group_grants()` (`api/v1/helpers.py`) remove the id and its permission entry from every model `share_grant_models()` derives from the mappers, a new shareable model included (pinned by `tests/test_share_grant_cleanup_coverage.py`). The principal row is locked first, the rows are read `FOR UPDATE` (a concurrent grant edit is never overwritten), and the writers that check their principals exist lock them `FOR KEY SHARE` - `normalize_user_grants()` for every user grant, `normalize_group_grants()` for every entity group grant, `provider_access.apply_provider_access()` for an LLM provider's users and groups - so a share racing the deletion is pruned or refused.

**Group grants have one writer**: `normalize_group_grants()` (`apply_group_share_fields()` for a request body, with `null_keeps_stored` on the update routes that read `null` as "unchanged") is the only write of `shared_group_ids` / `shared_group_permissions` on every route, the agent builder tools and the skill materialization: canonical UUIDs, de-duplicated; a newly added group must exist (422, `Cannot share with unknown group(s)`), a stored one whose group was deleted is dropped; permission entries only for granted groups, with a known tier. `tests/test_group_share_grants.py` pins that nothing under `app/` assigns the columns another way (a clear to `None` excepted). A flow run's copy of its flow's audience is history (`GRANT_SNAPSHOT_MODELS`) and is left as it was.

### Company-Managed Entities

Every entity of the `CompanyManagedEntity` union (`api/v1/helpers.py`) supports an `is_company_managed` flag:
- When `true`: the entity is shared with all users and only admins can edit it; `user_id` keeps its owner (the creator, or the admin picked by `resolve_company_managed_owner_id` for seeded rows).
- When `false`: the entity is private to the owning user.
- Admins can toggle this flag at any time via the update API.
- When switching from company-managed → private, the backend automatically cleans up references from other users' agents (removes bindings, KB references, MCP references).
- An agent is cleaned up whenever who reaches it changes, not only on that toggle: a grant removed, `access_restricted`, company-managed made private or a new owner. The personal agents whose owner no longer reaches it stop naming it in `handover_agent_ids` (with `handover_types` / `handover_conditions`) and `work_item_owner_agent_ids`. A company-managed agent, edited by administrators only, is not judged by its owner's reach: it stops handing over to it once it is no longer company-managed and keeps it on its work-item roster (`unlink_agent_from_lost_holders()`, `services/agent_bindings.py`, on the REST update and the agent-builder `update_agent`). Losing a group does the same: a member removed by the groups route, SCIM or the SSO login sync (`unlink_agents_shared_with_group()`), or the group deleted (`prune_group_grants()`, also when the SSO sync merges a group named by its IdP id into the group of its display name). A deleted user needs none: their private agents go with them and their company-managed ones to an administrator, who reaches every agent.

### Anonymous Access (External Channels)

External channels (Slack, Teams, WhatsApp, Telegram, Discord, Google Chat) often receive messages from users who don't have a Copilot account. The `allow_anonymous` feature lets agents process these messages without requiring user identification.

**Bot-enforced resolution** (resolved in `channels/router.py` via `_resolve_allow_anonymous()`):
- Bot `allow_anonymous = false` -> always false. The bot-level setting is a hard constraint that the agent override **cannot** defeat.
- Bot `allow_anonymous = true` -> the agent's per-channel override (`channel_config[channel].allow_anonymous`) applies; `null` inherits the bot's `true`.
- No channel bot -> `false`.

The bot-level toggle is admin-only in Settings > Channels & Bots. See `backend/app/channels/ROUTING.md` for the full matrix.

When anonymous access is enabled:
- Messages are processed normally; the channel user's metadata (name, phone, platform ID) is passed as `message_context` to the agent.
- Conversations are created with `user_id = NULL` and matched by `channel_thread_id`.
- All enabled agents with `allow_anonymous` and `receive_enabled` for the channel are eligible for anonymous routing (company-managed agents are preferred but not required). The bot-enforced `allow_anonymous` resolution is checked per agent during resolution.
- The General Assistant is **not** available for anonymous users.
- Downstream code receives `effective_user_id = "anonymous"` so LLM model resolution and memory degrade gracefully to defaults.
- The turn counts against the platform-wide agentic limits: the quota gate reads `"anonymous"` as no account and checks and charges the platform-wide tiers alone (the licence ceilings, the platform-wide cap) - no user or group limit applies and nothing is attributed to a user. At the ceiling the sender reads "This service is at capacity right now. Please try again later.", and while the quota store is unreachable in XTM One mode "This service is temporarily unavailable. Please try again later." The refusal is answered where a model would have answered, like the licence refusal (where the bot stays silent while it has capacity, it stays silent), and a refused turn never generates a conversation title (`channels/router.py`, `error_out` code in `QUOTA_REFUSAL_ERROR_CODES`).

### Private Conversations (External Channels)

When channel receive restrictions are configured (e.g., restrict a Slack bot to `#support` only), private/DM conversations could be blocked. The `allow_private` feature (default `true`) lets private conversations bypass channel restrictions.

**Bot-enforced resolution** (resolved in `channels/router.py` via `_resolve_allow_private()`):
- Bot `allow_private = false` -> always false. The bot-level setting is a hard constraint that the agent override **cannot** defeat.
- Bot `allow_private = true` -> the agent's per-channel override (`channel_config[channel].allow_private`) applies; `null` inherits the bot's `true`.
- No channel bot -> `true`.

The bot-level toggle is admin-only in Settings > Channels & Bots. See `backend/app/channels/ROUTING.md` for the full matrix.

Private conversation detection per platform (via `_is_private_conversation()`):
- **Slack**: `metadata.channel_type == "im"` (direct message)
- **Teams**: `metadata.conversation_type == "personal"` (also bypassed via `_extract_channel_id()` returning None)
- **Telegram**: `metadata.chat_type == "private"`
- **WhatsApp**: `metadata.chat_type == "private"` (DM).  Group messages have `chat_type == "group"` and return False so that channel restrictions apply to groups.
- **Discord**: `metadata.is_dm` (DM or group DM channel)
- **Google Chat**: `metadata.space_type == "DM"`

### Only-Mention Mode (External Channels)

When a bot is added to group channels (Teams channels, Slack public channels, Telegram groups), it may respond to every message by default. The `only_mention` feature (default `false`) restricts the bot to only respond when explicitly @mentioned.

**Bot-enforced resolution** (resolved in `channels/router.py` via `_resolve_only_mention()`):
- Bot `only_mention = true` -> always true. The bot-level setting is a hard constraint that the agent override **cannot** disable.
- Bot `only_mention = false` -> the agent's per-channel override (`channel_config[channel].only_mention`) applies; `null` inherits the bot's `false`.
- No channel bot -> `false`.

The bot-level toggle is admin-only in Settings > Channels & Bots. See `backend/app/channels/ROUTING.md` for the full matrix.

Mention detection per platform (via `_is_bot_mentioned()`, all reading the adapter-set `metadata.bot_was_mentioned` flag):
- **Teams**: flag set by the adapter from the Bot Framework `entities` array
- **Slack**: flag set by the adapter for both `app_mention` events and `<@BOT_ID>` detected in message text
- **Telegram**: flag set by the adapter from Telegram message entities
- **Discord**: flag set by the adapter from `message.mentions`
- **Google Chat**: flag set by the adapter from `USER_MENTION` annotations of type `BOT`
- **WhatsApp**: always False — WhatsApp groups support @mentions in message text, but the Cloud API does not provide structured mention entities

Private/DM conversations always bypass the only-mention check — users can always message the bot directly regardless of this setting.

### Multi-Model Support

LLM model resolution follows this priority:
1. **Agent override** — `Agent.llm_model` (if the agent has a specific model), or, when `Agent.llm_model_source == "routing"`, the platform routing model (`PlatformSettings.routing_model` / `routing_provider_id`) instead of the agent's own fields; with no routing model configured, nothing is overridden and the tiers below apply. Every call site reads these overrides through `app.llm.agent_model.agent_model_selection`, never from the columns (pinned by `tests/test_agent_routing_model_source.py`). Choosing a model of its own clears the source; choosing the source clears the agent's own fields. A create or update body (REST or the agent builder tool) that sends the source with a model, provider or provider config is refused (422 / tool refusal) rather than written and silently dropped, an imported bundle on the routing model keeps none of its own, and the assignment activation gate runs on the same selection as the run.
2. **Agent default** — `PlatformSettings.agent_default_model` (admin-set default for all agents)
3. **User preference** — `User.preferred_llm_model` (from profile settings)
4. **Platform default** — `GeneralAssistantConfig.llm_model` (admin-set, also used by General Assistant)
5. **Any configured provider** — fallback to the first of `implicit_chat_configs()`: a config listing a chat model, or, while none does, one listing no model

Each LLM provider can declare multiple `available_models`. The first model selected when configuring the first provider automatically becomes the platform default.

The **decision model** (`PlatformSettings.decision_model` / `decision_provider_id`) sits outside these tiers: a decision model (CLM) answers choice questions through the provider's `decisions_api` (`app/llm/decisions.py`) and never chats. `act_on_page` is the only reader, through `flow_llm.decision_model()` and `flow_classifier.classify()`; unset, the tool is not offered. Its picker lists `decision_listing()` (`/settings/available-decision-models`), with a per-provider status that the card turns into a reason when a listing provider offers none; a provider that cannot list (`lists_decision_models` false: OpenRouter) takes a typed model id.

Every tier is resolved within the providers the run's user may use (#5160, `app/llm/provider_access.py`). An admin can restrict a provider to groups and users (`LLMProviderConfig.access_restricted` + `shared_group_ids` / `shared_user_ids`, Settings > AI Models > Access); an unrestricted provider serves everyone, a caller with no account only the unrestricted ones, and admins route like everyone else. A provider granted to the user is tried before an unrestricted one, so a shared agent runs on each team's own key; a model only withheld providers offer skips its tier, and a pin to a withheld provider reads as absent. Failover stays inside the same set; embeddings and image generation stay platform-wide. Every reader goes through `provider_routing()`, never a filter on `access_restricted`. A provider may also EXCLUDE groups and users (#4684, `excluded_group_ids` / `excluded_user_ids`): never used for them, whatever it grants, restricted or not. An exclusion follows the person the work is for: a call made with no user of its own resolves as the user the context acts for (`provider_access.bind_acting_user`, bound by authentication, the web chat's send stream, `get_llm_for_user` and the worker adapters, scoped with `acting_for`), and the platform-level embedding and image providers refuse an excluded person's content (`ensure_not_excluded`) instead of receiving it. A group named in an exclusion cannot be deleted (409).

### User Timezone

Users can set an IANA timezone (e.g. `"America/New_York"`) in their profile (`User.timezone`). When set, the system prompt includes both UTC and local time so agents can give timezone-aware responses. The timezone is injected via `format_datetime_prompt()` in `builtin_tools`.
