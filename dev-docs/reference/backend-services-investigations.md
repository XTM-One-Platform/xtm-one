# Services: Deep Investigation

Service map rows for Deep Investigation (the chat entry, packs and the pack builder, orchestrator, queriers, state, events, report, continuation, web search) in `backend/app/services/`; the binding rules live in `backend/app/services/AGENTS.md`.

## Service map

| File | Purpose |
|------|---------|
| `investigation_packs.py` | Source packs + subject classification for Deep Investigation. A pack names the sources to query for a kind of CTI subject. The code-declared built-ins (`BUILTIN_PACKS`, behind `get_pack` / `recommend_packs`) are `web-general` (public deterministic URL templates through `web_fetch`) and `web-research` (a `web_search` source: provider search with span citations, `web_search.py`); the install-specific packs come from `investigation_pack_resolver.py` and the packs users build from `investigation_pack_builder.py`. `plan_for` returns the pre-run skeleton and the executable source list **from one traversal**, so the plan the analyst sees and the work the orchestrator does cannot diverge; a source shared by two selected packs is planned once, under the first pack carrying it. `classify_subject` is a deterministic regex classifier (IP / domain / URL / hash / CVE, `unknown` otherwise) — NOT an LLM call, because for these shapes a regex cannot hallucinate a type, costs nothing and is unit-testable, and a wrong subject type silently aims the whole investigation at the wrong sources. **`disinfo-infrastructure`** (`disinfo_infrastructure_pack()`, CheckFirst's Storm-1516 method) qualifies a newsroom-named domain or the IP hosting it, with two source kinds of its own: `site_fingerprint` (a named `FINGERPRINT_SETS` entry tested against the site's own home page and response headers - it contacts the investigated site, so the pack is never auto-selected and not in `BUILTIN_PACKS`) and `passive_dns` (VirusTotal resolutions through the caller's integration, by id; an IP source filters host names through a named `HOSTNAME_KEYWORD_SETS` entry whose pattern is shown in the step's query). **Goal plans** (GOAP): a pack may declare `SourcePack.goal`, a `GoalPlan` of predicates, `GoalAction`s (preconditions, effects, cost, an icon of the closed `GOAL_ACTION_ICONS` set, `produces_report` for the report action) and the predicates each subject type starts with; `plan()` is A* (g = cost, h = goal predicates unmet), so a subject further along gets a shorter path. A source serves an action (`SourceDefinition.action`) and may query its own `subject` (a hop: the IP a pivot reads, a neighbouring site); `identity()` keeps the subject apart while `access_identity()` is what a continuation re-authorises. `disinfo-infrastructure` declares `DISINFO_GOAL` (qualify the seed, map its hosting, pivot on the newest IP, qualify up to `MAX_NEIGHBOURS_QUALIFIED` neighbours, apply the doctrine, write the report) and its hops are leads (`pivot_leads`, `neighbour_leads`) inside ONE run. **OpenCTI, both ways**: the `opencti` source kind reads what the registered OpenCTI already knows, as the caller (observables by value with their containers and the campaigns / intrusion sets they are tied to, or threats by name; a list of values in one query through `opencti_values`), and the disinfo pack starts with `check_opencti` when the caller can see an OpenCTI (`investigation_pack_resolver.visible_opencti_integration`) and asks it again at each hop (`hop_opencti`: the IP, then every co-hosted site at once, so the run tells the known from the new). Writing back is the agent's, through the OpenCTI integration's own tools in a draft: "Send to OpenCTI" sends `investigation_opencti.opencti_record_request`, and `read_investigation_report` appends the exact objects to create (`build_knowledge`, pure, from the steps). A pack that declares no plan is drawn with the **default plan** (`default_goal_plan`, one action per kind of source through `DEFAULT_ACTION_BY_KIND`, `follow_leads` for leads, the report last): every run is rendered as a goal plan, and a pack experiments with the rendering by declaring one, with no UI code. Every `label` / `description` / `objective` a plan sends is a key of the frontend catalogs (pinned by `tests/test_investigation_goal_plan.py`). **A pack can declare knowledge bases** (`SourcePack.knowledge_bases`, `KnowledgeBaseSelector`): by `slug` (the `slug:<slug>` tag the seed gives a built-in corpus) or by `tags`, each with the subject types it answers, a `query_template` (a doctrine is asked about modelling the subject, never searched for its name) and a `min_similarity` floor (cosine; a passage that matched the question's words is kept). `with_knowledge_bases` turns them into one `knowledge_base` source per corpus for ONE caller and says in the description which selector named nothing that caller can see. `disinfo-infrastructure` declares the VIGINUM doctrine (`VIGINUM_DOCTRINE`, floor `VIGINUM_MIN_SIMILARITY` measured on text-embedding-3-large). |
| `investigation_events.py` | Wire format for a live investigation: the stream frames and the chat marker. `planned_frame` / `step_frame` / `complete_frame` build the three `investigation_*` frames the orchestrator emits through the chat service's `on_event` — the same channel the agent loop uses for `tool_start` / `segment_complete`. Two properties are load-bearing. **Frames are advisory, the record is authoritative**: every builder reads rows the orchestrator has ALREADY committed (`_checkpoint_and_emit` commits then emits, never the reverse) and every frame carries the run's `revision`, so a client that missed frames rebuilds the identical block from the record and a duplicate / out-of-order frame is discardable instead of corrupting — which is why the transport is a lossy callback with no delivery machinery. **A step's own state is `step_status`, never `status`**: a frame's top-level `status` names the frame KIND, and a step payload spread into a frame would otherwise overwrite it, leaving `frame.status` reading `"error"` with no way to tell what kind of frame it was. `build_investigation_marker` / `INVESTIGATION_MARKER_RE` own the `[[INVESTIGATION:uuid]]` shape — never format it by hand; the channel stripper (`channels/base.strip_channel_investigation_markers`) and the web app (the chat panel's marker grammar, `frontend/src/pages/chat/answerMarkers.ts`) read the same shape, tested on the same samples (`frontend/src/pages/chat/answer-markers.contract.json`, `tests/test_investigation_events.py`). The marker is deliberately just an id: encoding step state in message text nothing updates would give the block a second, frozen copy of the run's history. `goal_plan_payload` is the plan the block draws (on the planned frame and the REST read): the declared plan's A* path, or the default plan read from the actions the run's steps serve (also for a run recorded before its pack declared one); what HOLDS is never sent, the client derives it from the steps. `step_action` is the one reading of the action a step serves (its declared one, else the default for its kind). `executive_summary_payload` is what the block's "Generate executive summary" sends once a run has a report: the instruction (`investigation_packs.executive_summary_request`, built from the plan, naming the built-in XTM One Brand Deck - which settles the template choice - and the run id the agent reads the report by with the `deep_investigation` suite's `read_investigation_report`, owner-only, the stored report rendered by `investigation_report.stored_report_draft` + `render_markdown` exactly as the reader was shown). |
| `investigations.py` | Read-side serialization for investigation runs: `serialize_investigation` returns the run, its steps in display order and the derived summary, for `GET /api/v1/investigations/{id}` — the endpoint that makes the live block robust rather than merely pretty, since #3302 requires the block to render identically from the record alone (reload mid-run, late join, stream down), which makes the stream frames an optimisation and this the source of truth. Each step is built through `investigation_events.step_payload`, the very function the frame builders use, rather than repeating the field list: the block hydrates from REST then merges frames into the same objects, so a second copy would be free to drift and the drift would surface as a step changing shape (or vanishing, if the merge key moved) the moment a frame arrived. Asserted field-for-field by `tests/test_investigation_api.py`. The summary is computed here for the same reason it rides on the completion frame: `all_succeeded` gates the "everything passed" affordance and one server-side rule must decide it on every surface. |
| `investigation_orchestrator.py` | The Deep Investigation bounded loop. `DeepInvestigationOrchestrator.run` resolves the subject, plans from the packs, queries within an iteration budget and closes the run — every transition through `investigation_state`, so the persisted rows are written by the loop and never inferred from model output. The `SourceQuerier` is **injected** for two load-bearing reasons: the budget / skip / circular-lead / error-taxonomy paths (the ones most likely to be wrong) become testable without a network, and integration-backed packs are new queriers over an unchanged loop. `SourceOutcome` reports FACTS (findings count, evidence, partial, error type) and carries no status — the status is derived downstream. Leads are deduplicated at ENQUEUE time keyed on the built URL and seeded with the planned URLs, so a duplicate never reaches the block at all; `MAX_LEAD_STEPS` bounds the PLAN while the budget bounds the WORK. A querier that raises fails only its own step (`invalid_response`) rather than aborting the run. `commit_each_step` (default on) is what makes the state readable WHILE the run happens — the live block's whole premise; a single final commit would lose everything on a mid-run crash. No confidence value is produced anywhere (the #3302 "no unearned metrics" invariant). Under a declared goal plan the next step is the one whose action comes first in the plan (`GoalPlan.rank`), so a hop found mid-run is queried before later actions; a source's `subject_for()` is what it queries, and a lead inherits its source's action. Without a declared plan the order is the pack's, unchanged. |
| `investigation_queriers.py` | How one source is actually interrogated. `make_dispatching_querier` routes on `SourceDefinition.kind`; the three queriers all map success and failure onto `STEP_ERROR_TYPES`, the vocabulary shared by the block, the report and the `investigation.source_error` metrics. **HTTP** (`make_web_fetch_querier`) is opinionated where HTTP is ambiguous: **5xx → `unreachable`** (the source could not answer at all) while `invalid_response` is reserved for a 2xx that answered with something unusable; **an empty 2xx is NOT an error** (zero findings → the orchestrator derives `empty`); **truncation is `partial`** → `degraded`. `MIN_USEFUL_CHARS` discards cookie-wall / "no results" boilerplate. **Knowledge base** (`make_knowledge_base_querier`) counts distinct DOCUMENTS, not chunks, and resolves each `source_id` to a real filename — `HybridResult` carries no name, so citing it directly would render every corpus citation as a bare UUID; a full `KB_TOP_K` page is `partial`, because the corpus may hold more. **MCP** (`make_mcp_querier`) opens and closes one connection per source and cites *server · tool* rather than a URL. `_subject_argument` reads the subject's parameter off the tool's own input schema and returns None whenever that is ambiguous — guessing would put the subject into a parameter chosen by coincidence, on a tool that may do anything. **Site fingerprint** (`make_site_fingerprint_querier`) fetches the subject's home page through the same SSRF-checked `fetch_and_extract` (`_guarded_fetch` is the one failure mapping both page queriers share) and reports one cited finding per matched signal and never a verdict; none matched is `empty`, a page past `FINGERPRINT_MAX_BYTES` is `degraded`, and the whole read (HTTPS and its HTTP fallback) is bounded by `FINGERPRINT_STEP_TIMEOUT`, a `timeout` past it. **Passive DNS** (`make_passive_dns_querier`) reads one VirusTotal page (`PASSIVE_DNS_PAGE_SIZE`), up to `PASSIVE_DNS_FILTERED_MAX_PAGES` when host names are filtered (on a shared IP the newest resolutions are other people's sites; a page failing after the first, or the read passing `PASSIVE_DNS_STEP_TIMEOUT`, keeps what was read, `degraded`; a short `Retry-After` on a 429 is waited out once per page), matching keywords on the decoded form of a punycode name too (`display_host`, also its label), with the key `load_virustotal_api_key` re-reads under the caller's three-tier visibility at query time (no caller, no key); more records than one page is `degraded`, a keyword filter says how many it kept, and at most `PASSIVE_DNS_MAX_EVIDENCE` matches are cited (the newest), the rest counted and the step `degraded` (`shown`). The knowledge-base querier searches `knowledge_base_query()` (the source's template applied) and drops passages under its `min_similarity`, over a wider pool (`KB_FLOOR_POOL`) than it shows; nothing left over is `empty` with `source.kb_below_floor`, which says how many best-ranked passages were examined. Their quotes are platform-written observations carrying the matched values verbatim, so the report can cite them (`is_quotable`). **OpenCTI** (`make_opencti_querier`) mints the caller's token at query time (`load_opencti_access`, three-tier, on its own session), cites each value OpenCTI holds (`opencti_observable_quote`, linked on the platform's public URL) and lists the ones it does not (`source.opencti_known` / `opencti_none_known`, `opencti_unavailable` without one). No querier returns confidence; the passive-DNS querier returns leads only for a source serving a goal-plan hop action (`_goal_hops`: a domain's newest IP, an IP's newest sites). |
| `investigation_pack_resolver.py` | The install-specific investigation packs: `knowledge-bases` (one source per knowledge base the CALLER can see, one each so the block can say which corpus answered) and `mcp-tools` (one source per MCP server whose owner designated a tool). Exists because `investigation_packs` is code and ORM-free while a corpus and a server are rows with per-user visibility — two people asking about the same subject can legitimately be offered different packs. Both packs are `auto_select=False`: a run that skipped the picker gets the built-ins alone, because searching every corpus the caller can see is a decision somebody makes, not one a subject regex makes for them. Visibility is `user_visible_query`'s, and both queries **reset its inherited `ORDER BY created_at DESC`** before sorting by name — appended, the name would be a second key that never decides anything. `disinfo-infrastructure` is offered to every caller, with passive-DNS sources when `_visible_virustotal_integration` finds a connected VirusTotal integration holding a key (three-tier, no admin bypass, first by name). Every pack's declared knowledge bases are resolved here, from the same visible rows as the `knowledge-bases` pack (`_visible_knowledge_base_rows`, `expand_declared_knowledge_bases`), and the orchestrator's all-built-ins shortcut and recommendation path do not skip a pack that declares any. `resolve_selected` preserves the caller's order (it decides attribution in `plan_for`) and RAISES on a slug that no longer resolves rather than dropping it, so a run's persisted `source_pack_slugs` can never claim coverage it did not have. |
| `web_search.py` | Provider web search, normalised into text plus SPAN-LEVEL citations. Anthropic and OpenAI both return a written answer with its sources attached to spans of that answer (`cited_text` on one, `start_index`/`end_index` on the other); both integration formatters reduced that to a flat list of URLs and `cited_text` was read nowhere in the repo — the material for an inline citation was arriving and being discarded. The parsers stay PURE so the span arithmetic is pinned without a key or a network: a citation in a later block must not claim the opening sentence (offsets are tracked as blocks concatenate), and an offset that is out of range, inverted or non-numeric loses its SPAN rather than slicing an unrelated fragment and presenting it as a quotation — a fabricated quote is worse than no quote. Titles and quotes are HTML-unescaped for display; URLs never are, since an entity in an address is part of the address. `search()` classifies HTTP failures onto `STEP_ERROR_TYPES`, the same vocabulary the fetcher uses. |
| `investigation_report.py` | The one cited report across every source a run queried. **What "constrained" means:** every marker the model writes is resolved against the numbered passages it was handed, and one that resolves to nothing fails the WHOLE report — once with a retry that names the invented numbers, then closed — because the same draft produced the sentences around it. **What it does not mean:** this checks a citation POINTS somewhere real, never that the passage supports the sentence; the guarantee is traceability, and the docstring says so rather than letting the word imply more. `collect_sources` allocates the excerpt budget ROUND-ROBIN across steps, not first-come, so one prolific source cannot crowd the corpora or the last tool of the plan out of what the model is shown. `is_quotable` drops passages that are structure rather than prose (serialised JSON, table headers) — offering them spends budget and invites a claim attached to a fragment that cannot carry it. Uncited sentences are COUNTED, not forbidden, and the count travels in the message: forbidding them pushes a model to attach sources to sentences they do not support. `render_sources_queried` / `render_leads_not_followed` are DERIVED from the step record, never asked of the model, so the report and the live block cannot disagree. |
| `investigation_state.py` | Deep Investigation step-state machine: the single place that decides what state an investigation step is in, backed by the `investigations` / `investigation_steps` models. `create_investigation` / `plan_steps` / `append_lead_step` / `start_run` / `mark_step_active` / `record_step_result` / `record_step_error` / `mark_step_skipped` / `finish_run` write the run's history; `summarize` and `duration_seconds` derive the collapsed summary. Three invariants are enforced here rather than at the call sites, because the failure they prevent is silent — a failed source that renders as a success is indistinguishable from a real one. (1) **A failure never becomes a success**: `record_step_result` takes no `status` parameter and DERIVES it from the facts (an `error_type` forces `error`, `partial=True` forces `degraded`, zero findings force `empty`), so no caller can assert `completed` for a source that failed or found nothing; every terminal write goes through that one function, error path included. (2) **No unearned confidence**: `confidence` is nullable with no default anywhere in the path (schema included) and is dropped on `empty` / `error`, so a run that cannot compute one shows none. (3) **No derived duration**: `duration_seconds` returns `None` until both wall-clock stamps exist and must never gain a step-count fallback. `summarize().all_succeeded` requires EVERY step to be `completed`, which is what makes an aggregate "all checks passed" affordance unreachable while any step is empty, degraded, errored, skipped or unfinished. Mutates in place and flushes; the caller owns the commit. Invariants asserted by `tests/test_investigation_state.py`. |
| `deep_investigation_chat.py` | Running a Deep Investigation as a chat turn: the chat handler hands the subject to `run_deep_investigation_chat` instead of the agent loop and gets the assistant text back; the rest of the turn (user message, `done` frame, attachments, turn guard) is untouched. The message body is derived deterministically from the run's summary and carries the `[[INVESTIGATION:uuid]]` marker - no model writes it; the cited report is written after the run (`_write_report`). |
| `investigation_continuation.py` | Continuing a run that stopped on `run.budget_spent`: `analyse_coverage` / `build_offer` show what the plan named and the budget never reached, and a continuation is a NEW run (a `skipped` step never becomes active), chained to its predecessor (`chain_of`). |
| `investigation_report_status.py` | Whether a run's cited report is being written: a Redis marker set when the run's row exists (`DeepInvestigationOrchestrator.run(on_created=...)`) and cleared when the writer returns; the TTL only bounds a dead writer, and an unreadable marker is `unknown`, never a claimed activity. |
| `investigation_opencti.py` | What a run established, as STIX knowledge for OpenCTI: `build_knowledge` (pure, from the stored steps) decides WHICH objects; the conversation's agent records them through the OpenCTI integration's own tools, in a draft the analyst validates (`opencti_record_request`). |
| `investigation_pack_builder.py` | Packs users build (`InvestigationPack`): the `PackDefinition` validated where the body is parsed (a bad one is a 422) and re-validated before use, and `build_source_pack`, which turns a definition into a `SourcePack` FOR ONE CALLER (every integration-backed source resolved against what that caller may use); `builder_catalog`, `definition_from_builtin`. |
| `investigation_pack_assistant.py` | The pack builder's assistant: one round of the person's instruction, the draft and the conversation to the caller's model, which answers a reply and a whole pack validated by `PackFields` (refusal reasons sent back once); offers only the corpora and MCP tools the caller can see, stores nothing. The draft reaches the model whole (`draft_text`): the request refuses one over `MAX_DRAFT_CHARS` (422), and the route limits rounds per user. |
| `pinned_fetch.py` | Fetching a URL a pack author typed: through `app.core.pinned_request`, the host resolved once, every address public (`destination_policy.forbidden_address_reason`, metadata endpoints refused), the request sent to that address with the original name as `Host` and TLS server name, no connection reuse; `fetch_pinned`, `PinnedFetchRefusedError`. |
