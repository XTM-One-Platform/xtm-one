# LLM thinking, reasoning and prompt caching

Anthropic prompt caching, turning thinking off for utility calls, streaming reasoning text, the guarded thinking-block replay, and checking a request shape against the real API; the rules of this area live in `backend/app/llm/AGENTS.md`.

## Prompt Caching (Anthropic)

The direct Anthropic provider applies Anthropic prompt caching on every request, following the best-practice layout from the [prompt caching guide](https://platform.claude.com/docs/en/build-with-claude/prompt-caching). This is critical for the agentic loop, which re-sends the full conversation + all tool schemas on every iteration — with caching, the stable prefix is billed at the cache-read rate (0.1x input) instead of the full input rate, and cache reads are not deducted from Anthropic rate limits.

Strategy (implemented in `_apply_prompt_caching()`, 3 of the 4 breakpoint slots):

1. **Explicit breakpoint on the last tool definition** — tool schemas are the most stable prefix segment (identical across iterations and across runs of the same agent), so they cache independently of the more volatile system prompt.
2. **Explicit breakpoint on the stable system prefix** — the merged system string is split at its volatile tail (`app/llm/system_prompt_split.py`): the tail starts at the clock line `format_datetime_prompt` writes (`SYSTEM_VOLATILE_TAIL_MARKER`) and holds what changes on every run (clock, local time, identity, fenced memory and recent activity, and what the prompt builders place after them). The stable prefix (organization summary, persona, guardrails, attached prompts, skills, agent context, knowledge bases, coordination) is a `cache_control`-carrying text block; the tail is a second, unmarked block after it, covered by the automatic breakpoint within a run. The next run of the same agent configuration reads tools + stable system from the cache and writes only the tail. A prompt without a clock line stays one marked block. The prefix must be byte-identical across runs and calls of one agent configuration (#11971): `run_agent_chat` (`app/services/agent_chat.py`) writes every stable section first (persona to coordination tools, connected integrations, knowledge bases, peer agents, output format, workspace sources), then the clock, identity and memory it holds in `_tail_parts`, then the per-call sections it holds in `_call_parts` (page context, Presentation Studio, Message Context with its conversation, message and thread ids, Account brief, prior conversation or current thread, the must-respond, silent-response and thread-continuation blocks, handover context, files), then the content and security policies. `_build_system_message` (`app/services/assignment_helpers.py`) writes its stable sections (assignment, element bindings, channel context, output format, AI label, HITL, execution policy) before the identity and memory. A builder that adds a section that can differ from one call to the next adds it to the tail, never to the stable parts; `tests/test_system_prompt_split_chat.py` guards the chat builder and `tests/test_system_prompt_split_chat_postgres.py` checks two calls with different contexts share one prefix.
3. **Automatic conversation caching** — a top-level `cache_control` (sent via `extra_body` for SDK-signature safety) lets the API move the final breakpoint forward as the conversation grows. This is Anthropic's recommended default for multi-turn conversations.

Configuration:

| Setting | Default | Purpose |
|---------|---------|---------|
| `PROMPT_CACHING_ENABLED` | `true` | Global kill switch — `false` restores fully uncached requests |
| `PROMPT_CACHE_TTL` | `5m` | Cache TTL: `5m` (refreshed free on every hit) or `1h` (2x write cost, for slow HITL / channel conversations) |

Per-call opt-out: pass `prompt_cache=False` as a kwarg to `chat()` / `chat_stream()` / `chat_stream_with_tools()`.

Notes:

- Requests below the per-model minimum cacheable length (512–4096 tokens depending on model) are silently processed uncached by the API — small utility calls are unaffected.
- No explicit `cache_control` is ever placed on message blocks and all markers share one TTL, so the documented automatic-caching edge cases (conflicting last-block TTL, exhausted slots) cannot trigger.
- **A mid-run system message stays in place.** The loop appends system messages while it runs (step-budget nudge, loop-breaker warnings, wind-down, vision notes). Merged into the top-level `system`, each one changed the cached prefix and the next request wrote the whole conversation to the cache again (measured on Sonnet 5: 0 tokens read, ~32.5K written, +0.6 s to first token at 40K tokens). On a model whose rule sets `in_place_system_messages` (`supports_in_place_system_messages()`, each verified against the API: Sonnet 5, Opus 5 / 5.5, Fable 5 / 5.1, Opus 4.8 - Opus 4.7 refuses one) `_build_anthropic_messages` keeps it inside `messages` where the API's placement rule holds (`_fits_in_place`: after a user or system message, before an assistant message or at the end); the same request then reads 32,347 tokens from the cache. A 400 naming `role 'system'` folds them back into `system` and retries once (`_fold_in_place_system`), and the thinking replay treats an in-place entry as part of the tool round. The two refusal recoveries (replayed thinking blocks, in-place system messages) are ONE `_RefusalRecovery` per request, each taken back once in whichever order the API refuses them - a model refusing both answers the first retry with the other refusal - and a replay fallback after a fold folds the rebuilt conversation again from the original `system`, never onto the folded one.
- Both the streaming accumulator (`_StreamUsageAccumulator`) and non-streaming `chat()` (`_usage_from_response()`) surface `cache_creation_input_tokens` / `cache_read_input_tokens`, which the Langfuse tracing (`_normalize_usage`) and deterministic cost calculator (`services/tracing/cost_calculator.py`) already price at their discounted/premium rates.
- OpenAI (and Azure OpenAI) apply automatic server-side prompt caching — no client work needed. Gemini 2.5+ uses implicit caching. Bedrock applies implicit prompt caching to the models that support it (Anthropic Claude, Amazon Nova) with no change to the request; the provider sends no explicit `cachePoint` blocks, and the cache counters Converse reports reach the usage dict (see "Token usage per provider" below). OpenRouter (block-level `cache_control`) is follow-up scope.

## Turning thinking off for utility calls (Anthropic)

Bounded structured-output utility calls - conversation compaction (`services/conversation_memory.py`), memory fact extraction, reconciliation and consolidation (`services/persistent_memory.py`), the agent medium-term summary consolidation and compression (`services/agent_memory.py`), the cross-agent user profile rewrite (`services/user_memory.py`), classification - pass `disable_thinking=True` to `chat()`. On a model that runs adaptive thinking by default (`model_capabilities.defaults_to_adaptive_thinking`: Sonnet 5, Opus 4.7+, Fable 5, ...) the Anthropic provider then sends `thinking: {"type": "disabled"}`, because thinking off shares no `max_tokens` budget with the JSON answer. On the AI Gateway a Claude model gets `reasoning_effort: "none"` instead, which the gateway maps to that model's off form (`FiligranGatewayProvider._reasoning_effort`). Other providers ignore the kwarg. The streaming paths never turn thinking off; the only `thinking` they send is the display opt-in below.

Some models refuse that form outright: `claude-fable-5-1` answered HTTP 400 `"thinking.type.disabled" is not supported for this model. Use "thinking.type.adaptive" and "output_config.effort" to control thinking behavior.` Left to the router, that 400 would send every such call to the FAILOVER model - one wasted round trip and one WARNING per call on a healthy platform, and the work done on a model the admin did not pick. The set of refusing models is not knowable up front (the 5.x family keeps growing; a prefix table would be stale on release day), so the provider LEARNS it: `_refuses_disabled_thinking()` matches that exact 400 (status 400 AND the `thinking.type.disabled` path, whatever the quoting, in the API's structured error message - `structured_error_message`, never the SDK's rendering of the body, which a proxy can fill with an echo of the request), `AnthropicProvider._create_message()` retries the SAME request once in the documented equivalent - `thinking: {"type": "adaptive"}` plus `output_config.effort` at its lowest level (`_LOWEST_EFFORT = "low"`, the lowest value of the pinned SDK's `OutputConfigParam.effort`) - and adds the model id to the process-wide `_MODELS_REFUSING_DISABLED_THINKING` set, which `_apply_thinking_off()` reads so every later call in the process sends the adaptive form first. The memo is keyed by exact model id and resets on process restart (one wasted round trip per process per model - accepted). The adaptive retry runs under the same client timeout and the same transient-error retry as any request, and a 400 carries no usage, so nothing is counted twice. Invariants: a model that accepts `disabled` keeps receiving it, and the hint adds no effort setting of its own there - a caller's `reasoning_effort` is left alone (only capped where the model's thinking-off form has an effort ceiling, below), because effort applies to every output token and is valid with thinking off (it bounds the text, not any thinking); on the adaptive form effort IS the thinking lever, so `disable_thinking` writes the lowest level over any caller value; any other error, and a failure of the adaptive form itself, propagates unchanged so the failover chain runs exactly as before; the adaptive form never carries `disabled`, so there is never a second retry.

A model Anthropic documents as refusing `disabled` at every effort (its thinking is "Always on") can skip the lesson: its capability rule sets `thinking_always_on` next to `adaptive_thinking`, and `_apply_thinking_off()` sends it the adaptive + lowest-effort form from the FIRST request, so no `disabled` request ever reaches it. Claude Mythos (`claude-mythos-5`, `claude-mythos-5-1`, `claude-mythos-preview`) is declared this way. The declaration is read by this `chat()` path only: every other Mythos request (the streaming paths, the display opt-in below, the omitted temperature) is unchanged. Opus 5.5 and Fable 5 / 5.1 are declared the same way; the learned path stays for a model the rules do not know yet.

Two models turn thinking off in a form of their own, declared on their rule. Sonnet 5.5 refuses `disabled` but has a lowest setting that is not adaptive: `between_tools_thinking_off` sends `thinking: {"type": "between_tools"}` (no thinking before the first answer, none at all without tools; the API refuses any other field next to it), so its utility calls need no extra room for thinking. `thinking_off_max_effort` is the highest `output_config.effort` the thinking-off form is accepted at - `high` for Sonnet 5.5 (`between_tools`) and Opus 5 (`disabled`); a caller's effort above it is lowered to it (`capped_effort()`) on that request only. A refused `between_tools` is never memoised: the memo only reads a request that sent `disabled`. A model the rules do not declare yet is learned from that 400 too: Sonnet 5.5's wording ("send `{"type": "between_tools"}` instead of `{"type": "disabled"}`") names no parameter path, so `_asks_for_between_tools()` matches a 400 whose structured message names both forms, the same request is retried once with `between_tools`, and the model joins `_MODELS_TURNING_THINKING_OFF_BETWEEN_TOOLS`, which `_apply_thinking_off()` reads like the declared flag; with no declared ceiling its effort is held to `_BETWEEN_TOOLS_MAX_EFFORT` (`high`, Sonnet 5.5's).

On the adaptive form the thinking still counts against `max_tokens` - Anthropic documents it as "a hard cap on total output for the request, thinking and response text combined", and effort as guidance that "doesn't guarantee a token count" - while the utility callers size their budget for the answer alone. `_apply_thinking_off()` therefore raises `max_tokens` by `_ADAPTIVE_FORM_HEADROOM` (4096) on that form, and on that form only, up to the model's output ceiling (`model_limits.resolve_provider_max_output_tokens`: admin override, snapshot, family floor, provider default - a larger `max_tokens` is an HTTP 400) and never below the caller's own budget: a cap, not a target, since output is billed per generated token and `max_tokens` does not count towards Anthropic's rate limits; the `disabled` form keeps the caller's budget. The callers trust no budget either: an answer that stopped at `max_tokens` (`ChatResponse.stop_reason`, which every provider maps - `tests/test_llm_stop_reason_max_tokens.py` holds each mapping) is never used, because json-repair closes the cut body into a parse that looks complete. Each memory call retries it once at twice its budget, capped at the model's output ceiling (`model_limits.retry_output_budget`), and when the retry is cut too: compaction raises `CompactionTruncatedError`, so `manage_conversation_memory` keeps the previous compaction and persists nothing - and from the second consecutive cut the conversation's compactor calls pause (15 minutes, doubling per cut up to 6 hours, process-local), so a conversation that is always cut does not pay the compactor on every turn; reconciliation falls back to plain ADD (`curator_degraded`); fact extraction drops the cut last line; fact consolidation keeps the batch for the next run instead of deleting it for a cut merge; the user profile rewrite keeps the existing profile. Fact extraction, consolidation and the profile rewrite pass `disable_thinking` too. Every other utility call outside the agentic loop (which continues a cut answer itself) follows the same rule through `app/llm/cut_answers.py`: `answer_was_cut()` is the check they use, and `chat_retrying_a_cut()` asks once more at `retry_output_budget` - not at all when the model's output ceiling leaves no more room, the same request again - then hands a still-cut answer to the caller's own failed-call path: routing and a flow condition read it as the answer with no decision it is (the fallback target, the False / Default branch, the reason quoting it), the tool selector its error edge, the in-run summary the deterministic pruner, a title the fallback title, style learning fails as its provider call does (nothing stored), a workset item fails, an LLM-only evaluation case fails; the prompt generator and a comment draft, whose text a person edits before anything is stored, return it as generated with `truncated: true`. A retry is metered as a second call: its own generation where the caller traces its calls (the in-run summary's is flagged `cut_answer_retry`, its usage merged into the run), its usage added to the LLM-only evaluation's trace, charged to a workset's call ceiling in a short transaction of its own. The two classifiers pass `decided`: routing's number and a flow condition's yes / no or option number are read from the start of the answer, so a cut after them is used as is and only an answer cut before them is asked again; both pass `disable_thinking` (a flow condition unless its node sets a reasoning effort). The assignment activation gate and the Nova rule LLM check are deliberately left as they are: their decision is read from the answer's first word, which a cut after it cannot change, and an answer with no decision word still runs the assignment and does not match the Nova rule - `tests/test_utility_calls_cut_at_max_tokens.py` pins both. A stream's own stop reason is read through `StreamStopReason`, never off the provider: the router caches a provider and concurrent requests share it, so `BaseLLMProvider.last_stop_reason` also records each write for the task iterating the stream (`task_stream_stop_reason()`; the failover wrapper, which only copies it, records nothing). The OpenAI-compatible proxy (`api/v1/llm_proxy.py`) reports `finish_reason: "length"` for a cut upstream answer on every path, every other value unchanged.

## Streaming reasoning text (the chat reasoning window)

A streaming call that passes an `on_thinking` consumer is asking for reasoning TEXT, and several providers return none unless the request says so. The signal is `reads_reasoning(on_thinking)` (`base.py`), never the callback merely being set: when nothing reads the reasoning, the agent loop's idle watchdog still hands the provider a `ThinkingActivitySink` so thinking deltas count as liveness, and a silent run (an assignment) must not pay for text nobody reads. Each provider opts in on that signal only - a caller that reads no reasoning keeps the provider default - and never on `chat()`:

- **Anthropic** (`_apply_summarized_thinking`): Claude Sonnet 5, Opus 5 / 5.5, Fable 5 / 5.1 and Mythos think by default but default `thinking.display` to `"omitted"`, which streams no `thinking_delta` at all. The provider sends `thinking: {"type": "adaptive", "display": "summarized"}` to the models `model_capabilities.requires_summarized_thinking_opt_in` names (adaptive is their default mode, so only the returned text changes), and leaves a `thinking` config the call already carries alone. Opus 4.7 / 4.8 omit the text too but do not think unless asked: opting them in would turn thinking on, a cost and behaviour change, so they stay out of the rule. `_ThinkingBlockJoiner` opens every thinking block after a response's first on a new paragraph (Fable 5.x writes a progress update as a block of its own). That text is for display only: no replayed block is ever built from it. By default `_build_anthropic_messages` replays an assistant turn as its text and `tool_use` blocks, never a `thinking` / `redacted_thinking` block. Adaptive thinking accepts such a turn (only manual `enabled` mode requires the final assistant turn to open with a thinking block), but it is not Anthropic's tool-use protocol, which asks for a tool-use turn's thinking blocks back, complete and unmodified: without them each tool round resumes without the reasoning that led to the call. The guarded replay below closes that gap behind a flag: it sends the SDK's blocks as captured from the raw deltas, never `ChatResponse.thinking` (a modified thinking block is a 400), and only while the system prompt, tools and messages before them are unchanged - from Claude Fable 5.1 on a block is only valid then, and progressive tool disclosure (`load_tools`) and in-place tool-result pruning both break it. Billing is the same for both displays: omitted only buys an earlier first answer token.
- **Gemini** (`_streaming_thinking_config`): thought summaries only come back with `ThinkingConfig(include_thoughts=True)`, set for the families that think (2.5 and later), merged with the reasoning-effort level / budget. Thought parts reach `on_thinking` only, never the answer, and stay in the verbatim `gemini_parts` replay of a tool-calling turn: on `generateContent` a thought signature can ride on any part.
- **OpenAI-compatible** (`openai_reasoning_text`): `reasoning_content` (DeepSeek, LiteLLM, vLLM) or `reasoning` (OpenRouter, recent vLLM / Ollama), one field, never both. Mistral instead sends `content` as a list of `thinking` and `text` chunks once `reasoning_effort` turns reasoning on: `openai_content_parts()` splits it on every path (`chat()`, `chat_stream()`, the tool stream), so the `thinking` chunks reach `on_thinking` and only the `text` chunks reach the answer. The LLM proxy's OpenAI-compatible pass-through (`/v1/chat/completions`) forwards the chunks to its client unchanged and reads the answer text with the same helper for the trace and the metering.
- Not covered: OpenAI direct (Chat Completions exposes no reasoning; summaries need the Responses API) and Bedrock (the Converse provider reads no `reasoningContent`).

The agent loop gives every model call its own `on_thinking` (`_new_on_thinking()`), which opens that call's reasoning on a new paragraph in the pane and the persisted reasoning; the generation's trace capture keeps the provider's text verbatim. However much streams, what is kept stays bounded: the persisted reasoning is `ReasoningAccumulator`'s 20,000-character head + tail (`api/v1/chat.py`, shared with the platform relay), the chat window renders a 6,000-character tail and the public widget keeps at most 4,000 characters, cut back to the last 2,000. The Gemini replay and the Anthropic thinking capture are the copies with no character cap: every tool round's thought parts ride in `gemini_parts`, and every thinking block in `_provider_extra["anthropic_thinking"]`, until the run ends (in memory, never persisted), counted by each provider's overflow check (`_measure_gemini_payload`, `_measure_anthropic_payload`). Only the Gemini parts are for the provider-extras hook of the agent loop's gates: a thought signature must be re-sent. The Anthropic blocks deliberately never are - they are droppable (below).

## Replaying thinking blocks within a tool round (Anthropic)

Anthropic asks for the thinking blocks of a tool-use turn to be passed back "complete and unmodified" when its tool results are answered. Replayed as text + `tool_use` only, which adaptive thinking accepts (no 400), each tool round of a model that thinks by default (`model_capabilities.thinks_by_default`: Sonnet 5, Opus 5 / 5.5, Fable 5 / 5.1, Mythos) resumes without the reasoning that asked for the tools. Replaying blindly is not safe either: a modified block is a 400, and from Fable 5.1 a replayed block is only valid while the system prompt, the tools and the earlier messages are the ones it was produced under - which the agent loop rewrites routinely (`load_tools`, the tool-result curation, pruning, compaction, and every system nudge, all merged into the one system string). `app/llm/anthropic_thinking_replay.py`, behind `ANTHROPIC_THINKING_REPLAY_ENABLED` (default off):

- **Capture.** `chat()` (from `Message.content`), `chat_stream_with_tools()` and `chat_stream()` (from the events, `StreamedBlocks`: raw `thinking_delta` text concatenated, the `signature_delta` assigned as the SDK does, a `redacted_thinking` block whole from its `content_block_start`) keep the response's layout - thinking / redacted blocks verbatim, text blocks, one marker per `tool_use` - as a `ThinkingCapture` on `_provider_extra["anthropic_thinking"]`: in memory only, never persisted (`serialize_messages` drops it), never shown. The agent loop already carries `_provider_extra` onto the assistant turn it appends; `chat_stream` exposes it as `last_provider_extra` (with `last_trace_metadata`), which `_streaming_chat` and the failover wrapper forward like `last_usage`. A model that does not think by default captures nothing, and neither does a response holding a block that could not be re-sent as returned: a thinking block without its signature, a redacted block without its data, a block the stream never closed (the SDK ends a stream the connection closed cleanly without `message_stop`).
- **Fingerprint.** A turn that calls tools also stores a `PrefixFingerprint`: SHA-256 of the canonical JSON of the tool definitions as sent (taken before prompt caching adds its markers), of the merged system prompt, and - a running digest - of every earlier message exactly as sent, the earlier turns that got their blocks back included. With the setting off nothing is hashed.
- **Replay.** `ThinkingReplay.apply()` (run by `_prepare_request`) re-emits a turn's blocks in their original positions only when the setting is on, the model thinks by default, the request runs in the same `adaptive` thinking mode on the same model, the turn belongs to the current tool round (`current_tool_round`: the trailing unbroken run of `tool_use` turns each answered by a turn of tool results only - a human message ends it), the turn is still what the model produced (its text + `tool_use` rendering digests to the captured one; the argument coercion rewrites `tc.arguments` in place), and the recomputed prefix fingerprint equals the stored one. A `chat()` call made with `disable_thinking` never re-sends blocks, whichever form turned thinking off (the adaptive + lowest-effort form on a model that refuses `disabled`). Every other turn goes out as text + `tool_use`, exactly the bytes sent before. Three strips are final (`RETIRING_REASONS`: the round ended, the loop rewrote the turn, the API refused its blocks) - a retired turn is never re-sent its blocks, so a refusal costs one 400, not one per request; any other strip (a prefix that can come back, another model, thinking off for one call, the context budget) is decided again by the next request.
- **Fail safe.** Blocks that would take the request over the overflow threshold are dropped again (`context_budget`). A refusal the API answers to what the request re-sent (`ThinkingReplay.refused_by`: a 400 whose structured error message refuses a thinking block or signature - `rejects_replayed_blocks`, never a bare word a tool name could carry - or names a turn the replay laid out again, `messages.<i>.content...`; or a refusal of the request's size, a 400 "prompt is too long" or a 413, since the blocks' pre-flight estimate is chars-based) is retried once without the blocks, on all three paths, and retires the re-sent turns (`retry_without`); any other error, and any refusal of a request that re-sent nothing, propagates unchanged. The classifiers read the API's structured error message (`body.error.message`) only, never the SDK's rendering of the exception, which folds in the whole response body: a proxy's page or a malformed 400 can echo the request, the user's own words included. A body without that message (a proxy page, plain text, another envelope) is never a refusal - bar a 413, a size refusal whatever its body; a gateway re-wrapping the error in the same envelope (LiteLLM) still is; an `error` event mid-stream rides the stream's 200 and never is. `retry_error` (and its WARNING line) carries that structured message, bounded, or the error class and HTTP status alone - never the body.
- **Measure.** `ChatResponse.trace_metadata["thinking_replay"]` = `{enabled, outcome (replayed / partial / stripped), replayed_turns, replayed_blocks, stripped_turns, stripped_blocks, reason, reasons, retry_error?}` on every request that carried a captured turn, merged into the LLM generation's metadata by the agent loop (`_record_request_trace_metadata`, Langfuse and the durable store alike). `reason` is that of the latest stripped turn: `flag_off`, `not_tool_round`, `model_changed`, `thinking_config`, `turn_changed`, `prefix_changed:tools`, `prefix_changed:system`, `prefix_changed:messages`, `context_budget`, `retry_without`.
- **Counting.** A re-sent block is input the model reads. The provider's own overflow check counts it (`_measure_anthropic_payload`, `block_chars`: the larger of the visible text and the decoded signature, which carries the whole reasoning) and sheds the blocks when they would overflow (`context_budget`): that is the one place they are counted. They are deliberately NOT registered with the loop's provider-extras hook ("Provider extras" below), and a tripwire test (`test_the_replayed_blocks_are_never_registered_on_the_loop_gates`) keeps it that way: the blocks are droppable where Gemini's thought signatures are required. The provider owns them - it decides per request whether to re-send them and sheds what would not fit - while every gate that reads the hook acts on the transcript or the run (the compaction trigger and its prune, semantic compaction, the 95% overflow guard, the emergency prune and `ContextOverflowError`, the forced-answer guard, the run-budget reservation that stops or downgrades). Counted there, the blocks would make the loop prune real transcript content, stop the run or fail the turn for blocks the provider strips anyway: any rewrite of an earlier message invalidates their prefix, a model change strips them, and they sit on the current round's turns, which no compaction removes. The loop gates stay provider-agnostic and measure what every request always carries; the replay only ever adds blocks the provider has checked fit.

Scope: the direct Anthropic provider only. Bedrock uses the Converse API (it reads no reasoning content), OpenRouter / LiteLLM the OpenAI-compatible builder. No prompt text is involved (invariant 16).

## Thinking blocks on the AI Gateway

The gateway returns a Claude response's blocks verbatim as `thinking_blocks` (streamed: `delta.thinking_blocks`) and takes them back on an assistant message. `app/llm/openai_thinking_blocks.py`, enabled by `replays_thinking_blocks` on `FiligranGatewayProvider` only, keeps them on a tool turn (`_provider_extra["openai_thinking_blocks"]`, in memory) and sends them back on the current tool round's turns when the provider, the model and the tool-call ids are unchanged; never with `disable_thinking`. No prefix fingerprint: a refused request is retried once without the blocks and retires them, unless the retry is refused too. The gateway's 502 marked `retryable: false` is read as the upstream status it names (`gateway_upstream_refusal`): a 400 is retried when the provider's message (XTM-One-Platform/ai-gateway#348) refuses a block or a signature or says the prompt is too long, or carries no message; a 413 always; another 4xx never, as a direct one. Blocks that would overflow the window are dropped for that request. The gateway sends every block before the text and tool calls, so an interleaved turn goes back reordered.

A Gemini tool call's thought signature (`tool_calls[].extra_content.google.thought_signature`, chat and streamed) rides the same replay: kept on the turn's `ThinkingBlocks.signatures` and sent back on that call. Signatures outlive what the blocks do not: the overflow drop sheds the blocks first and the signatures, for that request only, when they alone do not fit; a refusal retires them only when its message names a thought signature (`refuses_replayed_signatures`, final: never restored), and a size refusal sheds them for its retry only. A refusal that would leave the request unchanged is not retried. Round turns are paired with the request's assistant messages by position, never by call id: a gateway before XTM-One-Platform/ai-gateway#347 restarts Gemini's ids at `call_0` every response. When Gemini serves the model (name, pinned target or listed owner, `_upstream_of`), its tools also go through `gemini_wire_tools`, the direct provider's cleaning, and its tool results carry the tool `name`.

## Checking a request shape against the real API

The provider unit tests mock the SDK: they pin what a provider sends, never whether the API accepts it. After changing a request shape (a `thinking` or `output_config` form, a replayed block, a new parameter), run the opt-in live smoke suite `backend/tests/live/` against the real API: it builds the providers through `build_provider()` and covers the reasoning display opt-ins above, the tool loops (Anthropic, Gemini thought signatures) and the lowest-effort form. Skipped unless `LIVE_LLM_SMOKE=1` and the provider key are set; real cost, never in CI - see its README.
