# Services: memory

Service map rows and patterns for agent, user, persistent and conversation memory, deletion tombstones and memory events in `backend/app/services/`; the binding rules live in `backend/app/services/AGENTS.md`.

## Service map

| File | Purpose |
|------|---------|
| `persistent_memory.py` | Durable agent memory with vector search: persists consolidated memories and extracted facts to PostgreSQL with embeddings. Includes **conflict-aware reconciliation** (`reconcile_and_persist_facts`) so new facts can SUPERSEDE / MERGE / SKIP contradicting old entries instead of coexisting with them. **State entries and supersession**: an entry names the object it describes (`subject_key`); a newer `state` entry on a subject, or an entry naming `supersedes`, flags the writer's own older entries (`superseded_at` / `superseded_by_id`, kept and searchable), `retire_memories()` retires without a successor, and `superseded_for_reader()` is the one read rule (flagged, or outdated by a newer state entry the same reader sees) - the prompt loader and renderer leave such entries out, the search ranks them last. Contract: `dev-docs/reference/agents-and-assignments.md` > "Persistent Agent Memory". |
| `agent_memory.py` | Short-term + consolidated agent memory (Redis). Auto-consolidates after 5 interactions (`CONSOLIDATION_THRESHOLD`); an oversized medium-term summary is compressed before it is stored (`_MAX_MEDIUM_TERM_PROMPT_CHARS`). |
| `user_memory.py` | Cross-agent user memory (Redis), scoped by agent: the user's PROFILE is read by every agent, each NOTE an agent's work left by that agent only. Interactions record their agent (`store_user_memory(agent_id=...)`); after 6 the consolidation model answers JSON `{profile, notes}` and decides which statement is about the user and which is an agent's work, while the code sets the owner (the window's agent), the freshness and who reads it - no keyword list, no classifier, nothing about what a note is about (`test_the_user_memory_knows_no_integration`). `format_user_memory_for_prompt(memory, agent_id=)` renders what the receiving agent may read - every caller passes it. `migrate_legacy_profile()` has the same model split a free-text profile written by an older build, which no agent reads until then. Every write of the entries goes through `update_entries()` (Lua compare-and-set of the entries and their profile copy, retried on a fresh read, dropped once the purge generation the writer read has moved), never a bare `SET`; a user's Clear is `purge_user_memory()`, clearing one agent also runs `forget_agent_notes()`. `user_mem:medium:` keeps the rendered profile alone and interactions go to `user_mem:recent:`, both so an older replica never shows a note or another agent's interaction. The profile is bounded by `_MAX_PROFILE_CHARS`: a rewrite over it, or an existing profile a rewrite cut twice could not carry, is condensed by one LLM pass and cut at its last whole line within the cap if that pass does not fit; the injected copy is cut the same way. |
| `user_memory_entries.py` | The entries of the user memory and the ONE read rule: `MemoryEntry` (`scope` `global` / `agent:<id>`, `owner_agent_id`, `created_at`, `last_verified_at`, `ttl_seconds`, `perishable`), `new_entry()` (a perishable note gets `PERISHABLE_TTL_SECONDS`), `keep_history()`, `visible_to()` (the profile + the agent's own live notes, nothing else), `render_line()` (the `UNVERIFIED as of <date>` label). Pure, no Redis, no text inspection: what an entry says never decides who reads it. |
| `user_memory_maintenance.py` | The hourly user-memory sweep (install-wide lease, background task, run only while agentic AI may run): has the consolidation model split each free-text profile written by an older build (`migrate_legacy_profile()`, given the agents the user worked with in the last 180 days, at most `_MAX_MIGRATIONS_PER_SWEEP` a sweep) and drops expired notes, both through `update_entries()`. |
| `conversation_memory.py` | Automatic incremental conversation compaction with **Pinned Directives**: every compaction round produces (a) a structured directives block with the user's still-active constraints / corrections / format preferences that is *rolled forward* across cycles, and (b) a concise rolling summary. Memory auto-flush extracts key facts and calls `reconcile_and_persist_facts` so contradictions supersede old durable entries. |
| `memory_tombstones.py` | Deletion tombstones for the Redis memory tiers: a purge buries a tombstone (`bury`) BEFORE deleting any key, and every detached writer (`consolidate_memory`, `consolidate_user_memory`) checks after its write and undoes it when one is there (`undo_if_buried`), so a late write never resurrects a purged account's or agent's memory. |
| `concierge/memory_steward.py` | Platform Health Memory Steward (#8258): one consolidation pass per memory **lane** (an agent's own pool, or one user's pool with an agent; never across lanes), only on lanes level 1's consent allows (`memory_steward_deps.memory_lane_readable`). Merges duplicates (same text, cosine >= 0.92 in one embedding space, or a group the model names: newest kept), settles contradictions (newest wins unless the older is confirmed more often, then `flag`), demotes time-bound entries past `PERISHABLE_TTL_SECONDS`, promotes a medium-term bullet that survived 3 summary versions (`source="memory_steward"`). Writes land in the persistent tier only (`superseded_at`, the flag the prompt already honours); each change is a `memory_consolidations` row; an undone one, or a promotion whose entry was deleted by hand, is never redone (its `fingerprint` kept in `memory_consolidation_tombstones` until the lane's purge). Unchanged lane (`memory_lane_checkpoints.fingerprint`): no read, no model call. Dry-run (level 2) writes nothing. Tools: `builtin_tools/memory_steward.py` (`list_memory_lanes`, `consolidate_memory_lane`, `list_memory_consolidations`), refused outside a health run; REST: `api/v1/memory_consolidations.py` (`/settings/me/memory/consolidations`, `/agents/{id}/memory/consolidations` for managers). |
| `concierge/memory_steward_plan.py` | The Memory Steward's planning, pure (#8258): `parse_verdict` keeps the model's answer to well-formed 1-based groups; `plan_entry_operations` (merge, then contradictions, then demotions; one operation per entry per pass; a model-named duplicate group never grows past `MAX_MODEL_GROUP`; a recorded `fingerprint` is never planned again); `observe_summary` / `plan_promotions` (a medium-term bullet seen in `PROMOTION_SEEN` summary versions). `memory_steward.py` reads the lane and applies the plan. |
| `concierge/memory_history.py` | The Memory Steward's history (#8258): `Lane`, `list_consolidations` (one user's lanes, or one agent's own lane), `consolidation_counts` (the digest), `undo_consolidation` (all or nothing, 30 days: `memory_holds.RETENTION_DAYS`, B19), `purge_expired_consolidations` (hourly, autonomous tick; undone rows after 90 days), `purge_lane_consolidations` / `purge_entry_consolidations` (a user's own deletion, at once; deleting the winner of a contradiction restores the older entry) and `purge_on_revocation` (a user's opt-out, registered with `consent.register_revocation_handler`). |
| `memory_holds.py` | `held_by_consolidation()`: an entry a Memory Steward change keeps for its undo, which `enforce_memory_cap` and `prune_old_memories` leave to the consolidation purge. |
| `memory_flow_events.py` | Durable memory writes on the flow event bus (#516): `persist_memory` emits a typed "Memory persisted" `FlowEvent` (seeded event type) so an `On event` flow reacts within a reconciler tick; the chain context (`set_memory_chain_context`, bound by the assignment adapter) bounds self-retriggering at `EVENT_CHAIN_MAX_DEPTH`. |

## Memory System

Five-tier memory architecture:

| Layer | Storage | TTL / Persistence | Consolidation | Used by |
|-------|---------|-------------------|---------------|---------|
| Agent short-term | Redis (per agent and lane) | 24h | Rolling 10 entries | Assignment engine, agent chat |
| Agent medium-term | Redis (per agent and lane) | 30d | After 5 short-term items → LLM consolidation | Assignment engine, agent chat |
| Agent persistent | PostgreSQL + pgvector | Durable | Auto-persisted on Redis consolidation + fact extraction during context compaction | `search_memory` tool |
| User memory | Redis (per user ID): profile for every agent, notes per agent | 30d; perishable notes 72h | After 6 interactions; hourly sweep drops expired notes and splits older profiles | Assignment engine, agent chat, public widget |
| Conversation memory | DB (messages table) | Durable | Sliding window summarization with memory auto-flush at 60% of the model's context window (estimated tokens), or past 45 messages as a safety net | Chat services |

**Lanes.** The agent's Redis tiers are kept per lane (`agent_memory._base_key`): a user's lane with the agent (`scope_id=<user id>`), an anonymous conversation's (Redis only, never persisted), or the agent-level lane (`scope_id=None`). A consolidation persists in its lane's scope, and every user's chat reads the agent-level pool (`persistent_memory._readable_by`), so only the designated agent-level writer inside a trusted autonomous run writes it (`agent_chat._derive_memory_scope_id`). An assignment run reads and writes the lane of the user it acts as (`assignment_helpers.assignment_memory_scope`: `run.user_id`, else the agent's owner; a run with neither stores nothing), never the agent-level one: its summary can hold what that user's integrations and knowledge bases returned. Runs and that user's chats share the lane's short-term window and consolidation count, so a frequent schedule moves the user's recent chat turns into the medium-term summary sooner; the self-heal pass a run schedules compresses that lane.

**Who changes an agent's memory.** The REST write routes (clear `DELETE /agents/{id}/memory`, `POST /agents/{id}/memory/maintain`, edit and delete of an entry, import) require `helpers.can_manage()` (`agent_memory._managed_agent`): the owner, an admin, or a `config` / `config_with_chats` grantee; a `read_only` grantee gets 403 (`tests/test_agent_memory_grantee_writes_postgres.py`).

**Conversation compaction with Pinned Directives** (`conversation_memory.py`): Once the estimated tokens of a conversation's history (characters / 3, the agent loop's estimate) pass `COMPACTION_WINDOW_SHARE` (60%) of the context window of the model the compactor runs on (`compaction_context_window`, resolved like the agent loop's window: admin override, model metadata, family table, provider default), with at least `_MIN_TOKEN_TRIGGER_BATCH` (4) messages beyond the recent window, or once its message count exceeds the `SUMMARIZE_THRESHOLD` safety net (45 messages, below the 50 rows `get_conversation_history` loads), the oldest messages (everything before the last `KEEP_RECENT` = 15) are compacted into a single system message. The share applies to each model's own window (a 1M-window model is summarised at ~600k tokens, a 128k one at ~77k); until #8497 the message count at 30 was the only trigger, blind to the window. On the count, the re-compaction interval is `SUMMARIZE_THRESHOLD - KEEP_RECENT + 1` (31 new messages per cycle with the strict `>` trigger), and the gap `SUMMARIZE_THRESHOLD - KEEP_RECENT` MUST stay at least as large as the keep-window — the `should_compact()` predicate is the single trigger source of truth shared with the chat "Summarizing…" status frame. The compaction message contains:

- **Pinned Directives** — a bullet list of every still-active CONSTRAINT, CORRECTION, FORMAT REQUIREMENT, or PREFERENCE the user has set (e.g. "use field filter on subregion, not country", "currency prefix is €", "ADS metrics must be YTD average"). The block carries forward across every subsequent compaction cycle: parsing the prior compaction message yields the previous directives, which are fed back into the next LLM call so the compactor can remove now-superseded entries and add new ones.
- **Rolling Summary** — a concise narrative recap that grows incrementally, never rebuilt from scratch.

The compaction message is prepended to the trimmed history with strong "treat these as active instructions, never silently revert" framing, so even in 100+-turn conversations the LLM keeps the user's early instructions in view.

**Cross-agent personal preferences (language, tone, communication style) are NOT stored in agent memory at any tier** — they are routed exclusively through the platform-wide user profile (`user_memory.py`). The agent-memory consolidation prompt, the persistent-memory fact-extraction prompts (both `extract_and_persist_facts` and `reconcile_and_persist_facts`), and the conversation-compaction Pinned Directives prompt all explicitly exclude these from agent-side memory. This prevents shared/per-user agent memory from pinning a stale language preference (e.g. an agent replying in French to a user who has switched to English) and keeps the user profile as the single source of truth for cross-agent preferences.

**Memory auto-flush with reconciliation**: Before compaction, key facts are extracted from the messages being summarised and passed through `persistent_memory.reconcile_and_persist_facts`. For each candidate fact the system pulls existing entries in the **contradiction zone** (cosine similarity ∈ [0.65, 0.92)) and asks an LLM curator to decide ADD / SKIP / SUPERSEDE / MERGE. Superseded ids are deleted; merged content replaces both originals. Plain ADDs still benefit from the standard 0.92 dedup short-circuit inside `persist_memory`. When the curator fails (after one terser retry) every candidate is a plain ADD and the result reports `curator_degraded`.

**Memory hygiene** (`persistent_memory.py`): Automated maintenance keeps persistent memory healthy for long-running agents:

| Mechanism | Function | Trigger |
|-----------|----------|---------|
| **Semantic deduplication** | `_is_duplicate_fact()` — checks cosine similarity ≥ 0.92 before persisting | Every `persist_memory()` call for facts |
| **Age-based pruning** | `prune_old_memories()` — removes facts and state entries older than 90 days | Hourly (autonomous scheduler) + on-demand |
| **Per-agent cap** | `enforce_memory_cap()` — evicts superseded facts first, then the oldest, when count exceeds 200 | Hourly (autonomous scheduler) + on-demand |
| **Subject history** | `persist_memory()` — keeps at most 10 superseded state entries per (agent, scope, subject) | Every state write that supersedes |
| **Fact consolidation** | `consolidate_agent_facts()` — LLM merges batches of 15 oldest facts into condensed summaries | Hourly (autonomous scheduler, when ≥ 50 facts) + on-demand |
| **Health stats** | `get_memory_health()` — returns entry counts, staleness, cap status, config | API: `GET /agents/{id}/memory/health` |
| **On-demand maintenance** | `run_memory_maintenance()` — orchestrates all hygiene tasks across all agents | API: `POST /agents/{id}/memory/maintain` (single agent) or hourly scheduler (all agents) |
| **Reactive self-heal** | `auto_heal_agent_memory()` — per-agent hygiene (prune, cap, consolidate, re-embed) + Redis medium-term compression, throttled by Redis `SET NX EX` for 6h: the hygiene per agent, the compression per lane | Fired automatically when the Redis tiers alone breach the assignment prompt cap; the persistent block never does - it holds the whole entries that fit in what the Redis tiers leave (`format_persistent_context(max_chars=...)`) |
| **Write-time clamp** | `consolidate_memory()` in `agent_memory.py` compresses an oversized medium-term summary (extra LLM pass via `_compress_summary()`, hard-truncate fallback) BEFORE storing it in Redis | Every consolidation cycle — the Redis tier can never accrete past `_MAX_MEDIUM_TERM_PROMPT_CHARS` |
