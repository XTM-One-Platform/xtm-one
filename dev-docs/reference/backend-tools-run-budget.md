# Per-run spending budget

How `run_budget.py` bounds an agent run in cost, tokens, tool calls and duration, the model downgrade, and the per-agent / per-flow override layer of `services/budget_policy.py`; the rules of this area live in `backend/app/tools/AGENTS.md`.

## 3d. Per-run spending budget (`run_budget.py`)

`max_iterations` bounds reasoning steps, not spend: one iteration can fan out into many parallel tool calls, and an expensive model can pass any intended spend long before a step limit. The legacy `run_agent_loop(max_total_tokens=...)` argument is a *soft* wind-down (tools stripped, run continues).

`RunBudget` bounds cost, tokens, tool calls and duration in one object, passed as `run_agent_loop(budget=...)` and enforced **in the loop** (never per provider), with the reserve → call → debit → block pattern:

1. **Reserve** — at the top of every iteration the loop reserves that call's *worst case*: the prompt as it stands (chars ÷ `_CHARS_PER_TOKEN`) plus the **full** `max_tokens` output allowance, priced from the model's own rates. When what is left cannot cover that allowance in every enforced dimension (cost and tokens, the stricter one binds), the reservation is **sized to the remaining budget** instead of refused: `try_reserve(..., min_output_tokens=MIN_OUTPUT_TOKENS)` reserves the largest allowance that still fits (`RunBudget.affordable_output_tokens`, a bisection over the same gate, so pricing stays `cost_calculator`'s one rule) and the call is made with exactly that `max_tokens` (`_call_max_tokens`), through the `max_tokens` kwarg every provider already maps - never above the model's own allowance, never below the floor (`MIN_OUTPUT_TOKENS` = 1024, or the model's allowance when that is smaller). A budget that covers the full allowance reserves and sends exactly what it always did, and the downgrade keeps its place: a call is sized only where it would otherwise be refused. A sized call spends everything that is left, so it is priced on what it is sent with: the tool definitions it carries (`_estimate_prompt_tokens(messages, tools)`, weighed like the context readout) and the messages the loop appends past the gate (the budget, step and wind-down nudges, the last-chance prompt), priced again right before the call, and the backstop sizes its synthesis with the closing instructions it sends. A sized call is followed only by calls the budget prices again (`_reprice_call`): its empty-response retry and its max-tokens continuations (`_continue_truncated_response(next_max_tokens=...)`) are sized to what is left or not made, and they stay priced for the rest of the iteration even once one of them fits in full again, as after a compaction that shrank the transcript the call was sized on (`_chain_sized`, reset by the gate); in the backstop a sized synthesis is continued only within the full limit and is not retried with the stronger prompt, also when a backstop compaction lets it fit in full. A sized answer is never delivered as if complete: one the budget could not continue ends with `BUDGET_EXHAUSTED_MESSAGE` (`_say_budget_cut`) and says so outside its text too, with `stop_reason="budget_exhausted"` (`answer_cut_by_budget()`), which the structured-output repair of `agent_chat` and `assignment_engine` reads so a cut payload is never re-serialized as a complete one; and a sized synthesis that comes back empty (a reasoning model can spend a lowered allowance whole) ends with the text a run whose synthesis the budget could not pay for returns (`_budget_exhausted_text`).
2. **Block** — a reservation that does not fit even at the floor (or whose prompt alone does not fit) is **refused**, and the refusal is a hard stop for the tool-calling phase (unlike the legacy soft token wind-down): the loop breaks to the Stage-3 backstop, which sizes the synthesis against the full limit the same way before it falls back to the digest.
3. **Debit** — `_merge_usage`, the single sink for LLM usage in the loop, debits the **actual** tokens and cost of every call (in-loop calls, max-tokens continuations, compaction summarisers, the forced answer).
   - The forced-answer backstop debits each of its calls **once**. `_continue_truncated_response` hands back the response it was given with the continuations' text appended and its `usage` still the first call's (each continuation is merged on its own), and the stronger-prompt retry replaces the first synthesis, so a synthesis response is merged through `_record_forced_usage` (under the model it names, like the in-loop calls) by whichever of the retry, the continuation and the final exit reaches it first, and never again; an aborted call's usage is merged by `_end_aborted_generation`. Its calls are traced like in-loop ones, as generations of the run's own span (the iteration spans are closed by then): `forced_final_answer`, `forced_final_answer:retry`, and `attempt:continuation:N` for their continuations, each closed with what the call returned, or with its error and the usage its stream reported before the end.
4. **Release** — the iteration's `finally` hands the worst-case reservation back, so the gap between worst case and reality is never lost to the run.

| Dimension | Limit | How it is enforced |
|---|---|---|
| Cost (USD) | `AGENT_LOOP_MAX_COST_USD` | Priced from `llm_model_prices` via `cost_calculator.price_usage` - the ONE pricing rule, which the trace store (`calculate_costs`, local and ClickHouse sinks, repricing) prices with too: the Langfuse-normalized detail keys (`input_cached_tokens` at the cache-read rate, `output_reasoning_tokens` and the other details at their side's rate) and the unaccounted remainder of a reported total are priced on both sides. Raw usage's nested `prompt_tokens_details.cached_tokens` (OpenAI, and Gemini's `cached_content_token_count`) is INSIDE `prompt_tokens`: that part is priced at the cache-read rate and the rest at the input rate, never subtracted twice (a `cache_read_input_tokens` bucket wins); `prompt_tokens` stays inclusive and the token count is unchanged. **Fails open**: with no price row for the model, cost is not enforced (WARNING logged) — missing pricing data must never stop every run. A reported total above what the input / output split prices (`cost_calculator.priced_token_count`, the formula's own reading) has the difference priced (`UsageCosts.estimated_cost`) at the HIGHER of the two rates, never as $0: a usage with no split at all (`{prompt: 0, completion: 0, total: N}`) WARNS once per run, xAI's reasoning tokens (in its total, not in its `completion_tokens`) are noted once per run at INFO. The non-streaming OpenAI providers keep the server's `total_tokens` and `prompt_tokens_details` for this (`openai_compat.extract_openai_response_usage`, like the streaming `extract_openai_usage`). A run's summed usage (`_merge_usage`) keeps its calls' `*_tokens_details` maps, so its root trace prices like its generations; the root trace's token columns and the run's token totals are read without them and still count the cached prompt tokens. A run whose calls report usage in different conventions (a failover or a downgrade to another provider's model: Anthropic's `input_tokens` next to OpenAI's `prompt_tokens` / `total_tokens`) cannot be read back from that flat sum, and a run two models served cannot be priced at one price row even when its calls share a convention (a Gemini call next to a Bedrock one: every token at the root model's rates, and Bedrock's `cache_read_input_tokens` bucket drops the cached tokens Gemini counts inside `prompt_tokens`). So the loop also keeps its usage per convention and serving model (`_RunUsageParts`, `langfuse_tracing.usage_convention`) and attaches it as `usage_parts` only while the calls that reported tokens fill more than one part and either span more than one convention whose flat reading loses tokens or were made with more than one model (a response that reported only zeros, such as a compatible server's response without a usage object, is no second convention and no second model): the root trace and the run's token totals read each part with its own convention, and the trace sink prices each part at its own model, so the root trace is the sum of its calls. A call counts toward the model it was made with - the failover wrapper's `last_model` when a fallback served it, else the run's model, which a budget downgrade replaces - never the name its response carries (a non-streamed OpenAI or Anthropic call names the API's dated model, a streamed one the model it was asked for). The legacy soft token wind-down (`run_agent_loop(max_total_tokens=...)`) reads the flat sum. A run one model served in one convention carries no parts and records exactly what it did, whatever names its responses carry. Every call is recorded under the model its response names, the one its generation records: the loop's own call sites pass it (`_merge_usage(usage, served_model=...)`), and so do the helpers the loop hands its usage hook (`UsageHook`: the compaction summariser, a max-tokens continuation, the forced answer) and `_end_aborted_generation` for a call a failover fallback was serving (the model the wrapper noted on the call's `StreamUsageSink`). Only a call that never returned and that no fallback was serving hands its usage over alone: it goes to the run's model, the one the call was made with and its generation keeps, whichever model served its convention earlier in the run. |
| Tokens | `AGENT_LOOP_MAX_TOTAL_TOKENS` | Hard block when the budget object is active. The legacy `run_agent_loop(max_total_tokens=...)` argument keeps its soft wind-down for callers that pass it directly. |
| Tool calls | `AGENT_LOOP_MAX_TOOL_CALLS` | Counted per **batch** at the single pre-dispatch choke point, not per iteration — one iteration can fan out into many parallel calls, which is exactly what `max_iterations` fails to bound. `load_tools` reveals and dry runs are not counted. A batch larger than what is left (`RunBudget.remaining_tool_calls()`) crosses the ceiling. By default it runs in full, as it always did: one WARNING per run names the budget, the batch and the overshoot, the iteration span records `tool_call_budget_overshoot`, and the next LLM call is refused. With `AGENT_LOOP_MAX_TOOL_CALLS_STRICT` (`RunBudget.strict_tool_calls`) it is **cut** to the remaining allowance: the calls past it are answered in place with a "Not executed" tool result (`_format_tool_budget_refusal`) and a `tool_done` event flagged `budget_exhausted`, never executed, never counted as a tool failure, never screened by the loop breaker, and tagged `ChatMessage.not_run = "budget"` (kept by `serialize_messages`), which is what leaves them out of the deterministic digest and out of `track_tool_usage`'s counts - never the text, which a tool could return verbatim. A pause the run owns (`_run_pause_names`: the loop's own `wait` when the loop offered it, and `check_task_status` only when every definition behind that name is the built-in `builtin:sub_agent` one) is neither debited nor cut, one per batch (`_debited_tool_calls`): a second pause in the same batch is charged like any call, since status polls run in the parallel gather and a batch of them would be the fan-out the ceiling bounds; a custom or MCP tool that merely carries one of those names is always charged. Cut calls are answered before the kept calls run; every provider builder sends the results back in call order (`llm/base.tool_results_in_call_order`). |
| Duration | `AGENT_LOOP_MAX_DURATION_SECONDS` | Folded into `wall_clock_deadline` (tighter bound wins) so duration keeps the existing enforcement path — the in-loop minimum-budget guard, per-call timeout capping and the forced-answer reserve — instead of a second, parallel one. |

Three details worth knowing before changing this:

* **The closing-synthesis reserve** (`AGENT_LOOP_BUDGET_FINAL_ANSWER_RESERVE`, default 10%). In-loop calls are gated at `limit * (1 - reserve)`; the forced-final-answer backstop is gated against the **full** limit (`final=True`), so an exhausted budget still buys the one call that turns the work into an answer. When even that is gone, the backstop returns the deterministic tool-result digest **without any LLM call** — the money/token mirror of the wall-clock shortcut. The reserve deliberately does **not** apply to tool calls (the synthesis is tool-free, so a 50-call budget admits 50 calls before the gate refuses; only strict mode also cuts a batch that crosses it) or to duration (which already gets an equivalent reserve in seconds).
* **A warning before the block.** Crossing 75% of any dimension injects a one-shot consolidation nudge (`_BUDGET_NUDGE`) plus a user-visible `thinking_text` event, mirroring the wall-clock nudge. The model cannot see the budget, so being told the remainder is small is the only way it can spend it well.
* **A third outcome: degrade instead of stop** (`AGENT_LOOP_BUDGET_FALLBACK_ENABLED` — off by default). A per-run cost cap and a usable result are not actually in conflict: an operator who caps a run at $0.50 on Opus means "not more than $0.50 *at this quality*", not "abandon the task". When the **cost** gate refuses a call and a fallback model is configured, `RunBudget.can_downgrade` re-prices the very same reservation with the fallback's `ModelPrice`; if it fits, `commit_downgrade` swaps the price row for the rest of the run and the loop switches provider + model and carries on — **once per run**, never a ladder. Bounded on purpose: cost only, because tokens / tool calls / duration are model-independent (a cheaper model buys no extra wall clock). The loop re-derives everything it had pinned to the primary (`max_tokens`, and the context budgets when it derived them itself — the per-iteration compaction then brings an oversized transcript under a *smaller* fallback window before the next call), drops `reasoning_effort`, tells the model what happened (`_MODEL_DOWNGRADE_NOTICE`) and emits a `model_downgraded` event; the existing `llm_step` events already carry `llm_model` per call, so cost attribution stays readable. `_plan_model_downgrade` holds the three guards that keep the **hard stop** instead: a fallback window too small for the system prompt, a provider `max_tools` below the run's tool surface (for a gated run that surface is the gate's *minimum* — always-on core + `load_tools` — because the gate is re-capped to the fallback's `max_tools` on the switch and LRU-evicts revealed groups, which the downgrade notice names, while the catalogue message is rewritten in place for the new cap, rather than refusing a switch over an inventory that was never on the wire in one piece — with the floor that a gated run is never moved onto a provider whose `max_tools` is below `MIN_GATED_BUDGET`, since a gate cannot be re-capped below what it could have been built on), and a cross-provider switch that would silently drop native structured output. The closing synthesis degrades too — writing the final answer on the cheap model beats the deterministic digest.

Wiring: assignment runs build the budget in `services/assignment_engine.py` (`build_run_budget` + `resolve_budget_price`, resolved **before** the loop so no DB connection is held for accounting). The fallback model is resolved there too, from the *same* configuration surface the failover chain uses — `PlatformSettings.fallback_model` / `DEFAULT_FALLBACK_MODEL` via `llm/router.resolve_configured_fallback` — so there is one fallback model on the platform, not two. Every dimension at `0` (and no override, below) means no budget object at all: the run is unbudgeted.

### The override layer (`services/budget_policy.py`)

The table above reads the env settings through `budget_policy.platform_ceilings()` rather than `settings` directly, because those values are not the only configuration surface. `BudgetOverrides` is a **partial** policy object — `None` on a field means "inherit" — and `build_run_budget(overrides=...)` resolves a chain of them **nearest-wins, per dimension**:

    Budget node wired to the Agent node
      -> Budget the calling flow handed down (flow.call's `budget` socket)
        -> Agent.budget_config (the Budget tab)
          -> the platform env

Per-dimension is load-bearing: a layer that pins only cost must not unbound the tokens a further layer set — `flow_runner._compose_budget` merges the two CANVAS layers (wired node over inherited) for exactly this reason, rather than picking one dict.

**The agent's own budget is a BOUND on the canvas layers, not a default they replace** (`budget_policy.bound_by`, limits composed as `min`). Authority is checked against `platform_ceilings()` at write time and only there, so nearest-wins alone would let a non-admin's Budget node *widen* an admin-pinned `budget_config` while staying under the env value, making `budget_config` advisory and the env the sole real bound. The bound is applied at RESOLUTION time because that is the only place it holds: a flow is saved once, but the agent's budget can be tightened afterwards, so a save-time check goes stale. It applies to admins too — the run-time layer cannot tell who drew a node. The three ungated fields keep nearest-wins (none can increase spend). `flows._assert_budget_nodes_authorised` additionally gates the **edge set** of an above-ceiling node: gating the value alone would let a non-admin re-wire an admin-authored exception to every agent on the canvas.

Two more consequences worth knowing:

* **An override can activate a budget on an unbounded platform.** `budget_configured()` and both builders gate on the *resolved* configuration, not on `settings` — otherwise a per-agent budget would resolve and then be discarded on the (common) deployment that never set a global one.
* **Chat paths take overrides only.** `agent_chat.run_agent_chat(budget_overrides=...)` builds a budget **only when a nearer layer pins something**; the env values keep applying to assignment runs alone. Extending them to every chat message would bound conversations on deployments that configured a ceiling for autonomous work only.

`fallback_model` may also be pinned per layer, resolved through `llm/router.resolve_model_provider` instead of `resolve_configured_fallback` — an agent whose primary model IS the platform fallback has nowhere to downgrade to otherwise.

**Authority is enforced at the API edge, never here.** `ceiling_violations(submitted, previous=…, is_admin=…)` decides whether a write is allowed: tightening is always free, raising a limit above the platform ceiling needs an admin, and a value *unchanged* from what is stored is never re-litigated (otherwise one admin-raised budget would lock every non-admin out of editing the agent). Two enforcement shapes, chosen by whether the caller *authored* the value:

* **Authored** (agent create/update, flow create/update, flow detach — the detach body is a client-supplied graph, so it counts): `api/v1/helpers.assert_budget_within_ceiling` / `flows._assert_budget_nodes_authorised` raise 403 naming every offending dimension at once. A precise message is actionable when you typed the number.
* **Copied** (agent duplicate + import, flow duplicate + import + version restore): `helpers.lower_budget_to_ceiling` / `flows._lower_budget_nodes_to_ceiling` silently lower to the ceiling instead, mirroring what `clamp_max_iterations` already does on the duplicate path. Refusing a duplicate over a number somebody else typed would block the ordinary "adapt the company-managed entity" flow to prevent an escalation that lowering already prevents. Admins are exempt from the lowering — they could have typed the value.

A new endpoint that writes `budget_config` or a graph must pick one of the two; `tests/test_agent_copy_manifest.py` will catch a new `Agent` column, but nothing catches a new endpoint. Note that the restore path lowers a **deepcopy**: a `FlowVersion` is an immutable record, so editing its stored graph in place would rewrite history rather than restore it (hence `restore_flow_version(graph=...)`). `final_answer_reserve` / `fallback_enabled` / `fallback_model` are deliberately ungated: none of them can increase what a run spends.
