# Services: chat turns

Service map rows and patterns for agent and General Assistant chat turns, the turn lock, live fan-out, channel continuation, mentions, approvals and the consumer side of reasoning streaming in `backend/app/services/`; the binding rules live in `backend/app/services/AGENTS.md`.

## Service map

| File | Purpose |
|------|---------|
| `general_chat.py` | General Assistant chat (`run_general_chat`): loads the admin-configured resources (KBs, MCP, custom tools, integrations, handover agents) and runs the agentic loop. The trailing security anchor is `prompt_guard.build_security_policy(include_identity=True)`, `scan_user_input` flags the message, and an identity-override attempt gets a one-shot security reminder. |
| `general_assistant_link.py` | The agent linked to the General Assistant ("Link to Agent") that answers in its place: `stand_in_refusal()` (enabled, chat on, company-managed, not `access_restricted`) and `general_assistant_stand_in()`. A web conversation created without an agent is bound to it, and the settings API refuses a new link that does not qualify. `turn_stand_in()` says who answers a turn of an unbound conversation started outside the web chat, the same on every surface: the channel router, the web chat's REST and streamed sends, the wake and the conversation responses (`answering_agent_id`) ask it, for a user who may chat with the agent (`may_chat_with()`), else the General Assistant answers (conversation left unbound, the agent still the turn's answerer for compaction, @mentions, attribution and Activity). Never read `linked_agent_id` anywhere else. |
| `general_assistant_skills.py` | The skills the General Assistant carries: `GeneralAssistantConfig.skill_ids`, rendered like an agent's as a catalog with `load_skill` / `read_skill_resource`; `NULL` = the platform's choice, the built-in skills declared with `bind_to_general_assistant` (`GENERAL_ASSISTANT_SKILL_SLUGS`, `default_skill_ids`), so a new one reaches every General Assistant whose admin never chose; `effective_skill_ids` is what a turn carries (a General Assistant linked to an agent takes that agent's skills instead); `unbindable_skills` refuses a skill that is not a company-managed, enabled one. |
| `agent_chat.py` | Agent chat (`run_agent_chat`): builds the tools from the agent's configuration and runs the agentic loop with its persona; also the chat quota gate (`enforce_agentic_quota_ex`) and the lazy chat parent run of handovers (`_ensure_chat_parent_run`). |
| `chat_turn_guard.py` | Single-flight guard for chat conversation turns: `acquire_turn()` / `refresh_turn()` / `release_turn()` make the `chat:processing:{conv_id}` marker an enforced per-conversation turn LOCK (unique token value); `fold_into_inflight_turn()` + `drain_steering_inbox()` + `release_turn_and_drain()` implement the cross-connection steering inbox so a message sent while another turn runs (page reload mid-turn, second tab, another replica, REST client) is folded into the running agent loop as steering — with `SteeringPayload.file_ids` for attachments — instead of spawning a second concurrent loop. A fold the turn accepted but never read - past its last leftover check while it still held the lock, drained by `release_turn_and_drain()`, or bridged into its queue after its loop returned (`PartnerAnswerQueue.take_unanswered()`; the turn's end stops the bridge with `stop_bridge()`, once the batch it holds is queued) - is answered by a follow-up turn once the lock is released (`parent_wake.schedule_fold_follow_up()`, from the streamed and REST turns; a wake turn follows its own up), unless the turn was stopped: a Stop recorded (`recorded_stop()`) at or after the moment the turn took the lock asks none, whether or not a pass read it. Fold atomicity uses a push → check-marker → `LREM`-recover handshake, with one Lua call for the push of a partner's answer: its fold carries when the work was sent (`SteeringPayload.delegated_at`, written only when set) and is refused (`FoldRefusedError`) once a Stop at or after that moment is recorded (`record_stop()`); every drain that would deliver one re-checks it - the REST / streamed / parent-wake bridges and the streamed turn's leftover pass through `parent_wake.without_stopped_partner_answers()`, the wake's release by requeueing it instead of following it up. The marker check reads the holder's token, handed to a caller that passes `accepted_by` (#4395: the turn a fold went into, named in the fold responses). A successful `acquire_or_fold()` acquisition **purges the inbox** before returning: every fold is persisted as a user message before being pushed, so an entry still present when a new turn takes the lock (crashed marker, `requeue_stranded()`) is already in the history that turn loads — re-injecting it as steering would deliver it twice, ordered after the new user message. Used by the web chat's turn runner (`chat.run_chat_connection`) and REST `send_message`. `request_turn_cancel()` / `consume_turn_cancel()` are the cross-process Stop path: a Stop on a replica that does not run the turn binds a `chat:cancel:{conv_id}` request to the current marker token, and the in-flight turn's steering bridge (streamed turn, REST turn, parent-wake turn) consumes it on the next poll tick and sets the loop's `cancel_event` — token-bound, so a request never kills a later turn. The web Stop passes its client id (`request_turn_cancel(client_id=, keep_for_send=)`, one Lua script): with no turn it keeps the Stop for that client's send not yet holding the lock (`chat:cancel:pending:{conv_id}:{client_id}`, `PENDING_CANCEL_TTL_SECONDS`) only when the client says one is on its way (`awaiting_send` on the cancel route, `keep_for_send`), else it drops any kept one, since a Stop pressed as a turn ends finds no turn and must not end the next send; `consume_pending_cancel()` takes it right after that send's `turn_started` (a folded send never does); a Stop that reaches a turn drops it (`drop_pending_cancel()`). A web turn's acquisition also records it (`chat:turn:open:{conv_id}`, `OPEN_TURN_TTL_SECONDS`, #6046): its release forgets the record before the lock goes unless `mark_turn_interrupted()` kept it (called by `TurnPublisher.aclose(terminal=...)`), a dead process leaves it, and `interrupted_turn()` (a record whose token no longer holds the lock) is what `GET /chat/conversations/{id}` serves as `interrupted_turn`; `dismiss_interrupted_turn()` forgets it. Plain commands, best-effort, channel turns not recorded (`dev-docs/chat-turn-resilience.md` section 6). |
| `channel_continuation.py` | One conversation continued across the web, Slack and Teams, every rule in one place: `is_private_channel_thread()` / `web_listable_clause()` / `continuable_on_web()` (the web lists and continues web conversations and the owner's Slack DM threads `D...` and Teams personal chats `a:...` - never a group thread, an anonymous or another user's conversation), `web_continuation_refusal()` / `web_send_refusal()` (the REST and streamed sends, the conversation upload and the platform chat API refuse a Slack / Teams group thread, the platform chat API - whose turn takes no lock - every conversation a Slack / Teams turn can reach, `platform_chat_refusal()`; the REST and streamed sends also refuse rather than fold while a turn a channel message started holds the lock - `chat_turn_guard.acquire_turn(channel=...)` / `channel_turn_holder()`), the `ConversationChannelBinding` writes and the owner-scoped `find_bound_conversation()` the router reads before its own thread lookup, and `ChannelTurn` - the turn lock a channel message takes on a conversation the web also reaches (one attempt, keepalive, the web Stop as its `cancel_event`, `TurnPublisher` fan-out to the web, stranded folds requeued; fail-open when Redis is down). A Slack / Teams message that finds the turn taken is queued (`take_turn_or_queue`, `chat_turn_guard.enqueue_channel_message`, capped and expiring, redeliveries dropped by `claim_channel_message`) and answered as the next turn: every lock release starts `drain_channel_queue` (`chat_turn_guard._release_turn_inner`), which takes the lock before claiming (the message moves to `chat:channel_queue:{id}:claimed` until its turn answers it, forgotten by `ChannelTurn.release` before the lock goes; a claim a dead holder left is put back, `QUEUED_MESSAGE_ATTEMPTS` starts at most, never once its turn stored it, `_stored_turn`; a message queued past the TTL is dropped; a dropped message's sender is told, `_tell_dropped` through the adapter's `post_queued_notice`; an adapter that cannot answer at all raises `QueuedMessageUndeliverableError`), folds consecutive messages of one thread into one inbound and hands it to the adapter's `run_queued_message`, the router adopting the held lock; `sweep_channel_queues` (scheduler tick) restarts a queue, or a claim, whose lock holder died. The files of a queued message are stored marked (`queued_file_source`), claimed by its turn (`claim_queued_files`) and otherwise deleted, object before row (`discard_queued_files` through `widget_uploads.purge_unsent_files`, the hourly upload purge past `QUEUED_FILE_RETENTION`). A tool call left waiting for approval is retired as a web send retires it (`retire_pending_approval`). Routes: `api/v1/chat_continuation.py`. |
| `chat_turn_stream.py` | Live fan-out and resume of an in-flight chat turn — the reason a reload, a second device, an impersonating admin, a REST send or a parent wake all see the SAME turn the originating stream sees (full design: `dev-docs/chat-turn-fanout.md`). `TurnPublisher(conversation_id, turn_token, origin=...)` is held by whoever owns the turn lock: `offer(frame)` is synchronous and never blocks the loop, a drainer task batches the frames (`DRAIN_INTERVAL_SECONDS`), coalesces adjacent `stream` / `thinking_text` chunks (`coalesce_frames`), strips the heavy `tool_done` payload, a consulted agent's under `consult_progress.inner` included (`slim_frame`), stamps `origin` / `turn` / `seq` and writes ONE pipeline: the live batch on `chat:turn:{conv}` plus the **journal** keyed by the turn token — `status` frames in order (chatty ones excluded), the reasoning and the answer of the CURRENT segment as appendable strings (the client's own resets mirrored: a per-iteration `thinking` / `stream_retract` clears the answer, `transfer_start` the reasoning, an intermediate `done` both), the start time, the sequence number and the turn's agentic-action charges as running totals per quota period in the state hash (`agentic_actions`, #2545 - never in the trimmed status list, and counted as their batch is flushed, so a publish quiet period drops the frame but not the charge) (`journal_keys`, `JOURNAL_TTL_SECONDS`). `on_event` is the `run_agent_chat` / `run_general_chat` adapter for stream-less turns (REST, parent wake — `on_event` only, never `on_token`, so their LLM call mode is unchanged); every event travels as `event_frame()` builds it, a `status` frame except the charge, which is a frame type of its own (`AGENTIC_ACTION_FRAME`) that clients released before it ignore. Terminal frames are published BEFORE the marker is released - by every producer, the REST path included (`_rest_end_turn`: reply stored and committed under the lock, `done` offered, publisher closed, THEN `release_turn_and_drain`); `aclose()` flushes, drops the journal and leaves an `ended` tombstone in the state hash (`TOMBSTONE_TTL_SECONDS`, outliving the marker TTL) that `read_snapshot()` reads as "no turn in flight", so a viewer attaching between the close and the marker release is not resumed into a finished turn; the exits that never reach their own terminal (cancellation, a persistence failure, shutdown) close with `aclose(terminal=interrupted_frame())`, which offers an `error` frame on the turn's behalf only when none was offered yet (an intermediate `done` does not count), so viewers are released at once rather than at their next safety poll. `publish_live()` fans out a journal-less frame (`user_message`, published by whoever persists a user message — streamed send, steer route, REST, a channel turn); `publish_user_message()` builds that frame with the serializer the chat API registers (`set_user_message_serializer()`), so a service relays a stored message without importing the API layer. Best-effort by contract: a failure trips a PROCESS-WIDE quiet period (`FAILURE_COOLDOWN_SECONDS`, shared like `flow_run_stream.py`'s), never raises into the turn; polling stays the floor. The viewer side is `relay_turn_frames(conversation_id, origin=, send=, is_closed=, attached=)`, run per events stream for its lifetime (`attached` is set once each attachment's resume is handled): it listens through the process-wide `_RelayHub` (ONE Redis subscription per process, dynamic `SUBSCRIBE` per conversation, no I/O under its lock, fanned out to bounded per-viewer queues — a viewer costs no pooled connection; a confirmation or a reconnect queues `RESYNC`), and on every `RESYNC` reads `read_snapshot()` (the marker decides IF a turn is in flight, its token's journal describes it — a marker without a readable journal resumes from the ack alone) and replays `resume_frames()` through the client's own vocabulary: a `thinking` ack flagged `resumed` with `elapsed_s`, one `agentic_action` frame per quota period carrying the turn's charges, the status frames, one `thinking_text`, one `stream`; live frames are then forwarded flagged `relayed`, minus the viewer's own (`origin`), minus what the snapshot covered (`(turn, seq)`). The relay follows ONE turn at a time (the marker holder at the last `RESYNC`, or the turn whose frames it saw since): a TERMINAL frame stamped with another turn while one is followed is the late terminal of a turn that is over and is dropped rather than closing the newer turn on the viewer, while any other frame of another turn moves the relay onto that turn (its opening ack, or its first frame after a quiet period that swallowed the ack); `following` is a turn IN FLIGHT as far as the relay knows, never one it saw end: a `RESYNC` that finds no turn in flight (no marker, or the `ended` tombstone) or cannot read the snapshot follows NOTHING from then on, so the terminal of a turn that started and ended between the subscription confirmation and the snapshot read - queued right behind the `RESYNC` - is delivered instead of being read as stale, and the relay follows nothing again once it forwarded the followed turn's own terminal, so the `done` of a turn whose opening frames a publish quiet period swallowed still lands; a SUBSCRIBE that fails on a live hub connection (`_apply`) flags the reader to tear that connection down (`_resubscribe`), because the reconnect is what covers every listener channel again. Subscription changes are applied from the DESIRED state (`_apply`: subscribed iff the channel has listeners, re-read under a wire lock that serializes the connection's commands), never from the change that scheduled them - the unsubscribe a channel's last listener schedules is a no-op once a replacement attached, and that replacement is announced with a `RESYNC` since no confirmation will come; `detach` applies through a task so a viewer tearing down never waits on Redis. The hub runs one reader generation at a time: the last `detach` cancels the reader without waiting (a viewer tearing down never waits on Redis) and the next `attach` waits for that retiring reader before starting a replacement, since the reader's `finally` closes whatever connection the hub holds at that moment. The web chat routes gate the relay AND the cross-process Stop on conversation ownership. Every turn a relay SHOWS is owed an end (#4395, `_TurnRelay`), because a client following a relayed turn has no poll behind it: the tombstone keeps the terminal (`terminal`, `_stored_terminal`) so a resync after the turn ended delivers it; a publisher whose terminal or tombstone Redis refused delivers them once Redis answers (`_recover`: one pipeline after each quiet period, for `TERMINAL_RECOVERY_WINDOW_SECONDS`); a shown turn silent for `LIVENESS_CHECK_SECONDS` is probed (`probe_turn_end` - the lock is the liveness signal, the one `is_processing` reads) and, once over with nothing to recover, ended with `lost_turn_frame()` (`reason: "lost"`) after `TERMINAL_GRACE_SECONDS`, at once for a tombstone without a terminal; a turn superseded by another is ended before the next turn's first frame, never while it still holds the lock (the other turn's frame is then the stale one, dropped); a lone terminal of another turn lands only when that turn holds the lock (the newest turn, whose opening frames were lost); a provisional end (`is_provisional_end`: an end marked `provisional: true` - a Stop acknowledgement, the `error` of a streamed turn whose loop raised; any other end is final) releases the viewer while the final end that follows (the stored one, carrying `message_id`, or `interrupted`: a provisional end does not count for `aclose(terminal=...)`) still lands; and a copy of an end already delivered is dropped. Every turn frame names its turn with `turn_id` (`public_turn_id`, a digest - the lock token never leaves the server), on the stream that runs it and on every relayed copy (`publish_live()` takes only `NON_TURN_FRAME_TYPES`, so every turn frame on the channel comes from a publisher); `folded_into_active_turn` and the REST `202` (folded or queued, `chat._rest_fold_response`) name the turn that answers the message (`fold_turn_id`: the turn the fold's own marker check saw, `acquire_or_fold(accepted_by=...)`, never a second read of the lock; for the requeue fallback the running turn), and the send's stream starts relaying the turn it folded into only after writing the fold frame, which comes first; that stream probes the turn as soon as the relay attached (a turn already over is closed from its tombstone at once) and closes it as `lost` once Redis cannot vouch for it during `FOLD_RELAY_UNCONFIRMED_SECONDS`; a synthesized terminal carries `reason` (`interrupted` / `lost`). A message that @mentions several agents is ONE turn under all of this: one `turn_id`, each reply a segment, the last reply the terminal the tombstone keeps. Protocol for clients: `dev-docs/chat-turn-fanout.md`. Tests: `tests/test_chat_turn_fanout.py`, `tests/test_chat_relay_reliability.py`, `tests/test_mention_turn.py` (the multi-agent turn). |
| `chat_web_transport.py` | The web chat's SSE transport, served by `api/v1/chat_web_stream.py`: `sse_data()` frames, `keepalive_delay()` (a `: keepalive` at most `SSE_KEEPALIVE_SECONDS` after the last write, both streams), `SSE_HEADERS`. `HeadlessTurnConnection` is the `ChatConnection` `chat.run_chat_connection` serves for one send: Stop and skip-wait are `inject()`ed on the turn's replica (`live_connection()`, registered at `turn_started`; elsewhere the routes go through `chat_turn_guard`), a steer goes through `steer()`, `client_present()` is the approval presence, and a send refused before its turn answers plain JSON (`refuse()`), and every frame it writes of its turn names it (`turn_id` of the `turn_started` or `folded_into_active_turn` it wrote, `stream_turn_id`; the `thinking` ack held until then included) but `NON_TURN_FRAME_TYPES` and `session_expired`. `DetachedTurnStreamResponse` (raw ASGI, not `StreamingResponse`): a client that leaves detaches the connection and the turn runs on and stores its answer; `StreamConsumerGoneError` is the write to a gone client. | `turn_checkpoint.py` | The tool work of a web chat turn, kept until it stores its answer (#5687, `dev-docs/chat-turn-resilience.md` section 5). `TurnCheckpoint.offer()` is the `run_agent_loop(on_checkpoint=...)` callback: synchronous, it keeps the completed tool rounds (`completed_work()`: an assistant message whose every call has its result; system and user messages left out; `bounded()` to `MAX_CHECKPOINT_CHARS`, oldest rounds first) and a writer task upserts the latest into `chat_turn_checkpoints` (one row per conversation) on a session of its own, created from the loop's context so the JSON serializer redacts secret variables. The streamed and REST turns read it under the turn lock (`load_resumable()`, younger than `RESUME_MAX_AGE`) and append its rounds to the history right before the new message, past the compaction; they close the writer before storing the answer (`aclose()`, `flush=True` on an error so the next turn resumes everything) and delete the row in the answer's transaction (`discard()`, SAVEPOINT, after `store_message`). A turn that dies keeps it. Best-effort: a failure costs the resume, never the turn. Parent wakes, channel turns and mentioned agents do not checkpoint. `kept_tool_calls()` counts what the next turn would resume, without its log, for the conversation's `interrupted_turn`. |
| `interrupted_turn.py` | What a chat turn cut by the graceful shutdown timeout leaves behind (#5693, `dev-docs/chat-turn-resilience.md` section 7). `TurnProgress` folds the loop's `tool_start` / `tool_done` / `thinking` events into the calls started, the trace (`tool_trace_entry()`, bounded at `TRACE_TEXT_LIMIT`) and the calls still `running`; `meta()` is the reasoning details panel's keys, and it IS the streamed turn's tool tracking (`_turn_progress`). On `is_graceful_shutdown_cancellation` only, the streamed and REST turns store `interrupted_reply()` with `INTERRUPTED_META_KEY` before the lock goes (`chat.py` `_store_cut_turn`), and `run_agent_chat` records `interrupted_memory_note()` through `_store_chat_memories(consolidate=False)`; both as `core/shutdown_finalizers` finalizers the lifespan drains. Both name what stopped the process (`core/worker_shutdown.cut_cause()`, `cut_cause_text()`: its recycle, a stop signal, or nothing recorded; `INTERRUPTED_CAUSE_META_KEY` in the metadata, #6213), never "a server restart". Never an event sink of its own: `run_agent_chat` observes the chain it has, else the note names no tool. |
| `conversation_awaited_work.py` | The work a conversation waits on, which resumes it once it ends: `awaited_work(conversation_id)` lists the Video Studio jobs owed to it still queued or running (`jobs.owed_jobs_pending`, each read through `jobs.job_state`, never a second reading of a row), behind `GET /chat/conversations/{id}/awaited-work` (owner only; any other reader gets an empty list) and the chat's `AwaitedWorkBanner`. | `chat_selection.py` | What a chat REQUEST may add to the MCP servers, custom tools, knowledge bases and integrations its turn loads. `refused_chat_selection()` is called by the REST and streamed message paths before anything is stored: an id the request ADDS - absent from the user's profile defaults, the agent's bindings and the General Assistant's settings - must name a row its caller could bind to an agent of their own (`binding_access.refused_additions`: three-tier, admins bypass; integrations keep chat's own rule, no admin bypass), else a 400 (the streamed send's too, before its stream) whose sentence names the kinds, never an id (`refusal_detail()`), a missing row refused like a hidden one. Everything already known is used as stored - nothing is hidden or silently ignored at chat time; the profile lists are checked where they are saved (`PUT /settings/preferences`, additions only). The conversation's saved selection makes no id known: `usable_saved_selection()` is it less the ids neither configured today nor bindable by the owner (an MCP server unbound from the agent since the save), read by the conversation read the chat page restores its picker from, the conversation list's tool count, the parent wake and the channel turn, so the page never sends one back and no turn loads one. Such an id goes without a notice, as from a new conversation with the agent: it names a row its owner can no longer see. Only an id not configured today costs the owner's groups and a visibility query; a caller reading many conversations passes one `lookups` dict so owners, groups, agents' bindings and each owner's visibility verdicts are read once; the list's count is best-effort (a row whose check fails counts its selection as saved). Whether a VISIBLE integration's personal OAuth token may be used is not decided here: the session resolver withholds it and the turn says so, so a picker offering it never blocks a message. |

| `chat_reply_suggestions.py` | The user's likely next message once a chat turn is `done` (design: `dev-docs/reply-suggestions-discovery.md`): `suggest_after_turn` asks the platform routing model (`flow_llm.routing_model`, through `get_llm_for_user` for the user's provider access) with a digest of the turn - the user's message, the answer (head and tail), the tool names and outcomes from the `done` meta, the agent's name and description, never a tool's raw output - and answers a live-only `reply_suggestion` frame (`{conversation_id, message_id, text}`) or nothing. ## Reasoning streaming: the chat consumer side

The loop side (the `thinking_text` events, the hold-back window, `segment_complete`, `stream_retract`, and the invariant that `streaming` never clears accumulated reasoning) is `dev-docs/reference/backend-tools-streaming-events.md`. What the web chat's stream adds:

- On the stream an iteration opens with `{"type": "thinking"}`; loop status events travel as `{"type": "status", "status": ...}` (`thinking_text` chunks carry `content`, then `streaming`), and answer tokens as `{"type": "stream", "content": ...}`.
- `segment_complete` (the streamed web chat only, `deliver_segments`): the consumer persists the text as an intermediate assistant message and sends the pair built by `_send_intermediate_segment_frames` in `api/v1/chat.py` - `done` with the stored payload and `"intermediate": true`, then `thinking` (also flagged) to re-arm the working UI. The turn's final `done` never carries the flag. The panel treats a flagged `done` as a mid-turn commit; an unflagged `done` ends the turn.
- `strip_reasoning_echoed_in_reply` (`api/v1/chat.py`, used by `api/v1/platform.py` too) drops reasoning paragraphs that were merged verbatim into the reply, so the reasoning panel never repeats the visible answer.
