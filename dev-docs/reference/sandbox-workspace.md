# Sandbox workspace

The code interpreter's durable directory, its kernels, the ingestion that fills it, the way its files reach a tool or a commit without a conversation file, and the resume of an interrupted turn. User page: `docs/docs/usage/sandbox-workspace.md`; settings: `docs/docs/deployment/configuration.md` > "Code interpreter sandbox workspace". Code: `backend/app/services/sandbox_workspace/` (one module per concern, listed in its `__init__.py`).

## What a workspace is

- One per conversation, else per assignment run (`WorkspaceScope.build`: a conversation wins, so a consult inside a run works in the conversation the person sees). A turn with neither has none: the code interpreter is then exactly the stateless tool of earlier releases (no argument, no tool added).
- Carried across the runs of one work item (#9868): a workspace created by a run the inbox dispatched for item X (`assignment_engine.dispatched_work_item_id`: the server-built trigger context and the payload agree, a payload alone is no grant) is labelled `sandbox_workspaces.work_item_id = X`. When the run ends while X is open, `gc.collect_runs` and the sweep keep it (`gc._not_handed_over`); the next run of X by the same agent for the same person adopts it in `WorkspaceStore.open` (`_adopt`: one conditional UPDATE moves `assignment_run_id` to the new run, only from a run already terminal, so a live run's workspace is never taken and two racing runs get it once). Another item's, agent's or person's run never adopts it. It is deleted once X is done, cancelled or gone (at the next run end or sweep), or after `CODE_INTERPRETER_RUN_WORKSPACE_IDLE_TTL_HOURS`; the per-workspace quota is unchanged; no new storage path. Files generated by earlier runs of X are readable by id from the run's file section (#9859, `load_earlier_item_run_files`).
- `workspace/` in the sandbox's working directory, on every backend; `WORKSPACE_DIR` holds its absolute path. Not `/workspace`: the local subprocess sandbox has no mount namespace, and one relative path keeps a cell portable across backends.
- Rows: `sandbox_workspaces` (owner, scope, size, file count, `last_used_at`, `last_gc_at`, `kernel_restarts`, bytes read / written, `kernel_state`) and `sandbox_workspace_files` (path, size, sha256, mtime). No foreign key to `conversations` / `assignment_runs` / `users` (no lock on hot tables); the sweep deletes what they no longer back.
- Bytes: the platform bucket, `sandbox-workspaces/<workspace id>/<sha256>`, one object per distinct content (two paths with the same bytes share one). The sandbox never gets a key or a credential: the backend hands it the files of ITS workspace only.

## Backends

- **Local subprocess**: `local.materialize` copies the manifest's files into the run's temp directory (through `local.BlobCache`, a per-process cache keyed by workspace and sha256, LRU-bounded by `CODE_INTERPRETER_WORKSPACE_CACHE_MB`), `local.scan` reads it back. The output-file collection never walks `workspace/`.
- **OpenSandbox**: `remote.reconcile` makes `/tmp/workspace` hold exactly the manifest with ONE tar in (what is missing or different) and removes what the manifest does not list; `remote.collect` lists the changes in the container, refuses past the quota on the reported sizes before fetching anything, fetches the changed files as ONE tar and hashes them on the server (the container's sha256 only decides what to fetch). `remote.TOOL_SRC` runs through the sandbox command API, outside the user-code wrapper.

## Kernels (`session=true`)

- The kernel IS the code interpreter wrapper (`code_interpreter._build_sandbox_wrapper(kernel=True)`): the same env scrub, module blocklist and removed `os` functions, then `_KERNEL_TRAILER` loops over cells in one namespace. One cell runner (`_run_cell`) serves the stateless run and the kernel.
- Local: a child process per workspace (`kernel.KernelPool`), cells as token-framed JSON lines on stdin/stdout; exits on its idle timeout or when stdin closes. A process keeps at most `CODE_INTERPRETER_KERNEL_MAX_PER_PROCESS`. A call reaching another process starts a new kernel and reports `restarted`.
- OpenSandbox: a container per workspace (`kernel.execute_in_remote_kernel`), named in `kernel_state` and reached by id from any replica; cells as `<id>.json` + `<id>.ready`, results as `<id>.res` renamed into place; the container's TTL is the idle timeout, renewed per call.
- `kernel_state` writers: the kernel's keys, `labs`, `services` and `commands` share one JSON column, so every writer goes through `WorkspaceSession.update_kernel_state(change)`: the state as stored now is read and the change's answer written under the named workspace lock `kernel_state` (an advisory lock across replicas). A read then write of the whole object outside it let two labs started in parallel put back each other's older record, and a lab start answered the bare key `'preview_url'` (#10584).
- Status in every result: `new`, `reused`, `restarted` (counted in `kernel_restarts`), `reset`. A timeout stops the kernel after what the cell wrote is saved.

## Ingestion (`to_workspace_path`)

- A tool declares `ToolDefinition.workspace_ingest` (never a name list). While the run's composite has a sink (`SandboxToolExecutor.on_composite` sets `CompositeToolExecutor.workspace_sink`), `all_tools` adds the argument to those schemas and `execute_tool` runs the tool without it, inside `capturing_ingest()`: the files the call brings into the turn (`FileContext.add_fetched` / `add_produced`, `register_*_file`, `ToolResult.files`) are written, else the result's text. `ingest.WorkspaceIngestor` writes; a failed call is returned as is, a refused write returns neither the content nor a file. A written call returns the path, size and sha256 only, never `ToolResult.files`: a file on a tool result is read into the model's context as its text (`file_resolver.prepare_tool_result_attachments`), which echoed the whole file the call had just put in the workspace; a stored file stays in the turn's `FileContext` and is named in the result.
- A tool that renders its content checks `workspace_ingest_requested()` and returns the raw bytes instead (`get_github_file` delegates to its download; `read_file_content` returns the file); `deliver_file` and `keep_file` keep the bytes in memory instead of creating a conversation file.
- **Text layer of a document** (`ingest._with_text_layers`): a single file the call brings in (not a tree) that is a PDF or Office document, by its name, the target's name or its declared type (`file_content.DOCUMENT_EXTENSIONS` / `DOCUMENT_MIME_EXTENSIONS`), is also extracted on the parse executor with `chunking.extract_text_from_file_async` (the reader of the inline result and the knowledge base; up to `MAX_DOCUMENT_BYTES`). The raw bytes go to the target and the text to `<target>.txt` in the same `put_tree` (quota and file caps apply); a target ending in `.txt` receives the text alone. No text (a scan, an encrypted or broken file) writes the raw bytes and a note in the answer. The sandbox images carry no PDF library, so this is how a fetched report becomes searchable in code.
- A tool that brings in a **tree** sets `FileRef.relative_path` on each file it registers: the ingest writes it at `<to_workspace_path>/<relative_path>` (normalized; a refused or repeated path falls back to the file name), and the answer names the first 60 files and counts the rest. `download_github_workflow_artifact` (GitHub Actions artifacts) uses it: it reads the artifact's metadata (an expired artifact or one over 100 MB is refused before the download), fetches the zip with the integration credential (the redirect to the storage host drops the `Authorization` header) and, when `workspace_ingest_requested()` and `unzip` (default true), registers every regular member (`actions._artifact_members`: at most 2,000 files and 256 MB uncompressed, links, directories and names `paths.normalize` refuses skipped and counted). `unzip=false` or no workspace: the zip itself through `deliver_file`. It is hand-gated with the download family (`hitl_whitelist_platform.HAND_GATED`).
- A tool whose result is text declares `workspace_ingest` too: `get_github_pr_diff` and `get_github_job_logs` return the whole text uncut when `workspace_ingest_requested()` (the sink writes it), the truncated rendering otherwise. `get_github_job_logs(patch=true)` returns only the unified diff(s) the log printed (`ci_logs.extract_patch`: `diff --git` or `--- a/` + `+++ b/` blocks, hunks kept while their `@@` counts are met, runner timestamps and colours removed, no line clipped, a blank context line written back with its space), so `to_workspace_path` writes a file `sandbox_apply_patch` takes as is; a log with no complete hunk answers `Error:` and writes nothing (#1477). A job that has not completed has no log yet (GitHub's redirect points at a missing blob): when the logs request fails or comes back empty, `get_github_job_logs` reads the job and, if its status is not `completed`, answers an `Error:` line naming the status and telling the agent to poll `get_github_ci_status` (`_running_job_answer`), so nothing is written to the workspace and the storage error never reaches the agent. A job that completed without a published log (a hosted runner that lost communication with the server, a job cancelled before its runner started: the logs request answers 404 / `BlobNotFound` or an empty body) gets its steps and its check-run annotations read from `/check-runs/{job_id}/annotations` (an Actions job id is its check-run id) and answered as a non-error result naming that the log was never published (`_log_is_missing`, `_unpublished_log_answer`); any other logs error (403, 5xx) is answered as it came. Under a workspace ingest that answer carries the `Error:` prefix, so no summary is written as the log file.
- `query_github_graphql` (the query-only GraphQL read) declares `workspace_ingest`: under `to_workspace_path` it returns the whole JSON answer uncut (a search over hundreds of issues lands in the workspace, not the context); without it the answer is cut at `_MAX_GRAPHQL_CHARS` and the cut names `to_workspace_path`. `github_graphql_query` (a write tool) does not declare it. A mutation sent through `github_graphql_query` is never retried; when it fails (a gateway 5xx, a 200 with `errors`) `gh_graphql(keep_partial=True)` keeps the answer's partial `data`, and the error names the response keys the document sent (`mutation_response_keys`), those the partial data shows applied and those not confirmed, with the advice to re-read before resending and to send at most 10 aliases per mutation (`partial_mutation_report`, issue #9242).
- The read (GET) operations of an OpenAPI integration and of a custom bundle's declarative tools declare `workspace_ingest` (`declarative_http_executor.spec_is_read`; a tool whose spec is invalid or whose client certificate refuses does not): under `to_workspace_path` a non-JSON answer is returned whole (`workspace_ingest_requested()`) and the sink writes it, within the spec's `max_response_bytes`; without it the text is cut to `_MAX_TEXT_RESPONSE_CHARS` by `clip_head_and_tail`, head and tail, the cut naming `to_workspace_path` (issue #10364).
- `get_shared_state` declares `workspace_ingest` (issue #11218): under `to_workspace_path` (`workspace_ingest_requested()`) `_export_selection` returns the selection the windowed read would show (the whole value, `path`, `where_json` with the layout-free grouping by list path, `fields` / `item_offset` / `item_limit`) as one plain JSON document, with no character window, untrusted-content wrapper, header or notes, and the sink writes it; a missing key or path answers an `Error:` and nothing is written. Without the argument the read is unchanged. The schema budget does not move: the argument is added at offer time (`with_workspace_path`).
- `set_shared_state` declares `workspace_read` (the write-side counterpart): with a workspace the dispatcher offers `from_workspace_path` (`with_workspace_read`, added at offer time, so the schema budget does not move). The tool reads the file itself through `current_workspace().read_file` (no conversation file, nothing parked), at most 4 MiB: one JSON object whose keys are among `value_json`, `append_json`, `remove_json`, `keep_last_json`, `unique_by_json`, `update_json`, each value the JSON the argument would carry (an object, or that JSON as a string). They merge with the inline arguments (the same argument in both is refused) and then go through the inline validation and `upsert_state` unchanged (row lock, `unique_by`, read-back). A missing file, non-JSON, a non-object, an unknown key or a run without a workspace answers `Error:` and nothing is written.
- A cut never keeps the head alone: `app.tools.base.clip_head_and_tail(text, max_chars, hint=)` keeps three quarters of the budget from the start and one quarter from the end around a marker that counts what was left out; the agent loop's per-result cap (`_truncate_tool_result`, `max_tool_result_chars`, at most 150,000) uses it, so a log's error summary and an API's continuation token survive the cut.
- `materialize_repository` calls the provider's `repository_archive` tool (`download_github_repository_archive`) through the composite, so the integration's credential, its repository scope and the run's approval gate apply; the nested call is exempt from the gate because the outer call passed it. `repository.extract_tree` drops the archive's top directory, every `.git` path, links and non-regular files.
- **A repository whose archive is over 256 MB (#414).** Without `sub_paths` the GitHub tool refuses it (`_MAX_ARCHIVE_BYTES`, read in memory) and the refusal names the way out: `paths` / `sub_paths`. With `sub_paths`, `_archive_tree` passes them (and the rebase's `extra_files`) as `paths` to an archive tool whose `input_schema` declares it. `download_github_repository_archive(paths=...)` then streams the tarball to a temporary file (`_MAX_STREAMED_ARCHIVE_BYTES`, 4 GB of disk, never memory): within 256 MB it answers the whole archive as before; over it, `repository.narrow_archive` reads the tar once as a stream and repacks every regular file under the paths, plus, outside them, every detection file up to `NARROW_OUTSIDE_MAX_BYTES` (8 MB) (`_detection_file`: manifests, lock files, requirements and tool configs by name, `detect.is_companion_name`, workflows, `.xtm-one/`, the actionlint config) and the other small non-media files (`_MEDIA_EXTENSIONS`, `.svg` included) in archive order up to `NARROW_OUTSIDE_BUDGET_BYTES` (64 MB); a file past that budget is left out and named, never a refusal (#432: a site whose seed data and pages outside the sub_path passed 256 MB could not be narrowed at all), so the companions, the declared checks and the widening `extract_tree` does still find what they read. Member names keep the top directory, so the checkout record's commit and per-file hashes are unchanged and `create_github_commit(from_checkout)` works as on any checkout. The kept bytes keep the 256 MB cap (`ArchiveTooLargeError` naming the bytes under the paths, the detection bytes and the other small files outside them apart). The files left out are counted in the tool's answer and returned in `ToolResult.structured["left_out"]`; `materialize_repository` lists them under "Not written" ("outside the sub_paths of an archive over its limit"), never silently. A widening that would need a left-out file (a media file a check reads outside the sub_paths) is the cost: name that path in `sub_paths`.
- With `sub_paths`, `materialize_repository` also keeps the **companion files** zero-config detection reads: `detect.companions(sizes, sub_paths)` picks, among the archive's regular files, the manifests, lock files, wrappers and tool configuration (`detect.COMPANION_FILES`, compose and requirements files, and the formatter, linter and TypeScript configs `detect._TOOL_CONFIG` matches: `.prettierrc*`, `.prettierignore`, `biome.json`, `.editorconfig`, `eslint.config.*`, `tsconfig*.json`, `turbo.json`, and the test runner configs a unit check loads: `vitest.config*.*`, `vite.config*.*`, `jest.config*.*`, `playwright.config*.*`, `vitest.workspace.*`...) in each directory above a sub_path up to the root, every `.github/workflows/*.yml`, the CircleCI configuration and `.xtm-one/checks.toml`; never a file under a sub_path, under a `detect.SKIP_DIRS` directory or past `MAX_COMPANION_BYTES`, at most `MAX_COMPANIONS`. `repository.extract_tree` writes them with the tree (`ExtractedTree.companions`), the record lists them like any written file (an edit to one is a change, its `sub_paths` stay what was asked), and the next checkout at the same path replaces them (`put_tree` replace scopes: the sub_paths, each companion, `.github/workflows`). A repository test script above a sub_path (`run_test.sh`, `run-tests.sh`, `test.sh`: `detect._TEST_SCRIPT_NAME`) is a companion too. So is every repository file a check declared in `.xtm-one/checks.toml` names in its `argv` or `default_args`, resolved from its `cwd` (`detect.check_support_files`: `python ../.xtm-one/stores.py` from `backend/` keeps `.xtm-one/stores.py`); an option, an absolute path, a path out of the repository, a directory or a file past `MAX_COMPANION_BYTES` adds nothing, so every declared check runs on a narrow checkout without an `add_paths` call. A directory of the same repository that a requirements file under a sub_path installs from (`pkg @ git+https://...#subdirectory=connectors-sdk`, which the project's test script installs from the checkout) is added as a sub_path (`detect.subdirectory_dependencies`, a name that is a directory of the archive and outside the sub_paths, at most `MAX_DEPENDENCY_DIRS`; `ExtractedTree.dependencies`), and the answer says so ("connectors-sdk/ added"). A sub_path inside a JavaScript workspaces root also keeps the `package.json` of every workspace member (`detect.workspace_member_manifests`): `extract_tree` reads the `package.json` and `pnpm-workspace.yaml` of the directories above each sub_path (at most `MAX_REQUIREMENTS_BYTES` each), and the members their `workspaces` globs (a list, or `{packages: [...]}`) or `packages:` list match (`*` one directory, `**` any depth, `!` excludes) are companions, outside the sub_paths and `SKIP_DIRS`, at most `MAX_WORKSPACE_MEMBERS`; the root lock file is already a companion, so `yarn install --immutable`, `pnpm install --frozen-lockfile` or `npm ci` resolves the workspace with no `add_paths` (without the member manifests yarn rewrites the lock and stops on YN0028). The install also runs the root's lifecycle scripts (`detect.INSTALL_LIFECYCLE_SCRIPTS`: `preinstall`, `install`, `postinstall`, `preprepare`, `prepare`, `postprepare`), which may build another member (`cd packages/core && tsup`) or copy a root file (`../../llms.txt`): `detect.install_lifecycle_paths` reads those scripts of the `package.json` files above each sub_path, split on `&&`, `||` and `;`; a `cd` into a directory of the archive adds that directory as a sub_path (`ExtractedTree.lifecycle`, at most `MAX_DEPENDENCY_DIRS`, the answer says "packages/core/ added"), and a word that, resolved from the directory the script is in at that point, names a regular file of the archive is a companion; the root, an absolute path, a path out of the repository, `SKIP_DIRS` and what the sub_paths already hold add nothing (without it, a narrow checkout of one member of a design system whose root `prepare` builds the core package failed `pnpm install` on `tsup: No input files`).
- A package under the sub_paths that depends on a sibling workspace member by the `workspace:` protocol (`"eslint-plugin-custom-rules": "workspace:*"` in `opencti-front/package.json`) keeps that member whole: `detect.workspace_dependency_dirs` reads every `package.json` of the archive (outside `node_modules`), maps each `name` to its directory, and for each manifest under the sub_paths, and for the member a sub_path lies in (the nearest `package.json` above it, never the root: `openaev-front/src/utils` is linted with `openaev-front`'s config), adds the directory of every `dependencies`, `devDependencies`, `optionalDependencies` or `peerDependencies` entry whose value starts with `workspace:`, then that member's own `workspace:` dependencies, transitively (`ExtractedTree.workspace_links`, at most `MAX_DEPENDENCY_DIRS`, the answer says "... added (a package of the checkout links it: workspace:)"). The manifest alone (a workspace member companion) lets the install resolve but not the check that imports the member's source (an `eslint.config.ts` loading the plugin). The root, a member already under a sub_path, a member holding a sub_path and an unknown name add nothing.
- An ESLint flat configuration in or above a sub_path (`eslint.config.ts`, a member's `local.eslint.config.ts`) that imports a sibling member by package name with no `workspace:` dependency declaring it (OpenCRQ: `from 'eslint-rules/src/rules'`) keeps that member whole too: `detect.lint_config_member_dirs` reads each bare specifier (`from`, `import(`, `require(`), maps its package name to a member's directory and adds it to `ExtractedTree.workspace_links` under the same exclusions and cap.
- With `sub_paths` in a multi-module Maven project, `materialize_repository` also keeps the **reactor** a module builds against (`detect.maven_reactor_paths`, `ExtractedTree.reactor`): every `pom.xml` of the archive is parsed with defusedxml, the sibling modules a POM under the sub_paths names as a dependency, plugin or annotation processor path (by groupId and artifactId, by artifactId when the groupId is a property), followed transitively, are added to the sub_paths (30 at most, the answer says "<dir>/ added (a Maven module under them builds against it)"), and the `pom.xml` of every module a POM above a sub_path lists is kept as a companion, so `mvn -pl <module> -am` reads the reactor instead of failing on "Child module ... does not exist" or searching the project's remote repositories for unpublished siblings.
- `materialize_repository` writes a **checkout record** beside the tree, `<path>/.xtm-checkout.json` (`checkout.build_record`): provider, repository, ref, the commit the archive's top directory names, the `sub_paths` kept and the sha256 and size of every file written. The record is a regular workspace file (listed, removed with the tree, replaced by the next checkout); it holds no credential.
- `materialize_repository(path, add_paths=[...])` **grows** an existing checkout instead of replacing it: `_grow_checkout` reads the record at `path` (refused when there is none, when `repository` differs, for a whole-tree record, and with `sub_paths` or `ref`), drops the `add_paths` the record already covers (`CheckoutRecord.covers`: answered without a fetch), reads the tree at the record's `commit` (its `ref` when none) through `_archive_tree` (same widening and companions), and writes in one `put_tree` without `replace`: only the files the record does not name and the workspace does not hold, with the record moved by `checkout.grown` (the `sub_paths` union, a path under another dropped; each new file recorded with its hash at the commit, a recorded file keeping its hash). Nothing is removed, so an edit survives; status, diff, rebase and `from_checkout` cover the new files. A file the workspace already holds under an added path is told apart by `checkout.stale_on_grow` (#10998): identical to the tree, it is left as is; held by the record's out-of-scope baseline with the hash it still has (left by an earlier, wider checkout and untouched since; on a record without a baseline, written before the record), it is stale and written at the record's commit in the same `put_tree`, counted as stale in the answer, so `from_checkout` never commits an older commit's file back as a change; otherwise it is an edit, kept and named in the answer (the first 10, the rest counted).
- **`sandbox_put_file` resolves like `read_file_content`** (`_resolve_put_ref`): the turn's `FileContext` first (the id bare, `file-<id>`, the `[[FILE:<id>]]` marker or a unique 8+ hex prefix, `_shared.resolve_file_ref`), then the conversation's or run's own `FileAttachment` row by id (`_shared.load_scoped_file_ref`), which a context misses for a file stored past the turn's load bound or by a tool that did not register it, then a stored file the acting user owns in any of the user's conversations or runs, by id or prefix (`work_item_files.load_owned_file_ref`, the Files page's "Mine" predicate; issue #11504), then a template asset (a brand logo or background `get_template` lists) by its full id when the user can see its container (`template_containers.load_visible_asset`, the `caller_visible_filter` grant `get_template`, the file download and `render_html_to_image` apply; issue #1318). A row found joins the context as a fetched file, so `code_interpreter` mounts it under `attachments/` (and `index.json`) from the next call. A prefix that starts several of the user's files is refused with the candidates (`id_prefix.ambiguous_text`). Another user's file is refused like an unknown id; the refusal names the scope (`(it is a file of conversation X)`, `of assignment run Y`, `unregistered`) only when the acting user owns the row (`_file_owner_note`). `create_work_item` and `complete_work_item` admit attachments by the same id or prefix (`work_item_files.resolve_owned_file_id`). `save_video_frames(keep_frames=true)` registers every kept frame in the run's context as a fetched file, in a conversation too, so the frames are put and mounted in the run that saved them (issue #10043).

## git status and git diff of a checkout (`sandbox_checkout_status`, `sandbox_checkout_diff`)

- Both read the record and the manifest through `WorkspaceSink.checkout_changes` (the same `checkout.changes_since` change set `from_checkout` commits, `paths` narrowing it the same way), so status, diff and commit never disagree.
- An install check (`commands.is_install`) that rewrote a manifest or lockfile the checkout tracks (`commands.rewritten_manifests`, the `LOCKFILES` names among `CommandOutcome.rewritten`, the files it changed rather than added) is named in the `sandbox_run_command` answer: `from_checkout` would otherwise commit the rewritten `package.json` as a change of the branch (#474).
- `sandbox_checkout_status` is a workspace read: `checkout.format_status` answers the origin (`checkout.origin`: repository, ref, commit), the counts and one `M` / `A` / `D` line per file sorted by path (`checkout.marked`), at most `MAX_STATUS_LINES`, the rest counted; "clean" when nothing changed. A file outside the record and its `sub_paths` (left by an earlier, wider tree) is never a change, but one added, edited or removed against the record's out-of-scope baseline (`outside` in the record: the sha256 of each such file when `materialize_repository` first wrote the record, `checkout.outside_baseline`; carried forward by `advance`, `grown` and `rebase.rebased_record` through `CheckoutRecord.carried`, so no record rewrite and no clock skew hides an edit) is named in `CheckoutChanges.untracked`: in the status, in `sandbox_checkout_diff`, in `sandbox_run_command(affected=true)` and in every `from_checkout` answer, with the remedy (`paths` together with the checkout's `sub_paths`, since `paths` replaces the selection, or `materialize_repository(add_paths=...)`), so an edit there is never silently left out of a commit (#10144); a `from_checkout` commit without `paths` that would carry other changes beside such files is refused whole, nothing written (`contents._changes_from_checkout`, #237): `paths` = the `sub_paths` plus those files commits them, `paths` = the `sub_paths` alone leaves them out. With `paths`, a named file the record does not hold that is still byte for byte its out-of-scope baseline (a leftover nobody edited) is a `leftover`, never added (#237). A check's output (`.xtm/runs`), an installed or cache directory (`checkout.GENERATED_DIRS`) and a nested checkout are never named. A record written before the baseline existed falls back to the record's write time (manifest `mtime`). An untracked file (not in the record) that the checkout's `.gitignore` files exclude is never a change nor named, only counted in `CheckoutChanges.ignored` and said by `ignored_note` (#10650): `WorkspaceIngestor.checkout_changes` reads every `.gitignore` under the checkout (`gitignore.gitignore_paths`, shallowest first, at most `MAX_GITIGNORE_FILES`) into `gitignore.GitIgnore`, a pure matcher of git's rules (anchoring by slash, directory-only trailing `/`, `!` negation with the last match winning, `*` / `?` / `[...]` inside a segment, `**` across, no re-inclusion under an excluded directory), and passes it to `changes_since(ignore=...)`; a recorded file stays a change whatever the rules say. `.gitignore` is a `detect.COMPANION_FILES` name, so a narrow checkout carries the files above its `sub_paths`.
- `sandbox_checkout_diff` reads each modified or removed file's base through the provider's `repository_file` tool (`ToolDefinition.repository_file`; GitHub: `download_github_file`) at the recorded commit (the ref when the record names none), inside `capturing_ingest` so the bytes stay in memory (no conversation file), with the nested call exempt from the gate like `materialize_repository`'s; at most 6 reads at once. A base whose sha256 differs from the record is refused for that file ("the base moved"); an added file is diffed from `/dev/null` and needs no read; a binary is named, its base not read. `checkout.file_diff` builds each unified diff (`clamp_diff_context`: `DEFAULT_CONTEXT_LINES` 3, `MAX_CONTEXT_LINES` 10), bounded by `MAX_FILE_DIFF_CHARS` per file, `MAX_DIFF_FILES` files and `MAX_DIFF_RESULT_CHARS` per answer; what does not fit or could not be read is named in the answer, never dropped.
- HITL: the diff reaches an integration, so it is listed in `DELIBERATELY_EXCLUDED` beside `materialize_repository`; the status follows the other `sandbox_*` read tools.

## git rebase of a checkout (`sandbox_checkout_rebase`)

- Before any read, a file the workspace changed (modified or added) that still holds a conflict hunk (`rebase.has_conflict_markers`: a `<<<<<<< ` line followed by a `>>>>>>> ` line) refuses the rebase with each file named and nothing written: a rebase over it would merge the old markers as text and nest new ones inside them (a replayed or repeated rebase before the conflicts are settled).
- Exactly once (#11479): the compare of the recorded commit against the ref is read first (`_compare_with`, the provider's `repository_compare` tool). Its `status` `identical` (the checkout already sits on the ref's commit) or `ahead` (it holds it) answers "already sits on / ahead of" with nothing downloaded or written: a rebase whose answer was lost with its worker landed, and its replay must not merge the ref a second time (the nested markers of a 270 MB checkout rebased twice).
- The tree at the new ref is read by `_archive_tree`, the archive read `materialize_repository` uses (same provider, the record's `sub_paths`, its companions), in memory.
- The base is the merge base of the recorded commit and the ref, read by `_compare_with` through the provider's `repository_compare` tool (`compare_github_commits(base=ref, head=commit)`, whose `ToolResult.structured` carries `merge_base`). A checkout on a feature branch records the branch's own files, so the record as base read each file the branch added as "deleted by the ref" and removed it. When the merge base differs from the recorded commit (`_same_commit`, abbreviations allowed), the tree at the merge base (the ref's tree when it is the ref's commit, else a second `_archive_tree` with the same sub_paths) replaces the in-scope files of the record for `plan`, and is the source of each `MERGE`'s base bytes (no `_base_bytes` read). When it equals the recorded commit, or cannot be read (no compare tool, no recorded commit, an error), the record stays the base as before, and the answer says why. A `KEEP` absent from the base and the ref is listed as "Your added files kept" (`RebaseSummary.added`); the audit row carries `added_kept` and `merge_base`.
- The branch's files outside a narrow checkout (#11853): `compare_github_commits` carries the changed `files` (`filename`, `status`, `previous_filename`) and `files_capped` in `structured`; `rebase.branch_changes` reads them and `BranchChanges.outside(record)` keeps the paths the record does not track. When the merge base differs from the recorded commit and the checkout has `sub_paths`, each such file is read at the recorded commit (`_base_bytes`) and brought in as the workspace side (unless the workspace holds an edit of it), the paths join the record's `sub_paths`, and both archives (ref and merge base) are read with them through `extract_tree(extra_files=...)`, kept as they are, never widened. The plan then merges them like any file of the checkout and the moved record holds the ref's version of each, so status shows the branch's change and a later `add_paths` never overwrites it. A file the branch deletes is removed from the workspace when it still holds the recorded version. An unreadable file, a compare at its file cap or more than `rebase.MAX_PULLED` (200) files refuses the rebase before any archive is read, naming the files and the `add_paths` call to run first. Before, the trees were read at the `sub_paths` only and the branch's backend hunks of a frontend checkout were lost.
- Stale branch side (#1029): a record a `from_checkout` commit moved (`base_commit` set and different from `commit`) keeps the checkout-time sha256 of every file the commit did not write, so when the branch gained commits the checkout never held (main merged in on the server, a split commit set) the workspace holds those files older than the branch. Before `plan`, `_rebase_now` reads the tree at the recorded commit (`_archive_tree`, same scope) and `rebase.stale_branch_sides` names each file whose workspace hash is still the recorded one and whose branch version differs (or is gone, in scope): the branch's bytes become the workspace side (written with the rebase), so a file only the ref changed follows the ref and a file both changed is merged from the branch's text. When the merge base is the recorded commit itself, its tree is the base. An edited file is never replaced. The answer lists them under "Read from the branch commit first". A JSON/YAML/TOML parse after the merge is not a merge-correctness check: it says the text is well formed, not that no key was lost.
- Block written twice (#1171): when the workspace and the ref add the same block at different places, the two hunks do not overlap and the line merge writes both copies. `rebase.merge_file` calls `rebase.duplicated_block` on a clean merge of a plain-text file (a structured file is judged by its parser): a run of 3 consecutive substantive lines the merge holds more often than either side keeps the workspace bytes and reports the file in conflict, naming the line where the copy starts, never "merged cleanly".
- `rebase.plan` gives each file of the base (the record's sha256, or the merge base's tree), the workspace (the manifest, tracked files only) and the ref one step: unchanged in the workspace follows the ref (`TAKE` or `REMOVE`); changed in the workspace and not on the ref, or changed the same way, is `KEEP`; a file the ref holds exactly as the checkout wrote it (`checked_out=record.files`, the record before `base_files_of` replaced it: the squash of the checkout's own branch, #779) is `KEEP` too, never an add-add merge from an empty base; a delete against a change is `CONFLICT` (workspace side kept); changed on both sides is `MERGE`. A recorded file outside the `sub_paths` (committed from the checkout with `paths`) is out of the ref's tree and left alone (`in_scope=record.covers`).
- A `MERGE` reads its base through `_base_bytes` (the `repository_file` tool at the recorded commit, like the diff) and checks it against the recorded sha256; `rebase.merge_file` merges UTF-8 text with `rebase.merge_text` (diff3 over `difflib` opcodes; changes whose base ranges overlap or touch form one group; one side changed takes it, both the same takes it once, otherwise `<<<<<<< workspace` / `=======` / `>>>>>>> ref` markers). `on_conflict` (`rebase.OnConflict`, #11479) changes what a both-sides hunk writes: `markers` (default), `ref-then-workspace` (the ref's lines, then only the lines the workspace inserted or rewrote against the base in that hunk: `merge_text(lead="theirs")`, so a line added next to a line the ref rewrote ends as the ref's line then the added one, never the old line twice) or `workspace-then-ref` (`lead="ours"`), or `ref` / `workspace` (that side's lines alone in the hunk: `merge_text(prefer="theirs" | "ours")`, every hunk only one side changed still merged; a binary changed on both sides takes that side's bytes); such a hunk counts as merged, not as a conflict. Three texts that do not share one line-ending style (a CRLF side against an LF one) are merged on LF and written back in the workspace side's style, so a change of endings alone is never a conflict; `sandbox_diff_files` and the line merge of `merge_github_branch` share it. A binary, an undecodable file or an unreadable base keeps the workspace bytes and is reported.
- Writes: the ref's deletions through `session.remove`, then the taken and merged files and the new record (`rebase.rebased_record`: the ref's tree hashes plus the out-of-scope entries) in one `put_tree`. `sandbox_checkout_status` then lists only the agent's changes on top of the ref; the conflicts stay changes until resolved with `sandbox_edit_file`.
- Background job (#11479, slice 3): `background=true` records a job in the workspace ledger (`jobs.rebase_running`: `kernel_state["jobs"]` keyed by `jobs.rebase_key(checkout, ref, on_conflict)`, `tool` `checkout_rebase`, `status` running, a `heartbeat` every `HEARTBEAT_EVERY` s) and answers its `run_id` at once; the rebase runs as an asyncio task of the worker in the session's write turn and ends the job with its answer (`status` ended, `answer` cut to `MAX_SAVED_ANSWER`, `is_error`). `sandbox_checkout_rebase(run_id=...)` (a read-only call) waits up to `POLL_WAIT` s when this worker holds the task, else answers from the ledger: ended (the saved answer), running (a heartbeat younger than `STALE_AFTER`), or lost with its worker (start it again: the one-change-set write landed whole or wrote nothing, and the exactly-once compare answers a landed one). Any call (background or not) with the same checkout, ref and mode while that job beats answers that job instead of starting a second rebase; the tool's `landed_probe` (`jobs.rebase_landed`) answers a repeat of an ended job with its saved answer. The tool is registered without `_counted_write` (a poll must not hold the write turn its job waits for): the handler counts itself with `session.writing()` and takes `write_turn()` for the synchronous rebase and inside the job.
- HITL: reads through an integration, so it is in `DELIBERATELY_EXCLUDED` like the diff. Metrics: `checkout_rebase` ok, conflict, refused, failed, started; audit `checkout_rebase`.

## History of a checkout, read server-side (`get_github_blame`, merge base)

- A checkout has no `.git` (`extract_tree` drops it; the sandbox has no credential and no network), so history verbs are provider reads: `get_github_blame` (providers/github/commits.py) runs GraphQL `Commit.blame(path)` at `ref` (`HEAD` when empty: the default branch) and `format_blame` answers one line per range clipped to `start_line..end_line`, `_MAX_BLAME_LINES` (400) per call with the next `start_line` named; an unknown ref, a missing, empty or binary file (GitHub answers no range) and a line past the end are one `Error:` line each.
- `compare_github_commits` adds `Merge base: <sha12>` from the compare's `merge_base_commit`.
- `list_github_commits(contains=TEXT, path=P)` is the pickaxe (`git log -S`): it lists the commits touching `P` (`_MAX_PICKAXE_COMMITS`, 50, at most; `since` / `until` / `branch` narrow it), reads each commit's diff and answers only those whose patch under `P` adds or removes a line holding `TEXT`, with `file (+A -R)` per matching file (`pickaxe_hits`; context lines never count). A file GitHub sends without a patch (binary or too large) is counted as not searched; `contains` without `path` is refused before any request.
- A 404 on compare is explained, not passed through (`_compare_not_found`, #8788): the repository is read, then each ref through `commits/<ref>` (404 or 422 = missing). A missing ref answers a non-error `ref_not_found: <ref> (base|head)` result, `structured = {status: "ref_not_found", missing, pull_requests, merge_base: ""}`, with the last pull request that used a missing branch as head (`pulls?head=owner:branch&state=all`, skipped for a SHA). A branch deleted after its pull request merged is an expected outcome for a caller that read the PR open a moment earlier, so it records no tool_error friction. A missing repository, both refs present, or a ref whose existence cannot be read keeps the original error; `_merge_base` reads no merge base from `ref_not_found`.
- HITL: a read (whitelist snapshot entry); repository scope: `repo` is checked like every GitHub read. A local `.git` with a server-side push stays out: main requires signed commits, which only GitHub-built commits (`create_github_commit`) carry.

## Out of the workspace without a conversation file (`workspace_path`, `from_checkout`)

- A tool that takes a file of the run by `file_id` declares the arguments in `ToolDefinition.workspace_files` (`"file_id"` for a top-level argument, `"files[].file_id"` for a key of each item of an array argument; never a tool name list). While the run has a workspace, `all_tools` adds a sibling `workspace_path` to each (`with_workspace_files`), and `CompositeToolExecutor._dispatch` resolves it before the tool runs: `WorkspaceSink.read_file` reads the bytes on the server (`ingest.WorkspaceIngestor.read_file`; a read changes no state, so it writes no audit row, only the `read_for_tool` metric, #9743, pinned by `tests/test_sandbox_workspace_audit_reads.py`), the dispatcher parks them in the turn's `FileContext` as an in-memory `FileRef` under the `file_id` the tool reads as any other (`read_pipe_file`, `resolve_upload`), and forgets the reference once the tool returns (`FileContext.forget`). No row, no storage object, no download card. A path outside the workspace, a missing file, both `file_id` and `workspace_path`, or a run without a file context is refused before the tool runs. Declared today: `create_or_update_github_file` (`file_id`) and `create_github_commit` (`files[].file_id`); any integration upload or import tool can declare its own.
- `create_github_commit(from_checkout=<directory>, paths=[...])` commits what the sandbox changed under a `materialize_repository` checkout: `WorkspaceSink.checkout_changes` reads the record and the manifest (`checkout.changes_since`: modified and added files as repository-relative paths, removed files as deletions; the record itself is never a change; without `paths` a file outside the recorded `sub_paths` is not one either, while a file under a path named in `paths` is one wherever it is, added files included, and a named path under which nothing changed is said in the result as `unmatched`), the tool reads each changed file through `read_file` and builds the same change set `files` / `delete_paths` would (`_WorkspaceBytes`). A change set over the 5 MB or over the 100 changes of one commit is not refused (a `files[]` change set over the 5 MB too since #764, through `_split_files_change_set`: a single file over the cap keeps the refusal; an `edits` set whose resolved files pass the cap is resolved whole at the tip read first and then goes through the same split, `merged_on` that tip, so a branch moved meanwhile is refused (#1307); the record of a `workspace_path` file of a checkout moves to the last part through `_advance_checkout_files`, as on the single-commit path): `_commit_checkout_in_batches` splits it with `checkout_commit_plan` over `checkout_batches` (smallest files first, next fit, each commit under both `_MAX_COMMIT_CONTENT_BYTES` and `_MAX_COMMIT_CHANGES`, so code and tests land before the i18n catalogs; the deletions ride with the first batch, which gets that much less room, and a full 100 of deletions is a commit of its own) and runs one ordinary `create_github_commit` per batch on the tip the previous one left, each signed by GitHub, the message's body naming "Part N of M"; the result lists every SHA with its signature line. A batch that fails stops the chain, the record moves to the last commit made (`_advance_checkout` with the files of the landed batches), so a second call commits only the rest. A single file over the cap is refused before any request (no split can carry it), and a change set over `_MAX_CHECKOUT_SPLIT_BYTES` or `_MAX_CHECKOUT_SPLIT_CHANGES` (8 commits' worth of bytes or of changes, 800 files) is refused before any request. Base drift (`checkout_drift.reconcile`, wired by `_reconcile_checkout_drift`): before the single or batched commit the branch tip is read; when it is not the record's `commit`, the recursive trees of both commits are listed (`merge_resolution._read_side`) and each written or deleted path whose blob differs between them is merged three-way (ancestor, workspace, tip) with `merge_hunks.merge_path`. The ancestor is the merge base of the record's commit and the tip (`checkout_drift._merge_base`, one compare; the record's commit when the branch grew from it): a record moved by a commit on another branch, then a branch cut from a newer main, used to make the workspace look like the ancestor, so the merge took the tip's text and answered "No change" over real changes (#11990). A path whose workspace bytes are the tip's blob is not merged (the commit answers no change for it), and a path whose recorded sha256 is the tip's version (an earlier commit from this checkout wrote it) is written as the workspace holds it, so two consecutive `from_checkout` commits on one branch both land. A clean merge replaces the workspace bytes in the commit and is handed to `WorkspaceSink.advance_checkout(rewrites=...)`, which writes it into the workspace before the record moves; an overlap, a binary changed on both sides, a delete against a change, a link or submodule, more than `MAX_MERGED_PATHS` drifted paths or more than `MAX_MERGE_READ_BYTES` refuse the call with `describe_conflicts` hunks and the `sandbox_checkout_rebase` call, nothing written; a deletion the branch already made is dropped. The other files the record tracks are compared too (`tracked`, #10061): one the commit does not carry whose blob differs between the record and the tip is `Reconciled.stale`, the result says "Checkout behind the branch" with the paths and the `sandbox_checkout_rebase` call, and the record keeps its `commit` (see the next point), because the workspace still holds those files at the record's text: moving the record to the new commit would make the next commit's tip equal its base, skip the merge and write them whole over the branch's change (checkout at 789ee3f7, branch cut at c15976d1, commit 1 clean, commit 2 reverted two main commits). The commit then lands only on the tip it was merged against (`merged_on`; another tip answers `_moved_tip_refusal`). A record moved by a commit made from the checkout (`base_commit` set and not `commit`) is reconciled even when the tip is the record's `commit` (#1040): a path the commits from the checkout did not write or delete (not in `record.branch`) is held in the workspace at the baseline's text, so its ancestor and its stale comparison use the `base_commit` tree (`reconcile(baseline=..., committed=...)`); a branch cut from a newer main than the checkout, a first commit of new files only, then a second commit of an older file used to write it whole and revert main's lines. A tip equal to an unmoved record costs one ref read and nothing else. The run's sink is reached through `current_workspace()` (a `ContextVar` set by `_dispatch` for the call); a checkout of another repository, a directory without a record, or `from_checkout` together with `files` / `delete_paths` is refused; an unchanged checkout commits nothing and says so.
- The record moves with the commit: once the branch points at the new commit (and on "no change: the branch already has this content", to the tip read), `create_github_commit` calls `WorkspaceSink.advance_checkout` (`WorkspaceIngestor`), which writes `checkout.advance(record, commit, ref, written, removed)`: the written files' sha256 and size replace the recorded ones, deleted files leave the record, untouched files keep their hash (an edit made since stays a change), `commit` and `ref` become the new commit and the branch, `sub_paths` are kept; when `reconcile` found stale files (the branch changed tracked files this commit did not carry), `_advance_checkout` gets an empty commit, so `commit` stays the record's and only the written hashes move: the next commit from the checkout still sees the drift and merges those files. A file written outside `sub_paths` is recorded, and `CheckoutRecord.tracks` (recorded, or under `sub_paths`) makes its later edits and its removal changes without `paths`. The advance never fails the commit: a refused or failed write is a sentence in the result. A commit given `files` / `delete_paths` never touches a record.
- A `files[]` commit moves the record too when its writes are files of a checkout (`files[].workspace_path` under a directory holding a record; the dispatcher stamps the parked `FileRef.workspace_path`): `WorkspaceSink.advance_checkout_files` finds the nearest record above each path and writes `checkout.advance_files`, which moves it to the new commit only when the record names the repository and the branch tip the commit was built on, each checkout file is committed at its own repository path, and no other tracked path of the checkout was written from elsewhere; otherwise the record is kept and the result says so, so the next `from_checkout` reconciles with the branch. Without it, a file committed through `files[]` then edited again was refused by `from_checkout` as an overlap with the branch.
- A `files[]` write of a checkout file never reverts the branch (#11852): before the tree is built, `contents._reconcile_workspace_writes` looks the records up with `WorkspaceSink.checkout_records_for` (the nearest record above each `workspace_path`, the lookup `advance_checkout_files` shares) and, for each record of the same repository with a commit, the file committed at its own repository path goes through `_reconcile_checkout_drift`, the `from_checkout` reconcile: a branch tip past the record's commit that changed the file since merges it three-way (record, workspace, tip) into the commit, and an overlap, a binary or a delete against a change refuses the whole commit with the hunks named. The workspace file is not rewritten (the answer says to run `sandbox_checkout_rebase`), and the commit must land on the tip it was merged against (`_moved_tip_refusal` otherwise). A file outside any checkout, of another repository's checkout or committed at another path is written as given. Before it, a checkout older than the branch wrote the file whole at the checkout's text and silently undid the branch's commits on it.
- `create_github_commit` `files[].edits`: `_parse_commit_changes` parses the edits with `services/sandbox_workspace/editing.parse_edits` into an `_Edits` write (refused with `content` or `file_id` beside it). Once the tip and its tree are read, `edited()` reads the file's blob (`GET git/blobs/{sha}`, the size from the tree entry checked against `_MAX_COMMIT_CONTENT_BYTES` first), decodes it as UTF-8 and applies `editing.apply_edits(..., read_with="get_github_file")`; an `EditError`, a missing path, a directory, symbolic link or submodule, or non-UTF-8 bytes return before the tree is built, so the branch is untouched. The new text then follows the plain-content path (`createCommitOnBranch`, signed), and `editing.unified_diff` of each edited file is appended to the result under "Edits applied:". No sandbox session is involved.
- Issue and pull request body edits (`providers/github/body_edits.py`): `update_github_issue` and `update_github_pr` take `edits` and `expect_updated_at`. `edited_body` parses the edits with `editing.parse_edits` (no line ranges), reads the issue or pull request (`GET issues/{n}` or `pulls/{n}`), refuses when `expect_updated_at` differs from the stored `updated_at`, applies the edits with `editing.apply_edits` to the stored body and returns the new body with `editing.unified_diff`; the tool then PATCHes it and answers "Body diff:". `body` and `edits` together are refused; the PR tool runs the closing-reference refusal on the edited body. GitHub has no conditional PATCH, so the guard narrows the race to the read-to-write gap of one call. `get_github_issue` keeps `include_body` for the body window and reads comments whole only with `include_comments` (first page of 100), so a body window of a long-lived tracking issue no longer carries every comment. `update_github_comment` (`providers/github/issues.py`) reuses `edited_body` on `GET/PATCH issues/comments/{id}`: the comment is named by its id or its link (`comment_id_of`), `body` and `edits` are exclusive, and `mark_self_action` takes the issue number from the stored `issue_url`.
- `merge_github_branch(resolutions=[...])` (`providers/github/merge_resolution.py`): a conflicting merge is landed in commits GitHub builds and signs, since `createCommitOnBranch` has one parent and a Git Data API merge commit is unsigned. `parse_resolutions` checks the argument before any request (`keep` branch|ref, `content`, or `workspace_path` read through `current_workspace().read_file`); `resolve_and_merge` requires exactly one resolution per path changed differently on both sides (`merge.conflict_answer` compares both sides' blob ids from the two compares: a path both sides hold at the same blob, or both removed, is listed apart and needs no resolution; a compare listing `_COMPARE_FILE_CAP` (300) files, GitHub's cap, is replaced by `_changes_from_trees`, the three recursive trees of the merge base, the branch and the ref diffed entry by entry, so no conflicting path is hidden; a conflict answer for a symbolic `from_ref` names the commit it resolved to and asks the next call to pass that SHA, so a whole-file `content` written against it is never merged over commits the ref gained since), reads both trees and the blobs it needs (`_MAX_READ_BYTES`, 40 MB), refuses a non-`100644` mode and any single file over `_MAX_COMMIT_CONTENT_BYTES` (named with its size), then (1) `createCommitOnBranch` commits giving each resolved path that differs the ref's version, (2) the Merges API, (3) commits writing every resolution not equal to the ref's version. Steps 1, 3 and the undo go through `_signed_commits`, which splits the payload with `split_batches` (first fit, largest first, each batch under 5 MB and 100 changes) and chains each commit on the last with `expectedHeadOid`. A failure inside step 1 undoes the commits already landed; a merge still refused after (1) is undone the same way. `manage_github_pr action=update_branch` asks for `expected_statuses={422}` and answers a conflict with `conflict_answer` for the PR's head and base (a fork's branch is named, not analysed); when that answer is a landed merge, the PR's self-action is marked and the answer says it merged line by line.
- A stopped call is never merged over (#9461): a call cut between the alignment commits and the merge (a worker stop, a deploy) leaves the branch on commits giving the conflicting paths the ref's version, and a replay merging from there would see those paths equal to the ref and keep the ref's version silently. `merge_github_branch` first calls `merge_resolution.drop_stopped_alignment`: it reads the branch tip and, while the tip is a single-parent commit whose headline matches `_ALIGNMENT_HEADLINE_RE` ("Take <ref>'s version of N conflicting file(s) before the merge", with the `(i/n)` batch suffix), walks back (at most `_MAX_STOPPED_ALIGNMENT`), then moves the branch to the commit before them with `_restore_head` (`updateRefs`, `beforeOid` = the tip read, so a push made meanwhile is never dropped). The merge then resolves every conflicting path from both sides again and the answer names the commits dropped. A refused move merges nothing and says why; a tip that is not an alignment commit changes nothing (one extra commit read per call).
- The branch moves once (#1517): `merge_resolution.resolve_and_merge` refuses resolutions that do not settle the conflict before any write, then makes a `tmp/commit-batch/` scratch branch at the target's tip and builds every step on it (the alignment commits, the Merges API merge, the `(k/n)` resolution chunks, the undo). Only when the whole resolution landed and checked is the target fast-forwarded once to the last commit (`PATCH git/refs`, `force: false`, and only while the target still points at the tip read), so a push, a CI run or a stacked pull request never sees a partial merge. A refused move leaves the target unchanged and keeps the scratch branch for a pull request; otherwise the scratch is deleted. Answers name the target, never the scratch. `drop_stopped_alignment` and `finish_stopped_resolution` stay for branches an older build left on its in-branch states.
- `rebase_github_branch` (`providers/github/rebase.py`, #11479): a true rebase on the server. The commits of `branch` since `upstream` (default: `onto`'s commit, the compare's merge base) are listed by one compare (at most 250, refused past it; merge commits skipped, as `git rebase` does). Each commit's change, its tree against its first parent's (`merge_resolution._read_side`), is applied to the tip of a work branch `rebase/<branch>/<expected_head[:12]>-onto-<onto[:12]>` made at `onto`: a path the work tip holds as the parent did takes the commit's blob, a path already equal to the commit's is skipped, any other path goes through `merge_hunks.merge_path` (diff3, JSON key merge); a commit with nothing left to write is dropped. Each replay is one signed `createCommitOnBranch` (`merge_resolution._signed_commit`, `expectedHeadOid` chained) with the original message plus `Co-authored-by` and `Rebased-from: <sha> (<date>)` trailers. A conflicting commit returns before any write of it, with `describe_conflicts`; `resolutions` are keyed by (commit prefix, path). A call made again reads the work branch's `Rebased-from` trailers and replays only the rest, so a cut call, a conflict stop or `max_commits` never replays a commit twice. The final move is `updateRefs` with `beforeOid = expected_head` (the lease), read back, then the work branch is deleted; a branch whose tip already carries `Rebased-from: <expected_head>` answers no change, so a replayed final call writes nothing.
  - Rebase state (`providers/github/rebase_state.py`, #11802): one Redis key per rebase, `github:rebase:<repo>:<branch>:<expected_head>`, 7 days, dropped once the branch moved. It holds the `onto` ref and the commit it pointed at on the first call (a later call naming the same ref replays onto that commit and says so when the ref moved; another ref is another rebase), every resolution passed so far (a later one for the same commit and path wins, so a call passes only the new commit's), and the commits settled with nothing to write. A merged or resolved path whose bytes equal the work tip's blob is not written, so a commit is never replayed as an empty commit; a `keep: onto` resolution is named in the answer as dropping that commit's change to the path. Redis unreachable: the call runs on its own arguments, as before.
- Write fence of a replaced attempt (`core/turn_writer.superseded_reason`, `agent_loop._execute_fenced`, #11802): besides the single-writer check before each tool round, every WRITE call of a round (not declared read-only, not classified read by name) asks the check again right before it runs. A call that starts after another attempt took the execution over is answered unrun with `superseded_write_refusal` (is_error), so a round's later write never lands after the resumed attempt started; the next round's `ensure_single_writer` stops the turn. Reads run. A turn no engine execution backs is unchanged.
- Key merge of JSON object files (`services/sandbox_workspace/jsonmerge.py`, #8880): when the diff3 line merge leaves conflicts, `rebase.merge_file` and `merge_hunks.merge_path` try `merge_json_objects`. If the three sides are JSON objects with no duplicate key, in a layout `json.dumps` writes back byte for byte (indent and ensure_ascii detected, final newline kept), the sides merge key by key. A key changed on one side takes that side, and the same change on both sides is taken once. A key added goes after its predecessor on its side (ours first, then theirs; the server merge of `merge_github_branch` and `manage_github_pr update_branch` passes `ref_first=True`, so the ref's keys come first and the branch's own keys follow them, and the branch's diff against the ref holds its own keys only, #1116), a key removed on one side and unchanged on the other is removed, and objects merge recursively. A key changed differently on both sides, or any uncertainty, answers `None` and the line merge's markers or hunks stand. This covers two branches appending keys to the i18n catalogs: neither the sandbox rebase nor `merge_github_branch` asks for a resolution any more.
- Keys the branch removed (#1095): `jsonmerge.removed_keys(base, ours, theirs)` lists the dotted keys the merge base and the ref hold that the branch removed. A three-way merge removes them without a conflict (right for a meant removal, wrong for a stale copy of a catalog). `merge_hunks._checks` sets `PathMerge.removed_keys` on every path both sides hold as JSON, and `merge.conflict_answer` adds `merge_hunks.removed_lines` ("Keys the branch removed that the merge base and the ref still hold", 20 keys per path, the rest counted) to the landed, clean and conflicting answers of `merge_github_branch` and `manage_github_pr update_branch`, before the Final head line. The merge itself is unchanged.
- Keys a resolution drops (#1311): `jsonmerge.dropped_keys(resolved, *sides)` lists the dotted keys every side holds that a resolved JSON content lacks. `merge_resolution._broken_resolutions` refuses a `content` or `workspace_path` resolution of a JSON path that drops one when both sides' versions were read (a stale copy of a catalog), naming 10 keys and counting the rest; nothing is written.
- Structured files are parsed after every merge (`services/sandbox_workspace/structured.py`, #11986): `structured_kind(path, *texts)` names JSON, YAML or TOML by extension (JSON by content when every side is an object or array), `parse_defect(kind, text)` answers the parse error or the key written twice (`object_pairs_hook` for JSON, a `SafeLoader` subclass refusing a repeated mapping key for YAML, `tomllib` for TOML) with its line, and `merge_defect(path, ours, theirs, merged)` judges a merge only when both sides parse (a Helm template or a JSON file with comments is not refused for a breakage the merge did not make). `rebase.merge_file(path=...)`: a clean line merge that breaks the file falls back to the key merge, else keeps the workspace bytes as a conflict naming the defect; an `on_conflict` lead merge that breaks it is written with markers instead and `FileMerge.detail` names the keys both sides changed (`jsonmerge.conflicting_keys`, dotted for nested keys). `FileMerge.validated` feeds `RebaseSummary.validated` ("Parsed after the merge, valid with no duplicate key"). `merge_hunks.merge_path` keeps `structured_kind` on `PathMerge` (it replaces `json_sides`), so a duplicate key or a YAML/TOML breakage is a defect of a clean merge and of `keep: both`; `LineMerge.validated` is listed in the `merge_github_branch` / `update_branch` answers; `merge_resolution._broken_resolutions` refuses a given structured content with the reason; `filediff.three_way` sets `defect` / `validated`, said in the `sandbox_diff_files` head. The #11937 shape (a key added on both sides with two values at one hunk join) is a conflict naming the key, never "merged cleanly".
- Line merge on the server (`providers/github/merge_hunks.py`, #8639): before answering a conflict, `conflict_answer` reads the merge base, branch and ref trees (`_read_side`) and the blobs of the paths changed on both sides (at most `MAX_MERGED_PATHS` 40 paths; the read budget is per path since #9040: each path's three versions are read, merged and released before the next, a path over `MAX_MERGE_READ_BYTES` 15 MB is a conflict with its reason resolved whole while the others still merge, and reads past `MAX_LINE_MERGE_TOTAL_BYTES`, the resolver's 40 MB `_MAX_READ_BYTES`, in all, a failed read or more than 40 paths fall back to the list of paths with the reason), and `merge_path` merges each with `rebase.merge_text` (diff3). A path whose hunks do not overlap gets its merged text as a `content` resolution filled in by `merge._settled`; when every path is clean the merge lands in the same call through `resolve_and_merge`. Otherwise nothing is written and `describe_conflicts` names each overlapping hunk (`TextMerge.regions`: 0-based line ranges on both sides; at most 40 lines per side, 300 characters per line, 20,000 characters in all), so the second call resolves the conflicting paths only. `keep: both` is the union merge (`merge_text(both=True)`: the branch's lines then the ref's in each overlapping hunk, no markers); a binary changed on both sides, a delete against a change and a non-`100644` path are conflicts with their reason and refuse `both`. Resolutions naming every conflicting path without `both` skip the line merge. Tests: `tests/test_github_merge_hunks.py` (unit cases and a fixture repository behind a fake GitHub), `tests/test_github_merge_resolution.py`, `tests/test_github_merge_branch.py`.
- Line merge time budget (#51): `line_merge` runs each path's `merge_path` in a worker thread (`asyncio.to_thread`, so difflib on a large file never blocks the event loop and the worker keeps its lease) within `LINE_MERGE_SECONDS` (60 s) in all; a path not merged in time, and every path after it, is a conflict with the reason "not merged within the time budget", resolved whole, so `update_branch` and `merge_github_branch` always answer.
- Merge output validation (#11708): `merge_path` checks every merged text before it is written. A line merge without an overlap that writes a line both sides added more often than either side holds it, or that breaks a file both sides held as valid JSON, is answered as a conflict with that reason (the JSON key merge is tried first). `keep: both` (`rebase.merge_text(both=True)`, `_union`) writes our whole hunk then theirs whole, nothing deduplicated or dropped (#12179: a blank line, a brace or a `with` body both hunks hold stays in each), and is refused when its text does not parse as the structured format both sides hold (`PathMerge.parse_defect`). `resolve_and_merge` refuses, before any write, a given content that still holds a conflict hunk, a `.json` / `.yaml` / `.toml` content that does not parse while the ref's version does, or a `.py` content (a `keep: both` union included) that does not parse while both sides do, naming the line (`_broken_resolutions`, `structured.resolution_defect`); `rebase_github_branch` refuses the same `keep: both` or `content` resolution of a commit before it is written (`providers/github/rebase._resolved`). `resolutions` take up to `_MAX_CHECKOUT_SPLIT_CHANGES` paths, split into signed commits under the per-commit cap. An `Error:` answer of `merge_github_branch` or of the `update_branch` fallback ends with `Outcome: landed true|false` and the branch head read from GitHub (`merge.outcome_line`). Per-hunk keep: `keep: branch|ref` on a path the line merge read is settled by `merge._settled` into `PathMerge.keep_ours|keep_theirs` (`rebase.merge_text(prefer="ours"|"theirs")`: the overlapping hunks take that side, every non-overlapping hunk of both sides is kept; a JSON object file the key merge reads is settled by `jsonmerge.merge_json_objects(prefer=...)` instead, the keys both sides changed taking that side and every key either side appended kept, so a catalog's tail hunk never drops the other side's keys), checked by `PathMerge.defect`; a binary, a delete against a change, a non-plain file (an executable file 100755 on every side merges as a plain one, since `createCommitOnBranch` keeps the mode of a path it overwrites; `merge_resolution._mode_refusal` refuses a link, a submodule, a directory or an executable bit on one side only, which the signed commit cannot write), a path over its read budget, a line merge that could not run or a per-hunk text that fails the checks keeps the whole side, and the answer's "How each resolution was applied" lines say which. Every answer of `resolve_and_merge` that wrote commits ends with `Final head: <40-char sha>` (`merge_resolution.final_head_line`), and `outcome_line` re-reads the branch through `_settled_tip` until it shows that commit (`final_head_of`), since a REST read can lag a GraphQL commit and name the intermediate merge commit. `sandbox_checkout_rebase` gives no base entry to a path only the ref's widened sub_paths cover (`rebase.base_files_of`), so it is taken from the ref, never read as a workspace deletion.

## Reads and edits without echoing (`sandbox_read_file`, `sandbox_grep`, `sandbox_outline`, `sandbox_read_symbol`, `sandbox_edit_file`, `sandbox_replace_in_files`, `sandbox_codemod`, `sandbox_apply_patch`, `sandbox_move_files`, `sandbox_write_file`, `sandbox_diff_files`)

- `sandbox_read_symbol(path, symbol, occurrence=0, max_line_chars)` reads one definition whole: `reading.symbols` gives every class and function with its span (Python through `ast`: qualified names `Class.method` / `outer.inner`, the first decorator line to `end_lineno`, definitions under a module-level `if` / `try` / `with` included; a module that does not parse and every other outlined extension through the `outline()` scan, a definition running to the line before the next one at its depth or above, trailing blank lines dropped). `reading.find_symbol` takes the exact qualified name, else every name whose last part matches; several matches are answered by `format_symbol_choices` (spans, `occurrence=N` reads one), none by the names containing it. The span is rendered by `format_window`, so the result cap and the continuation offset are the window's.
- `sandbox_playwright_trace(path, around, window_ms, frame_at, max_chars)` reads a Playwright `trace.zip` of the workspace (a CI artifact unzipped by `download_github_workflow_artifact`) in one bounded answer (#11242). `playwright_trace.parse` reads every `.trace` and `.network` member on the trace's one monotonic clock: `before`/`after` pairs by call id (test steps from `test.trace`, library calls from `N-trace.trace`, their `log` lines), the test `error`, main-frame `frame-snapshot` URLs, `console` and `screencast-frame` events, HAR `resource-snapshot` entries, and the attachments (name, type, member). `summarize` answers, in order: the failure (message without ANSI, locator, spec line, start, end and duration of the failing step), the attachments (JSON ones inlined up to 600 characters each, 1,500 in all, so `browser-log.json` lands before anything is cut), then inside the window the actions with their last call-log lines (request routing folded into a count, a passing test step that mirrors a browser call, hook, fixture or attach left out, an `APIRequestContext` call reduced to its status line), the page URL timeline, console lines, and the requests (status, method, path, duration; static files counted, not listed; the failures outside the window listed). The window runs from `window_ms` (default 5,000) before the failing action to 250 ms after its end; `around` is a call id or seconds from the trace start. `frame_at` writes the nearest screencast frame beside the zip as `frame-<s>s.jpeg`. The answer is cut at `max_chars` (default 8,000, at most 40,000), the lines cut counted. Not a zip, or a zip without a `.trace` member (the artifact archive itself), is refused with that reason. On the a2a artifact of run 43082693474 (1.9 MB, 782 calls, 406 requests) the answer is under 8,000 characters; the six free-form scripts it replaces printed 22 to 36k each.
- The tools read the bytes through `WorkspaceSession.get_bytes` (one blob) or `entries` + `WorkspaceSession.read_entry` (a search) and shape them in pure modules: `reading.py` (window, grep, outline) and `editing.py` (edits, diff). Every result is bounded, and what is left out is counted, never silently dropped: `MAX_WINDOW_LINES`, `MAX_MATCHES`, `MAX_RESULT_CHARS`, `MAX_GREP_FILES` / `MAX_GREP_BYTES`, `MAX_TEXT_FILE_BYTES`, `MAX_OUTLINE_ENTRIES`, `editing.MAX_DIFF_CHARS`.
- A binary file (`reading.is_text`: a NUL byte or undecodable UTF-8 in its first `TEXT_HEAD_BYTES` (8 KB); the head is decoded incrementally with `final=False`, so a multi-byte character cut at its end, a CJK catalog's for one, never makes a text file binary) has no window, no search hit and no outline; the refusal points to `sandbox_get_file`.
- The outline is chosen by the file's extension (Python through `ast`, with a `def` / `class` line scan when the file does not parse; a declaration-line scan for `_DECLARATIONS` extensions; headings for Markdown); an extension without a scan is named, not guessed.
- `sandbox_grep` skips `SKIPPED_DIRS` (`.venv`, `.xtm`) unless `path_prefix` names them, so installed packages never flood a search.
- Inline global flags (#453): `reading.compile_pattern` (the pattern of `sandbox_grep` and `sandbox_replace_in_files`) reads a global inline flag group written mid-pattern (`error|(?i)warning`), which Python refuses since 3.11, with the meaning older Pythons and other engines give it: `_hoist_global_flags` moves every unescaped `(?aiLmsux)` group to the start; a scoped `(?i:...)` group is untouched. A pattern still refused for an inline flag names `ignore_case=true` in its reason.
- `sandbox_grep` output budget and JSON log lines (#8776): `reading.format_grep` keeps whole matches (a match with its context lines is one block) up to `max_chars` characters (`DEFAULT_GREP_CHARS`, 12,000, through `reading.clamp_grep_chars`, 1,000 to `MAX_RESULT_CHARS`) and counts the matches cut in a trailer that names `max_chars` and `json_fields`. `json_fields` (or `compact_json`, which means `DEFAULT_JSON_FIELDS`: `timestamp`, `level`, `message`) shows a matched or context line that holds a JSON object (after at most 64 characters of prefix, such as a CI runner's timestamp, kept in front) as the values of those keys joined by ` | `, an absent key written `-` (`reading.compact_json_line`); the regex still runs on the whole line, and a line that does not parse is shown as before. A field may be a dotted path into a nested object (`attributes.queue`, `reading.json_get`; a key written with the dot wins).
- `sandbox_grep` grouped by a JSON key (#9281): `group_by` (`reading.clamp_grouping`, a `Grouping` with `time_field`, default `DEFAULT_TIME_FIELD` `timestamp`) keeps no line: `reading.grep_text` counts every matched line under the value of that key in a `GroupStats` per file (count, first and last line number and time in log order; the time is the line's `time_field`, else its runner prefix), and `reading.format_groups` answers one row per value sorted by name with one cell per matched file side by side (`Columns: [1] <path>; [2] <path>`, `-` for a file with none), rows bounded by `max_chars` with the rows cut counted. `max_matches` does not bound a grouped search; at most `MAX_GROUPS` (500) values are kept and the lines of later values are counted in a trailer, as are the matched lines with no JSON object or no such key, per file. Use: a red job log and a green one saved in one directory, one call per question ("which queues got a message, and when, in each job").
- `sandbox_grep` budgets: `reading.plan_grep` takes the selected files in path order, skips unread a file past `MAX_GREP_FILE_BYTES` (32 MB, so a CI job log written with `to_workspace_path` is searched) or with a `BINARY_SUFFIXES` suffix (images, fonts, archives, media, compiled objects), and counts both as skipped without stopping. It stops at `MAX_GREP_FILES` (25,000), `MAX_GREP_BYTES` (128 MB) or the call's time budget (`commands.wait_budget()`, checked before each batch, #758: a 4,000-file cap stopped a whole xtm-one checkout before `frontend/src`) and records the rest in `GrepResult.left`; the answer names how many files were not searched, the directories holding most of them and the first one. Blobs are read in batches of at most `GREP_READ_FILES` (8) files and `GREP_READ_BYTES` (16 MB), a batch's reads run at once with `asyncio.gather`, matches are taken in path order so the result is deterministic.
- Reads see the workspace as it is when they run (#8617). A commit moves the manifest, then drops the blobs it orphaned (`plan.orphaned`), so a read holding a manifest taken just before (a call of the same tool round, a resumed turn on another worker) could name a blob that no longer exists and answered the raw `Object not found in storage: sandbox-workspaces/...`. Now: (1) `sandbox_read_file`, `sandbox_grep`, `sandbox_outline` and `sandbox_read_symbol` wait for the workspace writes of their tool round (`session.settled()`, as `sandbox_run_command` does) before reading the manifest, so an edit next to a search is seen; the write tools themselves (`sandbox_edit_file`, `sandbox_diff_files` with `write_merge_to`) read with `settle=False`, they are counted in flight and would wait for themselves. (2) `WorkspaceSession.read_entry` reads a blob and, on `FileNotFoundInStorageError`, reads the manifest again once and reads the path's current blob: a path gone is `FileNotFoundError`, a blob still missing is `WorkspaceFileUnreadableError`, whose message names `workspace/<path>`, never the storage key. (3) `sandbox_grep` reads each file through `read_entry`: a file gone meanwhile is left out, an unreadable one is recorded in `GrepResult.unreadable` and named in one line (`[N file(s) not searched, their content missing from storage: ...]`) while the other files are searched.
- A write never points a path at a released blob (#1496). `WorkspaceSession.commit` skips the upload of a content the manifest held when it looked and passes those contents as `reused` to `store.commit`; under the row lock (the memory store's lock in tests) a reused content no path holds any more raises `BlobReleasedError`, nothing written, and the session uploads the released contents from the bytes it has and commits once more (metric `reused_blob_released`). Before it, a concurrent commit that released the content between the look and the lock left the path listed with its bytes gone (a resumed checkout: 171 files unreadable; a command stage failing on `UploadReadError`).
- A line of a window or a match shows `DEFAULT_LINE_CHARS` (400) characters, the rest counted in the cut marker; `max_line_chars` on `sandbox_read_file` and `sandbox_grep` raises it up to `MAX_LINE_CHARS` (20,000) through `reading.clamp_line_chars` (unset, not an integer or below 1 is the default), so a Markdown table row, a minified JSON or YAML line or a generated file is read whole without `code_interpreter`. The marker names the argument, and says the cap is reached at 20,000; `MAX_RESULT_CHARS` still bounds the whole result.
- `sandbox_grep` argument and output edges (#11765): (1) `paths.normalize` drops a `.` segment (`retest/xtm-one/.`, `src/./a.py`, `.` alone is the root for a prefix), and still refuses an empty or `..` segment. (2) `reading.selected` reads an `include_globs` entry against the file name, the path relative to `path_prefix` and the workspace path, so `sub/*.py` under `src` and `src/sub/*.py` select the same files in `sandbox_grep`, `sandbox_replace_in_files` and `sandbox_codemod`, which share the selector. (3) With `context_lines`, a match whose context overlaps or touches the previous match's block of the same file continues it (`Match.last`, `Match.joined`): its lines are printed once, every matched line marked `:`, no `--` between them; each match still counts once against `max_matches`. (4) A matched line longer than `max_line_chars` is shown as the window of that many characters centred on the first match (`reading._match_window`), the characters before and after counted; a match inside the head keeps the head cut as before. Hitting `max_matches` is a normal trailer, never an error.
- A `sandbox_read_file` call with no `max_lines` (#8828) answers the default window (`DEFAULT_WINDOW_LINES`, 200) bounded at `DEFAULT_WINDOW_CHARS` (16,000) characters through `format_window(max_chars=...)`: a file of long lines answers its first part, a trailer `[window cut at 16,000 characters: N lines in total; pass max_lines ...]` and `continue with offset_line=M`. An explicit `max_lines` keeps the `MAX_RESULT_CHARS` (60,000) bound. A single line longer than the bound still shows, so a window is never empty.
- `sandbox_edit_file` is the workspace sibling of `edit_file_content`: `editing.parse_edits` validates the list (at most `MAX_EDITS`), `editing.apply_edits` applies in order and raises `EditError` on the first `find` that is missing or ambiguous (unless `replace_all`), so the file is written only when every edit applied. `parse_edits(allow_ranges=True)` (passed by `sandbox_edit_file` only; `create_github_commit`'s `edits` stay find/replace) also accepts a line-range edit `{start_line, end_line, expect_first, expect_last, replace}`: `_apply_range` cuts the text with `splitlines(keepends=True)`, the numbering `reading.window` shows, checks that `expect_first` occurs in line `start_line` and `expect_last` in line `end_line` (required when the range spans several lines), and raises `EditError` naming the line it found when they do not, so a number read before the file changed never cuts the wrong block; the range counts the text as the previous edits of the call left it, a CRLF file is handled by the same LF normalisation as a find, and a `replace` without a final newline gets one when the replaced last line had one. A range end that is a blank line is anchored by `expect_first_blank` / `expect_last_blank` (booleans) instead of a text; `_check_line` refuses the edit when that line is not blank. A find edit may carry `occurrence` (an integer >= 1, `_parse_occurrence`, `sandbox_edit_file` only: `parse_edits(allow_ranges=True)`; the other callers ignore the key): `_replace_occurrence` replaces that occurrence alone of a non-unique `find`, counted non-overlapping in the text as the previous edits left it, refuses a number past the count with the count, and refuses `occurrence` with `replace_all`. A move edit `{start_line, end_line?, expect_first, expect_last?, move_to_after_line, expect_target?, expect_target_blank?, replace: ""}` (`_parse_move`, `_apply_move`; `Edit.is_move`, `move_after`) moves lines `start_line`..`end_line` after line `move_to_after_line` (0: the top), both numbered in the text before the move (as the previous edits of the call left it): the block is anchored as a range is, the target line by `expect_target` or `expect_target_blank` (not asked for line 0); a target inside the block or right before it, past the end, a non-empty `replace`, or a `find` / `insert_after_line` in the same edit is refused; a moved or target line without an ending gets one. `landed.edit_key` names a move by its range and target, and `edit_verdict` gives it no verdict (it writes no text to find). An insert edit `{insert_after_line, expect_first?, expect_first_blank?, replace}` (`_parse_insert`, `_apply_insert`) puts a non-empty `replace` after line `insert_after_line` (0: the top of the file, no anchor asked) and replaces nothing; the anchor line is checked like a range's first line, a `replace` without a final newline gets one, and an anchor that is the last line without an ending gets one first. Any edit may carry `replace_from` (a workspace path) instead of a non-empty `replace` (#305): `editing.replace_from_sources` names them (both given is refused), `sandbox_edit_file` reads each with `_text_of` (an absent or binary file refuses the call, nothing written) and `editing.with_replace_from` sets its text as the `replace` before `parse_edits`, so a section drafted in `work/` is inserted or appended into a source file without its text re-sent; `landed._with_sources` reads the same files for `edit_probe` and `judge` (an unreadable source: no verdict). The write goes through `session.put_bytes(operation="edit")` and is audited (`workspace_edit`). The result is the diffstat and the unified diff, a read-back rather than a patch: `editing._compact` shortens every line longer than `LONG_LINE_CHARS` (400). A removed line and the added line that replaces it show only the changed part with `CHANGE_CONTEXT_CHARS` (80) unchanged characters on each side and the rest counted (`[N unchanged chars]`); an unpaired long line keeps its first 400 characters and a long context line its first `CONTEXT_LINE_CHARS` (120), the rest counted. Short lines, hunk headers, the diffstat and the bytes written are unchanged.

That summary is the default answer, followed by `ci_logs.last_lines` (the last `LAST_LINES` 25 non-blank lines, at most `MAX_LAST_CHARS` 3,000 characters); `failures_only=true` drops those lines, `tail=true` and a log with no failure cue keep the `_MAX_LOG_CHARS` tail. A summarised log that names `Error Context: test-results/<dir>/error-context.md` (a failed Playwright test) gets the page that test saw appended by `_playwright_contexts` (#11266): the job's run, its `test-results*` artifacts (not expired, at most `_MAX_CONTEXT_ARTIFACT_BYTES` 25 MB, the one sharing most words with the job name first, a `1/6` shard read as job-index 0, at most `_MAX_CONTEXT_ARTIFACTS` 3), only the matching `error-context.md` members read, reduced by the pure `app/integrations/playwright_context.py` to the snapshot's text lines without the navigation, banner, contentinfo and complementary landmarks or `[ref=...]` attributes (`MAX_CONTEXTS` 3 tests, `MAX_SNAPSHOT_LINES` 40, `MAX_SNAPSHOT_CHARS` 2,500); a file not found names the paths and the download to make, never fails the read. `split_steps` keeps the runner's echo of a step (a `##[group]Run ...` group up to its `##[endgroup]`: the script, `with:`, `env:`) apart as `Step.header`, never scanned for a cue (`expect-error: false` is no error); another group inside a step's output (an action's `Uploading results`) stays in it as a `> name` line. With no cue left (a step that dies without an `##[error]` line), `failures_only=true` answers where the job stopped: `Summary.stopped_step` and its last `STOPPED_LINES` (40) non-blank lines before the post-job cleanup, at most `MAX_STOPPED_CHARS` 6,000 characters, a run of `MIN_ENCODED_CHARS` (200) base64-like characters replaced by an omission marker. `get_github_pr` / `get_github_issue` show `_BODY_HEAD_CHARS` (1,500) of the body and one `one_line` per review or comment (`_ITEM_PREVIEW_CHARS` 240; the latest `_DEFAULT_COMMENTS` 10 comments); `include_body=true` reads the body by window through `_common.body_section` (default 20,000, at most 60,000). On an open PR, `get_github_pr` also reads the head's check runs and statuses (`checks.classify_ci`) and the review thread counts (`_THREADS_COUNT_QUERY`) in parallel; either line is left out when its read fails. `_common.gh_graphql` passes `TRANSIENT_RETRY_STATUSES` to `safe_request` for a document without the word `mutation`, so a gateway 502/503/504 on a query is retried with the shared backoff and a mutation never is.

## Commands (`sandbox_run_command`, zero-configuration detection, `.xtm-one/checks.toml`)

- No file is required in a target repository. A checkout without `.xtm-one/checks.toml` (almost every repository) gets the checks `detect.py` reads from what it already has; `commands.checkout_checks` lists the checkout (`session.entries`), reads only `detect.candidates` (the workflows under `.github/workflows/` and the CircleCI configuration `.circleci/config.yml`, then `package.json`, `pyproject.toml`, `setup.cfg`, `pom.xml`, `build.gradle(.kts)`, `Cargo.toml`, `dbt_project.yml`, `Makefile`, compose files, at most `MAX_CANDIDATES` files of `MAX_FILE_BYTES`, `MAX_DEPTH` levels, never under `SKIP_DIRS`) and calls the pure `detect.detect`. Sources, strongest first, the first to name a (directory, stack, kind) wins: (1) the repository's own workflows, every `run:` line `detect.classify` recognises as an install, lint, format check, type check, parse, unit test or build, in its directory (`defaults.run.working-directory`, the step's `working-directory`, `cd DIR && ...`, a bare `cd` moving the rest of the step; an absolute CI mount path is mapped to the checkout directory it ends with, a path outside the checkout drops the line; a repository Python script, `uv run plugin/scripts/flow_lint.py` or `python scripts/run_tests.py`, takes the kind its file name says, as a `package.json` script name does, its PEP 723 header carrying its dependencies; a gate script named `check_*`, `validate_*` or `verify_*` is a check of its own, `python-check-<rest>` (`_gate_script_kind`); an option of such a script whose value is a `${{ }}` expression is left out with its flag (`_without_expression_options`), the call's args giving it); release, publish and deploy workflows and jobs, global tool installs (`npm install -g`, `pip install --user`), end-to-end runs and every other `${{ }}` expression are never read; a line with shell syntax or an environment assignment runs as `sh -c`; then the CircleCI configuration (`detect._circleci`), every job's `run` steps read the same way: the job's `working_directory` (`~/repo`, default `~/project`) is where its checkout step writes the repository, so its steps run at the checkout root, a step `working_directory` below it is that directory of the checkout and any other one (`~/`, a path outside it) drops the step, a line or a directory naming a pipeline parameter (`<< parameters.x >>`) is skipped, the job directory written in a line (`flake8 ~/repo`) becomes `.` at the root, the job's `environment` travels with its checks, its first `docker` image's `python:X.Y` tag is the job's Python and the next images are listed as services; a release, publish or deploy job is not read (a repository whose format gate runs `isort --profile black --check .` from the root on CircleCI gets that root check, #191); (2) the manifests: `package.json` scripts with the manager its lock file or `packageManager` names (one install at the lock, scripts per package; the manifest at the lock and every workspace member also offer each namespaced script (`a:b`) one of whose segments is a generator or gate verb (`generate`, `extract`, `compile`, `check`, `test`, `validate`, `verify`: `check:bundle-size`, `i18n:check`, `i18n:extract:clean`), a hyphenated one read the same way with the gate nouns `checker`, `validator`, `verifier` too (`i18n-checker`, `check-licenses`, `generate-i18n-checker-constant`; a script whose body names a URL, a live API, is left out), and any script whose body runs a code generator (`graphql-codegen`, `relay-compiler`, `openapi-typescript`, `orval`, `prisma generate`, `buf generate`: `relay`, `build:types`) so a narrow checkout without its generated sources can produce them before the types or unit check, that a kind or a workflow line does not already run as a check of its own, `node-<script>` with `:` written `-` and the member's directory as prefix, e.g. `node-check-bundle-size`, `front:node-i18n-check`, end-to-end, watch, install, release, publish and deploy scripts left out, offered after every manifest's kinds so the `MAX_CHECKS` bound never drops a kind, #10981; a `pnpm install` check, detected or read from a workflow, gets `--config.strict-dep-builds=false` unless its line sets that option, so pnpm 11+ reports unapproved dependency build scripts as a warning instead of failing with `ERR_PNPM_IGNORED_BUILDS` after linking every package; every pnpm check, the install included, runs the release its checkout pins through corepack, `corepack pnpm@<version> ...` (`detect.pnpm_pin` then `detect._apply_pnpm`): the nearest `packageManager` first (`pnpm@x.y.z`, its `+sha512` hash kept; another manager's means no pin), else the nearest `engines.pnpm`, an exact version as is and a semver range as written (corepack runs the highest release satisfying it); the image's `pnpm` shim resolves `packageManager` but not `engines`, so a repository pinning pnpm only there (`engines.pnpm: 10.10.0`) got corepack's default release and failed its install on `ERR_PNPM_UNSUPPORTED_ENGINE`; the version and its source are in the check's description, the argv carries it so the run output shows it and the install cache key (which hashes the argv) is per version, and a Relay-first check pins both its generator and its check; a checkout with no pin runs `pnpm` as before), `uv.lock` / `poetry.lock` / `requirements*.txt` and the ruff, flake8, mypy and pytest configuration (a Django project, `manage.py` beside the manifest and no pytest configuration or `tests/` directory, gets `python manage.py test --noinput` as its `python-unit`, and a workflow line `python manage.py test` classifies as a unit test; the database its CI services start is listed with the services, not started), `pom.xml` (root of a multi-module build, `mvnw` when present), Gradle and its wrapper, `Cargo.toml`, `dbt_project.yml`; (3) `Makefile` targets named like a check, run on the stack of their directory. A check is named `<stack>-<kind>`, prefixed by its directory (`front:node-unit`), and carries its source in its description, so the listing says where each command came from. Image key per stack: `detect.STACK_IMAGES`, the generic toolchain images first (`toolchain-node`, `toolchain-python`, `toolchain-jvm`, `toolchain-rust`, `toolchain-dbt`), then the locked dev images and the plain keys, the first one `OPENSANDBOX_IMAGES` configures. A Helm chart root (a `Chart.yaml` with none above it, read from the listing) gets `<dir>:helm-lint` (`helm lint .`) and `<dir>:helm-parse` (`helm template xtm-check .`) on the first toolchain image configured, since `helm` is a binary of every toolchain image and of no dev image; a chart whose dependencies are not vendored under `charts/` needs `helm dependency build` first. Services the CI jobs (`services:`) and the compose files start are listed beside the checks (`detect.Infra`), as information: starting them is the lab's job (`agentic-labs.md`). No product, repository or file of a target repository is known to the platform (invariant 18): the tools named are the public conventions of the manifests themselves.
- Workflow env (#10430, #11503): `detect._layer_env` overlays the workflow, job and step `env:` blocks; a literal travels, `${{ env.NAME }}` takes the outer literal, any other expression maps the name to `None` (never copied). `_Collector.add` splits them into `CheckSpec.env` and `CheckSpec.env_unset`; `commands.resolve(env=...)` validates the call's override (`commands.env_override`: names only, no runner or container variable, `detect.MAX_ENV` / `MAX_ENV_CHARS`) and lays it over the check's env, dropping the names it sets from `env_unset`; the answer ends with `commands.unset_env_note` when names remain unset.
- A package whose unit script runs a Node wrapper of its own (`"test": "node test/run.mjs"`) that collects every test file and appends them after its arguments cannot run one file through `node-unit`: a path given as args runs beside the whole suite. `detect._node_test_files` then adds `<dir>:node-unit-file`, `node --import ./<wrapper dir>/<loader> --test`, when a loader (`register.mjs`, `register.js`, `setup.mjs`, `setup.js`) sits beside the wrapper: the call the wrapper makes, with the args as the only files run (`args=["src/a.test.ts"]`). No loader beside the wrapper, a wrapper outside the checkout or a script that is already `node --test`: no extra check.
- A package that depends on `vitest` (`dependencies` or `devDependencies`) and has no such wrapper gets `<dir>:node-unit-file` from `detect._node_vitest_files`: `<runner> vitest run --coverage.enabled=false` (`yarn`, `pnpm exec` or `npx --no-install`), the args being the only test files run. Its unit script may run the whole suite with coverage (`vitest run --coverage`, a coverage provider the install may not hold: minutes and hundreds of temporary files for one file). When the package holds several `vitest.config.*` files, the one whose name holds `unit` and not `integration` is passed with `--config` (`vitest.config.ci-unit.ts` beside `vitest.config.integration.ts`), so unit tests run without the services an integration config needs; with one config or none vitest picks its default.
- A package linted by ESLint (an `eslint.config.*` or `.eslintrc*` in its directory or above it, and `eslint` in its own or an enclosing manifest) gets `<dir>:node-lint-file` from `detect._node_eslint_files`: `<runner> eslint` from the package directory, the args being the only files linted. Its lint script usually names its target (`eslint --max-warnings 0 .`, or `run lint:lint` reaching a root script that does), so `node-lint` with two files as args still lints the whole tree, and a type-aware config on a large front ran the container out of heap after about 205 s. A Yarn Berry member whose ESLint is the workspace root's runs `yarn run -T eslint` (a member runs only its own dependencies' bins). The check declares `affected = "files"` on the ESLint source globs and `affected_by_default`: a call without args lints the changed sources, never the tree. Relay and fetched build steps run first, as for `node-lint`.
- The `unit` kind takes the first of `test:unit`, `unit`, `test`; when that is `test` and the manifest also has a `test:<name>-unit` or `test:<name>:unit` script (`test:ci-unit`), `detect._unit_script` runs that one instead: a package whose `test` runs its integration config with coverage (opencti-graphql) keeps its `node-unit` free of services and of the coverage provider.
- A Relay package (`relay-compiler` in `dependencies` or `devDependencies`, and a script whose command starts with `relay-compiler`, `"relay": "relay-compiler relay.config.json"`) imports what the compiler writes under `__generated__/`, which git ignores and CI produces in its build: without it every `*.graphql` import is unresolved. `detect._relay_first` wraps the package's `node-lint`, `node-types`, `node-unit` and `node-unit-file` checks as `sh -c '<manager> <script> && exec "$@"' xtm-relay <the check's argv>`, so the artifacts are generated first and the call's args still reach the check; install, build and the named scripts are left as they are, and a check whose argv already runs the script is not wrapped. A script that runs the compiler alone is preferred (#303): XTM Hub's `build` is `relay-compiler && next build`, and picking it ran a whole Next build (Google Fonts fetched, failing offline) before every lint and unit check; when only a chained script calls the compiler, its first command runs alone through the package manager (`yarn relay-compiler ...`, `npx --no-install relay-compiler ...`, `pnpm exec relay-compiler ...`). The generated files are kept out of the change set by the checkout's `.gitignore`.
- A node package whose `build*` script calls a `get-*` script of its own (opencti-graphql: `build:prod` runs `run get-connectors-manifest`, which fetches `src/__generated__/opencti-manifest.json`, git-ignored and imported by the sources) runs those steps before its `lint`, `types`, `unit` and `unit-file` checks (`detect._fetched_first`): without the file `tsc` fails TS2307. The description says `build steps run first`.
- The install runs `yarn install --mode=skip-build`, so no dependency build script runs. A package that depends on an add-on its workspace root marks `dependenciesMeta.<name>.built: true` (opencti-graphql: `node-calls-python`, `re2`) gets `yarn rebuild <names>` before its `unit` and `unit-file` checks, then each of its `install:*` scripts (`install:python`: the pip packages its Python bridge imports), as the CI unit job runs them (`detect._runtime_first`); lint and types stay without them. The description says `runtime first`.
- `actions-lint` (`actions_lint.py`): a checkout whose listing holds a workflow (`.github/workflows/*.yml`) or a composite action (`action.yml` anywhere) gets this check from the listing alone, whatever its stacks, and a checkout with `.xtm-one/checks.toml` gets it beside its declared checks unless it declares a check of that name (`detect.actions_lint_check`, `commands.checkout_checks`). With `affected=true` it takes the changed files matching `detect.ACTIONS_LINT_GLOBS`; it needs no install. The module is a script run inline (`python -c <its source> [files]`, `detect.ACTIONS_LINT_SCRIPT`) from the checkout root on the Python image, needing only the standard library: when PyYAML is importable (the toolchain-python and python-dev images carry it) it parses every file, a syntax error reported at its line (`yaml-syntax`), and checks the shape (`actions-schema`: a workflow has `on` and a `jobs` mapping; an action has `runs.using`; each composite step has exactly one of `run` and `uses`, and `shell` beside `run`); it runs `actionlint` on the workflows (both images carry the digest-pinned binary), and always extracts every `run:` block whose step runs on bash or sh (no `shell:` is bash), replaces each `${{ ... }}` with a placeholder word and runs `bash -n` on it, each error mapped back to its line in the YAML file. A layer the image cannot run is a finding, never a silent skip (`missing-layer` at line 1 of the first file: PyYAML not importable, or `actionlint` not on `PATH` while a workflow is checked), so a green result means every layer ran; `--allow-missing-layers` turns it off for a local run, and the toolchain-python smoke test of `sandbox-images.yml` asserts both. Findings print as `path:line: message [rule]` and go to `.xtm/actions-lint.sarif` (the check's SARIF report); args name the files to check. Tests: `tests/test_sandbox_actions_lint.py`.
- A per-project test script: a monorepo whose CI runs its tests through one repository script per project (`bash run_test.sh "$req_file"` over a matrix of `test-requirements.txt` files) gets one check per directory holding a `test-requirements.txt`, named `<dir>:python-test` (kind `test`, after `unit`). `_workflows` records in `_Collector.scripts` a run line of a step whose text names requirements and that calls a `.sh` file of the checkout on one shell variable (`_SCRIPT_CALL`); `_script_tests` turns each recorded script that exists in the listing into the checks: `sh -c SCRIPT_TEST_SHELL xtm-test <script> <requirements>`, cwd the repository root (as CI), image `toolchain-python` first, `report = junit`, `report_path = .xtm/junit.xml`. Such scripts call `git merge-base origin/master HEAD` and `git diff`, and a local package build lists its files through git, while a checkout has no `.git`: `SCRIPT_TEST_SHELL` makes a throwaway repository whose base commit (under `origin/main` and `origin/master`) holds everything but the project and whose head holds the whole checkout, so the script sees the project, and only it, as changed and runs its tests; an empty base would make every file a change and the script would print the whole diff of the shared package (815 KB of output in the first trial). After the script it copies the JUnit and `coverage.xml` files the run created to `.xtm/`, removes every file the run created outside `.xtm/` (`git clean -fdx`) and the throwaway `.git` (trap), so the read-back of the workspace carries no venv, report or `.git`; a checkout with a `.git` of its own runs the script as it is. The inline script is shown as `(inline script of N lines)` in a listing, an answer and the audit summary (`checks.shown_argv`). The run needs the pods to reach PyPI and github.com (pip installs from git URLs), which the toolchain pods do where `AGENTIC_CODING` is on.
- `.xtm-one/checks.toml` stays an override, used by this repository for its locked dev images: a checkout that carries it runs what it declares and nothing is detected. A `checks.toml` that holds no `check` table (services only, a lab another repository adds without restating its CI: `checks.declares_checks`) keeps the detected checks, and the listing still names its services; its header then names the file as declaring no `[check.NAME]` table (`CheckoutChecks.has_checks_file`), never "no .xtm-one/checks.toml", and so does the refusal when nothing is detected either (`_nothing`). The listing bounds both parts: past `checks.LISTING_MAX_CHARS` (4,000) the checks are one short line each, past `checks.SERVICES_LISTING_MAX_CHARS` (2,000) the services are named on one line (`describe_services(budget=...)`), their descriptions, ports and dependencies left to `sandbox_start_service` without a service, so a listing read for one check name stays a few KB on a repository with dozens of lab services. A `checks.toml` the agent writes into a checkout in its workspace is read the same way and is intended: it is how an agent runs a command the detection does not name without `CODE_INTERPRETER_COMMAND_ALLOW_ARGV`, in the same container, image allow-list (`known_images`), timeout cap and network policy as a detected check, and it is never committed unless the agent commits it (it shows in `sandbox_checkout_status` as added).
- A narrow checkout also keeps the **files its tests name outside it**: `extract_tree` reads every test file and TypeScript, Vite or Relay config under the sub_paths (`detect.is_referencing_file`), plus such a config in a directory above a sub_path (`detect.is_referencing_config`: the `relay.config.json` of a frontend whose `src/schema/relay.schema.graphql` a checkout of `src/utils/hooks` would otherwise leave out, so the Relay ESLint plugin failed before eslint), and `detect.referenced_files` resolves each quoted `./` or `../` literal (no `${`) from the file's directory, then from the sub_path that holds it, with the suffixes an import omits (`.ts`, `/index.ts`...). An existing file outside the sub_paths is kept as a companion (`ExtractedTree.referenced`), a directory a test reads whole only within `MAX_REFERENCED_DIR_FILES` and `MAX_REFERENCED_DIR_BYTES`; a path out of the repository or under `detect.SKIP_DIRS` adds nothing. A frontend checkout thus carries the backend fixtures its tests read, and an Office add-in checkout the web modules its tests import, without an `add_paths` that widens to the whole `backend/`.
- A narrow checkout inside a **Relay project** also takes its `src` (#188): the Relay compiler and the test transform read every `graphql` tag of the `src` a `relay.config.*` names, so a query spreading a fragment defined elsewhere failed as an undefined fragment until the whole `src` was grown by hand. `detect.relay_source_dirs` reads the `src` of each Relay config in or above a sub_path's project (JSON parsed, `src: './x'` read from a `.js` / `.ts` config) and adds it to the sub_paths when it is not under one already, lies in the repository (never its root) and holds at most `MAX_RELAY_SOURCE_BYTES` (64 MB; past it only the schema is kept, as above). - A narrow checkout also keeps the **files its CI commands name outside it** (#11712): `detect.command_named_files` reads every `run` line of the repository's workflows (release, publish and deploy workflows and jobs left out, from the step's working directory and after a `cd`) and every script of the `package.json` files above and under the sub_paths (from the manifest's directory), and keeps each word that names a regular file of the repository outside the sub_paths (`ExtractedTree.named`): the root `ci-requirements.txt` a format job installs with `-r`, a `node ../../scripts/x.mjs` a package script runs. `detect._TOOL_CONFIG` also keeps the Python tool files above a sub_path (`.isort.cfg`, `.pylintrc`, `.pre-commit-config.yaml`, `.coveragerc`, `.yamllint`, `.markdownlint*`, `.sqlfluffignore`) and the secret scanner configuration (`.betterleaks.toml`, `.gitleaks.toml` and their `*ignore` files), so the `secrets` check of a narrow checkout scans with the repository's allow-list. A workflow job that runs a second formatter or linter of the same kind in the same directory (isort then black) gives a second check named after the tool (`python-format-black`, `detect._second_tool_kind`), so the sandbox gates on what CI gates on. Every detected formatter check that runs in check mode gets a write-mode sibling named `<check>-apply` (`detect._apply_formatters`, `_write_argv`): black, isort and `ruff format` lose `--check` / `--check-only` / `--diff`, `cargo fmt` loses `--check`, prettier's `--check` becomes `--write`, `spotless:check` / `spotlessCheck` becomes `spotless:apply` / `spotlessApply`; the Python and prettier ones take the changed files by default (`affected_by_default`, Python ones on `*.py` / `*.pyi`), so a red format check is fixed by one run instead of a hand edit per hunk, without reformatting what the change did not touch; args name other files, `.` the whole directory. Every locked Node install (`yarn install --immutable` or `--frozen-lockfile`, `pnpm install --frozen-lockfile`, `npm ci`) gets a `<dir>:node-relock` sibling (`detect._node_relock`, `_relock_argv`): the same manager in lock-update mode (`yarn install --mode=update-lockfile`, `pnpm install --lockfile-only`, `npm install --package-lock-only --ignore-scripts`), with no install first and not an install, so after a dependency or pin bump the lockfile it rewrites is the change `from_checkout` commits instead of a hand edit. A repository that keeps release notes in a root directory (`.changeset/` declared by `.changeset/config.json`, `.changes/` by `.changie.yaml`; `detect.RELEASE_NOTE_DIRS`) has that directory added to the sub_paths (`ExtractedTree.release_notes`, within `MAX_RELEASE_NOTE_FILES` and `MAX_RELEASE_NOTE_BYTES`), so a note written there is covered by the record and committed by `from_checkout`. A file outside the record and its sub_paths still as an earlier, wider tree left it (the out-of-scope baseline) is named by `sandbox_checkout_status` as a leftover (`CheckoutChanges.leftover`, `leftover_note`): never a change, but not at the record's commit, so a check that reads it may read an old version.
- A narrow checkout also keeps the **local files its install reads** (#11750): `detect.package_local_files` reads the root and workspace `package.json` files the checkout keeps (`dependencies`, `devDependencies`, `optionalDependencies`, `peerDependencies`, `resolutions`, `overrides`) and the `.yarnrc.yml` above a sub_path; a value with the `patch:` protocol (each path after `#`, the `::` locator parameters left out), `file:`, `link:` or `portal:`, and a `yarnPath`, `patchFolder` or local `plugins` path, is resolved from that file's directory (`~/` from the root). A file is kept as a companion, a directory gives its files (at most 50 files and 2 MB); out of the repository, under `node_modules` or under a sub_path adds nothing. A checkout of `opencti-platform/opencti-front/src/utils` keeps the root `patch/react-relay.patch` its `resolutions` names, so `node-install` no longer fails ENOENT. `ExtractedTree.local` lists them and `materialize_repository` names them.
- A narrow checkout is widened to what its declared checks import: a check runs from its `cwd` and imports what lies there (`python -m pytest` from `backend/` collects the whole `app` package), so `extract_tree` reads the archive's `.xtm-one/checks.toml` (`_declared_checks`, at most `_MAX_CHECKS_FILE_BYTES`; absent or invalid: nothing widens) and `detect.widen_to_check_dirs` replaces each sub_path strictly inside a declared `cwd` by that directory, the outermost first; a check run from the repository root never widens (the whole tree). `ExtractedTree.sub_paths` carries the result: the checkout record, the replace set and the answer use it ("backend/app/x widened to backend/ (the directory backend-unit, ... run from)"), the audit row keeps `requested_sub_paths`. - `commands.run_command` runs it on the OpenSandbox backend only (`commands_offered()`: the local subprocess sandbox runs no command, so the tool is not offered there), in a container of the check's image kept per workspace and per image key (`kernel_state["commands"][<image>]`, found again by id from any replica, renewed per call, discarded after a timeout). Its lifetime: the check's timeout + `HARD_TIMEOUT_MARGIN` + 60 s while a command may run in it, then, once the command ended (or an install-cache answer was given), back to the idle window `CODE_INTERPRETER_KERNEL_IDLE_SECONDS` (`commands._release_to_idle`). Kept for the whole run lifetime after a 30 s run, a `backend-unit` container (1800 s timeout) held its Pool slot for 31 min; a few workspaces filled the `python-dev` Pool and every next create waited for capacity until the server's HTTP 504 (`K8S_POD_READY_TIMEOUT`, xtm-one #8549). Pool sizing itself is the deployment's (`dev-docs/opensandbox-pool-management.md`). Before the command: `remote.install_tool` + `remote.reconcile` with `IGNORED_PATTERNS` (what a command builds in the container, `node_modules/`, `.venv/`, `__pycache__/`, `.xtm/` ..., stays there between commands and never enters the manifest; a `dir/` pattern covers every path under it in the helper's `_ignored`, so a manifest file under an ignored directory, such as an earlier run's `.xtm/runs/<id>/` or a `.venv` package, is neither sent to the container nor reported as removed by `collect`); the command runs detached (next point) through the helper's `exec` action, its argv as JSON (no shell), in `<cwd>` with `SAFE_ENV` and the check's timeout, with no core files (`RLIMIT_CORE` 0 in `_exec`'s `preexec_fn`: an aborted process, a V8 heap exhaustion, would otherwise leave a dump the size of its memory under the workspace and the read-back would refuse the whole change set for the quota) and with `NODE_OPTIONS=--max-old-space-size` set to three quarters of the container's cgroup memory (`_memory_limit`, `_node_heap_env`) unless the command's `NODE_OPTIONS` already names a heap size (V8 sizes its heap from the host, so eslint or tsc died near 2 GB on a 4Gi pod), and with the Python user base's `bin` (`$PYTHONUSERBASE/bin`, else `$HOME/.local/bin`, i.e. `/tmp/.local/bin`) first on `PATH` (`_user_bin_env`): a detected `pip install ruff yamllint` check on an image whose site-packages is read-only falls back to a user install, and the next check `ruff check .` then failed `No such file or directory` (exit 127), where the CI runner finds the tool its job installed; after it: the report file read from the container and parsed (`checks.parse_junit` / `parse_sarif`, findings bounded by `MAX_FINDINGS`, the rest counted; a JUnit file with junk after its first document, a second write appended, is read from that first document and the headline says so, any other unreadable JUnit file keeps its raw text as the run's `failures.txt` and the answer points to it beside the runner's output, xtm-one #11523; the vitest checks `frontend-unit` and `frontend-bump-unit` run `--reporter=default` beside `--reporter=junit --outputFile.junit=...`, so each test's console output and the error behind a failure, a render error's stack included, reach stdout and stderr, which the JUnit reporter alone never wrote), `remote.collect` + `commit_scan` of what the command wrote under the workspace (a checkout whose own `.xtm-checkout.json` is among the removals was lost by the container, never removed by the command: `keep_vanished_checkouts` keeps it and the answer names it, #859), the whole stdout, stderr and a `run.json` saved under `.xtm/runs/<id>/` (`_save_run`), quota (`enforce_combined_sandbox_quota`, `increment_sandbox_usage`), a `sandbox_call` log with `usage_type="sandbox_command"`, an audit row `sandbox_run_command`.
- The result (`checks.format_result`) is bounded: status line, the report headline, the findings as `path:line: severity [rule] message`, a head and tail of stdout and stderr (`OUTPUT_HEAD` / `OUTPUT_TAIL`), the run directory. No free-text parsing: a `lines` check returns its output only. A declared or detected check that exits 0 keeps only the last lines of each stream (`checks.green_tail`, `GREEN_OUTPUT_CHARS`), where a runner prints its totals: pre-existing lint warnings and test progress stay in the run directory, a marker counts the lines left out. The built-in `script` check and an argv keep their output (it is the answer).
- Detached runs: the agent loop cancels a tool call at its per-tool deadline (`TOOL_EXECUTION_TIMEOUT_SECONDS`, 300 s), while a real `npm ci` or `pip install` takes longer; a command that held the HTTP call for its whole duration died with the call (`tool 'sandbox_run_command' timed out after 300s`). The command is now started DETACHED: `commands._start` writes its argv (`argv.json`) and the workspace baseline (`baseline.json`) under `remote_run_dir(run_id)` (`/tmp/.xtm/runs/<run_id>/`, outside the workspace) and launches the helper's `exec` action as a background command; the helper runs the argv in its own session (a timeout kills the whole process group), writes `stdout.txt`, `stderr.txt` and `pid`, then `exit.json` atomically last (its presence is the end). The call polls `exit.json` (0.5 s doubling to 5 s) within `wait_budget()`: the call's own deadline (`tool_events.current_tool_deadline`) less `FINISH_RESERVE_SECONDS` (45 s for the report, the read-back and the save), `COMMAND_WAIT_SECONDS` outside the loop. Not ended by then: the answer is `<check>: running for N s of its T s timeout (run_id ...)` with the tail of the output so far, and the run is recorded in `kernel_state["commands"][<image>]["run"]` (run_id, start, the resolved command, the cache key). `sandbox_run_command(checkout, run_id=...)` -> `commands.poll_run` finds it again from any replica, reconnects the container, rebuilds the baseline from `baseline.json` and waits again; at the end the report, the read-back (`collect` against the baseline), the run directory and the answer are exactly those of a command that ended within one call, and the run is cleared (a second poll is refused: "no command is running with run_id"). While a run holds a container, another command on the same image is refused with its run_id; a run past its timeout + `HARD_TIMEOUT_MARGIN` with no `exit.json` means the runner is gone: the container is discarded. Why detached and not a longer deadline: the 300 s ceiling is shared by every tool and capped by the run's wall clock; a polled run keeps each call bounded, survives a backend restart between calls (the state is in the container and the row), and lets the agent work in between. A run lost with its container (`api.connect` fails, or the container answers without `baseline.json`: a restart, a pod recycle) is rerun ONCE by the poll itself (`commands._rerun_lost`, not on `stop=true`): the stored record (`_command_record`, which keeps the check's `install` so a fresh container installs first; `_command_from_record` reads it, a record without `install` reads as none) starts again through `run_command`, and the answer opens with `(Run <old> of <check> was lost: <why>. It was started again once in a new container, as run <new>.)` followed by the rerun's own outcome (its end, or `running` with the new run_id). A poll of that old run_id afterwards finds no record and answers `lost` (`_not_running`): one rerun per lost run, never a loop.
- Restarts handled alike (#12045): when ANOTHER call meets the restart first and creates the new container (`_create_and_remember`), the run the replaced container held is kept under `kernel_state["lost_runs"][<run_id>]` (bounded to `_MAX_RERUNS`), so the later poll of that run_id reruns it once too (`poll_run`, the entry dropped first by `_forget_lost`) instead of answering a bare `lost`. A kernel start (`kernel._record_kernel`) keeps `jobs`, `reruns` and `lost_runs` with the other records. An install-first answered `running` (`_install_then`) records the check that waits for it on the run (`run["then"]`, `_attach_then`): the poll of the install's run_id runs that check once the install ended with exit 0, and a rerun of a lost install-first reruns the check with its install (`_lost_command`), so a new container never meets Yarn's missing node_modules state file. Calls of one round on one container (frontend-unit and frontend-types, node-types and node-lint-file) set it up one at a time: `run_command` holds a process-local claim per workspace and image key (`_CLAIMS`, `_Claim`) from its read of the held run to the record of its own run (upload, install probe, start), and releases it before any wait or nested call, so the second call reads the first's run and queues behind it instead of running a second install into the same node_modules (ENOENT, EEXIST in the link step); a call that cannot take the claim within its budget is answered busy. A second, different check on a container whose run is still going queues behind it within its own `wait_budget()` (a `poll_run` of the held run, then its own start, answered `(Queued behind <check>, run <id> ...)`); only a `background=true` call, or a held run still going at the end of the budget, is answered busy with the run_id.
- Every concurrent lost run reruns (#12188): a rerun that does not start at once (the new container still starting after the restart, the container busy with the concurrent check met first, a refused create) keeps the lost run under `kernel_state["lost_runs"]` with `rerun_attempts` + 1 (`_remember_lost`), so the next poll of that run_id tries the rerun again, at most `_MAX_RERUN_ATTEMPTS - 1` (5) times, instead of answering `lost`; a busy answer names the holding run and is never linked as the rerun. `.xtm-one/stores.py` calls `reset_leftovers` before it starts the stores: the store processes (executable under `/opt/stores`) whose arguments name an `xtm-stores-` run directory under the temp directory are ended (SIGTERM, then SIGKILL after 10 s, a zombie counted as ended) and those directories removed, so a `backend-integration` run cut by a restart never leaves the next one failing on its ports or its database; a lab's stores (data under the lab's own root) are never touched.
- A check lost after its install ran first reinstalls (#12302): when the install ran first in the old container (`_install_then`, or a backgrounded install whose `then` check `poll_run` starts), the check itself runs with no install of its own; `run_command(..., _rerun_install=install)` keeps that install in the check's run record only (`_command_record(rerun_install=...)`), so `_lost_command` reruns the check with its install probe and the new container is installed first instead of running the check with no dependencies.
- Durable jobs (#11484): a worker stop while a `sandbox_run_command` call waits leaves the command running in its container, but the resumed turn only holds the call it repeats, not the `run_id` the cut call never answered; the in-flight guard held that repeat back once, and the repeat after it ran the check again even when it had ended. Each call that starts a command now binds its job (`sandbox_workspace/jobs.py`, `jobs.bound`): `job_key` is a digest of the arguments that define the command (checkout, check, args, argv, cwd, affected; never background, and none for a `run_id`, `service_id` or listing call). `run_command` records the run it starts for the check the call asked for under that key in `kernel_state["jobs"]` (`jobs.record`; an install run first or a reaped run is not the job, a rerun or fallback of the same check replaces it; at most `MAX_JOBS` 64, oldest first out). The tool declares `landed_probe=jobs.landed`: a repeat whose job's run ended and was saved is answered with that saved result (`commands.saved_outcome`, the same text a poll of an ended run gives) in place of the repeat, one execution; a run still held by its container answers `False` and the repeat reattaches to it (the same check asked again is the held run, waited for, unless a file of its checkout changed after the run's `started_at`: `commands._edited_since_start`, #748, makes it another command, queued behind the held run and run on the tree as it is now); no job or a lost run answers `False` and the repeat runs. `_wait_and_finish` now clears the held run only after `_save_run` wrote `.xtm/runs/<id>/`: a worker lost in between leaves the run held (the next call collects it) instead of a run with no record and no saved result. `_save_run` keeps at most `commands.MAX_KEPT_RUNS` (100) run directories: the files of the oldest beyond it (age: a directory's newest mtime; `.xtm/runs/prepush/` is never counted) are removed in the same change set as the new run's files (`_stale_run_files`), so saved results never fill the workspace's file limit and a later check's own writes are never refused for it (a workspace had grown 924 run directories, 2,868 files). The installed tree lives in the container (`kernel_state["commands"]` keeps its id), so a resumed worker reuses it and an install of unchanged lockfiles is a cache hit; a container the sandbox server recycled still loses its run and tree, where `_rerun_lost` (#11189) reruns once. The background checkout rebase reuses the same ledger rather than a second mechanism.
- Background and Stop: `sandbox_run_command(..., background=true)` passes `background` to `commands.run_command`, whose `_wait_and_finish` then waits `BACKGROUND_FIRST_LINES_SECONDS` (1 s) instead of `wait_budget()`: the call answers `running` at once with the run_id and the first lines, and the turn goes on while the command runs (one command per image container, as for any detached run). `sandbox_run_command(checkout, run_id=..., stop=true)` -> `commands.poll_run(stop=True)` writes a `stop` file in the run directory; the helper's `exec` loop waits on the process in 0.25 s steps and, on seeing `stop`, kills the whole process group (`os.killpg`, SIGKILL) and writes `exit.json` with `stopped: true`; the poll waits at least `STOP_WAIT_SECONDS` (10 s) for it. The answer is a finished run (exit code, output so far, report, read-back of what it wrote, run directory) with the note `Stopped on request after N s, with every process it started`; `CommandOutcome.stopped` is set, the operation metric and the command stage are labelled `stopped`. `stop=true` without a run_id is refused; a stop for a run that already ended is answered like a poll of an ended run ("no command is running with run_id"). Gated like every command by `code_interpreter_command_allow_argv` for argv: only what the platform already lets run can be backgrounded or stopped.
- Install cache: an install check (`is_install`: a check named `install` or ending `-install`, the detected `<scope>:node-install`, `python-install`, `jvm-install`, ...) gets `install_cache_key`: sha256 of the image key, the directory, the argv and the manifest hashes of the lockfiles at the top of that directory (`LOCKFILES`: npm, yarn, pnpm, uv, poetry, Pipenv, `requirements*.txt`, `pyproject.toml`, Maven, Gradle, Cargo, dbt; no file is read, the manifest's sha256 is used); `None` without a lockfile. A successful install writes `/tmp/.xtm/cache/installs/<key>.json` in its container, where the dependencies stay (`node_modules/`, `.venv/` are `IGNORED_PATTERNS`, kept between commands). The same install on a reused container with the same key is answered `exit 0 (cached: ... installed by run <id> ... in N s)` without running; a lockfile or argv change runs it again. The record also lists the install state files present in the check's directory after the install (`INSTALL_STATE_FILES`: `node_modules/.yarn-state.yml`, `node_modules/.package-lock.json`, `node_modules/.modules.yaml`, `.yarn/install-state.gz`, `.venv/pyvenv.cfg`), read by the helper's `probe` action (`remote.probe_files`: the relative paths in `/tmp/.xtm/probe.json`, never on its command line; an absolute or `..` path is answered absent). A hit re-probes them: one gone (a crashed call, a re-materialized checkout, a recycled container) runs the install again and the answer adds `Not answered from the install cache: <path> (left by run <id>) is no longer in this container`; a probe that fails counts as gone; a record with no state list (or an install that writes nothing in its directory) is answered as before. A check that is not an install and fails in a directory with a Node lockfile (`NODE_LOCKFILES`) and none of `NODE_STATE_FILES` (the `node_modules/` state files of Yarn, npm and pnpm, or `.pnp.cjs`; not `.yarn/install-state.gz`, which Yarn 4 writes on the failed `yarn run` itself), or whose output carries Yarn's `Couldn't find the node_modules state file` (`YARN_NO_INSTALL_MESSAGE`), gets one more line: no installed dependencies in that directory in this container, run the checkout's install check first. Install first: `resolve` binds to every check that is not an install the install check of the same `cwd` and image key (`_sibling_install`, the first by name among `is_install_name`; `ResolvedCommand.install`), else the install of the nearest enclosing `cwd` on the same image key (`_encloses`, segment-aware: `packages` encloses `packages/a`, not `packagesx`; the checkout root encloses every directory), so a package check of a Yarn, npm or pnpm workspace (`packages/x:node-unit`) runs the root `node-install` that writes the workspace's `node_modules`, and `_needs_install` probes that root directory, unless the check declares `install_first = false` (`CheckSpec.install_first`, default true; `frontend-design-system-guards` opts out). `run_command` probes after the reconcile (`_needs_install`: a directory with a Node lockfile and none of `NODE_STATE_FILES`, or state files but no cache record for the current lockfiles' key) and, when it must, runs the install (`_install_then`: a cache hit, a miss and a lockfile change are the install's own cache path), audits it, then runs the check in the same call; the answer starts `<install> ran first (no installed dependencies in <dir> in this container): exit 0 in N s`. An install that fails answers `<check> did not run: its install check <install> ran first ... and failed` with the install's outcome; an install still running, busy or starting is answered as such with a line saying the check has not run yet. A directory without a Node lockfile, or a probe that fails, runs the check as asked. The cache lives as long as the workspace's container (`kernel_state["commands"][<image>]`, renewed per call): a new container installs once. A cache shared across containers (a volume per repository) needs an OpenSandbox volume the platform does not mount today.
- Creation, upload and size: the container is created first (`_container` -> `_create_opensandbox`), the workspace is sent after; a failure says its stage. **Create**: the OpenSandbox server answers HTTP 504 (`K8S_POD_READY_TIMEOUT`) when the pod is not Running with an IP within its `[kubernetes] sandbox_create_timeout_seconds` (60 s by default; the server's TOML, rendered by the deployment chart): a cold pod of a large image (dev, toolchain) once the Pool's warm pods are taken. `_create_opensandbox` retries a 504 once (`_CREATE_TIMEOUT_RETRIES`, jittered pause, identical network policy) and then raises `SandboxUnavailableError` with `stage create:`, the image key, the attempts, the seconds and the setting to raise; the workspace size plays no part at this stage. The workspace command container is created as its own task past the call (`_CREATES`), so it passes `retry_timeouts_for=CREATE_RETRY_WINDOW_SECONDS` (900 s): its 504 is retried with a doubling pause capped at `_CREATE_TIMEOUT_RETRY_DELAY_MAX_SECONDS` until that window, and a cold Pool ends in a container rather than an error (#8574). The `still starting` answer carries the pool state of the image key (`sandbox_pool_state`: pods running, creating, pulling the image, read from `SandboxManager.list_sandbox_infos`, fail-open), so a run can push to CI at once when nothing runs for the key; `get_platform_overview` shows the same counts for every key as `sandbox_pods_by_image_key` (administrator scope, `null` when the server was not read). **Upload**: `remote.reconcile` reads the blobs to send `remote.BLOB_READ_CONCURRENCY` (32) at a time, packs them into tars of at most `remote.UPLOAD_PART_BYTES` (32 MiB) of content each (`remote._upload_parts`, in order; a larger file is a part of its own; the removal list travels with the first part alone), writes and unpacks each part with its own `write_file` and helper call, and logs files, MB, parts and seconds; a fresh container that receives a whole checkout (140 MB and more after a rollout) no longer sends it in one write that fails whole: a failed part leaves the parts already unpacked, and the next call's listing sends only what is still missing; only what is missing or different in the container is sent, so a reused container receives the diff. What is sent is `commands.staged_entries`: a command whose directory is inside a checkout (a directory holding `.xtm-checkout.json`, the nearest one) gets that checkout and the files outside every checkout, never the other checkouts, except a checkout a relative path in its manifests names (`commands.linked_checkouts`: `pyproject.toml`, `package.json`, `requirements*.txt`, `setup.cfg` of its directory up to the checkout root, e.g. `pyoaev @ ../../client-python`), which is staged with it and named in the staging line; a command outside every checkout gets the whole workspace. The read-back compares the container to that same staged manifest, so the checkouts left out are never taken as removed. The archive and its removal list are written under per-call names (`remote._stage_files`: `stage-<token>-in.tar`, `-remove.json`, and `-pack.json`, `-out.tar` for the read-back), so two commands on one container never unpack each other's archive; each call drops its own files (helper `drop`), the hourly sweep takes what a cut call left. `remote._upload` passes the archive's size and sha256 to the helper's `unpack`, which refuses (exit 3) an archive that arrived short or different before it removes or extracts anything; a failed write, unpack or check is sent once more (`UPLOAD_ATTEMPTS` 2), then `UploadError` names the archive's MB and each attempt's cause. A failure there is reported as `stage upload` with its seconds and the staged size (`staged N MB: <checkout>/ and the files outside every checkout, of a M MB workspace`). The repeat-failure guard is unchanged.

- Deselected markers: a check whose argv deselects pytest markers with a plain `-m "not X"` (`backend-unit`: `-m "not integration"`; read by `affected.excluded_markers`, a `not X and not Y` expression included, any other expression read as none) gets every selected test file applying one of them (`pytest.mark.X`, `pytestmark = pytest.mark.X`) listed in `Selection.deselected`: pytest collects such a file and runs nothing of it, so the answer carries the line "Deselected by this check's -m: N selected test file(s) are marked X, which this check does not run: <files>" and names the check to run them with: each declared or detected check of the same directory whose argv selects the marker with a plain `-m X` (or `-m "X or Y"`; `affected.selected_markers`, a `python -m <module>` never read as a marker) is named by `affected.marker_runners` (`integration` -> `backend-integration`), and the generic "the check that selects that marker" stays only when none does (gap `affected-deselect-note-no-check-name`). The files stay in the run (a file may mix marked and unmarked tests); the line keeps a selected integration test from passing as covered (gap `affected-skips-integration-tests`, xtm-one #778 dropped from the queue).
- Wording-only changes: a changed Python file whose code tokens are equal on both sides (comments and docstrings aside, `affected.wording_words` over `tokenize`) names neither its definitions nor its module path; the words it replaced (a word diff of its comments and docstrings, the same length and common-name filters) select the tests that pin the former or new text, and the answer notes `N changed file(s) change wording only`. Any other string literal (a status value, a key, a regex, a message, an f-string) is code and keeps the definition and module selection, and a change whose replaced words are all filtered out keeps it too, so the selection is never empty for a changed file. A product rename in docstrings and comments of 17 modules selected 55 test files, about 60 minutes of run, before this rule (gap `affected-tests-selection-too-wide`).
- Ordering within a tool round: the agent loop runs the calls of one response under `asyncio.gather`, so a `sandbox_run_command` next to a `sandbox_edit_file` used to read the manifest before the edit committed and ran the old file. Every tool of `WORKSPACE_WRITE_TOOLS` (`builtin_tools/sandbox_workspace.py`: put, remove, edit, write, materialize, rebase, diff with `write_merge_to`) is registered through `_counted_write`, which holds `WorkspaceSession.writing()` (a synchronous counter, entered before the handler's first await) while it runs. `sandbox_run_command` (a new command, not a `run_id` poll, before the checks are resolved) and `sandbox_start_service` first await `WorkspaceSession.settled()`: a `SETTLE_GRACE_SECONDS` (0.05 s) sleep so the other calls of the round reach their handler, then a wait for no write in flight, bounded by `SETTLE_TIMEOUT_SECONDS` (60 s). The answer names a wait of 0.1 s or more, and a bound reached ("the command may not see them; run it again"). The counter is per session (one turn or one run), so another conversation's writes never hold a command. Tests: `tests/test_sandbox_round_ordering.py`.
- Writes of one tool round take turns (no lost update): a writing tool reads the files it changes, computes, then commits them whole, and `WorkspaceSession.commit` serializes only the commit. Two writes of one round on the same file (two `sandbox_replace_in_files`, a replace next to a `sandbox_edit_file`) each read the old content, both answered success, and the later commit dropped the earlier change. `_counted_write` now also holds `WorkspaceSession.write_turn()` (one `asyncio.Lock` per session, first in first out) around the handler, after `writing()` is entered: the writing tools of a round run one after another in the order the loop started them, each from what the previous one committed, and a waiting write still counts as in flight for `settled()`. The lock is not reentrant: no writing tool calls another registered writing tool (`materialize_repository`, `sandbox_checkout_diff` and `sandbox_checkout_rebase` call only integration reads through the composite). Readers never take it. The tool contracts are unchanged; a round of writes now costs the sum of their times instead of the longest. Tests: `test_writes_of_one_round_take_turns_in_issue_order_and_are_all_counted`, `test_a_failed_write_releases_the_turn` (`tests/test_sandbox_round_ordering.py`) and `test_two_writes_of_one_round_on_one_file_both_land` (`tests/test_sandbox_replace_in_files.py`).
- Read-your-writes for every reader of a round (#11714): `settled()` also runs before `sandbox_get_file`, `sandbox_list_files`, `WorkspaceIngestor.read_file` (every `workspace_path` / `from_workspace_path` argument) and `WorkspaceIngestor.checkout_changes` (`sandbox_checkout_status`, `sandbox_checkout_diff`, `create_github_commit(from_checkout=...)`), and before a `code_interpreter` call mounts the workspace. Two writers that were not counted are now: a `to_workspace_path` call (the dispatcher enters `WorkspaceIngestor.writing()` around the tool and its ingest, so a read next to `get_github_file(to_workspace_path=...)` finds the file) and a `code_interpreter` call that uses the workspace (`writing(run=True)`: waited for by every reader, not by another `code_interpreter` call, which waits with `settled(tools_only=True)` for the writing tools only, so two calls of one round still run side by side). A read made inside a writing tool's own task answers `settled()` at once (`_WRITING` context variable), so a writer that reads never waits for itself. Tests: `tests/test_sandbox_read_your_writes.py` (one case per reader, the dispatcher, and 100 rounds of edit plus three readers with 0 stale reads).
- `sandbox_list_files(glob=...)` expands `{a,b}` alternatives (#449): `manifest.matches_listing_filter` matches the file name (or the path under `path` when the glob holds a `/`) against each pattern `manifest.expand_braces` gives, nested groups included; a group with no comma or no closing brace is literal, and past `MAX_BRACE_EXPANSIONS` (64) patterns the glob is matched as written. `fnmatch` alone has no brace form, so `{architecture,overview}.md` used to list nothing.
- Resources per image key: `settings.sandbox_resources(key)` reads `SANDBOX_CPU` / `SANDBOX_RAM` as a bare value or a `key:value` list (`_per_key_value`, the `OPENSANDBOX_IMAGES` convention); every container creation goes through it (code interpreter and kernel: `python`; custom tools: `nodejs` and `python`; `sandbox_run_command`: the check's image key), never the raw fields.

- Install fallback (#10657): an install check may declare `fallback = { image, when, reason }` (`CheckSpec.fallback_image`, `fallback_when`, `fallback_reason`; refused on a check whose name does not end in `install`, without `image` or `when`, or with `image` equal to its own). `resolve` binds it on the install and on every check that runs that install first (`bind_fallback`, `fallback_configured` when `OPENSANDBOX_IMAGES` holds the image). The tool calls `run_with_fallback`: when the run ends non-zero with `when` in its output (not stopped, timed out, refused, busy or still running), the first failure is audited and kept in its run directory, and the same command, its install included, runs again on the fallback image in the same call; the answer opens with one line, `<install> failed on <image> (output in ...): <reason>. Ran <check> again on <fallback>, the fallback <install> declares.` An unconfigured fallback image gets that line naming it and no rerun. A run answered `running` first (`background=true`, or an install longer than the wait budget) falls back the same way when `poll_run` sees it end: the stored run record keeps the command's `fallback_*` fields (`_command_record`) and `_follow_fallback`, the tail `run_with_fallback` shares, reruns it on the fallback image in the poll call (never in background); before this a backgrounded `frontend-install` on a lock newer than `nodejs-dev` ended on a bare `YN0080` (`test_a_background_install_that_fails_as_its_fallback_declares_falls_back_when_its_poll_sees_the_end`). A fallback that installed is remembered in the workspace's `kernel_state["install_fallbacks"]` (kept across a kernel start), keyed by the install's cache key (image, directory, argv, lockfile hashes): every later check bound to that install (`frontend-build`, then `frontend-design-system-classes` reading its `dist`) runs on the fallback image at once, in the container that holds the install and the build, the answer opening `Ran <check> on <fallback>: <install> fell back there earlier in this workspace (...)`; a changed lockfile is a new key and tries the declared image first. The workspace helper's `list` stage (`remote._listing`) clears its output before the run and names an empty or missing output (its size, the exit code or none, the workspace file count, the stderr tail) instead of a bare `Expecting value` JSON decode. `backend/uv.lock` on `python-dev` is out of scope: python-dev declares no install check (its environment is baked and the backend checks run on it as is), so a `uv.lock` change shows as an import error in the check, not as an install failure.
- Which lock a check ran on (#11514): every ended answer of `run_with_fallback` and `poll_run` for an install, or a check that ran its install first, ends with one line from `lock_line`, `Lockfiles: <path> <sha256[:12]>, ... (dependencies from <image>).`: the lockfiles of the install's directory as the workspace manifest hashes them and the image the dependencies came from (the declared image on the fast or cached path, the fallback image after a fallback or a remembered one). - The toolchain images (`backend/sandbox/Dockerfile.sandbox.toolchain`, same script): the build environment of a stack for any repository, no lock baked. Image keys by convention: `toolchain-python` (Python 3.14 default and 3.12 at `/usr/local/bin/python3.12`, found by `uv python find 3.12` so `uv venv -p 3.12` needs no download; pip, uv, git; pytest and pytest-asyncio at the versions of `backend/uv.lock`, so a detected `python -m pytest` runs before the checkout's own install), `toolchain-node` (Node 24 default, Node 26 under `/opt/node26/bin`, npm, corepack's yarn and pnpm; `npm_config_nodedir=/usr/local` points node-gyp at the bundled headers so a native addon builds without nodejs.org, which the pods do not reach), `toolchain-jvm` (Temurin 21, Maven 3.9; a Gradle checkout runs its wrapper), `toolchain-rust` (stable, clippy, rustfmt; `CARGO_TARGET_DIR=/home/sandboxuser/.cache/cargo-target`, so a build never writes `target/` into the checkout, which the workspace would save back and a commit from the checkout would carry, and the container keeps it between commands), `toolchain-dbt` (dbt-core and dbt-postgres in a Python 3.12 environment). Each also carries Python 3.14 (the workspace helper's `python`), git and a C toolchain, and runs as `sandboxuser`. A checkout's dependencies are installed in the container at checkout time (`uv sync`, `yarn install`, `mvn dependency:go-offline`, `cargo fetch`, `dbt deps`), so these keys are configured only where `AGENTIC_CODING` is on and the pods reach the package registries or the registry proxy; which key and which install command a checkout gets is the stack detection's choice, not a declaration in the target repository. The hardening exception they rely on: `sandbox-image-hardening.md`, "Toolchain images". Their network comes from their Pool, not from the create call: the chart labels a toolchain Pool's pods `app.kubernetes.io/component: toolchain-sandbox`, the label the registry egress policy selects, while a direct create gets the server's own template (`component: sandbox`) and the namespace deny-all (no DNS). So a `toolchain-*` key is pool-bound (`_sandbox_selector.is_pool_bound`): its create keeps the `poolRef` when the Pool is starved (the toolchain Pools idle at `bufferMin: 0`, so every cold create read as starved) or times out, and never takes the #9503 direct fallback; before this every cold JVM, Rust and dbt check ran offline and could not resolve Maven Central, crates.io or the dbt hub (`test_sandbox_toolchain_pool_bound.py`).

## Services (`sandbox_start_service`, `[service.*]`)

- A checkout may also declare how it runs, in the same `.xtm-one/checks.toml`: one `[service.<name>]` table per service, `argv` (one command, no shell), `port` (the TCP port it listens on), `cwd`, `image` (an `OPENSANDBOX_IMAGES` key; `python` when absent), `ready_path` (an HTTP path answered below 500 once it is up; empty for a bare TCP check), `ready_log` (a one-line text, at most `checks.SERVICE_MAX_READY_LOG` characters, the service's output must also hold before it counts ready, within the same `timeout`: what it logs after its port answers, a seed and the URLs it prints, is then in the first `sandbox_service_logs` read; the xtm-one labs declare `"lab up: "`), `timeout` (seconds to readiness, at most `checks.SERVICE_MAX_TIMEOUT`), `lifetime` (seconds its container lives after the last call on it, at most `checks.SERVICE_MAX_LIFETIME`), `env` (a table of upper-case names), `depends_on` (services started first, in the same container: same image, distinct ports, no cycle) and `needs` (the repository paths, files or directories relative to the checkout root, the service reads; at most `checks.SERVICE_MAX_NEEDS`, inside the checkout, deduplicated). `checks.load_services` parses them (a file with checks only declares no service), `checks.service_chain` orders a service after what it depends on.
- The same file may declare the repository's **pull request title rule**: a `[pull_request]` table with `title_pattern` (a Python regular expression, at most `pr_title.MAX_PATTERN_CHARS`), `title_rule` (how to say it; the pattern when absent) and `title_example`. `create_github_pr` and `update_github_pr` (when a title is given) read the file raw on the target branch (`base`; the default branch when an update names none) through `integrations/providers/github/pr_title.py` and refuse a title that does not match before any write, naming the rule, the example and the file. No file, no table or no `title_pattern` (a pull request title only): the rule is read from the repository's workflows (`pr_title.workflow_title_rules`): the files of `.github/workflows` whose name matches `title|convention` (at most `MAX_WORKFLOW_FILES`, each under `MAX_WORKFLOW_BYTES`), each step that either uses an action of `KNOWN_TITLE_ACTIONS` (by its directory name, with its `exempt` text such as `(deps)`) or runs a script naming `pull_request.title` that tests a pattern variable with `=~` or `grep -P` (quoted variables expanded in order, the rule and example taken from its `echo` lines). Steps with no `if:` all apply; steps with an `if:` are alternatives, a title matching a later one passes with a note naming the condition. Workflow folder unreadable: silent and unchecked; no check found: `Title not checked: ... no title check was found in its workflows`; a parse error never blocks (`tests/test_github_pr_title_workflows.py`). An `[issue]` title is never read from workflows. A malformed table never blocks: the write goes on and its result carries `Title not checked: <why>`. This repository declares the pattern of `.github/workflows/pr-title-check.yml`; `tests/test_github_pr_title.py` fails when the two drift.
- The same file may declare the repository's **issue title rule** (`providers/github/pr_title.py`, `ISSUE`): an `[issue]` table with the same three keys. `create_github_issue` and `update_github_issue` (when a title is given) read it raw on the default branch and refuse a non-matching title before any write, naming `[issue]`, the rule and the example; the `[pull_request]` table never applies to an issue. No table, no file, an unreadable file: unchanged. A malformed table rides along as `Title not checked: <why>`, never a refusal. xtm-one declares the pull request form without the trailing `(#N)` (`tests/test_github_pr_title.py` keeps it so).
- **Closing keywords aimed at a pull request** (`providers/github/closing_refs.py`): GitHub closes the target of `close|fix|resolve` (and their -s / -d forms, an optional colon) followed by `#N`, `owner/repo#N` or an issue / pull URL when the PR carrying it merges; aimed at another pull request, that silently closes it. `create_github_pr` (title, body), `update_github_pr` (title, body when given) and `merge_github_pr` (the PR's title and body read first, plus `commit_title` / `commit_message`) refuse such a reference with nothing written, naming each one. `#N` and `owner/repo#N` are resolved through `GET /repos/{owner}/{repo}/issues/{n}` (a `pull_request` key means a PR; at most `closing_refs.MAX_REFS` reads per write); a `/pull/N` URL is refused without a read and an `/issues/N` URL is never read. An issue reference, or one that cannot be read, goes on as before. `merge_github_pr` also reads the PR's commits (`GET /repos/{owner}/{repo}/pulls/{n}/commits`, one page of `closing_refs.MAX_COMMITS`) whenever their messages reach the base branch: a squash without `commit_message` (GitHub builds the default message from them), a merge commit or a rebase; each commit message carrying a closing keyword is checked under the same `MAX_REFS` cap and a refusal names `commit <sha12>`. A squash with an explicit `commit_message` reads no commit; an unreadable commit list never blocks.
- **Review-loop verdict before ready or merge** (`providers/github/review_loop.py`): an agent review loop posts its verdict as a PR comment whose first line reads `UX-LOOP round=N verdict=APPROVE|CHANGES_REQUESTED ...`. `merge_github_pr` and `manage_github_pr` (`ready_for_review`, `enable_automerge`) read the newest 50 comments before any write and refuse when the newest marker is not `APPROVE`, naming the round, the verdict, the comment link and its time; a newer `verdict=APPROVE` comment releases it. No marker, or a comment list that cannot be read, never blocks. A broad "merge everything" instruction therefore never lands a pull request whose reviewer asked for changes (#11351).
- **Assignees in the same call** (`providers/github/pulls.py`, `_assign_pull_request`): `create_github_pr` takes an optional `assignees` list (logins). Right after the pull request is created they are added with `POST /repos/{owner}/{repo}/issues/{number}/assignees`, and the result carries one more line, `Assignees: <logins GitHub answered>`, naming every requested login GitHub dropped (no access to the repository) as `not assigned`. A failed assignment is reported on that line (`Not assigned (...): <error>`) and never undoes or fails the creation; no assignees, no extra request.
- **Open pull requests that overlap** (`providers/github/pr_overlap.py`, #10353): right after GitHub creates the pull request, `create_github_pr` lists the open pull requests of the repository (`GET /repos/{owner}/{repo}/pulls?state=open`, one page of `pr_overlap.MAX_OPEN`, most recently updated first), keeps those of the same author (at most `pr_overlap.MAX_PEERS`), and compares their files (`GET .../pulls/{n}/files`, one page each) and their issue references (`close|fix|resolve|refs|part of #N` in the title or body, and a trailing `(#N)` in the title) with the new one. Each peer that shares a file or an issue is named on a `Warning:` block of the result with the shared issues and up to `pr_overlap.MAX_NAMED_FILES` shared files. It is never a refusal: the pull request exists, the caller closes the duplicate or says why both are needed. A read that fails adds nothing and never fails the creation.
- **Full CI on the head before a merge** (`providers/github/full_ci_gate.py`, #11985): the same file may declare `[merge] full_ci_workflows = ["ci.yml"]` (at most `full_ci_gate.MAX_WORKFLOWS` workflow file names), for a repository whose pull request CI skips its suites. `merge_github_pr` reads it raw on the base branch after the closing-keyword and review-loop guards and, for each workflow, lists its `workflow_dispatch` runs on the PR head SHA (`GET .../actions/workflows/{wf}/runs?head_sha=&event=workflow_dispatch`, newest wins). None on that SHA (a green on an older head never counts): it dispatches the workflow on the head branch (same-repository heads only) and answers NOT merged with the run to follow; queued or running: NOT merged, run named; completed and not successful: NOT merged, run and conclusion named. All green: the PUT is pinned with `sha` to that head, so a push in between is refused by GitHub, and the merged answer ends with `Full CI on head <sha12>: <wf> run <id> (<url>), green.` No file, no table, or an unreadable file: no gate. A malformed table rides along as `Full CI gate not checked: <why>`, never a refusal. xtm-one declares `ci.yml`, whose manual run runs every job; the PR-time path filters stay as they are (`tests/test_github_full_ci_gate.py`).
  - **A red that is the base's own** (`full_ci_gate.base_red_verdict`, `services/full_ci_parking.py`, #12069): on a red full run, the gate lists the failed jobs of the head's run and of the newest completed runs of the same workflow on the base branch (`push`, `workflow_dispatch`, `schedule` events, `full_ci_gate.BASE_RUNS`). The newest base run red on one of the same jobs: the refusal says "red on <base> too" and `merge_github_pr` parks the pull request (Redis hash `full_ci:parked:<provider>:<repo>:<base>:<workflow>`, field the PR number, with its head SHA and the person the run acts for, `PARK_TTL_SECONDS` two days). The base already green again after such a red: the refusal says to update the branch and rerun, nothing is parked. A signed `workflow_run` completed `success` on the base branch for that workflow, with no pull request (`pr_events` sets `extra.base_run` and `extra.workflow_file`), makes the webhook receiver start `full_ci_parking.on_base_green` in the background: every parked pull request (at most `MAX_REDISPATCH`) goes to the provider's `FullCiRedispatcher` (`integrations/full_ci_redispatch.py`; GitHub: `full_ci_gate.redispatch`) with the parking person's token, which leaves a closed pull request or a moved head alone, runs `update-branch` (pinned to the parked head), waits for the new head, and dispatches the workflow on the head branch.
- **Full CI started at push time** (`providers/github/full_ci_gate.py`, `start_on_push`, #12067): the full run the gate requires is started when the head moves, not at the first merge call, so it executes in parallel with the pull_request checks. After a commit lands on a branch (`create_github_commit`, `create_or_update_github_file`, `delete_github_file`, the shared `name_pushed_pull_request` step in `contents.py`) and after `create_github_pr` opens a pull request, the tool reads the branch's open pull request and, when its base declares `[merge] full_ci_workflows` and the head is in the same repository, dispatches each gated workflow that has no `workflow_dispatch` run on the new head yet. The answer carries one line naming what was dispatched (or why a dispatch failed); a base with no gate, a fork head or a closed pull request adds nothing. The step never fails the write. A newer push cancels the stale full run through the workflow's own concurrency group (a `workflow_dispatch` run groups by ref in `ci.yml`). `merge_github_pr` then finds the run running or green and merges at the first moment both CIs are green on the head.
- **A merge answer of unknown outcome** (`providers/github/pulls.py`): when `merge_github_pr`'s `PUT /pulls/{n}/merge` answers a gateway 502/503/504, no response, or a 405/409 saying a merge is already in progress, GitHub may still land the merge. The tool reads the PR back; merged means it answers merged with the merge commit and puts nothing else. Otherwise it retries after `_MERGE_RETRY_DELAYS` (5 s, then 15 s: at most three PUTs), every retry pinned with `sha` to the head read before the first attempt, so a push in between gets GitHub's 409 instead of an unseen merge. A definite refusal (405 not mergeable or conflicting, 409 head modified, 422) is never retried; the last answer names the attempts and the state.
- **A draft toggle of unknown outcome** (`providers/github/pulls.py`, `_toggle_draft`): `manage_github_pr` `ready_for_review` / `convert_to_draft` is a GraphQL mutation, which `gh_graphql` never retries. When it answers GitHub's internal "Something went wrong" GraphQL error, a gateway 5xx, a timeout, a transport failure or an empty body (`_draft_outcome_unknown`), the tool reads the PR's `draft` flag back over REST: already in the target state means it answers applied and sends nothing else; otherwise it sends the mutation again after `_DRAFT_RETRY_DELAYS` (5 s, then 15 s: at most three mutations). A definite refusal (permission, not found, validation, rate limit) is answered as it is, never retried; the last answer names the attempts and the state read back.
- **A merge refused because the base moved** (`providers/github/pulls.py`): a 405 "Base branch was modified" means the base branch moved seconds before the PUT and GitHub is recomputing the PR's mergeability (`mergeable` null, `mergeable_state` unknown). The tool reads the PR after each pause of `_BASE_MODIFIED_POLL_DELAYS` (3, 5, 7, 15 s: about 30 s) until the state is computed. Merged meanwhile: answered merged. Head moved: stopped, nothing put. `clean`, `blocked` or `has_hooks` (`_BASE_MODIFIED_RETRY_STATES`): one more PUT pinned with `sha` to the head read before the first attempt. `behind` or `dirty`: the answer points at `manage_github_pr` update_branch. Still `unknown`, or `unstable`: NOT merged, with the state named and no branch update suggested, since a clean PR needs none (a branch update costs a whole CI round).
- **A merge queue entry that will not merge** (`providers/github/merge_refusals.py`, `_stuck_entry`, #409): on a base protected by a merge queue, `merge_github_pr` enqueues the PR (`enqueuePullRequest`) or reads it already queued. A merge queue applies no review bypass, so an entry whose review decision reads `REVIEW_REQUIRED` or `CHANGES_REQUESTED`, or whose entry state reads `UNMERGEABLE`, sits in the queue without merging: the answer is then `Error: ... is in the merge queue but will NOT merge as it stands`, with the cause (the missing approval, or the base's rules and checks to read) and the position, never "the queue merges it".
- **A merge answered as a receipt** (`providers/github/pulls.py`, `_receipt`): every merged answer of `merge_github_pr` (direct, retried, or read back after an unknown outcome) ends with the merge commit's full SHA, its signature verdict read from `GET /commits/{sha}` (`signed (<reason>)` or `NOT verified (<reason>)`) and its committer date, so a caller needs no `get_github_pr` + `get_github_commit` read-back. A failed commit read says `signature not read`; a merge answer without a SHA points at `get_github_pr`. Nothing is guessed.
- `services.resolve` binds `sandbox_start_service(checkout, service)` to the workspace. Before any container, it checks the `needs` of the service and of its `depends_on` chain against the workspace manifest (`services._missing_needs`: with the checkout's `.xtm-checkout.json`, a need is held when the record's `sub_paths` cover it, the whole tree when none, or the record lists it as a file, so the companion files a narrow checkout keeps for check detection, such as `frontend/scripts/*.mjs`, never make `frontend` look held; without a record, when the workspace holds it as a file or a file below it): a narrow checkout (`materialize_repository` with `sub_paths`) missing one is refused as `start_service refused`, naming each missing path and the `materialize_repository(path=..., add_paths=[...])` call that grows the checkout. This repository's `[service.lab]` needs `.xtm-one/lab`, `backend` and `frontend`. Then `services.start_service` creates a container of the service's image (`_create_opensandbox`, `usage_type="sandbox_command"`, counted against the sandbox quota like a check, the operator's egress allow-list, `settings.sandbox_resources(image)`), copies the workspace in (`remote.install_tool` + `remote.reconcile`, `commands.IGNORED_PATTERNS`), starts each service of the chain as a background command (`RunCommandOpts(background=True)`, output appended to `/tmp/.xtm/services/<name>.log`) and probes its port from inside the container until it answers or its `timeout` passes. The port is resolved with `Sandbox.get_endpoint(port)`: with `OPENSANDBOX_USE_SERVER_PROXY` the server answers its own proxy route (`/sandboxes/<id>/proxy/<port>`). The headers the server asks for on that route (its API key) are never returned to the agent.
- The container is kept per workspace and per `checkout:service` (`kernel_state["services"]`: sandbox id, port, services, lifetime, preview URL, readiness time), found again by id from any replica. A second start of a service that still answers returns it; one that does not is discarded and started again. `sandbox_service_status` and `sandbox_service_logs` renew its lifetime; `sandbox_stop_service` kills it. `sandbox_service_logs` answers the last `lines` lines per service (`services.DEFAULT_LOG_LINES`, at most `services.MAX_LOG_LINES`, cut at `services.MAX_LOG_CHARS`); with `pattern` (a Python regular expression searched per line, `ignore_case` optional, at most `services.MAX_LOG_PATTERN_CHARS` characters) it scans the newest `services.MAX_LOG_SCAN_LINES` lines and keeps the last `lines` matching ones, its heading naming how many matched out of how many were scanned (`services.log_section`, shared by the OpenSandbox and the lab paths). With or without `pattern`, lines that repeat once their times are masked (ISO dates and times, clock times, epoch stamps of 10 digits or more; any other digit keeps lines apart) are shown once at their newest place followed by `(xN)`, the heading naming how many were folded (`services.fold_repeats`), and each line keeps at most `services.MAX_LOG_LINE_CHARS` characters, the rest counted as `[+N chars]` (`services.cut_line`), so a recurring one-line JSON stack trace cannot fill the answer; an invalid pattern is refused with the `re` error before any read. Nothing else keeps it alive: a service left running ends at its lifetime, which bounds a run that forgot to stop it.
- The preview URL is the server proxy route on the configured origin, `<OPENSANDBOX_PROTOCOL>://<OPENSANDBOX_DOMAIN>/sandboxes/<id>/proxy/<port>/` (`services.preview_url`, once `get_endpoint` has resolved the port), never the pod address an endpoint names, which the platform's browser cannot reach.
- Reachability (`sandbox_workspace/preview.py`): that origin is on the operator's network, which the outbound URL policy refuses, and its proxy asks for the server's API key. A start registers the `(sandbox id, port)` pair in Redis (`sandbox_preview:<id>:<port>`, for the service's lifetime; renewed by status and logs, deleted by stop). `preview.allowed(url)` admits a URL only on the configured origin, under the proxy route of a registered pair, with no userinfo and no encoded dot, slash or backslash in its path; fails closed without Redis; a positive answer is cached 5 s in the process. The browser tool's URL check (`_outbound_or_preview`) and its route filter admit such a URL and add `preview.request_headers()` (the server's key) to every request to it; `web_fetch` reads it through `preview.fetch` (the key added, every redirect hop held to `allowed`, never cached). Every other URL, the server's lifecycle API, another sandbox and another port of the same sandbox stay under the outbound policy. No `browser_private_targets` exemption is involved and no agent ever sees the key.
- Refusal reasons (`preview.admission(url)`, #9697): the same check answers `admitted`, `not admitted` (the registration is gone: the service stopped, or a lab restarted on another address), `unreadable` (Redis could not be read) or `not a preview`; `allowed` is `admission == admitted`, unchanged. When the outbound policy also refuses a URL shaped as a preview, the browser tool raises `PreviewRefusedError` with that reason instead of the generic private-address error, so a navigate answers why, and a resumed session's reopen (`_reopen_resumed_page`) reads an unreadable admission once more after one second and says in its notice whether a navigate can work. Nothing else private is admitted.
- With `AGENTIC_CODING` on and `AGENTIC_LABS_NAMESPACE` set (`labs.labs_enabled()`), a start is a Kubernetes lab pod instead (`labs.start_lab`, no quota checked or counted), and status, logs and stop reach it by its pod name: `agentic-labs.md`. A lab start waits for readiness for `labs.ANSWER_SECONDS` (180 s, below the agent loop's 300 s per-tool timeout) after the pod runs and holds the checkout; past it, with no service ended, it answers `starting` (`ServiceOutcome.starting`, metric outcome `starting`) with the service_id, the preview URL and each service's state (`labs.service_states`), so a lab whose declared readiness outlives a tool call (an OpenCTI lab: 900 s) is never lost with its id. `background=true` answers `starting` as soon as the checkout is in. The record carries `files` once the checkout is copied: a second start of the same declaration whose pod is live, nothing ended, its window (`agentic_labs_start_seconds` plus the chain's timeouts from `started_at`) not over and no `timed_out` mark, follows that pod (`_await_ready`, note `already starting`) instead of replacing it. A start that waited out the whole window marks the record `timed_out`, and the next start replaces it. `lab_status` names each service: `ready`, `starting` or `exited with code N`.
- Offered with `sandbox_run_command` (`commands_offered()`: `CUSTOM_TOOL_SANDBOX=opensandbox`), or alone when the labs are on. Each start and stop is audited (`sandbox_service`). Results are bounded: a log read is at most `services.MAX_LOG_LINES` lines and `services.MAX_LOG_CHARS` characters per service.

## Clean-up

`gc.sweep` (the `sandbox_workspace_sweep` adapter's periodic hook: each process asks every `gc.ATTEMPT_INTERVAL_SECONDS` (300 s); `gc.take_lease` answers yes once per `SWEEP_INTERVAL_SECONDS` for the install through the `sandbox_workspace:gc:swept` marker a finished sweep sets, and a `_LEASE_SECONDS` (600 s) lease renewed after every deletion keeps one sweep at a time, so a sweep cut by a rollout is resumed by another worker within minutes; fail-open): archived / deleted conversations, deleted runs, ended runs (a status in `TERMINAL_RUN_STATUSES`, never left; reason `run_ended`), live runs idle past `CODE_INTERPRETER_RUN_WORKSPACE_IDLE_TTL_HOURS` (24 h; a run in `awaiting_human` keeps the conversation TTL), anything idle past `CODE_INTERPRETER_WORKSPACE_IDLE_TTL_HOURS`, then objects under a prefix no row names. Each pass takes `SWEEP_BATCH` per reason, up to `SWEEP_PASSES` passes a sweep, so a backlog drains over a few hours; a workspace's objects go through `file_storage.delete_many` (S3 DeleteObjects, `DELETE_BATCH` 1,000 keys a request, one delete per key only on a store without the bulk API), never one request per object. The chat archive and delete routes call `gc.collect_conversations_soon` after their commit; a run's terminal ending (`assignment_engine._publish_run_ended`, after its commit) calls `gc.collect_runs_soon`, which reads the status again and removes nothing for a run not terminal. What a sweep or a collect freed (workspaces and bytes per reason) is logged and summed in Redis (`sandbox_workspace:gc:freed`, after every pass of a sweep and every collect, so a cut sweep is still counted) and a finished sweep is recorded under `sandbox_workspace:gc:last_sweep` (the sweep only, never a collect); `get_platform_overview` returns it under `sandbox_workspaces.freed` with the live footprint (count, bytes, files, `by_holder`: conversations / live_runs / ended_runs / deleted_runs, `top_owners` for an administrator). Each deletion is a `log_system_audit` row (`system:sandbox_workspace_gc`).

Stale checkouts at the file limit (`eviction.py`, pure, #9993): when `materialize_repository` is refused by `plan_commit` (`QuotaExceededError`), `_evict_stale_checkouts` reads every other checkout root of the workspace (a directory holding `.xtm-checkout.json`; the destination being written is never one), counts per root its files, size and local changes (`checkout.changes_since`, plus any file outside the recorded `sub_paths` unless it is still byte for byte what the record's out-of-scope baseline holds (a leftover of an earlier, wider tree, #341), the `.xtm/runs/` outputs and bytecode caches left out, and an untracked file the checkout's own `.gitignore` files exclude left out too, read as `sandbox_checkout_status` reads them (`_gitignore_of`, `footprints(ignores=...)`, #1334: a build output in an ended run's checkout no longer keeps it), then asks the provider's `repository_compare` tool whether each clean root's recorded ref still exists (`compare_github_commits(ref, ref)`; `status: ref_not_found` = gone; at most `MAX_LISTED` 10 reads; no ref or a SHA ref = pinned, kept). The clean roots whose ref is gone (a branch deleted at its merge) are removed in the SAME change set as the new tree (`put_tree(remove=...)`), audited as `workspace_remove` and named in the answer ("Evicted to stay under the file limit"); a root with a local change is never removed. When nothing may go, or the retry is still over a limit, the refusal adds `eviction.refusal_hint`: each root by files, size, `repo@ref`, ref state and local state, the largest first, and the exact `sandbox_remove_files(paths=[...])` call for the clean ones, then names `prune_clean_checkouts=true`. The `add_paths` grow (`_grow_checkout`, #10125) runs the same retry: the grown checkout is the excluded destination, its edits are never touched, and the answer says "Nothing of this checkout was removed" with the evicted roots. `sandbox_checkout_rebase` (`_rebase_now`, #645) runs the same retry on its final change set: the rebased checkout is the excluded destination, the evicted roots join the rebase's own removals in one change set, the answer ends with the evicted line, and a refusal (no `prune_clean_checkouts` on the rebase) leaves every file and the old record as they were. `prune_clean_checkouts=true` (explicit, default false; `eviction.chosen(prune=True)`) widens the choice, only when a write is over a limit, to every clean root whatever its ref (a branch merged by squash whose branch still exists): no provider read is made, a root with a local change or a stray file still never goes, and the audit entry carries `prune: true`. Checkouts carry their run (#11511): `build_record(run_id=...)` writes the assignment run that wrote the tree into the record (`run_id`, absent in a conversation workspace and on older records; kept by `carried`, set again by an `add_paths` grow). At the limit, `_evict_stale_checkouts` reads the runs the other roots name in one query (`_ended_runs`: `TERMINAL_RUN_STATUSES`, or the run gone; a failed read ends nothing) and marks them `RUN_ENDED`; a root of the calling run is `RUN_LIVE` and never stale. A clean root of an ended run, or one whose record is older than `eviction.IDLE_SECONDS` (24 h, the TTL for a run-less workspace), is evictable whatever its ref, without a provider read; the answer and the refusal name each root's run (`run <id8> ended`, `run <id8> (this run)`) or its idle age, and the audit entry carries `runs` and `reasons`.
