# Agent accounts

The root `AGENTS.md` keeps one line per entity; this file holds the contract of agent accounts. Add detail here, never there.

An **agent account** is an agent operating a real user account of a messaging platform - or a mailbox - through that account's delegated OAuth integration - not a bot. Two modes, one engine:

- `on_behalf` (delegate): the account is a person's; the agent answers for them.
- `ai_user`: the account is a dedicated service account that IS the agent (an AI colleague everyone knows is an AI).

The mode only chooses the preset (`rules.preset()`) and the wording of the account brief; every behaviour comes from the settings and the rules.

## Rules (the engine's contract)

An account holds an ordered list of rules (at most `MAX_RULES`); **the first enabled rule whose scope and trigger match decides**. Scope: `conversation_types` (empty = all), `conversations` (ids picked from the provider; empty = any), who may ask - `senders` (match by id or any of the sender's addresses, `AccountEvent.sender_addresses`, case-insensitive; a target `@example.com` names every address of that exact domain, never a subdomain, `_matches_sender`) or `groups` (XTM One group ids, matched against `EventState.sender_group_ids`), either one; neither = anyone - and `exclude_senders` (domains too). Trigger: `mention` (the message mentions the account, or is a direct message, or follows a thread the agent answered in when `continue_threads`) or `any`. A rule whose scope matches but whose trigger does not lets the next rule decide. `action: ignore` stops there.

A matching `respond` rule yields a `Decision` carrying `must_reply` (`reply: always` and not a thread continuation; `decide` lets the agent answer `[NO_RESPONSE]`), and the effective `response_mode`, `ai_label`, `grace_period_seconds` and `instructions` (the account's, then the rule's). After the match: `owner_takeover` when the account's human wrote in the conversation within `owner_takeover_minutes`, `rate_limited` past `max_replies_per_hour` (replies in this conversation), `account_rate_limited` past `max_turns_per_hour` (`EventState.turns_last_hour`: agent turns of the whole account, every conversation together, 0 = no limit; a mailbox starts a conversation with each new email, so only this one bounds a sender writing new emails). Before the rules: disabled account, no agent, the account's own message, then `no_matching_rule` when no enabled rule reaches the conversation (`_conversation_in_scope`: its type and its `conversations`, whoever wrote - so a message in a channel nobody follows reads "No rule covers it", never "an app wrote it"), an application author, a message another agent account posted (`agent_author`, `EventState.agent_post`), an empty message, outside `active_hours`. Every reason is in `rules.REASONS` and labelled by the frontend's `DECISION_REASON_LABELS`.

Never re-spell any of this outside `rules.py`: the simulator (`POST /simulate`), the pipeline and the tests all call `evaluate()`.

Every account write normalizes the rules against the account's provider (`normalize_rules(raw, capabilities=provider.capabilities)` in `management.apply_settings` and `management.simulate`: create, update and `/simulate`, from the API and the agent tools alike): a conversation type the provider does not declare (`capabilities.direct` / `group` / `channel`), or a named conversation on a provider without `capabilities.conversations` or of a type it lacks, is refused (400) - stored, it would never match. An empty `conversation_types` then means the provider's own types (`provider_conversation_types()`). `/simulate` refuses a `provider` the platform does not have (422, `SimulateRequest`) instead of reading it as a chat provider. The editor sends its rules through `rulesForProvider()`, which drops a type the provider lacks from a rule that also names one of its own (a rule saved before the check).

`preset(mode, kind)` is where an account starts: a provider's `kind` (`chat`, `mailbox`) picks the rules. A mailbox answers the emails sent to it alone (`direct`, `trigger: any`) and those with it in `To` (`group`, `trigger: mention`), the agent deciding (`reply: decide`); `Cc` alone is for its information. The catalog serves each provider's presets (`ProviderCatalogItem.presets`).

## The pipeline

1. A provider event reaches `process_event()` (a notification, a poll, the end of a grace period). Dedup by conversation and message id (`state.first_delivery`): a platform may number messages per conversation (Teams chat ids are millisecond timestamps), so every per-message key in `state.py` carries the conversation.
2. The account's own message: an agent-sent echo is ignored; otherwise the human is writing, so the takeover window starts. Nothing else.
3. `decide()` = `evaluate()` with the Redis conversation state and, when an enabled rule names groups (`rules.rule_group_names`), the sender's XTM One groups: `sender_directory()` finds the active user whose email is one of the sender's addresses (the provider reports them from its directory - Teams: `mail` and `userPrincipalName`, which may differ - the first that names a user wins), read on every message so a removal applies at once. The decision then carries `sender` (`SenderDirectory.explain`: `known`, `emails`, and the rule-named groups the user is in, with the names the rules hold - never the user's other memberships), shown in the decision log and the tester so an owner sees why a group rule did or did not match. Not answering: the decision is recorded (`activity.record_decision`) and that is all.
4. The background gate (`agentic_gate.agentic_refusal`) - refused: recorded as `ai_unavailable`, nothing runs.
5. Grace period: the event is parked in the `agent_account:pending` sorted set and a timer (`loop.call_later`, holding no processing slot) re-runs `process_event(after_grace=True)`. The scheduler sweep runs a parked message whose process died (`state.overdue`, `PENDING_STALE_SECONDS` late). After the grace: the decision is taken again on fresh state, and a message the account wrote in the thread since (not an agent-sent echo) drops it (`owner_replied`).
5bis. One turn per conversation (`services/agent_accounts/turns.py`): on a chat provider (every provider whose `capabilities.triage` is false: WhatsApp, Teams, Slack), the message takes the conversation (`turns.take`, a Redis lock on account and conversation, `TURN_TTL_SECONDS`) and is answered after `settings.chat_event_coalesce_window_seconds`, outside the request's session (`pipeline.hold_turns`). A message that finds a turn in flight is queued (`turns.enqueue`, outcome `queued`, group `waiting`) and never answered on its own: the holder drains the queue and answers the queued messages as ONE next turn on the latest of them (the others `coalesced`, group `answered`), decided again on fresh state; the turn replays the platform conversation, so it reads every queued message and the reply before. "Latest" is by writing time (`created_at`), not by arrival: a grace timer, a poll batch or a second sender can deliver a burst out of order. The absorbed messages are passed to `conversation.build_turn(absorbed=...)`, which puts each in the user message even when the provider's context left it out, and the brief says `N messages merged` (`conversation.merged_note`); the turn's context carries `coalesced_count` and `coalesced_message_ids`, recorded on its trace metadata, and every message of the turn gets the trace id in `agent_account_decisions.trace_id` (`activity.record_turn_trace`, from `run_agent_chat(trace_out=...)`), shown as `trace_id` by the activity API and as "turn trace" by the agent's activity tool. The release re-checks the queue, and an arrival re-tries the take after queueing, so a queued message always has a turn coming. A queue a dead process left (`turns.orphaned`: indexed in `agent_account:turn_queues`, quiet for `ORPHAN_AFTER_SECONDS`, its lock expired) is handed to a new turn by the maintenance pass (`listening.resume_orphaned_turn`). Without Redis every message is its own turn, as before. A mailbox answers each email on its own.
5ter. One turn per sender of the agent, across its accounts (`services/agent_accounts/sender_turns.py`): `pipeline._answer` logs every inbound message (`sender_turns.note`, direction `in`, absorbed ones included) and runs the turn inside `sender_turns.hold(agent_id, account_id, event, label=provider.label)`, a Redis lock keyed by the agent and the sender's primary address lower-cased (`sender_key`, the provider's directory address: a chat message and a forwarded email of one person share it), refreshed every `POLL_SECONDS` while the turn runs, `LOCK_TTL_SECONDS` after a dead process. A message whose sender holds a turn on ANOTHER conversation of the agent (any of its accounts) is pushed to that turn's steering inbox (`sender_turns._offer`), which a bridge moves into the running loop's `steering_queue` (`run_agent_chat(steering_queue=sender_turns.current_queue())`): the turn in flight reads it at its next iteration, before any further tool call, a send included. The message's own turn then waits for the sender (`WAIT_SECONDS` at most, the request's session committed first through `before_wait`, holding no slot of the platform) and runs after it; past the bound it runs unserialized, logged. Every turn's user message carries what the same sender wrote to the agent, and what the agent answered (`note(direction="out")` after the reply's record), on its other conversations within `RECENT_WINDOW_SECONDS` (`recent_elsewhere`, `with_recent`): a turn resumed after a restart reads what arrived while it was down. A sender with no address, an account with no agent, or no Redis: no serialization, as before. The same conversation of one account keeps its own turns (5bis).
6. The turn is taken from the account's hour (`state.take_turn`): one Redis transaction adds it to the account's sorted set of the last hour's turns and gives it back when that makes more than `max_turns_per_hour`, so messages arriving together never all pass the read `decide()` made. Refused -> `account_rate_limited`, nothing runs. It fails closed (no Redis: a limited account runs no turn): whoever writes to the account would otherwise set what it spends. Every turn counts, whatever it decides - a `needs_owner` notifies the owner, a `no_reply` is still metered.
7. The provider's thread or chat (`fetch_context`, `context_messages`) is replayed by `build_turn()` - account messages as the assistant, others as named user lines, consecutive turns folded, the conversation never opening on the assistant. The message's files (`AccountEvent.attachments`, `AccountAttachment(name, url, content_type)`, read by the provider from the message alone; Teams: `reference` attachments through Graph `/shares/{id}/driveItem/content`, and the hosted contents its body references under the same message, at most `MAX_MESSAGE_ATTACHMENTS`; never on the account's own or an application's message) are downloaded as the account by `provider.download_attachment()` (default: refused; Teams: `fetch_file` on a Graph URL only, under `MAX_UPLOAD_SIZE_BYTES`, the redirect followed without the token), stored as `FileAttachment` rows of the owner (`source` `account:<provider>`, S3 prefix `accounts/<id>`) committed before the turn, and handed as `run_agent_chat(files=...)` by `pipeline._message_files()`. A file that fails is skipped and logged; the answer never waits on it.
8. `run_agent_chat` as the account's OWNER (`user_id`), `allow_handover=False`, acting as the account (see below: `pinned_integrations`, `identity_from_platform=True`), held to the matching rule's access (`access_arguments()`, see "Access by audience"), `context=message_context(...)`: `platform` (output format), `response_policy` (`always` / `decide`, read by `agent_chat` and winning over the conversation's shape; `schema` on a triage turn, below), `account_brief` (whose account, as whom, the rule it answers under and its instructions, the AI label the platform adds to the reply), the sender's `contact_name` / `sender_email`, the platform's `message_id` (structural: what the account's own tools of that platform take to act on the message, an email's attachments for instance), and beside it what those tools also take to reach the message, `provider.message_reference(event)` (#11099; empty by default; Teams: `chat_id` for a chat message, `team_id` / `channel_id` plus `parent_message_id` for a thread reply, the argument names of `add_microsoft_chat_message_reaction` and `add_microsoft_channel_message_reaction`, so the turn can react to the message it answers with the pinned integration, as the account; rendered as structural keys of `services/message_context.py`). `[NO_RESPONSE]` -> `silent`. On a provider that triages, see "Triage". An `error_out` code or a non-empty `approvals_out` (a gated tool) -> `failed`, nothing posted: the turn's explanation is never posted as the account. A message an agent account recorded as its post while the turn ran (its send returned after the notification reached this account) -> `agent_author`, nothing drafted.
9. The AI label is applied in code (`labelled()`), never asked of the model. `auto` posts (`send_reply`, the post marked as agent-sent and as an agent account's post, the thread marked active, the hour counted), `approval` stores a `pending` reply and notifies the owner (an `Activity` with `notification_source: agent_account`, `notification_kind: pending`, theirs alone), `shadow` stores it. An `auto` post also notifies the owner (`notification_kind: sent`) unless they turned `notify_on_send` off; an approved reply does not, its owner sent it.

## Triage

A chat message is answered or left; an email may be beyond the agent or need no answer at all. On a provider whose `capabilities.triage` is set (a mailbox), every answering turn ends in a structure, never in a phrase of its text (invariant 16): `run_agent_chat(session_output_schema=triage.output_schema(must_reply=...))`, with `response_policy: schema`, under which `agent_chat` adds none of the `[NO_RESPONSE]` / "You MUST respond" / thread-continuation blocks - the schema carries the choice. The structure is `decision` (`reply`, `needs_owner`, `no_reply`; a rule with `reply: always` leaves `no_reply` out, never `needs_owner`: handing over is the honest alternative to an answer the agent cannot stand behind), `reply` (Markdown, no quoted thread, no signature) and `note` (one line for the owner).

`triage.read()` reads it back; anything else is `failed` ("did not say whether to reply, hand it over or leave it"), a `no_reply` under `reply: always` is `needs_owner` (`unanswered()`). Then:

- `reply` goes the usual way (auto / approval / shadow); the note is the decision row's.
- `needs_owner` is recorded `flagged` (`OUTCOMES`, group `needs_owner`), with the note; the owner is notified (`notification_kind: flagged`, the bell opening the Decisions tab on `group=needs_owner`) unless `notify_needs_owner` is off.
- `no_reply` is recorded `silent`, with the note.

What the mailbox shows of each is the owner's choice, `AgentAccount.mailbox_actions` (`normalize_mailbox_actions`, 400 on a fault; NULL = `DEFAULT_MAILBOX_ACTIONS`; an update is merged over the stored actions by `merge_mailbox_actions`, a key left out keeps its value, and `reaction_feedback` the same way by `management.merged_reaction_feedback`, #9898): a follow-up flag on a handed-over email, read on an answered one (or one needing no reply), a category per outcome (empty = none). `triage.mark_for()` turns it into a `MessageMark` that `provider.mark_message()` files: for `needs_owner` / `no_reply` right after the turn, for a reply in `_post`, once it is sent (an approved draft included). Shadow mode files nothing and notifies nobody. A failure to file is the account's `last_error`, never the reply's.

## Signatures

A reply a provider sends through its API is never composed in the platform's client, so a signature add-in of that client never signs it. On a provider whose replies are signed (`capabilities.signature`, Outlook), the owner chooses where the signature comes from, `AgentAccount.signature_source` (`providers.SIGNATURE_SOURCES`; NULL = `own`): `own` - the provider finds the account's own (Outlook: the `<div id="Signature">` block of its sent mail, `_extract_signature_block`); `integration` - read from `signature_integration_id` (a plain column, no foreign key: a deleted integration reads as gone) when each reply is sent; `none` - none, the mail server signs (a server-side signature). Saved by `_apply_signature()`: the integration must be one the owner can see and of a provider in `email_signatures.signature_providers()` (400 otherwise, a non-signed provider refuses anything but `own`); the catalog serves `signature_providers` for the picker.

`pipeline._sign()` resolves it in `_post`, before every send (auto and approved alike), onto `ProviderSession.signature` (`AccountSignature`: `own` / `given` with the signature service's HTML, its reply variant first / `none`); the provider places it (Outlook: `signature_block()` above the quoted thread). It reads through `services/email_signatures.read_signature()` (the one reader: the integration as chosen, its relay route, `READ_TIMEOUT_SECONDS`, a `CACHE_SECONDS` cache per integration and address), by the account's `account_email`. An integration that cannot be read, or holds no signature for the address, falls back on `own`: the reply goes out, and `account.last_error` says why until a reply carries the integration's signature again. A signature service registers with `email_signatures.register_signature_source()` (Letsignit, `integrations/providers/letsignit.py`); nothing generic names one.


`agent_account_decisions` holds one row per message an account heard (unique on account, conversation and message id), written by `activity.record_decision()` in its own session - it never raises, a lost row never stops a reply. The row is upserted as the message moves on (`waiting` during a grace period, then its outcome): `waited` stays true once set, `reply_id` and `conversation_name` keep the first value they get. `reply_id` points at the `AgentAccountReply` the message produced, without a foreign key; the outcome shown is the reply's status when there is one (`effective_outcome()`: `coalesce(reply.status, decision.outcome)`), so an approved, dropped or expired draft reads as such without rewriting the log. `OUTCOME_GROUPS` folds outcomes into what the page counts: `answered`, `needs_owner` (`flagged`), `awaiting_approval`, `shadow`, `dropped`, `silent`, `waiting`, `failed`, and `left` for every reason the agent was not asked. `note` keeps the agent's own line on its triage (kept by a later outcome that brings none, searched by `q`). Rows older than `RETENTION_DAYS` (30) go in batches at each maintenance step (`purge_old_decisions()`).

Routes, all on the account's visibility (`_get_visible`): `GET /{id}/decisions` (`group`, `conversation_type`, `conversation_id`, `sender` - platform id or name -, `q`, `limit` <= 100, `offset`; returns `items` + `total`), `GET /{id}/replies` (`status`, `q`, `limit`, `offset`, with ratings), `GET /{id}/activity` (`period` `24h` / `7d` / `30d`, `tz` the browser's zone, an unknown one falls back to UTC). `activity_stats()` computes everything in SQL: counts by group, outcome and conversation type, a timeline bucketed in the viewer's zone (hours for 24h, days otherwise, empty buckets filled), the top conversations (with `with_name`, someone who wrote there besides the account, which names a direct chat) and senders, what each rule decided, replies by status, the median time to answer (auto-sent replies, from the message) and to approve (from the draft), and the ratings (`Annotation` on `agent_account_reply`).

The owner is notified of each reply posted automatically (`notify_on_send`, on by default); the notification opens the account's `Replies` tab (`Header.agentAccountRoute`), a pending one with `?status=pending`.

## Acting as the account

One XTM One user may operate several platform accounts - their own, and a service account such as `executive-assistant@` they hold the credentials of - each through its own integration and its own agent account. A turn runs as the owner (their permissions, their quota) but speaks as the account:

- **Tools of the account's platform act as the account.** `run_agent_chat(pinned_integrations={provider.integration_provider: account.integration_id})` -> `integration_tools.pin_bindings()`: the account's integration takes the provider's base slot, after template resolution and the shadow guard, and every binding of that provider the agent did not choose itself (template resolved for the owner, session override, their `provider#N` instances) gives way to it. Only a provider the agent uses (bound, or in `integration_template_bindings`) is pinned; an integration the owner may not see or whose token they may not use drops the provider's tools, never falls back to another account. Without it a template binding resolves to the owner's own integration: the Executive Assistant would read its owner's mailbox.
  - A **direct binding** of the same provider that names another integration (`binding_origin_map` value `DIRECT_BINDING_ORIGIN`) is kept beside the pin as `provider#2`, `provider#3`...: the agent's owner bound it on purpose (the executive's own calendar the assistant manages), and a chat run exposes it. With two instances every tool of the provider is suffixed (`tool__<slug>`, `_suffix_instance_tools`) exactly as in a chat run, the account's own sign-in and the other one alike, so a Teams or Outlook turn reaches both accounts under the same names a chat turn does. A direct binding of the pinned integration itself is folded into the pin. A rule's `access.integrations` still drops a provider it leaves out, pin and kept bindings together.
- **The person writing is the sender, not the owner.** `identity_from_platform=True` makes `interlocutor_record` `None`: the identity block is the platform-reported, unverified sender (`build_identity_context(None, is_anonymous=True, timezone=<owner's>)`), the security policy never calls an identity verified, and the identity-override reminder never names the owner.
- **The owner's user memory and defaults stay out**: user memory is about the owner, so it is neither loaded into nor written from a turn that talks to someone else (`_mem_user`); the owner's default knowledge bases and MCP servers (`user_kb_ids` / `user_mcp_ids`) are theirs to chat with and are not merged in either. The agent's own memory tiers are unchanged unless a rule's access turns them off.
- **One enabled agent account per platform account, and per provider and integration**, so two accounts never both answer nor compete for subscriptions a provider grants once per resource. One integration may serve two providers - a Microsoft sign-in runs a Teams account and an Outlook mailbox, which hear different conversations:
  - At save (create, a changed integration, enabling): `_claim()` reads who the integration is signed in as (`provider.identify`, bounded by `IDENTITY_TIMEOUT_SECONDS`, `None` when the provider cannot say) and `operator_of(..., excluding=account, integration_id=...)` (both checks on the account's provider) refuses with a 409 naming the other account to its own owner only (`Operator.message`). Before anything is released, so a refused save leaves the account as it was.
  - The partial unique indexes `uq_agent_accounts_operated` (`provider, account_external_id WHERE enabled AND account_external_id IS NOT NULL`) and `uq_agent_accounts_provider_integration` (`provider, integration_id WHERE enabled AND integration_id IS NOT NULL`) are the backstop: `_flush_claimed()` turns their `IntegrityError` into the same 409. Migration `a5450uniq01` paused the enabled duplicates saved before the rule (the oldest kept it, the others `enabled=false`, `status='error'`, reason in `last_error`); `u5702mail01` replaced the per-integration index by the per-provider one (its downgrade pauses what the old one would refuse).
  - A sync that reads the identity of an account saved without one checks `operator_of` before storing it: a platform account already operated leaves this one in `error`, its subscriptions released and its identity unstored.
  - `GET /pickers/{provider}/identity` shows the editor who an integration is signed in as and whether an agent account already operates it; the editor refuses to save an enabled duplicate.
- **Two agent accounts never answer each other.** `_post()` records every post in `state.mark_agent_post(provider, conversation, message)`, a key shared by all accounts; `decide()` reads it into `EventState.agent_post` (reason `agent_author`), and the pipeline asks again after the turn, before anything is drafted or posted. A message that says so itself counts too (`AccountEvent.from_agent_account`): two mailboxes never share an id for one email, so the Outlook provider marks every email an agent account sends with a header and reads it back.

A new sign-in (`integration_id` changed) releases the subscriptions with the previous one's token before the identity is read again.

## Access by audience

A rule's `access` (`normalize_rule` -> `_access`) narrows what the agent uses for the messages that rule answers: `integrations` (providers), `knowledge_base_ids`, `mcp_server_ids`, `builtin_tool_ids`, `custom_tool_ids`, `skill_ids` - each `None` (the agent's whole set, ids it gains later included) or a list - and `memory` (`on` / `off`). A block that narrows nothing is stored as `None`. Ids are not checked against the agent when saved (it may change): `pipeline.access_arguments()` intersects every list with the agent's own at each turn, so access only ever narrows.

`access_arguments()` maps it onto existing `run_agent_chat` arguments, enforced in code:

- the five id lists -> `session_knowledge_base_ids`, `session_mcp_server_ids`, `session_builtin_tool_ids`, `session_custom_tool_ids`, `session_skill_ids` (they replace the agent's sets, and the owner's defaults with them);
- `integrations` -> `allowed_integration_providers`: `agent_chat` drops every other provider's bindings after `pin_bindings` (and pins nothing it would drop), withheld-integration notices included;
- `memory: off` -> `memory_overrides` with every tier off, read and write.

Order is the policy (first match): a channel rule placed first gives everyone in that channel its access, whoever asks. The rule's `instructions` are the guardrail the model follows for that audience; `/ai/generate-prompt` writes them (`agent_account_rule_instructions`, and `agent_account_instructions` for the account's own). `/simulate` returns the decision's `access` and reads the sender's groups from `state.sender_group_ids` or, through `sender_directory()`, the XTM One user of `event.sender_email` (then returns `sender` like the pipeline's decision).

Approvals: `POST /replies/{id}/approve` posts a `pending` or `shadow` draft (as edited, the label applied at send), `reject` drops a `pending` one; a `pending` reply expires after `APPROVAL_TTL` (scheduler).

## Listening

`listening_plan()` derives what the provider must hear from the answering rules: all chats when a rule covers direct or group chats, the named channels (mentions only unless an answering rule reaching them answers every message, `trigger: any`), every channel of the account (bounded by the provider) when a channel rule names none - with mentions only, again, unless such a rule answers every message (`hears_channel_in_full()`). `sync_account()` keeps the account's `AgentAccountSubscription` rows equal to the provider's `desired_subscriptions()`: deletes the stale, renews within `RENEW_BEFORE`, creates the missing with a random `clientState` and a lifecycle URL. Chats with no live push subscription are polled when the provider can (`transport`: `push`, `poll`, `mixed`, `none`).

A follow-up in a thread the account answered in carries no mention, so a channel heard for mentions only never notifies it. Hearing the whole channel for it - what the plan did before - brought every message of every channel a mention rule reaches (alerts and bots included) to the account. Instead, when the account posts in a channel thread (`pipeline._post`) that the plan hears for mentions only and a rule reaching it follows threads (`follows_channel_threads()`), the thread goes on `state.FOLLOWED_THREADS_KEY` with a read cursor living `THREAD_ACTIVE_TTL_SECONDS` (each answer extends it, never moves the cursor back). `follow_threads()` (spawned by `run_maintenance`) reads each due thread every `FOLLOW_EVERY_SECONDS` through `provider.thread_messages_since()` (`capabilities.threads`), at most `FOLLOWED_THREADS_PER_PASS` per pass, and dispatches the new replies like notified messages; the pipeline's dedup drops one a mention already brought. A thread is dropped once its cursor expires, its account is gone or off, or the plan hears its channel in full. A message the owner's agent sends in a channel thread through the account's integration outside the pipeline (`send_microsoft_channel_message`, `reply_microsoft_channel_message`, `send_microsoft_channel_file`) does the same: the tool passes `_teams._thread_route()` to `MicrosoftContext.log_account_send(thread_route=...)`, and `sent_log.record_proactive_send` calls `follow_sent_thread()` for each account it logs the send for: `state.mark_thread_active()` (the thread continues for `continue_threads`, without counting against the replies per hour) and `state.follow_thread()` under the same conditions as a rule reply.

**The sync report**. A sync collects one `problems.Problem` per failed step and `_settle()` stores `problems.report()` on `AgentAccount.sync_report`: `checked_at`, `wanted` / `heard` (subscriptions the rules need, and those of them the provider holds), and the problems grouped by cause (kind, permission, holder) in `KINDS` order, each with its conversations (`covers` + `name`, from the `DesiredSubscription`) and at most `MAX_DETAILS` distinct provider messages for the technical details. `last_error` is cleared by a sync and keeps the failures of replies. The kind says what can be done: a provider reads `reauthorize` / `refused` / `not_found` / `throttled` / `unavailable` / `error` from the status of its own answer (`ProviderError.kind`), never from its words; the sync adds `integration` (`AccountUnavailableError`), `operated` (`operator_of`; the holder named to the same owner only), `no_public_address`, `not_subscribed` (a conversation the rules cover that the provider subscribes to none for: `provider.desired_listening()` answers the subscriptions with the `UnheardConversation`s left out, on Teams the channels past `MAX_DISCOVERED_CHANNELS` of a rule answering in every channel, the teams whose channels cannot be listed and a channel named without its team; they count in `wanted`), and explains a refused creation (`_Refusals`) from facts it holds: another agent account recorded a subscription to the same `provider.subscription_slot()` (`taken_by_account`, named to its own owner only), or the provider lists one of the account's subscriptions to that slot at another address (`taken_elsewhere`, the host named). A creation that failed with `error` while the provider never called the notification address back since it started (`state.handshake_since() is False`; the notification endpoint records each handshake with `note_handshake`, bounded to `HANDSHAKE_WRITE_TIMEOUT_SECONDS` so the validation answer is never late) is `unreachable`. The frontend names every kind (`SYNC_PROBLEM_TITLES` / `SYNC_PROBLEM_HINTS`) and renders the report on the account card (`AgentAccountSyncProblems`).

A sync never runs in a request nor in the scheduler tick: a provider may take long to accept a subscription (Graph calls the notification and lifecycle addresses back first, up to ten seconds each), so `schedule_sync()` runs it in a bounded background task (`spawn_channel_task`) with its own session. Saving or `POST /{id}/sync` sets `status: setup`, commits and answers; the list polls while an enabled account is `setup`. The scheduler's pass (`run_maintenance`, under its lease) only decides which accounts are due - the settings changed, a subscription expires soon, the account polls, an hour passed - and schedules them. `sync_account()` holds a per-account lease (`sync:<id>`, `SYNC_LEASE_SECONDS`, given back at the end): a second sync of the same account returns `None` instead of creating the same subscriptions twice. Before creating a missing subscription, `_drop_unrecorded()` deletes the provider's subscriptions to this platform's notification address that no account recorded (`list_subscriptions`): a sync stopped between the provider's answer and the commit would otherwise hold that resource until it expires.

The notification endpoint (`POST /api/v1/agent-accounts/notifications/{provider}`) answers the provider's handshake, reads the body under `NOTIFICATION_MAX_BODY_BYTES`, and acts only on an entry naming a recorded subscription of that provider and echoing its decrypted `clientState` (constant-time); the answer is the same whatever was wrong. A notification only says where to look: the message is read back with the account's token. A message from a conversation the plan does not hear (`rules.plan_hears`) came through a subscription the rules no longer want (a sync still running or one that failed): `handle_notification()` clears the sync marker (`state.clear_synced`) so the scheduler's next pass syncs the account again, and the message is still decided (`no_matching_rule`).

**Where listening stands**. `management.serialize()` adds to each account its `subscription_count`, `subscription_expires_at` (the earliest `expires_at` of its subscriptions: a Gmail watch lapses after 7 days and is renewed a day before) and `read_cursor` with `read_cursor_label` (the poll cursor `state.read_cursors()` reads for every listed account in one `MGET`, worded by `AccountProvider.cursor_label`: `last history id` on Gmail, `read cursor` by default). `get_agent_account` prints both under "Listening"; a cursor never read, or a Redis out of reach, prints nothing.

## Providers

`AccountProvider` (`providers/__init__.py`) is everything a platform must offer: `identify`, `desired_subscriptions` (each `DesiredSubscription` says what it `covers` - `chats`, `inbox`, `channel` -, its conversation's `name` and the `permission` it needs) / `create_subscription` / `renew_subscription` / `delete_subscription` / `list_subscriptions` / `subscription_slot` (what one subscription occupies, filters aside), `handshake` / `parse_notifications` / `event_from_notification`, `poll`, `thread_messages_since`, `fetch_context`, `account_messages_since`, `send_reply`, `mark_message` (a triaging provider's), `list_conversations`, `search_people`. A provider also declares what it is: `kind` (`chat` / `mailbox`, the presets and how the editor words conversations), `chats_covers` (what its subscription to the account's direct and group conversations covers: the sync polls them when no such subscription is live, and says so in a problem) and its `capabilities` (`direct` / `group` / `channel`, `conversations` - a rule may pick specific ones -, `triage`, `signature` - the owner chooses the replies' signature -, ...); the generic layers read these, never a provider's name or resource. A failed call raises `ProviderError` with its `kind` (`ERROR_KINDS`). A new platform is one module and one line in `_registry()`; nothing else changes.

Microsoft Teams (`microsoft_teams.py`): `/users/{id}/chats/getAllMessages` (delegated `Chat.Read`) and `/teams/{team}/channels/{channel}/messages` (delegated `ChannelMessage.Read.All`, with `$filter=mentions/any(...)` when mentions alone decide), `includeResourceData: false`, at most `MAX_DISCOVERED_CHANNELS` discovered channels; chat polling through `/me/chats` ordered by `lastMessagePreview/createdDateTime`; replies posted with `build_graph_chat_body()`; every id put into a URL goes through `graph_path._validate_path_segment`; a channel reply's thread comes from Graph's own `replyToId`, never from the notification. With the per-user chat subscription the account's own posts are notified too, possibly before the send call returns their id: `_post()` opens a short "send in flight" window (`state.mark_sending`) and an account message arriving inside it is checked again after `ECHO_WAIT_SECONDS` before it counts as the human writing. Graph grants one subscription per application and chat or channel, whatever `$filter` it carries (`subscription_slot` drops it): a second account following the same channel through the same Microsoft application is refused, and the sync report says so (`taken_by_account`, or `taken_elsewhere` for another platform on the application). Graph failures are classified by status (`_graph_error`: 401 `reauthorize`, 403 `refused`, 404 / 410 `not_found`, 429 `throttled`, 5xx `unavailable`), Graph's own message kept as the detail. A subscription Graph refused to validate (`Subscription validation request failed`) means Microsoft could not reach `BASE_URL/api/v1/agent-accounts/notifications/microsoft_teams` from the internet within ten seconds - an address behind a VPN or an access proxy, or a pod not ready yet - and is reported `unreachable` when no handshake reached the platform meanwhile. A followed thread is read through `/teams/{team}/channels/{channel}/messages/{root}/replies` (`FOLLOWED_REPLIES_READ`), each reply's thread checked against Graph's own `replyToId`.

Mentions in a Teams reply (`teams_mentions.py`, read by `MicrosoftTeamsProvider.send_reply` and `send_reply_files`): a reply whose text holds an `@` token outside code reads the members of its chat or channel (`/chats/{id}/members` or `/teams/{team}/channels/{channel}/members`, at most `MAX_MENTION_MEMBERS`) and turns `@email` of a member, `@Full Name` as Teams shows it (longest first, any case) or `@Firstname` of exactly one member into a `<at id="N">` tag with its Graph `mentions` entry (the tools' `Mention.graph_entry`). An unknown or ambiguous token, the account itself, a text that already places `<at id>` markers and members that cannot be read leave the text as written: never a wrong person. What matched and what did not is set on `ProviderSession.delivery` and `pipeline._post` stores it under `origin.delivery` of the sent `AgentAccountReply` (`mentions_resolved`, `mentions_unresolved`). `AccountProvider.reply_mention_hint` is the line of the account brief that tells the agent how to mention (Teams only).

Microsoft Outlook (`microsoft_outlook.py`), a mailbox on the same Microsoft integration (`Mail.Read`, `Mail.ReadWrite`, `Mail.Send`): one subscription to `/users/{id}/mailFolders('inbox')/messages`, created - like every read and write - with `Prefer: IdType="ImmutableId"`, so an email keeps its id when it is moved; without a public address the inbox is polled on `receivedDateTime ge` the cursor (an email of the cursor's second is read again and dropped by the dedup). The email is read back by id with its text body and `uniqueBody`, the account's addresses (mail, sign-in name, `smtp:` aliases) read once from `/me`. Mapping: the account in `To` with nobody else on the email is `direct`, anything else `group`; the account in `To` is `mentions_account` (`Cc` alone is not); the thread is `conversationId`; the subject is the conversation's name and the first line of the text; attachment names are appended. Automated mail is `from_application` - RFC 3834's list for an automatic responder: `Auto-Submitted` other than `no`, `Precedence: bulk / junk / list`, a `List-Id` / `List-Unsubscribe` / `List-Post` header, no sender - and drafts and calendar invitations are not heard. A meeting response (`#microsoft.graph.eventMessageResponse`: accepted, tentative, declined) or a cancellation (`#microsoft.graph.eventMessage`) is heard only when its written body (`uniqueBody`, else `bodyPreview`) is non-empty (a counter-proposal, a reason); its sender is then Graph `sender` (the delegate of "X on behalf of Y", who acted on the calendar) with `from` kept in `sender_emails`, so a rule naming either matches. A bare response is filtered on purpose. Any other `@odata.type` is not heard. Context: the thread's messages (`$filter=conversationId eq '...'`, quotes doubled; Graph refuses `$orderby` with that filter), read across `@odata.nextLink` pages up to `THREAD_READ` and sorted here, so the latest `context_messages` of a long thread are kept; the owner-takeover check (`account_messages_since`) reads the same pages with the headers alone (`id,from,sender,sentDateTime,isDraft`). Answering: `createReply` (`createReplyAll` when others are on the email; `reply_recipients` counts them - every `To` and `Cc` address once, but the account's own and the sender's - for the account's `max_reply_recipients`) with the `X-XTM-One-Agent-Account` header (retried without it when a mailbox refuses it), the answer (`build_graph_email_body`) and the signature the owner chose (see "Signatures"; the account's own is its sent mail's, `_extract_signature_block`) put above the quoted thread, then `send`; a draft that cannot be sent is deleted. `mark_message`: a follow-up flag, read, a category added to the email's own (never twice).

Gmail (`google_gmail.py`, key `google_gmail`), a mailbox on a `google` integration (`gmail.modify`, `gmail.send`; the integration's existing scopes). Listening is a poll of the mailbox's history (`users.history.list`, `historyTypes=messageAdded`, no `labelId` since the API takes one label only: an added message is kept when it carries `INBOX` or `SENT`, `HEARD_LABELS`) from the last `historyId` read, the cursor the listening state stores: a new cursor starts at the profile's current `historyId`, so the past is never replayed; a cursor Gmail no longer holds (404, history kept about a week) is recovered by reading the inbox of the last `RESYNC_DAYS` (7) days oldest first, the pipeline's dedup dropping what was heard, and the cursor restarts at the current `historyId`. Push: when the integration's extra config names `gmail_pubsub_topic` (`projects/<id>/topics/<name>`, Gmail granted publish on it) and `gmail_push_service_account` (the service account the topic's push subscription signs its OIDC token with, its push endpoint `<BASE_URL>/api/v1/agent-accounts/notifications/google_gmail` and that same URL as the token's audience), the account wants one subscription, `users.watch` on `INBOX` and `SENT`, recorded as `gmail-watch:<address>` with the signer as its `client_state` (Gmail echoes no secret, `CreatedSubscription.client_state`); the maintenance pass renews it a day before its 7-day `expiration` by calling `users.watch` again, and `users.stop` deletes it. A delivery goes through `AccountProvider.parse_delivery`: Gmail verifies the bearer against Google's keys (`RS256`, Google issuer, audience = the notification URL, `email_verified`) and puts the signer it names in `client_state`, so `accept_notifications` admits it only when it matches the recorded signer; an unsigned or unverified delivery is dropped. A delivery names no message (`push_wakes_poll`): it wakes one history read from the cursor under a per-account lease (`push-poll:<id>`). Push may be lost, so the account stays polled every `FALLBACK_POLL_SECONDS` (300) all the same (`poll_fallback`, transport still `push`); without the two settings it is polled as before. An email maps as an Outlook one does (to the account alone: `direct`; other recipients: `group`; the account in `To` is addressed; the thread is its `threadId`); `DRAFT`, `SPAM` and `TRASH` are never heard; the RFC 3834 / `List-*` headers and the `CATEGORY_PROMOTIONS`, `CATEGORY_SOCIAL`, `CATEGORY_UPDATES` and `CATEGORY_FORUMS` labels make it an application's (`from_application`). A message the owner sent (`SENT`, from one of the mailbox's send-as addresses) is `from_account`: it starts no turn, and unless the agent sent it (`state.was_sent_by_agent`, or another agent account's header) the pipeline raises the platform event `agent_account.owner_sent` (`pipeline.publish_owner_sent`, every mailbox provider, Outlook included; payload `platform_events.agent_account_message_data`: account, provider, agent, thread, message, Internet Message-ID, subject, sent time; personal to the account's owner, the account's agent its participant; event id `agent_account.owner_sent:<account>:<message>`, so a message pushed and polled starts one run per subscriber), the hook a flag-clearing assignment listens to. A reply is one `messages.send` in the thread (`threadId`, `In-Reply-To`, `References` grown from the answered email's), carrying `X-XTM-One-Agent-Account`, the owner kept in `Cc` on a reply-all, guarded by the mail tools' send guard of the mailbox; its signature is the owner's choice: `own` = the primary send-as address's Gmail signature, `integration` = the signature integration's, `none` = none; a personal mailbox never gets a signature it did not choose. Triage: `mark_message` adds `STARRED` for the flag, removes `UNREAD` when asked, adds a user label for the category (created when the mailbox has none of that name, case-insensitive); `INBOX` is never removed: nothing is moved, archived or deleted. Ids are checked (`[A-Za-z0-9_-]`) before any call.

WhatsApp (`whatsapp.py`), a business phone number on a `whatsapp` integration (WhatsApp Cloud API, system user access token, `phone_number_id` in extra config). The provider declares `credential = "api_key"` and `session_config_keys = ("phone_number_id",)`: `pipeline.open_integration_session` then opens the session from the integration's stored key (`vault.reveal_field`, no refresh) and carries the keys, plus `integration_id`, in `ProviderSession.config`; an OAuth provider (the default) is unchanged. No subscription and no poll (`push=False`, `poll=False`): Meta posts every message of the number to the single WhatsApp callback, `whatsapp_inbound.record_change` stores it and hands each row it newly inserted to `providers.whatsapp.dispatch_stored`, which dispatches it to every enabled `whatsapp` account on the integration; a redelivered message is not inserted again, so never answered twice, and reactions are not dispatched. Direct conversations are a phone number, groups the group id (`conversation_type` `direct` / `group`, no channel). `identify` reads the number's `verified_name`; `fetch_context` replays the conversation from the inbound store (the account's own replies are not in it: the Cloud API does not echo them, so `account_messages_since` is empty); `send_reply` posts one text message (4,096 characters at most) as a reply to the message answered (`context.message_id`) through the slice 1a helpers (`recipient_fields`, `whatsapp_headers`); `list_conversations` lists the stored conversations. The integration's send tools log every send (text, template, media, interactive; not reactions) in the activity log of the accounts on the integration (`sent_log.record_proactive_send`, provider `whatsapp`, with the run's `send_origin`).

## Reactions as feedback

A reaction on a posted answer is a rating of it, stored as an `annotations` row of target type `agent_account_reply` by a platform rater (`rater_ref`, no `user_id`; the rule, the setting and the write are `services/reaction_feedback.py`'s, see `dev-docs/reaction-feedback.md`). The setting is `AgentAccount.reaction_feedback` (NULL = enabled, thumbs up / thumbs down), validated by `ReactionFeedbackConfig` in the request body (422). The rating goes to the agent that wrote the answer (`AgentAccountReply.agent_id`, the account's current agent for an older reply).

- Push: with the setting on, `desired_subscriptions(..., reactions=True)` asks `created,updated` for every subscription without a mention filter (`AgentAccountSubscription.change_type`; a subscription whose change types changed is deleted, then created again, in `_sync_subscriptions`), with `fallback_change_type="created"`: refused (`refused` or `error`), the subscription is created for the new messages alone, the refusal reported as a `reactions_refused` sync problem and kept for a day (`state.note_reactions_refused`), the syncs of that day keeping the fallback instead of recreating it. `accept_notifications()` drops an `updated` entry (`provider.updated_message`, parsed from the notification alone) whose message is not one of the account's sent answers with one query per delivery (`ix_agent_account_replies_sent_message`), so the noise of a `created,updated` subscription spawns no task; `handle_notification()` hands the rest to `reactions.on_updated_message()` without a session of its own, which checks the answer again BEFORE any provider call, claims the read (`state.claim_reaction_refresh`; its `REACTION_COALESCE_SECONDS` TTL only bounds a holder that died), waits `reactions.COALESCE_WAIT_SECONDS` (3 s) for the notifications that follow, releases the claim, then reads the FULL current reactions back (`provider.read_reactions`) and hands them to `reaction_feedback.apply_reactions`.
- Periodic checks: every posted answer is put on `state.REACTION_CHECKS_KEY` (`schedule_first_check`, five minutes on); `run_due_checks()` (spawned by `run_maintenance`) reads it and reschedules it until `REACTION_WINDOW` (14 days): every 5 minutes the first hour, 30 the first day, 6 hours after, and every `PUSHED_CHECK_INTERVAL` (6 hours) at most while a subscription hears it (`provider.reactions_pushed`), since push may stop hearing it before the window closes (a subscription removed, or recreated for mentions only). That covers channels heard for mentions only - Graph grants one subscription per application and channel, and its mention filter also filters the changes - and accounts that poll.
- Setting or account off: a check drops the answer; the ratings already stored are kept. `reactions.resume_checks()` (called by `PUT /agent-accounts/{id}` when the account is enabled again or its effective setting changed while enabled) makes every sent answer still in its window due at once, so its ratings are brought in line with the setting from its full current reactions.
- Excluded: the account's own reaction in `ai_user` mode (the account is the agent); a reply not `sent`; an answer past the window; the setting off. `on_behalf`: the owner's reaction counts.
- Raters per answer: `MAX_RATERS_PER_TARGET` raters who give a rating, the smallest `rater_ref` first (stable whatever order the provider lists reactions in).
- Persona Improvement `gather_evidence()` reports the users' ratings (`ratings`) and the platform raters' (`reaction_ratings`) apart (`summarize_agent_annotations(raters=...)`).
- Teams: `reactionType` legacy names (`like`, `heart`, `laugh`, `surprised`, `sad`, `angry`) are turned into Unicode (`teams_reaction_emoji` in `integrations/providers/microsoft/_teams.py`, shared with the reaction tools of the Microsoft integration), `custom` is ignored; a reaction with no user (an application) is dropped.

## From an agent

The agent tools are the REST surface offered to a model, so they decide what the routes decide: every write goes through `management.py` with the REST request schemas (`AgentAccountCreate` / `AgentAccountUpdate`, the same bounds), is audited like the REST one with `details.via: agent`, and a refusal is the route's own sentence. Nine tools (`AGENT_ACCOUNT_TOOL_NAMES`): `list_agent_accounts`, `get_agent_account` (every setting, the rules in order as stored, the sync report), `list_agent_account_options` (the registry's providers, their presets and the integrations the caller may use, `usable_integrations()`), `create_agent_account`, `update_agent_account` (every setting, `enabled` included, or the full rule list), `edit_agent_account_rule` (`add` / `update` / `remove` / `move` one rule, `edited_rules()`; `update` merges the fields given over the stored rule, its id kept; the result is normalized by the engine on save, a fault changes nothing), `delete_agent_account`, `preview_agent_account_decision` (`management.simulate()` on the saved settings, or proposed rules; nothing saved) and `list_agent_account_decisions` (`activity.list_decisions()`, the messages and replies quoted inside one `wrap_untrusted()` block). An account is named by its id or by the exact name of one of the caller's own.

Two ways in:

- **The agent builder** (`build_agent_builder_tool` registers them): the General Assistant, an agent carrying `agent_builder`, `/mcp/xtm`. Every account of the caller; an administrator's agent every account (`agent_tool_admin_bypass`, `scope: all` on the list), its writes still binding what the OWNER may use. The read half (`list_*`, `get_*`, `preview_*`) is in `XTM_MCP_READ_TOOLS`.
- **The agent configuring itself** (`agent_chat._add_own_account_tools`): an agent that operates an agent account of the person chatting with it (`management.operated_by`) gets `OWN_ACCOUNT_TOOL_NAMES` - all but `create_agent_account` and `list_agent_account_options` - scoped to the accounts it operates for that person (`build_agent_account_tools(agent_id=...)`, no admin bypass, another account answers like an unknown id), source `builtin:agent_accounts`. Wired with the scheduling tools' conditions (someone signed in asking, not an evaluation, not an A2A partner's task) and only when the turn does not carry the agent builder. The agent's `tool_deny_list` keeps any of them out.

**Never in an account's own turn.** Under `identity_from_platform` the turn runs as the owner while someone else writes: `_add_platform_builder_tools(account_turn=True)` drops every `AGENT_ACCOUNT_TOOL_NAMES` from the builder and `_add_own_account_tools` is not called, so the person writing to the account can neither read its rules nor change them. What that turn needs of the configuration is in the brief (`account_brief(rule_name=..., label=...)`): the rule it answers under, and the AI label the platform adds to the reply (a delegate's reply is then not presented as the owner's own).

## Access

Owner-only: every route serves the caller's own accounts, administrators every account (`?scope=all` on the lists, detail routes by id). The integration must be one the OWNER can see (`user_visible_filter`) and whose token the owner may use (`oauth_credentials_usable`), of the provider's `integration_provider`; the agent one the owner can see, enabled. An administrator editing someone's account binds what the owner may use. Create, update, delete, approve and reject are audited (`entity_type: agent_account`). Tested as non-admins in `tests/test_agent_accounts_postgres.py`.

With AI off (`test_ai_disabled_read_surface.py`): the routes stay open on the record - CRUD and sync are own-data housekeeping (refusing them would leave a user unable to stop or narrow an agent acting in their name), approve and reject operator control, simulate a read, the push endpoint an inbound delivery - because the one place an agent turn starts, the pipeline, asks `agentic_refusal` per message (an allow-listed entry point in `test_ai_toggle.py`) and records `ai_unavailable`.
