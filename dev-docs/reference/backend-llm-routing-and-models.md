# LLM routing, failover and model configuration

The key design decisions of the LLM layer (failover, declines, provider access and exclusions), multi-model configuration, env-seeded providers, the router functions and shared constants; the rules of this area live in `backend/app/llm/AGENTS.md`.

## Key Design Decisions

- **Direct SDK usage**: No LangChain. Each provider wraps the official SDK directly.
- **Raw event streams (Anthropic)**: both streaming paths open `messages.create(stream=True)` (`_open_event_stream`) and accumulate what they read themselves - never the SDK's `messages.stream()` helper, which rebuilds a snapshot of the whole message on every event and re-parses a tool call's accumulated input JSON on each `input_json_delta`. The API sends that input 7 bytes at a time, so the helper is quadratic in its size, on the event loop: a ~35 KB tool call stalled the loop 144 times past 20 ms (up to 0.2 s, real API), a 120 KB deck spec costs 1.1 s. Pinned by `tests/test_anthropic_raw_event_stream.py`.
- **Automatic retry**: All LLM calls use `retry_llm_call()` with provider-specific retryable predicates. Transient errors (rate limits, server overloads) are retried transparently.
- **Automatic failover**: When multiple providers are configured, `get_llm_for_user()` wraps the primary provider in a `FailoverLLMProvider` that automatically falls back to other configured providers if the primary fails after exhausting retries. Failover is transparent to all consumers — the model is automatically adjusted (fallbacks use their own default model). Both `chat()` and `chat_stream()` support failover. When a fallback serves a call, `chat()` and `chat_stream_with_tools()` as much as a text stream, the wrapper names the model it called it with on `last_model` (reset per call, left `None` when the primary serves). A text stream carries no model of its own, so `agent_loop._streaming_chat` puts that model on the response: the call's generation, and a run that ends on it, are recorded under the model that answered, like those of `chat()` and `chat_stream_with_tools()`. The agent loop also counts each call toward the models serving its run under it, because the model a response names cannot tell a fallback from the primary (a non-streamed OpenAI or Anthropic call names the API's dated model, a streamed one the model it was asked for): a run two models served is priced per model. A stream cut short after a fallback started answering (an error, a timeout, a stop), with or without tools, is closed under that fallback's model too: from the fallback's first chunk or token the wrapper notes the model on the call's `StreamUsageSink` (`note_served_model`, dropped by `restart()` with the abandoned attempt's usage), and `agent_loop._end_aborted_generation` closes the generation from that sink and hands its usage to the loop's usage hook under that model too, so a run mixing providers prices it at the fallback's rates.
- **Explicit fallback model**: Admins can pin a specific fallback model via Settings → AI Models ("Fallback Model") or the `DEFAULT_FALLBACK_MODEL` env var (stored in `PlatformSettings.fallback_model`). When set, `get_llm_for_user()` resolves the owning provider and the `FailoverLLMProvider` tries that exact model **first** on failover — before the generic per-provider chain. This also enables a same-provider model fallback (the wrapper is created even when only one provider is configured), e.g. fall back from a rate-limited frontier model to a cheaper/higher-quota model on the same provider.
- **Failover targets must chat**: `FailoverLLMProvider._iter_fallback_targets()` drops a target whose model `is_chat_capable_model()` classifies as non-chat (the declared capability decides first), then one whose config's endpoint refused that model on a chat call within the last `_REFUSED_CHAT_TARGET_TTL` (15 minutes). A refusal counts only through `is_non_chat_model_error()`: the model-naming OpenAI wording ("not a chat model", "this model is only supported in v1/responses") on a 404 or an error pointing at `param: "model"` - never a rate limit, an overload, an auth error, a timeout, a context-length error, an unknown model or a 400 about another parameter. The memory is keyed by `(provider_config_id, model)` (`build_provider()` stamps the config id on every instance; a provider built without a config is never remembered), bounded at `_MAX_REFUSED_CHAT_TARGETS`, per process, cleared by `invalidate_provider_cache()`, and never filters the primary. Every failover log line names `config=<id>, model=<id>`, and a chain that tried no target because none could chat raises an `AllProvidersFailedError` naming the skipped targets (`skipped`). The LLM proxy keeps its own `_is_non_chat_model_error()` on purpose: its answer tells the caller to use `/v1/completions`, which is wrong for a responses-only model.
- **Why each leg of an exhausted chain failed**: `AllProvidersFailedError.legs` holds one `FailoverLeg` per failed target (provider, config label or id, model, kind `declined` / `http_error` / `timeout` / `connection` / `other`, decline category, HTTP status, short error code, error text redacted with `redact_secrets` and bounded to 200 characters). The message appends one `model: outcome` clause per leg (`claude-opus-5-5: declined (cyber); gpt-6-astra: HTTP 429 rate_limit_exceeded`) and, when every leg before the last declined (`content_declined`), says a retry of the same content will not help instead of "Please try again". `classify_run_failure` reads a chain that ended on a decline as `model_declined` (detail: the categories), any other as `all_providers_failed` with the legs as detail; the classification carries them as `failure_legs` on the trace metadata, and the platform chat API error body and streaming error frame carry `legs` next to `last_status`.
- **Responses-only models are not chat models**: `gpt-5.x-pro`, `o1-pro`, `o3-pro`, the `-codex` and `-deep-research` models are served by OpenAI's Responses API only, which no provider here speaks. The router's `_COMPLETION_ONLY_CATALOG_MODES` refuses catalog `mode: responses` like `completion` and `realtime` - by EXACT unprefixed catalog key, so a gateway that serves the same model on chat completions (`openai/gpt-5.2-pro` on OpenRouter) keeps it - and `OpenAIProvider.list_models()` filters through `is_chat_capable_model()`, so they are never offered, picked as a default or tried on failover. The refusal memory above stays the net for a model the catalog does not list yet.
- **A model's decline is an error, not an answer**: Anthropic answers a request its safety classifiers decline with `stop_reason: "refusal"` and a `stop_details.category` (`cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms`, or none; Claude Sonnet 5.5 declines in more categories than Sonnet 5). `chat()`, `chat_stream()` and `chat_stream_with_tools()` raise `ModelDeclinedError` (`base.py`) in place of the declined answer, carrying the category, the API's explanation and the call's usage (a decline is billed; the streaming paths have reported it to the call's `StreamUsageSink` already, and the agent loop charges a non-streamed one to the run off the error, `_end_aborted_generation`), so a decline is never mistaken for an empty or finished answer and never added to the conversation. The OpenAI-format providers (`openai_compat.py`, `openai_provider.py`) raise the same error on `finish_reason: "content_filter"`: the AI Gateway names the category in the choice's `stop_details` (a plain `dict` on the SDK types, read by `declined_error`; `content_filter_finish` and `declined_by_filter` in `openai_compat.py` are the one place a `content_filter` finish is named and becomes a decline, the LLM proxy's OpenAI pass-through included, which traces it as `model_declined`), a provider's own filter names none and never fails over. The failover wrapper hands it to another model only for the categories `FAILOVER_DECLINE_CATEGORIES` names - `cyber` and `frontier_llm`, the ones Anthropic's own server-side fallback retries on Sonnet 5 - and stops on any other (`_is_non_failoverable`). Such a decline first goes to the models the requested one declares (`decline_fallback_models` in `model_capabilities.py`), in order, on the primary's own provider, before the rest of the chain (`_targets_after`, a target repeating one of them dropped): Sonnet 5.5 to Sonnet 5 then Opus 4.8, Sonnet 5 / Opus 5 / Opus 5.5 / Fable 5.x to Opus 4.8. A model declaring some gets the wrapper even when no other provider is configured, and a decline fallback (a chain target at `index < declined`, run on `self.primary` with another of its models) keeps `structured_output` and `reasoning_effort`, which the provider fits to each model (`same_provider`); any other target, an admin fallback model included (even when the provider cache hands back the primary's instance), still gets neither. The LLM proxy dispatches a decline-only wrapper (no chain, no admin fallback model: `not has_configured_fallbacks`) on its primary so it keeps the Anthropic bridge and raw-error surfacing of an unwrapped single-provider install. Once a decline fallback answered, the wrapper (one agent run) sends that requested model's later calls straight to it (`_decline_routes`, `_routed_model`), so a declining model is asked once per run, not once per iteration; a routed model that declines in turn moves to the next fallback and `_targets_after` resumes the chain after it, a transient (non-decline) failure of the routed model never re-asks the requested one, and a new wrapper starts from the requested model again. A run that ends on one is classified `FailureCause.MODEL_DECLINED` (detail: the category), which `chat.py` words as a decline, with a cyber-specific message for the `cyber` category. The LLM proxy answers it as `finish_reason: "content_filter"`, never as a provider error: the Anthropic bridge from the stop reason, and the provider bridge (Gemini, Bedrock, and a failover-wrapped provider, which has no raw client) from the error, a chain that ended on a decline included (`_model_declined`). Its trace is closed as the `model_declined` failure with the decline's usage (`_end_declined_trace`), never as an ordinary answer.
- **Bedrock structured outputs**: Bedrock serves Claude Sonnet 5.5 without structured outputs (Converse `outputConfig`, strict tools), so `bedrock_provider._apply_structured_output` sends `outputConfig` only where `supports_bedrock_structured_output()` (the `no_bedrock_structured_output` rule field) allows it; the prompt-based SAP instructions and validation enforce the schema either way, and an operator is told so once a day for the whole platform (`log_once_soon`, keyed on the model).
- **Mistral limits**: Mistral has no separate output cap - prompt + `max_tokens` must fit the context window - so its family entries in `model_limits.py` keep the output at 16K (8K for Magistral's 40K window) and the class floors (`context_window = 128_000`, `max_output_tokens = 16_384`) at what fits beside a prompt compaction lets grow to 80% of the smallest current window. Overstating the window is the costly direction: compaction then fires too late and the request overflows.
- **Context window scan**: `POST /settings/llm-providers/{id}/context-windows/scan` (admin, AI gate, read-only) answers each model from the provider's own listing (`list_model_context_windows()`: OpenAI-compatible `context_length` / `max_context_length` / `max_model_len` / `context_window` / `max_input_tokens`, Anthropic `max_input_tokens`, Gemini `input_token_limit`; `None` = the listing carries none), then the bundled catalog, then the family table - never the flat class default. A listing value is external input: read it through `reported_context_window()` only. A listing that fails or takes more than `PROVIDER_LISTING_TIMEOUT_S` is reported as `live_lookup: "failed"` (the reason stays in the logs). The admin saves what it found as `context_windows`, which `LLMProviderRequest` / `LLMProviderUpdateRequest` parse with `parse_token_count()` (`128K`, `1.05M`, `200,000`; 422 for anything else); the frontend mirrors the grammar in `src/lib/token-count.ts`.
- **Embedding provider**: `get_embedding_provider()` uses the admin's choice first (`PlatformSettings.embedding_provider_id`, else the newest config of `embedding_provider`, with `embedding_model` or the config's default model; a `tei` config needs no model). With no choice that resolves, `implicit_embedding_fallback()` takes the first configured provider of `_EMBEDDING_PROVIDERS` - OpenAI, Gemini, Azure OpenAI, Mistral, Bedrock, Ollama - on its `EMBEDDING_DEFAULTS` model; it also tells the provider-deletion preview where embeddings go. A Custom OpenAI-compatible endpoint, a `tei` server or the Filigran AI Gateway embed only once an admin selects them. Image generation follows the same pattern over `_IMAGE_PROVIDERS` (OpenAI, Gemini, Azure OpenAI) and `IMAGE_DEFAULTS`, Azure only with an admin-named model. A provider that adds embeddings joins `_EMBEDDING_PROVIDERS` and `EMBEDDING_DEFAULTS` (`backend-llm-providers.md` > "Supported Providers" says which ones implement `embed()`).
- **Provider access** (#5160, `provider_access.py`): `llm_provider_configs` rows are platform-level (Fernet-encrypted keys), and an admin may restrict one to groups and users (`access_restricted`, `shared_group_ids`, `shared_user_ids`, Settings > AI Models > Access) so a team runs on its own key. A caller may use the unrestricted providers plus those granted to them directly or through a group; a caller with no account (anonymous channel sender, widget visitor, `/mcp/global`, an ownerless run) the unrestricted ones only; admins route like everyone else. Every chat resolution goes through `provider_routing(db, user_id, configs)` / `ProviderRouting`: the usable configs, a GRANTED one first (`team_first`, `owner_for`, `prefer_team`, `choose`), so one shared agent runs on each caller's team key; a model only withheld providers list (`is_reserved`) skips its tier, a stored reference to a withheld provider reads as absent (no stale-reference warning), failover stays inside the usable set. A matter of access raises `ProviderNotUsableError` (a `ValueError`): `NO_USABLE_PROVIDER_MESSAGE` when no provider is usable, `RESERVED_MODEL_MESSAGE` when an explicitly named model is only on other teams' providers; a handler that words its own refusal lets it through, since "ask for access" and "no such model" are different remedies (the LLM proxy answers it 403). A capability that spends a vendor's key directly rather than resolving a model (speech-to-text, investigation web search) takes it from `usable_provider_configs(db, user_id, providers)` (the caller's team first, then the admin default), never from a bare `select(LLMProviderConfig)`, which would hand one team's key to anyone and break once a vendor is configured twice; speech resolves through `router.get_speech_provider()` over the same routing. Embeddings and image generation stay platform-level. Writes: `apply_provider_access()` is the one write of an access list (only an id the write ADDS is checked, the lists are kept while the provider is open, so restricting it again restores its audience); a non-admin's model / provider pin is validated against their usable providers (`validate_selectable_chat_model(..., scoped=True)`, `provider_id_usable_by()`), and a copy (import, duplicate, catalog clone) drops a pin the copier may not use instead of refusing. Never filter configs by `access_restricted` by hand.
- **Provider exclusions** (`provider_access.py`): `excluded_group_ids` / `excluded_user_ids` keep groups and users OFF a provider whatever it grants, restricted or not - a member of an excluded group is excluded even when granted (`is_excluded()` runs first in `provider_usable_by()`), so it rides every reader of the routing unchanged and `ProviderRouting.excluded_ids` lets `reserved_model_message()` word the refusal (`EXCLUDED_MODEL_MESSAGE`: asking for access would not help). An exclusion follows the PERSON the AI work is for: `load_provider_audience()` resolves a call with no user of its own as the user bound to the context (`bind_acting_user()`, a `ContextVar`: bound by `deps.get_current_user_ungated`, the MCP endpoints' own authentication, the web chat's send, `get_llm_for_user` itself, the assignment / sub-agent / flow adapters, a KB sync around its source's user; `acting_for()` scopes a binding - the orchestration reconciler and the scheduler tick run every execution and every tick inside `acting_for(None)` so nothing bound for one person reaches the next piece of work, memory maintenance walks its user scopes with it) - so compaction, memory and titles of an excluded person never reach the provider. Embeddings and image generation stay platform-level for everyone else, but `get_embedding_provider()` / `get_image_provider()` call `ensure_not_excluded()` for `user_id` (else the bound person) and REFUSE with `ProviderNotUsableError` rather than send an excluded person's content; a KB document is refused at ENQUEUE time while its person is known (`kb_helpers.refuse_documents_for_excluded_person`: marked `embedding_not_available`, no automatic retry, so no sweeper re-enqueue - which knows no person - ever finds it pending), and its job carries the person too (`kb_helpers.document_job_kwargs`, `on_behalf_of`, falling back to the knowledge base's owner) as a second check; re-embedding EXISTING documents (reprocess routes, the platform-wide reset after a model change) goes through `kb_helpers.enqueue_reembedding()`, which binds no one, so each job embeds for the person recorded on the document (`KnowledgeDocument.added_by_user_id`: set by the refusal and by every job that names a person) AND for its KB's owner, refusing when either is excluded (`document_processor._embedding_people` - a company-managed KB has no owner) rather than for whoever clicked; a memory SEARCH an excluded person cannot run raises (`embed_text(..., refuse_excluded=True)`): the tool answers the refusal, the REST search keeps its text (ILIKE) half and says so in `X-Semantic-Search-Refused`; a memory WRITE stores without a vector, with no retry and no warning (`persist_memory` asks with `refuse_excluded=True` to tell the exclusion from a failure); re-embedding skips the stored memories of `excluded_user_ids()`. A group an exclusion names cannot be deleted (`providers_excluding_group()`, 409), and a group the SAML sync merges into another hands its exclusions over (`carry_group_exclusions()`); a deleted user is pruned (`prune_user_exclusions()`). Written by `apply_provider_access(..., excluded_group_ids=, excluded_user_ids=)`, bounded like the grants (each list on its own).
- **Agent override**: an agent runs on its own `llm_provider` / `llm_model` / `llm_provider_id`, or on the platform routing model when `llm_model_source` is `"routing"`. Every path that runs an agent reads them through `agent_model.agent_model_selection()` and passes them to `get_llm_for_user()` as overrides, never from the columns directly.

## Multi-Model Support

Each `LLMProviderConfig` has an `available_models` JSON array listing which models are enabled for that provider. Admins configure this in Settings.

- **Platform default**: The admin-set agent default lives on `PlatformSettings.agent_default_model`; the General Assistant's own chat model (also the last-resort platform default) lives on `GeneralAssistantConfig.llm_model`.
- **First-time setup**: When the first provider is configured and models selected, the first model automatically becomes the platform default.
- **Model resolution priority**:
  1. Agent-level override (`Agent.llm_model`)
  2. Agent default (`PlatformSettings.agent_default_model`)
  3. User preference (`User.preferred_llm_model`)
  4. Platform default (`GeneralAssistantConfig.llm_model`)
  5. Any configured provider (fallback) - the first of `implicit_chat_configs()` in the order Settings lists them (oldest first, tie-broken by id): the configs listing a chat model, or, while none does, the ones listing no model at all (on their provider's built-in chat model). The failover chain takes the same set, so a provider configured for its media alone (a key, no model list) never chats next to listed chat models. Every implicit reader loads configs through `select_provider_configs()` (`get_llm_provider`, `get_llm_for_user`, `get_embedding_provider`, `get_image_provider`), so the pick never depends on heap order.
- **Deleting a provider** (`services/llm_provider_deletion.py`): `GET /settings/llm-providers/{id}/deletion-impact` and `DELETE /settings/llm-providers/{id}` run the same `compute_deletion_impact()`, so the confirmation names exactly what the delete applies. The platform default (`agent_default_*`) and the GA chat model move to ONE replacement - the request's `replacement_provider_id` (422 unless a surviving chat-capable config), else the first of `replacement_candidates()` (chat-capable survivors, oldest first; when a moving route carries a model, only survivors that list one - the others are reported as `unlisted`) - pinned by provider id, on `replacement_model_for()`: the route's model if the replacement lists it, else its `default_model` if listed, else its first listed chat model, so the router's owner check never re-routes it. The image default moves to the first survivor whose provider class implements `generate_image` and that can serve its model or has an `IMAGE_DEFAULTS` model (`pick_image_target()`, replacement first; with `DEFAULT_IMAGE_MODEL` set alone only a survivor keeping the model qualifies), else it is cleared. The embedding default is cleared and NEVER switched (another model makes the stored vectors unsearchable); the preview names `implicit_embedding_fallback()` - what `get_embedding_provider` falls back to meanwhile - and, with no embedding default stored, announces when the deleted config is the one embeddings fall back to today (`fallback_moves`). `_prune_orphaned_env_providers` deletes through the same path (`delete_provider_config_as_system` in `api/v1/settings.py`, system-actor audit entry). Agents / user preferences pinned to the config are reset by `_cleanup_orphaned_model_references` (the orphan predicates live in the same service, shared with the preview) and inherit the defaults. The audit entry records the replacement per route and the reset counts. The delete takes `lock_provider_configs()` before it reads anything (a second deletion, a catalog edit and every provider reference writer wait, see below), and the preview's `DeletionImpact.fingerprint()` is sent back as `expected_impact`: the delete answers 409 with the fresh preview instead of applying anything the admin did not see. Every other writer of a provider reference is serialized with deletions the same way: `lock_provider_configs()` is a transaction advisory lock, which also covers a config created after the row scan, then every config row in id order (`FOR NO KEY UPDATE` exclusive - the weakest row lock that still stops every other update or delete of a config row; `FOR UPDATE` would also exclude the `FOR KEY SHARE` of a foreign key check onto the configs, which nothing needs excluded: no foreign key points at them, and an install still carrying the old foreign key from the embeddings keeps its embedding writes flowing - and `FOR SHARE` shared), taken before the write reads what it changes; a wait past the statement timeout is refused with a 503 (`ProviderLockBusyError`, "another LLM provider change is in progress", the same sentence as the agent-builder tool result) instead of a raw 500 - exclusive for a deletion, a catalog edit (the env provider and built-in embedding endpoint seeds included: they also run when AI is switched on at runtime) and the General Assistant / platform defaults save (a save that only completes a stored provider name / id pair included), shared for agent create / update / duplicate / import (a bundle naming a provider without a model included), a catalog install, the agent-builder `update_agent` and provider creation. The agent fields a deletion reads are `AGENT_MODEL_FIELDS`, the one list the REST and import lock conditions are derived from. A provider id the write adds or changes that names no config is refused (`provider_reference_problem()`: 422 on REST, the error string in the tool); an id already stored and sent back unchanged is not re-checked, a duplicate or a catalog install drops a pin to a config that is gone, and an id sent with a cleared provider is never stored, so it is not checked. Installs already left with a NULL default are not backfilled.

### PlatformSettings / GeneralAssistantConfig

`PlatformSettings` (singleton) holds the platform-wide agent defaults:
- `agent_default_provider` / `agent_default_model` — default model for all agents
- `embedding_*` / `image_*` / `default_reasoning_effort` — embedding/image/reasoning defaults
- `fallback_model`, `mcp_exposed_agent_ids`, AI-adoption config

`GeneralAssistantConfig` (singleton) holds the General Assistant chat config:
- `llm_provider` / `llm_model` — the GA chat model (also the last-resort platform default)
- `system_prompt` — default system prompt for the general chat assistant (admin-set, not user-overridable)

### Providers fed by an integration (`source_integration_id`)

A company-managed OpenRouter integration can create or adopt the platform's OpenRouter config (`services/openrouter_llm_provider.py`): the config records it in `LLMProviderConfig.source_integration_id` (a partial unique index: one config per integration), its API key is a copy kept in step with the integration's by the `on_update` lifecycle hook (a hook failure fails the integration edit), and its models are saved through `settings.update_provider_config()` - the same path as `PUT /settings/llm-providers/{id}`, with every lock and cleanup. Unlinking, making the integration private or deleting it (`ON DELETE SET NULL`) leaves the config running on the key it holds. An env-seeded config is never adopted.

### Env-seeded providers (`env_models.py`)

`LLM_PROVIDER_{PROVIDER}_API_KEY` (+ optional `LLM_PROVIDER_{PROVIDER}_MODELS`) upserts a company-level `LLMProviderConfig` on every boot (`main._seed_llm_providers_from_env`), flagged `is_from_env`. The credential is env-managed in every regime (env wins on every boot) and the row cannot be deleted from the UI (the seed would recreate it; dropping the env var and restarting prunes it). Who owns the **model catalog** is decided by `LLM_PROVIDER_MODELS_EDITABLE`, and `app/llm/env_models.py` is the single source of truth for that, shared by the seed and `api/v1/settings.py`:

| Helper | Purpose |
|--------|---------|
| `env_models_for(provider)` | Parsed `*_MODELS` list, or `None` when unset / blank — `None` means the seed never touches the stored catalog, except a `filigran_gateway` with no other chat provider: `main._seed_listed_models` lists its chat models, the seed applies them as an env list (locked) or as the catalog (editable), and snapshots them on `env_models`. A catalog still equal to that snapshot keeps being refreshed, even next to another chat provider; one an admin edited is left alone. A listing's removals clear no references (`_cleanup_orphaned_model_references` is skipped): it may be partial. Never re-spell the `split(",")` inline. |
| `merge_env_models(current, previous_env, env)` | Editable regime: fold only the *delta* between the env list and the snapshot applied at the last boot (`LLMProviderConfig.env_models`) into the admin-curated `available_models` — env additions are added, env removals removed, every other admin edit preserved. A `None` snapshot (a row seeded before snapshots, or a baseline added to a curated provider) counts the whole env list as newly added and removes nothing. |
| `resolve_default_model(current, available)` | Keep the provider `default_model` while still offered, else the first available. |
| `models_env_locked(config)` | The one predicate behind both the `PUT /llm-providers/{id}` 403 on `available_models` / `default_model` and `LLMProviderResponse.models_env_locked`, which the `ProviderCard` gates its Models editor on. Locked = `is_from_env` and `settings.provider_models_admin_curated` is false (neither `LLM_PROVIDER_MODELS_EDITABLE` nor `BYOLLM_ACTIVATED`). The built-in TEI embedding row stays locked even in editable mode (its own seed pins the single served model). |

Pinned regime (default): the env list *is* the catalog and overwrites `available_models` / `default_model` on every boot. Both regimes snapshot the applied list on `env_models`, and any model the seed drops from a catalog goes through `_cleanup_orphaned_model_references` like a UI shrink does. `DEFAULT_MODEL` is matched against what the env-seeded row *still offers*, so a model an admin removed cannot come back as the platform default. `MODELS_ENV_PROVIDING_ONLY=true` blocks every provider mutation upstream regardless, through the one gate `services/llm_provider_management.ensure_llm_provider_management_allowed()` (the Settings routes, an OpenRouter integration feeding the provider) — unless `BYOLLM_ACTIVATED=true` wins over it (`settings.provider_management_env_only`). BYOLLM also makes every `DEFAULT_*` platform value furnish an install that has no LLM configuration yet and nothing after that (`main._env_may_seed`, decided by `main._byollm_install_configured` from a snapshot taken *before* the provider loop's fill-if-empty seed) and empties `_env_managed_ga_fields()`, so admins own the defaults as well as the catalogs. An agent, embedding or image default the platform filled itself (`settings.platform_filled_models` of the env-seeded config it is pinned to) does not make an install configured; on a configured install neither the provider loop (`_ensure_platform_default_model(fill_empty_defaults=False)`) nor the XTM One embedding seed fills an empty default. Read the two resolved predicates on `Settings`, never the raw flags.

The video, speech, music and decision models are pinned the same way by `DEFAULT_<ROLE>_PROVIDER` / `DEFAULT_<ROLE>_MODEL` (+ `DEFAULT_SPEECH_VOICE`), owned by `env_capability_defaults.py`: the seed calls `seed_env_capability_defaults()` and `_env_managed_ga_fields()` reads `env_locked_fields()`. A value the platform cannot serve (a provider type that does not implement the capability or has no model to pin, no configured provider, a model or voice named without its provider) is logged and never stored. Add a role there (one `CapabilityRole` in `ROLES`), never as a new block in `main.py`.

### LLM Proxy

The OpenAI-compatible proxy at `/v1/chat/completions` validates requested models against `available_models`. Use `model: "auto"` for the platform default. A client's `tool_choice` that forces a tool call (`required`, a named function, Anthropic's `any` / `tool`) is sent as `auto` to a model whose rule sets `refuses_forced_tool_choice` (Claude Sonnet 5.5 refuses it with HTTP 400), and OpenAI's `allowed_tools` keeps its subset with `mode: "auto"` in place of `required`, the way a `temperature` the model refuses is dropped (`_proxy_tool_choice`, on the OpenAI-compatible pass-through: the Anthropic bridge sends no tools); the `/v1/messages` pass-through forwards the client's body unchanged.

## Router Functions

| Function | Purpose |
|----------|---------|
| `get_llm_provider(user_id, db, provider_override)` | Resolve provider within the providers `user_id` may use, theirs first: (1) override, (2) the first chat-capable config in Settings order (oldest first), else the first non-embedding-only one on its built-in chat model (`implicit_chat_config()`) |
| `get_llm_for_user(db, user_id, provider_override, model_override, *, provider_id_override, failover=True)` | Resolve `(provider, model)` with automatic failover, within the providers `user_id` may use, theirs first; binds `user_id` as the acting user. Returns a `FailoverLLMProvider` when another provider can serve as fallback, an admin fallback model resolves, or the model declares `decline_fallback_models`. `failover=False` returns the primary alone, for a caller that must measure the model it names (an evaluation turn, `evaluations.md` §4). |
| `build_provider(config)` | Instantiate a `BaseLLMProvider` from a `LLMProviderConfig` DB row. Stamps `provider_config_id` / `provider_config_label` on the instance: `provider_name` is only the TYPE, shared by every config of that type |
| `find_provider_for_model(db, model_id)` | Find which provider owns a model by checking `available_models`, falling back to prefix inference |
| `choose_provider_config(configs, provider, model_id)` | Pick ONE config of a provider when several exist (no unique constraint on `provider`): the config listing `model_id` (no prefix inference, which cannot choose within one provider), else the default, else the newest - whatever the order of `configs`. Never read "the" config of a type with `scalar_one_or_none()` |
| `resolve_provider_for_model(db, model_id, *, user_id=None)` | Look up provider + validate model exists within the caller's providers (unrestricted ones with no user), raises `ValueError` if not found |
| `get_platform_default_model(db)` | Return the platform default model (`PlatformSettings.agent_default_model`, falling back to the GA `llm_model`) |
| `FailoverLLMProvider(primary, fallbacks, fallback_configs, *, fallback_model, fallback_model_config, prepared)` | LLM wrapper that tries primary then fallbacks on failure. When `fallback_model` is set, its owning provider is tried first with that exact model. Transparent to consumers. When a fallback answers, `app.llm.attribution.record_failover_served()` re-points the CURRENT trace (`trace_root_ctx(get_current_trace_ctx())`: its root, never the iteration or tool span the agent loop made current) at the fallback's config, so a trace never names a config that did not serve it; when the same wrapper's primary serves a later call, `record_primary_served()` points it back, unless a downgrade or another wrapper re-pointed it since. A streamed answer is attributed from its first chunk / token (`on_token`, never the `on_thinking` sink `reads_reasoning` reads by type), so one cut short by an error, a timeout or a stop still names the fallback that produced it. An attempt whose output already reached the caller moves on only when another target remains AND the caller passed `on_stream_reset` (declared by `supports_stream_reset`, popped by the wrapper, never forwarded to a provider): it is awaited first, the caller takes the partial answer back, and the next answer streams from the start. Without it, or when it raises (the caller could not take the output back: fail closed), the error surfaces with the partial output left as it is - never a second answer glued after the first (`chat_stream` and `chat_stream_with_tools` alike). |
| `app.llm.attribution.provider_config_metadata(provider)` | The `llm_provider_config_id` / `llm_provider_config_label` keys every trace writer adds next to `llm_provider` (which stays the type pricing reads); `config_metadata(config)` for a config row used without a provider (the Anthropic pass-through). `config_identity(config)` is the one id / label rule, stamped by `build_provider()`. A caller that opens a trace and then calls the LLM must set that trace as current (`set_current_trace_ctx`) for the failover correction to reach it. A budget-driven model downgrade calls `record_model_downgrade()`: the config keys and the trace `model` (metadata and the durable trace model) name what the run continued on, and `llm_model_downgrade` records `from_model` / `to_model` / provider / config; `llm_provider` stays the type the run started on, as after a failover. A trace that only wraps other traces (`llm-proxy-agent`, `flow-run:`) carries none: `tests/test_llm_provider_config_attribution.py` counts every other `trace_llm_call` against a config stamp. |
| `provider_for_config(config)` | The cached provider instance of a config the caller already chose and checked (`provider_access`), for an endpoint chat routing knows nothing about - a decision model |
| `get_embedding_provider(db, *, user_id=None)` | `(provider, model, provider_config_id)` for embeddings: the admin's choice, else `implicit_embedding_fallback()` (see "Embedding provider" above). Platform-level, but refuses with `ProviderNotUsableError` when the provider excludes `user_id` (else the bound acting user) - see "Provider exclusions" |
| `get_image_provider(db, *, user_id=None)` | `(provider, model)` for image generation: the admin's choice, else the first of OpenAI, Gemini, Azure OpenAI with a model. Same exclusion check |
| `is_image_model(model_id)` | Whether the model catalog's `mode` is `image_generation`; an id the catalog does not know is not one (its name decides nothing) |
| `provider_capabilities(provider_type)` | What a provider type serves, from its class: `[only_capability]`, else `chat` (+ `decision` with a `decisions_api`). Settings offers chat models only to a provider that chats |
| `get_video_provider(db, *, user_id=None, provider_id=None, model=None)` | `(provider, model, config)` for video: the caller's choice, then `PlatformSettings.video_*`, then the first of `_VIDEO_PROVIDERS` (chatless ones first) on its `VIDEO_DEFAULTS` model, then the first provider listing a video model. A model its provider retired (`video_model_unavailable`) is refused when the caller named it, skipped otherwise; the error names every skip. Same exclusion check |
| `platform_video_model_problem(db)` | Why the video model chosen in Settings can no longer make a video (the check `get_video_provider` runs), or `None`, so Settings never shows a retired model as active |
| `get_speech_provider(db, *, user_id=None, provider_id=None, model=None)` | `SpeechTarget` for speech: the caller's choice, then `PlatformSettings.speech_*`, then a `SPEECH_DEFAULTS` model, among the providers the person may use |
| `get_music_provider(db, *, user_id=None, provider_id=None, model=None)` | `(provider, model, config)` for music, resolved like speech over `PlatformSettings.music_*` and `MUSIC_DEFAULTS`; a provider the person may not use is refused with `ProviderNotUsableError` |
| `list_video_models_for` / `list_speech_models_for` / `list_music_models_for(db, *, user_id)` | Every model of that capability the person's providers offer (`[{model, provider, provider_id, label}]`); a provider whose listing fails is skipped |
| `is_video_model(model_id)` / `is_music_model(model_id)` | Video: catalog first, then the family prefixes. Music: the family prefixes (`_MUSIC_MODEL_PREFIXES`; the catalog lists Lyria as `chat`). `is_chat_capable_model()` refuses both |
| `get_available_models(db, *, user_id=None, every_provider=False)` | The models of the providers the caller may use (`every_provider` for an admin configuring the platform), each with `access_restricted` |
| `validate_selectable_chat_model(db, model_id, *, user_id=None, scoped=False)` | Write guard for a stored chat model; `scoped` checks it against the caller's providers (a non-admin's agent write) |

### Provider/Engine Resolution Examples

Use router helpers as the single abstraction layer (avoid re-implementing provider/model matching logic in services):

```python
# Resolve provider + model for a specific model id. Lookup is two-step:
# (1) exact membership in some provider's ``available_models`` list, then
# (2) prefix-based inference via ``_infer_provider_from_model`` for newly-
# added models that haven't been refreshed into ``available_models`` yet.
# Raises ``ValueError`` only when neither step finds a configured owner.
llm, effective_model = await resolve_provider_for_model(db, model_id)

# Resolve judge model with platform fallback, then route through the same
# owner-resolution path (so newly-added models still work).
judge_model = evaluator_model or await get_platform_default_model(db)
llm, judge_model = await resolve_provider_for_model(db, judge_model)
```

## Shared Constants

| Constant | Purpose |
|----------|---------|
| `EMBEDDING_DEFAULTS` | Default embedding model per provider: `openai` / `azure_openai` `text-embedding-3-large`, `gemini` `text-embedding-004`, `mistral` `mistral-embed`, `ollama` `nomic-embed-text`, `bedrock` `amazon.titan-embed-text-v2:0`. Read by the implicit fallback, by the OpenAI / Gemini / Mistral / Ollama `embed()` when no model is passed, and by `api/v1/settings.py` to fill `PlatformSettings.embedding_model` on a provider's first config. |
| `IMAGE_DEFAULTS` | Default image model per provider (`{"openai": "gpt-image-1", "gemini": "imagen-3.0-generate-002"}`). Also read by `api/v1/settings.py` (first config) and the provider-deletion image move (`pick_image_target()`). |
| `CHATLESS_PROVIDERS` | Provider types whose class declares `only_capability` (`tei`, `elevenlabs`, `kling`, `runway`, `seedance`, `vertex_ai`): left out of implicit chat selection and failover, no "no chat-capable model" warning. |
| `EMBEDDING_ONLY_PROVIDERS` | The embedding subset of `CHATLESS_PROVIDERS` (`{"tei"}`): no embedding model required. |
| `SPEECH_DEFAULTS` / `VIDEO_DEFAULTS` / `MUSIC_DEFAULTS` | Built-in model per provider, read from the class attributes `default_speech_model` / `default_video_model` / `default_music_model`; `_SPEECH_PROVIDERS` / `_VIDEO_PROVIDERS` / `_MUSIC_PROVIDERS` order the fallback, a provider that serves no chat first. ElevenLabs declares no video model, so it never becomes the video generator on its own. |
| `REQUEST_TOO_LARGE_KEYWORDS` | Lowercased substrings identifying a request-size / payload error (HTTP 413 `request_too_large`, Gemini "payload size exceeds the limit", gateway "payload too large" / "request entity too large", Anthropic's request-wide PDF cap "A maximum of 600 PDF pages may be provided"). Read only through `is_request_too_large_error()`, which also counts a 413 whose `error.code` is `request_too_large` (not another 413 code, such as Groq's tokens-per-minute limit) and recognizes an `AllProvidersFailedError` whose chain ended on a size error; `FailoverLLMProvider._is_non_failoverable` (an oversized payload reproduces on every provider, so it must not burn the failover chain), `services/failure_causes.classify_run_failure` (which the chat error mapper `api/v1/chat._friendly_error_message` words) and `public_chat` all call it, so classification and user messaging never drift. A 413 carrying the provider's `body_cap_error_code` (the AI Gateway's 10 MiB cap) fails over to other providers and skips that provider's other legs. |
