# Services: assignments, orchestration, flows and evaluations

Service map rows and patterns for assignment execution, the orchestration engine, scheduling, delegation and coordination, emergency stop and deletion, flows, and evaluations in `backend/app/services/`; the binding rules live in `backend/app/services/AGENTS.md`.

| `panic.py` | Emergency stop ("panic button", profile menu). TWO transactions, never merged: `arm_admission_barrier(db, actor, scope)` pauses the assignments in scope, flips the AI switch (platform) and writes the `panic_stop` audit row; the router COMMITS that, invalidates the AI cache, then `cancel_live_work(db, ...)` runs `emergency_stop(db, actor, scope, outcome=...)`, which cancels everything live, completes the row and commits (a failure there is rolled back, marks the row `phase: incomplete`, reports `completed: false` and still lets `after_commit` sweep). One transaction would reintroduce the admission race (a run admitted between the SELECT and the commit). `after_commit()` runs `sweep_late_admissions` for pre-commit reads (`late_admissions_cancelled`; every run still active in scope, no `created_at` cut-off since that column is stamped at the flush), at once and again a cache lifetime later; for the platform scope it also cancels the background tasks and chat turns still live (`_sweep_platform_live_work`). Scopes: `self` (the actor's runs incl. run-as, background tasks, in-flight chat turns, flow runs, open runner commands given up through `runner_transport.give_up_on_command` - queued ones cancelled, dispatched ones never delivered again - and the assignments they own or that run as them) or `platform` (admin: every user, plus evaluation / autonomous executions and the `ai_state` kill switch). Composes existing primitives only: `a2a.tasks.cascade_cancel` + `orchestration_engine.cancel_executions_for_runs` for run trees, `sub_agent.cancel_sub_agent_tasks_for_scope`, `chat_turn_guard.list_processing_conversations` + `request_turn_cancel`, the flow-run cancel recipe, `assignment_pause.pause_assignment(reason="panic_stop")`. Both phases flush only; `after_commit()` does cache invalidation, `spawn_run_cancel` to partners (deduplicated), SSE frames and the sweep. `platform_stop_open()` (the open platform stop's state on `PlatformSettings`: `platform_stop_at` / `platform_stop_times` / `platform_stop_ai_override`, set by the first platform barrier and cleared by the platform resume, never derived from the audit rows that cascade with their user) is the one signal for "a platform stop is in effect", never the raw `ai_disabled` bit; a `self` resume under an open platform stop raises `PlatformStopActiveError` (409). `resume_after_emergency_stop` re-enables ONLY `panic_stop`-stamped assignments no other open stop covers (`_open_self_stops` + `_covered_by_open_stop`: overlapping stops of an owner and a run-as user each hold the assignment until both are lifted; `emergency_stop_status` reports `self_stop_active` so a stop holding only shared assignments stays liftable) and restores the AI override the open platform stop recorded (`platform_stop_ai_override`); `assignment_pause.is_emergency_stopped()` is the one predicate every other re-enable path refuses on (the power toggle, the agent-builder tool) or keeps the pause for (startup seeding: a restart never lifts a stop). One `panic_stop` / `panic_resume` audit row with per-kind counts. The stop never waits for a reason: `record_stop_reason(audit_id, reason)` annotates the `panic_stop` row and the `paused_details` of the assignments it paused (joined on `paused_at == details.stopped_at`) afterwards; the resume takes a mandatory `reason` up front (on the `panic_resume` row and as `details.note` on every per-assignment `resume` row). Token path: `generate_emergency_token` / `revoke_emergency_token` / `emergency_token_status` manage ONE platform-wide `xes-…` credential on `PlatformSettings` (bcrypt hash + prefix + who/when/last used, shown once); `resolve_emergency_token` verifies it (a refusal is a `panic_token_rejected` security event) and returns the minting admin as actor; `emergency_stop_with_token` runs the platform stop with an optional reason, `details.via = "api_token"`. |

## Assignment Execution Flow

```
trigger_assignment() / trigger_or_queue_assignment()     (assignment_engine.py)
  → agentic gate (_refuse_if_ai_disabled), owner check (refuse_if_owner_deactivated)
  → skip_if_active? per-assignment advisory lock + has_active_run → skip (None)
  → AssignmentRun(status="pending")            (queued: status="queued", promoted later
                                                 by drain_assignment_queues → same path)
  → _schedule_run_execution()
      run_at = now + configured delay + schedule spread + extra delay
      deadline_at = run_at + floored timeout + orchestration grace (none when timeout <= 0)
      run.status = "delayed" | "pending"
      create_execution(adapter="assignment", dedup_key="assignment_run:<id>")
      commit → notify_orchestration_wake()

orchestration_reconciler (worker; every cycle or on a wake)
  → sweep deadlines → reclaim expired leases → claim due executions (SKIP LOCKED)
  → AssignmentAdapter.execute() under a heartbeated lease + cancel watcher
      → close_hold_if_ai_is_back() → execute_assignment_run(run_id, hold=, cancel_event=,
                                                           deadline_at=, attempt=)
  → AssignmentAdapter.periodic() → drain_assignment_queues()
  → drive outbox events (a HITL "resume" re-arms the parked execution)

execute_assignment_run()
  → terminal-state guard, attempt fence + lost-charge credit (attempt_charges)
  → gate verdict (deferred: RUN_DEFERRED, held: RunHeld)
  → optional tool check (activation_check: one read-only tool call, no model;
    failed = run completed "Skipped: gate check ...", zero tokens, uncharged;
    evaluated once per run, at dispatch: a HITL or checkpoint resume skips
    it, a held_by_run naming the run itself is left out of the result, and a
    run holding any shared-state lease is never ended skipped, #8831)
  → agentic quota check
  → optional activation gate (YES/NO filter, one model call)
  → build system message (persona + memory + execution policy) and tools
    (MCP + custom + integration + KB + sub-agent + HITL)
  → run_agent_loop(...)
  → request_human_input → status "awaiting_human" → adapter returns await_event
  → record result + actions + memory
  → failed: retry (retry_on_failure, or a transient model failure) as a NEW run
    with its own execution
  → completed + next_assignment_id: chain via trigger_assignment
  → notify_on_complete: notification
```

The adapter maps the run's final status onto the execution: `awaiting_human` parks it (`await_event`, no deadline), `failed` fails it non-retryable (retries are new runs), any other terminal status completes it, and a run still active is force-failed so run and execution never disagree. `resume_assignment_run` re-arms a paused run with a `resume` outbox event (or a fresh execution when none is parked). Engine contract: `dev-docs/FSM/`.

## Sub-Agent Background Tasks

When an agent can delegate (`handover_agent_ids` configured, or self-fan-out enabled, see below) it gains tools for async delegation (`builtin_tools/handover.py`, `build_sub_agent_tools`):

1. `spawn_background_task(agent_id, task)` - creates a `SubAgentTask` and its `sub_agent` orchestration execution
2. `check_task_status(task_ids)` - waits adaptively: returns the moment every task is terminal (completed / failed / cancelled), or after a per-call budget with each task's live status (`wait_for_tasks` in `sub_agent.py`, `_STATUS_WAIT_BUDGET` 20 s / `_STATUS_POLL_INTERVAL` 2 s)
3. `get_task_result(task_ids)` / `get_full_task_result(task_id)` - read a completed result (preview / full), in chat and assignments alike
4. `collect_task_results(task_ids)` / `clear_collected()` - (chat path, where a session-variable store exists) merge structured items into the `$collected` session variable for a downstream tool, and release it. The extractor handles OpenCTI / OpenAEV-shaped items (id-key / `raw_configuration`), arrays of objects, nested `response` envelopes and flat structured JSON objects.
5. `list_background_tasks(status?)` - list recent tasks with optional filter
6. `cancel_background_task(task_ids)` - stop tasks this agent spawned for the acting user (#2217): `cancel_sub_agent_task(..., spawned_by=<the agent>)`, the same durable cancel as the Operations > Background Tasks stop button (execution transitioned, lease released, delivery suppressed); another agent's or another person's task answers "not found"

A task runs its target agent through `run_agent_chat` in a session of its own and persists its result to `sub_agent_tasks`; it may hand over further while its depth is below `_MAX_DELEGATION_DEPTH` (5) and the target has handover agents.

**Resume across a rollout** (`dev-docs/background-task-resume.md`): the task's completed tool rounds are checkpointed per iteration (`background_checkpoint.TaskCheckpoint`, Redis per task); an attempt that follows a lost one replays them with the resume note and the workspace manifest, at most `MAX_RESUMES` (3) times, each recorded in `metadata_json["resumes"]` (`resumed_from` / `resumed_as`). A worker asked to stop (SIGTERM) winds the turn down at an iteration boundary and hands the task back, re-queued at once; a task nobody works on is failed within `STALE_IN_PROCESS_RUN_SECONDS` (900 s), at once when its worker is known gone, and its work item claims are released in the same scheduler pass.

**Execution budget inheritance**: a task spawned **from an assignment run** inherits the parent run's budget - the assignment's effective `timeout_seconds` (carried in the execution payload; `0` / negative = no per-task deadline, bounded only by the reconciler's `worker_job_timeout` fallback) and the run's resolved `effective_max_iterations` (assignment override -> agent override -> platform default), forwarded to `run_agent_chat` as `max_iterations_override` (not floored). `resolve_sub_agent_timeout()` is the single source shared by the orchestration `deadline_at` (`create_sub_agent_task`) and the `asyncio.wait_for` bound (`_execute_sub_agent_task`). A task spawned **from chat** (no assignment scope) takes its wall-clock from the **target agent's** `max_iterations` through `resolve_chat_sub_agent_timeout()`, the formula of `run_agent_chat`: `chat_loop_timeout_seconds(iteration_reach(chat_loop_max_iterations(n)))` (`models/general_assistant_config.py`: at least `CHAT_MIN_LOOP_ITERATIONS` = 15 iterations, `CHAT_SECS_PER_ITERATION` = 120 s each, floor `CHAT_MIN_LOOP_TIMEOUT_SECONDS` = 1800 s; `iteration_reach` sizes it for the auto-extended iterations while `AGENT_LOOP_AUTO_EXTEND_ITERATIONS` is on). The execution's `deadline_at` bounds every attempt (`orchestration_engine.bound_by_deadline` / `deadline_spent` / `deadline_cut_budget`): a re-run or a late claim runs on what the deadline leaves (nothing left: it records its own timeout before it charges), the task's loop gets that bound minus a wrap-up reserve (`loop_wall_clock_deadline`, `run_agent_chat(wall_clock_deadline=...)`), a timeout that fired on the bound the deadline cut past the grace is credited back free through the attempt's receipt (`attempt_charges.task_receipt_token`), and a re-run of a task still `running` from a lost attempt keeps that attempt's recorded files and credits its charge back free (`attempt_charges.credit_lost_attempts`). See `dev-docs/FSM/05-failure-and-recovery.md`.

**Self-fan-out** (`settings.agent_self_fanout_enabled` for the platform AND the agent's own `allow_self_fanout`, both on by default, read together by ONE helper, `self_fanout_enabled(agent)` in `builtin_tools/handover.py`): an agent can spawn parallel background copies of **itself** by passing `agent_id="self"` (or its own id / slug) to `spawn_background_task`, even with no peer handover agents. Wired in both the chat path (`agent_chat.py`) and the assignment path (`assignment_engine.py`) via `build_sub_agent_tools(self_agent=..., allow_self_fanout=...)` and surfaced to the LLM by `format_self_fanout_prompt()`. In assignments the tools require a resolvable effective user (run owner, else the agent owner - `SubAgentTask.user_id` is a `users` FK). The cycle guard normally rejects `target == self`; the carve-out is offered **only at the top delegation level** (`delegation_depth == 0`, so a self-spawned worker cannot recurse; assignment runs are chain roots) and bounded by `max_concurrent_sub_agent_tasks_per_run` (5); `create_sub_agent_task(allow_self=True)` excuses **only** the direct `target == parent` case. **Quota**: each background task is a real autonomous work unit metered against the agentic execution quota (`run_agent_chat` with the default `meter_quota=True`); only nested consult / transfer handovers pass `meter_quota=False`. **Per-agent opt-out**: an agent whose owner turned `allow_self_fanout` off (Configuration > General > Agent Handover, `PUT /agents/{id}`, the agent-builder `update_agent`) is never offered itself as a target, in chat, assignment runs and flows; its peer handovers are untouched and the "Parallel self-execution" prompt block goes with it. The platform switch wins, a NULL reads as on, tasks already running finish, and the wait-budget continuation of a task (`_spawn_wait_budget_continuation`, the platform resuming a task that ran out of wait budget) is unaffected. Every copy of the agent carries the option (the four manifests of `models/agent_copy.py`): it narrows what the agent may do, so a copy that dropped it would turn self-fan-out back on.

On completion, a chat-originated task does not post a truncated extract into the thread when the parent will wake (`_should_deliver_completion_notice()`, `parent_wake.py`): the hidden wake prompt carries the full result (capped at 32k; longer results require `get_full_task_result`) and the parent's own answer is what the user sees. A leftover extract is posted only when the parent will not wake (no conversation, already woken, cancelled / delivery-suppressed, incomplete). An in-flight parent turn receives the wake as steering (and skips an in-flight `wait()`).

| `concierge/flow_lab_access.py` | The one access rule of every Flow Lab path, on the rows, by id or exact name: Platform Health within its supervision scope and consent (content audited), a person who may manage the flow or modify the assignment, sandbox copies the Flow Lab authored to Platform Health only. Its sandbox reach: a sandbox graph names only what its source flow or basis agent names. |
| `concierge/flow_comparison.py` | Flow Lab run comparison: two ended runs side by side - a flow run or an assignment run, status, final output, tokens, cost, duration and level 2's intercepted and simulated writes - and a deterministic verdict (`agree` / `disagree` / `both_failed` / `incomplete`, never agreement for a missing or unfinished side). |
| `concierge/flow_shadow.py` | Flow Lab shadows: the `flow_shadows` lifecycle and one scheduler step (`flow_shadow_tick`, step 9d) - pair each live run of the assignment with a run of the sandbox copy (`start_sandbox_flow_run(purpose="shadow", run_as_user_id=` the assignment's acting identity), waiting on Platform Health budget and licence gate; each run reserved on the shadow's own `flow_lab` cycle and charged when its pair settles, at most `MAX_PAIRS_PER_SHADOW` pairs; a run whose consent no longer holds or that its trigger did not start is `skipped`), compare the pairs, settle (`settle_decision`: enough pairs, success rate, agreement); a shadow retains its copy past its watch. With Platform Health off the take-over waits (given up at the deadline), the watch and its rollback still run. |
| `concierge/flow_switch_over.py` | A held `switch_over` shadow (B12): the production flow created from the copy only then, owned like the assignment, activated; the assignment paused `concierge_switch_over`; the watch (`watch_decision`: B18's failure spike and cost drift against the assignment's baseline) and the rollback (flow deactivated, assignment resumed unless an emergency stop holds it, both audited as `system:concierge`); a person's change during the watch is kept (`regression_kept`). |
| `concierge/flow_experiments.py` | The Flow Lab on level 6: the four flow change types on `register_experiment_kind` (both arms fresh sandbox copies of exactly the drafted graph, measured by level 4 with flows as subjects) and the `flow` finding rule (`register_target_access`); its findings and drafts are the Flow Lab agent's own writes (`record_flow_finding`, `draft_flow_variant`). |
| `concierge/flow_proposals.py` | The four flow proposal types on level 3: `flow_repair` / `flow_optimization` write a flow version and are watched live, `new_flow` creates a draft its manager activates, `agent_to_flow` starts the switch-over shadow on a fresh copy of the approved graph and owns its watch; loaded through `registry._HANDLER_MODULES`. |

| File | Purpose |
|------|---------|
| `concierge/diagnosis.py`, `concierge/findings.py`, `concierge/experiments.py`, `concierge/text_kinds.py`, `concierge/access.py` | Platform Health's Quality Analyst and Experimenter: quality signals from the stored run rollups and ratings, findings recorded once per pattern, experiments measured on sandbox copies and filed as improvement proposals, one access rule for every surface. Tools: `builtin_tools/health_quality.py`, `builtin_tools/health_experiments.py`. See `dev-docs/health-quality.md`. |

Design: `dev-docs/evaluations.md`; contract: `dev-docs/reference/evaluations.md`. |
| `evaluation_continuation.py` | State-safe primitives for asynchronous evaluation episodes (`ConversationContinuationService`, `process_resume_episode`, `timeout_waiting_episodes`). |
| `evaluation/` | The evaluation module's parts: launch checks (`launch.py`), settings, the reuse fingerprint, headline aggregation, metric rows, output extraction (`extraction/`), run ownership, run search, tags, placebo, and `metric_package/`, the only importer of `app/evaluation_metrics`. |
| `evaluation_placebo.py` | Placebo-controlled evaluation (`dev-docs/agent-placebo-evaluation.md`): `PlaceboConfig` and the execution-mode rule (`placebo_mode_error`) the evaluation's write paths apply, and `build_placebo` - neutral text from `app/evaluations/placebo_corpus/` in the original's language, free of its distinctive words, matched in length by a `LengthMeasurer`, rebuilt identically from its seed. |
| `evaluation_comparison.py` | Deterministic comparison of two runs of one evaluation: per metric, candidate minus baseline on the 0-100 scale, read against `NOISE_MARGIN_POINTS`. |
| `improvement_proposals/` | Improvement proposals: file (dedup key, one open change per target, an agent states its measurement or `unmeasured`), approve / reject (the target's managers, no admin bypass on a private target; approving writes a new version through the type's handler, `registry`), watch and settle (the re-evaluation's verdict, live watchers, the watch window; a regression rolls back as a new version while the change is still in force; `set_proposal_status` for a handler that owns its watch). | `persona_improvement.py` | The `persona` type of the improvement proposals, the human-approved persona self-improvement loop: propose (a rewrite from the latest baseline run's weakest cases and the human feedback), approve / reject (someone who may manage the agent; approval writes a persona version and queues one candidate run), settle (the scheduler compares the candidate's quality score with the baseline's through `evaluation_comparison`; a regression rolls the persona back as a new version while the loop's version is still active). |
| `annotations.py` | Rating agent work: one registry resolves every rateable `(target_type, target_id)` (chat message, run result, background task, delegation answer, agent-account answer) under the same read rule as the target's own detail endpoint; upsert / delete, the agent feedback summary, Langfuse forwarding. |
| `feedback_criteria.py` | Feedback criteria: the one place that validates a criterion and a score, normalizes it to [0, 1] and computes a rating's weighted score; used by the REST API, the rating endpoints and `annotations.py`. |
| `reaction_feedback.py` | Reactions as feedback: an emoji on an agent's answer is a rating; the setting (`ReactionFeedbackConfig`), emoji normalization, the keyed rater digest (`rater_ref`) and `apply_reactions`, for every platform. |
