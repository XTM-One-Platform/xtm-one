# Services: files and knowledge bases

Service map rows for attachment reading, file access, storage and serving, widget uploads, the knowledge-base pipeline (chunking, embedding, sync, search) and worksets in `backend/app/services/`; the binding rules live in `backend/app/services/AGENTS.md`.

| `attachment_extract.py` | The ONE reader of data-bearing ATTACHMENTS - HTML, JSON, JSON Lines, CSV: what the model gets for such a file on every surface. `extract_attachment_text()` (the entry point; `*_async` runs it on the parse executor, and a rendering is memoised per content hash - thread-safe LRU - because the inline fallback re-reads every attachment of the history on every turn) dispatches on `attachment_kind()` (extension first, then the MIME type, so `application/vnd.api+json` under `.bin` is JSON) after `decode_attachment_text()` (BOM, then the DECLARED charset - the MIME type's `charset`, then for HTML only the page's `<meta>` / `http-equiv`, a text codec only - then strict UTF-8, then cp1252: bytes can be valid UTF-8 and still not BE UTF-8, a BOM-less UTF-16 file first; JSON / JSON Lines read UTF-8 FIRST (`utf8_first`: RFC 8259 gives the JSON media type no `charset` a compliant reader honours, so a UTF-8 file served as `iso-8859-1` stays its characters; UTF-16 / UTF-32 without a BOM - valid UTF-8 too when its text is ASCII - is recognised by `json.detect_encoding` from the NUL in its first two bytes, which UTF-8 JSON never holds, declared or not); an offset means the same characters on every surface, a non-UTF-8 export included). The memo key is everything a rendering reads (`_render_key()`: kind, extension, the whole MIME type, the bytes). HTML: `render_html_attachment()` - ONE streaming pass on the stdlib `html.parser` (no tree, no ancestor walk, no recursion - linear in the input whatever the nesting, an unclosed `<td>` run or a row of empty cells), the rendered text in reading order with scripts, styles, SVG geometry and canvases stripped and accounted for in one line, table cells as pipe rows with `\|` escaped, only the `hidden` attribute hiding (`until-found` stays); the page's DATA leads (`## Embedded data`, before `## Page text`, so a cap never cuts it): every JSON `<script>` AND every JavaScript data literal of a script (`const ROWS = [...]`, `window.X = {...}`, `Object.freeze(...)`, `JSON.parse('...')`, a bare literal) found by a linear possessive-regex tokenizer (identifiers, strings, comments, template literals, regex literals read as ONE token each; brackets counted in one pass; a literal parsed from its exact slice, normalised from JavaScript to JSON under a total budget - bare keys, single quotes, trailing commas, `undefined`), numbered in document order (`query_file_json(block=)`), summarised largest first. `summarize_json()` renders against its budget (it stops emitting at the cap instead of rendering the tree and cutting), records as one compact line each plus field statistics (`// N records`, distinct values, numeric min / max / sum overflow-safe), numeric / geo payloads folded to their shape; `dump_json_bounded()` stops the encoder at its bound. JSON Lines line by line, split on `\n` only (`JSONL_MAX_RECORDS` lines): `$[i]` is line i+1 of the file on every surface (rendering, line report, query, counts) - a line holding no value, invalid or blank, keeps its slot as a `JsonlPlaceholder` (`<invalid line N>` / `<blank line N>`, never data: the statistics skip it; the records-or-values decision and the field statistics read ONE sample of the values, `_stats_sample()`, and a summary whose head holds only placeholders names the first line holding a value with its `$[i]`) and only the end of the text is trimmed; every JSON parse - a document, a data block, the JSON Lines records together - is capped at `JSON_PARSE_MAX_CHARS` (parsed objects weigh up to ~25x the text; past it the text is reported, never parsed); a CSV header's repeated and blank names are made unique around every name the file uses (`_unique_columns()`: a real `amount_2` keeps its name, and a row wider than its header is keyed on the same terms) so no column overwrites another; a large CSV leads with `digest_csv_text()` (dialect sniffed, grouped numbers coerced, rows counted up to `CSV_MAX_ROWS` while only the `STATS_SAMPLE_ROWS` x 64-column statistics sample is held) ahead of its text, under a header that says whether it read the whole file. Every result says what it did NOT read: a sampled statistic, a capped count, a data block past `MAX_EMBEDDED_BLOCKS`, a query over a partial block (`EmbeddedJson.partial`, placed where no cut reaches it - never a bare "No value matches"), a page ending inside an unclosed element (an unclosed `<title>` - RCDATA - is recovered from what the tokenizer still holds, the source, never from the decoded RCDATA: the title runs to the first tag, after any text read before an end tag the tokenizer could not finish, and the page after it is re-read as written), a rendering that failed and fell back. `query_json()` / `run_query()` is a JSONPath subset (`$.a.b[0]`, `['k']`, `[1:3]`, `[*]`, `..key`; filters refused with the forms named) evaluated as lazily chained steps with NO per-step working set (a cap turned `$[*].b` into a false "No value matches" whenever the one `b` sat past it) under ONE `QUERY_VISIT_BUDGET` per `query_file_json` call, shared across the blocks it queries (`$..a..b` is quadratic on a nested document, and a file of 64 blocks must not buy 64 budgets), and the result says "More than N" at its cap, names a search the budget cut short with the budget it ran under (`QueryOutcome.more` / `.exhausted` / `.visit_budget`) and says "not searched" for a block reached after it ran out; `run_json_query()` validates `block` and `path` up front. Every rendering and query result is UTF-8-encodable (`_encodable()`: a `\ud83d` escape parses to a lone surrogate the HTTP client, the LLM SDK and the database all refuse; a `JSON.parse('...')` string's `\ud83d\ude00` escape pair stays the one character it is), a decimal character reference `int()` may refuse (more than 640 digits - `sys.int_info.str_digits_check_threshold`, the floor of any `sys.set_int_max_str_digits()` - which raised out of the whole page) never reaches the tokenizer: `_HtmlReader.feed` holds it out - as its index between two noncharacters the page does not carry (`_absent_pair()`; only a page carrying 65 of the 66 gets each reference's short form in place instead) - and puts back, in the same single pass and before any text rule of the reader, its value where the tokenizer decodes (text, RCDATA, attribute values - leading zeros dropped, U+FFFD past the last code point, whatever limit the process set) and the reference itself in raw text, so a `<script>` body stays data byte for byte, and the `<title>` heading the rendering is clipped (`_TITLE_MAX_CHARS`) so it cannot push the page past the inline cap. `inline_truncation_footer()` is the ONE footer of a capped inline attachment: the cut, "do not page", the offset in the rendered view and, only when the reader has the code interpreter, the exact sandbox mount path - its `code_interpreter` argument is required and the renderings / `run_json_query` take the same flag (part of the memo key): inside a loop it is `code_interpreter_offered(offered_tools())`, the surface `run_agent_loop` binds for its run, the upload message decides from the conversation's agent or General Assistant tools, and a caller that cannot know names nothing. Used by the LLM inline fallback (`file_resolver._extract_fallback`), the chat upload message (both through `inline_attachment_text()`, the rule of `extract_inline_attachment_text()` cut at the cap: a file whose plain extraction fits the inline cap is inlined as that extraction, whole, as it always was - an empty one, an archive the extractor reads as nothing, as the size stub - and only one the cap would cut is rendered; the upload hands the rule its own extraction, `plain_text`, so a file is read once), `read_file_content(mode="extract_structured")` and `query_file_json`, every call off the event loop. KB ingestion keeps `chunking.extract_text_from_file` (the source) by default: rendering there would change every HTML document's embedding on its next re-embed, so rendering is a per-knowledge-base opt-in (`html_ingestion = "rendered"`) resolved by `kb_embedding_text.py`. Never re-spell an HTML-to-text pass, a JSON summary or a CSV digest in a tool. |

## Workset counters and concurrent writers

`Workset.item_count` (live items: every status but `evicted`), `evicted_count` and `content_chars` (the content of the live items) are what Operations > Worksets shows and what `_eviction_plan` checks `max_items` and `max_content_chars` against. They are moved in Python, so every item write in `add_item` (create, revision, metadata re-add) first takes the workset row lock with `_lock_for_write` (`SELECT ... FOR UPDATE`, `populate_existing`): the eviction plan, the evictions, the insert and the counter moves of one write run under the lock on the committed values (the sealed or resolved refusal is checked again there, so a seal that lands while a write waits is honoured), and two writers to one workset (parallel tool calls, overlapping runs, `to_workset`) queue instead of losing an update. The lock is held to the caller's commit; workset before items is the order the processing worker locks in. A correction of an evicted item counts it live again. Alembic revision `w12165wscnt1` recomputed the three counters from `workset_items` once for the worksets written before the lock (`reconcile_in_batches`, batched, idempotent); a later drift is a bug of the write path, not something to reconcile again.

## Ingesting a tool result into the workset (`to_workset`)

While an agent holds the `workset` built-in tool, the workset executor sets `CompositeToolExecutor.workset_ingestor` through `on_composite` (not for an anonymous caller). `all_tools` then adds a `to_workset` argument (`WORKSET_INGEST_SCHEMA`) to every tool that is not a write by its name (`offers_workset_ingest`: the shared classifier's positive evidence only, as the loop breaker's `_is_named_write`, so an MCP `cases` qualifies and `create_*` or `get_or_create_*` never does; the `workset_*` tools are left out). `_dispatch` strips the argument, runs the tool, and hands its full result, before the loop's size cap, to `builtin_tools/workset.py`, which splits it (`workset_split.py`), calls `add_item` per item in one transaction (`extra_metadata.ingested_from` names the tool), queues each stored item after the commit, and returns a receipt in place of the content: counts (added, unchanged, revised, updated, not stored), items left out, undated items, items keyed by a digest, the first references, the text outside the items (the preamble, or the values next to a JSON list; fenced, as data) and the coverage line. Every third-party value in it is flattened to one line. A failed call is returned unchanged; a failed split stores nothing and says why; a `WorksetSourceError` is said in its own words; `to_workset` with `workspace_path` runs nothing. A `to_workset` call is the workset's write (`WORKSET_INGEST_WRITE_TOOL`, `workset_add_item`) on every path: `execute_tool` and `screen_for_approval` also pass it through the approval gate as that tool, `fit_descriptions_to_surface` withdraws the argument from a surface that no longer offers that tool (`withdraw_workset_ingest`: a deny list, a per-function scope), and `_dispatch` refuses it on such a surface. The per-tool schema (`WORKSET_INGEST_SCHEMA`) is names and types only, since every read tool carries it on every turn; how to fill it (`WORKSET_INGEST_GUIDE`) is on `workset_add_item` alone. Tests: `tests/test_workset_split.py`, `tests/test_to_workset_dispatch.py`, `tests/test_workset_tools_postgres.py`.

People's records never enter a corpus whole: a read tool whose result is people's records declares `ToolDefinition.personal_records=True` (HubSpot contacts, SES contacts, Drata personnel today), the dispatcher passes it to `WorksetIngestor.ingest`, and `_ingest` replaces each item's content with a reference line (`as_personal_reference`: the tool and the item's `external_ref`), keeping its title, ref and link; the receipt says so. A new provider tool returning people's records sets the property. The record is read again from the source tool by its reference.

A chat corpus is one per agent, person and workspace (`chat_workset_key`). An agent whose `config.workset_chat_scope` is `"conversation"` (the `FIMI Analyst`) gets one per conversation instead: personal (`is_company_managed=False`) whatever the agent's tier, created without an owner agent (`owns_corpus=False`, so `retier_agent_worksets` never moves it), and expiring `CONVERSATION_WORKSET_TTL` (30 days) after its last use (`expires_after`, a sliding retention every call renews; purged by the retention sweep). A flow node's binding always wins.

Implicit worksets (`Workset.implicit`, `build_workset_tools(implicit=True)`): the corpus the runtime derives itself, an agent's chat corpus with no flow binding (`agent_chat.py`) and the assignment corpus `assignment-<id>` (`assignment_engine.py`). `resolve_workset(implicit=True)` renews its idle expiry on every resolve (`workset_implicit_idle_days`, default 30; the sweep then purges it like any expired workset), and an ingest (`ingest=True`: `workset_add_item`, `to_workset`) into a resolved or sealed generation retires that row under `<key>~<id12>` (resolved, kept for the retention window) and creates a fresh generation under the key; a summary or priority write never rotates. Its `max_auto_calls` is a rolling budget: `auto_calls_used` counts the window opened at `auto_calls_window_started_at`, reset by `roll_budget_window` (one conditional UPDATE) once older than `workset_implicit_budget_window_hours` (default 24; 0 = lifetime). A new item that would need an automatic call on a spent budget is answered by `add_item` at write time: stored with `AddOutcome.warning` (`spent_budget_message`: the replenish time and how to summarise by hand) on an implicit and an explicit workset alike, never refused, since a `to_workset` diversion cannot retry or pass a summary and a refusal dropped the tool result (#2206); the `to_workset` receipt names the items whose summary waits; an explicit workset's lifetime ceiling is unchanged; `Coverage.auto_budget_resets_at` puts the time in every read. `workset_resolve` is offered only on an implicit binding. Sealed and resolved EXPLICIT worksets are guarded on their own write path.
