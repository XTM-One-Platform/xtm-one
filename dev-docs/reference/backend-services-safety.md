# Services: audit and prompt safety

Service map rows for audit logging, prompt guards (Nova), untrusted-content quarantine, tool-result screening, HITL consent, the approval whitelist and standing approvals, URL guarding, API keys and MFA, security options and the Security Audit, and resource exposure in `backend/app/services/`; the binding rules live in `backend/app/services/AGENTS.md`.

## Service map

| File | Purpose |
|------|---------|
| `audit.py` | Audit logging: `log_audit()` records user actions across all API routes (CRUD, config changes, auth events); `log_system_audit()` an action the platform took on its own, under a `system:<component>` actor anchored on the user it concerns; `log_security_event()` a security event of a raw user id - a caller passing `system_actor` + `anchor_agent_id` keeps the event of a user deleted meanwhile (a UUID naming no account) as a `log_system_audit()` row anchored on the agent's owner with `details["acting_user_id"]`, and a WARNING naming the ids when the agent has no owner (the Nova chat check and memory-write screen do) |
| `hitl_consent.py` | The HITL consent contract behind every escalated irreversible action: `hitl_history_approves()` decides whether a run's `human_input_history` approves one action code, read through `integration_tools._make_hitl_approval_fn`. Fail closed: a reply approves the code right after `APPROVE` or nothing - a second code without its own `APPROVE` right after the first approval (an `M-` code; a bare hex token such as a date, a ticket or a git hash is not one), a strike-through, a symbol outside the short list that cannot say no (check marks, OK, a thumbs up, sign-off and signature symbols - a list of refusal symbols is never complete), anything before the keyword but whitespace, Markdown and quote marks, a quoted phrase followed by more, or a bidi control approves nothing, a question does not void a reply, approvals back to back (`APPROVE <A>, APPROVE <B>`) approve each code, and the latest reply naming a code wins. Never re-spell the reply parsing in a tool, and keep the behaviour here, not in prompt text. |
| `nova_engine.py` / `nova_guard.py` / `nova_matching.py` | Nova prompt-safety rules: `nova_engine.evaluate_prompt()` is the one entry (full engine when `nova-hunting` is installed, the `nova_guard` keyword tier otherwise); the embedding / LLM pre-computation runs on the event loop, the CPU part - parsing each rule and running its matcher - in `nova_matching`'s worker process (CPython's `re` holds the GIL for a whole match, so a thread could not free the loop). Each rule gets `rule_budget_seconds()` (2 s + 5 s per million characters) of the worker's CPU time (`core/cpu_time.process_cpu_clock`, read by pid; wall-clock where the platform cannot read it), with a wall-clock backstop at `RULE_WALL_CLOCK_BACKSTOP_FACTOR` times it for a worker the host does not run; a rule past it, or one the worker dies on, is cut by killing the worker, skipped for that input and logged with its label and the input length (never the content), and the other rules still decide with their inline verdicts. No worker available: the same matching in-process on the parse pool, with a WARNING. `nova_matching` is imported by the spawned worker and stays stdlib + `nova_guard` (`test_the_worker_module_stays_light`). Each rule is evaluated once per input, deduplicated by id across the platform rules and the per-run ones; an `llm:` verdict is judged and kept per condition and temperature (`llm_verdict_key`: Nova passes the pattern's threshold as `temperature=`). A `semantics:` score is mapped onto the `all-MiniLM-L6-v2` scale the community thresholds were written in through `nova_calibration.calibrate_score()`: every entry there is a measurement of `scripts/calibrate_nova_semantics.py` on `nova_calibration_set.json`, recording the set version it was measured on (`tests/test_nova_calibration.py` pins the set's content to its version); a model without one is scored raw and reported (engine status, the rule's `has_semantics` badge, the Security Audit), never re-scaled on a guess. `nova_guard.parse_rule` refuses a pattern value outside 0-1, naming what it means per tier |
| `prompt_guard.py` | Pattern-based prompt-injection detection (`scan_user_input`: flags, never blocks) and the trailing security anchor of every system prompt: `SAFETY_SYSTEM_PROMPT`, `build_security_policy(include_identity=...)` (adds the anti-impersonation clause), `insert_before_safety_anchor()` (late blocks go BEFORE the anchor; used by `agent_chat`, `general_chat`, `assignment_engine`) |
| `prompt_guards.py` | The connected prompt guard's verdict (Nova, while its company-managed integration is connected): `evaluate_text(text, *, surface, user_id, timeout)` is the ONE way to ask it and takes NO session - it opens a short-lived one of its own for the connection-state lookup and the evaluation, statement-scoped (`core/database.StatementScopedSession`: a pooled connection only while a statement runs, never while the engine waits on an embedding or a model), bounded (`GUARD_EVALUATION_TIMEOUT_SECS`, 60 s), fail-open (a guard that raises or times out is skipped and logged), because a bound that cancels a guard statement aborts the transaction of the session it ran on, which failed the request when it was the request's. "No guard connected" is kept for `CONNECTION_STATE_TTL_SECONDS` (5 s), so such a turn opens no session; a connected guard is looked up on every evaluation, so disconnecting applies at once. `guard_chat_message(db, message, ...)` is the chat-message check of agent chat, the General Assistant and the public widget: the verdict, the `security_alert` audit on the caller's session (never touched by the evaluation) and the refusal; with `anchor_agent_id` (agent chat) the match of a user deleted mid-turn is kept under `system:nova_guard`, anchored on the agent's owner. `enforce=True` (agent chat) refuses a `block` rule's match with the entry's `action` the rule's; `enforce=False` (the General Assistant and the widget unless `PROMPT_GUARD_BLOCK_GENERAL_ASSISTANT` / `PROMPT_GUARD_BLOCK_PUBLIC_WIDGET`, security options) audits `rule_action` + `action: allowed` and lets the message through; a writer with no account is audited through `log_system_audit` as `system:nova_guard`, anchored on `audit_anchor_user_id` (the widget's admin), since `log_security_event` drops an entry with no user. `guard_model_output(text, *, streamed, ...)` (`PROMPT_GUARD_MODEL_OUTPUT` = `off` default / `log` / `block`, a security option) is the answer's check, called on the final text of a top-level turn - `run_agent_chat` when `meter_quota` and not `evaluation_mode` (its main return and its transfer return), `run_general_chat` (and its transfer), the widget turn, the extension endpoint (it meters itself): `off` evaluates nothing; `log` returns the text at once and evaluates it in a background task (strong reference in `_output_tasks`, `MODEL_OUTPUT_CONCURRENCY` per loop, `MODEL_OUTPUT_BACKLOG` per process, `MODEL_OUTPUT_TIMEOUT_SECS`, first `MODEL_OUTPUT_MAX_CHARS`); `block` evaluates an answer delivered whole before returning it and returns `MODEL_OUTPUT_WITHHELD_MESSAGE` for a `block` rule's match, while a `streamed` answer (the caller passed `on_token`) has already left and is handled as in `log`. The audit is written on a session of its own (`surface: model_output`, `streamed`), as the guard anchored on the admin when there is no account. Write-tool arguments are not a surface yet. Never hand a request session to a guard or call `nova_engine.evaluate_prompt` from a caller; the one exception is the memory-write screen (`builtin_tools/memory.py`), which runs after the write on a `StatementScopedSession` of its own |
| `content_safety.py` | Untrusted-content quarantine ("spotlighting"): `wrap_untrusted()` wraps external content (webhook/integration_event trigger payloads, web_fetch results, the channel thread / group chat backfill `agent_chat` puts in the system prompt, the member-typed channel metadata, and the file names and `annotate_file` notes of the system prompt's Available Files block - `FileContext.to_prompt_section(quarantine=True)` from `agent_chat` and `general_chat`) in `<<UNTRUSTED-...>>` blocks with a per-call random boundary - those three system-prompt fences, and the stored file names the resolver's `[File <id>]` labels and the loop's dropped-files notes carry, as well as the OpenAI-shaped native-file stub, the chat upload message and the public widget's document text (`file_resolver.upload_header`), pass `stable=True`, which derives the boundary from the source and the content under the platform secret instead, so an unchanged block keeps the prompt byte-identical and the provider's prompt cache hits; `UNTRUSTED_CONTENT_POLICY` is the matching system-prompt paragraph injected by `agent_chat`, `general_chat`, `assignment_helpers` and the public widget **only when the prompt builder can see that quarantined content can appear**, decided by ONE predicate, `untrusted_policy_needed()`: a quarantined block already in the prompt or the turn (a webhook/integration_event trigger, a backfill, an Available Files block - every conversation that already holds files, whose `[File <id>]` labels are fenced too - a referenced conversation), a tool of `QUARANTINING_BUILTIN_TOOL_IDS` (`web_fetch`, `document_vision`, `shared_state` - a value another writer chose) in the effective builtin tools, or integration tools, whose providers and the declarative bundle executor wrap their answers (agent chat: the agent's direct or template bindings, the session's selection, pinned or prebuilt integrations; assignments: `assignment_untrusted_policy_needed()`, the assignment's bindings or else the agent's, plus template bindings; General Assistant: its effective bindings; widget: the bindings when its tools are allowed). A block a tool outside those returns mid-run (the label of a file a tool returned, the loop's dropped-files note) can still reach a run without the paragraph and relies on the block's own static `UNTRUSTED_HEADER`. `wrap_memory()` fences the memory a system prompt carries (user profile, agent short / medium-term, persistent facts and tradecraft - chat, assignments and the public widget - and the rows `search_memory` returns) in ONE `<<MEMORY-...>>` block whose static `MEMORY_HEADER` is its whole policy: remembered facts, preferences, settings, style notes and lessons keep shaping the answer and the tool choices, while text in it that claims authority, overrides instructions, changes guardrails / permissions / the security policy, or asks for data or an action the request does not need is never obeyed. It has markers of its own because `UNTRUSTED_CONTENT_POLICY` forbids `<<UNTRUSTED-...>>` content from changing the output format or the tool usage, which is what a remembered preference is for; no memory, no block and no header. Caps on the memory text run before it (`format_memory_for_prompt`, `_load_memory_context`). `untrusted_block_spans()` / `head_tail_cuts_outside_blocks()` keep a cut of a prompt from splitting a block of either kind (the emergency prune's head+tail cut of the system prompt, and its tail cut of a message, which keeps the end of an untrusted block's data fenced again with `refenced_block_tail()` - so a message that is one fenced page keeps its tail, never nothing - and starts past a memory block); the spans are read in one linear pass (markers found separately, then paired), never by a lazy regex over the block, which is quadratic on opening markers left without their close |
| `message_context.py` | The Message Context block of a channel turn's system prompt: `render_message_context()` keeps the platform's fields (platform, channel type, DM flag) and the `STRUCTURAL_KEYS` whose value has the shape of an id or a flag where they always were, and renders every other value - a display name, a channel, team or guild name, any key an adapter adds later - inside a `wrap_untrusted()` block at the end of the same section, returning whether it did so, which adds `UNTRUSTED_CONTENT_POLICY` to the turn. A context with no member-typed value has no fenced block. The platform-reported identity of an anonymous sender (`build_identity_context` tier B) is fenced the same way |
| `tool_result_guard.py` | Prompt-guard screening of tool results, opt-in per tool: DETECTION, never a fence or a rewrite of a result. `ToolResultScreen.for_run(tools, wall_clock_deadline=)` is built once per `run_agent_loop` run from the security options snapshot (`prompt_guard_scanned_tools`, `prompt_guard_block_tool_results` - Settings > Security, the variable first) and is `None` when the scope is empty (the default), so the loop does exactly what it did before the option existed: no connection check, no session, no task. `covers(name)` matches the registered name, the `base_name` of a renamed multi-instance tool, and for a custom tool (`source` `custom:...`) `custom:<entity_id>` - custom tools are listed by id, so a rename needs no settings write and takes no lock, and a deleted one's entry is shown stale in the editor for the admin to remove. `screen()` (one call) and `screen_batch()` (a parallel batch, BEFORE its duplicate mirrors and the cache) evaluate what the model reads - the result's text through the loop's own truncation, then the text of its non-image attachments read by the providers' reader (`file_resolver._extract_fallback`, memoised per content hash) - through `prompt_guards.evaluate_text` (surface `tool_result`), skipping everything while `known_unconnected()`. Default: the evaluation runs in a background task (strong references, `MAX_PENDING_BACKGROUND` backlog, the next model call never waits) and a match is only a WARNING line plus a `security_alert` audit on a session of its own, attributed to the user the model resolution bound (`llm.identity`; none bound = the log line only), details `source` / `surface` / `tool` / `rules` / `categories` / `rule_action` / `action` / `blocked`. Blocking on: the verdict is awaited before the append - a parallel batch's screened results in ONE gather under the slots, never one after the other and never in a second pass - and a `block` rule replaces the result by `WITHHELD_RESULT_TEMPLATE` (files dropped, flags kept, never cached, mirrored by its batch duplicates), audited `blocked: true`. Every evaluation is bounded (`TOOL_RESULT_EVALUATION_TIMEOUT_SECS`, slot wait and attachment reading included, capped by the run's wall-clock deadline), holds one of `MAX_CONCURRENT_EVALUATIONS` per-loop slots and fails open. The scope editor's candidates are `GET /settings/security-options/scannable-tools` (admin only: built-ins, custom tools by id with their current name, MCP and integration tools); the Security Audit reports log-only screening while a guard is connected (`agents.tool_result_guard_log_only`) |
| `url_guard.py` | Platform URL validation and auto-correction: `guard_urls()` post-processes FINAL assistant responses — detects OpenCTI/OpenAEV deep links (markdown, raw, relative `/dashboard/...`), validates route segments against `OPENCTI_ROUTE_MANIFEST`, auto-corrects hallucinated segments via `CORRECTION_RULES` + reverse-lookup + singular/plural rules, rewrites unverifiable UUID-bearing links to the universal `/dashboard/id/<uuid>` resolver, and degrades the rest to a search link or plain text. `collect_base_urls_from_integrations()` derives the known platform origins from bound integrations; `finalize_platform_links()` is the one entry point of the answer pipelines (agent chat, General Assistant, assignment results, mid-turn segments): links on a bound platform's internal URL are moved onto its registered URL outside code spans (`collect_platform_link_bases()`), then `guard_urls()` runs. Pure CPU, no network, fail-open, gated by `URL_GUARD_ENABLED`; manifest extensible via `URL_GUARD_MANIFEST_PATH` JSON. **No-prompt-inflation principle**: this service exists precisely so output-quality fixes are deterministic code — it must never grow a system-prompt counterpart. Used by `agent_chat`, `general_chat`, and `assignment_engine`. |
| `nova_calibration.py` | Semantic-threshold calibration of the Nova rules per embedding model: `calibrate_score()` maps a model's similarity onto the `all-MiniLM-L6-v2` scale the community thresholds were written in; the measurements live in `nova_calibration_set.json` (versioned, pinned by `tests/test_nova_calibration.py`). |
| `nova_rule_sync.py` | Syncs `.nov` rules from a GitHub repository into company-managed `NovaRule`s (row-driven like KB sync sources): `sync_nova_rule_source` upserts and prunes, `process_scheduled_nova_syncs` runs the due sources; `served_sync_error` says what a reader may see of a failure. |
| `hitl_whitelist.py` | The effective HITL whitelist, computed, never materialised: `effective = ((shipped_default \| platform_reads) - admin_removals) \| admin_additions`, so a release replaces the default while an admin's removal survives it (`resolve_whitelist`, `set_override` / `clear_override`); the approval gate (`build_approval_gate`, fail-closed when it cannot be read; the platform kill switch `platform_settings.tool_approvals_enabled` is read first by `resolve_platform_kill_switch` and is absolute: off, the gate is a recording gate alone (`OUTCOME_APPROVALS_DISABLED`) and nothing pauses, always-ask tools included; otherwise an agent that does not ask (`hitl_enabled` false: its `approve_tool_calls` false, or NULL under an install default that is off, or a bot marked uninterrupted) gets `make_ungated_gate`, which pauses nothing and stamps nothing (approval is opt-in, always-ask tools included; the trail names the agent's switch through `resolve_log_outcome`), and every gate it or a run installs for an agent that asks goes through `make_always_ask_gate`, which pauses a call setting its tool's `ToolDefinition.always_ask_argument`, or any call of a tool declaring `ToolDefinition.always_ask`, whatever the whitelist, exemptions, standing approvals or the user's allow-all say; the proposal of such a call carries `always_asks: true`), `agent_asks` (the agent's `approve_tool_calls`, else the install default). |
| `hitl_whitelist_default.py` | The HITL whitelist shipped with the product: data, reviewed as data - a name added here runs without approval on every deployment that did not override it. |
| `hitl_whitelist_platform.py` | The registered Suite platforms' read tools, exempt from approval by default: derived from `tool_classification`, never enumerated. |
| `hitl_whitelist_derived.py` | The same read-derived exemption for the rest of what a deployment connected: its integrations and bound MCP servers, scoped to what is connected (`connected_read_tools`). |
| `tool_approval_service.py` | Standing approvals ("Yes, always"): a user preference that follows its owner across their runs, never visible to or usable by another user, keyed on a fingerprint of the tool's input schema so a changed tool asks again (`grant_exception`, `revoke_exception`, `invalidate_stale_approvals`). Each approval records the tool it was granted to (`tool_source`, `tool_entity_id`): `approval.standing_approval_covers` covers a custom tool only by its own `custom:<id>`, an MCP server's tool only by an approval granted on the same server id (the product's own `read_mcp_resource`, which has no server, by an approval with no id and the same source), and a product tool by name unless the approval was granted to an MCP or custom tool. |
| `tool_approval_usage.py` | Whether approvals are in use and which agents ask (`load_approval_usage`, `approvals_in_use`), read by every screen that labels a tool "Asks first", the profile and the Security Audit; advisory, decides no call. |
| `api_key_access.py` | Personal API keys (`fcp-...`): one resolution (`resolve_api_key`: prefix lookup then bcrypt; revoked, expired or deactivated owner = 401, uncovered surface = 403) for every surface that accepts one (the REST API, the LLM proxy, the MCP endpoints; `API_KEY_SURFACE_SITES` in `tests/test_api_key_access.py`), then the key's own rate limit and quota; scope checks (`enforce_rest_scope`, `require_agent_run`, `require_model_access`, ...) and lifetime limits. |
| `api_key_notices.py` | Notifications to a personal API key's owner: revoked, and expiring `EXPIRY_NOTICE_DAYS` (7, then 1) before - a scheduler scan at most once per `NOTICE_INTERVAL_SECONDS` install-wide, each notice sent once per key (`expiry_notified_days`). |
| `mfa.py` | TOTP two-factor authentication (RFC 6238, SHA-1 / 6 digits / 30 s for authenticator compatibility): secrets encrypted at rest (`encrypt_secret`), recovery codes, the challenge token between password and code. |
| `token_store.py` | Invitation and password-reset tokens: short-lived, single-use, in Redis with a TTL, keyed by the SHA-256 of the raw token (returned once at creation). An invitation may carry a `destination` (a registered platform and a path, `platform_access_notices.py`); `reissue_invitation()` sends a pending one again under a new token (the old link stops working, one pending invitation per email), valid for the longer of what it had left and the lifetime asked, moved by one Lua script (`REISSUE_INVITATION_LUA`) so it is never lost between the two keys and of two concurrent reissues one wins; `invitation_link()` is the one `/register?token=` URL. |
| `security_options.py` | The database half of the security options: `refresh_security_options_cache` publishes the stored values to the per-process snapshot (`app/core/security_options.py` holds the registry and the resolver), refreshed by `run_security_options_refresh_loop` in every web and worker process; `update_security_options`. |
| `security_audit_finding_states.py` | What the platform remembers about a Security Audit finding: dismissal (an admin may accept a `critical` / `warning` / `info` finding the current run reports, audited; it leaves every count and is never notified), reopening on escalation, the notification memory. |
| `security_audit_notifications.py` | Notifies active administrators of `critical` and `warning` findings once each: the scheduler asks `notify_new_findings_if_due`, a Redis lease runs the audit at most once per `NOTIFY_INTERVAL_SECONDS` (1 h) install-wide in the background. |
| `csp_reports.py` | Content-Security-Policy violation reports: parsed in both report formats, scrubbed (query strings, fragments and user info dropped, blocked resources reduced to their origin), counted and logged, never stored. |
| `registered_platform_origins.py` | The origins of the registered platforms (OpenCTI, OpenAEV, OpenCRQ) allowed to frame the platform under an enforced CSP (`frame-ancestors`): a per-process snapshot, primed at startup, refreshed after a registration change and every `REFRESH_SECONDS` (300). |
| `resource_exposure.py` | The one exposure engine: who can use a resource a person lends (an integration credential, an MCP server and its secrets, a custom tool, a channel bot, a variable, an attached knowledge base, skill or prompt) and through what - direct sharing and every entity that carries it (agents, assignments, widgets, A2A partners, the platform MCP key); `resource_exposure`, `exposure_summaries`, `preview_change`. |
| `pii_redactor.py` | Regex PII and secret redaction (`redact_pii`, `RedactionConfig`: email, IP, phone, card, SSN, ...) applied to text written to external systems (GitHub issues). |
