# Services: integrations

Service map rows for integration tools, credentials and sharing, read-only bindings, event polling and push receivers, OAuth (integrations and MCP), vault secrets, agent accounts, email and outbound message formatting in `backend/app/services/`; the binding rules live in `backend/app/services/AGENTS.md`.

## Service map

| File | Purpose |
|------|---------|
| `integration_tools.py` | Generates `ToolDefinition` + executor pairs from integration and channel bot bindings (e.g. email, calendar, drive, Slack, Teams tools). Supports `channel_bot_mode` for standalone channel bot tool resolution. |
| `integration_read_only.py` | Read-only integration bindings: parses `Agent.integration_read_only` and `Agent.integration_template_read_only` (provider keys of template bindings), `read_only_integration_ids(agent, resolved_bindings)` for the context key `READ_ONLY_CONTEXT_KEY` every agent run hands `build_integration_tools`, and `withhold_write_tools()`, which drops a read-only binding's write tools (the `tool_classification` reading) and refuses them by name. Contract in `dev-docs/reference/integrations-and-knowledge-bases.md`. |
| `event_poller.py` | Integration event polling: checks for new emails, messages, etc. on connected services. Every polled event is queued through `trigger_or_queue_assignment`: a poll reads up to `_MAX_PAGES_PER_POLL` pages oldest first, a full queue hands the rest back, and the poll is stamped (waiting its `POLL_INTERVALS`) only once it caught up, so a backlog is never paced by the poll interval. Graph writes a mail's `receivedDateTime` to the second but filters on its sub-second value, so a Microsoft mail page that fills one second (or would leave the cursor on the second it holds) reads that second whole (`_read_mail_second`) and moves the cursor past it (`_past_second`). A trigger's integration the run's acting user cannot see is still polled and delivered, and flagged (`trigger_integration_access.py`). `give_back_polled_event()` un-consumes an event a poll could not dispatch (out of the seen set - an assignment's sorted set through `release_seen`, a flow's plain set - and the provider cursor put back), so it fires once on a later poll - shared by the refused and full-queue paths and the flow poller (`flow_triggers`), never re-spelled. Microsoft also polls `new_teams_reply` (the latest 50 threads of each channel with `$expand=replies`), `new_teams_chat_message` (the listed `chat_ids`, else the chats whose last message is new), `calendar_event_changed` (`/me/events` by `lastModifiedDateTime`, `change_kind` created / updated / cancelled) and `email_flag_changed` (mail modified after the cursor whose flag status changed, `flag_changes`); these start from now. Their payload builders (`teams_reply_payload`, `teams_chat_payload`, `calendar_event_payload`, `flag_change_payload`, `microsoft_mail_payload`) are shared with the Graph notifications, and `advance_event_cursor` moves the poll cursor on every notified event so a lapsed subscription polls on from there. An assignment whose Graph subscription is active is skipped unless a `missed` lifecycle notification asked for one catch-up read. |
| `integration_event_filters.py` | The one module for `trigger_config.filter`: which polled or notified events create a run at all, evaluated before the run and before any gate (`event_filter_reason`). Mail: `from` allow / deny lists of addresses or domains, `to_me` / `cc_me` (against the mailbox owner's addresses, `event_poller.mailbox_addresses`), `subject_contains`, `exclude_automated` (Auto-Submitted, bulk Precedence, mailing-list and auto-response-suppress headers, `multipart/report`, a null return path, a calendar response, a conventional no-reply sender), `from_contains`; Teams: `channels` / `scope`, `chat_ids`, `exclude_authors`; calendar `change_kinds`; flags `flag_status`; every other event (the webhook-delivered ones, applied by `api/v1/webhooks.py`) the generic `payload_filter_reason`: each key a payload field, a dotted path reaching a nested one (a literal dotted key wins), an object recursing, a list any of; `scope` and `channels` are read-side keys it skips. What only the filter reads (recipients, headers, the resource type) rides under `FILTER_SIGNALS_KEY` and is removed before the run (`without_filter_signals`); a trigger with no filter gets the payload it always had. A dropped event stays in the seen set and is counted (`record_filtered_events` -> `Assignment.events_filtered_count`). |
| `graph_event_subscriptions.py` | Microsoft Graph change-notification subscriptions for `integration_event` assignments: `subscription_plan` (mail `me/mailFolders('<folder or inbox>')/messages`, flags the same resource on `updated`, `me/events`, one per selected Teams channel or chat), `public_notification_url` (`BASE_URL` on public https and `INTEGRATION_EVENT_GRAPH_SUBSCRIPTIONS_ENABLED`), `maintain_graph_event_subscriptions` (the scheduler tick, every 2 minutes under a Redis lock: create with a random clientState through `store_graph_subscription`, renew under a day before expiry, retire what is no longer wanted). The `graph_sub_wf:<id>` record lives as long as the subscriptions and makes the poller skip the assignment; a refusal (`graph_sub_fail:<id>`, retried after an hour), removal or lapse hands it back to polling. `handle_lifecycle_notification` (reauthorization renews, removal resumes polling, `missed` asks the poller for one catch-up read), `notified_event` (the notification's resource read back into the poller's payload for every event type), `delivery_mode` (what `get_assignment` shows). |
| `teams_chat_posts.py` | The Teams chat messages an assignment's run posted (`record_teams_chat_post`, `is_agent_teams_chat_post`), through the `agent_posts` store, so a `new_teams_chat_message` assignment never runs on its own reply. |
| `trigger_integration_access.py` | Whether a run's acting user can see the integration its events come from: the acting user of an assignment (`run_as_user_id`, owner, agent owner) or a flow (owner) is checked against the trigger's integration - an event for a user who cannot see it is delivered all the same (nothing is withheld at run time) with a rate-limited WARNING (`log_unseen_trigger_integration()`) and a security-audit warning (`assignment_trigger_visibility()` / `flow_trigger_visibility()`); owner-less company-managed assignments keep the OAuth gate alone. A KB sync source bound to an integration syncs through it as bound, scheduled or "Sync now", and a configuring user (else the KB's owner) who cannot see it is reported the same way (`log_unseen_sync_source_integration()`, `sync_source_integration_visibility()`) |
| `token_refresh.py` | OAuth token refresh: periodically refreshes expiring tokens for OAuth integrations. One classifier (`permanent_refresh_failure_reason`) and one back-off key (`refresh_cooldown_key`) are shared with the chat-time refresh (`integration_tools._try_inline_refresh`). A dead grant or rejected client credentials (the classifier's terminal set, pinned table-for-table by `tests/test_token_refresh_reauthorize_contract.py`) mark the integration `reauthorize`, and that is TERMINAL until a new authorization: neither refresh path calls its token endpoint again, editing its client secret, token URL or scopes (REST or agent builder) leaves it marked and retries nothing, a new client ID is a new OAuth app (`integration_state.replace_oauth_client_id()`: its tokens are dropped and it waits in `configured`, which no refresh selects either), the connection test refuses it, and only the OAuth callback / GitHub App install writes `connected` back. By design there is no automatic retry, no long back-off retry of `reauthorize` rows and no clear-on-credential-update; transient answers (network, malformed, 5xx, 429, other 4xx, unexplained 401 / 403, AADSTS outside a 400) only back off, and a 2xx is a refresh only when `usable_token_answer` finds an access token in it (`read_token_answer`, on all three paths): without one it is malformed, and one carrying an OAuth `error` backs off like an unexplained 401 / 403, except the refusals GitHub and Slack send inside a 2xx, which are the same verdicts: a dead refresh token (GitHub `bad_refresh_token`, Slack `invalid_refresh_token`) or rejected client credentials (GitHub `incorrect_client_credentials`, Slack `invalid_client_id` / `bad_client_secret`), matched on the exact `error` value, JSON or form-encoded, on a 2xx without an access token only (`_DEAD_REFRESH_TOKEN_CODES_INSIDE_A_SUCCESS` / `_REJECTED_CLIENT_CODES_INSIDE_A_SUCCESS`, pinned); every other code there (Slack `ratelimited`, `internal_error`, ...) stays retryable, and a non-JSON error body names an RFC code only as a whole word (`invalid_client_id` is not `invalid_client`). MCP servers have no `reauthorize` state (permanent, inside a 2xx or not, or 401 / 403: 1 h back-off); a transient MCP failure (network, 5xx, 429, malformed) backs off for half the token's remaining lifetime, between 30 s and 15 min (`mcp_transient_refresh_cooldown`), so a short-lived token is retried before it expires. The sweep refreshes an MCP token once half its lifetime (`token_issued_at`, stamped with the expiry by `apply_mcp_token_expiry`, to `token_expires_at`) has passed, never later than 15 min before its expiry and never sooner than 2 min after it was received (`mcp_refresh_due_at`); a token stored without `token_issued_at` is refreshed 15 min ahead, and a server that is not due is neither refreshed nor locked. Both paths take the per-integration Redis lock (a holder token, released by an atomic compare-and-delete), refresh from the row as stored under it on a session of their own (never from a row read earlier: Atlassian rotates the refresh token and answers a spent one like a dead grant), and commit before releasing it. Every outcome (new tokens, `reauthorize`, `error`) is applied right after `lock_stored_tokens` row-locks the row in the committing transaction and finds the tokens the refresh started from (`stored_tokens`), so neither a re-authorization (which takes no refresh lock) nor a refresh that outlived its Redis lock is ever overwritten. The sweep refreshes an MCP server (the only path that does) the same way under a lock of its own (`mcp_refresh_lock_id`: `token_refresh:mcp:<id>`), applying an outcome after `lock_stored_mcp_tokens` finds the tokens it started from on a server still `connected` / `error` (discarding a dynamic client disconnects it but keeps them); the tick's final commit never carries a refresh outcome. A back-off (`start_refresh_cooldown` / `refresh_cooling_down`) names the refresh token it was learned from and holds back only that token (a bare `"1"` holds back any), so one a stale refresh starts after a re-authorization never applies to the new grant; re-authorization also clears it (`clear_refresh_cooldown`) and always writes `connected`. |
| `email_html.py` | Email body normalization (platform-side, single source of truth): `markdown_to_email_html()` converts agent-authored Markdown / HTML / plain text into a sanitized, inline-styled HTML fragment (GFM tables, emphasis, links) so reports render in Outlook instead of showing literal `\|` / `*` / `[]` characters; `build_graph_email_body()` returns a Microsoft Graph message `body` dict that is **always** `contentType: HTML`. Detects already-HTML bodies (idempotent, never double-converted), sanitizes via `nh3` (allow-list, strips scripts / handlers / unsafe URLs), and injects Outlook-friendly inline styles on `table` / `th` / `td` / `a`. Used by the Microsoft `send_microsoft_email` + `create_microsoft_draft_email` tools, and by `create_microsoft_draft_reply` for `content_type` `html` / `markdown`. `starts_as_html_markup()` tells a body written as HTML (opens with a tag, closes one) from text that mentions a tag. |
| `integrations/providers/microsoft/_send_confirm.py` | An Outlook send (`send_microsoft_email`, `send_microsoft_draft`, `reply_microsoft_email_in_thread`, `forward_microsoft_email`) answered by a Graph 5xx, a timeout or a transport failure is never retried: `_settle_send` in `mail.py` reads Sent Items (since the send started, minus `WINDOW_SKEW_SECONDS`, after each of `READ_DELAYS_SECONDS`) and `find_sent_copy` matches the copy by `internetMessageId`, else by subject and To / Cc. A copy found counts the send as made (recorded, logged, guarded) and the answer names it; none answers "NOT sent"; an unreadable Sent Items answers "Send state UNKNOWN". A 4xx, a 429 or a connection never opened is answered as it is (`is_ambiguous_send_error`). #11848. |
| `teams_format.py` | Teams message normalization (platform-side, single source of truth): `markdown_to_teams_html()` / `build_graph_chat_body()` for Graph `chatMessage` HTML, `markdown_to_teams_text()` for Bot Framework `text`. Autolinks bare and backtick-wrapped `https://` URLs so they render as clickable `<a>` (Python-Markdown does not; a backtick-wrapped URL otherwise lands as unclickable `<code>`). Fenced code, existing Markdown links, and live `<a>` / remaining `<code>` / `<pre>` are left alone. `build_graph_chat_body(mention_texts=)` writes a message's `<at id="N">` mention tags AFTER the conversion (the sanitizer drops `<at>`): where the body places `<at id="N">...</at>`, else on a first line of their own; a marker naming no mention, a mention placed twice or lost by the conversion raises `MentionPlacementError`. Before either conversion, `_normalize_markdown_blocks()` puts a blank line before and after every list, table, heading and fence, turns a one-line `Lead: - a - b` run into a list and decodes `&nbsp;` / `&amp;` outside code, so a list written straight under its sentence renders one item per line. The Graph HTML path passes a body through as agent HTML only when it carries a block tag outside code AND no Markdown layout (`_looks_like_markdown_document()`: a heading, a list item, a bold lead-in line or a GFM table on a line without `<`); a Markdown reply naming `<p>` or `<li>` in prose is converted, never sent raw and collapsed into one paragraph. A block tag whose opening and closing counts do not balance outside code (one `<li>` named in a sentence) is escaped to text before conversion (`_escape_unbalanced_block_tags()`), and such names alone never make a body HTML unless it opens with a tag: left live, nh3 closed that `<li>` at the end and Teams showed the rest of the message inside one bullet. Used by every Microsoft Graph and Teams bot send/edit path; the inbound side reads a chatMessage body with `_teams_body_text()` (`integrations/providers/microsoft/_teams.py`), which keeps its lines and decodes entities. |
| `integration_credentials.py` | Who may use an integration's stored OAuth token: anyone but the owner needs the owner's consent (`oauth_share_acknowledged`, recorded by `apply_oauth_share_consent` when the integration is shared); the opt-out stores `credential_mode = "per_user"` (everyone else authorizes their own account, `integration_user_credentials.py`). `oauth_credentials_usable_clause()` / `oauth_credentials_usable()` are the gate the tools and pollers apply; `resolve_session_integration_bindings` / `visible_integration_ids` / `integration_ids_writer_cannot_see` the visibility reads. What a chat turn says about what it withheld: see `backend-services-chat.md`. |
| `integration_user_credentials.py` | Each person's own account on a `per_user` OAuth integration: the one answer to which row holds the credential used for a person (`resolve_token_holder`), loading a holder back from its reference, and a person's credential writes. Contract: `dev-docs/integration-user-credentials.md`. |
| `integration_state.py` | Shared definitions of integration state: `replace_oauth_client_id()` (a new OAuth app drops the tokens), `uses_admin_oauth_app()`, `api_key_binding_of()`. |
| `integration_exposure.py` | The integration-only exposure routes (`GET /integrations/{id}/exposure`, `/integrations/exposure/summary`, `POST /integrations/exposure/preview`) in their legacy field names, computed by `resource_exposure.py`; `lent_personal_credentials` for the Security Audit. Writes nothing. |
| `integration_bundle_manager.py` | Integration bundle ZIP import / export: metadata-driven tool declarations with optional declarative HTTP execution specs (`declarative_http_executor.py`), archive and metadata validation, OAuth endpoint checks, checksum on export. |
| `integration_notification_auth.py` | Sender authentication for the shared notification receivers, before anything is read or run: Slack (`check_slack_delivery`: the `X-Slack-Signature` HMAC keyed with the signing secret of the app that sent it, per integration) and Microsoft Graph (`clientState` per subscription, `store_graph_subscription`, `graph_notification_assignments`); `admin_app_scoping_required()` / `verification_required()`. |
| `docusign_connect.py` | DocuSign Connect, the real-time path of the DocuSign envelope events: `verify_connect_signature` (`X-DocuSign-Signature-<n>`, base64 HMAC-SHA256 under any `connect_hmac_key`, fail-closed), `connect_events` (the poll's payloads from the delivery's envelope summary, same `message_id`), `dispatch_connect_delivery` (the assignments reading the integration by the poll's rule, `connect_assignments`; each payload claimed in the seen set the poll shares with `claim_seen`, released for the poll when it cannot run now; a delivery older than `SEEN_SET_TTL_SECONDS` ignored). |
| `slack_events.py` | Scoped dispatch of real-time Slack message events to `new_slack_message` assignments: an integration receives an event only for its own workspace / installation, and each assignment runs once per message (`claim_message` / `claim_seen`); `dispatch_slack_message`. |
| `github_echo.py` | Self-action echo suppression for GitHub webhooks: a GitHub write tool records `(integration, repo, number)` for `SELF_ACTION_TTL_SECONDS` (`record_self_action`), and the receiver skips the matching event for assignments with `ignore_self_triggered_events` (`was_self_action`). |
| `github_token_installations.py` | Which GitHub App installations an integration's own token sees: under "Require verified integration notifications" an admin-app event reaches an integration only when its token sees the event's installation (`GET /user/installations`, cached; `installation_reach`, `settle`). |
| `mcp_oauth_discovery.py` | Outbound MCP OAuth (client side): authorization server discovery from the resource, RFC 7591 dynamic client registration, PKCE (`discover_oauth_endpoints`, `register_dynamic_client`, `ensure_mcp_oauth_client`, `generate_pkce_pair`); the platform-as-authorization-server side is `api/v1/mcp_oauth.py`. |
| `mcp_oauth_tokens.py` | `StoredMCPOAuthToken`, the `httpx.Auth` hook of the MCP transports: sets the current stored token on every request, refreshes it ahead of expiry and on a `401` (one replay), so a run outlives a short-lived token. |
| `mcp_oauth_clients.py` | Who a client of the platform's MCP authorization server is: a registered `mcp-...` client (Dynamic Client Registration or an A2A partner) or a Client ID Metadata Document URL (`resolve_client_metadata`, fetched and validated, refusals cached); `redirect_uri_allowed`. |
| `vault/` | Secrets read from enterprise vaults (providers `aws`, `azure`, `gcp`, `hashicorp`): a secret field holds a value or a `vault://<provider>/<path>#<key>` reference, and code that uses a secret reads it ONLY through `reveal_field` / `reveal_ciphertext` / `reveal_json_field` (`tests/test_vault_secret_readers.py` fails the build on a bypass); an unresolvable reference raises `SecretUnavailableError` with a generic message. |
| `agent_accounts/` | Agent accounts: an agent operating a real user account of a messaging platform - `events`, `rules` (the rule engine, presets, listening plan, AI label), `conversation`, `state` (Redis), `pipeline` (message to answer, approvals included), `management` (the one writer of an account's configuration, for the REST routes and the agent tools), `listening`, `triage`, `reactions`, `activity`, `problems`, `teams_mentions` (a Teams reply's `@Full Name`, `@email` or unique `@Firstname` of a member becomes a real mention before it is posted; unknown or ambiguous names stay text, the outcome recorded under `origin.delivery` of the reply), and `providers/` (the platform interface and its implementations). Contract: `dev-docs/reference/agent-accounts.md`. |
| `email.py` | Transactional email over SMTP (`send_email` / `deliver_email` in a worker thread; `False` when SMTP is unconfigured or the send fails, each caller owning its fallback) and the platform's email templates (`render_email`, `invitation_email`, `password_reset_email`, `access_granted_email`, `platform_invitation_email`). |
| `email_signatures.py` | Email signatures read from a signature integration: a provider registers how it reads one (`register_signature_source`), a provider whose tools send email registers as a sender (`register_email_sender`), and the agent-account mailbox and every sender's mail tools read it through `read_signature`, the one reader. A sender's tools sign through a `MailSigner` built from the builder kwargs `signature_fn` and `signature_plan` (a `SignaturePlan`: on / off, the signature integration, why none). |
| `email_signature_settings.py` | Which signature an email-sending integration's tools add: `plan_signatures()` resolves it per sending integration when the tools are built - the agent's binding override (`Agent.integration_signatures`), else the integration's Email signature setting (`signature_enabled`, `signature_integration_id`), else on; an unset signature integration is the single one bound alongside, else the single one the acting person may use, else none (logged, and the plan's `missing` says how to set one). The write checks of the integrations and agents REST routes and of the agent builder live here. Read views: `api/v1/email_signatures.py`. |
