# Models: adding a model, conventions and the company-managed pattern

The step-by-step recipe for a new model or a new `Agent` column, the company-managed pattern and the model conventions in full; the rules for changing models live in `backend/app/models/AGENTS.md`.

## How to Add a New Model

### Step 1: Create the model file

```python
# backend/app/models/my_model.py

import uuid
from datetime import UTC, datetime

from sqlalchemy import DateTime, ForeignKey, String
from sqlalchemy.dialects.postgresql import UUID
from sqlalchemy.orm import Mapped, mapped_column

from app.core.database import Base


class MyModel(Base):
    __tablename__ = "my_models"

    id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    # A strictly per-user record: NOT NULL. A shareable / company-managed
    # model declares `Mapped[uuid.UUID | None]` with `nullable=True` instead.
    user_id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True
    )
    name: Mapped[str] = mapped_column(String(255), nullable=False)
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), default=lambda: datetime.now(UTC)
    )
```

### Step 2: Register the model

Add a single import line, in alphabetical order, to **`app/models/__init__.py`** — the
centralized model registry. The app, SAQ worker, and Alembic all import from here:

```python
import app.models.my_model
```

Then **run the migration**:
   ```bash
   cd backend
   uv run python -m alembic -c alembic/alembic.ini revision --autogenerate -m "add my_models table"
   uv run python -m alembic -c alembic/alembic.ini upgrade head
   ```

> **MANDATORY: harden the autogenerated migration before committing.** `--autogenerate`
> emits raw `op.create_table` / `op.add_column` / `op.create_index` that are NOT idempotent
> and can take heavy locks - unsafe for the multi-replica auto-migrate-on-startup path. Every
> migration MUST be idempotent and lock-safe per **`dev-docs/reference/migrations-safety.md`**: rewrite adds as `op.execute("... ADD COLUMN IF NOT EXISTS ...")`, build indexes
> with `create_index_in_place()` (`app.core.migration_ddl`) inside
> `op.get_context().autocommit_block()` - never `CONCURRENTLY`, which hangs the rollout - keep a SINGLE Alembic head, prefer constant-default `ADD COLUMN` (metadata-only), and avoid
> table rewrites / `SET NOT NULL` on large tables / unbounded backfills. Verify with
> `uv run python -m pytest tests/test_migration_integrity.py`.

## Company-Managed Pattern

The shareable entities are the members of the `CompanyManagedEntity` union in
`app/api/v1/helpers.py`, the single list: every helper that filters or toggles
visibility is typed against it. Each declares the full column set
(`is_company_managed`, `shared_group_ids`, `shared_group_permissions`, `shared_user_ids`,
`shared_user_permissions`, `access_restricted`). A new model can inherit the full set
from the `VisibilityColumns` mixin (`app/models/visibility.py`), as `BrowserProfile`
and `VideoProject` do, rather than re-spelling it: a partial set is a 500 for the
first non-admin user, since `user_visible_filter` reads every column.

Entity visibility is three-tier: **own + shared (groups and individual users, each grant
`read_only` / `config` / `config_with_chats`) + company-managed**; the full rules are in
`dev-docs/reference/entities.md` ("Entity Visibility & Permissions").

When `is_company_managed = True`:
- Shared with all users; the flag alone decides visibility
- `user_id` keeps the owner (the creator, or the admin picked by `resolve_company_managed_owner_id`)
- Only admins can edit

When `is_company_managed = False`:
- `user_id` points to the owning user
- Visible to the owner and to the users and groups it is shared with

## Conventions

- Every model has a UUID `id` primary key (auto-generated)
- A shareable or company-managed model has a nullable `user_id` FK (NULL only on legacy rows,
  which the startup seed backfills, or for system-managed rows); a strictly per-user record (API key, tool approval preference, arcade
  score, ...) declares it `nullable=False`
- All timestamps use `DateTime(timezone=True)` with UTC defaults (`datetime.now(UTC)`)
- Use `Mapped[]` annotations (SQLAlchemy 2.0 style)
- Encrypted fields end with `_enc` suffix (e.g., `access_token_enc`)
- JSON blobs use `postgresql.JSON` type
- Vector columns use `pgvector.sqlalchemy.Vector()` to support configured embedding dimensions

## Adding a column to `Agent` or `Assignment`

`app/models/agent_copy.py` holds the field manifests that decide which columns
travel when an agent is copied:

- in place (`POST /agents/{id}/duplicate`): `AGENT_COPY_FIELDS` / `AGENT_COPY_SKIP_FIELDS`;
- across instances (export bundle → import): `AGENT_BUNDLE_PORTABLE_FIELDS` /
  `AGENT_BUNDLE_EXPORT_ONLY_FIELDS` / `AGENT_BUNDLE_SKIP_FIELDS`;
- a Filigran AI Catalog "Add to my account" clone: `AGENT_CATALOG_CLONE_FIELDS` /
  `AGENT_CATALOG_CLONE_SKIP_FIELDS`;
- the assignments that ride along (a new `Assignment` column): `ASSIGNMENT_COPY_FIELDS` /
  `ASSIGNMENT_COPY_SKIP_FIELDS` and `ASSIGNMENT_CATALOG_CLONE_FIELDS` /
  `ASSIGNMENT_CATALOG_CLONE_SKIP_FIELDS`.

Every mapped column must appear in one bucket of each manifest, and
`tests/test_agent_copy_manifest.py` fails until it does, so a new column cannot be
silently dropped by a copy. Copying is the right default; the skip lists are
for identities, secrets, sharing grants, activation state and references that only
resolve on the source instance. The public catalog download is the opposite, an
allow-list (`PUBLIC_DOWNLOAD_AGENT_FIELDS` / `PUBLIC_DOWNLOAD_ASSIGNMENT_FIELDS`): a new
column is not published until it is added there.
