# Services: agents, platform settings, runners and relays

Service map rows for agent configuration rules, versioning and portability, variables, workspaces, provisioning and branding, LLM provider management, CTEM metrics, XTM Hub registration, the arcade, and the machine-side services (runners, XTM One Desktop, relays) in `backend/app/services/`; the binding rules live in `backend/app/services/AGENTS.md`.

## Agents

| File | Purpose |
|------|---------|
| `agent_bindings.py` | What an agent may bind, applied by every write surface (the agents REST API and the agent-builder tool alike): handover targets (`sanitize_handover_config`, `validate_handover_conditions`), bindings (`validate_personal_agent_bindings`: a personal agent binds only what its owner can see; `validate_company_managed_bindings`: a company-managed agent binds only company-managed resources), channels (`validate_channel_config`, `derive_available_channel_types`), and what the bindings become when the tier changes (`strip_personal_bindings`, `revert_company_managed_to_private`). |
| `agent_bundle_projection.py` | An agent's export bundle (`build_agent_export_bundle`) and the ONE projection a reader who cannot manage the agent gets (`build_reader_agent_bundle`: the Filigran AI Catalog download and `GET /agents/{id}/export` by a read-only reader): internal ids dropped or redacted, credentials masked, personal custom tools omitted. |
| `agentschema/` | Agent portable formats - the native XTM One bundle and Microsoft AgentSchema (`spec`, `detect`, `mapping`, `corrections`): `prepare_agent_import` (parse, detect, verify; persists nothing), `build_agentschema_export`, `portability_report`. |
| `agent_config_versioning.py` | Versions of an agent's tracked config fields: create / list / get, diff, rollback (as a new forward version), versions pinned by evaluation runs. |
| `prompt_versioning.py` | Prompt and agent-persona versions, the model the other versioning services mirror: every edit writes a version under a row lock on the parent, the active version is the highest number, a rollback is a new forward version; versions pinned by evaluation runs are reported. |
| `agent_version_snapshots.py` | The persona, prompt, config-field and skill versions an agent runs on now (`resolve_agent_version_snapshots`), pinned by an evaluation run so it can be replayed on exactly what it measured. |
| `agent_template_skills.py` | The skills an agent created from a template starts with: a template names built-in skills by slug (`slug:<slug>` tag), resolved per caller through `user_visible_filter`, so a default never makes agent creation fail. |
| `agent_wizard_assistant.py` | The agent wizard's assistant (behind `AGENT_WIZARD_ASSIST`): one round of the request, the draft and the conversation to the caller's model with what the wizard offers THIS caller; the answer is a patch checked against that offer (refusals sent back once, then left out and said). Stores nothing. Design: `dev-docs/agent-wizard-assistant.md`. |
| `variable_resolver.py` | Variables: `{{var_id.UUID}}` placeholders substituted at run time in personas, guardrails, assignment prompts, skills, prompts and custom tool code (`load_variables`, `substitute_variables`); a reference names one variable by id (no key shadowing) and resolves only when the current user can see it; `restore_secrets_in_history`. |

## Platform settings and administration

| File | Purpose |
|------|---------|
| `workspaces.py` | Workspaces: unique slug per owner and exactly one default workspace per user under races (partial unique indexes, retry to the winner's row; no reader assumes the count, so were the invariant broken the oldest default is read and promoting a workspace clears every current default), and every workspace rule (default neither archived, deleted nor company-managed; a company-managed workspace nobody's default; work items block a delete; an archived workspace takes no conversation; only a visible KB is bound), raised as `WorkspaceActionRefusedError` for the REST routes and the agent-builder tools alike. |
| `provisioning.py` | Provisioning the built-in AI content: `provision_builtin_content` (the ordered `seed_builtin_*` steps), `wire_default_agents` (links the CTEM Assistant as the General Assistant only while no administrator chose the link, `linked_agent_configured`), `provision_env_providers`; run at boot and when an administrator turns AI on at runtime. The order matters. |
| `branding.py` | Platform branding (name, logo, description, theme colours, favicon, social preview) from `platform_settings`, decoupled from `PLATFORM_MODE`: every user-visible text and asset comes through `get_branding(db)` (async, source of truth) or the cached sync accessor; the branded `index.html` and web manifest. |
| `llm_provider_management.py` | `ensure_llm_provider_management_allowed`: with `MODELS_ENV_PROVIDING_ONLY` the environment is the only source of LLM providers (every provider mutation asks first); `BYOLLM_ACTIVATED=true` wins over it (`settings.provider_management_env_only`). |
| `llm_provider_deletion.py` | What deleting an LLM provider config does to every route that used it, computed once for the Settings confirmation (`GET /settings/llm-providers/{id}/deletion-impact`) and the delete: the platform default and General Assistant models move to ONE replacement config pinned by id, the image default to a config that can serve images, the embedding default is cleared, never switched (`compute_deletion_impact`, `apply_deletion_impact`). |
| `integration_llm_provider.py` | The one mechanism by which an integration feeds a platform LLM provider (`IntegrationFeed`: which integration provider feeds which LLM provider, why it may not, what the config stores): `link_refusal`, `create_linked_provider`, `adopt_provider`, `unlink_provider`, `merged_context_windows`. |
| `lmstudio_llm_provider.py` | The LM Studio feed: a company-managed integration routed through a relay group with a server URL; the config stores no credential; `IntegrationRelayTransport` / `resolve_target` read the integration through the config on every request (30 s per process, `forget_target` on edit, unlink, delete) and refuse with a non-retried 424; `on_update` unlinks a config whose integration went private. |
| `openrouter_llm_provider.py` | The platform OpenRouter LLM provider fed by a company-managed OpenRouter integration: create one from its key or adopt an existing one (`LLMProviderConfig.source_integration_id`), key copied again on every edit (a vault reference as the reference), models saved through the one Settings update path; `unlink_provider`. |
| `model_catalog_announcements.py` | Tells a platform's users when its env-managed model catalog changes: the change is recorded at the env seed (`model_catalog_watch`, under `bootstrap_lock()`), net changes are folded, a queued change waits for the catalog to settle (`MODEL_CATALOG_EMAILS_SETTLE_MINUTES`), and the scheduler emails the users (`deliver_pending_announcements`). |
| `ai_metrics_collector.py` | Hourly aggregation of the platform's own agentic AI usage into `ai_adoption_metrics` (`collect_all_metrics` runs `collect_platform_metrics`). The GitHub Copilot and Cursor collectors were removed in #11380. |
| `platform_insights/` | The `platform_insights` built-in suite's reads (`builtin_tools/platform_insights.py` builds the tools): LLM analytics through `tracing/breakdown.py` over the dashboard's read path (the dashboard's figures, caveats included; departments, attributed usage, the metric matrix, projections, comparisons and CSV export), the Admin Objects union counted and bucketed, the AI Adoption route functions trimmed to rows, the audit log (its reads audited once per window), an overview, and `render_chart`'s pivot. `scope.load_scope()` decides the platform (an administrator's agent, `agent_tool_admin_bypass`), a group manager's team (LLM analytics only) or the caller's own slice, and every result says which; `traces.py` lists the Traces and Sessions pages as rows, never their content, a manager's own slice only. Contract: `backend-shared-utilities.md`. |
| `group_managers.py` | Group managers: `managed_groups()`, `members_of()`, `team_member_clause()` (a team leaves the administrators out) and `team_scope()` (the ONE rule of which users a non-admin's LLM Analytics cover, 403 on a group they do not manage; traces and sessions stay an administrator's). Contract: `backend-shared-utilities.md`. |
| `platform_access_notices.py` | Access notices (`POST /api/v1/platform/access-notices`): `acting_platform()` is the active registration that signed the caller's cross-platform JWT, or `None` for a session, an API key or a gone registration; `notice_link()` puts a path checked by `NOTICE_PATH` on that registration's public URL (`RegisteredPlatform.public_url`), so the email never links off the platform. `may_invite()` is the one rule of who may have XTM One invite someone with no account (an administrator today); an invitation stores `invitation_destination()` and `registered_destination()` reads it back at registration against the registration as it stands; `notice_made()` tells a pending invitation a notice made (role `user`, with a destination), the only kind a notice reissues: any other pending one answers 409. Limits in the route, notices and invitations alike: 200 an hour per sender, 1,000 per platform (its registration identifier), 5 per recipient (user id, or email for an invitation). Contract for platforms: `dev-docs/cross-platform-identity.md`. |
| `platform_builds.py` | The builds the platform ran: recorded at startup (`record_running_build`), refreshed by the scheduler (`touch_running_build_if_due`), read as release windows by the platform insights tools; never backfilled. |
| `xtm_hub_registration.py` | XTM One's registration with the XTM Hub: the token is stored only once the Hub confirms it, encrypted and bound to that Hub and this platform id; an hourly heartbeat keeps it (`active`), marks it `lost_connectivity` (`inactive` or unreachable Hub) or forgets it (`not_found`), declaring the edition as its contract (`EE` / `CE`, `registration_contract()`). `auto_register()` registers a trial deployment with `XTM_HUB_DEFAULT_URL` under the token its deployer hands it (`autoRegisterPlatform`, the licence type as contract, `existing_users_count()` leaving out `ADMIN_EMAIL`), with the manual flow's upsert. |
| `arcade.py` | The waiting arcade: server-issued game sessions (one run per session), run validation against the server-measured time and the game's own scoring bounds (`validate_run`, `max_run_score`; a strong legitimate player is never refused), leaderboards, live players, profiles. |

## CTEM metrics

| File | Purpose |
|------|---------|
| `dashboard_layouts.py` | The dashboards each person builds on a grid of widgets, and the bounds of that grid: the CTEM command center (XTM One home, one layout per vertical in `users.ctem_dashboard_layouts`, `CTEM_DASHBOARD_WIDGETS`) and the Copilot dashboard (the home of a deployment that is not XTM One, `users.copilot_dashboard_layout`, `COPILOT_DASHBOARD_WIDGETS`), both written through `PUT /settings/preferences` and validated by `check_widget_ids` / `max_grid_row`; the frontend's `CTEM_WIDGETS` (`pages/xtm-one/ctem/dashboard-layout.ts`) and `COPILOT_WIDGETS` (`pages/dashboard/copilot-dashboard-layout.ts`) list the same ids with their default places. A widget a layout names neither in `items` nor in `hidden` shows at its default size below the others, so a new widget needs no data migration |
| `ctem_posture_inputs.py` | The organization profile inputs the CTEM posture build reads (typed software and Software entities, asset rows and groups, by the fields the reachability rules read) and their fingerprint (`posture_inputs_stamp`): the cached posture's `profile_version` stamp, so a save, import or sync that leaves those inputs as they were (Owned domains, a description, the policy) keeps the cached posture fresh. The asset records are read on the page the build reads (the first `PROFILE_ASSET_CAP` by `(name_key, id)`), so the read stays bounded and a record beyond the cap never moves the stamp. A field the build starts reading is declared here; `tests/test_ctem_posture_inputs.py` fails otherwise. |
| `ctem_metrics_collector.py` | CTEM facts gathered live, per user (`build_posture_for_user`, behind `/api/v1/ctem-metrics` with a short Redis cache): every OpenCTI / OpenAEV call authenticated with a short-lived per-user JWT, so each query returns what that user may see; no service token stored. Vertical-aware (cyber / FIMI / fraud). |
| `ctem_scoring.py` | Pure CTEM scoring (no I/O): per-stage sub-scores and the composite Exposure Posture Score over the five stages, from the collector's facts (`score_stage`, `compute_posture`). |
| `ctem_verticals.py` | The one registry of CTEM verticals (cyber, FIMI / disinformation, fraud): per stage, the products that feed it, its weight and its methodology; read by the collector, the scorer and the API. |

## Runners, XTM One Desktop and relays

| File | Purpose |
|------|---------|
| `runners.py` | Runner service, the single source of truth the API router, the transport and the agent tools agree on: credential generation and hashing, the online signal (`last_seen_at` recency, correct across replicas), the per-command authorization gate (`authorize_command`: `permission_mode`, capability allow-list, shell / path scoping), serialization. Does not import `app.api.deps`. |
| `runner_transport.py` | Runner command dispatch: a WebSocket fast path (the replica holding the socket claims and pushes at once), cross-replica wake-ups and result wake-ups over Redis pub/sub, durable `RunnerCommand` rows as the backstop (`dispatch_command`, `claim_next_command`, `submit_result`, `await_result`); `give_up_on_command` (the emergency stop's path), `sweep_stale_runners`. |
| `runner_activity.py` | Machine activity as the chat shows it: one record per runner command (`RunnerActivity`), reported live through the tool progress channel and persisted with the message, so a reload, a relayed stream and a shared viewer show the same cards; records sanitized and bounded. |
| `runner_flow_events.py` | Runner happenings on the flow event bus: three seeded event types - "Runner command completed", "Runner online", "Runner offline" - emitted at the runner lifecycle chokepoints, so a flow can react; the runner transport is unchanged. |
| `desktop_login.py` | Browser sign-in for XTM One Desktop: the app, authenticated with its runner credential, opens a pending login, the person signs in in the SYSTEM browser (SSO works there), and the app collects the session (`start_login`, `complete_login`, `consume_login`). |
| `desktop_session.py` | A chat turn sent from XTM One Desktop: `desktop_runner_id` resolved per turn against the calling user's runner visibility (`load_desktop_context`; an invisible runner is dropped silently and the turn runs as plain chat), and the machine tools guaranteed on the turn (`ensure_desktop_tools`). |
| `relays.py` | Relay service, the single source of truth of the relay API router, the transport and the routing surfaces: `relays_active`, credentials and enrollment, the online signal, the destination pattern grammar shared with `apps/relay/src/policy.rs` (`normalize_destination_patterns`, `destination_allowed`), the egress route of an integration or MCP server, and which resources a group routes. Design: `dev-docs/relays.md`. |
| `relay_transport.py` | The XTM One Relay bus: a routed request is an encrypted `open` frame on the group's Redis stream, claimed by ONE connected relay of the group (load balancing and high availability) and answered frame by frame on a per-request stream; frames are `[u32 BE header length][JSON header][payload]`, Fernet-encrypted in Redis. |
