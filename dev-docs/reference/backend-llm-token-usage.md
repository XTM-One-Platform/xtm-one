# LLM token usage and stream usage capture

The usage dict each provider returns, how it is priced and counted, and how a stream that never ends still records its usage (`StreamUsageSink`); the rules of this area live in `backend/app/llm/AGENTS.md`.

## Token usage per provider

Every provider hands back the call's token usage as a plain dict: `ChatResponse.usage`, or `last_usage` once a `chat_stream()` generator is exhausted (the agent loop's `_streaming_chat` reads a missing one as `{}`). The run budget (`RunBudget.record_llm_usage` in `app/tools/run_budget.py`), the trace store and the Langfuse normalizer (`_normalize_usage`) all read that dict, so a token a provider leaves out of it is never priced. The keys keep each vendor's own convention; what the readers expect of them:

- `price_usage` (`services/tracing/cost_calculator.py`) is the one pricing rule: the run budget debits it and the trace store prices through its per-bucket form, `calculate_costs`. It prices `input_tokens` / `prompt_tokens` at the input rate, `output_tokens` / `completion_tokens` at the output rate, and cached tokens at the price row's cache rates (at the input rate when the row has none), in one of two conventions. A cache bucket (`cache_read_input_tokens` / `cache_creation_input_tokens`) is ADDED to the input count, so it belongs in the dict only when the input count leaves those tokens out, or they would be priced twice (Anthropic, Bedrock). The nested `prompt_tokens_details.cached_tokens` is INSIDE `prompt_tokens`, and the rule moves that part of it to the cache-read rate (OpenAI, Gemini; a cache-read bucket wins when a dict carries both). A reported `total_tokens` above what the split prices has the difference priced at the higher of the two rates.
- `count_usage_tokens` (the token dimension of the budget) takes an explicit total (`total_tokens`, or the normalized `total`) when there is one, and otherwise adds the input and output counts only: a cache bucket costs money but does not count toward a token budget, while cached tokens inside `prompt_tokens` do.

| Provider | Usage dict keys | Input and cache | Output and thinking | Streaming source | Vendor docs |
|---|---|---|---|---|---|
| Anthropic | `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` | `input_tokens` excludes the cache reads and writes; the total input is the sum of the three | `output_tokens` includes the thinking tokens | `message_start` plus the last `message_delta` (`_StreamUsageAccumulator`) | [prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking) |
| OpenAI and OpenAI-compatible | `prompt_tokens`, `completion_tokens`, plus `total_tokens` when the server reports it and the `*_tokens_details` maps: the stream (`extract_openai_usage`) keeps all four, `chat()` (`extract_openai_response_usage`) keeps `prompt_tokens_details` | `prompt_tokens` includes `prompt_tokens_details.cached_tokens`, the part priced at the cache-read rate | `completion_tokens` includes `completion_tokens_details.reasoning_tokens` on OpenAI itself; a compatible server may differ (xAI leaves its reasoning tokens out of `completion_tokens`) | the final chunk, requested with `stream_options.include_usage` | [usage object](https://platform.openai.com/docs/api-reference/chat/object), [prompt caching](https://platform.openai.com/docs/guides/prompt-caching) |
| Gemini | `prompt_tokens`, `completion_tokens`, plus `prompt_tokens_details.cached_tokens` when part of the prompt was cached (`_gemini_usage`, the one builder for `chat()` and both streams) | `prompt_tokens` = `prompt_token_count` + `tool_use_prompt_token_count` (`_gemini_prompt_tokens`): `total_token_count` is the sum of the prompt, candidates, tool-use prompt and thoughts counts, so the tool-use prompt tokens, billed as input, are outside `prompt_token_count` (see below). `prompt_token_count` includes `cached_content_token_count`, and `prompt_tokens` keeps it whole: proxy clients read it as the whole prompt. The cached part also rides as `prompt_tokens_details.cached_tokens` (`_gemini_cached_prompt_details`), which the pricing moves to the cache-read rate | `completion_tokens` = `candidates_token_count` + `thoughts_token_count` (`_gemini_completion_tokens`): the candidates count excludes the thinking, which Google bills at the output rate | `usage_metadata` is cumulative: the last chunk carrying it wins, never a sum | [UsageMetadata](https://ai.google.dev/api/generate-content#UsageMetadata), [thinking pricing](https://ai.google.dev/gemini-api/docs/thinking#pricing), [tool-use token count](https://ai.google.dev/gemini-api/docs/url-context) |
| AWS Bedrock (Converse) | `prompt_tokens`, `completion_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` | `inputTokens` is the non-cached input only; the total input is `inputTokens` + `cacheReadInputTokens` + `cacheWriteInputTokens` (`_bedrock_cache_usage`), and a cache counter is carried only when nonzero. `totalTokens` is not carried, so the token budget counts a Bedrock call like an Anthropic one; AWS does not say whether it also counts the cache counters (third-party reports disagree), and nothing here depends on it. `cacheDetails` (the cache writes split by TTL) is not read either: no request asks for the one-hour TTL (the provider sends no `cachePoint`), and the writes are priced at the row's one cache-write rate | `outputTokens` counts every generated token; Converse reports no separate thinking count | the single `metadata` event that closes the ConverseStream, assigned once | [TokenUsage](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_TokenUsage.html), [prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html) |

- A streamed usage that reports no tokens is `{}` on the Bedrock and Gemini paths, but a prompt read entirely from the Bedrock cache (0 `inputTokens`) is kept for its cache counters.
- `tool_use_prompt_token_count` is read even though the Gemini provider enables no server-side tool (Google Search grounding, code execution, URL context): Google counts there the results of a tool it runs itself during the request, fed back to the model as input and billed as input. A function the platform runs goes back in the next request's `contents`, the prompt that `prompt_token_count` measures, so the count is expected to stay 0 on this provider's requests; whatever fills it, it is priced once, at the input rate, since `prompt_token_count` leaves it out.
- Tests: `tests/test_streaming_usage_capture.py` drives the Bedrock and Gemini streaming paths and their non-streaming `chat()` with the same usage, and prices it through `RunBudget` (a Gemini call with cached, tool-use and thinking tokens reconciles to Google's `total_token_count`); `tests/test_provider_billed_usage.py` pins the two normalizers, `tests/test_gemini_tool_use_usage.py` the tool-use prompt tokens and `tests/test_cached_prompt_pricing.py` the cached prompt tokens.

## Usage of a stream that never ends (`StreamUsageSink`)

A stream cut short - a user stop, the degenerate-repetition stream cut (`_AnswerStreamCut`, which aborts the call like a user stop, never as a provider failure the failover wrapper would retry, and only once a report made after the cut counts more output than at the cut, so the recorded usage covers every shown token: a provider that reports its output only at the end - Anthropic, Bedrock, OpenAI-compatible - streams on unshown and is counted whole, so today only Gemini's calls are aborted), the loop's wall clock or idle watchdog, a task cancelled by a client disconnect or a deadline, an error mid-way - never reaches the normal end that returns its usage, yet the run budget, the traces and the usage the run reports must count the call. Every streaming method (`chat_stream` and `chat_stream_with_tools` of every provider, and the base-class fallbacks) takes an optional `usage_sink` kwarg (`base.StreamUsageSink`, read with `usage_sink_of(kwargs)`), `report`s into it the usage dict its normal end would return each time it learns more, and `restart`s it when it opens an attempt: an attempt it retries or fails over is re-sent, and is not the call's. What each provider knows before the end:

| Provider | Known before the end | Recorded when the stream never ends |
|----------|----------------------|-------------------------------------|
| Anthropic | `message_start`: input, cache write and read (plus its initial output token); each `message_delta`: the cumulative output | the `_StreamUsageAccumulator` state at the cut |
| Gemini | cumulative `usage_metadata` on the chunks | the latest chunk's counts (never a sum of chunks) |
| Bedrock ConverseStream | nothing until the final `metadata` event | nothing before `metadata`, its usage after |
| OpenAI and every OpenAI-compatible provider | nothing until the final `include_usage` chunk | nothing before it, its usage after |

The agent loop owns one sink per streaming call (`_streaming_chat(..., usage_sink=)` and the `chat_stream_with_tools` call). A call that returns `settle`s it: its usage travels in the response. Every error handler of such a call closes it through `_end_aborted_generation()`, which `take`s the reported usage once and feeds the two sinks a returned call feeds: the generation span (`end_generation(..., error=, usage=)` keeps the usage on an error close) and the usage hook `_merge_usage` (the run budget and the accumulated usage), a failing hook being logged and never raised over the error being handled. A cancelled or timed-out run's terminal response carries the accumulated usage, like every other terminal response, so the root trace and the run's token totals keep it. Nothing is estimated from the streamed text. A run that ends by an exception (a cancelled task) returns no response: its spans and budget carry the aborted call, and its root trace is still closed by the caller without usage.

The LLM proxy (`api/v1/llm_proxy.py`) streams through generators of its own and records the same way. The Gemini / Bedrock bridge hands `provider.chat_stream` a sink and closes its trace with what the sink holds, on a normal end too (`last_usage` lives on a cached provider instance other requests share); the Anthropic bridge feeds a `_StreamUsageAccumulator` from the events it relays; the OpenAI-compatible pass-through keeps its `include_usage` chunk; `/v1/messages` keeps the latest cumulative `message_delta` count (`_AnthropicSseTally`), never a sum. A client that disconnects stops the generator - `GeneratorExit` at a `yield`, `CancelledError` at an `await` - and the trace is closed once with the usage reported so far and a structural `run_cancelled` cause, including a chunk that was being handed over when the client left (`end_trace` keeps the usage of an error end for Langfuse's `total_usage` rollup too). The request is metered like a finished one (`/v1/messages` already meters before it forwards). Both are metered from a task of their own (`_meter_stream`; a finished stream waits for it through `asyncio.shield`): a client leaving cancels whatever the generator awaits, the metering included if it ran there, and an anyio cancel scope cancels every later `await`. The bytes sent to the client do not change.
