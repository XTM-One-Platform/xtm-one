# Services: built-in tools and sandboxes

Service map rows and patterns for the shared built-in tools (`builtin_tools/`), tool building, the code interpreter, custom tool sandboxes, declarative HTTP and OpenAPI tools, MCP and skill packaging, schema checks, the browser, web fetch and document / image rendering in `backend/app/services/`; the binding rules live in `backend/app/services/AGENTS.md`.

## Service map

| File | Purpose |
|------|---------|
| `builtin_tools/` | Every built-in tool builder plus the MCP / custom tool loaders, integration tool filtering and the prompt / identity helpers, used by `agent_chat`, `general_chat`, `assignment_engine` and the flow runner. One module per suite: `media` (code interpreter, image generation, file generation, `annotate_file`), `web` (web fetch, browser), `image_assets`, `html_render`, `kb`, `memory`, `handover` (sub-agent tasks), `agent_builder`, `flow_builder`, `workspaces`, `skills`, `presentation`, `report`, `templates`, `template_authoring`, `investigation`, `evaluations`, `traces`, `computer_use`, `conversation_reader`, `document_vision`, `scheduling`, `work_items`, `shared_state`, `workset`, `wait`, `stix` / `stix_comparator` / `stix_extraction` (the grounded extraction pipeline of `services/stix_extraction/` as `extract_stix_from_document`, on the turn's own model; `dev-docs/stix-grounded-extraction.md`), `fimi_math` / `fimi_metrics`, `timeline_diff`, `video_studio` (browser profiles, recordings, AI clips, video production and render jobs), `page_actions` (`act_on_page`: the embedded widget acts on its host page one action at a time, each chosen by the platform decision model), plus `loaders`, `filtering`, `prompting` and `_shared`. `__init__.py` is the facade re-exporting the full surface (`from app.services.builtin_tools import X`), pinned by `test_builtin_tools_facade.py`. |
| `web_fetch.py` | Shared web fetching and HTML-to-text extraction: `fetch_and_extract()` (full HTTP fetch + extraction), `extract_from_html()` (HTML-only). Uses trafilatura with BeautifulSoup fallback. Single source of truth for the `web_fetch` built-in tool, KB crawl endpoint, and website sync. `fetch_and_extract()` connects to the address it checked (`app.core.pinned_request.send_pinned`: one resolution per hop, the name as `Host` and TLS server name, `trust_env=False`), whatever relay route is current - its client never goes through a relay, so the check is never skipped. |
| `_sandbox_selector.py` | The OpenSandbox half shared by `custom_tool_executor.py` and `code_interpreter.py`: the process-wide reachability probe `_probe_opensandbox_available()` (TCP connect to `OPENSANDBOX_DOMAIN`; positive result cached for the process lifetime, negative re-probed after 60 s), `_build_opensandbox_config()`, and `_create_opensandbox()` (image from `OPENSANDBOX_IMAGES`, k8s pool from `OPENSANDBOX_K8S_POOL_NAMES`, default-deny egress policy; an egress-sidecar start failure is retried once, then raised as `SandboxUnavailableError`, never retried without the policy; `native_thread_env()` sets `NATIVE_THREAD_ENV_KEYS` (`OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS`) to the container's CPU request rounded up, at least 1 (a value in the caller's own `env` wins), because OpenBLAS sizes its pool on the host's core count and a many-core host otherwise exceeds the server's `pids_limit` at `import numpy`; both Python wrappers' env scrubs keep those keys). The Docker probe and the mode resolution (`_resolve_sandbox_mode()` / `_select_sandbox()` / `get_effective_sandbox()`) live in `custom_tool_executor.py`. |
| `_sandbox_utils.py` | The Python sandbox security source shared by `code_interpreter` and `custom_tool_executor` (embedded as source text in the subprocess script): `BLOCKED_MODULES`, `effective_blocked_modules()` (the admin allow-list applied), `build_sandbox_security_src()`; a defence-in-depth import hook - the subprocess is the boundary. |
| `sandbox_call_logging.py` | One structured `sandbox_call` log event per OpenSandbox execution (CPU / RAM, time, egress policy, outcome); observability only, never gates or records quota. |
| `custom_tool_executor.py` | Sandboxed executor for user-defined JavaScript (Node.js) and Python tools (`execute_tool_auto`). `CUSTOM_TOOL_SANDBOX` (`auto` \| `docker` \| `subprocess` \| `opensandbox`, default `auto`; the deprecated `CUSTOM_TOOL_DOCKER=true` counts as `docker` only when the setting is not provided at all) picks the backend through `_resolve_sandbox_mode()` / `_select_sandbox()`: `auto` prefers a hardened Docker container (no network, read-only FS, dropped capabilities, memory cap) and falls back to a timeout-enforced subprocess; `docker` and `opensandbox` fail with a clear error when their backend is unreachable. The subprocess fallback is hardened: JS runs under the Node.js permission model when supported (`node --permission` [+ `--allow-net` on Node 25+]: fs / child-process / worker / addon denied, network allowed; opt-out `CUSTOM_TOOL_NODE_PERMISSION=false`, also a Settings > Security option) and Python runs with `-I -X utf8` plus the `_sandbox_utils` import hook; its security notice is logged once a day platform-wide (`log_once`). `get_effective_sandbox()` exports the `xtmone_custom_tool_sandbox` Prometheus gauge (one-hot: `docker` / `subprocess` / `opensandbox` / `docker_unavailable` / `opensandbox_unavailable` / `disabled`; alert on `subprocess\|docker_unavailable\|opensandbox_unavailable`) and feeds the Security Audit; `warn_sandbox_mode_at_startup()` runs in the web and worker startup. `opensandbox` runs each call in an OpenSandbox-managed container through the `opensandbox` SDK (`OPENSANDBOX_DOMAIN`, `OPENSANDBOX_PROTOCOL`, `OPENSANDBOX_API_KEY`; images `OPENSANDBOX_IMAGES`, comma-separated `key:image` pairs merged over the defaults; egress allow-list `OPENSANDBOX_NETWORK_ALLOW`, all egress denied by default; `SANDBOX_CPU` / `SANDBOX_RAM`; `OPENSANDBOX_USE_SERVER_PROXY` routes sandbox traffic through the server when this process cannot reach the sandbox endpoints, e.g. a native dev backend against a containerized server or non-routable k8s pods). A custom tool's stages share one budget counted from the call's start, the tool's timeout less `_COMMAND_DEADLINE_MARGIN_SECONDS` (20 s, a tenth of a short timeout), so the executor answers before the agent loop's per-tool timeout (the same 300 s by default): `_bounded_stage` bounds the create and the script upload, `_run_bounded` the command, each expiry a `_StageTimeoutError` naming the stage (the run stage also names the egress policy), the sandbox killed (`kill_sandbox_best_effort` itself bounded to `_KILL_TIMEOUT_SECONDS`); the generated JS script exits once the tool's promise settles, so an open handle never holds the call, and writes a value the tool returns to stdout (a string as is, anything else as JSON) after what it logged; a failed fetch carries its network cause and `_explain_network_failure` names the egress policy and its allowed hosts. In OpenSandbox the JS script also wraps `fetch` with the allow-list (`_js_egress_guard`, targets read by `_egress_precheck_targets`: host names, IPs and `*.suffix` wildcards, each also letting its subdomains through; any other target form turns the pre-check off), so a host outside it fails at once with cause `EGRESS_DENIED` and the same egress-policy message instead of after undici's connect timeout; the server's policy stays the enforcement. Each JS call's stages (`quota`, `create`, `upload`, `run`, `cleanup`) are timed by `_StageClock` and put on the tool span as `custom_tool.<stage>_ms`, `custom_tool.total_ms` and `custom_tool.outcome` (`ok` / `error` / `stage_timeout`) however the call ends. Every OpenSandbox call (this executor's and `code_interpreter.py`'s) is gated by the per-user combined agentic + sandbox quota check in `quota.py` (`check_agentic_quota`). |
| `code_interpreter.py` | Sandboxed Python code execution: runs user code in a local subprocess with matplotlib chart capture (`inject_code_images` persists charts as durable `FileAttachment`s) and disk-output-file capture (`_collect_output_files` / `execute_python`'s `output_files`) so files the code writes persist as conversation / run files. When `CUSTOM_TOOL_SANDBOX=opensandbox`, delegates to `execute_python_opensandbox` which probes OpenSandbox availability (returning an error dict if unreachable), is gated by the per-user combined agentic+sandbox quota check (see `custom_tool_executor.py` row), and runs inside an OpenSandbox container respecting `OPENSANDBOX_NETWORK_ALLOW`. **Conversation files are mounted**: `input_files` - `(mount name, bytes)` pairs - are written under `attachments/` in the working directory (`ATTACHMENTS_DIRNAME`) with an `index.json` mapping file ids to paths, never collected as outputs, and the result's `mounted` lists the names that actually landed. `safe_mount_name()` makes a name flat, safe and unique BY CONSTRUCTION (`<stem>-<file id>.<ext>`, `mount_tag()`: a UUID's 32 hex digits, a digest of any other id - so a footer or a refusal naming one file's path is exact whatever else is mounted, and nothing is ever renamed at mount time; a prefix of the id could collide and a renamed mount would contradict every path already announced), NFC-normalised, stripped of invisible and line-breaking characters (Unicode `Cc` / `Cf` / `Zl` / `Zp`), capped at 255 bytes of UTF-8, Windows device names defused (`ntpath.isreserved` too); `mount_path_hint()` is the path every other surface names - only where `code_interpreter_offered()` finds the built-in on the reader's surface (its name AND its `builtin:code_interpreter` source, since a same-named MCP or custom tool mounts nothing). `input_files` may be a loader (`SandboxInputsLoader`) awaited only past the gates - reachable, quota open, sandbox created - so a refused run downloads nothing, a failing loader mounts nothing and never fails the run, and EVERY result, the early returns included, carries `mounted` (the tool's mount report believes nothing else). The local write refuses a directory or a file it did not create (`os.mkdir`, `O_EXCL` / `O_NOFOLLOW`); the local subprocess sandbox is still not a tenant boundary between runs of the same OS user - OpenSandbox is, one container per call. OpenSandbox creates the directory through the SDK (`files.create_directories`) before writing into it and takes the working directory as the run option (`RunCommandOpts(working_directory=...)`), never a shell `cd`. Bounded by `MAX_INPUT_FILES` / `MAX_INPUT_TOTAL_BYTES`. |
| `sandbox_workspace/` | The code interpreter's durable `workspace/` per conversation / run: manifest in PostgreSQL, contents in the bucket, quota + owner check, both kernels (`session=true`), `to_workspace_path` ingestion, `materialize_repository`, package installs, the sweep. Contract: `dev-docs/reference/sandbox-workspace.md`. |

| `browser_profiles/` | Browser profiles (design in `dev-docs/browser-profiles.md`), saved sign-ins every browser of the platform opens (an agent's `browser` tool, a Video Studio recording, the sign-in, the keep-alive): `profiles.py` the only reader / writer of a profile's encrypted credentials and session (write-only, never serialized; `list_usable_profiles` / `load_usable_profile` = the three-tier predicate without the admin bypass; `record_probe` / `effective_session_status`: `active` only after a probe rendered the application); `browser.py` the one launch recipe (`profile_browser`) and `check_target` the URL policy (the agent browser tool's rule, private hosts only under `browser_private_targets` and a declaration on the profile); `signin.py` the sign-in, MFA and the probe (`ensure_signed_in`: probe, then sign in again alone when the profile can; `start_sign_in` / `submit_code` / `dry_run_sign_in`), the page read by structure, never by its words; `totp.py` RFC 6238 codes from a stored TOTP secret (standard library only); `keepalive.py` the worker sweep (`keepalive_sweep`, run by `orchestration_adapters/browser_profiles.py`, one profile a sweep under a Redis lease); `agent_access.py` THE rule of which profiles a run's `browser` tool opens (bound to the agent or the person's General Assistant AND usable by the run's person; read-only bindings), read by every builder of the tool; `agent_sessions.py` the signed-in session (`open_profile_session`, audited `use`) and its compare-and-set write-back (`store_refreshed_session`). |
| `image_summary.py` | Server-side visual summary of a raster image: `summarize_image()` (Pillow, on the parse executor via `run_parse`, `None` for anything it cannot decode - never raises into the caller), `format_visual_summary()` (the ONE `Visual summary: WxH px; dominant #HEX n%; saturated colours (>= 0.05% coverage): #HEX n%, ...` line), `looks_like_raster_image()`, `parse_color_list()` + `conflicting_gate_colors()` + `check_color_expectations()` / `run_color_check()` (the `expect_colors` / `forbid_colors` gate: forbidden present / expected absent, "present" being the EXACT saturated colours (`ImageSummary.saturated`, Lab precomputed) within `COLOR_MATCH_DELTA_E` adding up to the threshold - never read off the merged list, whose tolerance is narrower, nor off the bucket means, which a larger colour in the same 16-cube pulls away from a small mark; a forbid check refuses on a summary that is not `complete` - an animation read at its first frame, an image `sampled` because it was too large or too colourful to count every pixel, or a whole-image count whose exact palette was `palette_cut` at `_MAX_EXACT_COLORS`; an expected and a forbidden colour closer than `GATE_SEPARATION_DELTA_E` (2 x the match radius, where one pixel counts for both) are refused up front). Every pixel counted at full resolution within `_MAX_EXACT_PIXELS` / `_MAX_EXACT_COLORS`, NEAREST subsample otherwise, transparent pixels excluded, "saturated" keyed on `core.color.chroma()` (HSV saturation reads dark navy as saturated), exact colours bucketed (at most 4096 by construction, every one tested against the kept colours) then folded by ΔE for the LINE so a gradient or an anti-aliased edge is one entry, the number of distinct colours the line keeps capped so a photograph costs a fraction of a second - `truncated` when the discarded buckets could add up to a colour over the threshold, a statement about the line only. Carried by the `browser` screenshot result and the `upload_notion_file` result so an unexpected hex is checkable after the vision block is pruned; the upload REFUSES, before any byte reaches Notion, when the gate fails or cannot run. Colour maths live in `app/core/color.py`. |
| `svg_raster.py` | The ONE bounded SVG rasterizer: `rasterize_svg()` (sync) / `rasterize_svg_async()` (async) - `render_svg()` / `render_svg_async()` are the same with why nothing was drawn (`SvgRender.reason`: a refusal, a worker killed or dead), for a caller that reports it - shared by `llm/base.py` (every SVG shown to a model - no vision provider takes `image/svg+xml`) and `image_geometry.py` (which keeps its own reading - the template sanitizer's output, a marker or an embedded image refused - and renders it at resvg-py's default `dpi=0`, so a stored trim box never moves). The markup is untrusted, so it is checked before resvg renders it, and what renders is the ORIGINAL bytes whenever nothing was dropped (byte for byte as resvg renders them): `defusedxml` parse, an INTERNAL entity expanded within bounds (an Adobe Illustrator export declares its namespaces this way; resvg expands them itself) while a parameter or external (`SYSTEM` / `PUBLIC`) entity, a billion-laughs expansion past `MAX_SVG_ENTITY_EXPANSION` and more than `MAX_SVG_ENTITIES` declarations are refused (`_check_internal_entities()`, whatever the libexpat in use caps); **nothing outside the document is reached** - a non-local `href` (outside `<a>`) or `url(...)` target in an attribute (case-insensitive) is DROPPED and the rest of the drawing renders (`_neutralize_references()`: resvg drew nothing there on its own, and READ the file a path names - absolute, relative, `..`, behind an unknown scheme, a Windows verbatim / device / UNC path), a `<style>` element's CSS is left (resvg loads nothing from it), a nested `data:image/svg+xml` on an `<image>` (draw.io icons) is checked under the same rules up to `MAX_NESTED_SVG_DEPTH` and charged at every draw of its image by the budget, and `SVG_STRICT_RENDERING=true` (`strict=`) refuses the whole SVG instead of dropping - on an entity too; a shape budget counting what resvg draws again - `MAX_SVG_EXPANDED_ELEMENTS`, or `EXPANSION_ALLOWANCE` x the document's own elements when that is more (a big flat chart is no multiplication): `<use>` / `url(#id)` / patterns / masks memoized per target, a marker per vertex on every shape, markers and paint servers INHERITED by every shape below the group or `<use>` naming them, a duplicated id charged as its costliest element, `xml:id` as an id; a reference cycle and nesting past `MAX_SVG_DEPTH` (resvg recurses per level and overflows a thread stack) refused; a **filter budget** in the same pass - every filter application costed as its region (the element's box, the filter region, or a `userSpaceOnUse` rectangle, scaled by every transform and nested viewport above it - resvg does NOT clip a region to the canvas) times its primitives' measured work (a morphology window, turbulence octaves, a convolution kernel, a blur ...), refused past `MAX_FILTER_WORK_MS` or a region past `MAX_FILTER_REGION_PIXELS`, so a filter bomb is refused in milliseconds instead of running into the worker timeout; and a fit INTO a `box` x `box` pixmap (never a fixed width, so a tall viewBox cannot allocate a tall pixmap). `keep_native_size` renders an in-box SVG at its own size: `intrinsic_size()` reads the size as resvg does (px, % of the viewBox, a width / height resvg cannot read as 100%, em / ex at the default font size, and pt / mm / cm / in / pc at `RENDER_DPI` = 96); every SVG renders at `RENDER_DPI` (`dpi=None`), the CSS definition of absolute units (1in = 96px, 1pt = 1/72in, 1pc = 12pt, 1cm = 96px / 2.54, 1mm = 1cm / 10) every browser applies - an SVG whose own size goes through an absolute unit (matplotlib's and Inkscape's default output, an em under a `font-size` in pt) renders at all, and a `12pt` font size, a `1mm` stroke or an `8mm` nested viewport inside a px-sized, unitless or viewBox-sized SVG is drawn as a browser draws it (resvg-py's default 0 dpi reads it as 0); an SVG with no absolute length renders byte for byte as a direct resvg call, and only a caller passing `dpi=0` (the logo geometry) reads absolute lengths at resvg-py's default; an em / ex size under a font size the document sets renders at resvg's size when `_font_size_bound()` (the default and every `font-size` / `font` declaration of the root and of every `<style>`, whatever its selector, as resvg reads a font size) fits the box, else it is fitted - never drawn at a size nothing bounds; every stylesheet reader (the filter budget's container charge, the font bound, `_css_declarations()`) reads the CSS through `_css_text()`, as a CSS parser does - comments blanked and the `{` / `}` / `;` of a quoted string too, so a `content: "}"` or `"/*"` never hides the rule after it, and a string left open is charged conservatively; and a size resvg takes from the CONTENT (no usable viewBox and no definite width AND height - an agent's `<svg xmlns=...>` with no size) renders at that size when `_content_extent()` bounds the content inside the box (shapes through their transforms, `<use>`, markers by their clipped viewport, text by a generous glyph width; a stylesheet or a relative length gives no bound), else it is fitted - and a render that still outgrows the box is fitted after all. resvg holds the GIL, so async callers render in a spawn worker process: a fresh worker starts under `WORKER_START_TIMEOUT_SECONDS`, then each render runs under `RASTER_TIMEOUT_SECONDS` (killed on overrun, and when its caller is cancelled) on a `WORKER_RENDER_STACK_BYTES` thread, with `RLIMIT_AS` on POSIX, and the worker exits with its parent; one worker + a per-loop semaphore cap concurrency, a render still queued after `RASTER_QUEUE_TIMEOUT_SECONDS` is skipped, and a worker that dies (mid-render or idle) **fails CLOSED** - the image is skipped, never re-run inline (which would drop the timeout and the memory cap on the payload that broke it), and the next call starts a fresh worker. What the worker RETURNED (the PNG, or `None` for a refusal) is kept in an in-process LRU cache keyed by the SHA-256 of the bytes + `box` + `keep_native_size` + the dpi rendered at + `strict`, bounded by `RENDER_CACHE_MAX_ENTRIES` (256) and `RENDER_CACHE_MAX_BYTES` (32 MiB, one entry at most a quarter of it) and invalidated by eviction alone, so a conversation's history is not rendered again on every turn (a hit is the same PNG bytes, off the queue); a timeout, a crash or a queue skip is never cached. `clear_svg_raster_cache()` empties it. The sync `rasterize_svg()` has the checks only - no timeout, memory cap or crash isolation - so async code never calls it (the `test_svg_raster_bounds.py` AST tripwire). Never raises: `None` = no image. `shutdown_svg_raster_worker()` is called from the web + worker lifespans. |

## Tool Building (shared across services)

All services build tool sets from the same sources:

1. **Built-in tools** — `build_code_interpreter_tool()`, `build_image_generation_tool()`, `build_web_fetch_tool()`, `build_browser_tool()`, `build_kb_search_tool()`, `build_memory_search_tool()` from `builtin_tools/`
2. **Sub-agent tools** — `build_sub_agent_tools()` from `builtin_tools/` (when handover agents configured)
3. **MCP tools** — `load_mcp_tools()` (`builtin_tools/loaders.py`), which builds each server's runtime config with `build_mcp_runtime()` from `api/v1/helpers.py`
4. **Custom tools** — `load_custom_tools()` loads them from the DB with sandboxed executors (`custom_tool_executor.py`)
5. **Integration tools** — Use `build_integration_tools()` from `integration_tools.py`, filtered via `filter_integration_tools()`. **Multi-instance:** when an agent binds several integrations of one provider, each instance's tools are renamed `tool__<slug>` (`_suffix_instance_tools`, `base_name` keeps the original for allow/deny). The slug is `Integration.tool_slug`: derived once from the display name at insert (`app.core.integration_tool_slug.derive_tool_slug`), backfilled by `t7319toolslug1` with the value the old per-build derivation yielded, never recomputed on a rename, editable through `PUT /integrations/{id}` (`tool_slug`: `^[a-z0-9_]+$`, at most 21 characters, unique per provider within the owner scope, `services/integration_tool_slugs.py`). `_instance_tool_slug` falls back to the display name only for a row without a valid slug and keeps the per-agent `_N` counter as the safety net. An assignment `activation_check` names one instance's tool as `tool@<integration id>` (or an `integration_id` key), resolved to the live suffixed name when it runs (`assignment_activation_check.resolve_check_tool`); `list_integrations` shows each integration's suffix.
6. **KB tools** — `search_knowledge` via `build_kb_search_tool()` (read, both chat + assignments) and `store_knowledge` via `build_kb_store_tool()` (write, exposed when the agent has KBs flagged `"write"` in `knowledge_base_permissions`, in both chat + assignments)
7. **HITL tool** — Built-in `request_human_input` (assignment engine only)

## Custom Tool Execution

User-defined JavaScript and Python tools run in the sandbox selected by `CUSTOM_TOOL_SANDBOX` (`auto` | `docker` | `subprocess` | `opensandbox`, default `auto` - see `custom_tool_executor.py`):

1. Input variables are injected into the tool source (`$variable_name` constants in JS, `variable_name` assignments in Python)
2. `auto` probes Docker lazily (`docker info`, single-flight; positive result cached for the process lifetime, negative re-probed after 60 s) and prefers a disposable hardened container (`node:24-slim` / `python:3.14-slim`, `--network=none`, `--read-only`, `--cap-drop=ALL`, 128 MB memory cap with swap disabled), else the subprocess; `docker` requires Docker (clear error, no fallback); `subprocess` always uses the plain subprocess; `opensandbox` requires a reachable OpenSandbox server (clear error, no fallback) and runs the tool in an OpenSandbox container
3. Subprocess fallback spawns `node` (script piped via stdin) or the system Python (temp script file) with a sanitized environment; JS runs under the Node.js permission model when the local Node supports it (`--permission` [+ `--allow-net` on Node 25+]: fs, child processes, workers and native addons denied, network allowed; probed once per process, opt-out via `CUSTOM_TOOL_NODE_PERMISSION=false`); Python runs in isolated mode (`-I -X utf8`) with the best-effort module-blocklist hook (`_sandbox_utils.py`)
4. stdout captured as tool result; timeout enforced (default 300 s) - process killed (a Docker container force-removed) on timeout
5. Temp files cleaned up after execution
