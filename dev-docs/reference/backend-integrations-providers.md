### Supabase database role

Both roles the Management API runs SQL as (`postgres`, `supabase_read_only_user`) bypass row level security. A Supabase integration can instead be given a Postgres login role of the project: `db_role`, `db_password`, `db_host`, `db_port`, `db_name`, `db_ca_cert` and `db_functions` in extra_config.

- **Connection** (`providers/supabase_postgres.py`): the host is a Supabase pooler (`*.pooler.supabase.com`, user `role.project_ref`) or `db.<ref>.supabase.co` (user `role`), port 5432 or 6543. It is resolved once, every address must be public (`destination_policy`), and the connection dials that address (IPv6 bracketed) with the TLS certificate verified against the host name (system trust store, or `db_ca_cert`). A relay-routed integration refuses it (a relay carries HTTP only). Each call runs in one transaction with a 60 s statement timeout, and a role that bypasses RLS (superuser or BYPASSRLS) is refused before any work; the probe and the connection test log in anyway to report it. Platform roles (`postgres`, `service_role`, `supabase_*`, `pg_*`...) are refused as settings.
- **Token**: `_get_token` builds `project_ref||pg:<base64url JSON>||access_token` (`encode_access`); `split_token` also reads the older `project_ref||access_token`.
- **Tools**: with a database role, the three free SQL tools (`query_supabase_sql`, `execute_supabase_sql`, `apply_supabase_migration`) and `query_supabase_logs` (its lines carry row values: a constraint violation's key, a PostgREST filter, a user's email) are withheld, also when the role's settings are unusable. `list_supabase_functions` and `call_supabase_function` reach only the allowed functions (`schema.name`), refused before any login otherwise. The call is built from the catalog read as the role: identifiers quoted, every argument bound as text and cast to the declared type (`build_call`), never SQL from the model. The result is sliced server side (`result_sql`): each row's text from `offset`, 40k characters a call, rows stop at the budget, the cut named with the offset that reads on. Results and database errors come back inside `wrap_untrusted`.
- **Connection test**: `validate_database` logs in as the role and reports whether it bypasses RLS and how many allowed functions it may execute.
- **Probe** (`api/v1/supabase_console.py`, `probe_management`): the projects, login roles, pooler hosts the access token reads, then, as the role, its databases, the functions it may execute and the tables it can still read (table or column SELECT). A part the access token cannot read is `null` with a fixed sentence in `errors`, and the tab offers a typed field instead: a scoped token reads the projects with Project Settings read, the login roles with Database read (a read-only query) and the pooler hosts with Connection Pooling read - without the last, no host is offered, not the IPv6-only direct host alone. A database refusal names the step and the condition (`InsufficientPrivilegeError, SQLSTATE 42501`), its message stays in the log. The stored password is sent only to the role, host and project it was saved for. The Database access tab of the integration saves the choices through the integration update.
- **SQL cell cap**: a SQL result shares half the output budget between its rows (`_cell_cap`): one row keeps 20k characters of a cell, a hundred rows 1,000 each.

### Run payload shapers

A provider can trim an event before the run is shown it: `app/integrations/run_payload_shapers.py` holds a registry of shapers `(event_key, payload) -> payload` (`register_run_payload_shaper(provider, fn)` at import, like `register_event_enricher`). `assignment_helpers._build_trigger_information` applies the shaper of `trigger_context.provider` (event from `event_key`, else `event`) to the Trigger Payload it shows the run, and only there: the stored run payload, the `{{trigger.*}}` template context and the trigger filter keep the delivery whole. A shaper that raises, or a provider without one, shows the payload whole. GitHub registers `providers/github/run_payload.py` for `push`: `head_commit` dropped when it is the last commit of `commits`, each commit message cut to its first line (200 characters, `message_truncated` set), every `*_url` key dropped at any depth except `html_url`; paths (`added`, `removed`, `modified`) are never cut. A squash of a long pull request goes from 174,383 characters (cut at the 150,000 cap) to under 20,000.
