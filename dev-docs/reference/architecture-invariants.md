# Design system and architecture invariants

The root `AGENTS.md` keeps one line per entry, because every agent session loads it; this file holds the full contract. Add detail here, never to `AGENTS.md`.

## Design System

- **Dark theme**: `hsl(220, 56%, 6%)` background, white foreground
- **Cyan accent**: `hsl(197, 100%, 53%)` – primary buttons, active states, glow
- **Cyan glow**: `hsl(197, 100%, 60%)` – enhanced glow effects
- **Fonts**: Geologica (headings), IBM Plex Sans (body)
- **Style**: Glass morphism, cyan glow effects, smooth transitions

## Architecture Invariants (DO NOT violate)

1. All automation must be implemented as **Assignments on Agents** — not ad-hoc
2. All secrets must be **Fernet-encrypted** before database storage (known exception: assignment `webhook_secret` lives plaintext in the `trigger_config` JSON column pending a data migration - SEC-5 follow-up; it is still redacted on every serialisation surface)
3. All API endpoints require **JWT authentication** (except public endpoints)
4. **No integration credentials in env vars** — everything in the DB via UI (not an exception: a secret vault provider, `SECRET_VAULT_<NAME>_*`, is deployment identity like `DATABASE_URL`, never an integration credential; what opens the vault comes from the environment or the workload identity, prefer a `_FILE` setting or a workload identity to an inline `TOKEN` / `SECRET_ID`, and the integration's own secret stays a field in the DB that holds a `vault://` reference - `docs/docs/deployment/secret-vaults.md`)
5. All server state in the frontend uses **TanStack Query**
6. The UI follows Filigran's design system (dark + cyan + Geologica + IBM Plex Sans)
7. Assignments execute via the **agentic loop** (LLM + tools), not hard-coded steps
8. SSO users are linked by email to existing local accounts. SAML 2.0 supports automatic group mapping from IdP group claims (`saml_groups_mapping_enabled`, `saml_groups_auto_create` on `SSOConfig`). Groups are synced on each login — added if present in the assertion, removed if absent.
9. **Company-managed entities** are marked by the `is_company_managed` flag, which alone decides visibility; the row keeps a real owner in `user_id` (the creator, or the admin `resolve_company_managed_owner_id` picks for rows created without a user, pinned by `tests/test_company_managed_owner_resolver.py`). Legacy rows may still have no owner: the seed backfills the built-in ones, and the readers that need an owner (flow triggers, trigger integration access, the security audit) handle a missing one. The owner matters because code runs as that owner (A2A external work) and hands it over when the user is deleted (`reassign_company_managed_entities`). Toggling company → private auto-cleans other users' references. The entities are the `CompanyManagedEntity` union in `api/v1/helpers.py`.
10. **No native checkboxes** — always use `Switch` toggle component
11. **Custom tools** execute user-provided JavaScript/Python in a hardened Docker sandbox when available (`CUSTOM_TOOL_SANDBOX`, default `auto`) with a timeout-enforced subprocess fallback
12. **Agents with `disable_chat`** are hidden from the LLM proxy `/v1/models` listing, the profile page, and appear greyed-out in the chat agent picker — use for assignment-only agents
13. **Migrations are Alembic-only AND must be safe to auto-apply** - no inline SQL / `create_all`-only schema changes. Every migration MUST: (a) keep a SINGLE Alembic head (`backend/tests/test_migration_integrity.py` fails the build on multiple heads; after rebasing onto a main that added migrations, re-point your earliest migration's `down_revision` to main's new head); (b) be IDEMPOTENT / re-runnable - `ADD COLUMN IF NOT EXISTS`, `DROP ... IF EXISTS`, `CREATE TABLE/INDEX IF NOT EXISTS`, `ALTER TYPE ... ADD VALUE IF NOT EXISTS`, `DO $$ ... IF NOT EXISTS ... $$` for constraints - because fresh installs run `create_all` + `stamp head` (the body never executes) while existing installs run the body, and a crashed replica may retry; (c) be CONCURRENCY- and LOCK-safe for multi-replica auto-migrate-on-startup - lock-light DDL only (constant-default `ADD COLUMN` is metadata-only on PG 11+; NO table rewrites, NO `SET NOT NULL` on large tables, NO unbounded in-transaction backfills; NEVER `CREATE/DROP INDEX CONCURRENTLY`, which waits on every older transaction in the database and hangs the rollout; build an index with `create_index_in_place()` from `app.core.migration_ddl` inside `op.get_context().autocommit_block()`, and ask before adding one to a large, hot table); (d) be LOCK-SAFE against rolling-deploy lock queues (2026-07-05 outage: there is NO cold table — any long-lived open transaction that has *read* the table blocks the ALTER; `platform_settings` took production down this way). Every lock-taking DDL must follow the canonical recipe: idempotency probe + early return, then `terminate_lock_holders(conn, "<table>")` + `set_lock_timeout(conn)` from `app.core.migration_ddl`, then the guarded DDL — enforced by `test_lock_taking_ddl_sets_lock_timeout` in `backend/tests/test_migration_integrity.py` (frozen grandfather list; never add to it). The startup runner retries transient 55P03/57014 lock failures with backoff, but the pre-flight is what makes the DDL complete. Startup migration is already serialized across replicas by a `pg_advisory_lock` in `app/core/migrations.py` - rely on it, never add a second migration lock or run DDL outside Alembic. Full rules + reference idioms: `migrations-safety.md`.
14. **Thinking/reasoning display** — while the agent works, reasoning (`thinking_text` events) renders in the dimmed scrolling window below the status bubble; the status bubble and the window both disappear the moment final answer tokens flow. The accumulated reasoning is persisted in the assistant message metadata (`reasoning`) and surfaced in the reasoning-details dialog. Pre-tool text must never stream full-size: the agent loop holds back the first `_PREAMBLE_HOLDBACK_CHARS` chars of stream-with-tools text — short preambles flow to `thinking_text`, long answers flush to the live answer stream. Text shown in the answer bubble is never taken back: when the flushed text is followed by tool calls and the consumer opted into `deliver_segments` (the streamed web chat) it is delivered as a completed `segment_complete` (persisted intermediate message, `done` frame flagged `"intermediate": true` + `thinking` re-arm) and the continuation streams as the next bubble; `status: "stream_retract"` is reserved for non-segment consumers (public widget, REST, channels) and for regeneration cases (LLM timeout retry, `max_tokens`-truncated round, a mid-answer failover to another provider - #4230: `FailoverLLMProvider` only restarts an answer that already streamed once the caller took it back through `on_stream_reset`, never glued after the first). The panel (`@filigran/chatbot`) clears the reasoning only on `"done"` (final or intermediate), `"error"`, `"cancelled"` or a new `"thinking"` ack — hiding the window during streaming must not discard the accumulated text.
15. **Application version is injected at build time** — never hardcode the version. Backend reads `APP_VERSION` env var (default `"0.0.0-dev"`) into `settings.app_version`; Docker/CI pass `APP_VERSION` as the single external version input and set `org.opencontainers.image.version` from it. The frontend build maps `APP_VERSION` to `VITE_APP_VERSION` inside the Dockerfile only because Vite exposes `VITE_*` variables to browser code.
16. **System prompt inflation is banned** — behavioral fixes must prefer deterministic code (post-processing, validation, tool-result grounding) over adding system prompt text. Any new prompt text requires explicit justification and should be net-neutral (trim as much as you add). The URL guard (`backend/app/services/url_guard.py`) is the canonical example: it fixes hallucinated platform links with a deterministic post-processor and zero added prompt characters.
17. **A license carries a quota, not a feature switch** (the XTM Platform model, FY2027). XTM One has exactly TWO editions and ONE licence question: `enterprise` — a valid Filigran license OR at least one connected platform whose Enterprise license validated server-side — turns EVERY agentic capability on (chat, agents, assignments, flows, KBs, skills, prompts, MCP servers, custom tools, integrations, A2A, MCP agent endpoints, the full catalog, AI adoption, custom quotas); `community` — neither — runs the platform with AI off. The license decides only the acts ceilings (`daily` / `monthly` / `yearly` quotas) and the module sub-licenses; when Enterprise Edition is inherited from a connected EE platform with no Filigran license, the included allowance (`DEFAULT_AGENTIC_*`, 30/100/300) applies. The certificate's legacy `agentic_ai` / `copilot` capability flags (OIDs `62944.110` / `62944.100`) are parsed for information and consulted by NOTHING — not the install-time validation, not a gate, not the wire (`tests/test_edition_model.py` fails the build on a new reader). Every licence gate resolves to `is_agentic_ai_licensed()` (`is_chat_licensed` and `ee_features_enabled` are its aliases; `resolve_deployment_edition()` / `get_deployment_edition()` are the ONE rule) so chat, A2A, creation flows and the briefing can never disagree; background execution (schedules, triggers, channel bots, flows, delegated tasks, queued runs, the worker's AI jobs) follows the same single gate through `services/agentic_gate.agentic_refusal()` - the AI switch AND a licensed edition, cached per TTL, never `ai_state.is_ai_enabled()` alone - and, where a refusal would fail work (a queued run or delegation, a fresh evaluation), through `agentic_verdict()`, which hands a refusal nothing could be read for back to the orchestration engine instead of failing the work (`tests/test_background_edition_gate.py`); every refusal carries `deps.licence_required_detail()` — `ENTERPRISE_EDITION_REQUIRED_DETAIL` in XTM One mode, `LICENSE_REQUIRED_DETAIL` in Copilot mode, which has no edition and no platform to connect (chat surfaces prefix it through `chat_unavailable_detail()`; the MCP agent endpoints and A2A sit outside the `/api` licence-wall middleware, so an unlicensed Copilot caller does reach these gates). `GET /platform/config` carries `edition` + one `agentic_enabled` (+ `agentic_source`: `xtm_license` / `ee_platform` / `none`); the frontend reads them through `useEdition()` / `useIsCommunityEdition()` / `useAgenticAIEnabled()` and says everything about Community Edition through `components/ui/enterprise-upsell.tsx` (`EnterpriseUpsellDialog` / `EnterpriseUpsellNotice` / `EnterpriseLockedTip` / `EditionBadge`, worded once in `hooks/useEnterpriseUpsell.ts`). The retired three-tier model (Community / Starter Pack / Enterprise, `deployment_tier`, the `activation_tiers` catalog, the tier comparison dialog) must not come back under another name. On Community Edition the platform NEVER walks a person through a setup the edition cannot use: the model / provider configuration warnings (`ModelConfigWarnings`, the reasoning-provider banner in `KBHealthWarnings`, the AI Models "unavailable until configured" copy) stay silent and the `EnterpriseUpsellNotice` (trial, sales, activate) is the one thing said instead.
18. **No workarounds**. XTM One is a generic platform: a behaviour is fixed at its cause, with a mechanism every agent, integration, language and model shares - never with a patch shaped like the incident that revealed it. In the generic layers (the agent loop and tool base classes in `tools/`, the built-in tools, memory, chat and assignment orchestration, prompt assembly), all of these are forbidden:
    - **vendor, integration or domain logic**: an integration or provider name, a vendor's error phrasing, a vendor's tool name, a channel adapter imported by name. What an integration needs is declared by the integration (its catalog entry, its provider module, its `ToolDefinition`) and read generically.
    - **keyword or regex lists reading natural language to decide behaviour** - the model's answer, the user's request, a title, a value - in one language or six. Ask for a structured answer (a JSON schema, a tool call), use a fact the platform holds (state, ids, timestamps), or let the model's decision stand.
    - **tool behaviour decided by the tool's name**, a fragment of it or its verb. The tool declares the property (`ToolDefinition`; the MCP annotations for an MCP tool).
    - **re-reading text the platform wrote itself**. Pass the fact as data (`ToolResult` fields, typed errors).
    - **code, constants or prompt text that exist for one run, one customer or one integration.**

    Invariant 16's "fix behaviour in code" means such a generic mechanism: a regex over prose is not deterministic code, it is a prompt in another form, and it fails silently on the next phrasing. Allowed: provider and channel adapters handling their own vendor's API, and identifier patterns used as security boundaries (secret redaction, the Nova rules, the tradecraft target guard), which match identifiers, not language. `backend/tests/test_no_workarounds.py` fails the build on an integration import, a provider or vendor-channel name, or a phrase list in a generic module; its exception lists only shrink.
