# Fleet fork and documentation (#9174)

Program: fork and documentation of fleets and skills, under the CTEM seeded fleets epic #8975. Seven slices: fleet fork backend (this file's first section), fork UI, "source changed" notice and diff, skill fork, fleet documentation model, About page with interactive diagram, AI-drafted documentation.

## 1. Fleet fork (slice 1)

`POST /api/v1/fleets/{id}/fork` (`app.api.v1.fleets.fork_fleet_endpoint`, gated by `require_agentic_ai` like agent duplicate) calls `app.services.fleet_fork.fork_fleet`.

- **One copy path.** Member agents are copied by `app.api.v1.agents.copy_agent_for_user`, the body of `POST /agents/{id}/duplicate` extracted so the two never drift: the copy manifest (`app.models.agent_copy`), v1 versions, bindings the forker cannot bind left out and counted, intent bindings. The manifest guard `tests/test_agent_copy_manifest.py` reads that function.
- **Members.** `copy`: every visible home member is copied; `_repoint_handovers` rewrites `handover_agent_ids`, `handover_types` and `handover_conditions` of the copies from source ids to copy ids. `keep`: the orchestrator is copied (a fleet needs a home entry agent, an agent has one home fleet) and every other member becomes a `connected` row, its role label as the collaboration instruction. A member the forker cannot see is left out with a warning.
- **Nothing runs.** Every copied assignment is `enabled=False` with `paused_reason="created_disabled"`, and its `trigger_config` loses `PROVISIONING_STATE_KEYS` (`app.agents.fleet_opt_in`): the source's OpenCTI / OpenAEV trigger ids stay with the source, so the copy's provisioning tick never removes or reuses them. Tripwire: `tests/test_fleet_fork_postgres.py`, the fork side of `tests/test_ctem_fleets_opt_in.py`.
- **Provenance.** `fleets.forked_from` (JSON, migration `f9174fleetfork1`): `fleet_id`, `slug`, `name`, `is_builtin`, `fingerprint`, `members`, `forked_at`. `fleet_fingerprint` hashes the structure a fork copies (card fields, members with role, parent, exposure, persona, skill ids and handovers by slug, connected links), never archiving, run defaults or timestamps. `source_changed(db, fork)` answers True, False, or None when the fleet is not a fork or its source is gone. Slice 3 renders it.
- **The fork is a normal fleet.** `is_builtin` is false on the fork and on every copied agent, so the seed (`app.agents.fleet_seed`) never reads or rewrites it.

## 3. Source changed since the fork (slice 3, backend)

- **Kept structure.** `forked_from.structure` holds `structure_snapshot(fleet_structure(...))` of the source at fork time: the same body the fingerprint hashes, each persona replaced by a 12-character digest so no persona text is copied into the provenance.
- **Diff.** `GET /api/v1/fleets/{id}/source-changes` (`fleet_source_changes_endpoint`, read only, the fleet visible to the caller) calls `source_changes(db, fork)`: `is_fork`, `source_exists`, `changed` (fingerprint comparison, null when unknown), `diff_available` and `changes`, one entry per object moved from `diff_structures(kept, live)`: `object` `fleet` | `member` (agent slug) | `connected` (agent or fleet id), `action` `added` | `removed` | `changed`, `fields` that moved. It names slugs, ids and field names, never a persona or a description.
- **Older forks.** A fork made before the structure was kept answers `changed` with `diff_available` false and no changes.
- Tests: `tests/test_fleet_fork_postgres.py` (diff by object and field, older fork, non-fork). The notice and the diff view on the fleet page are slice 3b.

## 3b. The notice on the fleet page (slice 3b, frontend)

- **Where.** `FleetSourceChangesNotice` (frontend/src/components/fleets) renders under the header of a fork's page (`FleetPage`, only when `forkProvenance` is set). It reads `useFleetSourceChanges` (`GET /fleets/{id}/source-changes`, `retry: false`, `throwOnError: false`: a failed read hides the notice and never reaches the page's ErrorBoundary).
- **When.** `showSourceChanges`: a fork whose source still exists and whose `changed` is true. Not a fork, a source gone, nothing changed: no notice.
- **What.** An info `DashboardNotice` ("The built-in fleet X has changed since you duplicated it", X the source's current name: `currentSourceName` reads the renamed card when the name moved), "Your copy is not changed", "Open the original fleet" in the notice's trailing actions (`NoticeAction` with `to`, a route link with the button look), and a `<details>` with one line per change (`describeSourceChange`) and the fields that moved in the reader's language (`changedFieldLabels`, `FIELD_LABELS` marked `@i18n-keys`, `formatList`). An older fork (`diff_available` false) says the detail is not available. Nothing is applied to the copy: the reader carries a change over by hand.
- **Names, never ids.** The endpoint names a member by agent slug and a connected link by agent or fleet id. `sourceChangeNames` maps them to display names from the agents and fleets lists the page already loads (same cache entries): a member reads its agent's name (the slug only when the agent is not visible), a connected link reads "Connected agent X" or "Connected fleet X", and an id that resolves to nothing reads "A connected agent or fleet you cannot open", never the id.
- Tests: `fleet-source-changes.test.ts` (when it shows, each change line, member and connected names resolved, no id printed, the renamed source title, field labels deduplicated and unknown fields kept).

## 5. Fleet documentation model (slice 5, backend)

- **Storage.** `fleets.documentation` (JSON, migration `d9174fleetdocs1`, NULL until written): `sections` (key to markdown), `version`, `updated_at`, `updated_by` (a user id, `seed` or `fork`), `fingerprint`, `history` (the previous versions, newest `HISTORY_KEPT` = 10). `app.services.fleet_docs` holds every rule.
- **Sections.** `DOC_SECTIONS`, in reading order: `purpose`, `use_case`, `triggers`, `flow`, `members`, `approvals`, `outcomes`, `roi_units`, `quota_estimate`, `objects_created`, `prerequisites`, `switch_off`. An unknown key is refused (422), an empty section dropped, a section over 20,000 characters refused. Mode-neutral: nothing in the model is CTEM-specific, so a Copilot-mode fleet a user built documents itself the same way.
- **Who writes.** A built-in fleet: the seed only, from its entry's `documentation` (`seed_documentation` in `seed_builtin_fleets`; same text = no new version, the fingerprint follows the seeded structure); the API refuses a save (403, "duplicate the fleet to edit it"). A custom fleet: whoever manages it (`_manageable_fleet`). A fork: `fork_fleet` copies the source's sections as the fork's version 1 (`copy_documentation`, empty history).
- **Concurrency.** `PUT` carries the `base_version` the editor opened; a save over a newer version is refused (409).
- **Out of date.** The fingerprint hashes the fleet's structure (`fleet_fork.fleet_structure`) and its member configuration (fleet defaults: context inclusion, collaboration instruction, organization scope; each row's own overrides). `out_of_date` is true once either moved since the last save; a read never rewrites anything, the page offers a regenerate (slice 7), user-initiated.
- **Routes.** `GET /api/v1/fleets/{id}/documentation` (visible fleet) and `PUT /api/v1/fleets/{id}/documentation` (`sections`, `base_version`), both `require_agentic_ai_licensed`: no model call, so not AI-gated (`_EXEMPT_OWN_DATA_HOUSEKEEPING` in `tests/test_ai_disabled_read_surface.py`). The answer carries `section_keys`, `sections`, `version`, `updated_at`, `updated_by`, `editable` (a custom fleet the reader manages) and `out_of_date` (null while nothing is written). Nothing starts a run.
- **Not in this slice.** The seeded text of each built-in fleet, the About page with its diagram (slice 6), the AI draft and per-section regenerate (slice 7).
- Tests: `tests/test_fleet_docs.py` (sections, fingerprint, versions, 409, built-in read only, bounded history, out of date, seed, fork copy), `tests/test_fleet_fork_postgres.py` (a fork copies the documentation, a member configuration change marks it out of date, the source unmoved).

## 6b. The About view (slice 6b, frontend)

- **Where.** The fleet page's `About` view (`?view=about`, `lib/fleet-operations.ts`), beside Graph, Members, Schedule and Operations: always reachable after setup, built-in or custom, in Copilot and XTM One mode alike.
- **Read.** `FleetAboutView` reads `useFleetDocumentation` and draws one card per written section, in the API's `section_keys` order, as markdown (`MarkdownText`: no HTML, no image). The line above says who wrote it (Filigran for a built-in, the fork copy, or the version and its age). `out_of_date` shows an info notice: a built-in follows at the next platform update, a custom fleet is reviewed and saved again. "Open the graph" goes to the Graph view, the fleet's interactive diagram (members, handovers, live state).
- **Edit.** Only when `editable` (a custom fleet the reader manages): every section as a markdown field, Save sends the non-empty sections with the `base_version` it opened (`useSaveFleetDocumentation`). A refusal reads one sentence per status (`fleet-documentation.ts saveRefusal`: 409 stale, 403 built-in, 422 too long or unknown), the server's words behind Details. Nothing starts a run.
- **Not in this slice.** The AI draft and per-section regenerate (slice 7: 7a backend below, 7b the buttons).
- Tests: `components/fleets/fleet-documentation.test.ts` (titles, written sections, draft and save, refusals), `lib/fleet-operations.test.ts` (the `about` view in the URL).

## 7a. AI-drafted documentation (slice 7a, backend)

- **Route.** `POST /api/v1/fleets/{id}/documentation/draft` (`section` optional: one key of `DOC_SECTIONS` to regenerate, omitted drafts every section), on a fleet the caller manages, gated by `require_agentic_ai` like `POST /fleets/generate` (a model call). The answer is `sections` (the drafted keys, in reading order) and `notes` (keys dropped, sections cut, sections not drafted). **Nothing is saved**: the person reviews the draft in the editor and saves it through `PUT /fleets/{id}/documentation`, the one write path, so a draft never bypasses the `base_version` check.
- **Rules.** `app.services.fleet_doc_generation`: a built-in fleet is refused (403, duplicate it first) and an unknown section (422) before any model call; one call on the caller's own model (`get_llm_for_user`), user-initiated and counted like a chat, no run starts; unknown keys are dropped and noted, a section over 20,000 characters is cut. Generation never fails for the fleet's size (#11292): see the next bullet.
- **Never fails for its size (#11292).** Each call's output budget is the model's own ceiling (`output_budget`: `resolve_provider_max_output_tokens`, capped at `DRAFT_BUDGET_MAX` 32,768; `DRAFT_MAX_TOKENS` 8,192 when unknown). `ask` retries a transient provider failure (timeout, connection, 429, 5xx; not one marked `x-should-retry: false`) with backoff (`TRANSIENT_RETRIES` 2) through `retry_llm_call`, and continues an answer cut at its budget where it stopped (the partial answer handed back as the assistant's turn, `CONTINUATIONS_MAX` 2), the pieces joined. The one call stays the fast path; a whole draft still cut, unreadable or failed is drafted in parts (`sections_in_parts`): the sections asked together, split in halves while cut or unreadable, down to one section asked in plain markdown (`_one_section_markdown`), kept as written back to its last whole line when still cut (a `section_cut` note), never an error. The structured parts are asked on their own (`_structured_only`) and, still cut, by half of `MODEL_PARTS`; none written = the computed blocks from the configuration (`structured_cut`). A section the provider still fails on is `pending` on the draft: `regenerate_fleet_documentation` saves the rest (a pending section keeps its current text on a regenerate), and the route, the tool and the generation at creation hand it to `fleet_doc_on_create.schedule_pending_sections` after the commit, which regenerates each pending section on its own in the background (`PENDING_RETRY_DELAYS` 30 s, 120 s, 300 s) under the same generation marker, so the page spins while it fills. Only nothing produced at all raises `FleetDocDraftError`, with one line naming the cause (`The AI model did not answer: <provider reason>`); no raised message names a cut or tells the person to work around the tool (guard in `tests/test_fleet_doc_generation_never_fails.py`).
- **What the model reads.** `draft_context`: the fleet's name, description and skills; each member by name and slug (never an id) with its role label, orchestrator flag, parent, exposure, description, a persona excerpt of at most 600 characters, its handovers, its effective member configuration (conversation shared, collaboration instruction, organizations: the row's override else the fleet default) and its assignments (name, trigger, on or off); each connected agent or fleet with its instruction. At most 40 members and 60 assignments. The current sections are given too, so a regenerate keeps the page coherent and writes in its language. Mode-neutral: a Copilot-mode fleet a user built drafts the same way.
- **Not in this slice.** The "Generate documentation" and "Regenerate section" buttons in the About editor (slice 7b, UX gate).
- Tests: `tests/test_fleet_doc_generation_never_fails.py` (#11292: continuation joined, a large fleet on a 4k model drafted in parts and complete, budget read from the model, transient retry, pending section with the rest saved, the honest one line, background fill, the no-cut-error guard); `tests/test_fleet_doc_generation.py` (built-in and unknown section refused before the model, whole draft and one-section regenerate, nothing written, parsing and cuts, an answer always cut still drafts every section, context carries configuration and no id, route AI-gated).

## 7c. One generator writes the sections and the structured parts (#9768 S1, backend)

- **Output.** A whole draft (`section` omitted) now answers `structured` too: the `StructuredDoc` parts the About page draws (purpose and outcome lines, trigger cards, steps with gates, gates, objects by module, prerequisites, quota) plus two new parts, `automations` (name, member, trigger, schedule in plain words, event and filter, on/off, run as) and `integrations` (per member: integration providers, MCP servers, built-in tool groups, skills, by name). A one-section regenerate answers `structured: null` and keeps the stored parts.
- **Facts computed in code first.** `draft_context` adds `automations` (`automation_facts`: the cron read by `describe_cron`, an unusual cron named as is), `schedule_quota` (`schedule_quota`: the ticks of the cron over 30 days, labelled an estimate, `runs_min` 0 when the automation is off), `tools` (`tool_use_facts`, names resolved by `_names_of_bindings`, never an id) and `approvals` (`approval_facts`: human in the loop, tool call approval, per automation). The model narrates them and maps the rest; it never overrides them.
- **Validation.** `build_structured` validates the model's mapping item by item with `clean_structured`: an item with an unknown module, an unknown prerequisite check, `runs_max` below `runs_min` or a value too long is dropped and named in `notes`, never guessed; `automations` and `integrations` always come from the configuration, a schedule's quota always from its cron.
- **Answer shape.** `{"sections": {...}, "structured": {...}}` when the structured guide is sent; the flat shape (one key per section) still parses. The lab stub (`doc_draft_answer`) answers both.
- **Next slices.** S2 removes hand editing and saves the generated parts; S3 adds `regenerate_fleet_documentation`; S4 the PDF datasheet; S5 the built-in seeds from this generator.
- Tests: `tests/test_fleet_doc_generation.py` (cron in words, schedule quota, automation facts with no id or secret, tools and approvals by name, item-by-item validation with computed facts on top, whole draft vs one section), `tests/test_lab_doc_draft.py`.

## 7d. The fleet tool for orchestrators (#9768 S3, backend)

- **Tool.** `regenerate_fleet_documentation(fleet_id, section?)` in the `fleets` suite (`builtin_tools/fleets.py`, alias of the platform group): the same `fleet_doc_generation.regenerate_fleet_documentation` the About page's button calls, saved as the next version and audited (`via: agent`). Permission of a configuration edit (owner, `config` grantee, admin); a built-in fleet is accepted and gets a local version, as on the page. A cut or refused generation saves nothing. A generation already running (the `fleet_doc_on_create` marker) is refused with its start time and elapsed time, no ETA (it ends when every section is answered), and the stuck window: the marker expires `GENERATING_TTL_SECONDS` after its worker's last refresh, then a new call starts; `get_fleet` and every fleet write answer carry the same `documentation_generating` line while one runs (`generation_text`).
- **Cost.** One model call on the caller's own model inside the calling run's tool call: counted on that run (or the chat), never a run of its own. Nothing regenerates on view, boot or schedule.
- **Out-of-date hint.** `documentation_hint(db, fleet)`: when the stored fingerprint differs from `current_fingerprint`, every fleet write answer (`_describe`: `update_fleet`, `set_fleet_members`, `set_fleet_exposure`, `set_fleet_member_parent`, `move_fleet_member`, `create_fleet`) and an applied `apply_fleet_spec` end with `documentation_out_of_date: true` and the call to make. A fleet with no generated documentation gets no hint.
- **Schema budget.** The tool's ~400 characters were paid by shortening six fleet tool descriptions (no meaning lost); `backend-schema-budget` stays under 441,000.
- Tests: `tests/test_fleet_tools.py` (custom and built-in fleet regenerate with notes and commit, refused generation rolled back, hint shown only when the fingerprint moved).

## 7e. The one-page PDF datasheet (#9768 S4)

- **Route.** `GET /fleets/{id}/documentation/datasheet.pdf` (read access to the fleet, licence-gated, not AI-gated): 404 while the fleet has no documentation. The About page's **Export PDF** button (top right, next to Version history) saves it under `<fleet-name>-datasheet.pdf`.
- **Content.** `services/fleet_datasheet.py` builds one A4 HTML page from the stored documentation and live state read by the route: hero (product, name, status from the automation counts, purpose and outcome lines), a fixed left-to-right mini graph of the member tree (names the reader may see, others "Agent"), triggers, steps with their approval gates, integrations and tools per member, objects by module, the evaluated prerequisites, automations on, the quota range (sum of the quota lines, labelled an estimate), the unit of work, and "Generated on <date>, version N". A part the documentation does not hold reads "Not stated in the documentation".
- **One page.** Each list is capped (`CAPS`) with "+N more", each text cut at `TEXT_CAP`; `pdf_render.render_document_to_pdf(document, first_page_only=True)` prints page 1 only (`page_ranges="1"`), on the same locked-down renderer (JavaScript off, network aborted). Printed light whatever the reader's theme.
- **Cost.** No model call and no quota; the export rate limit of the other PDF exports applies.
- Tests: `tests/test_fleet_datasheet.py` (status, every part shown, missing parts named, caps, escaping, fixed mini graph, safe filename, page 1 only with JavaScript off, licence gate), `frontend/src/components/fleets/fleet-about-focus.test.tsx` (the button downloads the server's PDF, no button before the first version).

## 7f. Built-in seeds from the generator, orchestrator guidance (#9768 S5, backend)

- **Seeds.** `fleet_seed.seed_builtin_fleets` passes each built-in fleet's shipped parts (`builtin_fleet_structured`) through `_with_computed_facts`: `fleet_doc_generation.load_draft_context` on the seeded fleet, then `with_computed_facts`, the same merge `build_structured` applies to a regenerated draft. A built-in fleet therefore ships the generator's `automations` table, `integrations` per member and the cron-computed quota of each schedule; a duplicated built-in fleet regenerated by AI renders the same blocks. The narrative (sections, purpose, steps, gates) stays the reviewed shipped text. A failed context read keeps the shipped parts and logs a warning; a local version is never overwritten (`seed_documentation`).
- **Orchestrators.** The persona of every built-in fleet orchestrator (four CTEM persona files and the posture orchestrator in `builtin_agents.py`) ends with: after a configuration change, call `regenerate_fleet_documentation` once. `generate_fleet_spec` answers the same step after the apply.
- Tests: `tests/test_fleet_docs_seed_s5.py` (computed facts on top of the shipped parts without mutating them, one merge shared by the generator and the seed, a failed read keeps the shipped parts, every built-in orchestrator names the tool).

## 7e. Visual parity of a regenerated corporate fleet (#9979)

- **Root cause.** On a corporate fleet (7 members, about 60 automations, Outlook, Teams, GitHub, Notion and platform events) the model answered one trigger card per automation. `build_structured` checked items one by one, then the merged block once more with `clean_structured`, where the list caps (`triggers` 20, `steps` 20, `gates` 20, `objects` 10) apply: that last pass refused and the WHOLE block was dropped, the computed automations, integrations and schedule quota included, so the page fell back to markdown everywhere. A trigger or an object in Outlook, Teams or GitHub could not be expressed at all (`DocModule` knew six values).
- **Modules.** `fleet_docs.doc_modules()`: the base modules (`opencti`, `openaev`, `opencrq`, `schedule`, `work_item`, `platform`, `webhook`, `manual`) plus every provider key of `integration_catalog.PROVIDER_CATALOG`. Anything else is refused, never remapped. The page draws a provider with `ProviderLogo` and its `PROVIDER_DISPLAY_NAMES` brand (`moduleLabel`), the datasheet with the catalog name (`fleet_datasheet.module_label`).
- **Field by field.** `clean_structured_fields`: each field is validated on its own and a list longer than its cap is cut to it with a note ("structured 'triggers': 20 of 45 kept"); one wrong field costs that field only. The computed facts always survive.
- **Derived parts.** `draft_context` carries `trigger_cards` (one card per enabled automation, its module from the provider or the trigger kind, grouped one per module past the cap: "Daily brief and 29 more"). When the model gives no triggers, steps or gates, `with_derived_parts` writes the trigger cards, steps (orchestrator, then members) and gates (the members' approval settings) and says so in the notes.
- **Second call.** A whole draft whose answer carries no `structured` part (flat shape, budget spent on the sections) asks for the parts in one more call (`STRUCTURED_ONLY`); still none, the parts come from the configuration, noted.
- **Version notes.** `fleets.documentation.notes` keeps what the generator left out, cut or derived, and `lost_blocks` adds "this version has no <block>: the version it replaces had them". `GET /documentation` returns `notes` to a reader who manages the fleet only; the About view shows them in a notice (warning with Regenerate when a block was lost).
- Tests: `tests/test_fleet_docs_visual_parity.py`, `components/fleets/fleet-about-showcase.test.ts` (`moduleLabel`).

## 7b. Generate and regenerate in the About editor (slice 7b, frontend)

- **Where.** The About view's editor (`FleetAboutView.tsx`, `FleetDocumentationEditor`), open only on a custom fleet the reader manages (`editable`). "Generate documentation" above the fields drafts every section; "Regenerate section" under each field drafts that one (`useDraftFleetDocumentation`, `POST /fleets/{id}/documentation/draft`).
- **Never saved by itself.** The answer fills the fields (`fleet-documentation.ts applyDraft`: a drafted section replaces its field, every other field keeps what the person typed, unknown keys are ignored); an info notice counts the sections drafted and offers "Undo the draft" (the fields as they were before the last draft). The save stays the Save button (`PUT` with `base_version`). Save is disabled while a draft is on its way.
- **AI off.** Both buttons are disabled with the shared `AiDisabledTip` (`useAiActionDisabled`), the route being `require_agentic_ai`. One model call per click, counted like a chat; nothing calls it on its own, no run starts.
- **Refusals.** `draftRefusal`: 422 (cut, empty or unreadable answer, unknown section) reads "The model could not draft this...", anything else a plain retry; the server's words behind Details. The built-in 403 cannot reach the editor (it opens on a custom fleet only).
- Tests: `components/fleets/fleet-documentation.test.ts` (a draft replaces only its sections and leaves the input untouched, a one-section regenerate changes that section alone, a refused draft reads one sentence).

## 8. About page redesign, S1: structured documentation and the live checklist (backend)

The About page redesign (design `fleet-about-redesign-design.md`, UX verdict of 7 Nov 2026: B1-B5) draws trigger cards, a stepper with gate markers, short definition tables, a live checklist and a quota range. This slice gives it the data; the markdown sections stay the contract and the fallback.

- **Model.** `fleets.documentation.structured` (optional, no migration: the JSON column already holds the document), validated by `fleet_docs.StructuredDoc` (`extra=forbid`): `purpose_line`, `outcome_line`, `triggers` (`module` among `opencti`, `openaev`, `opencrq`, `schedule`, `work_item`, `platform`; `name`; `filter` in plain words; `detail` for a key or a cron, shown in a tooltip, UX advisory A2; `automation_slug`), `steps` (`title`, `detail`, `gate`), `gates` (`action`, `module`, `approver`), `objects` (`module`, `objects`), `prerequisites` (`check` among `PREREQUISITE_CHECKS`, `label`, `fix_route`: an app route only), `quota` (`trigger`, `basis`, `runs_min` <= `runs_max`). An invalid part is refused (422) by `clean_structured`.
- **Writes.** `save_documentation(..., structured=)`: omitted keeps the stored parts (an editor that sends only markdown never erases them), `{}` clears them; versioned with the sections (`history` keeps them). `seed_documentation(..., structured)`: a change of the structured parts alone is a new seed version. `copy_documentation`: a fork copies them. `PUT /fleets/{id}/documentation` takes `structured`.
- **Built-in fleets.** `builtin_fleet_docs.BUILTIN_FLEET_STRUCTURED` for the five CTEM fleets (an entry's own `documentation_structured` wins); tests hold every trigger name to the markdown triggers section and to one quota line, and a gated step to a listed gate.
- **Live checklist.** `app.services.fleet_about.evaluate_prerequisites`: for the reader, `integration:<provider>` = a connected integration of that provider the reader can see (`user_visible_query`), `profile:<field>` = the field filled in the primary organization profile, `profile:tracked_organizations` = a tracked organization with monitoring on, `manual` = never evaluated (`met: null`). Each check is read once per request. Rows only: no run, no model, so viewing the page costs no quota. `GET /fleets/{id}/documentation` answers `structured` and `prerequisite_states`.
- **Not in this slice.** The UI (S2 hero and sections, S3 flow lanes), the editor and AI draft of the structured parts (S4), the agent About card (S5).
- **Derived live checklist (#10258 S1).** `fleet_about.live_prerequisites(db, user, fleet, documented)` computes the checklist from the home members' configuration, never from the model: one `binding:<integration id>` line per bound integration (its members listed, `integration_state`: present, `connected`, token not expired without a refresh token), one `template:<provider>` line per template binding (the reader's own connected account), one `agent_account:<id>` per agent account bound to a member (`agent_account_state`: enabled, integration kept, status `active`), one `handover:<agent id>` per handover to an agent outside the fleet (target present and enabled), `kb:<id>` and `mcp:<id>` (`mcp_state`: enabled, OAuth signed in), `automations:enabled` when the fleet has automations, and the documented `profile:*` lines. A documented `integration:<provider>` line is replaced by the bindings; documented `manual` lines are kept as `to_confirm`, at most `MANUAL_LINES_KEPT` (2). States: `met`, `not_met` (with `reason` in plain words), `unreadable` (a row not shared with the reader, another person's agent account: never shown met), `to_confirm`. Each line carries `member_ids`, `provider` (the logo) and `fix_route` (a real path: `/integrations/<id>`, `/profile/agent-accounts/<id>`, `/agents/<id>/config`, `/knowledge/<id>`, `/mcp-servers/<id>`, `/flows/fleets/<id>`). Served as `live_prerequisites` on `GET /fleets/{id}/documentation` beside `prerequisite_states` (kept for the current page until S2). Rows only: no run, no model, no quota.
- **The About prerequisites UI and the agent tool (#10258 S2, S3).** `FleetAboutPrerequisites.tsx` renders `live_prerequisites` when present (else the documented `prerequisite_states`, unchanged): lines not met first, then not shared with you, then met (`fleet-prerequisites.ts`, `prerequisiteGroups`); each line wears its provider logo, "Needed by <members>" from the health rows, the reason when not met and a "Fix it" link to `fix_route`; `to_confirm` lines sit apart under "To confirm" and are never counted. The hero's status band shows `FleetPrerequisitesChip`: "Prerequisites met/total" with "Fix with AI" while a line fails, "All prerequisites met" and nothing else once every checked line is met. Fix with AI opens a new chat (`useAskAssistant`) whose composer holds the request and the failing lines, for the person to send; without agentic AI it links to the first failing line's `fix_route`. The agent reads the same checklist with `get_fleet_prerequisites(fleet_id)` (platform group, `fleets` alias): the visible-fleet permission of `get_fleet`, `live_prerequisites` for the caller, one line per prerequisite `[state] label; reason; members; fix at <route> (check)`, no commit, no model call, no quota. Tests: `tests/test_fleet_about_live_10258.py`, `tests/test_fleet_tools.py`, `FleetAboutPrerequisites.test.tsx`.
- **The fleet's own automations, repaired entries, live checks (#10094).** `draft_context` and `load_draft_context` read the assignments of the HOME members only (`role == "member"`): a connected agent belongs to another fleet, it stays under `connected` (the flow graph) and never reaches `automations`, `trigger_cards` or `schedule_quota`, so the quota headline is the fleet's own estimate. `group_quota` keeps the largest rows on their own line past `QUOTA_ROWS_MAX` and groups the smallest (total unchanged). `build_structured` repairs instead of dropping: an invalid AI trigger entry is replaced by the computed `trigger_cards` the model's valid cards do not name (`repaired_triggers`, no `part_item_left_out` on triggers), a quota row with `runs_max` below `runs_min` is put in order (`repaired_quota`), an invalid row of a schedule is skipped because its row is computed; `typed_prerequisite` turns a `manual` or unknown line whose label names one catalog provider and a connection ("OpenCTI connected") into `integration:<provider>`, an unknown check into `manual` with its label kept. The "Switch on the automations" line is `automations:enabled`, evaluated by `evaluate_prerequisites(..., fleet=)` from `fleet_automation_counts` (met once one home automation is on). Stored versions render unchanged until regenerated. Tests: `tests/test_fleet_docs_visual_parity.py`, `tests/test_fleet_about.py`, `tests/test_fleet_doc_generation.py`.
- **The quota is computed only (#10148).** When the context carries the computed `quota` (one row per home automation, #10108), `build_structured` never validates the model's quota rows: they are only the estimates `_computed_quota` reads by automation name for an event-driven automation with nothing observed (an int within 0 to 100,000, never a bool, `runs_min <= runs_max`), and `with_computed_facts` writes exactly the computed rows, grouped past `QUOTA_ROWS_MAX`. ## 9. Suggestions: one count, dismissals that lapse on their own part (#12099, backend)

- **One count.** `fleet_docs.manager_suggestions` is the single reader of a fleet's open suggestions: the stored findings, the good-practice suggestions computed live and, through `fleet_doc_findings.with_lapsed`, every lapsed dismissal (a shown row is tagged `lapsed` with its reason; a lapsed dismissal whose finding a regeneration dropped is given back from its record, never a good-practice kind). `open_suggestion_count` is its length: the About page chip (`documentation_view`), the header of `list_fleet_doc_findings`, a line of `get_fleet` and of `get_fleet_health` (managers only) all read it, so a lapsed row is never under "0 suggestion(s)".
- **Only what the reader can change.** Every suggestion kind, computed or written by the model, names the surface its fix changes (`fleet_practice_suggestions.KIND_SURFACES`). On a built-in fleet `suggestion_editable` keeps only the surfaces the built-in lock leaves to the customer (`builtin_editable_surfaces`, read off `BUILTIN_FLEET_WRITABLE_FIELDS` and `INTEGRATION_LAYER_FIELDS`: `missing_integration` and `no_gate_on_sensitive_action` today); a built-in member of a custom fleet loses its mechanics suggestions the same way. The generation prompt is unchanged: its findings are filtered after, in `manager_suggestions`, so the chip, the list, `get_fleet` and the fleet health keep one count. A fork is a normal fleet and keeps every kind.
- **Dismissable by the id shown.** `dismiss_findings` accepts the id of a lapsed row the list shows, stored or not; the new record takes the current print.
- **A dismissal lapses on its own part.** `member_fingerprints` also stores one print per facet (`<member>#card`: name, description, persona; `#tools`: tools, integrations, MCP servers, skills, handovers, approvals, automations; `#config`: everything but the role label). A dismissal records the facet of its kind (`KIND_FACETS`: `description_mismatch` card; `no_gate_on_sensitive_action`, `missing_automation`, `missing_integration` tools; any other kind config) and lapses only when that print changes or after 90 days; a role label edit lapses none. A record of the former shape (no `print_facet`) still compares the member's whole print.
- **The draft reads the current connected instruction.** `draft_context` gives each connected row its effective settings (`effective_member_settings`: its own instruction, else the fleet default), and the previous version is handed to the model under `CURRENT_DOC_HEADER`: for tone and language only, the fleet's facts win.
- Tests: `tests/test_fleet_doc_findings_lapse_count_12099.py` (tool header = About page chip = shared count on one fleet, the facet rules, dismiss by the shown id, the connected instruction, the prompt header).

## 10. Former dismissals settled, fixed points dropped, the text readable (#12181, backend)

- **Former records settled.** A dismissal recorded before #12099 has no `print_facet` and compares the member's whole print, role label included. `fleet_doc_findings.settled_dismissals` moves each such record to the print of its kind's facet while it still holds; `fleet_docs.settle_dismissals` runs it before every member edit (`fleets.update_member`, `fleets.set_exposed_agents`), `dismiss_findings` and a whole regeneration run it on the records they write. A role label edit then lapses no dismissal; a lapsed former record is left as is.
- **A fixed point is dropped at regenerate.** A whole regeneration reads every member as it is now: `without_unraised_lapsed` drops a dismissal lapsed by a change of its member's part whose point the new findings no longer raise, so `with_lapsed` gives nothing back and the counts fall with it. A point raised again, a dismissal lapsed by age and a good-practice record are kept.
- **The text, readable.** `list_fleet_doc_findings` action `read` answers the stored sections (`fleet_docs.documentation_text`), with `member` only the lines naming it; a read, no write.
- Tests: `tests/test_fleet_doc_dismissal_settle_12181.py`.
