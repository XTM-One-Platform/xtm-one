# Phase 0 Research: Harden OpenSandbox Docker Images

## 1. Multi-stage build shape for `Dockerfile.sandbox.python`

**Decision**: Two-stage build. A `builder` stage (`FROM <pinned base> AS builder`) installs the full apt package list (base or extended) plus `pip install --no-cache-dir -r <requirements>` into a dedicated virtualenv at `/opt/venv`. The final stage starts fresh `FROM <pinned base>`, installs only the runtime-needed apt subset, and runs `COPY --from=builder /opt/venv /opt/venv`, then sets `ENV PATH="/opt/venv/bin:$PATH"`.

**Rationale**: A virtualenv copy is the simplest artifact to move between stages for Python (no need to hand-pick individual compiled `.so` search paths the way a Go/Rust binary copy would), and it cleanly separates "what pip needed to build wheels" from "what's importable at runtime." This mirrors the multi-stage precedent already in the repo (`Dockerfile`'s frontend-build → final-stage `COPY --from=frontend-build`).

**Alternatives considered**:
- *Single stage with a cleanup `RUN apt-get remove` at the end*: rejected — removed packages still bloat earlier image layers (layers are immutable once written), so the final image size/attack-surface reduction is far weaker than a true multi-stage copy, even though the installed-package *list* looks the same.
- *`pip install --target=/deps` instead of a venv*: rejected — some packages (`spacy`, `pydantic`) do import-time work assuming a normal site-packages/venv layout; a plain `--target` copy risks subtly breaking entry points. A venv copy is the more battle-tested pattern.

## 2. Classifying `apt.sandbox.extended.txt` into build-only vs. runtime-needed

**Context**: `apt.sandbox.extended.txt` is not tied to one image — per `create-register-images.sh` it's the `APT_FILE` for the `sandbox-python-data`, `sandbox-python-malware`, and `sandbox-python-network` builds (each paired with its own `REQ_FILE`); `sandbox-python-cti`, `-rules`, and `-soar` use `apt.sandbox.base.txt` instead. The builder-vs-runtime split below applies to the apt *file*, and thus to whichever domain image consumes it — it is not specific to a single "extended" tag.

**Decision**: Every package in `apt.sandbox.extended.txt` is installed in the `builder` stage (needed to compile wheels that lack prebuilt manylinux binaries for the pinned Python version). The **final** stage's apt install list — for each of `sandbox-python-data`, `-malware`, `-network` — is the runtime-needed subset only:

- Runtime-needed (shared libs the compiled wheels dlopen at import/use time): `libmagic1`, `libfuzzy2`, `libpcap0.8`, `libgl1`, `libglib2.0-0`, `libgomp1`, `libssl3`/equivalent, `libgdal`-runtime package, `libgeos`-runtime package, `proj-data`. Kept in all three (`data`/`malware`/`network`) since the split apt file doesn't vary per domain today.
- Runtime-needed CLI tools, kept **only in `sandbox-python-network`'s final image**, per the spec Clarifications: `tshark` (used by `pyshark`), `nmap` (used by `python-libnmap`) — `requirements.sandbox.data.txt` and `requirements.sandbox.malware.txt` don't need them, so `sandbox-python-data`/`-malware` drop them from the final stage even though they share the same `apt.sandbox.extended.txt` builder list.
- Build-only (compiler/headers, dropped from every final stage): `gcc`, `g++`, `make`, `cmake`, `python3-dev`, `pkg-config`, every `*-dev` package (`libssl-dev`, `libffi-dev`, `libkrb5-dev`, `libmagic-dev`, `libfuzzy-dev`, `libpcap-dev`, `libtsk-dev`, `libewf-dev`, `libafflib-dev`, `libvhdi-dev`, `libvmdk-dev`, `libgdal-dev`, `libproj-dev`, `libgeos-dev`, `libjpeg-dev`, `libtiff-dev`, `libhdf5-dev`, `libxml2-dev`, `libxslt1-dev`), `gdal-bin` (CLI, build/verification convenience only — not imported by any listed package), `openssh-client`.
- `git`: build-only for `data`/`malware`/`network` (used by `pip install` VCS refs, not by any package in those requirement files at runtime). **Correction after implementation** (see §3a): `sandbox-python-rules` directly depends on `GitPython`, which shells out to the real `git` binary at *import* time (`git.refresh()`), not just when a repo operation is invoked — this was missed here and only found by actually building and importing. `git` is therefore a second documented runtime-CLI exception, scoped to `sandbox-python-rules`.
- **Correction after a post-review code pass**: `libkrb5-dev` (line above) and `libtsk-dev`/`libewf-dev`/`libafflib-dev`/`libvhdi-dev`/`libvmdk-dev` (line above) are *not* purely build-only — `requests-kerberos` (network) and `pytsk3`/`dfvfs`/`plaso` (malware) dlopen their compiled `.so` counterparts (`libkrb5-3`/`libgssapi-krb5-2`, `libtsk19t64`/`libewf2`/`libafflib0t64`/`libvhdi1`/`libvmdk1`) at import/use time. Missed here for the same reason as `git` above — inspecting requirements files, not actually running the built image and importing everything. Unlike `git`/`tshark`/`nmap`, these aren't CLI-shell-outs, just runtime shared libraries the compiled C extensions link against — same category as `libmagic1t64`/`libgdal36` elsewhere in this list, just domain-specific rather than shared across `data`/`malware`/`network`.

`sandbox-python` (base), `sandbox-python-cti`, `-rules`, `-soar` all use `apt.sandbox.base.txt` (`gcc`, `libfreetype6`, `libpng16-16`): `gcc` is build-only and dropped from all four; `libfreetype6`/`libpng16-16` are `matplotlib`/`pillow`-family runtime shared libs and stay in all four final images.

Mechanically, this classification is captured as new final-stage-only files, selected per tag via a `RUNTIME_APT_FILE` build-arg rather than re-derived from `REQ_FILE` at build time: `apt.sandbox.base.runtime.txt` (`libfreetype6`, `libpng16-16` — base/`cti`/`rules`/`soar`) and `apt.sandbox.extended.runtime.txt` (the shared-lib set above — `data` only). **Post-review**: `malware` and `network` turned out to each need their own tag-specific additions on top of that shared-lib set (DFIR libs; `tshark`/`nmap`/`libkrb5`, respectively — see the correction note above), so they get their own full copies, `apt.sandbox.malware.runtime.txt` and `apt.sandbox.network.runtime.txt`, rather than sharing `apt.sandbox.extended.runtime.txt` with `data`.

**Rationale**: This mirrors the actual `import`/runtime behavior of the packages that pulled each apt entry in (per each requirement file's own section comments), rather than a blanket guess, and accounts for one apt file backing multiple differently-scoped domain images. The `tshark`/`nmap` exception is the one already resolved in spec Clarifications, now scoped precisely to `sandbox-python-network`.

**Alternatives considered**: Automated `ldd`-based detection of the runtime shared-library set (scan every installed `.so`/wheel for missing dependencies post-strip) — more precise in principle, but adds a nontrivial CI-time discovery step for a one-time classification; the manual mapping above is verifiable by building the extended image and running the User Story 1 acceptance scenario (import every package), which is the same validation an automated approach would need anyway. This is exactly what happened in practice — see §3a.

## 3. Minimal/hardened base image evaluation (User Story 2)

**Decision**: Adopt digest-pinning immediately for both Dockerfiles' current bases (`python:3.14-slim`, `node:22-slim`) as the P2 baseline, across every tag built from them (all 7 `sandbox-python*` tags share one `FROM` line in `Dockerfile.sandbox.python`, so pinning it once covers all of them). Evaluate `cgr.dev/chainguard/python` as the hardened-base candidate for the **final stage used by the `sandbox-python` (base), `sandbox-python-cti`, `-rules`, and `-soar`** builds (the four that only need `apt.sandbox.base.txt`) and for the **Node.js** image (small, actively-patched, non-root by default, glibc-based so manylinux wheels install normally). Do **not** move **`sandbox-python-data`/`-malware`/`-network`** (the `apt.sandbox.extended.txt`-based images) off `python:3.14-slim` in this feature: their package set includes GDAL, TensorFlow, HDF5, DFIR tools (`plaso`, `pytsk3`), and other packages with complex native build/runtime footprints that Debian-slim is known to package cleanly and that would need individual verification against Wolfi/Chainguard's package set — that verification is out of proportion to a single feature and is exactly the case the spec's Assumptions section anticipates ("extended variant may retain a fuller base... documented rather than silently dropped").

**Correction after implementation** (§3a): two of the four candidates for `final-minimal` didn't actually work there. `sandbox-python-cti` and `sandbox-python-rules` both ended up on `final-full` instead, for reasons unrelated to the base-image evaluation itself (see §3a) — only `sandbox-python` (base) and `sandbox-python-soar` actually ship on `final-minimal` today.

### 3a. Empirical findings from actually building and running the images (2026-08-10)

This plan initially assumed `final-minimal` (Chainguard) could run `RUN apt-get`/`useradd` like a normal Debian stage. It cannot — `cgr.dev/chainguard/python`'s non-`-dev` tag is genuinely distroless: no shell, no package manager, nothing beyond the Python interpreter and its stdlib. Building against it directly revealed:

- **No shell at all.** `docker run --rm --entrypoint sh cgr.dev/chainguard/python:latest -c "..."` fails with `exec: "sh": executable file not found`. Every verification command (build-tool absence, non-root check, tshark/nmap check) had to be rewritten to run through the image's own `python3` (`docker run --rm --entrypoint python3 <image> -c "..."`, using `shutil.which()`/`os.getuid()` instead of `which`/`id`) — this is the one invocation shape that works uniformly across both `final-minimal` and `final-full`. `Dockerfile.sandbox.python`'s final-minimal stage has no `USER`/`useradd` step for the same reason: it's impossible to run there, and unnecessary, since the base image already defaults to UID 65532 (`nonroot`).
- **The venv's own `bin/python` symlink is broken across bases.** `python -m venv` creates `/opt/venv/bin/python` as a symlink to the *builder's* interpreter path (`/usr/local/bin/python`, from `python:3.14-slim`) — that path doesn't exist in Chainguard's filesystem (`/usr/bin/python` there). Fix: for `final-minimal` only, `COPY --from=builder /opt/venv/lib/python3.14/site-packages /usr/lib/python3.14/site-packages` (straight into the base image's *own* site-packages, matching its Python minor version), rather than copying the whole venv. `final-full` doesn't have this problem — it's the same Debian base as `builder`, so the standard `COPY --from=builder /opt/venv /opt/venv` + `PATH` approach works unmodified.
- **matplotlib works on `final-minimal` with zero system libraries installed.** Empirically confirmed (`numpy`/`pandas`/`matplotlib`/`scipy`/`tabulate`, including an actual `Agg`-backend render) — its manylinux wheel bundles its own freetype/png. `apt.sandbox.base.runtime.txt` (`libfreetype6`, `libpng16-16t64`) is therefore not consumed by anything today; it exists purely as the documented fallback recipe if a future matplotlib version stops bundling them and a base/soar-family tag needs to move to `final-full`.
- **Two real runtime-CLI needs were found that this document's original classification missed, both by actually building the image and importing every package — not by reading requirements files:**
  - `sandbox-python-cti`: `pycti`'s own `__init__.py` eagerly imports `python-magic` (not a direct dependency in `requirements.sandbox.cti.txt` at all — pulled in transitively), which needs `libmagic.so` at import time. `final-minimal` has no package manager to provide it. **Fix**: moved `sandbox-python-cti` to `final-full` with a new `apt.sandbox.cti.runtime.txt` (`libmagic1t64`). Confirmed this is a **pre-existing gap, not a regression**: even a plain `python:3.14-slim` (no hardening at all) never shipped `libmagic1`, so `pycti` was already broken in the original single-stage image — this fix is a net improvement, not a preserved-behavior requirement.
  - `sandbox-python-rules`: `GitPython` (a direct dependency) calls `git.refresh()` at import time, which requires the real `git` binary on `PATH` — not just at `pip install` time as originally assumed in §2. **Fix**: moved `sandbox-python-rules` to `final-full` with a new `apt.sandbox.rules.runtime.txt` (`git`), and added `git` as a second documented runtime-CLI exception (hardening guideline rule 2), scoped to `sandbox-python-rules` only.
- **`node:22-slim` already ships a `node` user/group at UID/GID 1000.** The original plan to `useradd -u 1000` a new `sandboxuser` collided with it (`groupadd: GID '1000' already exists`, exit code 4). Fixed by reusing the existing `node` user instead of creating a second one.

Net result: of the four tags planned for `final-minimal`, two (`sandbox-python`, `sandbox-python-soar`) actually work there; two (`sandbox-python-cti`, `sandbox-python-rules`) needed the documented `final-full` fallback for reasons specific to their own dependencies, not a general failure of the Chainguard base. This is exactly the case this section's original "Correction after implementation" note and the spec's Assumptions section anticipated in the abstract — the concrete reasons just turned out to be transitive `libmagic`/`git` needs rather than the GDAL/TensorFlow-scale concerns originally worried about.

**One more fix, found by a post-implementation question**: Docker builds the *last* stage defined in a Dockerfile when `--target` is omitted. `final-minimal` was originally defined before `final-full`, so a plain `docker build -f Dockerfile.sandbox.python -t sandbox-python:0.2 .` with no flags at all — the exact zero-config ergonomic the original single-stage Dockerfile's own usage comment advertised — silently built `final-full` instead of the intended hardened minimal image. Fixed by reordering the stages (`builder` → `final-full` → `final-minimal`), with no change to `sandbox-images.json`/`create-register-images.sh`/CI (they always pass `--target` explicitly, so were never affected). Verified: zero-flag build now produces `final-minimal` (uid 65532, no `gcc`, all base imports clean).

Practically, since all `sandbox-python*` tags are produced from the *same* `Dockerfile.sandbox.python` via build-args, this means the final stage's base image itself becomes conditional on which tag is being built — implemented as two named final-stage build targets (`final-minimal` FROM Chainguard, `final-full` FROM slim), selected per tag via `docker build --target final-minimal|final-full` (a `final_target` field alongside `apt_file`/`req_file` in `sandbox-images.json`), rather than a single unconditional `FROM` line or a Dockerfile-internal `ARG` indirection.

**Rationale**: Chainguard/Wolfi images are glibc-based (unlike Alpine/musl), so the risk of native-wheel incompatibility that sinks most "just switch to Alpine" attempts doesn't apply the same way — but Wolfi's package repository is far smaller than Debian's, and heavy scientific/forensics packages are the likely failure point. Splitting the decision by variant (minimal for `base`, Debian-slim-but-pinned-and-non-root for `extended`) captures most of the security benefit (the `base` variant is what most sandbox sessions use) without gating the whole feature on porting ~200 packages.

**Alternatives considered**:
- *`gcr.io/distroless/python3`*: rejected as the primary candidate — no package manager at all, so installing OS-level runtime shared libraries (`libmagic1`, `libgomp1`, etc.) into it requires copying `.so` files by hand from a builder stage, which is exactly the kind of fragile, unverifiable-without-real-testing setup this plan avoids recommending outright. Worth a follow-up spike for the `base` variant specifically (it has the smallest runtime-shared-library need) but not adopted as the plan's default.
- *Debian-slim for everything, just pinned+non-root*: rejected as insufficient — satisfies P2's pinning/non-root requirements but does nothing for the "distroless-style minimal footprint" half of the issue's proposal; kept as the documented fallback for `extended` only, not the default everywhere.
- *Alpine (`python:3.14-alpine`)*: rejected — musl libc breaks or significantly slows down manylinux wheel installs (numpy, pandas, scipy, tensorflow, opencv all publish manylinux/glibc wheels, not musllinux, for several of the pinned versions here), which would reintroduce compiler dependence at *runtime* image-build time for packages that currently install from prebuilt wheels.

## 4. Non-root execution

**Decision**: Add a fixed non-root user (`sandboxuser`, UID/GID 1000) in the final stage of both Dockerfiles, `chown` `/opt/venv` and `WORKDIR /workspace` to it, and set `USER sandboxuser` after all root-owned install steps.

**Rationale**: `SANDBOX.md` and the sandbox `.toml` runtime configs document no requirement for the sandboxed process to bind a privileged (<1024) port or otherwise need root; OpenSandbox's own execd is injected/managed by the platform at container start, not baked into these images. UID 1000 is the conventional first non-system UID and matches what `node:*-slim` and most hardened base images (including Chainguard) already default to, minimizing friction if User Story 2 later widens which images use a hardened base.

**Alternatives considered**: Base-image-provided non-root user (e.g., Chainguard images already run as non-root by default) — adopted implicitly wherever User Story 2's hardened base is used; the explicit `USER` directive above is still needed for the Debian-slim-based images (`extended`, and any base not yet migrated) so non-root isn't contingent on which base is in use.

## 5. On-demand vulnerability scanning (User Story 3)

**Decision**: Add a new, separate GitHub Actions workflow (`sandbox-image-scan.yml`) triggered only by `workflow_dispatch` (image reference as input, e.g. `xtmone/sandbox-python:0.2` for a Docker-Hub-published tag, or a locally-built tag name for one of the six domain images that aren't published), running `aquasecurity/trivy-action` in image-scanning mode against that reference, with `exit-code: '0'` (never fails the run) and results uploaded as a build artifact/step summary. For a domain image, the workflow builds it first (same as the smoke test) since it has no registry copy to pull.

**Rationale**: Trivy scans both OS packages and language-level dependencies (covers FR-007's "OS and dependency-level" requirement) in one tool, has a first-party, low-config GitHub Action, and needs no persistent backend/account (unlike e.g. Snyk) — fitting a purely on-demand, no-new-infrastructure trigger. Keeping it a separate workflow file (rather than adding a scan step to `build-push-sandbox.yml`) keeps the existing publish workflow's behavior and permissions untouched, matching spec FR-008 ("MUST NOT be a required, blocking step of the standard... pipeline").

**Alternatives considered**:
- *Grype*: comparable capability; Trivy chosen for its combined OS+language-dependency scanning in a single invocation and slightly larger ecosystem adoption, matching the issue's own "Trivy or Grype" framing without a strong reason to prefer Grype specifically here.
- *Adding a scan step directly inside `build-push-sandbox.yml`*: rejected per the on-demand/non-blocking clarification — even a non-blocking step inside that workflow would run on every publish, which is closer to "wired into the build" than "on demand," and would need extra conditional logic to stay optional.
- *Scheduled (`cron`) trigger*: explicitly out of scope per spec Clarifications; not pursued.

## 6. CI smoke-test job for build-only-package removal (Constitution Principle III)

**Decision**: Add a matrix job to `.github/workflows/ci.yml` that builds all 8 tags — `sandbox-python` (base) and the 6 domain images (`-cti`, `-data`, `-malware`, `-network`, `-rules`, `-soar`, each with its documented `APT_FILE`/`REQ_FILE` pair from `create-register-images.sh`) plus `sandbox-nodejs` — on every PR touching `backend/sandbox/**`, then runs a short import-check script per variant (`python -c "import ..."` against that image's own requirement file; `node -e "..."` for nodejs) plus an explicit assertion that build-only binaries (`gcc`, `cmake`, etc.) are absent (e.g. `! command -v gcc`) and that `tshark`/`nmap` are present only in `sandbox-python-network`. (Since moved out of `ci.yml` into the path-filtered `.github/workflows/sandbox-images.yml` during review.)

**Rationale**: This is the concrete, CI-enforced check that makes spec FR-003 ("every package remains installable/importable") and SC-001 ("zero build-only packages") verifiable on every PR rather than only manually before merge, satisfying Constitution Principle III for this feature.

**Alternatives considered**: Rely solely on the (deliberately non-blocking, on-demand) vulnerability scan from research item 5 — rejected; that scan checks for known CVEs, not for "did we accidentally still ship `gcc`" or "did we break `pyshark`'s import," which are functional/hardening regressions a CVE scanner would never catch.
