# Feature Specification: Minimal A2A Client (Outbound)

**Feature Branch**: `feat/implement-A2A-client`

**Created**: 2026-08-26

**Status**: Draft

**Input**: User description: "Implement minimal A2A client i.e. XTM One agent discovering partners' agents. It should be in the continuation of existing integrations reusing policies and design choices from server implementation."

## Context

`dev-docs/agent-interop-benchmark.md` recommended A2A v1.0, server first, with the client (outbound) direction as Phase 2. The server phase shipped (`specs/006-a2a-server-inbound`) and defers this direction here. The benchmark prices it at roughly a third of the server's cost with no new inbound attack surface, and one new security obligation: finding **F7** — no card signature-verification concept exists on this platform, and a client's verification must be fail-closed.

**A partner's agent is registered as an ordinary integration, and binding that integration to an XTM One agent is the whole opt-in.** The server phase began with a dedicated "expose" switch and removed it, because a credential that reaches nothing and an exposed agent no partner can reach are both states an operator reconciles by hand. This is that shape pointing outward: a partner is a connection to an external service holding encrypted credentials, and the capability it confers is a tool on the agents it is bound to. No new registration entity, no attachment table, no per-agent allow-list. The benchmark's `MCPServer`-pattern suggestion predates that convergence and is declined; adopting it would give the platform two ways to describe one thing.

Scope is discovery plus exactly one delegated unit of work: one binding, one delegation, one result. Everything past the single exchange is in **Out of Scope**.

## Clarifications

### Session 2026-08-26

- Q: Is delegation in this phase, or discovery only? → A: Discovery plus one delegated unit of work. Discovery alone ships a register an operator cannot act on while paying the whole cost of card verification. Rejected: discovery-only.
- Q: Which partner platforms? → A: Both benchmark targets, Vertex AI Agent Runtime and Azure Foundry. The inbound phase already built two partner mechanisms, so supporting one outbound would leave a partner able to task us while we could not task it back. Rejected: one target; a standards-generic shape *instead of* the named ones, which reaches neither because neither serves its card anonymously at the conventional path. A generic shape *in addition to* them was admitted later — see the third-target answer below.
- Q: F7 requires fail-closed verification, but no target signs its card. How is an unsigned card treated? → A: Accepted, with verification enforced whenever a signature is present. A per-registration acknowledgement gate would have fired on 100% of registrations and assured nothing — machinery that reads as assurance while protecting nobody. Rejected: an acknowledgement gate; refusing unsigned cards, which ships a feature that reaches nothing.
- Q: Which run paths may delegate? → A: Both interactive chat and assignment-triggered runs, as an ordinary tool call. Both share the same agentic loop, so restricting to one would be an invented limit. On `input-required` the tool returns control to the model with the partner's task id and question; the model answers by calling the tool again. Rejected: parking the run, which means asking the *user* to answer the partner and needs a UX surface that does not exist.
- Q: How fresh must a card be when a delegation is sent? → A: A periodic sweep, plus mandatory re-verification at delegation time when the recorded verdict is stale. The threshold makes SC-008 a number instead of an undefined "cycle". Rejected: verifying on every delegation, which puts a partner's endpoint on the critical path of every run; verifying only on a schedule, which leaves the guarantee unmeasurable.
- Q: Which protocol versions outbound? → A: Negotiated per registration at verification time and recorded on it, highest in common. Rejected: v1.0 only, which refuses a partner for a reason no operator can act on — a customer cannot make their vendor's Preview surface serve a newer version. The accepted cost is that both exchange shapes must exist and be tested.
- Q: How much run time may one delegation consume? → A: A fixed deployment-configurable per-delegation ceiling, capped by whatever remains of the run's deadline. Rejected: a share of the remaining budget, a moving target that makes SC-010 hard to assert; the run deadline alone, which lets one slow partner consume an entire run.
- Q: What trips the circuit breaker, and when does it close? → A: Consecutive *transient* failures open it for a backing-off cooldown; durable failures never count toward it and mark the registration unusable directly. One classification feeds both the breaker and the health verdict (FR-053), because the inbound phase had two surfaces answering one question from different data. Rejected: a rolling failure rate, more machinery than a first client needs.

### Session 2026-08-27 — correction from planning review

- Q: Does FR-035's original premise — that outbound destinations are governed by "the deployment's existing egress policy" — hold? → A: No, withdrawn. No such policy exists on this code path: the repository's only egress allow-list governs sandbox containers, and nothing constrains backend-initiated HTTP. The requirement named an authority that does not exist, so code written against it would have satisfied it by doing nothing. Replaced by a scoped guard (FR-035) and classification of a deployment-level refusal (FR-054).

### Session 2026-08-27 — bidirectional integrations

- Q: Where does the inbound/outbound switch live, and may one integration serve both directions? → A: On the integration, exactly one direction each, switchable after creation. One catalog entry per mechanism matches the operator's mental model, but the directions need different fields and confer opposite capabilities, so serving both would be one row with two credential sets and two blast radii. Rejected: a per-binding switch, the first per-agent-per-integration control of its kind beyond tool scoping; allowing `both`.
- Q: Which partner does the OAuth mechanism target when switched outbound, and does that make a third supported target? → A: Yes, three. Outbound OAuth presents a client-credentials bearer, which is what this platform's own inbound surface issues — so its target is any partner exposing OAuth that way, another XTM One deployment included, and it is the one target testable end-to-end with no vendor account. Rejected: keeping OAuth inbound-only, which contradicts making both switchable; shipping it unsupported.
- Q: Which mechanisms cover which direction? → A: The two existing inbound mechanisms — platform-minted OAuth credentials, and verifying a partner's Microsoft Entra token — both become direction-switchable, with the fields each direction needs. A third entry is added for **Google Agent Platform outbound**, because neither existing mechanism's credential flow reaches it: outbound OAuth presents a client-credentials bearer, and Vertex requires a Google service-account assertion at `cloud-platform` scope.
- Q: What happens to live state when an operator switches an integration's direction? → A: The switch is refused while the integration is bound to any agent; the operator unbinds first. This makes the consequence explicit and impossible to trigger from a dropdown, where the alternative would mass-revoke exposures or silently hand every bound agent a new outbound tool. Rejected: applying immediately; applying to new bindings only, which leaves the integration and its bindings disagreeing; immutable direction, which forces credential re-entry to correct a mistake.

### Session 2026-08-31 — reconciled with the implementation

Recorded after the feature shipped. Four things in it differ from what the
clarifications above decided, each revisited with working code in hand rather
than drifting unnoticed.

- Q: A registration holds one card location, and a card describes exactly one agent. What about a partner exposing three? → A: The registration owns the partner and its credential; a **target** owns one card each, carrying that agent's verdict, pinned origin, negotiated version, fingerprint and circuit (FR-059). The original shape forced one registration per agent, which meant storing the same credential once per agent and revoking it in as many places. Rejected: keeping the card on the registration, which cannot express the cardinality; a per-agent allow-list, which is the attachment table this feature exists without.
- Q: Google Agent Platform was decided outbound-only, on the grounds that a Google-side caller can authenticate through `oauth_a2a` inbound. Does that hold? → A: No, withdrawn. The two are not one state, for the same reason `entra_a2a` exists beside `oauth_a2a`: `oauth_a2a` needs this platform to mint a secret and the partner to hold it, while a Google-issued token means no secret is stored on either side and Google refreshes the caller's credential forever. Google serves both directions (FR-056, FR-061). Rejected: leaving it outbound-only, which would have left the shared-secret path as the only Google-side option.
- Q: A2A defines no method that enumerates a partner's agents, so how does an operator learn about the second and third? → A: The platform serves an endpoint for it and DECLARES that endpoint on every card it publishes, through `capabilities.extensions` — the protocol's own way to name a capability it does not define. The outbound half reads a partner's declaration and asks only partners that made one (FR-060). Rejected: probing every partner's origin on a path it never advertised, which is what shipped first and cost a token mint and a refusal per partner per window; a registry crawl, which stays out of scope.
- Q: An A2A binding sits in the agent's Tools tab beside ordinary integrations, which offer a tool picker. What does that picker do for an A2A one? → A: Nothing, so it is not offered (FR-062). Inbound contributes no tools at all (superseded — Clarifications, 2026-09-11: it brings exactly one, `ask_the_caller`), and outbound contributes one delegation tool per verified partner agent — a set the partner's cards decide. The picker showed an empty list and saved an allow-list that filtered nothing, so an operator could set "0 tools" and watch delegation happen anyway.

## User Scenarios & Testing *(mandatory)*

### Session 2026-08-31 — a keyless Google credential

- Q: `constraints/iam.disableServiceAccountKeyCreation` is Google's recommended baseline and is enforced by default in many organisations. Under it the Google mechanism's only credential — a service-account key — cannot be created at all. Is that a supported state? → A: No. The mechanism gains a second mode, impersonation of a partner-named service account using the platform's own Google identity (FR-066). Leaving it key-only meant shipping a catalog entry that a customer with an ordinary security posture could not configure by any means. Rejected: documenting the limitation, which is a supported-configuration gap rather than a documentation one; an operator-run OAuth token broker, which works against the shipped `oauth_a2a` mode and was prototyped, but moves the Google identity into a component the customer must run, secure and monitor — a stopgap, and one whose client secret is exactly as powerful as the identity behind it; Workload Identity Federation, which is the general answer for a platform NOT running on GCP and is a larger piece: it needs this platform to be an OIDC issuer with published keys, where platform JWTs are symmetric today, and it should be scoped to serve the Entra mechanism at the same time.
- Q: Does impersonation still satisfy FR-010's "refreshable, non-interactive, never a stored bearer"? → A: Yes, and more strictly than a key does. The stored value is an address rather than a secret, the token is minted per use with a one-hour lifetime, and revocation is one IAM binding at the partner's end rather than a key rotation. A key, by contrast, is the one credential form in this feature that never expires.

### Session 2026-08-31 — transport bindings

- Q: Google's Agent Platform serves its A2A surface as HTTP+JSON and offers no JSON-RPC endpoint. Is the outbound client JSON-RPC-only, as the inbound surface is? → A: No. The client consumes JSON-RPC **and** HTTP+JSON, chosen per partner at verification from what the card declares, with JSON-RPC preferred where both are offered (FR-065). Keeping it JSON-RPC-only would have shipped a `google_a2a` mechanism that verifies a partner's card and then fails every delegation against it with a 404 — a catalog entry for a partner it cannot task. Rejected: JSON-RPC only; an operator-selected binding, which asks an operator to answer a question the card already answers and makes a wrong answer a silent 404; serving HTTP+JSON inbound too, which is a second public surface for no demand.
- Q: A v1.0 card carries no top-level `url` or `protocolVersion` — both move onto `supportedInterfaces[]`, per interface. Which is authoritative? → A: The interfaces are, and both card shapes are read. The endpoint, the binding and the version are ONE decision made together, in that order after the origin check, because a card may declare two endpoints whose bindings and versions differ. Rejected: reading only the top level, which refuses every genuine v1.0 card as malformed.

### Session 2026-09-11 — inbound brings one tool

- Q: FR-062 said inbound contributes no tools at all. Is that still true now that an exposed agent can ask its caller for a detail (`012` FR-001)? → A: No, and FR-062 is amended. Every inbound binding brings exactly one tool, `ask_the_caller` — `oauth_a2a`, `entra_a2a` and `google_a2a` alike, since all three resolve to the same inbound catalog entry. What FR-062 exists to protect is unchanged, and is why the picker is still not offered: nothing an operator selects decides whether that tool appears. It is registered by the external-task executor for the length of a partner's task and gone when the task ends, so `PROVIDER_TOOLS` stays empty for all three providers and an allow-list would still filter nothing. Rejected: leaving the sentence as written, which contradicted the Config-tab panel that names the tool on screen and the review scenario that told an operator to expect none.

### User Story 1 - Register and verify a partner's agent (Priority: P1)

An operator adds a partner's agent to the integrations catalog like any other external service: the partner platform, the location its card is published at, and the machine credentials the partner issued. The platform fetches the card with those credentials, verifies it, and shows the operator what it declares before anything is bound to it. A card that cannot be fetched, is malformed, is served over a connection that cannot be confirmed encrypted, or carries a signature that does not verify leaves the registration unusable with the reason stated.

**Why this priority**: The whole of discovery and the entire security boundary. It carries standalone value — an auditable register of verified partners with a health verdict each — and it is where F7 is answered. Every other story is unreachable without it.

**Independent Test**: Testable with no agent bound to anything: a good card produces a usable registration showing what the partner declares, each defective-card case produces an unusable registration naming its reason, and every change is audit-logged. Scenarios 7 and 8 are the exception — they describe what a *binding* does, so the foundational direction suite verifies them rather than this story's own tests.

**Acceptance Scenarios**:

1. **Given** an operator with authority to create integrations, **When** they register a partner with a valid card location and working credentials, **Then** the registration becomes usable, the card's declared name, description, skills and content types are shown, and the creation is audit-logged with actor and timestamp.
2. **Given** a card location that cannot be fetched, returns a malformed card, or is reachable only over a connection the platform cannot confirm is encrypted, **When** registration is attempted, **Then** no usable registration is created and the specific reason is reported.
3. **Given** a card carrying a signature that does not verify, **When** registration is attempted, **Then** the registration is unusable and no operator action can make it usable.
4. **Given** an actor without authority over a registration, **When** they attempt to create, edit or delete it, **Then** the attempt is denied and the denial is audit-logged.
5. **Given** a registered partner, **When** anyone reads the registration through any surface, **Then** its stored credentials are never returned in readable form and appear in no log.
6. **Given** the deployment-level switch is off, **When** a registration is used for anything outbound, **Then** nothing is attempted, regardless of registration state.
7. **Given** an outbound integration bound to an agent, **When** the agent's exposure is checked, **Then** it is not exposed — an outbound binding confers a delegation tool and no inbound reach; **When** an inbound integration is bound instead, **Then** the agent gains no delegation tool.
8. **Given** an integration bound to at least one agent, **When** an operator changes its direction, **Then** the change is refused and the bound agents are named; **When** they unbind and retry, **Then** it succeeds and the previous direction's credentials are cleared.

### User Story 2 - Bind the partner to an agent and delegate work (Priority: P1)

Someone with management authority over an XTM One agent binds a verified **outbound** registration to it, on the same tab and by the same act as every other capability. That binding — and nothing else — lets the agent hand work to that partner; an inbound registration bound to the same agent confers no such thing (FR-055). During a run the platform submits the message the agent composed, follows the partner's task to a terminal state, and returns the result. Failures come back distinguishable, never as one undifferentiated error.

**Why this priority**: The payoff, and the only part producing outbound traffic. Binding and delegation are one story because the server phase proved that separating the opt-in from the capability produces two states an operator must reconcile.

**Independent Test**: Testable against a stubbed partner: an unbound agent has no reach, a bound agent completes a delegation end-to-end, and each named failure class arrives distinctly.

**Acceptance Scenarios**:

1. **Given** an agent with no partner binding, **When** it runs, **Then** it has no means of reaching any partner and no outbound request is made.
2. **Given** an agent bound to a usable registration, **When** it delegates a unit of work, **Then** the platform submits it, follows the task to a terminal state, and returns the result into the calling run.
3. **Given** an agent bound to an unusable registration — a card that failed verification, credentials that can no longer produce a token, an unaccepted card change, or a forbidden destination — **When** it attempts to delegate, **Then** the delegation is refused before any request is sent, with the reason.
4. **Given** a delegation in flight, **When** the calling run is cancelled, fails, or exceeds its time bound, **Then** the platform attempts to cancel the task at the partner and reports the outcome.
5. **Given** a partner that reports it needs more input, **When** control returns to the calling agent with the partner's question, **Then** the agent may answer by continuing that same task within the same run, with no human waited on and no new task created; **When** the partner reports it needs an authorisation the platform cannot supply, **Then** the delegation fails with that reason and is not retried.
6. **Given** a partner returning a response that does not correspond to a task the platform submitted, has an unrecognised shape, or exceeds the ingest bound, **When** it arrives, **Then** it is refused whole rather than partially interpreted.
7. **Given** a partner that fails repeatedly, **When** further runs attempt delegation, **Then** attempts stop for a period rather than being retried on every run.
8. **Given** a delegation from an assignment-triggered run rather than an interactive chat, **When** the partner reports it needs more input, **Then** it behaves identically to the chat path — the same return of control, the same continuation, no parking.

### User Story 3 - Outbound work stays inside the calling run's boundary (Priority: P1)

A delegation carries only what the calling agent composed. The calling run's boundary applies unchanged: a registration confers no additional reach inside the platform, the run's history is not forwarded, no platform credential or session material is included, and what comes back is untrusted content that cannot widen the run's authority or change registration, credential or permission state. Usage is charged to the user whose run made it.

**Why this priority**: Where the outbound direction can leak, and unlike the inbound surface it is not protected by anything the server phase built. P1 because the failures it prevents are silent.

**Independent Test**: Capture every outbound request across runs holding known sensitive context and assert on what is absent; feed adversarial partner responses into a calling run and assert its authority is unchanged.

**Acceptance Scenarios**:

1. **Given** a run whose context includes conversation history and platform credentials, **When** it delegates, **Then** the outbound payload contains only the composed message.
2. **Given** a partner response containing instructions aimed at the calling agent, **When** it is returned into the run, **Then** it is handled as untrusted content and cannot cause the agent to act outside the calling user's boundary or alter registration, credential or permission state.
3. **Given** a card whose declared invocation endpoint is on a different origin from the one the registration was verified against, or a partner that redirects off that origin, **When** a request would be sent, **Then** it is refused.
4. **Given** a completed delegation, **When** usage is accounted, **Then** it is charged to the user whose run made the delegation and to no one else.

---

### User Story 4 - Registrations stay trustworthy as cards and credentials change (Priority: P2)

The platform re-verifies each card on a periodic sweep, on demand, and again at delegation time when the last check has gone stale, recording when it was last verified and whether it is usable with a reason when it is not. A materially changed card suspends delegation until someone with authority accepts the change. Credentials that can no longer produce a token report unusable for that reason, distinguishably from an unreachable partner and from one that rejected a valid token — a distinction the platform makes once and both the health verdict and the circuit breaker read.

**Why this priority**: A registration verified once and trusted forever is the fail-open version of F7 with extra steps. P2 because the feature is safe at first registration without it, and unsafe over time.

**Independent Test**: Mutate a stubbed partner's card and credentials and assert the registration's usability, reason and delegation behaviour change by the next delegation that finds the verdict stale, and in no case later than the sweep interval.

**Acceptance Scenarios**:

1. **Given** a usable registration, **When** its partner materially changes its card, **Then** delegation is suspended before the next delegation that finds the verdict stale and in no case later than the sweep interval, the suspension is audit-logged, and no delegation is sent against the unaccepted card.
2. **Given** a suspended registration, **When** someone with authority accepts the change, **Then** delegation resumes and the acceptance is audit-logged with actor, registration and the card accepted.
3. **Given** a registration whose credentials can no longer produce a token, **When** its health is read, **Then** it reports unusable for that reason, distinct from unreachable and from rejected.
4. **Given** a deleted registration, **When** anything attempts to use it, **Then** its stored credentials are gone and delegation stops immediately from every agent it was bound to.

### Edge Cases

Cases whose handling is not derivable from a requirement alone.

- **A partner that previously served a signed card serves an unsigned one.** A material change: delegation suspends until accepted.
- **A partner's card gains a signature that does not verify, after having been usable.** Unusable with no override, and acceptance of the previous card does not carry over.
- **A partner changes its card inside the staleness window.** A delegation may go out against the previous card, bounded by the threshold. The accepted residual of not verifying on every delegation.
- **Re-verification at delegation time cannot reach the partner.** The delegation is refused; the stale verdict is never a fallback.
- **A partner's card changes materially while a delegation is in flight.** The in-flight delegation runs to its outcome against the card it was submitted under; the next one is suspended.
- **A delegation is issued with less run deadline remaining than the ceiling.** The shorter binds, so a delegation never outlives the run that made it.
- **A run makes several delegations.** Each gets its own ceiling; the run's deadline caps the total.
- **A partner fails intermittently rather than consistently.** A consecutive-failure count may never open the breaker, so such a partner is retried each run, each attempt bounded by the ceiling. The accepted residual of choosing a count over a rolling rate.
- **A partner keeps reporting that it needs more input.** Bounded by the run's existing budgets; the run ends with a defined outcome and the outstanding task is cancelled. No new turn limit.
- **A run ends with a partner task still awaiting input.** Cancelled at the partner rather than left open.
- **A partner never reaches a terminal state.** The delegation ends at its bound with a timeout, after attempting to cancel.
- **A registration is company-managed and a bound agent runs for a user with no eligible access.** Per-user resolution follows the platform's ordinary rule; a provider with no eligible integration for that user is absent, never satisfied from another user's account.
- **An operator switches direction on a bound integration.** Refused, naming the agents it is bound to. Unbinding first is the operator's explicit act.
- **A registration is deleted while a delegation is in flight.** The in-flight delegation ends with a defined outcome; no further delegation is possible.
- **Two registrations are bound to one agent.** Each is a distinct capability with its own credentials, health and circuit state; neither reports the other's activity, and deleting one leaves the other working.
- **The partner is itself an XTM One deployment.** A supported target rather than a curiosity (FR-045): its inbound surface issues OAuth client-credentials, which the outbound OAuth mechanism consumes.

## Requirements *(mandatory)*

### Functional Requirements

<!-- Numbering is append-only: a requirement added after a later clarification takes the next free number rather than being inserted in sequence, so identifiers stay stable across the plan, tasks and contracts that cite them. Read the headings, not the numeric order. -->

#### Registration and authority

- **FR-001**: A partner's agent MUST be registrable as an entry in the platform's existing integrations catalog, holding the location of each of the partner's agent cards (FR-059) and the credentials to authenticate to it. No separate registration entity MUST be introduced.
- **FR-002**: Authority to create, edit, share and delete a registration MUST be the platform's existing integration authority — owner, administrator, or a member of a group it is shared with at a configuration-level tier, with company-managed registrations administrator-only. No new permission concept MUST be introduced.
- **FR-003**: The platform MUST deny any registration change by an actor lacking that authority, and MUST audit-log the denial.
- **FR-004**: Partner credentials MUST be stored encrypted using the platform's existing credential-handling pattern, MUST never be returned in readable form through any surface, and MUST never be written to a log or a health message.
- **FR-005**: An agent's ability to reach a partner MUST come from binding that registration to the agent and from nothing else — no second switch, no separate attachment record, no implicit availability to an unbound agent. What a binding confers MUST follow the integration's direction (FR-055).
- **FR-055**: An A2A integration MUST carry exactly one direction, inbound or outbound, and MUST NOT serve both. Binding it to an agent MUST apply only that direction: an outbound integration MUST NOT expose the agent, and an inbound integration MUST NOT contribute a delegation tool. The platform MUST therefore decide exposure from the integration's direction rather than from provider membership alone, which is how the shipped inbound hook decides it today.
- **FR-056**: Each partner mechanism MUST appear once in the catalog with a direction, not once per direction, and MUST present only the credential fields its active direction requires. The platform MUST offer a Google Agent Platform mechanism in both directions: outbound because neither existing mechanism's credential flow reaches Vertex, and inbound because neither offers a Google-side partner a path that stores no shared secret (FR-061).
- **FR-057**: The platform MUST refuse to change an integration's direction while it is bound to any agent, and MUST name the bound agents in the refusal so the operator knows what to unbind. A direction change MUST NOT silently revoke an exposure or grant a delegation tool.
- **FR-058**: On a direction change, the platform MUST clear the credentials the previous direction held. A partner credential retained for a direction the integration no longer serves is a stored secret with no purpose and no expiry.
- **FR-006**: Authority to bind a registration to an agent MUST be the platform's existing management authority over that agent, and per-user (template) bindings MUST resolve under the platform's ordinary per-user eligibility rule.
- **FR-007**: Outbound delegation MUST be governed by a deployment-level switch, off by default and independent of the inbound switch; while it is off, no outbound request MUST be attempted regardless of registration or binding state.
- **FR-008**: Deleting a registration MUST remove its stored credentials and MUST immediately stop delegation from every agent it was bound to.
- **FR-009**: A registration's mechanism and direction MUST determine which target it reaches; the platform MUST NOT infer a target from the card location. Registration MUST fail when the card location does not serve what that mechanism expects.
- **FR-045**: This phase MUST support three outbound targets: Google Agent Platform with `cloud-platform`-scoped Google machine credentials, Azure Foundry with Microsoft Entra credentials carrying at least the role its agent-consumer surface requires, and any partner accepting OAuth client-credentials — this platform's own inbound surface included. All three MUST reach identical delegation behaviour with no per-target difference visible to a calling agent, and no target outside these three MUST be presented as supported.
- **FR-010**: A registration MUST hold non-interactive machine credentials only, and the platform MUST obtain and refresh the short-lived tokens its target requires from them. A credential that can no longer produce a token MUST make the registration unusable with that reason, distinguishable from an unreachable partner and from a partner that rejected an otherwise valid token.

#### Discovery and verification

- **FR-011**: The platform MUST fetch and verify the partner's card at registration, and MUST NOT create a usable registration when the card cannot be fetched, is not well-formed, or fails verification.
- **FR-012**: Card retrieval and every outbound request MUST occur only over a connection the platform can confirm is encrypted; an unencrypted or unverifiable connection MUST be refused rather than downgraded to.
- **FR-013**: Verification MUST be fail-closed: any verification that cannot be completed confidently MUST block delegation rather than warn and proceed.
- **FR-014**: Card locations MUST be supplied per registration rather than derived from a base URL — one per partner agent (FR-059) — and card retrieval MUST present the registration's own credentials where the target requires them. Two targets serve their cards only to an authenticated caller; the third does not, because this platform serves its own cards anonymously so that a partner can register from a URL alone.
- **FR-015**: A card carrying a signature that does not verify MUST make the registration unusable, in every case, with no operator override.
- **FR-016**: A card carrying no signature MUST NOT by itself block registration, and no per-registration acknowledgement MUST be required. Its absence MUST be recorded rather than treated as equivalent to a verified signature, and FR-015 MUST still apply in full whenever a signature is present.
- **FR-017**: The platform MUST record whether the card it is operating against was signature-verified or accepted unverified, on the target it operates against, on every delegation made under it, and in the audit record. An unverified card MUST NOT be presented as verified anywhere.
- **FR-018**: The platform MUST show the actor what each verified card declares — name, description, skills, and accepted and produced content types — before that target is put to use, and MUST record per target when it was last verified and whether it is usable with a stated reason when it is not.
- **FR-019**: The platform MUST re-verify each of a registration's cards on a periodic sweep at a stated interval (default: hourly) and on demand, and MUST suspend delegation until an actor with authority accepts a material change — a changed invocation endpoint, authentication scheme, accepted or produced content types, or the loss of a signature the card previously carried. Suspension and acceptance MUST both be audit-logged.
- **FR-050**: The platform MUST NOT send a delegation against a verification verdict older than a stated staleness threshold (default: 15 minutes). Where it is older, the platform MUST re-verify before submitting and MUST refuse the delegation when that re-verification cannot complete, never falling back to the stale verdict. A verdict within the threshold MUST be read rather than re-checked.
- **FR-020**: A **health verdict** MUST be reported through the platform's existing per-provider connectivity mechanism rather than a surface of its own, distinguishing usable, usable-but-limited, and unusable with a reason. The verdict is per partner agent (FR-059); because that mechanism reports per integration, it MUST aggregate — a partner with one of three agents unreachable is neither healthy nor broken, and MUST be reported as the count reachable while naming the ones that are not. This specification calls that value the health verdict throughout; it is stored as `usability`.

#### Delegation

- **FR-021**: A bound agent MUST hand work to a partner through the platform's existing agent-to-agent delegation semantics rather than a separate interaction model, and MUST be able to do so from every run path the platform executes agents on — interactive chat and assignment-triggered alike — on identical terms.
- **FR-022**: The platform MUST submit the message the calling agent composed, follow the resulting partner task until it reaches a terminal state, and return its result into the calling run.
- **FR-023**: The platform MUST agree a protocol version with each partner agent at verification time — the highest both support — MUST record it on that target, and MUST declare it explicitly on every outbound request and card retrieval, never relying on a partner's default. A response not matching the agreed version's shape MUST be refused under FR-026.
- **FR-051**: This phase MUST support A2A v1.0 and the preceding version outbound. A partner with no version in common MUST make the registration unusable, naming that reason, rather than being attempted on a guess.
- **FR-066**: The Google mechanism MUST offer a keyless outbound credential mode in addition to the service-account key: impersonation of a partner-named service account, presenting the platform's own Google identity. Exactly one mode MUST be configured, and a registration carrying both MUST be refused rather than resolved by precedence. A deployment with no Google identity of its own MUST be told so in those terms, distinctly from a rejected or unreadable credential — the remedy is on the deployment, not on the registration. A partner that has not granted the impersonation permission MUST be reported with the permission named.
- **FR-065**: The platform MUST negotiate a transport BINDING with each partner agent alongside the version, from what the card declares, and MUST record it on that target. It MUST support JSON-RPC 2.0 and HTTP+JSON outbound; a partner offering both MUST be reached over JSON-RPC. A partner offering no supported binding MUST make the registration unusable naming that reason — distinct from having no version in common, because the two negotiations fail independently and no setting reconciles a gRPC-only partner. Delegation MUST use the recorded binding and MUST NOT re-derive one at request time. An interface on an origin other than the one the card was fetched from MUST be discarded under FR-034 before its binding is considered.
- **FR-052**: A partner that stops serving the agreed version MUST be treated as a material change under FR-019, suspending delegation until accepted. A partner that begins serving a newer supported version MUST renegotiate upward without suspension, and the change MUST be audit-logged.
- **FR-024**: A single delegation attempt MUST be bounded by a fixed, deployment-configurable ceiling (default: 5 minutes), and additionally by whatever remains of the calling run's deadline, whichever is shorter. The ceiling MUST apply per attempt: a continuation under FR-031 starts a fresh one. Where the partner has stopped answering, the platform MUST attempt to cancel the task at the partner and report a timeout into the calling run. Where the partner is still working on the task, the attempt MUST NOT cancel and MUST NOT report a timeout: the task is handed back for the calling agent to collect (`011-a2a-client-wait-arbitration` FR-001).
- **FR-025**: When a calling run is cancelled or fails with a delegated task outstanding, the platform MUST attempt to cancel that task at the partner. This reaches a task left outstanding by a hand-back as well as by a partner's question. The boundary is the work that would collect the result — an assignment run reaching its outcome, or a user abandoning the conversation; a chat turn ending does not cancel, because handing a task back is what ends that turn (`011` FR-005).
- **FR-026**: The platform MUST refuse whole any partner response that does not correspond to a task it submitted, whose shape it does not recognise, or that reports an unrecognised task state — never partially interpreting it or mapping it to the nearest known state.
- **FR-027**: The platform MUST bound the size of a partner response it will ingest, failing the delegation when the bound is exceeded.
- **FR-028**: The platform MUST refuse a delegation before submitting it when the card declares content types the platform cannot produce or consume for that exchange, and MUST report the mismatch.
- **FR-029**: Failures MUST be returned into the calling run with the partner's machine-readable reason preserved, distinguishing at minimum: unreachable partner, rejected credentials, partner-reported task failure, timeout, and content-type mismatch.
- **FR-030**: Consecutive transient failures against one partner MUST stop further delegation attempts for a cooldown that lengthens on repeat, following the failure-counting and circuit-breaking pattern the platform already applies to outbound integration calls. Circuit state MUST be per target, so one failing partner MUST NOT suppress another bound to the same agent, and one unreachable agent of a partner MUST NOT pause delegation to its siblings. A successful on-demand verification MUST close the breaker.
- **FR-053**: The platform MUST classify every delegation failure as transient or durable, and that single classification MUST be what both the circuit breaker and the health verdict read. A durable failure — rejected credentials, a destination refused under FR-054, no protocol version in common, a card that fails verification — MUST NOT count toward the breaker and MUST instead make the target unusable with that reason.
- **FR-031**: When a partner reports that more input is needed, the platform MUST return control to the calling agent carrying the partner's task identifier and its question, rather than parking the run or waiting on a human. The calling agent MUST be able to answer by continuing that same partner task, and a continuation MUST NOT create a new one.
- **FR-046**: A continuation MUST be accepted only for a partner task the calling run itself created; a task identifier naming any other delegation MUST be refused (FR-033).
- **FR-047**: A partner's question MUST be treated as untrusted content on the way back into the calling run, on the same terms as any other partner output (FR-036).
- **FR-048**: A back-and-forth with a partner MUST be bounded by the run's existing budgets — iteration, token, spend and wall-clock — and MUST NOT introduce a limit of its own. The run MUST end with a defined outcome when a bound is exhausted.
- **FR-049**: When a partner reports that an authorisation the platform cannot supply is required, the delegation MUST fail with that reason and MUST NOT be retried. Every partner state and run path this specification names MUST be reachable through the ordinary delegation path — no branch may exist for a state the implemented path cannot produce (SC-014).

#### Cardinality, discovery and the inbound Google half

- **FR-059**: One registration MUST be able to reach SEVERAL of a partner's agents. A card describes exactly one agent, so the verdict, pinned origin, negotiated version, card fingerprints and circuit MUST be held per partner agent, while the credential and the trust decision stay on the registration. Reaching three of a partner's agents MUST NOT require three registrations, three copies of one credential, or three places to revoke it. Removing a partner agent MUST stop it contributing a delegation tool immediately, and MUST NOT delete the record of work already sent through it.
- **FR-060**: The platform MUST be able to learn a partner's other agents from the partner itself rather than from an operator retyping card locations, and MUST bound that in four ways. It MUST require at least one operator-supplied card location first — discovery extends a relationship, it does not establish one. It MUST discard any location not on the origin it authenticated to. Every location it learns MUST run the whole of FR-011 through FR-035 before use, so discovery decides only what to LOOK at. And a partner answering with nothing MUST change nothing, so a malformed reply cannot strip an operator's list.
- **FR-063**: Because A2A defines no method that enumerates agents, the endpoint serving FR-060 MUST be declared on every agent card this platform publishes, using the protocol's own extension mechanism, naming the path and marking itself optional. The platform MUST ask a partner for its agents only where that partner's own card declared the same extension, and MUST NOT probe a path a partner never advertised. Where no card has yet been read from a partner, one attempt at the extension's default path is permitted; a partner whose cards HAVE been read and declare nothing MUST NOT be asked.
- **FR-061**: The Google mechanism MUST serve inbound as well as outbound. Inbound it MUST verify a token the partner's own Google identity minted, against a pinned audience and a pinned calling identity, and MUST refuse a configuration that lacks the calling-identity pin. That refusal is not symmetry with the Entra mechanism: Google publishes one signing keyset for every principal, so a valid signature proves only that some Google identity minted the token, and the calling-identity pin is the whole of what separates the partner from any other Google account.
- **FR-064**: An exposed agent MUST be able to CONSULT a peer agent during an external task — ask it a question and use the answer — and MUST NOT be able to transfer to one or delegate a background task to one. A peer qualifies only when it is exposed by the same partner registration the caller authenticated under, and it MUST execute under that peer's own exposure bounds: its session scope and its run-as identity. Consultation MUST therefore add a path and never a permission — anything a consult reaches, a direct submission to that peer's own card could already have reached. Where the calling registration cannot be attributed to an integration, or the caller has no eligible peer, no consultation MUST be offered at all.
- **FR-062**: An A2A binding MUST NOT offer the per-integration tool selection that ordinary integrations offer, in any direction. There is nothing for an operator to select: inbound brings exactly one tool, `ask_the_caller`, which the external-task executor registers for the length of a partner's task rather than the binding conferring it (`012` FR-001), and outbound contributes one delegation tool per verified partner agent, which the partner's cards decide rather than an operator. An A2A mechanism MUST NOT be offered as a per-user (template) binding either: a partner relationship has no per-user form, since the credential, the exposure and the partner's cards belong to the registration and not to whoever happens to be running.

#### Boundary, secrets and accounting

- **FR-032**: An outbound payload MUST contain only the message the calling agent composed. The calling run's conversation history MUST NOT be forwarded, and no platform credential, API key, session material or cross-platform identity token MUST ever be included.
- **FR-033**: A delegation MUST NOT be able to send outward anything the calling run could not itself see; a registration MUST confer no additional reach inside the platform.
- **FR-034**: The platform MUST send outbound requests only to the origin the registration was verified against, MUST refuse a card whose declared invocation endpoint is on another origin, and MUST NOT follow a redirect away from that origin.
- **FR-035**: The platform MUST refuse a card location or invocation endpoint resolving to a loopback, private, link-local or cloud-metadata address, at registration and before every request.
- **FR-054**: Where the deployment's own network policy refuses an outbound destination, the platform MUST classify that as a durable failure and surface it in the health verdict with a stated reason, rather than failing opaquely at the network layer on each run.
- **FR-036**: Content returned by a partner MUST be treated as untrusted and MUST pass the platform's existing prompt-injection defenses on the path back into the calling run. It MUST NOT be able to escalate its own authority, cause the calling agent to act outside the calling user's boundary, or change registration, credential, binding or permission state.
- **FR-037**: Platform usage consumed by a delegation MUST be attributed to the user whose run made it. No new accounting concept MUST be introduced.
- **FR-038**: Where a verification, credential, destination or authority decision cannot be evaluated, the platform MUST refuse the delegation rather than attempt it.

#### Observability

- **FR-039**: The platform MUST audit-log every registration creation, credential update, binding change, card-change acceptance, suspension and deletion with actor and timestamp. Where a change is applied by a hook with no request context, it MUST record what happened and leave who to the surrounding audit trail.
- **FR-040**: The platform MUST audit-log every delegation with the calling agent, the calling user, the registration, the time and the outcome.
- **FR-041**: A retry after a network failure with no response received MUST be recorded as individually attributable, and MUST NOT be represented as free of the risk that the partner started work twice.
- **FR-042**: Outbound delegation MUST be attributable to the partner it went to and presented that way: a registration's activity MUST show only its own delegations, and a run listed anywhere MUST identify the partner it delegated to. Attribution MUST key on what was recorded at submission time, never inferred from an agent's current bindings.
- **FR-043**: The platform MUST expose operational telemetry distinguishing outbound delegation traffic from internal and from inbound external traffic. Counters MUST be written from the single place the event occurs, so a counter reading zero means nothing happened rather than nothing instrumented.
- **FR-044**: Delegation records MUST share the lifetime of the internal runs they belong to, and MUST NOT be purged on an independent schedule.

### Key Entities

- **Partner Agent Registration** *(an integration plus its A2A settings record)*: A catalog entry for one partner mechanism, carrying **exactly one direction** — inbound or outbound (FR-055) — which with the mechanism determines the target, plus encrypted machine credentials. One operator decision to trust one partner. Not a new entity type: the credentials live on the integration and the direction on a settings record beside it. Everything that is a fact about one of the partner's AGENTS rather than about the partner lives on a Partner Target instead (FR-059).
- **Partner Target** *(one of a partner's agents)*: One card this registration can reach, and what is known of the agent it describes: the card location, the invocation endpoint the card declares, the agreed protocol version, the pinned origin, the card fingerprint and the accepted one, whether the signature verified, the health verdict and its reason, circuit state, and what the card declares about the agent. Deliberately holds no credential — that belongs to the partner, and a per-target copy would be one secret stored N times with N chances to drift.
- **Partner Card** *(read, never authored)*: The partner's self-describing document, fetched from the location the operator supplied, with the registration's credentials where the target requires them. Read for name, description, skills, invocation endpoint, authentication scheme and content types. Verified fail-closed; compared on re-verification to detect material change.
- **Partner Binding** *(an integration binding)*: The existing per-agent and per-user template binding. The whole opt-in, and what it confers follows the integration's direction: an outbound binding gives the agent a delegation tool, an inbound one exposes the agent, never both (FR-055). No new table.
- **Delegation**: One unit of work handed to a partner within a calling run. Carries the calling agent and user, the registration, the partner task identifier, and the outcome with its reason. Shares the lifetime of the run it belongs to.
- **Agent, User, Group** *(existing)*: Unchanged. Supply binding authority and the boundary and usage accounting every delegation runs inside.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An operator registers a partner's agent and successfully delegates one unit of work to it in under 15 minutes, supplying only the mechanism, the card location and credentials, with no XTM One-specific code on the partner side — measured independently on all three supported targets with no code change between them, the OAuth one against this platform's own inbound surface.
- **SC-002**: 100% of delegations reach a defined outcome — result, partner failure, timeout, or refusal — with zero left waiting indefinitely.
- **SC-003**: Zero registrations become usable when their card cannot be fetched, is malformed, carries a signature that does not verify, or is served over a connection that cannot be confirmed encrypted, measured across an adversarial probe covering each case.
- **SC-004**: On a fresh deployment and on an upgrade of an existing one, zero agents can reach any partner until both a registration and a binding are recorded, and zero outbound requests occur while the deployment switch is off.
- **SC-005**: Zero outbound payloads contain platform credentials, API keys, session material, cross-platform identity tokens, or any part of the calling run's history beyond the composed message — measured by capturing every outbound request across a suite of runs holding known sensitive context.
- **SC-006**: Zero outbound requests reach an origin other than the one their registration was verified against, measured across card-endpoint mismatch, mid-life card change, and redirect cases.
- **SC-007**: Exactly one surface can give an agent outbound reach. Measured by a zero-call-site sweep: no endpoint, task, tool or hook creates that reach other than the integration binding.
- **SC-008**: A partner that changes its card materially causes delegation to stop before the next delegation that finds the verdict stale, and in no case later than the periodic sweep interval — with zero delegations sent against the unaccepted card, measured across an endpoint change, an auth-scheme change, a content-type change, and the loss of a previously present signature.
- **SC-009**: 100% of delegation failures returned into a calling run distinguish unreachable partner, rejected credentials, partner-reported failure, timeout, and content-type mismatch; zero are reported as an undifferentiated error.
- **SC-010**: A partner that is unreachable or failing is abandoned within the configured per-delegation ceiling, or within whatever remains of the calling run's deadline if that is shorter — measured with a partner that never answers, one that answers slowly, and a delegation issued late in a run. Repeated failures stop further attempts within a bounded number of runs, with zero cross-suppression between two registrations bound to the same agent and zero between two agents of one partner.
- **SC-011**: Zero usage allowance is consumed from any user other than the one whose run made the delegation, across every delegation.
- **SC-012**: Zero registrations remain usable, and zero stored credentials remain, after a registration is deleted; and zero credentials appear in any log, health message or API response at any point in the registration's life.
- **SC-013**: 100% of registration changes, card-change acceptances, bindings and delegations are attributable to an actor or calling run, a registration, and a time; and 100% of delegations shown against a registration belong to that registration, measured with two registrations bound to one agent.
- **SC-014**: Zero requirements in this feature are served by code with no call site on the implemented path, measured by a zero-call-site sweep over every function introduced.
- **SC-015**: Zero partner responses that fail correspondence, shape, state or size checks are partially interpreted; each is refused whole, measured across a malformed-response suite.
- **SC-016**: 100% of registrations and 100% of delegations record whether the card they operate against was signature-verified or accepted unverified, and zero surfaces present an unverified card as verified.
- **SC-017**: Zero delegations are sent against a verification verdict older than the staleness threshold, and zero proceed on a stale verdict when re-verification fails — measured by holding a verdict past the threshold and making the card endpoint unreachable.
- **SC-018**: 100% of outbound requests and card retrievals declare the protocol version recorded on their registration; zero rely on a partner's default, and zero responses are interpreted against a version other than the one agreed. Measured on a partner serving v1.0 and on one serving only the preceding version, with no code change between them.
- **SC-020**: Zero exposures are created by an outbound binding, zero delegation tools by an inbound one, and neither by an A2A integration with no settings row — measured across all three mechanisms and across every path that reaches the exposure hook: binding an existing agent, unbinding, and creating an agent with bindings already set.
- **SC-019**: 100% of delegation failures are classified transient or durable, and the circuit breaker and the health verdict agree on every partner — measured by asserting both surfaces after each failure class in FR-029. Zero durable failures are retried by the breaker, and zero transient failures make a registration permanently unusable.

- **SC-021**: An agent bound on a partner's inbound side becomes reachable from this platform with zero card locations retyped, measured between two XTM One deployments; and zero partners are asked for their agents without having declared the endpoint on a card this platform has read, measured with a partner that declares nothing and one that has never been verified.
- **SC-022**: Zero inbound Google configurations become usable without a pinned calling identity, and zero tokens from a Google identity other than the pinned one are admitted — measured with a validly signed token from an unpinned service account.
- **SC-024**: Zero consultations from an external task reach a peer that is not exposed by the calling registration, and zero reach a tool or an identity that a direct submission to that peer's own card would not — measured by comparing a consult's resolved bounds against that peer's own exposure scope and run-as user, with a peer exposed to a different partner, one bound but unexposed, and one whose run-as user differs from the caller's. Zero external tasks can transfer to a peer or spawn a background task.
- **SC-023**: Zero A2A bindings offer tool selection, in either direction and on every surface that offers it for an ordinary integration; and zero A2A mechanisms are offered as per-user bindings.

## Assumptions

- **A partner agent is an integration, and binding is the opt-in.** The server phase's own conclusion applied outward, and what keeps this feature minimal.
- **Authority is reused wholesale.** Registration authority is the existing integration authority; binding authority is the existing management authority over the agent. This feature inherits both the strengths and the known limits of that model.
- **The boundary is the calling run's, not the registration's.** The outbound direction needs no run-as identity: a delegation happens inside a run that already has one. A registration confers credentials for reaching outward and no reach inward.
- **F7 is answered in full for a signed card and by transport for an unsigned one.** A failed signature is fatal with no override. Neither supported target signs today, so an unsigned card is trusted on confirmed-encrypted transport plus an operator-supplied location. The residual is bounded by recording the distinction wherever a delegation happens (FR-017) and by treating a signature's loss as a material change (FR-019), and closes when a target begins signing.
- **Signing this platform's own cards is out of scope.** The server phase deferred signing and verification here as a pair; this takes the verification half, which the client cannot work without. Signing is an inbound change to an already-shipped surface, valuable to partners rather than to this feature.
- **Both benchmark targets serve their cards authenticated and off the well-known path.** Hence the operator-supplied, credentialed card location per partner agent (FR-014, FR-059).
- **Both target platforms' A2A surfaces are Preview**, so breaking changes on their side are likely. This specification targets the standard, not either vendor's current subset — and it is why the agreed version is recorded per registration (FR-023) rather than assumed deployment-wide.
- **Supporting two protocol versions outbound is a cost accepted.** Both exchange shapes must exist and be tested. The inbound surface already tolerates both, so this makes the directions symmetric.
- **Delegation reuses the existing execution time bound and usage accounting.** No new accounting concepts, exactly as the inbound phase introduced none.
- **Partner credentials are conveyed out of band**, symmetric to how the inbound phase conveys card URLs.
- **Network policy is the deployment's authority; classification is this feature's.** No platform-wide egress policy exists on this code path, so this feature does not pretend to consult one: it refuses non-public and metadata destinations itself (FR-035) and surfaces a deployment-level refusal as a health verdict (FR-054). A general egress policy for every integration would be the better end-state and is out of proportion here.
- **Partner output is untrusted input to an LLM path, handled by an existing defense** rather than a bespoke filter.
- **Giving the existing inbound mechanisms a direction is a change to shipped inbound behaviour, accepted deliberately.** A separate entry per direction would have meant four catalog cards for two partners. The cost is that the inbound exposure hook must learn about direction — without that, binding an integration for outbound purposes would silently expose the agent, a fail-open regression on a shipped surface.
- **No new inbound LISTENER is created, but one new inbound credential path is.** This feature opens no endpoint and changes no inbound route. It does add a way to authenticate on the existing one — the inbound Google mechanism (FR-061) — which is inbound attack surface, and the original claim that this feature "changes nothing inbound" no longer holds. What bounds it is that the path admits exactly one pinned calling identity per configuration, refuses a configuration without that pin, and reaches only the agents that bind it. The rest of the risk this feature adds is egress and trust in someone else's card.
- **The periodic sweep is ordinary scheduled work** and follows the platform's existing multi-replica rules for it. A sweep that does not run widens nothing, because the delegation-time threshold (FR-050) is the binding control.
- **The Google Agent Platform mechanism serves both directions.** It was specified outbound-only, on the argument that a Google-side partner could authenticate with the OAuth mechanism inbound and a Google inbound entry would be a second way to reach one state. That was withdrawn (Clarifications, 2026-08-31): the OAuth path needs a shared secret and the Google one needs none, which is the same distinction that justifies the Entra mechanism.
- **Inbound Google trust rests on the calling-identity pin, not on the signature.** Unlike the Entra mechanism, whose signing keys are fetched from the pinned tenant and therefore cannot verify another directory's tokens, Google publishes one keyset for every principal. A configuration without the caller pin would admit any Google account, which is why FR-061 refuses one.
- **Existing inbound integrations are backfilled as inbound.** Direction is new; every integration in the field today serves inbound, so the backfill states what is already true rather than changing behaviour.
- **Two registrations may name the same partner.** A legitimate configuration — separate credentials, scopes or budgets against one partner — and FR-042 already requires them to be attributed separately. An accidental duplicate shows as two entries with two health verdicts rather than being silently merged.

## Out of Scope

- **Signing the platform's own agent cards.** Recorded in Assumptions.
- **Consuming a partner's event stream.** The platform polls a partner's task, and consumes a callback where the partner offers one (`011` User Story 3). A held connection per delegation is specified in `011` and deferred there.
- **Discovering a partner's agents without being told where.** No registry crawl and no catalog federation. An operator supplies at least one card location per registration; from there the platform may ask THAT partner what else its credential reaches, on the origin it already authenticated to, and every answer is verified like any other card (FR-060). Finding a partner in the first place stays out of scope.
- **Delegating from anything other than an agent run.** No scheduled outbound work, no flow node, no direct API. Within agent runs, every path qualifies (FR-021).
- **Parking a run so a human answers a partner's clarification.** A partner asks the calling agent, not the user; answering from the agent's own context (FR-031) is the whole of what is supported.
- **Fan-out to several partners as one act**, and any orchestration across partners.
- **Any partner-facing surface beyond the one callback route.** Being told requires being reachable, so `011` User Story 3 adds exactly one route a partner may call back on — gated on an operator's decision rather than on a partner's card, and carrying this surface's own guards: HTTPS, pre-auth rate limiting, a constant-time secret comparison before anything is read, and one uniform not-found. Nothing else is added: the inbound Google mechanism (FR-061) is a credential form on the surface that already exists rather than a surface of its own.
- **Serving any binding other than JSON-RPC**, matching the inbound phase. Outbound is asymmetric and deliberately so (FR-065): serving a second binding is a second public surface to secure, while consuming one is a path through code that already exists. The **gRPC** binding is out of scope in both directions.
- **Any new permission concept, credential model, or usage-accounting concept.** The pre-existing findings behind the platform's API-key model, administrator visibility bypass, and single-secret key derivation (benchmark F1–F4) remain open and are neither fixed nor widened here.
- **Per-partner outbound rate limiting.** The inbound surface rate-limits each partner registration; outbound relies on the per-delegation ceiling and the circuit breaker, and outbound volume is already bounded by how often agents run. A rate limit only narrows and can be added later.
- **Any guaranteed bound on a calling run's latency when a partner is slow**, and any new performance objective, matching the inbound phase's stance.
- **Data-residency guarantees for work crossing vendor boundaries**, which the benchmark flags as unresolved.
- **Any change to the inbound A2A surface's protocol revision, or to how it handles credentials while it stays inbound.** Clearing them when an integration leaves the inbound direction is required by FR-058 and is in scope. Its *exposure model* is deliberately in scope, and its execution bounds turned out to be too. Three inbound changes are in scope and named, and the list is exhaustive:
    - **exposure follows direction** (FR-055): the hook that creates an exposure consults direction instead of treating any A2A binding as consent, the catalog entries gain the direction field, and existing integrations are backfilled as inbound;
    - **a new inbound credential form** (FR-061): the Google mechanism verifies a partner's own Google-issued token. No new endpoint and no new route — a way to authenticate on the surface that already exists;
    - **peer consultation** (FR-064): an external task may consult a peer exposed by the same registration, under that peer's own bounds. It was disabled wholesale before, because a peer runs with its own tools and its own visibility; what makes it admissible is that the peer now runs under the exposure bounds a direct submission to it would have applied.
    Nothing else inbound changes. This entry read "nothing else inbound changes" when only the first was in scope, and was corrected as each of the others landed rather than left to imply a narrower blast radius than the feature has.
