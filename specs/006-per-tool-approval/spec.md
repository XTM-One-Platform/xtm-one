# Feature Specification: Per-Tool Human-in-the-Loop Approval

**Feature Branch**: `006-per-tool-approval`

**Created**: 2026-08-12

**Status**: Draft

**Input**: User description: "feat: per-tool human-in-the-loop approval for tool calls"

## Clarifications

### Session 2026-08-26

- Q: How long does a pending proposal stay answerable, given that a resumable turn's proposals live on a message that never expires while a live turn's live in Redis under the turn marker's TTL? → A: No wall-clock timeout, consistent with FR-015e, but a proposal is superseded the moment the conversation moves on — the next user message in that conversation retires any proposal still pending. The gate is also re-evaluated at the moment of execution, so a tool whose schema changed (FR-019a) or that has since been re-gated asks again rather than riding an old decision. A retired proposal stays visible in the conversation marked **expired** rather than disappearing. **Confirmed by Fred on 2026-08-26**, specifically the supersession rule and the expired-but-visible state — a proposal is bounded by the conversation moving on rather than by a clock. Not taken to the product owner, so it carries engineering sign-off rather than product sign-off.

- Q: The word "chatbot" names five different things across this spec and the product. How should the surfaces be named? → A: Define them once as a Key Entity — **Approval Surface**: browser socket, REST, platform stream, chat channels, public embed — and use those names throughout. "Chatbot" is reserved for the external `filigran-chatbot` package alone (FR-002d). Almost every requirement here is now per-surface (FR-002b1, FR-002c/c1, FR-008a), so acceptance tests need names that pick out exactly one surface.

- Q: The General Assistant has no agent behind it, so it has no `approve_tool_calls` of its own. What decides whether it gates? → A: The install default (FR-014), with no switch of its own. The platform-wide switch, a user's allow-all and the whitelist reach it like any agent.

- Q: On a surface where a proposal can land somewhere shared, such as a Slack or Teams channel, who is allowed to answer it? → A: Only the identified user whose turn is paused. A decision from anyone else MUST be refused and the attempt recorded. Approval is a personal, attributable act (FR-008, FR-015a, FR-017a), so a bystander MUST NOT be able to approve another person's call. It follows that the prompt must reach the reviewer in a form only they can act on: a shared channel may carry a pointer, but the decision itself is taken privately.

- Q: What must FR-002c1's "submit decisions and continue" mean in practice? → A: The resume request executes the approved calls with exactly the arguments the reviewer was shown, appends their results to the conversation, and lets the loop carry on from there. It is rebuilt from the stored messages plus the attached proposals — no durable store of intermediate loop state is introduced. FR-008 already forbids editing arguments, so the call is fully determined by what was displayed. This also settles that delivering a decision into a turn still waiting in memory does **not** satisfy FR-002c1: that requirement is about a turn that has already ended.

- Q: Which surfaces MUST be able to collect an approval, rather than gate and then only explain? → A: Every signed-in surface. Any surface with an identified user MUST be able to carry a decision — the browser, plain REST, and the chat channels alike — by a mid-turn exchange where the transport allows one and by propose-and-resume where it does not. Only the anonymous public embed may gate and explain, because there is no identity to attribute a decision to. This is the literal reading of FR-002b, so a signed-in surface that can only decline is an unmet requirement rather than a deliberate boundary.

### Session 2026-08-20

- Q: Must an administrator be able to set tool approval on a built-in agent? → A: Yes. Confirmed by the product owner (@AreDee-Bangs). Built-in agents are otherwise read-only, and they are what an embedded Suite assistant drives.
- Q: Which fields become admin-writable on a built-in agent? → A: `approve_tool_calls`, beside the existing `enabled`. `human_in_the_loop` and its prompt stay product-owned, and the agent's assignments stay read-only.
- Q: Who counts as an administrator allowed to set it? → A: The existing `can_manage` check, reused exactly as the `enabled` carve-out on built-in agents already does — which resolves to platform admin, since built-in agents are always company-managed. No new permission is introduced.
- Q: What happens to an administrator's approval setting on a built-in agent when the boot-time seed re-syncs it? → A: The administrator's value always wins. The seed MUST NOT write the field on an existing row, so the setting survives every restart and upgrade — unlike `enabled`, which the seed deliberately reverts.
- Q: What must the product require when an administrator turns approval off on a built-in agent? → A: Both a warning before saving — stating that the change reaches the agent's **chats** as well as its runs — and a durable audit record of who changed it, when, and to what. Same posture FR-005 and FR-018 already take toward weakening a gate.

### Session 2026-08-12

- Q: What turns the gate on for an agent, and is it on by default? → A: Its own switch, `agents.approve_tool_calls`, separate from `human_in_the_loop`, which keeps its prompt-driven meaning. Unset follows an install-wide default: on for a fresh install, off for an upgraded one, whose agents — existing or created later — do not gate until an administrator turns approval on (maintainer decision). No agent row is written by the upgrade.
- Q: With approval on, does every built-in tool gate (making an agent pause on every read)? → A: No. Exemption is driven by the HITL whitelist, and read-only tools ship whitelisted.
- Q: Does a standing approval exception survive a change to the tool it covers? → A: Only cosmetic changes. A material change — parameter schema or whitelist membership — invalidates the exception and forces re-approval.
- Q: Should exemption from HITL come from automatic per-tool classification, or an explicit whitelist? → A: An administrator-editable whitelist replaces classification entirely. The product ships a curated default whitelist so a fresh install is usable; anything not on the list gates.
- Q: Can an administrator whitelist a destructive tool, or is some set permanently protected? → A: Any tool can be whitelisted, consistent with how tool allow/deny lists are already administered. The safeguards are a warning before saving and a durable audit record, not a protected set.
- Q: Is the whitelist platform-wide, or overridable per agent or assignment? → A: One platform-wide list. A tool is whitelisted or not, everywhere — gating never depends on which agent or assignment calls it.
- Q: How does an upgraded shipped default interact with an administrator's edits? → A: Two layers. The shipped default is versioned data the product owns and replaces on upgrade; administrator additions and removals live in a separate overlay that survives. A removal stays a removal even if a later default re-adds the tool.
- Q: Does the whitelist apply to MCP tools, given MCP is "out of scope"? → A: Yes — MCP tools gate like everything else, since absence from the whitelist is what gates. Only MCP-specific *configuration* is deferred. Noted as a behavior change for MCP-heavy deployments, which will begin prompting on every MCP call.
- Q: Should `code_interpreter` ship whitelisted, given it executes arbitrary code? → A: Yes, it ships in the default whitelist. Decision taken with the product owner (@AreDee-Bangs). No new mechanism is needed for the fallback: a deployment that disagrees removes it, after which it gates and the reviewer approves each call with the code visible as an argument.
- Q: Is "approve always" an assignment-level configuration or a user preference, and how do admins manage it? → A: A user preference belonging to the person who granted it. Admins get no cross-user view; to act on another user's preferences they use the platform's existing impersonation mechanism.
- Q: Do standing exceptions apply to autonomous (unattended) runs, which have a resolved user identity but no live reviewer? → A: Yes — a standing exception applies to every run of that user, scheduled or interactive. Because this means one click also un-gates unattended execution, the reviewer MUST be told so at the moment they grant it, and the behavior MUST be documented.
- Q: Does approval gating apply to agent chat, or only to assignment runs? → A: Both. Confirmed with the product owner (@AreDee-Bangs) as a **miss in the spec**, not a deliberate boundary: the same agent calling the same tool must not behave differently depending on whether it was reached through a chat or a schedule.
- Q: Autonomous runs will now stall waiting for approval that nobody is watching for — weaken the gate or make the stall visible? → A: Make it visible. Keep the pause, proactively notify the assignment owner when an autonomous run pauses, and call the change out in the upgrade notes. No timeout, no auto-reject.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Gated tools always pause, regardless of LLM judgment (Priority: P1)

A high-stakes tool (e.g., entity deletion, bulk enrichment) is not on the HITL whitelist, so it requires approval. When the agent decides to call that tool during a run, the run pauses and waits for a human decision automatically — the agent cannot skip this step by simply not calling the free-text human-input tool.

**Why this priority**: This is the core safety guarantee the feature exists to deliver. Without deterministic, declarative gating, HITL remains a suggestion the LLM can ignore, which is the exact gap the issue was opened to close.

**Independent Test**: Ensure a tool is absent from the whitelist, trigger a run where the agent calls it, and confirm the run enters a paused/`awaiting_human` state before the tool executes — with no code path that lets the call complete unattended.

**Acceptance Scenarios**:

1. **Given** a tool that is not on the HITL whitelist, **When** the agent calls it, **Then** the run pauses before execution and no result is returned to the agent until a human responds.
2. **Given** a tool that is on the whitelist, **When** the agent calls it, **Then** it executes immediately with no pause.
3. **Given** a newly created agent on a fresh install with the shipped default whitelist untouched, **When** it performs a run mixing read-only and state-changing tool calls, **Then** the read-only calls complete unattended and the state-changing ones pause.

---

### User Story 2 - Reviewer sees a structured proposal and can approve or reject (Priority: P1)

A human reviewer watching a paused run sees exactly what the agent wants to do — the tool's name, its description, and every proposed argument — and can approve it as-is or reject it outright. If rejected, the agent receives a clear reason it can act on instead of crashing or stalling.

**Why this priority**: Pausing without a usable review surface is not a complete feature — this is what makes the pause actionable rather than just a hang. It also delivers the structured Action Proposal groundwork the issue calls out.

**Independent Test**: Trigger a paused run from User Story 1, call the resume endpoint with each of "approve" and "reject", and confirm the tool executes with the proposed arguments (or not at all) and the agent's next step reflects the decision.

**Acceptance Scenarios**:

1. **Given** a paused run awaiting approval, **When** the frontend requests the pending action's detail, **Then** it receives the tool name, description, and full proposed arguments in a structured form suitable for rendering a form (not free text).
2. **Given** a paused run, **When** the reviewer approves without changes, **Then** the tool executes with the originally proposed arguments.
3. **Given** a paused run, **When** the reviewer rejects the proposal, **Then** the tool does not execute and the agent receives a structured rejection it can reason about (e.g., to propose an alternative), rather than a raw/unhandled error.
4. **Given** a paused run, **When** the reviewer chooses "approve always", **Then** they are first shown that the preference also covers scheduled runs, and on confirming, the tool executes now and subsequent calls to that same tool run without pausing **for that reviewer** — in later runs, interactive or scheduled — until they revoke it; another user reviewing the same tool is still prompted.

4. **Given** a gated call proposed on a surface that cannot hold a turn open — a chat channel, or plain REST — **When** the reviewer submits a decision on a later request, and the process that ran the paused turn has been restarted in between, **Then** the approved call executes with the arguments that were shown and the conversation continues from there.
5. **Given** a proposal pending in a conversation, **When** a user other than the one whose call is paused submits a decision, **Then** it is refused and the attempt is recorded, and the proposal stays pending.
6. **Given** a proposal pending in a conversation, **When** that conversation's user sends a new message instead of deciding, **Then** the proposal is retired and a later decision on it is refused rather than executed.
---

### User Story 3 - Real-time proposal rendering (Priority: P2)

A reviewer watching an in-progress run in the UI sees the approval request appear live, without needing to poll or refresh, as soon as the agent proposes the gated action.

**Why this priority**: Builds directly on User Story 1/2's data; without a real-time signal, the reviewer has no way to know a run is waiting on them without manual polling, undermining the "human in the loop" premise for anything but batch review.

**Independent Test**: Subscribe to a run's event stream, trigger a gated tool call, and confirm an `action_proposal` event carrying the same structured data as User Story 2 arrives on the stream at the moment the run pauses.

**Acceptance Scenarios**:

1. **Given** an open event stream for a run, **When** the agent calls a gated tool, **Then** an `action_proposal` event is emitted on that stream containing the tool name, description, and proposed arguments.

---

### User Story 4 - Admins are warned before weakening a gate, and every call is auditable (Priority: P2)

An administrator adding a tool to the HITL whitelist sees an explicit warning the moment they do so — before saving — so they cannot disable a safety gate by accident. Separately, whether a given tool call was auto-run, approved, or rejected, it always shows up in the audit log.

**Why this priority**: Directly required by the refinement decision recorded on the issue; protects against silent scope creep of "which tools are actually gated" and keeps the feature auditable even when gating is bypassed — via the agent's approval switch, via whitelist membership, or via a standing exception. Because "approve always" lets a reviewer durably weaken a gate in one click, the ability to see and revoke that exception is what keeps the click safe. Since exceptions are personal preferences, that visibility belongs to the user who granted it, with administrators reaching it through impersonation rather than a cross-user console.

**Independent Test**: Add a tool to the whitelist and confirm the warning renders immediately (not only after save); grant a standing exception via "approve always", confirm it appears in the granting user's own preferences and can be revoked there, and that no cross-user administrative view of it exists; and run a mix of gated and non-gated tool calls, confirming all appear in the audit log with their gate outcome.

**Acceptance Scenarios**:

1. **Given** a tool that currently requires approval, **When** an admin un-gates it, **Then** a warning is displayed immediately, before the change is saved.

   > **Which control satisfies this** — the whitelist warning (FR-005), rendered when a tool is added to the whitelist. Un-gating a tool is whitelist membership (FR-001), so that is where the warning lives.
2. **Given** a run that includes both gated and non-gated tool calls, **When** the run completes, **Then** every tool call — auto-run, approved, or rejected — is present in the audit log along with its gate outcome.
3. **Given** a user who has granted one or more standing approval exceptions, **When** they open their own preferences, **Then** they see every exception they granted and can revoke any of them, and the tool resumes pausing on their next affected call.
4. **Given** an administrator who needs to revoke another user's standing exception, **When** they attempt it from an administrative screen, **Then** no such cross-user control exists; they must impersonate that user, and the resulting revocation is attributed to both the impersonated user and the administrator.
5. **Given** a reviewer grants or revokes a standing exception, **When** the audit trail is inspected, **Then** the change is recorded with the tool, the owning user, the actor, and the timestamp.
6. **Given** a tool covered by a standing exception, **When** an admin changes its parameter schema, **Then** the exception is invalidated, the tool pauses again on its next call, and the invalidation is recorded in the audit trail.

### Edge Cases

- What happens when an agent's approval switch resolves to off? All its tool calls execute without pausing, whitelisted or not — the switch is a hard override, not an additional gate. Each call is still recorded with the switch that let it run (FR-020).
- What happens to agents on an upgraded install? None gates: the install default is off and the upgrade writes no agent row (FR-014a). That includes agents created after the upgrade, until an administrator turns approval on, per agent or install-wide.
- What happens to a built-in agent whose approval an administrator set, when the platform restarts and re-seeds its built-in agents? The administrator's value stands (FR-012c). The seed re-synchronises everything else about the agent, never `approve_tool_calls`, so a gating decision is not quietly undone by a restart.
- What happens when a standing approval exception exists but the agent's approval switch is later turned off and back on? The exception survives — it is revoked only by its owning user (directly or via an impersonating administrator), not by toggling the switch.
- What happens when an autonomous run calls a gated tool and the run's user holds a standing exception for it? The tool runs without pausing (FR-015b) — the exception applies to unattended runs too. The call is still logged with an outcome identifying it as auto-run under a standing exception (FR-016).
- What happens when an autonomous run calls a gated tool the user has *not* granted an exception for? It pauses and the assignment owner is notified (FR-015f, FR-015d), exactly as if no exception existed anywhere.
- How does a reviewer know that "approve always" also affects scheduled runs? The approval UI says so before they confirm (FR-015c) — the reach of the preference is never discovered after the fact.
- What happens when nobody responds to an autonomous run's approval request? The run stays paused indefinitely — there is no timeout or auto-resolution (FR-015e). The scheduled work does not proceed until a human acts, which is the intended fail-closed outcome rather than a defect.
- What happens when a user who granted a standing exception is deleted or deactivated? Their preferences go with them; the exception stops applying, and any tool it covered pauses for approval again for whoever reviews next.
- What happens when a tool covered by a standing exception is later reconfigured? A material change — to its parameter schema — invalidates the exception, and the tool pauses for approval again on its next call (FR-020). A cosmetic change, such as an edited description or display name, leaves the exception in force.
- What happens when the agent calls a gated tool again immediately after a rejection? The agent is not blocked from proposing again; the same approval flow applies to the new proposal, and repeated identical proposals do not bypass gating.
- What happens when the human reviewer never responds? The run remains paused indefinitely, consistent with the existing pause/resume state machine — no new automatic timeout is introduced by this feature.
- What happens when the agent makes several gated tool calls within the same turn? Each proposed call is gated and surfaced independently; execution of the run does not proceed past a pending proposal.
- What happens when an upgrade ships a default whitelist that re-adds a tool the administrator deliberately removed? The removal wins (FR-001e). Upgrades never silently re-exempt a tool someone chose to gate.
- What happens when an upgrade ships new read-only tools? They take effect as whitelisted with no administrator action (FR-001f), so a release does not reintroduce approval fatigue.
- What does "require approval" mean for a connected platform whose read tools are exempt? *Ask before anything that changes this platform*, not *ask before anything from it* (FR-001g). The whitelist is evaluated before the per-platform exemption, so an agent may read the platform unattended and still stops before editing it. The alternative reading would gate a few hundred tools to protect against calls that cannot change anything.
- What happens when the same tool is used by two agents with very different risk profiles? It gates identically for both — the whitelist is platform-wide (FR-001c). An operator who needs one agent to avoid the tool entirely uses the existing per-agent allow/deny lists, which are a separate mechanism from approval gating.
- What happens when a brand-new tool appears that nobody has whitelisted — a newly added integration, a just-authored custom tool, or one introduced by an upgrade? It gates, per FR-001a. Absence from the whitelist is the default state, so a tool is never silently exempted merely because no one has considered it.

### User Story 5 - Answering a pause without opening the run (Priority: P2)

A reviewer is told an unattended run has paused. Acting on that means opening the run itself, one at
a time, so the answer waits until later and the run waits with it — and while it waits the whole
assignment is blocked, because a paused run counts as active and the schedule keeps skipping.
FR-015d made the pause visible; it did not make it answerable.

They should be able to read the proposal and answer it where they already are: the tool, the run it
belongs to, and the full proposed arguments, then approve or reject without navigating. And when a
fleet of scheduled assignments has paused on the same tool, or one run has paused repeatedly, they
should be able to answer several at once — because the same click repeated twenty times is not
reviewed twenty times.

**Why this priority**: FR-015d notifies the owner precisely because an unattended pause stalls
silently, and the notification is worth only as much as the action it leads to. This is the cost of
the decision path rather than of the decision, which is why it is the reviewer's problem to fix and
not the gate's.

**Independent Test**: Trigger an autonomous run that pauses on a gated tool. From an unrelated page,
open the executions list filtered to what awaits a decision, read the proposed arguments and
approve; the run resumes without opening it. Then pause three runs of one assignment on the same
tool, select all three, and approve once: all three resume and three separate decisions are
recorded.

**Acceptance Scenarios**:

1. **Given** a run carrying my identity is paused, **When** I expand its notification, **Then** I see the tool, its assignment and run, and the complete proposed arguments — not a truncated preview.
2. **Given** an expanded pending approval, **When** I approve or reject it, **Then** the run is answered and the page I was on has not navigated or reloaded.
3. **Given** I answered from the executions list, **When** I open the run afterwards, **Then** the decision reads identically to one made on the run page — same outcome, same attribution.
4. **Given** an approval belonging to another user's run, **When** I open the executions list, **Then** it is not offered to me to answer.
5. **Given** a selected group with a member I have not opened, **When** I try to act on the group, **Then** it is refused and I am told how many remain unread — a group action is not a way to approve something unread.
6. **Given** an expanded proposal, **When** I choose "approve always", **Then** I am told first that it un-gates that tool on every run carrying my identity, and the exception that results is identical to one granted on the run page.
7. **Given** a selection spanning several tools, **When** I act on it, **Then** "approve always" is not offered as a group verb and the confirmation names what the selection spans.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST maintain a single, **platform-wide HITL whitelist** — an administrator-editable list of tools that do not require approval. A tool's `requires_approval` is derived from membership: a tool on the whitelist runs without pausing; every tool not on it gates. There is no per-tool classification field.
- **FR-001a**: The product MUST ship a **default whitelist** covering tools that only read data, so a freshly installed deployment behaves sensibly without an administrator curating the list first. Any tool absent from the whitelist — including one nobody has considered yet — gates by default.
- **FR-001b**: Administrators MUST be able to add tools to and remove tools from the whitelist, and MUST be able to see which entries came from the shipped default and which they added.
- **FR-001c**: The whitelist MUST NOT be overridable per agent or per assignment. Whether a given tool gates MUST be answerable from the whitelist alone, without inspecting the calling agent or assignment.
- **FR-001d**: The whitelist MUST be stored as two layers: the **shipped default**, which the product owns and replaces wholesale on upgrade, and an **administrator overlay** of explicit additions and removals, which upgrades MUST NOT modify. Effective membership is the shipped default with the overlay applied on top.
- **FR-001e**: An administrator's explicit removal MUST persist even if a later shipped default contains that tool — a deliberate removal MUST NOT be silently undone by an upgrade. Likewise, an administrator's addition MUST survive a shipped default that omits it.
- **FR-001f**: Upgrading the shipped default MUST NOT require administrator action for its new entries to take effect, so newly shipped read-only tools do not gate until someone notices them.
- **FR-001g**: The shipped default MUST include the **read-classified tools of the registered Suite platforms**, derived from the same read/write classification the integration catalog presents rather than enumerated by hand — so a tool added by a later platform release arrives classified instead of stale. The classification MUST fail towards gating: a tool whose behaviour cannot be established from its definition counts as changing data. This layer MUST behave as part of the default in every respect an administrator can observe: scoped to platforms actually registered, subject to the overlay, and a removal from it MUST survive an upgrade and a reconnection exactly as FR-001e requires.
- **FR-001h**: Administrators MUST be able to re-gate **all** of one platform's read tools in a single action, and to restore them the same way. The derived layer arrives dozens of entries at a time, so an escape hatch that costs one action per entry would not be one — and a bulk rejection that cannot be undone would be worse than none.
- **FR-002a**: Approval gating MUST apply to **every** path that executes an agent's tools, including interactive chat with an agent and the general assistant — not only assignment runs. A tool that pauses on a schedule MUST also pause in chat.
- **FR-002b**: A chat that pauses MUST present the same structured proposals as a run, and MUST let the user approve, reject, or approve-always without leaving the conversation. Standing approvals granted in chat and in runs are the same preference — a tool a user has accepted does not ask again in either place.
- **FR-002b1**: The obligation in FR-002b is **per surface, not per product**. Every surface that gates a call for an **identified** user MUST be able to carry that user's decision — the browser, plain REST, and the chat channels (Slack, Teams, email) alike. The mechanism may differ with the transport (FR-002c, FR-002c1); the obligation does not. A signed-in surface that gates and can then only explain itself is an **unmet requirement**, not a deliberate boundary: the person is left unable to complete a request the product agrees they are entitled to make, and the gate reads as a malfunction rather than as a control. The single exception is the **anonymous public embed**, where there is no identity to attribute a decision to and to whom no approval may therefore be offered; that surface MUST gate and explain, and MUST NOT be given an approval channel.
- **FR-002d**: Gating changes what **API consumers outside this repository** observe. One is known: `packages/filigran-chatbot` in `FiligranHQ/filigran-ui`, a separate application that talks to the XTM One backend over SSE with a mid-run steering POST — so it already has the client-to-server channel a mid-turn approval needs. No others are believed to exist. A conversation that now pauses returns proposals instead of a completed answer, so any such consumer either renders an approval surface or must be treated as unable to complete gated calls. The corresponding work in `filigran-ui` is planned and proceeds in parallel. What this repository owes it is a stable contract and enough notice: a consumer that ignores pending approvals appears to hang rather than failing cleanly, so the shape must be settled before either side ships.
- **FR-002c**: A chat MUST pause **within the turn** where the transport allows it (WebSocket): the agent stops at the gated call, the reviewer decides inline, and the same turn continues with the tool result. Ending the turn and restarting would discard the reasoning already done and make an approval feel like a rejection — and in chat, unlike a scheduled run, a human is already present to answer.
- **FR-002c1**: Where the transport cannot carry a mid-turn exchange (plain REST), the turn MUST end cleanly with its pending proposals attached, and a subsequent request MUST be able to submit decisions and continue. This is the degraded path, not the intended one, and is what an external REST consumer codes against.
- **FR-002c2**: "Continue" in FR-002c1 means the subsequent request MUST execute each approved call **with the arguments the reviewer was shown**, append the results to the conversation, and let the agent carry on from that point. The resumed turn MUST be reconstructed from the stored conversation plus the proposals attached to it; this feature MUST NOT introduce a durable store of intermediate loop state (partial tool results, reasoning, iteration counters). Because FR-008 forbids editing proposed arguments, what the reviewer approved fully determines what runs, and re-planning the turn from scratch is NOT an acceptable reading — a reviewer who approves one action MUST NOT get another.
- **FR-002c3**: Delivering a decision to a turn that is **still waiting** does not satisfy FR-002c1. That requirement governs a turn that has already **ended**: its test is that the process holding the turn can be gone — restarted, or a different replica entirely — and the decision still lands. An implementation that only hands decisions to a live, blocked turn satisfies FR-002c, not FR-002c1, and leaves every surface that cannot hold a turn open unable to collect an approval at all.
- **FR-002c4**: A pending proposal MUST NOT expire on a clock — FR-015e's "no timeout, no auto-resolution" applies to a waiting reviewer on every surface, not only to autonomous runs. It MUST instead be **superseded by the conversation moving on**: the next user message in that conversation retires any proposal still pending, and a decision arriving for a retired proposal MUST be refused and recorded (FR-020) rather than executed. A retired proposal MUST remain **visible in the conversation, marked expired** — it MUST NOT simply disappear. It was a question the product asked and the person did not answer; removing it silently on their next message reads as the product having dropped the request, and leaves no trace of a gated call that never ran. Independently, the gate MUST be re-evaluated at the moment of execution, so a call whose tool schema has since changed (FR-019a), or whose tool has since been re-gated, asks again instead of riding a decision taken against a different tool. Rationale: the two mechanisms in play expire differently — a live turn's proposals are held under the turn marker's TTL while a resumable turn's are attached to a stored message that never expires — and without this requirement the same product would answer a day-old proposal on one surface and refuse it on another.
- **FR-002**: When a tool's resolved `requires_approval` is `true` and the agent's approval switch resolves to on (FR-012), the system MUST automatically pause the run and request human approval before executing that tool call — independent of whether the agent itself invokes the free-text human-input tool.
- **FR-003**: No tool is permanently exempt from whitelisting. An administrator MAY add any tool to the whitelist, including a destructive one, consistent with how tool allow-lists and deny-lists are already administered on this platform. The safeguards are disclosure at the moment of the change (FR-005) and a durable audit record (FR-018), not a protected set the product refuses to un-gate.
- **FR-004**: The whitelist MUST apply uniformly to built-in, custom, and integration tools — a tool's origin does not affect whether it can be whitelisted or how membership is evaluated.
- **FR-005**: The whitelist UI MUST display a warning the moment an administrator adds a tool to the whitelist, before the change is saved, stating that the tool will then run without human approval. The warning MUST be more prominent for a tool that writes, deletes, sends, or otherwise acts outside the platform.
- **FR-006**: The approval request payload MUST include the tool's name, its description, and the full set of proposed arguments — each argument's name, its value, and its description where the tool declares one — so the reviewer can judge what the argument means, not just what it is set to.
- **FR-007**: The system MUST emit an `action_proposal` event on the run's real-time event stream at the moment a gated tool call is proposed, carrying the same structured data as the approval request payload.
- **FR-008**: A human reviewer MUST be able to resolve a pending approval request by approving it as-is, approving it always (FR-015), or rejecting it. The proposed arguments are not editable: a reviewer decides on the call the agent proposed, and an agent that proposed the wrong call is corrected by rejecting it with a reason it can act on (FR-010).
- **FR-008a**: A decision MUST be accepted only from someone entitled to answer that run, and never from an unidentified or uninvolved party. A decision submitted by anyone else MUST be refused, and the refusal recorded per FR-020 — never silently ignored, and never applied. This holds on every surface, and it is the constraint that governs surfaces where a proposal can be seen by more than one person: a channel shared with other people MAY carry a notice that approval is pending, but the proposal's arguments and the decision itself MUST be delivered and taken where only that user can act. Approval is an attributable act by one named human (FR-008, FR-015a, FR-017a); a bystander MUST NOT be able to approve, and an administrator MUST NOT be able to answer on someone's behalf except through the impersonation route FR-017a already prescribes.
- **FR-008b**: Who is entitled follows the run's ownership, not the pause. For a **personal** run that is its owner and no one else. For a **company-managed** run it is any administrator — that is what company-managed means, and requiring the triggering user would strand automation the moment they are unavailable or have left. An administrator answering someone else's company-managed run is a deliberate, audited path (FR-017b), not an exception being tolerated.
- **FR-008c**: Where an administrator answers a company-managed run, any standing exception the decision creates MUST be granted to the identity the run **executes as**, not to whoever clicked. Granting to the clicker writes a preference onto an account the gate never consults: the tool would go on prompting while the administrator's own list claimed it never would — a silent no-op in a control whose entire promise is "this will not ask again".
- **FR-010**: When a reviewer rejects a proposed tool call, the system MUST return a structured rejection result to the agent (distinct from an unhandled/raw error) so the agent can adapt its plan.
- **FR-011**: The existing `request_human_input` builtin tool MUST continue to function unchanged for free-text human-input requests not tied to a specific gated tool call. `human_in_the_loop` (agent and assignment) keeps its meaning — this tool plus the review prompt, off by default — and MUST NOT turn the gate on.
- **FR-012a**: Gating MUST resolve from the agent's approval switch alone, for its runs (every trigger) and its chats alike, channel bots included. There is no assignment-level override.
- **FR-012a1**: The **general assistant** has no agent behind it, so it MUST follow the install default (FR-014) and MUST NOT be given a switch of its own. The platform-wide switch (FR-023), a user's allow-all (FR-024) and the whitelist reach it like any agent.
- **FR-012b**: An administrator MUST be able to set `approve_tool_calls` on a **built-in agent** — one the product ships and otherwise keeps read-only — beside the existing `enabled` carve-out; every other field, `human_in_the_loop` and its prompt included, stays product-owned, and the agent's assignments stay read-only. Authorisation MUST reuse the platform's existing agent-management check, which resolves to platform administrator because built-in agents are always company-managed. Confirmed by the product owner as required behaviour.
- **FR-012e**: Turning approval off on an agent MUST be disclosed and recorded, on the same footing as adding a tool to the whitelist (FR-005, FR-018). Before the change is saved the interface MUST state its reach — the agent's chats as well as its runs — and the change MUST produce a durable audit record identifying the agent, the value set, who set it, and when. Per-call gate outcomes (FR-020) are not a substitute: they record what a weakened gate allowed, never who weakened it.
- **FR-012c**: An administrator's `approve_tool_calls` on a built-in agent MUST survive the product's boot-time re-seeding of built-in entities. The seed MUST NOT write the field on a row that already exists, and this MUST be enforced by test. The distinction from `enabled` is deliberate: the seed reverts a disabled built-in assignment on purpose, and doing the same to a gating decision would revert an operator's choice on the next restart with no log line and no audit record.
- **FR-012**: Whether an agent's tool calls go through the gate MUST be its own switch, `agents.approve_tool_calls` — on, off, or unset — separate from `human_in_the_loop` (FR-011). Unset follows the install default (FR-014).
- **FR-013**: The resolved approval switch MUST act as a hard override: when it resolves to off, no tool call pauses for approval regardless of any individual tool's `requires_approval` setting; when it resolves to on, every tool call whose `requires_approval` is `true` pauses for approval unless a standing approval exception exists for that tool (FR-015) or the gate is suppressed wholesale by FR-023 or FR-024.
- **FR-014**: An install-wide default, `platform_settings.approve_tool_calls_default`, MUST decide for every agent whose switch is unset, and the general assistant. A fresh install MUST start with it on, so a new agent there gates with no operator action. An administrator changes it in Settings, strictly as a boolean and audited; any signed-in user may read it, so an agent page can say what "follow the install default" means.
- **FR-014a**: An upgraded install MUST start with the install default off and the upgrade MUST NOT write any agent row, so no agent — existing or created afterwards — begins pausing until an administrator turns approval on, per agent or install-wide.
- **FR-014b**: A call that ran because the install default is off MUST be recorded with its own outcome, distinct from an agent whose own switch is off (FR-020): the first is an administrator's install-wide decision, the second the agent's.
- **FR-014c**: The upgrade notes MUST describe approval as opt-in with nothing to do on upgrade, and say how to turn it on per agent or install-wide.
- **FR-015**: A reviewer resolving an approval request MUST be able to choose "approve always", which both approves the current call and records a standing approval exception as a preference belonging to that reviewer. The exception MUST persist across future runs until explicitly revoked.
- **FR-015a**: A standing approval exception MUST apply only to the user who granted it. A different user reviewing the same tool on the same assignment MUST still be prompted for approval, since they have expressed no such preference.
- **FR-015b**: A standing approval exception MUST apply to every run carrying that user's identity, whether **interactive** (a human triggered it and may be watching) or **autonomous** (scheduled, triggered, or otherwise executing unattended). A tool covered by an active exception therefore runs without pausing in a scheduled run.
- **FR-015c**: Because granting an exception also un-gates unattended execution, the approval UI MUST state this at the moment of granting — before the reviewer confirms — so "approve always" is never an uninformed choice. The scope of the preference MUST also be documented in user-facing documentation.
- **FR-015d**: When an autonomous run pauses for approval, the system MUST proactively notify the assignment's owner, so that a run waiting on a human nobody is watching for does not stall silently. The notification MUST identify the assignment, the tool awaiting approval, and how to act on it.
- **FR-015e**: An autonomous run awaiting approval MUST remain paused until a human resolves it. The system MUST NOT auto-approve, auto-reject, or time out the pending request.
- **FR-015f**: An autonomous run MUST still pause on any gated tool call **not** covered by an active exception, and MUST notify per FR-015d. Standing exceptions narrow which calls pause; they do not disable pausing for unattended runs.
- **FR-016**: While a standing approval exception is in effect for a tool, calls to that tool MUST execute without pausing, and MUST still be logged per FR-019 with a gate outcome identifying them as auto-run under a standing exception (distinguishable from a tool that was never gated).
- **FR-017**: A user MUST be able to view all of their own standing approval exceptions and revoke any of them from their own preferences; after revocation, the tool MUST resume pausing for approval on that user's next affected call.
- **FR-017a**: The system MUST NOT provide administrators a cross-user view of, or direct write access to, other users' standing approval exceptions. An administrator who needs to inspect or revoke another user's exception MUST do so through the platform's existing impersonation mechanism, acting as that user.
- **FR-017b**: Actions taken on standing approval exceptions while impersonating MUST be attributed in the audit trail to both the impersonated user and the administrator who performed the impersonation.
- **FR-018**: Granting and revoking a standing approval exception MUST each be recorded in the audit trail, capturing which tool, which user the preference belongs to, who made the change (including the impersonating administrator, if any), and when.
- **FR-019**: A standing approval exception MUST be scoped to a single user and a single tool. It MUST NOT extend to other tools, and MUST NOT apply to any user other than the one who granted it.
- **FR-019a**: A material change to a tool — to its parameter schema — MUST invalidate any standing approval exception covering it, so the tool pauses for approval again on its next call. Cosmetic changes, such as description or display name, MUST NOT invalidate the exception.
- **FR-019b**: Invalidation of a standing exception by a tool change MUST be recorded in the audit trail per FR-018, identifying the change that caused it, and MUST be visible to the owning user alongside their remaining exceptions.
- **FR-020**: The system MUST log every tool call and its gate outcome (auto-run because the agent's approval switch is off, auto-run because the install default is off, auto-run because whitelisted, auto-run under a standing exception, auto-run because approvals are switched off platform-wide, auto-run because the user allows all tools, approved, approved-with-modification, or rejected), regardless of whether that call was actually gated. A call the agent loop answers itself and never dispatches — the tool-gating meta-tool — MUST also carry a named outcome rather than a blank: a null is what a gate that failed to install looks like, and the two must stay distinguishable.
- **FR-021**: Integration tools MUST support, at minimum, a single approval toggle applied to the whole integration in this phase; true per-tool approval granularity for integration tools is deferred to a later phase and MUST first be validated end-to-end on one existing integration before wider rollout.
- **FR-021a**: A **registered Suite platform** (OpenCTI, OpenAEV, OpenGRC, …) contributes tools this product classifies only coarsely: the ones that merely read are exempt by name (FR-001g), and everything else — anything that changes the platform, plus every consolidated `manage_…` tool whose behaviour depends on its arguments — cannot be classified per tool. Whether *those* gate MUST therefore be decided **per platform**, from two inputs that MUST be kept separate: a **capability** the platform reports about itself at registration (can its embedded assistant display an approval prompt and return a decision?), and a **policy** only an operator can set (what to do while it cannot). Deriving the capability from a table of product versions is explicitly rejected — it writes another team's release schedule into ours and lies the moment anyone backports.
- **FR-021b**: The capability MUST be tri-state: never declared, declared unable, declared able. "Never declared" MUST NOT be read as "unable" — the first is every build predating the capability, the second is a deliberate statement — and both fall through to the operator's policy. A platform that later declares the capability MUST resume gating with no operator action, and an operator's explicit choice MUST outrank a later declaration, with the interface offering the safer posture rather than silently re-arming it.
- **FR-021c**: For a provider a registered platform governs, that platform's policy MUST be the **single** source of truth. The per-integration toggle of FR-021 MUST NOT be able to contradict it in either direction, and an attempt to set it for such a provider MUST be refused rather than stored — a preference nothing enforces is worse than none, because later reads report it as though it were in force.
- **FR-021d**: Where a client of a platform declares, per message, that it will answer an approval prompt, the system MUST record that observation and MAY use it to offer an operator the safer posture. It MUST NOT decide anything on its own: one capable client does not speak for an unattended caller of the same platform, so the observation informs the offer and never the gate.
- **FR-022**: MCP tools MUST be gated by the same whitelist as every other tool — they are not shipped on the default whitelist, so an agent whose approval gate is on pauses before each MCP call. What is out of scope is MCP-*specific* approval configuration (declaring approval in a server manifest, per-server modes); that MUST be addressed separately. An operator who needs a particular MCP tool to run unattended whitelists it by name like any other tool.
- **FR-023**: An administrator MUST be able to switch the approval gate off for the entire platform. While it is off, no tool call pauses for any user on any surface, and the controls that only shape *which* tools gate — the whitelist and the per-platform policies — MUST leave the interface with it rather than remain as controls that decide nothing. The switch MUST default to on, MUST NOT delete or alter any standing approval exception (FR-015), and MUST be read fail-closed: a switch the system cannot read MUST gate normally rather than suppress. It MUST NOT suppress the agent's own request for human input, which is the agent choosing to ask a question rather than the platform forcing a pause.
- **FR-024**: A user MUST be able to declare that none of their own tool calls pause — the wholesale form of the per-tool "approve always" of FR-015, and inheriting its reach: no run carrying that user's identity pauses, **interactive or autonomous alike**. Their existing standing exceptions MUST be preserved rather than deleted, so clearing the setting restores the exact previous posture, and the interface MUST NOT go on presenting the now-moot per-tool list as though it were still in force.
- **FR-025**: The two switches MUST be resolved at a **single** point shared by every Approval Surface and by the assignment engine's own gate, so that no entry point can honour one and miss the other. Suppression MUST install a gate that still records an outcome rather than no gate at all, so FR-020 keeps holding while nothing pauses, and the two outcomes MUST be named apart because they name different responsible parties — platform policy in one case, the user's own choice in the other. Setting either switch MUST itself be recorded in the audit trail per FR-018.
- **FR-026**: A reviewer MUST be able to approve or reject a pending approval from the executions list, without opening the run. A notification entry MUST lead somewhere the decision can be made; it need not be answerable in place itself.
- **FR-027**: Before a decision is possible, the surface MUST disclose everything the run page discloses for that proposal — the tool, its assignment and run, and the **complete** proposed arguments. This is FR-006 on a new surface, and no surface's size is a licence to abbreviate it.
- **FR-028**: Only someone entitled to answer the run may answer it, per FR-008a and FR-008b. An approval belonging to anyone else MUST NOT be listed as actionable, and an attempt to answer one MUST be refused and recorded rather than silently ignored. A group action MUST authorise **every member individually**, so bundling a run with ones the caller owns grants no reach over it.
- **FR-029**: A decision made from the executions list MUST be indistinguishable in effect from the same decision made on the run page — same resumption, same recorded outcome (FR-020), same attribution including impersonation (FR-017b). It MUST consume the existing decision path rather than grow a second one that can drift.
- **FR-030**: Answering MUST be safe against a proposal that is no longer pending — the run ended, or it was already answered on another surface. The system MUST refuse rather than record a second decision, and MUST say which happened. It MUST NOT claim more than it knows: the resume path clears every pause field, so no surface can name who decided or when without new state.
- **FR-031**: A reviewer MUST be able to select several pending approvals and act on them in one action. The selectable unit is the **run**, not the individual proposal: the agent loop refuses a partial set within a run, because an undecided call leaves a `tool_use` block with no `tool_result` and every provider rejects the next request.
- **FR-031a**: Because approvals sit interleaved with notices that cannot be answered at all, the surface MUST offer a shortcut selecting exactly those awaiting a decision, and every member MUST stay individually deselectable afterwards.
- **FR-031b**: A group action MUST make plain what it spans before it is taken — how many decisions, across how many runs and tools. An arbitrary group has no meaning of its own, so its contents are the only thing that can make it reviewable.
- **FR-031c**: A group rejection MUST collect **one** reason and apply it to every member. A rejection's reason is the agent's only signal about what was wrong; given none it is told "No reason given.", and the instruction it then receives leaves it nothing to do but ask how to proceed — so a reasonless group rejection buys one click and costs N follow-up questions. An empty reason MUST stay permitted: a reviewer may genuinely have nothing to say.
- **FR-032**: A group action MUST record each member as its own decision with its own audit entry, and MUST NOT create a blanket approval — widening what a group may decide never widens how it is recorded.
- **FR-032a**: "Approve always" MAY be the verb of a group action, provided the disclosure **enumerates every** tool the click would permanently un-gate. That tells the reviewer strictly more than the per-proposal disclosure does, which is what makes it safe over a set rather than a single call.
- **FR-032b**: A surface offering it MUST, before submitting, name every distinct tool it would un-gate, state that the effect reaches unattended runs, and say it is revocable. A generic "are you sure?" MUST NOT stand in for that list — the enumeration *is* the disclosure. The control MUST also be distinguishable from the one-off approve rather than hidden inside it, since a durable choice one pixel from a transient one is a durable choice made by accident.
- **FR-032c**: However granted, the exception MUST come from the same mechanism as one granted on a single proposal (FR-037b) — same scope, same fingerprint, same revocation. A batch MUST NOT grow a grant path of its own.
- **FR-033**: A group action MUST report per-member results. Members that could not be answered MUST be named with the reason, and MUST NOT cause the rest to be rolled back — partial success is the expected outcome here, not an error state.
- **FR-034**: FR-027's disclosure MUST hold for **every** member of a group. Where a surface renders each pending proposal expanded as a matter of course, that is satisfied by construction. Where a surface hides proposals behind an interaction, it MUST NOT allow a group action over anything unopened, and MUST say how many remain rather than only disabling the control.
- **FR-035**: A reviewer MUST be able to narrow the executions list to what awaits their decision, so a stalled run is discoverable without opening anything.
- **FR-036**: A pending approval MUST stay listed until it is answered or otherwise resolved, and MUST NOT be dismissible as though it were a notice. An approval is an obligation, not an announcement.
- **FR-037**: A reviewer MUST be able to choose "approve always" (FR-015) from this surface as well as from the run page. Withholding it would leave the fast path offering only the choice that keeps interrupting.
- **FR-037a**: FR-015c applies unchanged: the reviewer MUST be told, before confirming, that the exception also un-gates unattended execution of that tool on every run carrying their identity. It MUST NOT be reduced to a tooltip or a second meaning of the approve control.
- **FR-037b**: An exception granted here MUST be identical to one granted on the run page — same scope (FR-019), same invalidation on a material tool change (FR-019a), same visibility and revocation in the granting user's own preferences (FR-017).
- **FR-039**: A standing exception MUST be reachable by runs that are **already paused** on the tool it covers, not only by calls yet to be gated. The gate has already run for anything sitting awaiting a decision, so a reviewer who grants "always" on one of several identical pauses would otherwise still answer each of the others by hand — "always" doing least at the moment it is worth most.
- **FR-039a**: The system MUST NOT resume such a run on its own. A run restarting with no explicit action is surprising, and the reviewer may be part-way through deciding something else. Instead the surface MUST say that paused runs are covered and let them be released in one action, so the gesture is explicit and paid once rather than once per run.
- **FR-039b**: A run qualifies only when **every** one of its pending calls is covered. One covered and one uncovered call means the run is answered by hand: releasing it would approve a call the reviewer never consented to, which is FR-006 defeated by arithmetic.
- **FR-039c**: Releasing MUST go through the same group path as any other multi-run decision (FR-031–FR-033), so per-member results, authorisation and the already-answered race are handled identically. It MUST NOT grant anything: the exceptions already exist, and that is the whole premise.
- **FR-039d**: The offer MUST state the scope it can actually act on. Like every group action it answers only the runs the surface has loaded (FR-031), so a count presented as "everything waiting" would promise a release it cannot perform.
- **FR-040**: A reviewer MUST be able to answer every paused run that uses **only** tools they name, across everything they may answer rather than only the rows a surface has loaded. This is the one approval path that reaches past the loaded page, and it is safe for the same reason FR-015 is: the reviewer is judging a **tool**, not each call's arguments. It is the weaker form of that decision — it answers what is waiting and grants nothing durable — so wherever a standing exception is acceptable, this must be.
- **FR-040a**: A run qualifies only when **every** one of its pending calls is a named tool. A run cannot be half-answered, so approving it on one of its tools would sweep in a call the reviewer did not choose. Naming several tools is therefore not a convenience: it is what makes such a run answerable at all.
- **FR-040b**: Runs held back by FR-040a MUST be reported as the tool combinations they are, not merely counted. The combination is what makes such a run answerable, so a bare count leaves a reviewer unable to reach it — and a tool appearing in no single-tool run then cannot be named at all. It also leaves the FR-040d disclosure understating itself: a selection covering a combination answers its runs too, so a total built from single-tool runs alone claims less reach than the decision has. What the current selection does NOT yet cover MUST still be reported, since that is what tells a reviewer naming one more would release them.
- **FR-040c**: The counts offered MUST come from the whole answerable set, never from the loaded page — a per-tool decision reaches past the page, so a page-derived total would understate exactly what is being judged. Runs and calls MUST be counted separately: one run can hold several calls of the same tool.
- **FR-040d**: Before it fires, the surface MUST state that the decision answers calls the reviewer has not read individually. This is the counterpart to FR-015c: the reach is different — one turn's worth rather than every future run — but the thing being consented to is the same, a tool rather than a set of arguments.
- **FR-040g**: A run whose decision has been recorded MUST NOT be counted or offered again, even while it still reads as paused. Resuming is queued rather than immediate — the status does not change until a worker picks the run up — so a surface that counted status alone would tell the reviewer something needs them when what it needs is a queue drain, and would let a second decision overwrite the one already recorded.
- **FR-040f**: The cross-page total MUST be refreshed by **every** path that changes run state — answering from a card, from a selection, from the by-tool picker, dismissing, deleting — not only by the path that produced it. A total that outlives the work it describes claims a backlog that is already cleared, which is worse than not showing one. It MUST also refresh at least as often as the list it sits above: the two poll on independent clocks, so at equal intervals they can disagree for a whole one, which reads on screen as the total being wrong rather than late.
- **FR-040e**: "Approve always" MUST be available here too. It is the clearest-consented form of it in the product: FR-032b asks that such a disclosure enumerate every tool being un-gated, and here the reviewer named that list themselves. Its confirmation MUST still state the durable reach, which is the part they did not choose — every future run carrying their identity, not only the calls waiting — and the control MUST stay distinct from the one-off approve rather than folded in beside it. However many runs it answers, the exceptions granted MUST be one per tool (FR-032c), never one per run.
- **FR-040h**: Where the surface names a narrower set than "everything you may answer" — one agent's activity list — both the counts and the decision MUST be scoped to that set. A control offered on an agent's page that resumed another agent's runs would act outside the scope it shows, and a total taken from the whole queue would describe a backlog the page cannot clear. The scope MUST reach the decision endpoint and not only the count, since it is the decision that acts. "Approve always" is the exception and cannot be scoped: a standing exception is per user and per tool (FR-019), so its confirmation MUST also say that runs of other agents already paused on the tool stay paused — the gate has already run for them, and only the sweep beside the grant releases anything.
- **FR-041**: These surfaces are additive by default. Every control already reachable — the platform policy list, the profile's per-tool approvals, the agent's approval switch — MUST stay where it is and keep working, because an operator who learned one path must not lose it to a redesign. A control MAY be consolidated onto one screen only when that screen is a strict superset of the one it replaces: the whitelist editor is managed on the Tools page (FR-051) rather than in Settings, which keeps the platform switches. Anything short of a superset is a lost path, not a consolidation.
- **FR-042**: The user's own approval posture MUST read as one grouped surface rather than as sibling rows among unrelated profile settings. The wholesale switch and the per-tool list are two layers of a single decision — most permissive first — and a reviewer who cannot see them together cannot tell what their posture actually is.
- **FR-043**: The wholesale allow-all of FR-024 MUST default to off, and turning it on MUST offer to answer the runs **already paused**, listing the tools they wait on for the user to tick. This is FR-039 applied to the wholesale switch: the gate has already run for anything sitting awaiting a decision, so without it the switch does least at the moment it is worth most. Nothing MUST be answered for an unticked tool, runs mixing a ticked and an unticked tool MUST be reported as held back (FR-040a, FR-040b), and declining the offer MUST still leave the switch on — the grant and the sweep are two decisions.
- **FR-044**: The platform kill switch of FR-023 MUST be settable from deployment configuration, read **once**, when the platform settings row is first created. Thereafter the stored value is authoritative and the variable is ignored, exactly as `TOOL_APPROVALS_PLATFORM_DEFAULT` seeds a platform's policy: a variable that kept overriding would silently undo an administrator's choice on every restart, and one read on upgrade is what lets a deployment land the feature already off. It MUST stay fail-closed (FR-023) — a value that cannot be read gates.
- **FR-045**: Where tools are listed, each MUST show whether it currently gates. From there a user MUST be able to grant the standing approval of FR-015 for their own calls, and an administrator to add or remove the tool from the platform whitelist (FR-020) — the two are different decisions with different reach and MUST NOT be presented as one control. Tools that are neither builtin nor custom — MCP, integration and platform-contributed — MUST get their own section, because they can never appear on the shipped whitelist (we do not know what they do) and so are the ones an operator has to rule on.
- **FR-046**: An agent's gate status MUST be visible on its card in the list, not only inside its configuration, and the list MUST carry a count of how many of its agents gate. That count MUST open the list of gated agents and link to the user's own allow-all (FR-024), which is the one control that answers "why is everything asking me?" without visiting each agent.
- **FR-047**: A registered platform's chatbot MUST show its gate status where the platform is managed, reporting both halves the state actually has: whether the platform can ask at all (`supports_approval_prompts`, a fact it reports) and the policy applied when it cannot (FR-022). "Whitelisting a chatbot" is that policy set to skip — it MUST NOT introduce a whitelist scoped to one caller, which would contradict the whitelist being platform-wide and the sole source of truth for what gates.
- **FR-048**: The integrations surface MUST carry the same indicator for the platform behind each integration, and MUST allow an integration's tool gating (`requires_approval`) to be changed in place. An operator deciding whether a connection's writes should pause is looking at the connection, not at a settings screen two clicks away.
- **FR-049**: The rule that decides what is exempt MUST be the same wherever a tool comes from. A read tool of a connected integration or a bound MCP server MUST be exempt on the same classification basis as a registered platform's reads (FR-022), scoped to what is actually connected — an unconnected provider exempts nothing, since its tools do not exist here and listing them would make the one screen answering "what runs without asking?" unreadable. Before this widening, the same tool gated or did not depending only on which registry defined it, which is not a rule anybody could state.
- **FR-049a**: Three things MUST outrank the classifier, because each is a decision a person already made or a risk the classifier cannot see. A tool hand-gated by the product (the read that is a read *of an arbitrary document*) stays gated. A tool an administrator re-gated stays re-gated, and that override MUST survive the upgrade that would otherwise re-derive it. And a channel bot's tools are never derived at all: reading a channel is reading people's conversations rather than platform data, which is a decision for a person to make per tool rather than one to infer from a verb.
- **FR-049b**: The derived set MUST come only from what an administrator controls. A personal MCP binding needs no administrator, while this set is exempt platform-wide and the whitelist matches by name — so honouring one would let any user un-gate a name for everybody, including a name that is not theirs. Only company-managed, enabled servers count.
- **FR-049c**: Every derived entry MUST be listed and attributed to what contributes it, exactly as the platform half is. A tool that stopped asking and appears on no screen is the state this whole feature exists to make impossible, and "derived" is not a reason to hide it — it is the reason nobody chose it individually and so the reason it needs showing.
- **FR-050**: A channel bot MUST carry its own approval switch, per configured bot rather than per provider: two bots of one provider are two connections and can be trusted differently. Turning it off means the bot is trusted, which has two consequences and needs both — a conversation it routes runs uninterrupted whatever tool the agent reaches for, and the bot's own message tools stop pausing wherever they are called. The first is what makes a gated tool usable through a bot at all: the chat channels cannot collect a decision today (FR-002b1 is unmet there), so the turn ends with an explanation and the tool is not delayed but unavailable.
- **FR-050a**: The switch that governs a turn MUST be the bot the agent is bound to for that channel, not any connected bot of the same provider. Where several are connected, reading the wrong one would run one bot's conversations unattended on another bot's authority — and would make switching off the intended bot do nothing.
- **FR-050b**: A call that ran because a bot was switched to uninterrupted MUST be recorded with its own outcome, distinct from the agent's own switch. FR-020 asks why a call ran and the answer has to name the switch somebody flipped: an agent that gates on the web, on its scheduled runs and through every other bot is not an ungated agent, and recording it as one misattributes a per-connection decision to the agent.
- **FR-051**: The platform whitelist MUST be edited where the tools are listed, not on a settings screen, so that ruling on a tool and seeing what the tool is are the same act. That surface MUST offer everything the editor it replaces did: per-tool exempt and re-gate, a re-gated shipped default identified as such and restorable, a per-platform bulk re-gate of classified reads, and the addition of a tool by name that nothing here has run — with a louder warning when the typed name reads as consequential, since a free-text name has no row, description or classification to judge it by. It MUST refuse every edit while the effective whitelist cannot be computed (an unreadable platform registration), because a tool then shown as gating may in fact be exempt and exempting it would pin that mistake.
- **FR-052**: Where a connection lists the tools it contributes — an integration's configuration, a bot's tool list — each tool MUST report whether it pauses, and MUST answer for THAT connection rather than for the provider: the whitelist answers by name, and a switch turned off on one of three connections leaves the other two pausing. Those surfaces MUST link to the control rather than host it, because a control keyed by tool name sitting beside a connection's own switch reads as changing that connection.
- **FR-053**: Any count or state a surface shows MUST say whose answer it is. The catalogue's membership is the deployment's answer and excludes one person's standing approvals by design; a surface phrased for the reader MUST fold in their approvals, their allow-all and the platform switch. A group header reading "4 of 4 pause" above a row reading "you approved it for yourself" is one screen contradicting itself.
- **FR-054**: A gated state a reader cannot explain from the controls MUST explain itself. A read tool that gates anyway (FR-049a), a shipped default somebody re-gated here, and a bot's read tool (FR-049) all look like the product malfunctioning; each MUST say which decision produced it, in the surface's own words rather than by naming a layer.
- **FR-055**: Changing a tool's parameters withdraws every standing approval for it, because consent was fingerprinted against the old shape (FR-019a). The editor MUST say so before the change, and MUST count the other people it reaches — a count, never identities, and only of approvals that still describe the tool, since a stale one belongs to somebody the gate is already asking again.
- **FR-056**: A reader MUST be able to see which tools they have already approved, from the surface that can also revoke and re-gate them. An approval naming a tool that surface cannot list — a server since removed, a provider disconnected — MUST be reported rather than dropped, because a filter that hides it says the approval does not exist.

### Key Entities

- **Tool Definition**: A built-in, custom, or integration tool exposed to an agent; carries a name, description, and parameter schema. Whether it requires approval is not stored on the definition — it is derived from HITL whitelist membership.
- **HITL Whitelist**: The single platform-wide set of tools exempt from approval, computed from two layers — the **shipped default** (product-owned, versioned, replaced on upgrade) and the **administrator overlay** (explicit additions and removals, never touched by upgrades). Each effective entry is attributable to the layer it came from. Membership is the sole source of truth for whether a tool gates — it is not scoped to, or overridable by, any agent or assignment. Distinct from the existing per-agent tool allow-lists and deny-lists, which govern which tools an agent *can call at all*; this list governs only whether a call it is already permitted to make needs approval.
- **Approval Request (Action Proposal)**: A pending human decision tied to one proposed tool invocation; carries the tool name, description, proposed arguments, a reference to the run/assignment it belongs to, and a status (pending, approved, approved-with-modification, rejected).
- **Agent Approval Switch**: `agents.approve_tool_calls` — on, off, or unset — deciding whether an agent's calls go through the gate at all (FR-012). Unset follows the **install default** (`platform_settings.approve_tool_calls_default`, FR-014): on for a fresh install, off for an upgraded one. Writable by an administrator on built-in agents (FR-012b). Distinct from `human_in_the_loop`, which keeps its prompt-driven meaning (FR-011).
- **Wholesale Suppression Switches**: Two controls that sit *above* the whitelist and the agent approval switch and answer "does anything pause at all": a platform-wide switch an administrator owns (FR-023) and a per-user allow-all a user owns (FR-024). Neither narrows or widens *which* tools gate — that stays the whitelist's job — and neither destroys the standing exceptions it makes temporarily moot.
- **Approval Surface**: One of the distinct ways a person reaches a gated tool call, named canonically because nearly every requirement above is per surface rather than per product. Exactly five exist: the **browser socket** (the web app's bidirectional stream, which asks within the turn per FR-002c); **REST** (single request/response, which ends the turn and resumes per FR-002c1/c2); the **platform stream** (the SSE endpoint a registered platform's client consumes, with its out-of-band decision POST — this is what the external `packages/filigran-chatbot` talks to, and the only place the word "chatbot" is used in this spec, per FR-002d); the **chat channels** (Slack, Teams, email and the other bot integrations, which cannot hold a turn open and so resume per FR-002c1/c2, subject to FR-008a); and the **public embed** (unauthenticated visitors, the one surface that gates and explains and is never given an approval channel, per FR-002b1). "Chat" alone is ambiguous across the first four and MUST NOT be used where a requirement applies to only some of them. All five are **conversational** — a person is present and a turn is open or resumable. An autonomous assignment run has no such surface, which is why it is answered through the Approval Inbox below rather than by a sixth entry here.
- **Approval Inbox**: Where a pause with no conversation behind it is answered — the run page, and the executions list (FR-026). It is not an Approval Surface: no turn is open, nothing is being said to an assistant, and the reviewer may have no connection to the run beyond owning it. It is a second door onto the same decision, which is why FR-029 requires it to reuse the one path rather than grow a parallel one.
- **Approval Group**: A reviewer's selection of several pending approvals answered in one action (FR-031). Transient by construction — it exists for the duration of the action and is never stored. It is a shortcut through the list, not a policy, and nothing about it survives to affect a later call; the durable form of "stop asking me" remains the standing exception of FR-015, with the disclosure FR-015c requires.
- **Run Interactivity**: Whether a run has a live human reviewer present (**interactive**) or is executing unattended on a schedule or trigger (**autonomous**). It does **not** affect whether standing exceptions apply — those apply to both — but it determines whether a pause triggers the owner notification (FR-015d). An indeterminate run is treated as autonomous, so notification is sent rather than skipped. The **trigger** decides this, not the identity the run carries: a scheduled per-user fan-out names its target user so it executes as them, and reading that alone would call an unattended run interactive — the one direction that leaves a stalled run silent.
- **Standing Approval Exception**: A user preference recording that one specific tool no longer pauses for approval **for that user, on any run carrying their identity — scheduled runs included**, created by them choosing "approve always" after being told that reach. It lasts until that user revokes it or a material change to the covered tool invalidates it. Carries the owning user, the tool, when it was granted, and enough of the tool's approved shape (its parameter schema) to detect a later material change. It is never shared between users.
- **Tool Call Log Entry**: An audit record created for every tool invocation, capturing which tool ran, its arguments, and its gate outcome — including whether it was auto-run under a standing exception.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: With the agent's approval gate on and no standing exception in place, 100% of calls to a tool with `requires_approval: true` pause for human review before executing, across all tested run scenarios — with no path that allows the agent's own judgment to bypass the pause.
- **SC-002**: A reviewer can see the full proposed action (tool, description, arguments) and record an approve/reject decision in a single interaction, without needing to inspect logs or backend state.
- **SC-003**: An administrator adding a tool to the whitelist always sees the warning in the same interaction as the change, before any save step.
- **SC-004**: A rejected tool call never crashes or silently stalls a run; the agent's next recorded action always reflects awareness of the rejection.
- **SC-005**: 100% of tool calls in a completed run — gated or not — are visible in the audit log together with their gate outcome.
- **SC-006**: Every standing approval exception a user has granted is discoverable and revocable by that user from their own preferences, with no exception reachable only through the runtime popup that created it — and no cross-user exception console exists for administrators.
- **SC-007**: On a fresh install, a newly created agent gates its `requires_approval: true` tool calls with zero configuration steps.
- **SC-008**: On a fresh install with the shipped default whitelist untouched, an agent completing a typical read-heavy run raises zero approval prompts for whitelisted read-only tool calls.
- **SC-009**: After an upgrade, zero agents gate — existing ones and ones created afterwards — and zero agent rows were written, until an administrator turns approval on; turning it on for one agent gates only that agent.
- **SC-010**: Every reviewer who grants "approve always" is shown, before confirming, that the preference also applies to scheduled runs — measured as zero grant paths that omit the disclosure.
- **SC-011**: Every autonomous run that pauses for approval produces a notification to the assignment owner — no unattended run waits on a human without someone being told.
- **SC-012**: After an upgrade that ships a revised default whitelist, 100% of an administrator's prior additions and removals remain in force, and newly shipped default entries are active without any administrator action.
- **SC-014**: An administrator can set approval on or off for any built-in agent using the product's own interfaces alone, and the value is still in force after a restart that re-synchronises built-in agents.
- **SC-015**: Every change to an agent's approval switch is attributable in the audit trail to the administrator who made it, and no path to turning one off omits the warning that states the change's reach — measured as zero undisclosed and zero unattributed changes.
- **SC-013**: For every registered platform, what the settings page says about its tools matches what the gate enforces — measured as zero combinations of platform policy and per-integration toggle that produce a screen claiming approval is required while those tools run unattended, or the reverse.
- **SC-016**: On every signed-in surface — browser socket, REST, and the chat channels — a user who triggers a gated tool can complete that request without leaving the surface they started on: 100% of gated calls end in an executed or rejected call rather than in an explanation that no decision could be collected. Measured per surface, not in aggregate; the anonymous public embed is excluded by FR-002b1 and MUST continue to explain rather than ask.
- **SC-017**: A decision submitted by anyone other than the user whose call is paused is refused on 100% of surfaces, and every refusal is attributable in the audit trail.
- **SC-018**: A reviewer answers a pending approval in under 15 seconds from noticing it, without loading another page.
- **SC-019**: The page a reviewer was on is still there, in the same state, after they answer an approval.
- **SC-020**: Median time between an autonomous run pausing and a human answering it falls by at least half against the run-page-only path.
- **SC-021**: A reviewer facing ten pending approvals for one tool resolves all ten in a single action, having been able to see each one's proposed arguments first.
- **SC-022**: Every decision made from the executions list produces an audit record identical in content to the equivalent decision made on the run page.
- **SC-023**: No decision is ever recorded against a proposal already answered, including with two surfaces open at once.
- **SC-024**: A reviewer can narrow the executions list to exactly what awaits their decision, and select that set in one action.

## Assumptions

- Approval gating is driven by whitelist membership, not by a tool's origin or an inferred classification. Curating the shipped default whitelist — deciding which of the existing tools are safe to exempt — is in scope for this feature; it is the same judgement that a classification map would have required, delivered as versioned data an administrator can override rather than as code.
- `code_interpreter` ships whitelisted, so agents run generated code without pausing by default. This is a deliberate usability decision, accepted on the basis that the sandbox bounds the blast radius and that a deployment wanting stricter behavior removes the entry, after which every call gates with the code shown to the reviewer. It is the single most consequential entry in the shipped default and should be revisited if the sandbox's isolation guarantees change.
- Gating is a behavioural change to the API contract, not only to this product's UI. One external consumer is known — the `filigran-ui` chatbot — and is being updated in parallel; no others are believed to exist.
- MCP tools are in scope for *gating* but out of scope for *configuration*: they gate by default because they are absent from the shipped whitelist, and are exempted individually by name if an operator chooses. Declaring approval inside an MCP manifest is explicitly out of scope for this feature, per the refinement decision on the source issue, and will be addressed in a separate effort.
- Integrations ship with a single per-integration approval toggle in this phase; true per-tool granularity for integration tools is deferred and will be validated first on one existing integration end-to-end before wider rollout.
- No new automatic timeout is introduced for pending approvals; the existing indefinite pause/resume ("awaiting human") state machine is reused as-is. An indefinitely paused autonomous run is treated as correct fail-closed behavior, made safe by notification (FR-015d) rather than by auto-resolution.
- Making unattended automation stop and wait is an accepted cost wherever approval is on. The mitigation is visibility (FR-015d), not a weaker gate; an operator who needs unattended execution over state-changing tools turns approval off for that agent.
- Gating has its own per-agent switch rather than reusing `human_in_the_loop`, whose prompt-driven meaning and default stay as they are. On built-in agents, which are otherwise read-only, this opens exactly `approve_tool_calls` to administrators (FR-012b).
- Approval is on by default for a fresh install and off for an upgraded one (FR-014, FR-014a): turning it on for a deployed fleet is an administrator's decision, never the upgrade's.
- Standing approval exceptions are personal preferences, not shared configuration. They express "I, this user, have seen this tool and trust it" rather than "this tool is trusted here", so they never transfer between users — but they do follow that user across all of their runs, including scheduled ones. That reach is what makes the disclosure at grant time (FR-015c) load-bearing rather than cosmetic: it is the only point at which the user learns that one click also affects unattended execution.
- Administrators are deliberately given no cross-user view of exceptions. Inspecting or revoking another user's preference goes through the platform's existing impersonation mechanism, consistent with how other per-user operations are handled, keeping a single audited path for acting on someone else's behalf rather than a parallel god-mode surface.
- A standing exception is treated as consent to a tool's approved shape, not to its name: it records enough of that shape to detect a later material change, so a tool cannot be rewritten under an exception granted against an earlier version. This applies the same fail-closed reasoning used elsewhere in the platform — when prior state is no longer understood, re-approve rather than proceed.
- The structured rejection surfaced to the agent uses the same error channel/shape the agent already receives for other tool-execution failures, distinguished by a reason indicating human rejection rather than an execution failure.

- **Answering from the executions list is scoped to assignment runs** (FR-026). That is the surface which pauses with nobody watching, so it is the one where the path to a decision is the cost. A chat approval is answered in the conversation that raised it and is unchanged.
- **"Approve always" is offered here too** (FR-037), on a single proposal and over a group (FR-032a). Both carry FR-015c's disclosure; the group form enumerates every tool it would un-gate, which is more than the single form says.
- **Notification delivery is unchanged.** FR-015d already decides who is told when an autonomous run pauses. FR-026–FR-037 change what a reviewer can do with that notification, not who receives one.
