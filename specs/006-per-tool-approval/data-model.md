# Phase 1 Data Model: Per-Tool Human-in-the-Loop Approval

Derived from the spec's Key Entities and Functional Requirements. Existing structures are referenced with `file:line`; new structures are marked **NEW**.

---

## 1. `ToolDefinition` — **unchanged**

`backend/app/tools/base.py:368-391` — frozen dataclass, ~2,486 construction sites.

**No fields are added.** Whether a tool requires approval is derived from HITL whitelist membership keyed on the tool's canonical name, not stored on the definition (research D4). This keeps one source of truth, avoids touching every construction site, and lets an administrator's whitelist edit take effect without rebuilding definitions.

The gate consumes three existing fields: `name` (canonical, post-alias-resolution), `description` and `input_schema` (both surfaced in the approval payload, FR-006).

## 2. HITL Whitelist — computed, two layers

Effective membership is never materialised:

```
effective = (shipped_default − admin_removals) ∪ admin_additions
```

### 2a. Shipped default — **NEW**, code not data

`backend/app/services/hitl_whitelist_default.py`

```python
SHIPPED_WHITELIST_VERSION = 1
SHIPPED_DEFAULT_WHITELIST: frozenset[str] = frozenset({...})   # canonical tool names
```

Product-owned, replaced wholesale by deploying new code (FR-001d). Because it is code, an upgrade needs no data migration and new entries take effect with no administrator action (FR-001f).

Populated with the ~57 built-in tools following read-only verb conventions, plus `code_interpreter` (see below). Deliberately **excludes** `browser`, `web_fetch`, `check_task_status`, `consult_agent` so they gate. MCP tools are absent entirely this phase (FR-022), as are third-party integration tools (FR-021); the read tools of a *registered Suite platform* are the one exception, and they are derived rather than listed here — §2a-bis.

`code_interpreter` is included by product decision despite executing arbitrary code — the highest-risk entry in the default, kept exempt for usability and removable by any deployment that disagrees (research D3).

`SHIPPED_WHITELIST_VERSION` is for display and support diagnostics only; no logic depends on it.

### 2a-bis. Derived platform reads — **NEW**, code not data

`backend/app/services/hitl_whitelist_platform.py`

```python
PLATFORM_PROVIDERS = frozenset({"opencti", "openaev", "opengrc"})
HAND_GATED: dict[str, str]                              # read, but gated on purpose, with reasons

@lru_cache(maxsize=1)
def platform_read_tools() -> dict[str, frozenset[str]]  # {provider: read-classified names}
def read_tools_for(providers: frozenset[str]) -> frozenset[str]
def provider_of(tool_key: str) -> str | None
```

The second product-owned half of the default (FR-001g). Membership is **computed from the tool's classification**, not listed: a platform tool is exempt when `_infer_tool_type` (`app/api/v1/integration_catalog.py`) calls it `read`. That classifier is token-based and fails safe to `write`, so an unrecognised verb gates.

Provider builders are invoked with the catalog's dummy credential purely to harvest `ToolDefinition` metadata, so this is a pure function of the release and is cached once per process. A provider whose builder raises contributes **nothing** rather than a partial list — half a tool set would silently re-gate the other half.

Current shape: **111 exempt** of 256 platform tools (opencti 19, openaev 30, opengrc 62). All 54 consolidated `manage_…` tools classify `write` and stay gated, which is the point: their `action` enum mixes `list`/`get` with `create`/`update`/`delete`, so no name-keyed exemption can be right about them.

`HAND_GATED` is the human override for reads still worth a person's attention. It holds exactly one entry, `download_opencti_file`. Four OpenGRC identity/RBAC reads were there and were dropped: gating the RBAC *overview* while `list_opengrc_users` (with emails), `get_opengrc_user`, `get_opengrc_group` and `get_opengrc_role` stayed exempt bought no protection and only made behaviour inconsistent. A read is a read; a deployment that wants identity gated re-gates those tools on the whitelist screen.

**Scoped by registration.** `read_tools_for` is fed the providers a live registration speaks for (`platform_approval_by_provider`, excluding `unregistered`), including OpenAEV's legacy `openbas` alias. A platform nobody has connected exempts nothing — the entry would be inert anyway, but 58 OpenGRC names on a deployment that has never heard of OpenGRC would make the one screen answering "what runs without asking?" unreadable.

**Reviewability.** Deriving gives up the property that makes 2a safe to review as data, so `backend/tests/data/hitl_platform_read_whitelist.txt` holds the effective set, regenerated by `python -m scripts.dump_platform_read_whitelist` and pinned by a golden test. Every widening therefore appears as a diff line naming the tool that will run unattended.

### 2b. Administrator overlay — **NEW** table

`backend/app/models/tool_approval.py`, table `hitl_whitelist_overrides`

| Column | Type | Constraints | Purpose |
|---|---|---|---|
| `id` | `UUID` | PK | |
| `tool_key` | `String(255)` | **UNIQUE**, NOT NULL | Canonical tool name as resolved by `CompositeToolExecutor`, so aliases collapse to one key. |
| `action` | `String(10)` | NOT NULL, `add` \| `remove` | Whether the administrator exempted or re-gated the tool. |
| `created_by_id` | `UUID` | FK `users.id` ON DELETE SET NULL | Who made the change. |
| `created_at` | `DateTime(tz)` | NOT NULL | |
| `reason` | `Text` | nullable | Optional operator note, surfaced in the admin list. |

**`UNIQUE (tool_key)`** means one override per tool: adding a tool that is currently overridden to `remove` flips the row rather than inserting a second. Concurrent admin edits converge via a real `ON CONFLICT DO UPDATE` on `tool_key`, satisfying Principle II without a lock — select-then-insert does **not** satisfy it, since two callers both read no row and both insert.

**Why an overlay rather than a materialised list**: FR-001e requires a removal to survive an upgrade that re-adds the tool to the shipped default. Subtracting removals *after* applying the default makes that a property of the data shape rather than merge logic that could be got wrong.

**Resolution** (`backend/app/services/hitl_whitelist.py`):

```python
async def platform_read_default(db) -> frozenset[str]   # §2a-bis, scoped to registrations
async def default_membership(db) -> frozenset[str]      # shipped_default | platform_reads

async def resolve_whitelist(db) -> frozenset[str]:
    """Effective membership. Resolved ONCE per run and cached for its lifetime."""
    default = await default_membership(db)
    return frozenset((default - removals) | additions)
```

The subtraction is applied to the **whole** default, both halves, which is what makes FR-001e hold for a derived read: re-gating one survives a release that goes on classifying it as a read, and survives the platform reconnecting.

Membership is on the hot path for every tool call, so the result is resolved once per run into an in-memory set — O(1) per call, two queries per run (the overlay and the registrations). The failure modes are deliberately different, and there are three of them. An unreadable **overlay** MUST propagate as "gate everything", never as an empty-but-successful set (Principle I). Unreadable **registrations** raise `PlatformReadsUnavailableError`, which `resolve_whitelist` converts to "exempt nothing" — the curated default is still trustworthy, so the gate's answer is "everything we ship, nothing we inferred". But that conversion MUST NOT reach a caller answering "is this tool exempt?" for an administrator: the administration endpoints refuse with 503 instead, because a write recorded against membership nobody could read is not a decision. Absorbing it everywhere made `DELETE` report success having written nothing.

## 3. `ToolApprovalPreference` — **NEW**

`backend/app/models/tool_approval.py`, table `tool_approval_preferences`. The Standing Approval Exception entity (FR-015, FR-019).

| Column | Type | Constraints | Purpose |
|---|---|---|---|
| `id` | `UUID` | PK | |
| `user_id` | `UUID` | FK `users.id` ON DELETE CASCADE, NOT NULL, indexed | Owning user. Cascade implements the user-deletion edge case. |
| `tool_key` | `String(255)` | NOT NULL | Canonical tool name, same key space as the overlay. |
| `tool_source` | `String(100)` | NOT NULL | `ToolDefinition.source` at grant time, for display and audit. |
| `schema_fingerprint` | `String(64)` | NOT NULL | Hash over `input_schema` only. FR-019a. |
| `granted_at` | `DateTime(tz)` | NOT NULL | |
| `granted_by_admin_id` | `UUID \| None` | FK `users.id` ON DELETE SET NULL | Impersonating admin, if any. FR-017b. |
| `revoked_at` | `DateTime(tz) \| None` | NULL = active | Soft-delete so audit history survives revocation. |
| `revoked_reason` | `String(30) \| None` | `user_revoked` \| `tool_changed` | Distinguishes FR-017 from FR-019a invalidation. |

**Constraints**: partial unique index `UNIQUE (user_id, tool_key) WHERE revoked_at IS NULL`; index on `(user_id, revoked_at)` for the self-service listing.

**Scope invariant (FR-019)**: keyed `(user_id, tool_key)` — deliberately excluding assignment and agent. The exception follows the user across all their runs, interactive and scheduled alike (FR-015b), but never crosses to another user.

**Lifecycle**:
```
(none) ──"approve always"──▶ active ──user revokes──▶ revoked(user_revoked)
                               │
                               └──input_schema changes──▶ revoked(tool_changed)   [FR-019a]
```

A tool being whitelisted does **not** invalidate exceptions covering it — the exception simply stops mattering, since a whitelisted tool never gates for anyone.

## 5a. `PlatformSettings` / `User` (modified) — **NEW**

The two wholesale switches. They sit *above* every input in §6 and answer "does anything pause at all", so they are
deliberately not gate inputs: they select whether the gate of §6 is installed in the first place.

| Model | Field | Change |
|---|---|---|
| `PlatformSettings` (`models/platform_settings.py`) | **`tool_approvals_enabled`** | **NEW** `bool`, default `True` — administrator kill switch (FR-023). Read defensively: a missing settings row means the default, and an unreadable one gates normally. |
| `PlatformSettings` (`models/platform_settings.py`) | **`approve_tool_calls_default`** | **NEW** `bool`, column default `True` — the install default (FR-014). Migration `j1atc0173` adds it `FALSE` on an existing row, so an upgraded install starts off (FR-014a); a fresh install creates it `TRUE`. Unreadable → gate. |
| `User` (`models/user.py`) | **`approve_all_tools`** | **NEW** `bool`, default `False` — per-user allow-all (FR-024). |

Neither column deletes anything. `ToolApprovalPreference` rows (§3) survive both switches untouched, which is what makes
turning either one back off restore the exact previous posture rather than an empty one.

The column is named `tool_approvals_enabled` rather than `hitl_enabled`, because it governs the tool
approval gate only — the agent's own request for human input is not suppressed by it (FR-023), and `hitl_enabled` would
have claimed otherwise.

## 6. Gate decision inputs and table

Pure function in `backend/app/tools/approval.py`. All inputs resolved once per run and cached.

Preceded by one resolution step (FR-025): a single shared point reads the two switches of §5a, and on a hit installs a
**recording-only** gate instead of no gate — every call still gets a truthful outcome (FR-020) while nothing pauses.
The two outcomes are named apart because they name different responsible parties: `auto_run_approvals_disabled`
(administrator policy) and `auto_run_user_allows_all` (the user's own choice).

| Input | Source |
|---|---|
| `hitl_enabled` | `resolve_approve_tool_calls(db, agent)` — `hitl_whitelist.py`: the agent's `approve_tool_calls`, else the install default (FR-012, FR-014) |
| `whitelist` | `resolve_whitelist(db)` — §2, resolved once per run; includes the derived platform reads of §2a-bis |
| `active_exceptions` | `{tool_key: schema_fingerprint}` for `run.user_id`, one query per run |
| `current_fingerprint` | computed from the live `ToolDefinition` |

**Decision table** — order matters; each row maps to a requirement:

| # | Condition | Outcome | Log outcome (FR-020) | Req |
|---|---|---|---|---|
| 1 | `hitl_enabled` is false | execute | `auto_run_hitl_off` (agent's own switch) or `auto_run_install_default_off` (install default) | FR-013, FR-014b |
| 2 | `tool_key` in whitelist — curated, derived platform read, or admin-added | execute | `auto_run_whitelisted` | FR-001, FR-001g, FR-013 |
| 3 | active exception, fingerprint matches | execute | `auto_run_standing_exception` | FR-016, FR-015b |
| 4 | active exception, fingerprint differs | **pause** + revoke as `tool_changed` | — | FR-019a |
| 5 | otherwise | **pause** | — | FR-002 |

Interactivity is deliberately **absent**: a standing exception applies to interactive and autonomous runs alike (FR-015b). Interactivity only decides whether a pause notifies the owner (FR-015d, FR-015f).

Any failure to evaluate rows 2–4 — whitelist unresolvable, exception lookup failing — falls through to **pause**, per Principle I. `evaluate_gate` is contractually total and must never raise.

## 7. Action Proposal (transport object)

The structured payload for FR-006/FR-007. Lives in `pending_approvals`, the `action_proposal` SSE event, and the GET response.

It is also what makes a resumed turn possible without storing loop state: a proposal carries the call id, the tool name and the exact arguments the reviewer saw, so a surface that ended the turn can rebuild the call rather than asking the model to propose it again (FR-002c2). A proposal that has been retired because the conversation moved on (FR-002c4) is returned as `expired_approvals` on its message instead, and is no longer answerable.

**Surface names in this document follow the `Approval Surface` entity in [spec.md](./spec.md)** — browser socket, REST, platform stream, chat channels, public embed. "Chat" alone spans the first four and should not be used where a statement is true of only some of them; "chatbot" refers to the external `filigran-chatbot` package and nothing else.

| Field | Type | Notes |
|---|---|---|
| `tool_call_id` | `str` | LLM-assigned id. **The only correct match key** on resume — never the tool name (research D5). |
| `tool_name` | `str` | Canonical, post-alias-normalisation. |
| `tool_description` | `str` | FR-006. |
| `arguments` | `object` | Full proposed arguments; survives the pause via `serialize_messages` (`prompting.py:352-370`). |
| `input_schema` | `object` | Lets the UI render a typed form **and** show each argument's declared description (FR-006). |
| `source` | `str` | `ToolDefinition.source`. |

| Field | Type | Notes |

## 10. Answering from the executions list — **no new state** (FR-026–FR-037b)

Recorded as a section rather than omitted, because "we checked and nothing is stored" is a design
decision a later reader will otherwise re-litigate.

| Concept | Where it lives | Why not a table |
|---|---|---|
| Pending proposals | `AssignmentRun.pending_approvals` (§4), already returned by the run listing | The executions list reads a payload it already receives; a second store would be a cache that can disagree with the run. |
| **Approval Group** | Nowhere — it is the request body of one batch call | It is a selection, not a policy. Nothing about it may survive to affect a later call, and a stored group is exactly how it would. |
| Whether each proposal was disclosed (FR-034) | Nothing — the list renders them expanded | Satisfied by construction. A stored flag would claim the reviewer *read* it, which no storage knows, and would put an unenforceable field in the server contract. |
| "Approve always" granted here (FR-037) | `ToolApprovalPreference` (§3), unchanged | It is the same act as on the run page (FR-037b), so it must be the same row — a second shape would fork FR-019a's invalidation. |

The only schema-adjacent obligation is on the **response** side: the not-awaiting refusal must
distinguish already-answered from cancelled from failed ([contracts/executions-approvals.md §3](./contracts/executions-approvals.md)),
which reads existing run state and stores nothing.

## Entity relationships

```
SHIPPED_DEFAULT_WHITELIST (code, versioned)
        │  minus removals, plus additions
HitlWhitelistOverride ─┘
        └──▶ effective whitelist (computed per run) ──▶ gate decision

User 1──────* ToolApprovalPreference
 │                    │ tool_key (soft ref — tools span 4 sources, no single table)
 │                    │ schema_fingerprint ──▶ compared against live ToolDefinition
 │
 └─1──* Agent 1──* Assignment 1──* AssignmentRun
                                        │ user_id ──▶ approver identity + exception owner
                                        │ triggered_by_user_id ──▶ interactivity (notification only)
                                        ├─ pending_approvals   : [Action Proposal]
                                        └─ approval_decisions  : {tool_call_id: Decision}
```

`tool_key` intentionally has **no foreign key** in either table: tools come from four sources (built-in constants, `custom_tools` rows, integration provider modules, MCP servers) with no single table to reference. The fingerprint protects against stale consent; referential integrity is not available and not required.
