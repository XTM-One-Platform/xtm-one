# Working in the sandbox workspace

The code interpreter (`code_interpreter`) runs Python for your agents. Every conversation, and every assignment run, has a **sandbox workspace**: a directory that keeps its files from one code interpreter call to the next, across the turns of the conversation, and across a turn that was interrupted and resumed. An agent can download a repository once, then lint it, fix it and test it over as many calls as it needs, instead of rebuilding everything in one giant call.

!!! note "The code interpreter is off by default"
    In XTM One, the code interpreter is switched off by default: agents get neither the code interpreter nor the workspace tools this page describes. An administrator turns it on by switching off `Disable the code interpreter` in `Settings > Security`, or with its environment variable (see [Settings > Security options](../deployment/configuration.md#settings-security-options)). The workspace itself has its own settings (see [Code interpreter sandbox workspace](../deployment/configuration.md#code-interpreter-sandbox-workspace)).

## What persists and what does not

| | Kept between calls | Notes |
|---|---|---|
| Files under `workspace/` | Yes | The directory is `workspace/` in the code's working directory; its absolute path is in the `WORKSPACE_DIR` environment variable. |
| Packages installed into `workspace/.venv` | Yes | See [Packages](#packages). |
| Variables and imports, `session=false` (the default) | No | Every call runs in a fresh, isolated process, as before. |
| Variables and imports, `session=true` | Yes, while the kernel lives | See [Keeping variables](#keeping-variables-sessiontrue). |
| Files written elsewhere in the working directory | No | Kept as downloadable files of the conversation, as before. |
| `attachments/` | No | The conversation's files, copied in for the call, as before. |

The process stays isolated on every call: the workspace adds files, not privileges. The sandbox has no network access and holds no credential; the workspace only ever contains the files of its own conversation.

Each conversation and each assignment run has its own workspace; the next run of the same work item by the same agent takes over the workspace the previous run left. A background copy, a consulted agent or a run of another item starts with its own, empty one. To hand a file to it, pass it as a conversation file (`sandbox_get_file`, then its file_id), as a work item attachment, or inline in the task text, never as a `workspace/` path. A read of a path only another of your workspaces holds is refused with that workspace named (a conversation or a run) and these hand-overs; a path none holds keeps the plain "is not in the workspace" answer.

Every code interpreter result starts with one line saying how the call ran: a fresh process or the kernel, whether the workspace was mounted, what was read and written, and which files were added, changed or removed. A fresh-process call whose code names only fixed paths under `workspace/` (`open('workspace/data/a.csv')`, `glob.glob('workspace/data/*.csv')`) gets those paths and the installed packages, not the whole workspace, so reading one file of a large checkout stays fast; the line then says how many of the workspace's files were mounted. Code that lists the workspace or builds a path under it gets all of it. The tool description the agent reads lists what the workspace holds (the most recent files first, the rest counted).

## Putting content in without passing it through the conversation

Reading a 20-file repository through a chat model costs every file twice: once when the tool returns it, once when the agent pastes it into code. Content can go straight to the workspace instead:

- **`to_workspace_path`**: the tools that return a file or text from outside (`read_file_content`, `web_fetch`, the GitHub file tools, the integration download tools and the read operations of OpenAPI and custom integrations) accept it. The content is written to the workspace on the server, and the agent gets back the path, the size and the sha256 instead of the content. A PDF or Office document (PDF, DOCX, PPTX, XLSX, XLS) also lands as its text, extracted on the server: the file at the path and its text at `<path>.txt`, or the text alone when the path ends in `.txt`, so a fetched report can be searched in code although the sandbox has no PDF library. A document with no text layer (a scan) is written raw and the answer says so. A tool result too long for the conversation keeps its start and its end, with a note saying how much was left out between them, so a log's final error lines are never lost.
- **`sandbox_put_file`**: copies a file of the conversation (an upload, a download, a generated file) into the workspace.
- **`materialize_repository`**: checks a repository out into the workspace through a connected integration (GitHub today), on the server, with that integration's credential and repository scope. Choose a branch, tag or commit and, optionally, sub-paths. A sub-path inside the directory one of the repository's declared checks runs from (its `.xtm-one/checks.toml`) is widened to that directory, since the check imports what lies there, and the answer says so; a check declared without a directory runs from the repository root and widens nothing, so the sub-paths stay as given. With sub-paths, the few files the repository's checks are read from are kept too, outside them: the manifests, lock files and tool configuration of the directories above each sub-path, `.github/workflows` and `.xtm-one/checks.toml`, so `sandbox_run_command` lists the checks of a narrow checkout, plus every repository file a declared check's command names (a check that runs `python ../.xtm-one/stores.py` from `backend/` keeps `.xtm-one/stores.py`), so the check also runs there. A sub-path inside a JavaScript workspaces root (a `package.json` with `workspaces`, or a `pnpm-workspace.yaml`) also keeps the `package.json` of every other workspace member, so a frozen-lockfile install (`yarn install --immutable`, `npm ci`) of the narrow checkout resolves. When the root's install lifecycle script (`prepare`, `postinstall` and their pre and post scripts) builds another member (`cd packages/core && tsup`), that member is checked out too and the answer says so; a root file the script copies (`../../llms.txt`) is kept beside it, so the install passes without an `add_paths` call. The tree is written, never a git clone: no `.git` directory and no credential reach the workspace. Running it again replaces what it checked out before. To grow a narrow checkout by more paths without losing its edits, pass `add_paths` with the same `path` (and no `sub_paths` or `ref`): the paths are written at the commit the checkout records, nothing is removed, a file you edited is kept (the answer names it), a file an earlier checkout at the same path left there and nobody touched since is replaced by its version at that commit (so it is never committed back as a change), and status, diff, rebase and `from_checkout` cover the new files.
- **`sandbox_get_file`**: the other way, a workspace file becomes a conversation file the agent can hand to you or to another tool.
- **`sandbox_list_files`** and **`sandbox_remove_files`** list and clean it. A large tree is narrowed with `depth` (1: a directory's direct files) and `glob` (`*.test.ts`, or `sub/*.ts` from the listed directory), applied before the listing's limit.

## Reading and changing files without echoing them

A source file of 300 KB printed from the code interpreter costs more than the whole task. Five tools read, change and create a workspace file on the server and return only what the agent asked for:

- **`sandbox_outline`**: the definitions of a file with their line numbers (classes, functions and methods for Python; declaration lines for TypeScript, JavaScript, Go, Rust, Java, Kotlin, SQL, a `const Row = ({` arrow component whose parameter list spans several lines included; the types, inputs, enums, unions, interfaces, scalars and directives of a GraphQL schema file (`.graphql`, `.gql`), so `sandbox_read_symbol` reads one input of a large schema, such as the fields of `ReportAddInput` at a tag, without the server's introspection; headings for Markdown). The place to start: it says where to look.
- **`sandbox_read_file`**: a window of a text file with line numbers (`offset_line`, `max_lines`), the total line count and the next offset when more remains. A line longer than 400 characters is cut with the rest counted; `max_line_chars` (at most 20,000) reads a long line, such as a table row or a minified file, whole. A binary file is named as such, not shown.
- **`sandbox_grep`**: a regular expression over the text files of the workspace, or of a directory of it (`path_prefix`, `include_globs`): `path:line: text` hits, bounded by `max_matches` with the rest counted, optional context lines, `max_line_chars` as for `sandbox_read_file`. Installed packages and checkout records are skipped unless the prefix names them. An installed tree the workspace never records (`node_modules`, `.venv`, `site-packages`, written by an install check of `sandbox_run_command`) is searched in the workspace's live command container when the prefix names it (a directory or one file of it), and `sandbox_read_file`, `sandbox_outline` and `sandbox_read_symbol` read a file there the same way, their answer ending with the line `[read from the live command container: installed files, never recorded in the workspace]`: read-only, nothing enters the workspace, so `sandbox_checkout_status` and a commit are unchanged; with no live container (none started, or every one ended), the answer is a normal result, not an error, naming the exact call to run first (`sandbox_run_command(checkout="...", check="...-install")`, the install check of the directory holding the tree, else of the nearest enclosing one), then the same read again. Images, fonts, archives and media are skipped without being read. A text file up to 32 MB is searched, so a CI job log saved in the workspace can be searched. One call reads up to 4,000 files or 128 MB; past that, the answer says how many files were not searched and in which directories, so the next call can narrow `path_prefix` or `include_globs`. The matches shown hold at most 12,000 characters by default (`max_chars`, up to 60,000, lifts it; the matches cut are counted). On a log of JSON lines, `json_fields` (for example `["timestamp", "level", "message"]`, or `compact_json: true` for those three) shows only those keys of each matched line, joined by ` | `, an absent key written `-`, a dotted key such as `attributes.queue` read inside a nested object; a line that is not JSON is shown whole. To compare logs, `group_by` (a key, dotted when nested) replaces the lines by one row per value of that key, with, for each file side by side, the count of matched lines and the first and last of them (line number and time; the time is read from `time_field`, `timestamp` by default, else from the runner's prefix of the line). Save a red job log and a green one in one directory and one call answers, for example, which queues received a message in each job and when.
- **`sandbox_read_symbol`**: one definition of a file whole, by name (`Class`, `Class.method`, `function`, `outer.inner` for a nested function), with its decorators and line numbers, in one call. The name stays valid after the conversation's older tool results are pruned, so the same call reads it again. When several definitions share the name they are listed with their lines (pass the qualified name or `occurrence`).
- **`sandbox_playwright_trace`**: a Playwright `trace.zip` of the workspace (an E2E artifact downloaded from CI) read in one bounded answer: the failure with its locator and spec line, the test attachments (JSON ones inlined), then around the failing action the actions with their call logs, the page URL changes, console errors and the requests (status, method, path, duration), with what falls outside the window counted. `around` moves the window to a call id or a time, `window_ms` widens it, `frame_at` writes the nearest screencast frame next to the zip as an image you can open.
- **`sandbox_edit_file`**: exact find/replace edits on a file, applied in order: every `find` must exist and be unique (or `replace_all`), and nothing is written unless every edit applies. The result is the unified diff; on a line longer than 400 characters (a table row, minified JSON) it shows only the part that changed, with some context and the unchanged characters counted. A file with Windows (CRLF) line endings is matched as it reads, with plain line breaks in `find`, and keeps its CRLF endings when written. To replace or delete a long block (a whole function, an obsolete test) without copying it into `find`, an edit can name lines instead: `{start_line, end_line, expect_first, expect_last, replace}`, with the line numbers `sandbox_read_file` shows. `expect_first` and `expect_last` are a part of the text of the first and the last line of the range (`expect_last` is needed for a range of several lines); when the file has changed and the numbers no longer fit, the call is refused and nothing is written. An empty `replace` deletes the lines. When the first or the last line of the range is blank, `expect_first_blank: true` or `expect_last_blank: true` stands for its text. To add lines without replacing any, an edit can name `{insert_after_line, expect_first, replace}`: the text goes after that line (0 puts it at the top of the file, with no `expect_first`). Line numbers count the file as the earlier edits of the same call left it. When a `find` occurs several times (three identical blocks), `occurrence: 2` replaces the second one only, counted the same way, instead of widening the snippet. It is the workspace sibling of `edit_file_content`, which does the same on a conversation file.
- **`sandbox_json_keys`**: adds, changes, renames, removes or reads keys of JSON object files, such as the translation catalogs, in one call: `set` maps a file (or `"*"` for every file named) to the keys and values to set, `place` puts a key that `set` adds right after or before another key (`{"New key": {"after": "Existing key"}}`) instead of last, `rename` maps an old key to a new one (set the new key in the same call to change its value in each file, in place), `remove` lists keys to drop and `get` lists keys to read. Each file keeps its own layout; a file that holds a duplicate key, is not an object or mixes its indentation is refused, and nothing is written for any file. In a French catalog (`fr.json`, `fr-FR.json`), a value set with a plain space before `?`, `!`, `;` or `:` is named in a warning; `french_spacing: "fix"` writes the no-break space French typography takes there instead (narrow before `?`, `!`, `;`, regular before `:`). The same call edits a TypeScript or JavaScript catalog (a `.ts` or `.js` file holding one object literal such as `export const fr = { 'Save': 'Enregistrer', ... };`, one entry per line): only the lines of the keys named change, new entries follow the file's quotes, indent and commas, and the values set there are text. It also edits a gettext catalog (a `.po` file such as `locales/fr/messages.po`), keyed by the `msgid`: a set changes the `msgstr` of an entry or adds one, a rename changes the `msgid`, and the comments, references and every other entry keep their bytes; a plural entry is read, not set, and `locales/fr/messages.po` gets the French spacing check.
- **`sandbox_replace_in_files`**: one regular-expression replace across many files, for a rename, a moved import or an option renamed in many call sites. Give the `pattern`, the `replacement` (a Python `re` template, `\1` for a group, where `\u00a0`, `\U0001F600` or `\x41` is written as its character) and the files to change with `path_prefix` and/or `include_globs`. Every changed file is written in one step, or none: past `max_replacements` (200 by default) nothing is written. The answer lists each file with its count of replacements and lines changed, then the diffs; `dry_run=true` shows the same report without writing. Every text file up to 32 MB is searched, as with `sandbox_grep`; a file left out is named with the reason, and a pattern that matches but whose replacement changes nothing is reported as such.
- **`sandbox_codemod`**: a change across many files that one regular expression cannot express, because each site needs its context (the element around it, an import list to edit, a ternary to rewrite). Write a transform module in the workspace whose default export takes `{ path, source, parse }` and returns the new text (or `null` to leave the file as it is); `parse` gives the file's syntax tree. Then give the `checkout`, the `transform` path and the files with `path_prefix` and/or `include_globs`. The module runs in the checkout's own codemod check (`frontend-codemod` in XTM One), and every changed file is written in one step, or none: if the transform fails on a file or a changed file no longer parses, nothing is written and each file is named with its error. `dry_run=true` shows the per-file report and the diffs without writing. Available where `sandbox_run_command` is.
- **`sandbox_apply_patch`**: apply a unified diff to a checkout, for re-landing a pull request on a fresh branch or porting a change to another base. Save the diff in the workspace first (for example `get_github_pr_diff` with `to_workspace_path`), then give its `patch` path and the `checkout` directory. Every hunk must match the checkout exactly (it may sit a few lines away from where the diff says, which the answer reports); one hunk that does not match refuses the whole call with its file and line, and nothing is written. `exclude` leaves files out, `dry_run=true` checks without writing.
- **`sandbox_move_files`**: move or rename files and whole directories, for a renamed module or a moved package. Give `moves` as a list of `{from, to}` workspace paths; every move is written in one step and the content is kept as is. Nothing is written when a source is missing, a destination is inside its source, two moves land on one path, or a destination exists (`overwrite=true` replaces an existing file). With `copy=true` the sources stay where they are and the destinations get the same content, so a file is duplicated (for example a lab-only page copied into the source tree to type-check it) without reading it or rewriting it in `code_interpreter`. An edit's answer shows at most 40 lines of a long insertion: the first 30 and the last 5, with the line range of the rest, which `sandbox_read_file` reads.
- **`sandbox_diff_files`**: compares versions of a file held side by side in the workspace. `sandbox_diff_files(path, other)` is the unified diff of `path` to `other`. With `base` (the common ancestor) it is the three-way merge of `path` (ours) and `other` (theirs): the number of conflicts, the line where each one starts in the merged text, and the merged text's diff against `path`. Overlapping changes are written between `<<<<<<<` / `=======` / `>>>>>>>` markers labelled with the file names. `write_merge_to` stores the merged file, ready for `sandbox_edit_file` and then `merge_github_branch` resolutions (`workspace_path`). Only workspace files are read, nothing goes through an integration.
- **`sandbox_write_file`**: creates a text file (UTF-8) with the content given, its missing directories created (`create_dirs`, default true). An existing path is refused unless `overwrite` is true, so a file is never replaced by mistake; a path outside the workspace is refused. The result is the path, the size and the sha256. The file is stored before the answer, so a `sandbox_run_command` or `code_interpreter` call made next finds it. Use it, not a code interpreter script, to add a source file, a test or a document.

The GitHub tools follow the same rule: `get_github_file` reads a window (`offset`, `max_chars`) and says how much remains; `get_github_pr_diff` and `get_github_job_logs` accept `to_workspace_path`, so a large diff or a whole CI log lands in the workspace uncut instead of being truncated in the conversation; `download_github_workflow_artifact` takes an artifact listed by `list_github_artifacts` (a test report, a Playwright trace), up to 100 MB, and with `to_workspace_path` unzips it into that directory with its tree kept (`unzip=false` writes the zip itself; an expired artifact is refused); `get_github_job_logs` answers the failure blocks of a red job first (the runner's errors, the test runner's failure sections, linter and compiler findings, under the step that produced them; every finding line of eslint, oxlint, tsc, ruff, mypy, pytest, vitest or jest, with its file, line and rule, is listed right after the test runner's own report and ahead of every other block, at most 150 with the rest counted, and a rule timing table is the first thing left out when the answer runs out of room), then the log's last lines (a failure section too long for the summary is shown clipped to its first lines, never left out); `failures_only=true` drops the last lines, `tail=true` returns the raw last 40,000 characters; a failed Playwright test whose log names its `error-context.md` gets the page it saw appended (the text of its page snapshot, read from the run's `test-results` artifact, the navigation and header left out), and when that artifact cannot be read the answer names the file and the download to make; the command and environment the runner echoes at the start of each step are never taken for a failure, and a step that dies without any error line (an upload cut) is answered with the last lines of the step where the job stopped, encoded dumps left out; a job that completed but whose log GitHub never published (a runner that lost communication with the server) answers its steps and its check-run annotations instead of a storage error. `get_github_pr` answers a pull request's state (head SHA, mergeable state, the checks summary of the head, the unresolved review thread count) with the first 1,500 characters of its body and one line per review, and `get_github_issue` the first 1,500 characters of the body and one line per recent comment; `include_body=true` reads the body by window (`offset`, `max_chars`) and the reviews or comments whole.

To poll a pull request's CI, `get_github_ci_status(repo, pr_number=N)` answers the counts and details only what did not pass. It also reads the checks the base branch requires (every ruleset and classic protection) and adds a `Required by <base>: N of M passed` line naming the failing, pending and never-reported required checks; a failed or pending required check is tagged `(required)`. A required check that no workflow ever reported blocks the merge as surely as a red one.

To find your own pull requests in a busy repository, `list_github_prs(repo, author="login")` returns only the pull requests that login opened, and `head_prefix="fix/"` only those whose branch starts with that prefix; both read up to the 300 most recent pull requests and say so when older ones were not read. `include_preview=false` answers one line per pull request, without the body previews.

To sweep many pull requests at once, `list_github_pr_states(repo, numbers=[...])` reads up to 30 of one repository in one call and answers one line each: state, draft, head SHA, merge state (clean, dirty, blocked, unstable, behind), the checks verdict on the head with its passed / failed / pending / skipped counts (the latest run of each check, so a check that failed and passed on a re-run reads as passed, exactly as `get_github_ci_status` counts it), the unresolved review threads and the review decision. Right after a push to the base branch GitHub takes a few seconds to recompute mergeability: the tool reads those pull requests again for up to about 15 s (less when GitHub settles sooner) and answers `merge unknown (GitHub still computing ...)` only when GitHub has still not finished. Use it instead of a hand-written GraphQL query or one `get_github_pr` per pull request; `get_github_ci_status` then names the checks of the one that needs attention.

To know whether a push to a base left any open pull request behind, `list_github_prs_needing_update(repo, base, author)` lists the open pull requests whose merge state is behind or dirty, or that conflict (one GitHub is still computing counts too), or whose head commit, older than 30 minutes, never reported a status check the base branch requires (reason `missing_required_contexts`, with the `missing` names: a required check added to the base after the push, which GitHub shows as blocked, never behind, when the base does not require branches to be up to date), filtered by base branch and author (`@me` is the integration's account). Its result is structured, so an assignment listening to pushes can use it as its `activation_check` with the condition `non_empty`: a push that leaves nothing to update starts no run and spends no token. Add `exclude_drafts: true` and `exclude_head_prefix` (for example `feat/innovation-`) to leave out the pull requests the assignment never acts on, so a draft parked with conflicts does not wake it on every push.

To find past CI runs, `list_github_workflow_runs(repo, workflow="e2e.yml", status="failure", created=">=2026-11-03T00:00:00Z")` lists the failed runs of one workflow since a time in one call, newest first. `workflow` takes the file name or the numeric id; `branch`, `event` and `head_sha` narrow it further and `created` also takes a range (`2026-11-01..2026-11-03`). Each row carries the run_id, the event, the branch, the short head SHA and the creation time (UTC); `count` reads up to 100 runs per page and the answer ends with `More remain: call again with page=N.` while runs remain.

To read the jobs of a run, `list_github_workflow_jobs(repo, run_id)` lists the latest attempt (job ids and failed steps). GitHub replaces a run's jobs with the re-run's the moment an automatic retry starts, so while the latest attempt is still running the answer adds one line naming the failed jobs of the attempt before it, with their job ids; `attempt=N` lists one attempt whole (`attempt=1` reads a failed first attempt while its retry runs).

A checkout has no `.git` directory, so two tools answer the questions an engineer asks before a commit:

- **`sandbox_checkout_status`**: the `git status` of a checkout: one `M` (modified), `A` (added) or `D` (removed) line per file changed since `materialize_repository` wrote it, with the repository, ref and commit it came from, or "clean". It is the same set of files `create_github_commit(from_checkout=...)` commits; `paths` narrows it. An untracked file the checkout's `.gitignore` files exclude (root and nested, read as git reads them: `!` re-includes, a trailing `/` is a directory, `**` crosses directories) is never a change: a build's output such as `frontend/dist/` or `*.tsbuildinfo` leaves the checkout clean, counted in one line ("N ignored file(s) not listed"), and `from_checkout` never commits it. A tracked file stays a change whatever `.gitignore` says. A narrow checkout keeps the `.gitignore` files above its `sub_paths` for this. A nested checkout (another repository checked out under this one, its directory holding its own `.xtm-checkout`) is skipped whole: none of its files is a change, untracked or committed by `from_checkout`, and the status names it once ("N nested checkout(s) excluded whole"); read or commit it through its own checkout path.
- **`sandbox_checkout_diff`**: the `git diff` of a checkout: a unified diff of each changed file against the file as checked out, read through the connected integration at the recorded commit and checked against the hash in the record (a file that no longer matches is named, not diffed). Added files are shown from `/dev/null`, removed files to `/dev/null`, binaries are named. The answer is bounded (40 files, 60,000 characters) and names what it left out; `paths` and `context_lines` narrow it.
- **`sandbox_checkout_rebase`**: the `git rebase` of a checkout: `sandbox_checkout_rebase(checkout, ref)` brings it onto a new ref (main moved, a pull request conflicts) without losing its edits. The tree at `ref` is read with the same `sub_paths`, and the merge starts from the merge base of the checkout's commit and `ref`, as `git rebase` does, so a checkout of a feature branch keeps every file the branch adds (listed as "Your added files kept") and every change it made that the ref did not; a file you did not change takes the ref's version (or is removed when the ref removed it), a file only you changed stays yours, and a text file changed on both sides is merged line by line. Lines both sides changed are written between `<<<<<<< workspace`, `=======` and `>>>>>>> ref` markers to resolve with `sandbox_edit_file`, unless `on_conflict` says otherwise: `ref-then-workspace` writes the ref's lines then the lines you added there (a line you added next to a line the ref rewrote), `workspace-then-ref` the other way round, both without markers. A JSON, YAML or TOML file is parsed after the merge: when the merge would leave it invalid or write a key twice (a key both sides added with different values), it is reported in conflict with the reason and the keys named, never as merged cleanly, and the answer lists the structured files it checked under "Parsed after the merge". A binary, or a file one side deleted and the other changed, keeps your version and is reported. The record then names the new ref, so `sandbox_checkout_status` and `create_github_commit(from_checkout=...)` show only your changes on top of it. A rebase is applied once: called again when the checkout already sits on the ref (a call replayed after an interruption), it writes nothing and says so. A checkout narrowed with `sub_paths` keeps the branch's changes outside them: the files the branch changes elsewhere (a backend file of a frontend checkout) are brought into the checkout, merged with the ref and listed as "Brought in from the branch", so a later `add_paths` never writes the ref's version over them; when one cannot be read the rebase is refused with their names and nothing is written.
- **Large rebases in the background**: `sandbox_checkout_rebase(checkout, ref, background=true)` answers a `run_id` at once and rebases while the agent goes on; `sandbox_checkout_rebase(checkout, run_id=...)` waits for its answer. A repeat of the same rebase while it runs (a resumed turn) answers that job, so a rebase is applied once; a rebase whose worker stopped is reported as lost and started again safely.

`materialize_repository`, `sandbox_checkout_diff` and `sandbox_checkout_rebase` read content through an integration like the download tools they use, so when tool approvals are on for an agent they ask for approval; the other `sandbox_*` tools follow `code_interpreter`.

## Getting content out without passing it through the conversation

The reverse path costs the same: a file the sandbox wrote used to become a conversation file (a download card in the chat) before a tool could commit or upload it. Two arguments avoid that:

- **`workspace_path`**: the tools that take a file of the conversation by `file_id` (the GitHub commit tools today; an integration's upload or import tool can offer it too) accept a workspace path instead. The file's bytes are read on the server and handed to the tool for that call only: no conversation file, no download, nothing listed in the files of the conversation. Give one of `file_id` or `workspace_path`, not both. A `create_github_commit` write of a file inside a `materialize_repository` checkout is checked against the branch: when the branch moved past the checkout and changed that file since, both changes are merged line by line, or the commit is refused with the overlapping lines named; the branch's change is never written over.
- **Merging a branch** (GitHub): `merge_github_branch(repo, branch, from_ref)` merges `from_ref` (default: the default branch) into `branch` server-side, without a pull request; GitHub builds the merge commit. On a conflict nothing is merged and the answer names the paths changed on both sides since the merge base, with the refs to read them at, and the next call settles them with `resolutions` (below). The default branch is refused.
- **Resolving a conflicting merge** (GitHub): call `merge_github_branch` again with `resolutions`, one entry per path the conflict answer named: `{path, keep: "branch"}` or `{path, keep: "ref"}` takes one side in the overlapping hunks only, every non-overlapping change of both sides in that file being kept (in a JSON object file such as a translation catalogue, by key: the keys both sides changed take that side and every key either side added is kept; a binary, a delete against a change or a file too large for the line merge keeps that side's whole file, and the answer says so), `{path, content}` writes a merged text, and `{path, workspace_path}` writes a file of the sandbox workspace (for example a checkout brought onto the ref with `sandbox_checkout_rebase`, its conflict markers settled with `sandbox_edit_file`). Everything is checked before the first write: a path left without a resolution, a resolution of a path the answer did not name, an executable file, a symbolic link or a submodule, or a single file over the 5 MB commit cap writes nothing, and the refusal names each file with its size. The merge then lands in commits GitHub builds and signs, so a branch requiring signed commits accepts them: commits giving each resolved path the ref's version, the merge itself, then commits writing the resolved contents. Each step is split into as many signed commits as the 5 MB cap of one commit needs, so four large translation catalogues conflicting at once still merge. A path both sides changed the same way is listed apart and needs no resolution. When GitHub still refuses the merge (a conflict on a path the compare did not list), the first commits are undone by signed commits and the answer says so. The answer lists how each resolution was applied (the overlapping hunks taken from which side) and ends with `Final head: <sha>`, the last commit the call wrote: read CI on that commit, never on an intermediate one; the `Outcome:` line of an error answer reads the branch again until it shows that commit. `manage_github_pr action=update_branch` refused on a conflict answers the same list of paths and the `merge_github_branch` call that settles them.
- **A merge cut midway** (GitHub): when a `merge_github_branch` call with `resolutions` is stopped after its "Take <ref>'s version of N conflicting files before the merge" commits and before the merge (a restart of the platform, for example), the next call moves the branch back before those commits first, then resolves every conflicting path from both sides again, so no file is left at the ref's version by accident. The answer names the commits it dropped. When the branch cannot be moved back (someone pushed on it meanwhile), nothing is merged and the answer says so.
- **Rebasing a branch** (GitHub, true rebase): `rebase_github_branch(repo, branch, expected_head, onto)` replays each commit of `branch` since its merge base with `onto` (default: the default branch), oldest first, on top of `onto`. Each replayed commit is built and signed by GitHub and keeps its message; its original author is named in a `Co-authored-by` trailer and the commit it came from in a `Rebased-from` trailer. Once every commit is replayed, the branch moves in one step, and only while it still points at `expected_head` (force with lease): a branch that moved since you read it is refused and nothing is written. A conflicting commit stops the replay before anything of it is written; the answer names the commit and each overlapping hunk, and the call made again with `resolutions` (`{commit, path, keep: "onto" | "commit" | "both"}` or `{commit, path, content}`) goes on from that commit, never replaying one twice. `max_commits` (default 40) splits a long branch over several calls. For a branch stacked on a branch you just rebased, pass `onto` = the parent branch and `upstream` = the parent's old tip: only the stacked branch's own commits move (`git rebase --onto`).
- **`from_checkout`** on `create_github_commit`: `materialize_repository` leaves a small record beside the tree it checks out (`<directory>/.xtm-checkout`: the repository, the ref, the commit and the hash of every file). `create_github_commit(repo, message, from_checkout="<directory>")` commits exactly what the sandbox changed since: edited and new files are written, removed files are deleted, everything else is left alone; `paths` narrows it to some files or directories, new files included (a new file named in `paths` is committed even outside the checked-out sub-paths), and the result names any path under which nothing changed; a file under a named path that an earlier, wider checkout left and nobody edited is not counted as new. Without `paths`, a file changed outside the checked-out sub-paths refuses the whole commit, nothing written, so a commit never leaves part of your work behind: name the sub-paths and that file in `paths` to commit it, or the sub-paths alone to leave it out. An unchanged checkout commits nothing, and a checkout of another repository is refused. A change set larger than the 5 MB or the 100 files one commit may carry (the four i18n catalogs together, or a sweep over 115 files, say) lands in the same call as several consecutive signed commits, each under the cap, smallest files first so the code and the tests come before the large files; the result lists every commit. The commits are made on a short-lived scratch branch named `tmp/commit-batch/<creation time>-<tip>-<token>` (never a product branch: it is deleted as soon as the call ends, a failed or cancelled call included, and the next split on the repository deletes any such branch left over for more than a day) and the target branch moves once, to the last of them, so it never points at a partial change set and CI never starts on one. If one of them fails, or the branch was pushed to meanwhile, the branch is not moved and the whole change set is still a change of the checkout. A single file over 5 MB is refused. When the branch is no longer at the checkout's commit (someone pushed, or the branch was cut from a newer main), each file the commit carries that the branch also changed since is merged line by line with the branch's version instead of written over it, and the workspace file is brought to the merged text; if both changed the same lines, nothing is committed and the result names the overlapping hunks and the `sandbox_checkout_rebase` call to run. A deletion of a file the branch already removed is dropped. After the commit, the record moves to the new commit and branch, as a commit moves `HEAD` in git: `sandbox_checkout_status` is clean again, the next `from_checkout` commit carries only what changed since, and a file committed outside the checked-out sub-paths is tracked from then on. The record is a plain workspace file: it is listed, removed with the tree, and replaced by the next checkout.
- **Editing a repository file without the sandbox** (GitHub): an entry of `create_github_commit`'s `files` may give `edits` instead of `content` or `file_id`: `{path, edits: [{find, replace, replace_all?}]}`. The edits are applied server-side to the file as it is at the branch tip, with the contract of `sandbox_edit_file`: each `find` must exist and be unique unless `replace_all`, the edits apply in order, and a `find` absent or not unique refuses the whole commit, naming it, with the branch unchanged. The commit is the usual one, built and signed by GitHub, and may mix edited files with full contents and deletions; the result carries the diff of each edited file. Only an existing UTF-8 text file can be edited this way; changing one line no longer needs the whole file resent or a sandbox round trip.
- **Editing an issue or pull request body in place** (GitHub): `update_github_issue` and `update_github_pr` take `edits` (`[{find, replace, replace_all?}]`) instead of `body`. The edits apply to the body as GitHub stores it at write time, with the same contract (each `find` exists and is unique unless `replace_all`, nothing written unless every edit applies), and the answer is the body's diff, so ticking one checklist line of a long tracking issue never sends or reads the whole body. `expect_updated_at` (the `updated_at` you read) refuses the write when the issue or pull request changed since, with `edits` or a whole `body`. `get_github_issue(include_body=true)` reads a body window only; `include_comments=true` reads the comments whole.
- **Signed commits and executable files** (GitHub): `create_github_commit` lets GitHub build and sign the commit, so a branch that requires signed commits accepts it. An existing file keeps its mode: editing a script that is already executable is still a signed commit, and the script stays executable. Only a change of mode (a new executable file, `executable: true` on a plain file, `executable: false` on a script, a renamed script) is committed through another API, and that commit is not signed; the answer says so and names the file.
- **Moving a branch** (GitHub): `manage_github_ref(action="update_branch", branch, sha)` moves a branch to a commit as a fast-forward; a move that would drop commits needs `force=true`. Whatever `force` says, a move that leaves an open pull request of that branch with nothing ahead of its base is refused: GitHub closes such a pull request by itself and it cannot be reopened. To bring the base into a pull request's branch use `manage_github_pr(action="update_branch")`; to change the branch, add a commit with `create_github_commit`.
- **Creating a branch at a commit** (GitHub): `create_github_branch(repo, branch, from_branch)` takes a branch name or a commit SHA in `from_branch`. A branch of that name is used first, exactly as before; when none exists and the value is 4 to 40 hexadecimal characters, it is resolved as a commit (a short SHA must be unambiguous) and the branch is created at that commit, the answer naming the ref and the full SHA. So a branch can be cut at the commit a checkout records in `.xtm-checkout`. A value that is neither answers `Branch or commit not found: <value>` and nothing is created. Without `from_branch` the branch starts on the repository's default branch, read from the repository (never a fixed `main`: a repository whose default is `master` may keep a stale `main`); the answer names the base branch and its SHA, and warns when a named base is not the default branch. `manage_github_ref(action="create_tag")` without `sha` or `from_ref` tags the default branch the same way.
- **History of a checkout** (GitHub): a checkout carries no `.git`, so history is read server-side. `get_github_blame(repo, path, ref, start_line, end_line)` answers, for each range of lines, the commit that last changed it (short SHA, author, date, subject), at most 400 lines per call with the next `start_line` named when more remains; `compare_github_commits(repo, base, head)` names the merge base of the two refs, the base a merge or a `sandbox_checkout_rebase` starts from.

## Running a repository's own checks

A checked-out repository needs nothing added to it: the platform reads its checks from what it already has. Its own CI workflows first (`.github/workflows/`: the commands they run to install, lint, type-check, test and build, in the directory they run them in, with the plain-text `env:` values the workflow, the job and the step set, such as the profile variables a `dbt parse` reads, and `${{ env.NAME }}` resolved from those values; a value written as any other expression (`${{ secrets.X }}`, `${{ github.workspace }}`) is never copied, and the run's answer names those variables so a placeholder can be passed with `sandbox_run_command`'s `env` (variables for one run over the check's own; the runner's variables cannot be set); the runner's own variables (`PATH`, `HOME`, `GITHUB_*`, `RUNNER_*`) are left out; release and deploy jobs are left out), then its manifests (`package.json` with yarn, pnpm or npm; a pnpm repository runs the pnpm release it pins in `packageManager` or, failing that, in `engines.pnpm` (an exact version or the highest one satisfying a range), named in each check's description; `pyproject.toml` with uv, Poetry or pip requirements, `pom.xml` and Gradle, `Cargo.toml`, `dbt_project.yml`) and its `Makefile`. Each check is named after its stack and kind, prefixed by its directory (`front:node-unit`, `client:python-lint`), and the list says where each command came from; the databases and brokers its CI and compose files start are listed beside them. A repository whose CI runs its tests through one script per project (`bash run_test.sh <project>/tests/test-requirements.txt`, as a connectors monorepo does) gets one `<project>/tests:python-test` check per test requirements file: it runs that script from the repository root as CI does, in a throwaway git repository where only that project counts as changed, and reports the JUnit results; nothing the run creates stays in the checkout. A narrow checkout of one project keeps the script and the in-repository package its requirements install from (`#subdirectory=`). Calling `sandbox_run_command(checkout="<directory>")` without a check returns that list as a normal answer (not an error), with each check's directory, sandbox image and report, and the services the checkout declares; it is an error only when the checkout has no check at all. A repository can instead declare its checks in `.xtm-one/checks.toml` at its root (one command each, no shell, with the sandbox image that carries the tool and the report it writes): that declaration then replaces the detection. Writing such a file into a checkout in your workspace is the intended way to run a command the detection does not name: it runs in the same container, image list, time limit and network policy as a detected check, and is committed only if you commit it. `sandbox_run_command(checkout="<directory>", check="<name>", args=[...])` runs one of them in a sandbox container with the workspace mounted, and answers with the exit code, the duration, the findings of a JUnit or SARIF report (file, line, rule, message, bounded), a head and tail of the output, and the directory under `workspace/.xtm/runs/` that holds the whole output. What the command wrote in the checkout (a formatted file, a generated artefact) is saved back to the workspace; what it built in the container (`node_modules`, caches) stays there for the next command.

A Node package whose `test` script runs a wrapper of its own that collects every test file (`node test/run.mjs`) also gets a `node-unit-file` check when a loader such as `test/register.mjs` sits beside the wrapper: it runs the Node test runner on the files given as `args` only, so one test file runs in seconds instead of the whole suite.

A repository that holds GitHub Actions workflows or composite actions (`action.yml`) also gets an `actions-lint` check, even when it declares its own checks in `.xtm-one/checks.toml`: every file is parsed as YAML and its shape checked (a workflow's `on` and `jobs`, a composite action's steps with exactly one of `run` and `uses`, and `shell` beside `run`), the workflows are linted with `actionlint` (with the repository's `.github/actionlint.yaml` when it has one, for custom runner labels; a checkout narrowed to a workflow keeps that file beside it), and the shell of every `run:` block that runs on bash is syntax-checked with `bash -n`, each error reported with its file and line. Pass file paths as args to check only those files, or `affected=true` to check the workflow and action files the checkout changed.

The container holds no credential. On a sandbox without network, the images an administrator configures carry the repository's locked dependencies, and a check that tries to install something fails; where the administrator configures toolchain images (a stack's build tools without any repository's dependencies) and lets the sandbox reach the package registries, they are used first and a detected install check fetches the dependencies. A check that is neither declared nor detected is refused, with the list of those that are; an administrator can allow arbitrary commands for the platform (`CODE_INTERPRETER_COMMAND_ALLOW_ARGV`). Every checkout also has a built-in `script` check (unless the repository declares one of that name): its first argument is one file of the workspace (`.py` run with Python, `.mjs`, `.cjs`, `.js`, `.ts` or `.mts` run with Node), the others are the script's own arguments; it runs with the checkout root as working directory, or with the directory of the checkout the call names in `cwd` (a module script that reads files relative to its own package), on the image of the nearest check of the file's directory with that directory's dependencies installed and the same Python version its checks use, so a one-off reproduction script reads the checkout's dependencies without allowing arbitrary commands. A file outside the workspace is refused. The tool is offered on the OpenSandbox backend only.

An agent may edit a file and run a check in the same step: the command waits (at most a minute) for the workspace writes of that step to land before it reads the workspace, so it always tests the edited code, and its answer says when it waited.

To verify a change without picking test files by hand, call `sandbox_run_command` with the unit test check and `affected=true`: it reads what the checkout's changes touch (the functions and classes on the changed lines, the string keys they add or remove, a Python module's import path), finds the test files under the check's directory that name one of them (a function or class of a changed Python module counts only in a test file that imports that module, so a common name does not pull unrelated tests; a string key counts only in a test that quotes it, and only when it is distinctive: a JSON-schema keyword such as `description` or `properties`, or a short key without an underscore such as `sources`, is set aside and named; a name that more than a quarter of the test files carry, such as a shared fixture, is set aside and named), adds the test files you changed, and runs the check on those files only. On a checkout limited to some sub_paths, the answer also names the files a run looked for outside them (the tests failing on those are not runnable in this checkout, not regressions) and the files it wrote outside them (stray writes, never committed). A pytest check runs its affected selection with `--continue-on-collection-errors`: a selected test file that cannot even be imported in a narrow checkout (it reads a fixture outside the sub_paths at import) is named not runnable in this checkout, the other selected files still run, and the answer gives their own pass or fail count without it. Tests that fail on the same missing file are shown as one finding for that file, with the count of the others. The answer starts with what was selected and why; nothing runs when the checkout has no change or no test names what changed.

A command that lasts longer than one tool call (a real `npm ci`, `pip install` or full test suite) keeps running in its container: the call answers `running` with a `run_id` and the output so far, and calling `sandbox_run_command` again with that `run_id` waits for its end and answers the exit code, the output, the report and the workspace changes as usual. With `background: true` the call does not wait at all: it answers `running` within about a second with the `run_id` and the first lines, so the agent goes on working while the command runs. With a `run_id` and `stop: true`, the command is ended at once with every process it started, and the answer is its result marked as stopped, with what it printed and wrote until then. An install whose lockfiles did not change since it succeeded in the same container is answered from that container at once, marked `cached`, as long as what it installed (its `node_modules` or `.venv` state) is still in the container; a lockfile change, or dependencies gone from the container, runs it again, and the answer says which file was missing. A check that fails in a Node project whose dependencies are not installed in its container says so and names the install check to run first. The first command on an image the platform has not started yet for the workspace can find its container still starting (a large image being pulled): the call then answers that the container is starting and that nothing ran, and the same call a minute later runs the command in it. A container runs one command at a time: the same check asked again while it runs (a turn resumed after a restart that did not know its `run_id`) answers that command as a call with its `run_id` would, and a different command answers, without failing, that the container is busy and which `run_id` to wait for. When a turn is resumed after a restart, its resume note lists the sandbox commands its interrupted part left running, with their `run_id`s, so it waits on them instead of starting them again. A resumed turn that repeats the exact call its interrupted part had made is never a second execution either: while the command still runs, the repeat waits for that same run; once it ended, the repeat is answered with its saved result. A `run_id` whose command already ended answers its saved result (exit code and last output, from `.xtm/runs/<id>/`); a `run_id` whose container went with the restart starts the same command again once in a new container (its install first when the container has no dependencies) and answers that new run's result, its first line naming the lost run and the new `run_id`; with `stop: true`, or polled again afterwards, it answers without failing that the run is `lost`.

XTM One's own repository declares `backend-lint`, `backend-types`, `backend-dead-code`, `backend-unit`, `backend-tripwires`, `backend-snapshots`, `frontend-install`, `frontend-types`, `frontend-e2e-types` (the end-to-end specs, as CI types them), `frontend-lint`, `frontend-i18n` (the translation tables, validated as CI does), `frontend-unit` and `frontend-unit-update`. `frontend-unit-update` runs the test files given as args with `vitest --update=all` and `ARCHITECTURE_FIXTURE=write`, so a deliberate change to what a test pins (a vitest snapshot, the architecture fixtures the backend's Chromium tests draw) is rewritten in the checkout and reviewed with `sandbox_checkout_diff`. `backend-snapshots` regenerates the generated snapshots of the tools that skip approval in the checkout after a tool is added or renamed, so they are reviewed as a diff rather than edited by hand (`args=["--check"]` only verifies them).

A check whose directory has an install check (a check of the same directory and image named `install` or ending `-install`; without one, the install of the nearest enclosing directory on the same image, so a package check of a Yarn, npm or pnpm workspace such as `packages/x:node-unit` binds the root `node-install`) runs that install first, in the same call, when the container has no installed dependencies there or the lockfiles changed since the last install: the answer starts with a line naming the install and its duration, and the next call skips it. A check that needs no dependencies declares `install_first = false` in `.xtm-one/checks.toml`.

Once a pull request is open, its review threads are the other check a merge waits on: `list_github_pr_review_threads(repo, number)` lists the unresolved ones (thread id, file and line, first comment, last replier; `state=resolved` or `all` for the others). GitHub pages review threads by 100: the tool follows the cursor through every page before it states a count, so the unresolved and resolved counts cover the whole pull request; when paging stops early (a later page fails, or the cap of 50 pages) the first line reads `PARTIAL, N of M threads read`, the counts cover the threads read only, and the answer never says there is no unresolved thread. `manage_github_pr_review_thread(repo, number, thread_id, action="reply_and_resolve", body)` answers one and resolves it in one call (`reply`, `resolve` and `unresolve` alone too). A reply posted while the account holds a pending (unsubmitted) review on the pull request would join that review and stay unseen by everyone else: the tool reads the reply's state back and answers an error naming that review, and `reply_and_resolve` resolves nothing. The tool never submits the review itself, since that would publish everything in it (other drafts, its body): submit or discard it on GitHub deliberately. The listing names any pending review of the account. Several replies to one pull request issued in the same tool round are posted one after another (GitHub attached concurrent replies to a pending review), so answering every thread in one round is safe.

## Running the product from a checkout: services

The same file can declare how the repository runs, in `[service.<name>]` tables: the command that starts it, the port it listens on, the path that answers once it is up, the sandbox image, its environment, the services it needs started first and the repository paths it reads (`needs`). A service started on a checkout made with `sub_paths` that lacks one of those paths is refused before anything starts, with the missing paths and the `materialize_repository(path="<directory>", add_paths=[...])` call that adds them. `sandbox_start_service(checkout="<directory>", service="<name>")` starts it in a sandbox container of its own, from the files of the workspace, waits until it answers and returns a `service_id` and a `preview_url` that the browser tool and `web_fetch` open. `sandbox_service_status` says whether it still answers, `sandbox_service_logs` returns the last lines of its output (with `pattern`, only the lines matching that regular expression, e.g. `pattern="seeded|not seeded"`, and how many matched; a line that repeats is shown once with its count, `(x5)`, and a very long line is cut), `sandbox_stop_service` stops it.

The preview URL opens with the browser tool and reads with `web_fetch` for as long as the service runs: the platform recognises the preview of a service an agent started and adds what the sandbox server asks for itself, so no key is ever typed or shown. Any other address of the sandbox server stays refused.

A file the running application serves behind its sign-in (a PDF datasheet, a CSV export) is read back with the browser tool's `download` action: the page itself fetches the URL, with its cookies and, when the application keeps a bearer token in the page, the request headers an optional `expression` computes there (the token is never shown to the agent). A file served only from a POST route (an export that takes its options as a JSON body) is fetched with `method: "POST"` and `body`, a JSON text sent as `application/json`; a read-only browser profile refuses a POST. The response is kept as a file of the conversation or run, up to 25 MB; a PDF answers its page count, `read_file_content` reads its text and `render_source_pages` shows its pages. The URL is held to the same policy as a navigation.

A service has the network policy and the absence of credentials of every sandbox. It stops when the agent stops it, or at the lifetime its declaration gives (one hour by default) after the last call on it. The tools are offered with `sandbox_run_command`, when the sandbox backend is OpenSandbox.

### The xtm-one lab

The xtm-one repository declares `[service.lab]`: `sandbox_start_service(checkout="<directory>", service="lab")` starts the whole product from the checkout (its database, cache, object store and a stub model, the backend with its migrations, then the frontend) and answers a preview URL once the frontend is up and the lab has seeded its sample data and printed `lab up` (its `ready_log`), so the first `sandbox_service_logs` call already shows the signed-in session URL and the seeded pages; about three and a half minutes on a pod that has nothing cached. Sign in as `lab@filigran.io` with the password `lab-only-password`; those credentials exist only inside that lab. The lab runs without a licence, as XTM One, so every screen opens. If it does not become ready, `sandbox_service_logs` shows why: while it waits for the backend, the lab prints the backend's readiness answer every 15 seconds. A service whose process ends before it is ready (a seed refused, a script error) is answered at once with its exit code and its last 20 lines, not at the end of its readiness window. A lab that takes longer to start than one tool call allows (a product such as OpenCTI can need fifteen minutes) is answered `starting` after about three minutes, with its `service_id`, its preview URL and the state of each of its services; `background=true` answers that way as soon as the checkout is in the lab. Follow it with `sandbox_service_status` (each service: ready, starting, or exited with its code) and `sandbox_service_logs`, which reads a service's output while it starts. Calling `sandbox_start_service` again with the same arguments waits for that same lab, never a second one.

## The pull request title rule

The same file can declare the title a pull request must have, in a `[pull_request]` table: `title_pattern` (a regular expression), `title_rule` (the rule in words) and `title_example`. `create_github_pr`, and `update_github_pr` when it changes the title, read it on the branch the pull request targets and refuse a title that does not match before anything is written, with the rule and the example in the answer, so the title is fixed at once instead of after a failed CI check. A repository without the table is checked against the title check of its own CI: the workflows whose file name holds "title" or "convention", a shell step testing the title against a pattern, or the shared `pr-title-check` action (`type(scope?)!?: description (#123)`, a `(deps)` title exempt). Two checks that run on alternative conditions (a private issue, for instance) each accept the title, with a note naming the condition. No such check found: the result says `Title not checked`; a workflow that cannot be read never blocks the write. The xtm-one repository declares the rule of its *Validate PR Title* workflow: `type(scope?): description`.

## The issue title rule

An `[issue]` table with the same three keys declares the title an issue must have. `create_github_issue`, and `update_github_issue` when it changes the title, read it on the default branch and refuse a title that does not match before anything is written, with the rule and the example in the answer. A repository without the table creates and renames issues as before; the pull request rule never applies to an issue.

## Closing keywords that point at a pull request

GitHub closes whatever a closing keyword names (`closes #12`, `fix owner/repo#34`, `resolves` and a pull request URL) when the pull request carrying it merges. Aimed at an issue, that is how `Closes #12` works. Aimed at another pull request, it closes that pull request without a word. `create_github_pr`, `update_github_pr` and `merge_github_pr` therefore refuse a title, body or squash commit message whose closing keyword points at a pull request, in the same repository or another, and write nothing; the answer names each reference. Reword it (`see`, `needs`, `awaiting`) and call again. A reference to an issue, or one that cannot be read, is left as it is.

`create_github_pr` can assign the pull request in the same call: pass `assignees` (GitHub logins). The answer names who GitHub assigned, and any login it could not assign (someone without access to the repository). If the assignment fails, the pull request is still created and the answer says so.

`merge_github_pr` also checks the messages of the pull request's own commits whenever they land on the base branch: a squash without a commit message (GitHub then builds the message from the commits), a merge commit or a rebase. The refusal names the commit and the reference; pass a reworded `commit_message` to a squash, or amend the commit. A squash with your own commit message does not read the commits.

`manage_github_pr` with `ready_for_review` or `convert_to_draft` is safe to call once when GitHub has a bad moment: on a transient answer ("Something went wrong", a 502, 503 or 504, a timeout) it reads the pull request back, answers applied when the pull request is already in the state you asked for, and otherwise tries again, at most three times in about 20 seconds. A refusal such as a missing permission is answered at once.

## A review verdict that asks for changes

When an agent review loop posts its verdict on a pull request (a comment whose first line reads `UX-LOOP round=N verdict=...`), `merge_github_pr` and `manage_github_pr` (`ready_for_review`, `enable_automerge`) refuse while the newest verdict is not `APPROVE`. The refusal names the round, the verdict and the comment; a newer round with `verdict=APPROVE` releases it. A pull request without such a comment is never blocked.

## Keeping variables: session=true

`code_interpreter(session=true)` runs the code in the conversation's kernel, a long-lived Python process where variables and imports persist from one `session=true` call to the next. `reset=true` starts a new one. The result says which kernel ran: a new one, the same one as before, or a new one because the previous kernel was gone.

A kernel is gone, and its variables with it, when it was idle past its timeout (15 minutes by default), when a cell ran past the call's timeout, or when the call reached another server process (local sandbox). Files under `workspace/` are kept either way, so keep in files what a later step must not lose.

## Packages

When the administrator has set a package allow-list, `code_interpreter(packages=["name==version"])` installs packages into `workspace/.venv` before the code runs, where they stay. The server downloads the package from the configured index, as a wheel checked against the index's sha256, and the sandbox stays offline. Only listed packages (and their listed dependencies) are installed; the result names what was installed, what already was, and what was not and why.

## Quotas and clean-up

- A workspace holds at most 2 GB and 20,000 files by default. A call that would go past either saves nothing it wrote under `workspace/` that time, and the result says so. Remove files and run it again.
- A workspace is deleted when its conversation is archived or deleted, when its assignment run is deleted, and after 7 days without use.

## When a turn is interrupted

A deployment or a restart can stop the server while an agent is working. The tool calls the turn completed are kept: a graceful stop lets the call in flight finish, keeps every completed result, and marks the turn `interrupted_resumable`. **Continue where you left off** (or any message) starts a turn that receives those calls and their results in order, followed by a short note that names the last completed call, how many results were replayed, what the workspace holds, and which long results were shortened for the replay and the file each one is kept whole in. The agent continues from there instead of starting again, and the workspace is exactly as the interrupted turn left it.

When the platform itself stopped the turn (a deployment, a scale-in, a restart or the recycling of a web worker), the agent resumes the same message by itself once XTM One is back, from the same completed calls and the same workspace, as long as the message makes progress between two stops (up to twenty automatic resumes; three stops in a row without a new completed tool call end them). A turn stopped for any other reason waits for you: nothing restarts it on its own.
