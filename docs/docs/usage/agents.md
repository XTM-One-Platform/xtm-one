# Agents

Agents are the main assistants in XTM One. Each one is configured for a particular role, team, or workflow.

## What an agent is for

Use an agent when you want a more focused assistant than the `General Assistant`. An agent can answer questions in a specific domain, use selected tools and integrations, search one or more knowledge bases, hand work to other agents, and run background tasks automatically.

An agent works on its own through assignments: a trigger (a schedule, an event, a webhook) and a prompt. See [Assignments and triggers](assignments.md).

## The list page

Choose `Agents` from the left sidebar to open the list. You can browse all visible agents, search, filter by visibility or tag, import an agent from a file, and — if your role allows it — create a new one (see [Create an agent](create-agent.md)). Each card is a quick summary: the agent's status, what is attached to it, and whether it is company-managed or shared. Some cards also offer quick actions such as opening a chat or enabling and disabling the agent.

Click the star on an agent's card or row to make it a favorite. Favorites are pinned to the top of the list in both views, above everything else and whichever column you sort by, so the two or three agents you actually work with stay one glance away in a long fleet. The choice is yours alone — it is stored on your account, follows you to any browser, and changes nothing for anyone else. Click the star again to remove it. Filters still come first: a favorite that does not match your search or tag filter is not shown.

The toggle at the right of the filter row switches between the card grid and a sortable list. The list view is the better choice once you manage more than a handful of agents: it puts status, model, assignment count, and attached resources in sortable columns so you can answer questions like "which agents run which model?" by scanning one column. See [grid and list views](resources/index.md#grid-and-list-views) for how sorting and persistence work.

Not every visible agent is editable. Company-managed agents are shared broadly and often read-only for standard users, shared agents come from a group or another owner, and built-in agents are typically read-only. If you open an agent and cannot change it, the page is behaving as designed for your access level.

Connecting a resource to an agent or to one of its assignments (an MCP server, an integration or a channel bot) is limited to the ones you can see yourself, and a save that adds another one is refused; what the agent or the assignment already names stays in place when you save, whoever connected it. An agent shared with you runs with what its owner connected to it - their MCP servers, custom tools, knowledge bases, channel bots and integrations - in its assignment runs, and in your chats too with one exception, integrations: in a chat, an integration you cannot see, or whose owner's connected account is not shared with you, is not used for you (see [Sharing an OAuth integration](resources/integrations.md#sharing-an-oauth-integration)). Your own or a company-wide integration of the same service takes its place when the agent resolves one for you; otherwise a note under the answer names the integration (by its service only when it is not shared with you) and says why, and the agent is told too, so it can say what it cannot do.

## The detail page

Click an agent card to open its detail page. The header gives you direct actions — `Chat with Agent`, `Duplicate`, `Export`, enable or disable, and delete when you can manage the agent. If the agent is designed mainly for assignments, the chat button still works but XTM One warns that it is not optimized for conversation.

The page is organized into tabs (some appear only when your role can see them):

- `Overview` is the best first stop: a quick understanding of what the agent does and what is attached to it, without reading the full configuration. Its `Coming up` card lists what the agent will do next and when: your scheduled work items on it and the next runs of its scheduled assignments, with actions to cancel or reschedule a scheduled item, and `Open in Schedule` to see them in the fleet's schedule.
- `Configuration` is how the agent is set up — persona and instructions, tools and integrations, knowledge and memory, handovers, channels, and intent bindings. For most users this is a reading page; editing is usually reserved for admins. The `Intent Bindings` card is what makes the agent available inside OpenCTI, OpenAEV, or OpenCRQ; see [`Intents`](../administration/intents.md). A built-in tool the agent carries but this deployment has switched off (the code interpreter, Runners, a feature not enabled here) is shown greyed as `Unavailable`: it does nothing until an administrator enables it, and while editing you can remove it from the agent, not add it. On a company-managed agent that carries `Work Items` or `Shared State`, the same card holds its `Coordination access`: which agents can read and change the company-managed work items it creates and the shared state it owns (see [`Work history`](work-history.md)).
- The `Model` picker in `Configuration` chooses what the agent runs on: `Platform default`, one model, or `Platform routing model`. The routing model is the lightweight model an administrator sets in `Settings > AI Models` (the one that already evaluates routing conditions); pick it for an agent that takes a narrow, repeated decision - classify, judge, route - that a small model handles well and for less. The agent then follows whatever routing model the administrator configures. When none is configured, the agent runs on the platform default model, and the `Configuration` and `Overview` tabs say so. Choosing a model of its own takes the agent off the routing model.
- `Value` shows what the agent returns, then what it may spend. Its `ROI` section comes first: hours saved, net value and review rate over the last 7, 30 or 90 days, how they are computed, and what the agent delivered from chat. Below it, the run budget caps what one run of the agent may spend — money, tokens, tool calls or time — and can let a run that reaches its cost ceiling finish on a cheaper model instead of stopping. Lowering a limit is open to anyone who can edit the agent; raising one above the platform's own budget is an administrator's decision. See [`Run budgets`](agent-budgets.md). The tab was called `Budget` and the ROI sat on `Overview` before; links to either open `Value`.
- `Versioning` lists every version of the persona and of the tracked settings, to compare them and roll back.
- `Memory` shows the agent's longer-term memory, where authorized users can search it, review its health, and run maintenance. An entry that no longer holds is marked `Superseded` (see [What the agent remembers](#what-the-agent-remembers)).
- `Observability` shows how the agent performs over the recent period: traces over 7 days, average cost and latency, error rate, average feedback and quota consumed, then its cost over 30 days, its recent traces, its models, and the feedback it received. It is shown to the people who can see the agent's chats.
- `Chats` shows conversations associated with the agent, to review or reopen context.
- `Delegations` shows work the agent sent to or received from other agents, useful for understanding how handovers behaved.
- `Feedback` gathers every thumbs up and thumbs down given to the agent's work — its chat answers, its assignment runs, its background tasks and the answers it gave when another agent consulted it — with the comments people left, filterable by kind of work and by rating. When feedback criteria are defined (`Settings > Quality`), it also shows the agent's weighted score and, per criterion, the average, the distribution and the last 30 days. It is shown to the people who can manage the agent.
- `Activity` is the agent's run history — review recent executions and spot failures.

## What the agent remembers

An agent with persistent memory stores what it learns (`store_memory`), searches it (`search_memory`), and is given the most relevant entries at the start of each conversation and assignment run.

Some entries describe something that changes: what a document's footer says, how many slides a deck has, the status of a ticket. The agent stores those as **state** entries, named by the object they describe (a subject such as `doc:<id>` or `presentation:<id>`). When it records a newer observation of the same subject, that one replaces the older:

- The older entry is kept and still found by a search, listed after the current ones and marked `Superseded`. It is never given to the agent as context again.
- A state entry reaches the agent dated (`as of <date>, verify live`), with a reminder that it is a past observation and that the live document, deck or ticket is the one to check before acting on it.
- The agent can also retire an entry that no longer holds (`invalidate_memory`), by its id or by its subject. A retired entry is kept and marked `Superseded` too.

Entries that name no subject behave as they always did. In a conversation, the agent replaces and retires only the memory it keeps for you: the memory it shares with every user of the agent stays as it is for the others, and the newer entry is the one you are shown.

## What an assignment or a roster may name

An assignment whose trigger listens to an integration reads that integration's events with its credentials, so when you save it, the integration it names must be one you can see: yours, one shared with you or one of your groups, or a company-wide one. Admins may name any. Otherwise the save is refused with the same answer whether the integration exists or not. Editing anything else, or saving the trigger again with the integration it already names, is never refused, even if that integration is no longer visible to you. The agent builder tools apply the same rule; when strict admin access for agent tools is on, an administrator's agent may name only the integrations the administrator sees as their own, shared with them or company-wide.

An agent you create from a template gets the template's assignments and default skills (see [Create an agent](create-agent.md)). A template trigger that names an integration you cannot see is created without it, and then listens to the new agent's own integration of that provider.

The agents you let an agent hand work items to (the `Work Items` tool's roster) follow the same rule: you can add only agents you can see (admins may add any), and the ones already in the roster stay when you save.

## Duplicate and export

Two header actions are easy to overlook. `Duplicate` creates a private copy you can adapt without changing the original, and `Export` downloads the agent so it can be stored, shared, or imported elsewhere. This is especially helpful when your organization uses standard company-managed agents but you need a private variation.

The copy is yours, so it keeps only what you could connect to an agent of your own. When you copy an agent someone else owns, the integrations, MCP servers, knowledge bases, custom tools, skills, prompts, handover agents, work-item owner agents and channel bots you cannot use are left out, in the copied assignments too, and the confirmation says how many of each kind were left out and why (the `warnings` of the duplicate response). Everything you can use is copied as it is, a personal OAuth integration shared with you included. Whoever copies, an assignment trigger that listens to an integration you cannot see loses it: the copied trigger then listens to the copy's own integration of that provider. The original agent is not changed: it keeps running with everything its owner connected. Copied assignments start disabled.

`Export` asks which format you want. The **XTM One native bundle** (default, JSON) carries everything — assignments, handover routing, memory settings, prompts, skills and variables — so use it for backups and for moving an agent between XTM One instances. **Microsoft AgentSchema** (YAML) is an open, cross-vendor agent definition that other agent platforms can read, and only what that specification can express goes into its standard fields.

Choosing AgentSchema shows you exactly which of your agent's settings will not be included as standard fields — handover, memory tiers, assignments, integration bindings, prompts and skills among them — before the file is created. Nothing on that list is thrown away: it is preserved in an XTM One section of the document's metadata, so re-importing the same file into XTM One restores everything, while other platforms ignore that section.

Exporting everything is for the people who can manage the agent: its owner, someone it is shared with for configuration, and administrators. If you can see an agent but not manage it, such as a company-managed agent or one shared with you as read-only, `Export` gives you what its [AI Catalog](ai-catalog.md) download carries instead, in either format. A credential passed to an MCP server as an argument or in its URL is masked. Custom tools that are not company-managed are left out, unless the agent is published with its personal tools included. A company-managed tool, MCP server, skill or prompt restricted to a group you are not in is left out too, and variables come without their values. The file still imports: re-enter the masked values and fill in the variables afterwards.

## Read-only integrations

An integration bound to an agent can be made read-only for that agent: the agent keeps the tools that read from it (list, get, search, download) and loses the ones that change it (create, update, delete, send, post, transition, upload and any tool whose action is not clearly a read). The setting is enforced when the agent runs, not by an instruction in its prompt: a write tool of a read-only integration is not offered to the agent, and a call that names it anyway is refused. Removing the integration from the agent removes its read-only mark. The same integration can stay writable on another agent.

A per-user integration (bound under **Advanced: Dynamic integrations (per-user)** on the agent's Tooling tab, resolved to each user's own connection at run time) has the same switch: turn on **Read-only** on its card and the agent keeps only that provider's read tools, whichever user's connection it resolves to. The card then shows a Read-only badge outside edit mode. Turning the per-user binding off clears the switch. The API and the `create_agent` / `update_agent` tools set it as `integration_template_read_only`, a list of provider keys that must also be in `integration_template_bindings`.

## Building agents from a conversation

An agent with the agent builder tools (the `General Assistant`, or an agent given the `agent_builder` built-in tool) can build agents for you in chat:

- `update_agent`, `create_agent` and `duplicate_agent` accept every built-in group the agent settings offer (`files`, `web`, `cti`, `design`, `coordination`, `observability` and the others), plus the former ids they replaced. `builtin_tool_ids` follows `binding_mode`: `replace` (the default) makes the list the agent's set, `add` adds groups and keeps the others, `remove` takes groups out. The answer names the groups added and removed.
- `create_agent` sets up a complete agent in one call, with everything `update_agent` can change: model and temperature, built-in tools, memory, tool scoping and deny list, read-only integrations, handover and channels. If one setting is refused, no agent is created. The answer lists every integration bound to the new agent with its name, so you can check none is missing.
- `clone_agent` copies an agent you can see, with integrations, knowledge bases and built-in tools added or removed and the persona replaced or extended. It never copies assignments, sharing, intent bindings or the `builtin` tag (a copy is not a built-in agent), and it shows what differs from the original, naming each intent binding of the original the copy does not have. With `copy_memory` it also copies the original's persistent memory you may read, with its dates, types and subjects, and says how many entries it copied; the memory of a company-managed agent is copied by an administrator only. `Duplicate` takes the same option as `copy_memory=true` on `POST /api/v1/agents/{id}/duplicate`.
- `list_agent_intent_bindings`, `bind_agent_to_intent` and `unbind_agent_from_intent` read and change the intents an agent answers, which decide where a connected platform (OpenCTI, OpenAEV) offers it, for example in a playbook's AI agent step. See [`Intents`](../administration/intents.md).
- `edit_opencti_playbook_graph` refuses a node whose configuration names a value outside the choices the component offers, such as an AI agent the playbook step does not list, and says which values are allowed: nothing is saved.
- `list_integration_tools` shows which tools of an integration read and which write. For OpenAPI integrations (`provider: "openapi"`) it lists the operations imported from each integration's spec, grouped by integration, with each tool's HTTP method and path; `integration_id` lists one integration.
- `update_integration` shares an integration with groups: members can use it (bind it to their agents and run it) or also manage it. An agent shared with a group only uses, for each member, the integrations that member may use.
- `update_integration` with `is_company_managed` makes an integration company-managed (`true`, visible platform-wide) or private again (`false`), as the integration's edit page does. Only an admin can change it. A field the tool does not take is refused by name, so nothing is ignored without a word.
- `update_agent` also shares an agent, with groups or with named people outside any group: "share this agent with alice@example.com and marie@example.com, read-only" gives them the agent in their agent list and lets them chat with it; `config` lets them edit it too. Only people who already have an account here can be named - an address no account matches is refused, and nobody is invited. Removing someone takes their access away at once. The answer, and `get_agent`, say who the agent is shared with: each group by name with its number of members, each person by name and email, with their level of access. A company-managed agent is already open to everyone and is not shared this way. As for a group, a person the agent is shared with only uses, in their own chats, the integrations they may use themselves.
- `update_agent` and `update_assignment` change part of a long text without resending it: `mode` `edit` (a list of exact find/replace operations; nothing changes unless every one applies, and a text found more than once needs `replace_all`), `append`, `replace_section` or `insert_after` (a Markdown section named by its heading), on the `field` named: `persona` (the default), `guardrails` or `description` for an agent, `prompt` (the default), `activation_prompt` or `description` for an assignment. The answer shows the diff of the field, not the text. Without a `mode` the field passed is the whole new text, as before. An agent's persona and guardrails changes are versioned like any other edit.
- `list_groups` lists the groups of the platform with their number of members, so the agent can find the group to share with and say who an existing share reaches. Administrators' agents can also list the members of each group.
- `get_agent` takes an optional `sections` list to read part of an agent's configuration: `behavior`, `model`, `tools`, `handover`, `memory`, `human_in_the_loop`, `channels`, `sharing`, `guardrails`, `intents`, `persona`. The name, id and slug are always shown; without `sections` the whole configuration comes back, persona included. Checking one setting across many agents (for example `["tools"]` for their tool scoping) no longer reads every persona. An unknown section name is refused with the list of valid ones.
- `get_assignment` takes an optional `sections` list as well: `gates`, `activation_prompt`, `prompt`, `ai_label_prompt`, `human_in_the_loop_prompt`. The name, id, agent, trigger with its configuration and every execution setting are always shown; without `sections` both prompts come back in full as before. Checking a trigger or a tool check (`["gates"]`) no longer reads the prompts. An unknown section name is refused with the list of valid ones. For a schedule it also shows the next run, the last fire (`Last triggered`), the last time it was enabled again (`Schedule resumed at`) and, when the schedule was off over a cron slot, that `Skipped slot` (a resume never catches up). `list_runs` accepts the status `queued`: a delivery waiting for its busy assignment.
- `run_agent_once` runs an agent once on a prompt and returns its answer, so you can try a new agent without leaving an assignment behind. The run is listed with the agent's runs (trigger `run_once`, under the calling run when there is one) and has its own sandbox workspace: a file the agent writes under `workspace/` with code_interpreter stays for its next call, and a `$workspace:` reference to it resolves. Pass `file_ids` (up to 30 files you own) to attach them to the prompt as you would in a chat message: the agent sees the images and can read every file.
- `import_agent_memory` recreates persistent memory entries on an agent you can manage, up to 200 per call, for a migration or a restore. Each entry keeps its date, type, subject and the user it belongs to, and a state entry replaces the earlier one on the same subject. Entries belonging to another person need the agent's owner (or an administrator, on a company-managed agent).

An agent given the `agent_builder` built-in tool can also hand background tasks to any agent you own, the ones it just created included, without adding them to its handover agents first. It can consult one of them too (`consult_agent`), for example to test a desk it built: the consulted agent answers with its own handover agents available, as it would in one of its runs, so you see whether its handover works without scheduling anything. An agent consulted through its handover configuration can consult its own `Consult` handover agents in turn, nothing more (see [Agentic flow](agentic-flow.md)). Other agents only reach the agents set up in their handover configuration, and when a handover is not possible the answer says why - for an agent set up with another handover type, it names the tool that reaches it. The `General Assistant` tries an agent it just built with `run_agent_once`.

`consult_agent` and `spawn_background_task` take an optional `output_schema` (a JSON Schema object, 50 KB at most) that fixes the shape of that one answer: the agent consulted or delegated to answers one JSON object valid against it, whatever output format it is set to, and the background task's result keeps that JSON whole. A schema that is not valid JSON Schema refuses the call before anything runs, naming the problem. Without it, each agent answers in its own output format.

The agent called must accept it: **Accept a format requested by the caller** (Output format section of its configuration; `accept_caller_output_format` in the API and the agent tools) is off by default for every agent. Off, a call that passes `output_schema` to that agent is refused before it runs, and the caller can call again without it; on, the caller's schema wins for that call. A call without `output_schema` is the same either way.

## When an assignment runs: gates and event filters

Creating assignments and choosing their triggers is covered in [Assignments and triggers](assignments.md). An assignment can be kept from running when there is nothing to do, at three levels, each cheaper than the next:

- **Event filters** (integration-event triggers). On the trigger card, an email trigger can be limited to senders (allowed and blocked addresses or domains), to mail sent to you or where you are in Cc, to a subject, a folder, and can skip automated mail (no-reply senders, newsletters and mailing lists, delivery reports, calendar responses). Teams triggers can leave out some authors and, for chats, name the chats to follow; a calendar trigger can follow only created, updated or cancelled events; a flag trigger only some flag statuses. A webhook-delivered event (GitHub, LinkedIn, HubSpot, a generic provider) is filtered on its payload: each filter key names a field of the provider's body, a dotted path reaches a nested one and a list means any of its values, for example `{"action": "completed", "workflow_run.conclusion": "failure", "repository.full_name": ["org/repo"]}` on a GitHub `workflow_run` trigger. A key also takes an operator object: `{"sender.login": {"ne": "me", "not_in": ["dependabot[bot]"]}}`, `{"workflow_run.head_branch": {"starts_with": ["feat/", "fix/"]}}`, `{"sender.login": {"ends_with": "[bot]"}}`, `contains`, `matches` (a regular expression the whole value must match), `in`, `not_in`, `eq` and `exists` (true or false); and the filter takes `all`, `any` and `not`, for example `{"not": {"sender.login": {"ends_with": "[bot]"}}}`. On GitHub `workflow_run`, `check_suite`, `check_run`, `status` and `push` triggers, `enriched.pull_request` is the open pull request the commit belongs to, read from GitHub with the integration: `{"enriched.pull_request.user.login": "me"}` keeps the CI results of the pull requests you opened, whoever pushed, and `{"enriched.pull_request": {"exists": false}}` the commits with no open pull request. On `workflow_run`, `check_suite`, `check_run` and `status` triggers, `enriched.head.checks` is the check state of the commit (`total`, `completed`, `pending`, `failed`, `skipped`, `neutral`, `all_completed`, `all_green` and `names`), read again for every completion so it is never older than the event: `{"action": "completed", "workflow_run.conclusion": "success", "enriched.head.checks.all_green": true}` wakes only on the last check to finish green on a commit, whatever its workflow name, so a new or renamed workflow needs no filter change; an earlier result on that commit is counted as `enriched.head.checks.all_green does not match the filter`. A filter with an unknown operator is refused when the assignment is saved. An event the filter drops creates no run at all and is counted: the trigger card shows `Events filtered: N`, and `get_assignment` lists why.
- **Tool check** (on the prompt card, before the gate prompt). The platform calls one read-only tool of the agent and checks its result, with no AI model involved: for example "run only when this agent has an open work item" (`list_work_items` with `owner_agent_id` `{{agent.id}}` and `open_only`, runs when the result is not empty), "only when a shared state entry is active" (`get_shared_state`, runs when `$.status` is one of `active`), or "only when a Board meeting is in the calendar within 7 days" (`list_microsoft_calendar_events` with `days` 7, runs when `$.subject` contains `Board`). When the check fails, the run is listed as skipped (`Skipped: gate check ...`) with zero tokens and does not count as an agentic action. When the check chains further checks (`also`), the skip says which one failed: `(check 2 of 2: get_shared_state {"key": "..."})`. If a check cannot be evaluated (the agent does not have the tool, the tool fails, or it answers no structured result), the run goes ahead; the run lists the checks passed over under `gate_checks_not_evaluated` in its trigger context, and the assignment counts them in its dropped-event reasons (`gate check 2 not evaluated: <tool>`). The check runs once, when the run starts: a run resumed after a restart continues without checking again, a lease the run holds itself never counts as held by another run, and a run that already holds a lease is never skipped.
- **Fleet scope of work items**. An agent that belongs to a fleet reads the work items of its fleet: `list_work_items` returns the items owned, created or claimed by a member of the fleet (the orchestrator included) and the unowned items filed in the fleet's workspace, and its first line names the scope and the fleet. `scope` `own` keeps the items the agent owns or created; `scope` `all` reads every item the user can see and is for an administrator's agent only. `get_work_item` answers "not in your fleet" for an item outside it (an administrator's agent still reads it) and `claim_work_item` refuses it. An agent in no fleet reads as before. A tool check on `list_work_items` takes the same `scope` argument. Work item events and the work-item inbox trigger follow the item's owner, creator and holder, unchanged.
- **Completion time of work items**. Every work item records when it reached done or cancelled (`completed_at`, cleared when it is reopened; empty on an item that finished before this field existed). `list_work_items` shows it, with `claimed_at`, on each item; `completed_from` and `completed_to` (ISO-8601) keep the items completed in that window, `updated_from` the items written since a time, and `sort` `completed_desc` lists the newest completions first (`created_desc` stays the default, `updated_desc` is the third order). The first line of the answer names the sort in force. An audit of the last day's completions is then one listing: `list_work_items(status="done,cancelled", completed_from=<now minus 24 h>, sort="completed_desc")`. The REST list (`GET /api/v1/work-items`) and its count take the same parameters.
- **Text filter and compact listing of work items**. `list_work_items` `query` keeps the items whose title or correlation key contains a text, case-insensitive and literal (`_` and `%` are not wildcards), combined with the other filters and the same scope; the first line of the answer names it. `compact` `true` answers one line per item (id, correlation key, status, title) without the description preview. Checking whether an item about a tool already exists is then one short listing: `list_work_items(open_only=true, query="list_work_items", compact=true)`.
- **Fleet scope of shared state**. `list_shared_state` takes the same `scope` argument with the same defaults: `fleet` lists the entries owned by a member of the fleet and the unowned entries filed in the fleet's workspace, `own` the entries the agent owns, `all` every entry the user can see (an administrator's agent only). Its first line names the scope. `get_shared_state` and `set_shared_state` on an exact key are unchanged. A fleet's Operations tab (Work Items, Shared State) lists the same population as scope `fleet`, so its counts equal what the fleet's agents read.
- **Filtering a shared state entry without knowing its layout**. `get_shared_state` with `where_json` (for example `{"number": 12}`) and no `path`, or a `path` the entry does not hold, searches every list of the entry, starting at the shallowest level that holds one (an entry keeping its lists under an object of objects, such as `pools.<pool>.open`, is searched there), and, when none matches, the lists one level down; it answers the matching items grouped by the path they were found under, with the count per path. A filter that matches nothing is a normal answer, not an error: 0 matches and the lists searched (a dedupe read that finds nothing is the expected case). An entry that holds no list at all also answers 0 matches, with its top-level keys to pass as `path`. Only a `path` the entry does not hold, combined with no match anywhere, is an error naming the lists searched. A correct `path` reads as before.
- **Reading a nested part of a shared state entry**. `get_shared_state` takes a dot-separated `path` (for example `pools.alpha` or `pools.alpha.open`), the same form `set_shared_state` writes, and answers that part alone. A top-level key is looked up first, so a key that holds a dot reads as before; a segment that does not exist is refused naming the first missing segment and the keys at the nearest prefix. With `where_json`, a `path` that reaches an object searches the lists under it (from the shallowest level that holds one, then one level deeper when none matches) and answers the matches grouped by sub-path (`pools.alpha.open`) with the count per list, 0 matches naming the lists searched; a `path` that reaches a list filters that list.
- **Changing a nested list of a shared state entry**. `set_shared_state` with a `path` and `append_json`, `remove_json`, `update_json`, `keep_last_json` or `fold_json` applies those list changes to the lists of the object under the path (for example `path` `pools.alpha` with `remove_json` `{"open": [{"number": 12}]}` and `append_json` `{"merged": [{"number": 12}]}`), on the server under the entry's lock, so two agents moving items in the same nested object never lose each other's change. `value_json` is not needed; `archive_key` applies to top-level lists only.
- **Projecting and paging a shared state list**. With a `path` that reaches a list, or with `where_json`, `get_shared_state` takes `fields` (keep only these fields of each item, for example `["id", "count"]`) and an item page `item_offset` / `item_limit`. The page counts items, not characters, so it never cuts an item in half and stays on the same items while other runs append at the end of the list; the answer names `items N to M of T` and the `item_offset` of the next page. On a `where_json` read with no list `path`, the page runs over the matches in the order they are shown, still grouped by path. Without a list `path` or `where_json` these arguments are refused.
- **Counting a shared state list or work items per value**. `get_shared_state` with a list `path` and `group_by` (a field of the items, dotted allowed, for example `status` or `meta.class`) answers one line per value with its count instead of the items, after `where_json` when given, plus a `(missing)` line for the items without the field; with `fields`, each line also names the first field's value of up to 20 of its items. `list_work_items` with `group_by` (`status`, `owner_agent_id`, `priority` or `key_prefix`, the correlation key up to its first `:`) answers the count per value for the same filters and scope, no item bodies. Both answers state the read time.
- **Exporting a large shared state entry to the sandbox workspace**. When the run has a sandbox workspace, `get_shared_state` takes `to_workspace_path` like the file and fetch tools: the selection (the whole value, or what `path`, `where_json`, `fields` and `item_offset` / `item_limit` select) is written whole as JSON at that path, with no character window, header or notes, and the answer gives only the path, size and sha256. An entry of several hundred thousand characters is then analysed in the code interpreter in one call instead of being paged through the conversation. A key or a path that does not exist writes nothing and says so.
- **Writing a large shared state change from the sandbox workspace**. When the run has a sandbox workspace, `set_shared_state` also takes `from_workspace_path`: a JSON file of the workspace holding the write's arguments, for example `{"append_json": {"gaps": [...]}, "unique_by_json": {"gaps": "id"}}`. The file is read on the server and applied exactly as the same arguments sent inline (the same list rules and the same compact read-back), so a write of hundreds of list items never passes through the conversation. A file that is missing, not JSON or names an unknown argument writes nothing and says why.
- **Matching shared state list items by condition**. A field of a `where_json` match, of a `remove_json` match and of an `update_json` `match` may hold an operator object instead of a value, with the operators of a trigger's payload filter: `eq`, `ne`, `in`, `not_in`, `starts_with`, `ends_with`, `contains` (a substring of a text, an element of a list), `matches` (a whole-value regular expression) and `exists`. `{"retest_status": {"starts_with": "PASS"}}` selects every item whose status begins with `PASS`, `{"retest": {"exists": false}}` every item without a `retest` field (`null` counts as absent; `ne`, `not_in` and `exists: false` hold on an item without the field). Several operators, and several fields, must all hold. A plain value still means equality. A misspelled operator, an object mixing operators with other keys or a bad operand is refused with the list of operators, and nothing is written. So one `remove_json` call drops every closed entry of a long list, and its read-back counts them, without reading the list first.
- **A shared state entry that tracks a pull request ends with it**. When a pull request is merged or closed, the platform resolves every active shared state entry whose value names it: a number under `pr`, `pr_number` or `pull_request`, and the same repository under `repository` or `repo`, or named in the key before the branch (a branch lease `dev:branch-lock:owner/name:fix/12-x` holding `{"pr": 12}`, so two repositories with the same branch name keep separate leases), or, when no repository is named, the pull request's branch under `branch` or as the last `:` part of the key (an older lease `dev:branch-lock:fix/12-x`). An entry that names no pull request number is resolved too when it names the same repository and the pull request's branch is its `branch` or the last `:` part of its key (a lease taken before the pull request was opened, such as `{"repository": "owner/name", "issue": 11}`). The entry keeps its value and gets a note naming the pull request and how it ended; writing to it again makes it active again. When the closing notification is not signed, the platform first checks on the code host that the pull request really closed.
- **How large a shared state entry may grow, and what is purged**. A value is measured in characters of its JSON. Over the soft limit (`SHARED_STATE_VALUE_SOFT_LIMIT_CHARS`, 32,768 by default) a write lands and its read-back carries a size warning naming the largest top-level keys; over the hard limit (`SHARED_STATE_VALUE_HARD_LIMIT_CHARS`, 65,536 by default) a write is refused unless it makes the value smaller, so an oversized entry can always be compacted. A write that makes a top-level list longer than `SHARED_STATE_LIST_MAX_ITEMS` (500 by default) is refused the same way, with the fix named (`keep_last_json`, `remove_json`, or another key). `0` disables each limit. The hourly sweep compacts an entry written before these limits: it drops its oldest list items until it fits, with a note giving the count. `list_shared_state` shows each entry's size and longest list, and tags `OVERSIZE` the entries over the soft limit next to `STALE`; the Operations > Shared State tab shows the same flag as an Oversized chip beside Stale, and the hover card of a row gives its size and longest list. Resolved entries are deleted once resolved for `SHARED_STATE_RESOLVED_RETENTION_DAYS` (30 by default). Active entries are never deleted, but the items an `archive_key` write moves into an archive are stamped and dropped once older than `SHARED_STATE_ARCHIVE_RETENTION_DAYS` (14 by default, `0` keeps them), an archive is capped at the same list length and drops its oldest items past it, an archive is never archived into another archive (the write is refused), and an archive write that would pass the hard limit drops the oldest items the archive already held, across all its lists, never the items that write archives; when even that cannot make room, the archive write and the source write are both refused, so nothing is lost. Keep a history list bounded with `keep_last_json` and `archive_key`, and keep totals in counters rather than in the list.
- **What ends a shared state entry**. Every fleet, built-in or custom, gets the same lifecycle: an entry created by `set_shared_state(hold="take")` is a lease, resolved when its hold is released, by its holder or by the scheduler once the holder run ended (`lease=false` keeps a record that also carries a hold); `work_item_id` links the entry to a work item and the hourly sweep resolves it once that item is done or cancelled; `expires_at` resolves it at that date; `terminal_condition` names what ends it in words. Staleness reads how long the value has stood still: a note alone does not count as a change, and an entry past its `expires_at` is stale. `list_shared_state` shows each entry's value age and what ends it (`ends: not set` when nothing does).
- **Shared state hygiene per fleet**. A fleet's health (`GET /fleets/{id}/health`, field `shared_state_hygiene`) counts the shared state entries of the fleet you can read: `oversize` (over the soft limit), `stale`, `orphaned_leases` (held by a run that ended) and `terminal_linked` (linked to a work item that ended). The hourly sweep fixes the last two by itself. When a fleet still has oversize or stale entries after it, the sweep files one low-priority work item on the fleet's orchestrator, with correlation key `shared-state-hygiene:<fleet id>`. It is never duplicated while it stays open. This applies to every fleet, built-in or custom, whose orchestrator is enabled.
- **Patching several list items with one patch**. In `set_shared_state` `update_json`, `match` may be a list of objects: an item matching any of them is patched, so tagging many entries is one patch (for example `{"gaps": {"match": [{"id": "a"}, {"id": "b"}], "set": {"family": "f"}}}`). Each object of the list must match at least one item, or nothing is written and the refusal names the object that matched nothing.
- **Dropping and archiving fields of list items**. An `update_json` patch takes `unset`, a list of field names removed from every matched item (`{"entries": {"match": {"key": "k"}, "unset": ["retest_result"]}}`); an absent field changes nothing. With `archive_key`, the values the unset removes are first appended to the list `entries` of that key, one object per matched item (`source_key`, `list`, `match`, `archived_at`, `fields`), and the source is written only after the archive, so a long history leaves a live ledger without being read into the context or lost.
- **A retention policy that rolls a list instead of refusing the write**. `retention_json` stores a policy on the key, applied by the server on every later write: `{"keep_last": 200, "max_chars": 60000, "archive_key": "metrics-archive"}` (at least one of `keep_last` and `max_chars`; `lists` names the top-level lists it governs, every list by default; `{}` clears it). When a write would pass the bound, or the hard limit, the oldest items of the lists move to `archive_key` before the write, so an append at the cap lands instead of being refused; the items the call appends are never rolled out. The archive is written first, and an archive at its own cap drops its oldest entries instead of refusing. Without `archive_key` the rolled items are dropped, and a write that would roll more items out of a list than it appends to it is refused unless `confirm_trim` is true (a policy set on a list already over its bound would otherwise drop its oldest items in one call). The read-back names the policy and what rolled (`rolled by retention to ...: runs 4`). Add `archive_when`, a match in the `where_json` grammar or a list of them, to roll only finished items: `{"max_chars": 60000, "archive_key": "gaps-archive", "archive_when": {"state": {"in": ["merged", "closed"]}}}` moves the oldest matching items first and never an open one; `keep_last_json` on that list trims only matching items too (`N open kept` in the read-back). When finished items alone cannot bring the list under its bound, the write still lands and the read-back warns that open items were kept past the cap (the hard limit still refuses). A policy without `archive_when` rolls by age as before and the read-back warns that it did. `get_shared_state` and every write show `retention usage` (the size against `max_chars`) and warn from 80% of a cap. A write also states the value's size against the platform's soft and hard limits, and warns when `archive_when` matches no item while the value is over `max_chars` (nothing can roll: the rule names a value no item carries). Bound one item with `max_item_chars`: `{"max_item_chars": 600, "overflow_key": "gaps-overflow"}` moves the longest fields of any item over 600 characters to `gaps-overflow`, under `{list: {item id: {field: value}}}`, and the item keeps a pointer `overflow://gaps-overflow/gaps/<id>#<field>`; `item_key` names the identifying field (default `id`). Without `overflow_key` an item over the cap is refused with its size. `overflow_fields` (`["evidence", "runs"]`, with `overflow_key`) moves those fields from every item whatever its size. Setting the policy compacts the items already stored in the same call; the read-back names how many items moved fields. An `update_json` `append` on a field that moved (`{"match": {"id": "g1"}, "increment": {"count": 1}, "append": {"runs": ["r9"]}}`) goes through its pointer: the items absent from the list stored in the overflow key are appended there, the item keeps its pointer and the rest of the patch applies; the overflow is written first, and the read-back names the items added.
- **Overflow pointers resolved on read**. `get_shared_state` with `resolve_overflow: true` answers the selection with every `overflow://` pointer replaced by the field it names, read from its overflow key (a pointer whose key, item or field is gone stays a pointer and is counted).
- **Duplicate list items merged on the server**. `fold_json` names, per list, the identifying field(s): `{"gaps": "id"}` or `{"gaps": {"by": "id", "sum": ["count"]}}`. After the appends, every object item sharing those values merges into the first one: list fields are unioned in order, the `sum` fields are added, a field the first item lacks is taken from the later one, and the read-back counts `N folded`.
- **Moving list items to an archive, removing top-level keys**. `archive_key` also works with `remove_json` and `keep_last_json`: the items they drop are appended whole to the list of the same name under the archive key, before the source write, in one call (`{"runs": [...]}` moves to the archive's `runs`). If the list changes between the archive and the write, the write is refused, so an item never leaves without its copy. `unset_keys` (`["a", "b"]`) removes top-level keys of the value in the same atomic write; a missing key is not an error, and the read-back names the keys removed. With `path`, `value_json` may be any JSON value (`"text"`, `3`, `[1, 2]`), written at that sub-key.
- **Gate prompt**. One short AI call that answers YES or NO on the event; it runs after the tool check when both are set.

Microsoft triggers (new email, Teams messages and replies, Teams chat messages, calendar changes, email flag changes) are delivered within seconds when your platform is reachable from the internet over https: XTM One subscribes to Microsoft Graph change notifications for them. A Teams trigger needs its channels selected (a chat trigger its chat ids) to be subscribed. Otherwise, or if Microsoft refuses or drops the subscription, the trigger is checked every 5 minutes as before, and no event is lost or run twice when it switches from one mode to the other. The agent builder's `get_assignment` says which mode an assignment uses, when it was last checked or notified, and how many events its filter dropped.

## Work an agent's queue: the work item trigger

An assignment with the **Work item** trigger is its agent's inbox: it picks up the open work items the agent owns, as soon as they become available, and runs one assignment run per item. Each item is completed when its run succeeds and returns to the queue when it fails.

- Items are taken by priority (urgent, high, medium, low), then the earliest due date, then the oldest.
- By default the inbox works on one item at a time. Set **Items in parallel** in the trigger editor of the assignment page (`max_concurrent_runs` in the trigger configuration, a whole number from 1 to 10) to let it work on up to that many items in parallel, each in its own run; the trigger card then shows "up to N items in parallel". When a run ends, the next item starts at once.
- `correlation_prefix` and `priority_min` limit the inbox to some items.
- `express_lane` keeps short, time-critical items from waiting behind long runs: `{"correlation_prefixes": ["review-verdict:"], "slots": 2}` lets the items whose correlation key starts with one of the prefixes (1 to 10 of them) start up to that many runs (1 to 5) above `max_concurrent_runs`. Every other item still waits for a regular slot. It is set through the API or the agent builder, and the trigger editor keeps it on save.

The key is also set through the REST API or the agent builder (`create_assignment` / `update_assignment`).

### Programs: a status read live

A program is a work item keyed `program:<slug>`; its `payload.program` may give the owner, the target date, the exit criterion and the next step owed to a person. The items keyed `program:<slug>/...`, and any item whose `payload.program_key` names the program, are its children. Creating the root is the only step: the program then shows in `list_programs`. An existing item joins a program with `update_work_item(program_key="program:<slug>")`, its correlation key unchanged so its owner's inbox still routes it; `program_key=""` takes it out.

`get_program_status(program)` computes the status at the time of the call: each child with its status, owner, blockers and due date, each pull request the items name with its state, merge and CI read from the code host, the next steps, and what is owed to a person with its age. Each line says when it was read and which item or pull request it came from. Nothing is copied, so a completed item or a merged pull request shows at the next call. A next step owed to a person with no dated work item is flagged.

Every fleet orchestrator, the built-in fleets' included, carries `list_programs` and `get_program_status`: making an agent the orchestrator of a fleet (on the fleet page, from a fleet spec or a template) adds them to its Coordination tools, its other tools unchanged.

### Fleet health: findings and one advisory

Every fleet orchestrator also carries `get_fleet_health` and the built-in skills **Fleet health advisory** and **Fleet design and operations** (the suggested practices of a fleet, see [Good practices for a fleet](agentic-flow.md#good-practices-for-a-fleet)). Making an agent the orchestrator adds them; fleets that existed before get them at the next platform start.

`get_fleet_health(fleet_id)` reads the fleet at the time of the call, with no model call, and returns the member verdicts plus one finding per problem: a failing or disabled member, a disabled member that still owns open items, an assignment that failed its last 3 runs, a schedule silent for 14 days, an item still claimed by a run that ended, an item past its due date, a blocked item that names nothing it waits for, a shared-state entry over the size limit, a handover into a member the fleet does not expose, and a member whose tokens of the day are over 3 times its own daily average. Each finding carries the ids it was read from, its fix (`auto` or `owner`) and a recommendation. Its structured result has `healthy`, so an assignment gate (`{"path": "$.healthy", "in": [false]}`) skips a healthy fleet at zero tokens.

With `apply_safe_fixes=true` the read also applies the only safe fix: it releases the claims of runs that ended, through the platform's own claim sweep. The skill tells the orchestrator to apply that fix only, then to send the fleet's owner one advisory with a recommendation and the evidence for each remaining finding, deduplicated from one check to the next, and nothing when the fleet is healthy.

**Dismiss a finding the owner accepts.** Each finding has an id (for example `cost_spike:3f9a1c0b2e`), built from the fleet, the kind and all of its evidence, so new evidence raises the finding again under a new id. When a finding needs nothing, for example a cost spike on a platform where cost is not a concern or a schedule left silent on purpose, a person who can manage the fleet dismisses it with `dismiss_fleet_health_findings(fleet_id, ids, reason)`. Built-in fleets are included. A reason is required, and the platform records who dismissed the finding and when. An id can also be a kind such as `cost_spike`: that dismisses every finding of the kind on this fleet, whatever its evidence. `until` (a date) makes the dismissal lapse. Dismissed findings no longer count: a fleet whose only findings are dismissed reads healthy, and the weekly check stays skipped. `get_fleet_health` lists them under **Dismissed**. `action="restore"` brings back the ids you pass, or all of them when you pass none. Dismissals belong to one fleet only. Documentation suggestions keep their own `list_fleet_doc_findings`.

Each orchestrator also gets one automation, **Weekly fleet health check** (Mondays 07:00 UTC). It is created switched off: **Enable fleet** lists it with the fleet's other automations, and it runs as the person who enables it. Its activation check calls `get_fleet_health` before any model call and lets the run go ahead only when the fleet has a finding, so a healthy fleet costs no tokens. Making another agent the orchestrator moves the check to it; a check that never ran is removed from the former orchestrator.

**A fleet with its own health sweep.** Deleting the **Weekly fleet health check** turns it off for that fleet: it is not created again, after a restart either, and the fleet's automations badge no longer counts it. A person who manages the fleet can also set it with `update_fleet` (`health_check`) or `PUT /api/v1/fleets/{id}`: `off` (no check), the id of an assignment of a home member (that assignment is the fleet's health check, and the seeded one is removed), or `default` (the seeded check comes back, switched off). New fleets get the seeded check.

### The automations badge in agent tools

The badge of a fleet (**On**, **Partially on**, **Paused**, **Not set up**) follows one rule in the Fleets list, the home Fleets row, the fleet header and the agent tools, pinned by a test on both sides. `get_fleet` ends with the badge, the count of automations on (`3 of 4 on`) and one line per counted automation that is off: its agent, its name and id, its pause reason (`created_disabled`, `fleet_pause`, `user_toggle`, `panic_stop`, a quarantine) and what switches it on. `get_fleet_health` carries the same block in its structured result, under `automations`. A member with no assignment (an agent called only by consult or by a playbook) counts nowhere: it never makes a fleet partially on.

`get_fleet`, `list_fleets` and every `update_fleet` answer state the fleet's autonomy level (`Full human gates (full_gates)`, `Medium (medium)`, `Low (low)`, `Full autonomous (autonomous)`). `update_fleet` lowers it freely; it raises it only for an administrator, in a chat, with `confirm=true`. A refused raise names the condition that failed (not an administrator, an assignment or background run, no chat, `confirm=true` missing), what to do and the level kept; an update to the current level answers `already at` that level; an applied change reads the stored level back.

`set_fleet_automations` answers why a fleet stays partially on: `resume` switches on only what **Pause all** switched off, and when that is nothing it says so and names the automations still off. `action=enable` is **Enable fleet**: without `confirm` it previews the automations it would switch on, with `confirm=true` it switches them on (the seeded ones run as the caller), audited as `fleet_enable`. An automation held by an emergency stop is left as it is. On a built-in fleet, as for pause and resume, only an administrator can do it.

## React to what happens in the platform

An assignment can start when something happens inside XTM One rather than on a schedule: a work item gets a progress note, changes status, is claimed, released or completed; a run fails or ends without finishing while it held work items (for example when the platform restarts); a background task completes or fails; a Video Studio render, scene preview, AI shot or AI music track you requested is ready or failed (`video.render.finished`, `video.scene_preview.finished`, `video.clip.ready`, `video.music.ready` and their `failed` counterparts, with the video, its revision and quality, and the number of findings its checks raised); a new build of the platform is first seen serving (`platform.release.deployed`, once per build, with its `version`, `git_sha` and the build it replaces in `previous_version` and `previous_git_sha`: wait for a deployment with it instead of checking the release history on a schedule; every assignment hears it, whatever its scope); a connected OpenCTI, OpenAEV or OpenCRQ platform reports a new version on its registration heartbeat (`integration.version.changed`, once per platform and upgrade, never on a first registration, with its `provider`, `platform_identifier`, `integration_id`, `previous_version` and `version`: wait for a module upgrade with it instead of reading its version on a schedule; every assignment hears it, whatever its scope; to read a platform's version once, an agent bound to it uses `get_opencti_platform_version`, `get_opencrq_platform_version` or `manage_openaev_settings` with action `version`). Choose the `platform_event` trigger type (from a conversation with the agent builder, or through the API) and name the events in `trigger_config`, for example `{"event": "work_item.note_added", "filter": {"correlation_key": "release:2026"}}`. The agent builder's `list_platform_events` tool lists every event and the fields its filter can name. A filter field takes a value, a list of values (any of them), or an operator: `eq`, `ne`, `in`, `not_in`, `starts_with`, `ends_with`, `contains`, `matches` (a regular expression on the whole value) or `exists`, for example `{"correlation_key": {"starts_with": "mail:"}}`; `all`, `any` and `not` combine filters. A misspelled operator is refused when the trigger or the watch is saved. In the assignment's trigger settings, pick **Platform event**, then the event, optional filters (a field of the event and the value it must have) and, for a single wait, **One-off watch**; the run detail shows the event that started the run. Through the API or the agent builder, add `"once": true` to wait for a single event: the first one that matches starts one run and the subscription ends (save the trigger again to watch for the next one). Add `"expires_at": "2026-11-02T09:00:00Z"` (a date and time with its offset) to stop listening at that time: an event raised after it starts nothing, so a watch that expires without its event never fires.

- The run starts within seconds of the event, with the event in its trigger context (the event name, the work item or run it is about, the note).
- By default the assignment only hears about objects its agent takes part in: the work items it created, owns or holds, the runs and background tasks it started or delegated. An assignment of an agent that belongs to a fleet can set `"scope": "fleet"` to hear the events of every member of that fleet (membership is read when the event is delivered, so adding or removing a member needs no trigger change). An administrator's assignment can set `"scope": "all"` to hear every event.
- Each event starts at most one run per assignment. If a run of the same assignment is already working on that work item, the event is added to the item as a dated note instead of starting a second run.
- The event's content (a note, a title, a task outcome) is written by other agents and is treated as untrusted content by the run.

### Act later on one object: timers

A run that must come back to one object at a given time (a reminder an hour before a meeting, a thread still unanswered after three days) arms a timer instead of keeping a recurring assignment that checks every object. The agent calls `arm_timer` with a `correlation_key` naming the object (for example `schedule:thread-42`), a `due_at` with its UTC offset and an optional `payload`. At that time the platform raises the `timer.due` event, and every assignment of that agent on that event whose filter matches runs once with the payload, for example with the filter `{"correlation_key": {"starts_with": "schedule:"}}`.

- Arming the same `correlation_key` again replaces the earlier timer; `cancel_timer` cancels one and `list_timers` lists them.
- `unless_work_item_id` or `unless_shared_state_key`: the timer never fires if that work item is done or cancelled, or that shared-state entry is resolved, by its due time.
- A timer fires at most once, within a minute of its due time, and is kept in the database: a platform restart between the arm and the due time does not lose it.
- When nothing takes the key (no assignment of the agent on `timer.due`, no task watch and no flow trigger), `arm_timer` still arms the timer but its answer ends with a warning naming the key and the filters the agent's `timer.due` assignments do take. A timer that fires while none of them takes it ends `fired_unheard` in `list_timers` (state `ended`), so a follow-up that no run picked up is visible instead of lost.
- The tools come with the agent's shared state tools; no model is called to arm or fire a timer.

## Importing an agent

The import itself is described in [Create an agent](create-agent.md#import-an-agent-from-a-file); this section explains how the file is read.

You do not have to say what kind of file you are uploading. The platform reads the file, works out whether it is an XTM One bundle or an AgentSchema document, checks it against that format's rules, and only then creates the agent. Both JSON and YAML are accepted.

After a successful import you are told which format was detected, along with anything the platform had to assume about your file or could not resolve here. A tool declared in an AgentSchema document arrives without its code, because the specification describes what a tool takes rather than how it works, so you need to fill in the implementation before enabling it. An MCP server arrives as a placeholder, since no server address or credentials travel in the document. A knowledge base or file-search source may be referenced but not included, in which case you bind the agent to a knowledge base on this instance to restore retrieval.

If the file is neither format, fails its format's rules, or is an AgentSchema document describing a `hosted` or `workflow` agent — kinds XTM One has no equivalent for — the import is refused and the reason names the specific fields or rules that failed. Nothing is created in that case.

Whichever format you import from, integration bindings, knowledge bases and links to other agents are not imported: they belong to the instance the agent came from. Imported assignments always start disabled so nothing runs before you have reviewed it.

A native bundle exported by the agent's owner (or by an administrator, for a company-managed agent) also carries the agent's persistent memory: its current entries, with their dates, types, subjects and the users they belong to. Importing it recreates them on the new agent. An entry belonging to a person who has no account on this instance is left out, and the import says how many. A bundle without memory imports as before. To add memory to an agent that already exists, use `POST /api/v1/agents/{agent_id}/memory` (up to 200 entries per call) or the `import_agent_memory` agent builder tool.

An assignment limited to some of the agent's MCP servers keeps that limit. A server included in the file is mapped onto the copy the import creates, and a server outside the file is kept only if you can already use it on this instance; any other server is removed from the assignment's scope and the import says so. An assignment left with none of its servers runs without MCP tools rather than with every server of the agent.

An assignment's integration setting is never widened on the way in. An assignment set to use no integrations imports the same way, and one limited to specific integrations imports with no integrations at all, because those integrations do not exist here: the import report names it so you can re-select them. An assignment that uses all of the agent's integrations keeps doing so, as does any assignment from a file exported before this setting was carried.

An assignment whose trigger listens to an integration keeps it only if you can already see that integration on this instance (an admin keeps any that exists here). Otherwise the integration is removed from the trigger and the import names the assignment, so you can pick one of your integrations before enabling it.

## Exposing an agent on a messaging platform

An agent answers in web chat by default and nowhere else. To let it work in Slack, Microsoft Teams, WhatsApp, Telegram, Discord, or Google Chat, enable the channel in `Configuration` > `Channels & Bots`, where you choose whether the agent receives messages, publishes messages, or both, and on which channels.

The bot itself is connected once by an administrator. See [Channels and bots](../administration/channels/index.md) for the platform setup and the rules that govern mentions, direct messages, and anonymous users.

An agent can also answer visitors of a website ([Publish an agent on a website](web-widget.md)) and other organizations' agents ([Agent-to-agent (A2A)](resources/agent-to-agent.md)).

## When an agent is disabled

A disabled agent stays visible but does not behave like an active one: it looks dimmed in the list, chat is limited, and assignments do not run normally. If an agent you expected to use is disabled, contact the person who manages that workflow. To keep working in one of its conversations meanwhile, [continue it with another agent](chat.md#continue-a-conversation-with-another-agent).

## Delete an agent

The delete button of an agent's page asks which agent continues its conversations, then deletes the agent and all its assignments. Its conversations are kept, with their whole history:

- **With a successor.** Pick one of your agents in `Continue its conversations with`. The conversations of every person who can use that agent continue with it: the next message there is answered by the successor, which reads the deleted agent's answers labelled with its name. A note `Continued by <agent>` marks the change. A person who cannot use the successor keeps the conversation with no agent, as below.
- **Without one** (`No agent`). The conversations show that their agent was deleted, and each owner continues one with an agent of theirs from its `Conversation options` menu (`Continue with another agent`).

The deleted agent's traces stay until the trace retention removes them: the people who chatted with it, and its owner, still find them in the Trace Explorer, under its last name. An assistant asked to delete an agent (`delete_agent`) can name the successor the same way (`successor_agent_id`).

## When an assignment shows `Emergency stop`

An assignment paused by the [emergency stop](../administration/emergency-stop.md)
shows a red `Emergency stop` badge instead of `Paused`, in the agent's assignment
list and on its own page, with who pressed the stop, when and why. Its on/off
switch is disabled: the assignment comes back when the stop is lifted, not one
at a time.
